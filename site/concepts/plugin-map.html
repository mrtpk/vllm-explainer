All the ways to extend vLLM

IntermediatevLLM conceptsabout 16 min read + 5 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • How vLLM finds and loads plugins Intermediate
  • Python entry points Beginner

In one sentence

vLLM has three kinds of extension points: entry-point groups that vLLM reads, registries that your plugin fills, and config fields that name your class.

The idea#

An extension point is a place where code from outside the vLLM repository can change what vLLM does. Such code is out-of-tree (OOT). vLLM has about twenty extension points. They come in three kinds, and each kind reaches your code in a different way.

  1. Entry-point groups. Your package publishes an entry point under a plugin group, for example vllm.platform_plugins. vLLM finds it with no help from you. There are six groups. The page How vLLM finds and loads plugins explains how and when each process loads them.
  2. Registries. vLLM keeps tables of models, layers, attention backends, quantization methods, connectors and more. A function such as ModelRegistry.register_model adds your class to one table. You call these functions from a general plugin, so that the call runs in every process.
  3. Config hooks. A config field or a CLI flag names your class or your module, for example --scheduler-cls my_pkg.MyScheduler. vLLM imports the name when it needs the class. No entry point is necessary.

The three kinds work together. A typical plugin package publishes one general plugin. Its function calls several register functions. A platform plugin also sets config fields, for example worker_cls, in its check_and_update_config hook.

An everyday comparison. Think of a large office building. The entry-point groups are the front desk: it has a list of named visitors, and it calls each one at a fixed time. The registries are the notice boards on each floor: a visitor pins a card there, and the staff on that floor read it. The config hooks are an order form: you write the name of a contractor, and the building calls that contractor. The comparison stops here. In vLLM each process is its own building with its own notice boards. A card that you pin in the API server is not visible in a worker.

Step 4: which one do I need?#

Start from your goal. Each line names the extension point and the page that explains it.

  • New hardware. Write a platform plugin (vllm.platform_plugins) with a Platform subclass. Set worker_cls in check_and_update_config, and add a general plugin for your custom ops. See Platform plugins and current_platform and The Platform interface.
  • New model architecture. Call ModelRegistry.register_model("MyArch", "my_pkg.model:MyModel") from a general plugin. See Out-of-tree models and the model registry.
  • A faster kernel for one op. Subclass the in-tree CustomOp and decorate it with register_oot. On an out-of-tree platform, an enabled op calls forward_oot (vllm/model_executor/custom_op.py:183, vllm/model_executor/custom_op.py:202-203). See CustomOp, out-of-tree ops and IR op providers.
  • New quantization format. Use @register_quantization_config("my_quant") in a general plugin. See Quantization methods as plugins.
  • A custom HTTP route. Write an endpoint plugin (vllm.endpoint_plugins), and name it in VLLM_PLUGINS. See Plugins in the API server.
  • A custom metrics sink. Publish a StatLoggerBase subclass in vllm.stat_logger_plugins. See Plugins in the API server.
  • KV offload to your storage. Write a KV connector. Register it with KVConnectorFactory.register_connector, or name its module in kv_connector_module_path. See KV connectors.
  • A different scheduling policy. Subclass the scheduler and set --scheduler-cls. See Hooks in the engine core and the workers.

Deep dive#

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Deep dive

Registries live in one process

Each registry is a Python object at module level: a dict or a list in a module or a class. Examples: KVConnectorFactory._registry (vllm/distributed/kv_transfer/kv_connector/factory.py:28), _ATTN_OVERRIDES (vllm/v1/attention/backends/registry.py:344), _CUSTOMIZED_METHOD_TO_QUANT_CONFIG (vllm/model_executor/layers/quantization/__init__.py:58). A spawned child is a new interpreter, so it starts with the built-in entries only. (Derived from the start method, vllm/entrypoints/common/startup.py:147-149.)

So the place of the register call matters:

  1. A general plugin function runs in each process (vllm/v1/engine/core.py:132, vllm/v1/worker/worker_base.py:284). Its register calls reach every registry. This is the normal way.
  2. A platform module can register at import time, or in a hook. The test platform uses a second entry point in vllm.general_plugins to import its custom ops (tests/plugins/vllm_add_dummy_platform/setup.py:10-17).
  3. Code in your own launch script runs only in that process. With vllm serve the workers never see it.

Config hooks do not have this problem. The value is a string in VllmConfig, and each process imports the class itself. For example, a worker resolves worker_cls with resolve_obj_by_qualname (vllm/v1/worker/worker_base.py:293-296).

Worked example. One general plugin function registers a model, a quantization method and a KV connector. You run vllm serve with TP = 2. The function runs 4 times: front end, engine core, worker 0, worker 1. The front end uses the model entry for inspect_model_cls and the quantization entry to make the quantization config object. It uses the connector entry to check the connector class. The engine core uses the connector in the scheduler role. Each worker uses the model entry and the connector entry. It gets the quantization config as an object inside the pickled VllmConfig; Python imports the module of its class by name when it unpickles it. (Derived from the read lines in Step 2. A model registry subprocess, if one runs, is one more process.)

Deep dive

Lazy registration: why many registries store strings

Several registries store a name or a loader, not a class:

  • register_model with a "module:Class" string makes a lazy entry. The docstring says that this avoids "Cannot re-initialize CUDA in forked subprocess" (vllm/model_executor/models/registry.py:1165-1174).
  • The connector factories and the sleep-mode factory store a function that imports the module later (vllm/distributed/kv_transfer/kv_connector/factory.py:36-40, vllm/device_allocator/sleep_mode_backend.py:176-180).
  • The decorator form of ToolParserManager.register_module stores only the module path and the class name (vllm/tool_parsers/abstract_tool_parser.py:352-368).
  • register_backend stores a dotted path (vllm/v1/attention/backends/registry.py:406-418).

The general plugin runs in the front end too, where no model runs. A lazy entry keeps heavy imports (CUDA code, kernels) out of the front end. Only the process that uses the entry imports the module.

What can go wrong#

A name collision stops start-up

The KV and EC connector factories and the sleep-mode factory raise ValueError for a name that exists already. vLLM registers its own connectors when the factory module is imported, for example NixlConnector (vllm/distributed/kv_transfer/kv_connector/factory.py:177-181). Choose a name that vLLM does not use.

  • The registry is empty in a worker. You registered from a launch script or from code that runs only in the front end. Register from a general plugin instead (first deep dive).
  • An allowlist filters your general plugin. VLLM_PLUGINS applies to general plugins too (vllm/plugins/__init__.py:63-64). Then no register call runs, with no error. Use the timeline above with VLLM_PLUGINS=acme_admin to see it.
  • A short parser plugin value is ignored. A value of 3 characters or fewer is not imported (vllm/entrypoints/common/cli_args.py:579). A path that fails to import only writes an ERROR log (vllm/utils/import_utils.py:94-98).
  • A custom scheduler loses async scheduling. vLLM warns: if you subclass Scheduler instead of AsyncScheduler, async scheduling is off and performance drops (vllm/config/scheduler.py:247-253).
  • A worker extension hides a method. If the worker class already has an attribute of the extension, an assert stops start-up (vllm/v1/worker/worker_base.py:310-319).

Why it matters. The right extension point depends on the process that must see your code. An entry-point group or a config hook reaches its process by itself. A registry reaches only the process where your register call ran. Most "it works in the front end but not in the worker" problems come from this difference.

Check yourself#

  1. 1
    What are the three kinds of extension points, and which kind needs a general plugin?
    easy
    Show answer

    Entry-point groups, registries and config hooks. Registries need a general plugin (or another way to run the register call in each process). Each registry is a module-level object of one process. The general plugin runs in every process (vllm/plugins/__init__.py:77-90).

  2. 2
    You want a new HTTP route. Which extension point do you use, and what must you also set?
    easy
    Show answer

    An endpoint plugin in vllm.endpoint_plugins. You must also name it in VLLM_PLUGINS, because endpoint plugins load only when the list names them (vllm/plugins/__init__.py:122-131).

  3. 3
    Your general plugin calls KVConnectorFactory.register_connector("NixlConnector", ...). What happens at start-up?
    medium
    Show answer

    vLLM already registers a connector with this name when the factory module loads (vllm/distributed/kv_transfer/kv_connector/factory.py:177-181). The register function raises ValueError for a name that exists (vllm/distributed/kv_transfer/kv_connector/factory.py:33-34). The plugin function does not catch it, so start-up stops (vllm/plugins/__init__.py:89-90).

  4. 4
    You set --scheduler-cls my_pkg.sched:MySched. Why does it fail, and what is the right form?
    medium
    Show answer

    scheduler_cls is parsed by resolve_obj_by_qualname, which splits at the last dot (vllm/config/scheduler.py:256, vllm/utils/import_utils.py:119-123). The colon form is for register_model. Write my_pkg.sched.MySched.

  5. 5
    You serve with TP = 2. You set kv_connector_module_path and also register a connector with the same class name through a general plugin. Which class runs, and in which processes is it made?
    hard
    Show answer

    The class from kv_connector_module_path: for KV connectors the module path wins over the registry (vllm/distributed/kv_transfer/kv_connector/factory.py:106-108). It is made in the engine core, in the scheduler role (vllm/v1/core/sched/scheduler.py:177-181), and in each of the 2 workers, in the worker role (vllm/distributed/kv_transfer/kv_transfer_state.py:88-92). The front end only gets the class, for config checks (vllm/config/vllm.py:2243). For EC connectors the order is the opposite (vllm/distributed/ec_transfer/ec_connector/factory.py:66-73).

Related pages

  • How vLLM finds and loads pluginsvLLM finds plugins as Python entry points in six groups. Each process of vllm serve loads only the groups that it needs, at its own time. One environment variable, VLLM_PLUGINS, filters five of them.
  • Platform plugins and current_platformEach vLLM process makes one Platform object, current_platform, the first time code reads it. Five built-in detectors and the out-of-tree detectors from vllm.platform_plugins decide its class; one out-of-tree platform wins over the built-in ones.
  • The Platform interfaceThe Platform class is the contract between vLLM and a hardware vendor. Identity attributes describe the device; config hooks change VllmConfig in the front end; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation.
  • Out-of-tree models and the model registryModelRegistry maps the architecture name in config.json to a model class. A plugin adds or replaces an entry with register_model; a "module:Class" string keeps the import lazy, and a cached subprocess inspects the class.
  • CustomOp, out-of-tree ops and IR op providersA CustomOp is a layer with one forward method per platform. It picks one method when it is built - forward_native when disabled, the platform's method when enabled. Plugins replace whole classes with register_oot, and vllm.ir adds a second, per-op provider choice.
  • How vLLM chooses an attention backendEach attention layer asks the selector for a backend class when the worker builds the model. The selector asks current_platform. CUDA validates a priority list for the GPU generation and takes the first valid backend; an explicit --attention-backend is validated alone.
  • Quantization methods as pluginsA quantization method is a QuantizationConfig subclass registered under a name. The front end picks the name from the checkpoint or --quantization and makes one config object; each layer in the worker asks it for a quantize method that makes the weights and runs the forward.
  • KV connectorsA KV connector moves KV cache blocks between vLLM and something outside it. One connector class runs as two objects - a scheduler-side object in the engine core that plans loads and saves, and a worker-side object in each worker that moves the bytes. KVConnectorFactory finds the class by name.
  • Plugins in the API serverFive kinds of plugins act in the API server - endpoint plugins add or replace HTTP routes, IO processor plugins shape pooling input and output, tool and reasoning parser plugins parse model text, LoRA resolvers find unknown adapters, and stat logger plugins receive the metrics of each step.
  • Hooks in the engine core and the workersSeveral extension points of the engine core and the workers are config fields or registries, not entry-point groups - scheduler_cls, worker_cls and worker_extension_cls, logits processors, model loaders, sleep-mode backends and KV cache dtypes. This page shows where each one is read and what your class must do.
