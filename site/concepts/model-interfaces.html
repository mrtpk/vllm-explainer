Model capability protocols (SupportsPP, SupportsLoRA, ...)

AdvancedvLLM conceptsabout 9 min read + 3 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Out-of-tree models and the model registry Intermediate
  • PyTorch for serving: custom ops and torch.compile Intermediate

In one sentence

A model class inherits capability protocols such as SupportsPP; vLLM records them in _ModelInfo and checks them before it starts the workers.

The idea#

vLLM serves hundreds of model classes, and each supports a different set of features. Pipeline parallelism needs a forward that accepts the hidden states of the previous stage. LoRA needs a map of the fused weight names. vLLM must know this before it starts the workers, so that it can reject a bad configuration early, with a clear message.

A model class declares a feature with a capability protocol: it adds a base class such as SupportsPP or SupportsLoRA from vllm/model_executor/models/interfaces.py. The base class brings a class flag, for example supports_pp = True, and names the methods that the feature needs. A detector function, for example supports_pp(), checks the flag and often the methods too.

The registry runs all detectors on the class and stores the results in one model info record (Out-of-tree models and the model registry). The configuration code reads the record. Workers check some capabilities again on the built model object.

An everyday comparison. Think of the badges on a driving licence: "trucks", "motorcycles". A clerk checks the badges before you get the job, not on the road. The comparison stops here. For some badges, vLLM also tests the skill: it looks at the forward signature. And a few features need no badge, only the right attribute.

The picture#

Panel 2 is the important one. A flag test trusts the flag. A protocol test needs every member of the protocol. A combined test needs the flag and the structure, and it logs a WARNING when the two do not agree.

In the code#

Step 1: the base expectations (VllmModel)#

interfaces_base.py defines the protocol that every model must follow. Unlike the protocols of interfaces.py, it has no class flag. The comment says why: old out-of-tree models do not inherit these classes (vllm/model_executor/models/interfaces_base.py:35-37). So vLLM checks the structure by name:

  1. Line 66. __init__ must accept the keyword vllm_config.
  2. Lines 70-76. embed_input_ids must exist. A missing method logs a WARNING.
  3. Lines 86-87. forward must accept input_ids and positions.
  4. Lines 111-115. All three must pass.

Two derived protocols build on it. A generative model also has a callable compute_logits (vllm/model_executor/models/interfaces_base.py:140-147). A pooling model sets the flag is_pooling_model (vllm/model_executor/models/interfaces_base.py:226-232). A class that is neither fails the runner check in ModelConfig, unless --convert adapts it to a pooling model (vllm/config/model.py:715-737).

Step 2: flag-only detectors#

Most detectors only read the class flag:

getattr(model, flag, False) works on a class and on an object. It has a side effect: a class can set the flag without the base class. The test model MyOPTRawInputTokensForCausalLM sets requires_raw_input_tokens = True directly (tests/plugins/vllm_add_dummy_model/vllm_add_dummy_model/my_opt.py:21-24). The detector does not check that the methods of the protocol exist.

Step 3: protocol-member detectors#

Some detectors call isinstance with a runtime-checkable Protocol, for example supports_eagle3:

For a class object, Python checks that the object has every member of the protocol (general Python rule). Members with a value in the protocol, such as supports_eagle3 and the methods, come with inheritance. A member that is only annotated, such as SupportsLoRA.lora_manager (vllm/model_executor/models/interfaces.py:739), is not on the class. So isinstance(cls, SupportsLoRA) is false for every model class (derived). For a class, LoRA uses the helper protocol _SupportsLoRAType, which lists only the flag and the two mappings (vllm/model_executor/models/interfaces.py:744-749). The comment above it gives another reason: issubclass does not work with these protocols, so the code treats the class as an instance (lines 742-743). PP has a helper of the same kind, _SupportsPPType (Step 4).

Step 4: combined detectors with warnings (LoRA and PP)#

  1. Line 763. For a class: the flag supports_lora and the attributes packed_modules_mapping and embedding_modules must exist (lines 792-793 use the helper protocol).
  2. Lines 772-779. Flag set, attributes missing: WARNING "sets supports_lora=True, but is missing LoRA-specific attributes", and the result is false.
  3. Lines 781-786. Attributes present, flag missing: WARNING "contains all LoRA-specific attributes, but does not set supports_lora=True". The result is false.

PP is stricter: it also inspects the forward signature.

  1. Lines 867-875. The attribute test passes, but forward has no keyword intermediate_tensors: WARNING, and the result is false (line 897).
  2. Line 902. For a class, SupportsPP in the MRO passes the attribute test. The helper protocol (with make_empty_intermediate_tensors) is the second way.
  3. Lines 877-895. The same two mismatch warnings as for LoRA.

Simplified

The page shows the main protocols. interfaces.py has 26 runtime-checkable protocol classes (two of them helpers) and the mixins SupportsQuant, LocalArgmaxMixin and EagleModelMixin (from git grep at this commit). The table in Step 5 lists the ones that change start-up.

Step 6: mixins that are not detectors#

  • SupportsQuant is a plain class, not a protocol. Its __new__ finds the quantization config in the constructor arguments and stores it on the object as quant_config (vllm/model_executor/models/interfaces.py:1260-1290). It also applies the model's name mapping and packed_modules_mapping to that config (vllm/model_executor/models/interfaces.py:1292-1299).
  • EagleModelMixin goes on the inner decoder, not on the top class. It collects auxiliary hidden states for EAGLE-3 (vllm/model_executor/models/interfaces.py:1608-1680). SupportsEagle3.set_aux_hidden_state_layers asserts that the inner model has it (vllm/model_executor/models/interfaces.py:1745-1748).
  • SupportsEagle (EAGLE-1/2) is in the MRO of Llama, but at this commit git grep finds no call of supports_eagle() outside vllm/model_executor/models/.

Deep dive

The 24 fields of _ModelInfo

Every field is a bool, a string literal or a tuple of strings, so the record survives a JSON round trip to the modelinfos cache (vllm/model_executor/models/registry.py:1054-1070). Two fields read plain attributes without a detector: supported_video_pruning_methods and supports_mm_device_do_normalize (lines 948-953). supports_transcription_only reads the attribute only when the transcription flag is set (lines 943-945).

Deep dive

Front end versus worker: two checks of the same capability

The front end checks the class through the cached record. The worker checks the built object again in some places:

  • LoRA. LoRAConfig.verify_with_model_config runs in VllmConfig.__post_init__ (vllm/config/vllm.py:1572). The worker's load_lora_model calls supports_lora(model) on the object (vllm/v1/worker/lora_model_runner_mixin.py:49-50); Model Runner V2 calls it after it loads the model (vllm/v1/worker/gpu/model_runner.py:407-410).
  • EAGLE-3. No front-end check in the record; the worker checks the object (vllm/v1/worker/gpu/model_runner.py:412-414).
  • For an object. isinstance(obj, SupportsLoRA) succeeds by inheritance alone when the object's class names the protocol as a base (general Python rule for protocols). So for a class that inherits SupportsLoRA, the object check cannot fail where the class check passed. A class that only copies the flag and the two mappings passes the class check. But its object has no lora_manager, so the worker check fails. (Derived.)
Deep dive

Edge cases of the detectors

  • A flag without the base class. Works for every flag-only detector (Step 2). It does not work for isinstance detectors unless every protocol member exists.
  • A wrong flag. supports_multimodal = True on a class without embed_input_ids(..., multimodal_embeddings) passes the detector. The failure comes later, at run time. (Derived from line 589.)
  • SupportsPP without make_empty_intermediate_tensors. For a class, the MRO test at line 902 passes alone. The protocol only annotates this member (vllm/model_executor/models/interfaces.py:820-821), so the model must set it itself. Llama sets it on the object in __init__ (vllm/model_executor/models/llama.py:519-521). (Derived.)
  • Hybrid models without non-attention layers. ModelConfig.is_hybrid returns false when every layer_types entry is attention, even with the flag set (vllm/config/model.py:2040-2049).
  • Two score types. get_score_type asserts that the MRO has at most one non-default score type (vllm/model_executor/models/interfaces_base.py:279-287).

What can go wrong#

The cached record can hide a class change

For a lazy entry, the front end reads the record from $VLLM_CACHE_ROOT/modelinfos when the hash of the model's own file is unchanged (vllm/model_executor/models/registry.py:1088-1098). A new base class in another file does not change that hash. See Out-of-tree models and the model registry.

  • "Pipeline parallelism is not supported for this model". The class lacks SupportsPP, or its forward lacks intermediate_tensors. Look for the PP WARNING in the log (vllm/model_executor/models/interfaces.py:870-875).
  • "LoRA is not supported for ...". The class lacks SupportsLoRA or the two mappings (vllm/config/lora.py:137-143).
  • "This model does not support --runner generate". The base checks failed: a missing embed_input_ids, compute_logits, or keyword in __init__/forward (vllm/config/model.py:727-728).

Why it matters. These protocols are the contract between a model and the rest of vLLM. An out-of-tree model that forgets one does not crash; it loses a feature, and start-up rejects the flag that needs it.

Check yourself#

  1. 1
    Where does vLLM store the results of the capability detectors?
    easy
    Show answer

    In a frozen _ModelInfo record that the registry computes from the class (vllm/model_executor/models/registry.py:917-954). ModelConfig keeps it as _model_info (vllm/config/model.py:741-742).

  2. 2
    A class sets supports_lora = True but has no packed_modules_mapping. What happens with --enable-lora?
    medium
    Show answer

    supports_lora returns false and logs "sets supports_lora=True, but is missing LoRA-specific attributes" (vllm/model_executor/models/interfaces.py:772-779). Then LoRAConfig raises ValueError (vllm/config/lora.py:137-143).

  3. 3
    Why does supports_multimodal accept a class that only sets the flag?
    medium
    Show answer

    The detector is getattr(model, "supports_multimodal", False) (vllm/model_executor/models/interfaces.py:589). It checks only the flag, not the methods.

  4. 4
    Why do supports_lora and supports_pp use helper protocols (_SupportsLoRAType, _SupportsPPType) for a class?
    hard
    Show answer

    A runtime isinstance check on a class object needs every protocol member on that object. SupportsLoRA only annotates lora_manager, so a class does not have it, and isinstance(cls, SupportsLoRA) is false (derived). _SupportsLoRAType lists only the flag and the two mappings (vllm/model_executor/models/interfaces.py:744-749). The comment at vllm/model_executor/models/interfaces.py:742-743 adds that issubclass does not work with these protocols, so the code calls isinstance on the class.
