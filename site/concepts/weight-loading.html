"Weight loading: from checkpoint files to GPU parameters"

AdvancedvLLM conceptsabout 14 min read + 4 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Hugging Face checkpoints Beginner
  • How a vLLM model file is written (llama.py) Advanced
  • Tensor and pipeline parallelism in practice Intermediate

In one sentence

Each worker streams all checkpoint tensors; a mapper renames each one, and the target parameter's weight loader copies only this rank's slice.

The idea#

A checkpoint is a set of named tensors in safetensors files, and loading copies each tensor into the matching model parameter (Weight loading↗). The page Hugging Face checkpoints shows which files vLLM downloads and keeps. This page follows the tensors from the files into the parameters of each GPU.

vLLM loads the weights in six steps, in every worker:

  1. Pick a loader. The load format (--load-format, default auto) selects a model loader class. For auto it is DefaultModelLoader.
  2. Build an empty model. The loader builds the model class on the GPU. Each tensor-parallel layer makes parameters of its per-rank shape, with no values yet.
  3. Stream the tensors. An iterator opens the files one by one and gives (name, tensor) pairs. In the default path, the tensors stay on the CPU.
  4. Map the names. The model's load_weights() uses an AutoWeightsLoader. A WeightsMapper renames checkpoint names to vLLM names, for example q_proj to qkv_proj with the shard id "q".
  5. Copy the slice. The target parameter has a weight loader. It cuts the part of the tensor that this rank owns and copies it into the right rows of the parameter.
  6. Post-process. Each layer's quantization method can repack or quantize its weights once, in process_weights_after_loading.

An everyday comparison. Think of the branches of a library that all get the same delivery list. Each branch reads every line of the list. For each book, the list gives the shelf name in the publisher's words, and a branch translates it into its own shelf names. Some books go into a shared box with three marked parts, such as Q, K and V. Each branch keeps only the pages for its own readers. The comparison stops here. In vLLM, nobody sends a branch its part: every GPU walks the full list itself, and the parameter cuts its slice.

The picture#

Read panels 1 and 2 from left to right: they run the same way in every worker. Panel 3 shows the only step where the ranks differ. The rows of the stacked parameter are the same on both ranks; the rows taken from the checkpoint tensor depend on the rank.

In the code#

Step 1: the load format picks the loader#

get_model_loader() looks up load_config.load_format in this table and raises ValueError for an unknown name (vllm/model_executor/model_loader/__init__.py:123-128). The field default is "auto", and a validator lower-cases the value (vllm/config/load.py:30, vllm/config/load.py:136-138). EngineArgs copies this default without a change (vllm/engine/arg_utils.py:509). One later override exists: for a model in object storage (S3, GCS, Azure), auto becomes runai_streamer (vllm/config/vllm.py:2754-2762). A plugin can add a format with register_model_loader (Hooks in the engine core and the workers).

Model Runner V2 calls the loader in load_model() (vllm/v1/worker/gpu/model_runner.py:398-406). It runs in every worker: with TP = 2, two processes do all the steps below at the same time.

Step 2: build the model with empty parameters#

  1. Lines 73-74. The default dtype is the model dtype, and the default device is the GPU of this worker. So every torch.empty in a layer constructor makes a GPU tensor of the right dtype.
  2. Lines 76-80. create_model() calls initialize_model(), which builds the class with vllm_config and prefix (How a vLLM model file is written (llama.py)). The log line "Initializing model took ... seconds" measures this part.
  3. Line 88. self.load_weights() is the loader's method; for the default loader it streams the files (Step 3).
  4. Lines 106-109. Online quantization finishes first; then process_weights_after_loading() runs for every layer (Step 6).

The layer constructors do the per-rank sizing. UnquantizedLinearMethod.create_weights() makes torch.empty(sum(output_partition_sizes), input_size_per_partition) (vllm/model_executor/layers/linear.py:178-205). The page The tensor-parallel layers (linear.py and vocab_parallel_embedding.py) gives these sizes for each layer class.

Step 3: choose the files and stream the tensors#

DefaultModelLoader._prepare_weights() finds, downloads and filters the files (vllm/model_executor/model_loader/default_loader.py:147-263); Hugging Face checkpoints explains that part. Then _get_weights_iterator() picks an iterator by format (vllm/model_executor/model_loader/default_loader.py:301-365). The usual case is safetensors_weights_iterator():

  • Order. The files are sorted by a natural sort key, so ...-00002-of-... comes before ...-00010-of-... (vllm/model_executor/model_loader/weight_utils.py:1134).
  • Strategies. --safetensors-load-strategy is None by default. eager reads the whole file into CPU memory first; torchao rebuilds torchao tensors (vllm/model_executor/model_loader/weight_utils.py:1207-1242).
  • Prefetch. With the default None, vLLM prefetches the files into the page cache only on NFS or Lustre. They must also fit in 90% of the free RAM (vllm/model_executor/model_loader/weight_utils.py:1136-1155). prefetch forces it. Each process prefetches a different part of the files, sorted_files[rank::world_size]. Rank and world size are the global values of torch.distributed, not the TP values (vllm/model_executor/model_loader/weight_utils.py:1051-1057).
  • PyTorch files. For .bin and .pt files, pt_weights_iterator() calls torch.load(..., weights_only=True) on each file and yields its items (vllm/model_executor/model_loader/weight_utils.py:1479-1495).
  • Many threads. --model-loader-extra-config '{"enable_multithread_load": true}' selects the multi-thread iterators, with 8 threads by default (vllm/model_executor/model_loader/default_loader.py:58-59, vllm/model_executor/model_loader/default_loader.py:329-336).

The loader then calls model.load_weights() with the iterator, and logs "Loading weights took ... seconds" (vllm/model_executor/model_loader/default_loader.py:503-509).

Step 4: map the names (WeightsMapper and AutoWeightsLoader)#

Llama has two load_weights methods. The outer class makes an AutoWeightsLoader without a mapper (vllm/model_executor/models/llama.py:559-561). The loader groups the names by their first part and finds the child model. That child has its own load_weights, so the loader gives it the names without model. (vllm/model_executor/models/utils.py:387-400). LlamaModel.load_weights uses the mapper:

The mapper has six kinds of rule: orig_to_new_renaming, _regex, _substr, _stacked, _prefix and _suffix, applied in this order. A regex, substring, prefix or suffix rule that maps to None drops the tensor (vllm/model_executor/models/utils.py:48-61, vllm/model_executor/models/utils.py:108-145). AutoWeightsLoader.load_weights() adds more mappers. With a quantization config, it adds the config's mappers for KV cache scale names and checkpoint names. It always adds a rule that drops old rotary tables (vllm/model_executor/models/utils.py:460-473).

Then the loader walks the module tree:

  1. Line 409. _groupby_prefix() splits each name at the first dot: layers.0.self_attn.qkv_proj.weight becomes layers and 0.self_attn.qkv_proj.weight.
  2. Lines 412-415. A child module: recurse. For QKVParallelLinear the recursion ends early, because that layer has its own load_weights (line 388).
  3. Lines 416-424. A parameter: _load_param() calls param.weight_loader, or default_weight_loader when the parameter has none (vllm/model_executor/models/utils.py:340-341).

QKVParallelLinear.load_weights reads the shard id from the tensor and calls param.weight_loader(param, loaded_weight, shard_id) (vllm/model_executor/layers/linear.py:1339-1354). MergedColumnParallelLinear has the same method for the integer shard ids of gate_up_proj (vllm/model_executor/layers/linear.py:985-1000).

Step 5: the weight loader of each parameter#

A linear layer chooses one of two loader families when it is built. If the class name of its quantization method is in WEIGHT_LOADER_V2_SUPPORTED, it uses weight_loader_v2; else weight_loader (vllm/model_executor/layers/linear.py:530-534). UnquantizedLinearMethod is in the list, so a BF16 model uses v2 (vllm/model_executor/layers/linear.py:50-64). The v2 loaders give the work to the parameter class:

The shard size is the size of the parameter on this rank, so the loader needs no TP arithmetic of its own. ModelWeightParameter inherits both methods, and the layer calls the one that fits (vllm/model_executor/parameter.py:229-234). The v1 loaders do the same cut with getattr(param, "output_dim") and "input_dim" (vllm/model_executor/layers/linear.py:589-606, vllm/model_executor/layers/linear.py:1758-1774).

For a stacked parameter, the loader first selects the part of the parameter, then the part of the tensor:

  1. Line 191. For q, the slice index is the TP rank. For k and v it is tp_rank // num_kv_head_replicas; num_heads here carries the replica count (vllm/model_executor/layers/linear.py:1203-1209).
  2. Line 192. The part of the parameter: offset and size from the head counts of this rank (vllm/model_executor/layers/linear.py:1101-1117).
  3. Lines 193-195. The part of the checkpoint tensor. Then an assertion and one copy.

Other parameters:

  • Embedding and LM head. VocabParallelEmbedding.weight_loader cuts rows org_vocab_start_index to org_vocab_end_index, and fills the padding rows with zeros (vllm/model_executor/layers/vocab_parallel_embedding.py:497-520).
  • Norm weights. RMSNorm.weight is a plain nn.Parameter without a loader (vllm/model_executor/layers/layernorm.py:65-67). default_weight_loader checks the shape and copies the full tensor on every rank (vllm/model_executor/model_loader/weight_utils.py:1529-1547).

Step 6: older model files: stacked_params_mapping#

Before WeightsMapper had stacked rules, each model wrote the loop itself. 38 files in vllm/model_executor/models/ still do. 98 other files use orig_to_new_stacked, and no file uses both (git grep at this commit). An example:

  1. Lines 489-496. The list has the same content as Llama's mapper, as tuples (param_name, shard_name, shard_id).
  2. Lines 517-528. For each name, find a matching tuple and rename. Skip parameters of other pipeline stages. Call the loader with the shard id as the third argument.

Step 7: quantized weights#

For a quantized checkpoint, the layer's quantization method makes the parameters in create_weights() (Quantization methods as plugins). FP8, for example, registers an FP8 weight and a weight_scale (or weight_scale_inv for block scales), each with the layer's weight loader (vllm/model_executor/layers/quantization/fp8.py:312-339). The checkpoint has tensors with the same names, so the mapping and slicing above work for them too. A per-tensor scale of a stacked layer has one slot per part (q, k, v). PerTensorScaleParameter copies each checkpoint scale into the slot of its shard id (vllm/model_executor/parameter.py:253-301); the v1 loaders use adjust_scalar_to_fused_array for the same job (vllm/model_executor/layers/linear.py:97-121).

After all tensors are copied, process_weights_after_loading() visits every module with a quantization method and calls its post-processing (vllm/model_executor/model_loader/utils.py:157-196). FP8 with per-tensor scales, for example, re-quantizes the parts of a stacked layer to one scale, the maximum of their scales, and transposes the weight. This happens only without block scales and without the Marlin kernel (vllm/model_executor/layers/quantization/fp8.py:372-409, vllm/model_executor/layers/quantization/utils/fp8_utils.py:1454-1479). The page Quantized checkpoints explains the formats.

Deep dive

AutoWeightsLoader.load_weights, line by line

  1. Line 458. Unexpected .bias tensors are ignored; the comment says GPTQ checkpoints often have them.
  2. Lines 463-470. The quantization config can be on the model or on a direct child. If it exists, its mappers and its ignore list join in.
  3. Line 471. Old rotary tables such as rotary_emb.inv_freq are dropped (vllm/model_executor/models/utils.py:233-240).
  4. Lines 473-474. Both steps are generators: no tensor is read before the tree walk asks for it.
  5. Line 476. The walk returns the names of all loaded parameters. The default loader compares them with model.named_parameters() (next deep dive).
  6. Line 477. With tied embeddings (lm_head.weight is embed_tokens.weight), the loader loads the first name only. If that name is missing in the checkpoint, it raises ValueError (vllm/model_executor/models/utils.py:491-502).

Inside the walk, a PPMissingLayer returns at once, so the tensors of other pipeline stages are skipped (vllm/model_executor/models/utils.py:382-383). A name that matches no child and no parameter raises ValueError with the list of available names (vllm/model_executor/models/utils.py:425-448).

Deep dive

Memory, time and the completeness check

  • Where the bytes go. The parameters are allocated on the GPU in Step 2, at their final per-rank size. The checkpoint tensors stay on the CPU; each loader copies a slice into the GPU parameter with copy_.
  • Peak memory. After the load, the loader logs "Peak GPU memory after loading weights" at DEBUG level on CUDA, ROCm and XPU (vllm/model_executor/model_loader/base_loader.py:95-102).
  • Three timers. "Initializing model took" (constructors, vllm/model_executor/model_loader/base_loader.py:82-85), "Loading weights took" (the stream, vllm/model_executor/model_loader/default_loader.py:505-509), and "Model loading took ... GiB memory and ... seconds" (the whole load_model, vllm/v1/worker/gpu/model_runner.py:428-435).
  • Completeness. For a model without quantization, the default loader checks that parameters got a value; else "Following weights were not initialized from checkpoint" (vllm/model_executor/model_loader/default_loader.py:510-523, vllm/model_executor/model_loader/default_loader.py:567-572). In this case, it exempts all parameters of modules that have a quantization method (vllm/model_executor/model_loader/default_loader.py:533-566). Every quantize method has process_weights_after_loading (vllm/model_executor/layers/quantization/base_config.py:80-85), so in a BF16 Llama the linear, embedding and head weights are exempt too. The check then covers only parameters such as the norm weights (derived). enable_weights_track in --model-loader-extra-config turns the check on or off.

What can go wrong#

A checkpoint name that the model does not know stops start-up

The tree walk raises "There is no module or parameter named ..." for every name it cannot place (vllm/model_executor/models/utils.py:442-448). By default the loader ignores only .bias tensors and the suffixes of the quantization config, and the mapper drops old rotary tables. A fine-tuned checkpoint with extra tensors needs a mapper rule that maps them to None.

  • A shape mismatch. The weight loaders assert that the slice and the parameter have the same shape (vllm/model_executor/parameter.py:197, vllm/model_executor/model_loader/weight_utils.py:1538-1541). A checkpoint for another config, or a wrong --hf-overrides, fails here.
  • Missing weights. An unquantized model raises "Following weights were not initialized from checkpoint" for an empty norm weight, or another parameter outside quantize-method modules (vllm/model_executor/model_loader/default_loader.py:533-572). A missing linear weight gives no error here (derived).
  • A dtype mismatch. A tensor with another dtype is converted by copy_, and the loader logs a warning (vllm/model_executor/models/utils.py:324-339).
  • An unknown format. --load-format gguf raises "Load format `gguf` is not supported" (vllm/model_executor/model_loader/__init__.py:126-127).
  • Slow loads from network storage. On NFS, a large model that does not fit in 90% of the free RAM is not prefetched, and vLLM logs a warning (vllm/model_executor/model_loader/weight_utils.py:1156-1165). Try --safetensors-load-strategy eager or prefetch, or a pre-sharded checkpoint.

Why it matters. Weight loading is often the longest part of start-up, and its errors are the first errors of a new model or a new checkpoint. When you know the path from file to parameter, you can read the log timers, fix name and shape errors, and choose a faster format.

Check yourself#

  1. 1
    Which loader class serves the default --load-format auto, and which iterator does it use for a safetensors checkpoint?
    easy
    Show answer

    DefaultModelLoader (vllm/model_executor/model_loader/__init__.py:51). Without the multi-thread option it uses safetensors_weights_iterator (vllm/model_executor/model_loader/default_loader.py:337-349).

  2. 2
    How does QKVParallelLinear know that a tensor is the K part?
    medium
    Show answer

    Llama's mapper renames .k_proj to .qkv_proj with the shard id "k" (vllm/model_executor/models/llama.py:351-353). WeightsMapper.apply() stores it as tensor.shard_id (vllm/model_executor/models/utils.py:158-164), and QKVParallelLinear.load_weights reads it back (vllm/model_executor/layers/linear.py:1342-1354).

  3. 3
    For a BF16 model with TP = 4, which dimension of o_proj.weight does each rank cut, and at which offset?
    medium
    Show answer

    o_proj is row-parallel, so the loader cuts input_dim = 1 at tp_rank × shard_size (vllm/model_executor/parameter.py:216-220). For Llama-3-8B, the parameter is [4096, 1024], so rank 2 takes columns 2048-3071.

  4. 4
    A model has 8 KV heads and runs with TP = 16. Which rows of k_proj.weight does rank 5 load? Why does rank 4 load the same rows?
    hard
    Show answer

    num_kv_heads is 1 and num_kv_head_replicas is 2 (vllm/model_executor/layers/linear.py:1066-1068). The slice index for k is tp_rank // num_heads, where num_heads carries the replica count: 5 // 2 = 2 (vllm/model_executor/parameter.py:191, vllm/model_executor/layers/linear.py:1203-1205). With a slice size of 128 rows, rank 5 loads rows 256-383 (KV head 2). Rank 4 gives 4 // 2 = 2 too, so both ranks hold a copy of KV head 2.

  5. 5
    A model runs with PP = 2. What happens to the checkpoint tensors of layers 16-31 on stage 0?
    hard
    Show answer

    The iterator still reads every tensor of every file, because it calls get_tensor for each name (vllm/model_executor/model_loader/weight_utils.py:1243-1249). The tree walk reaches PPMissingLayer objects for those layers and returns without a copy (vllm/model_executor/models/utils.py:382-383). Hand-written loaders use is_pp_missing_parameter() for the same skip (vllm/model_executor/models/minicpm.py:524-525).

Related pages

  • The tensor-parallel layers (linear.py and vocab_parallel_embedding.py)vLLM's linear and embedding layers know their tensor-parallel rank. They resolve a quantization method per layer, allocate only their slice, cut checkpoint tensors when they load, and call the all-reduce or all-gather in forward. QKVParallelLinear splits by heads and copies KV heads when TP is larger than their count.
  • Quantized checkpointsA quantized checkpoint stores weights, and sometimes activations, in fewer bits with scales. Weight-only schemes (AWQ, GPTQ) save memory; W8A8 and FP4 schemes also make the matrix multiply cheaper. vLLM reads the scheme from config.json and frees the saved memory for the KV cache.
  • Quantization methods as pluginsA quantization method is a QuantizationConfig subclass registered under a name. The front end picks the name from the checkpoint or --quantization and makes one config object; each layer in the worker asks it for a quantize method that makes the weights and runs the forward.
  • Hooks in the engine core and the workersSeveral extension points of the engine core and the workers are config fields or registries, not entry-point groups - scheduler_cls, worker_cls and worker_extension_cls, logits processors, model loaders, sleep-mode backends and KV cache dtypes. This page shows where each one is read and what your class must do.
  • "model_executor/models/llama.py: the Llama model"vllm/model_executor/models/llama.py defines LlamaMLP, LlamaAttention, LlamaDecoderLayer, LlamaModel and LlamaForCausalLM from tensor-parallel layers, plus two bidirectional wrappers. It is the reference model file of vLLM; nine registry names and many other model files reuse it.
  • "model_executor/layers/linear.py: tensor-parallel linear layers"vllm/model_executor/layers/linear.py holds LinearBase and the replicated, column-parallel, merged-column, QKV and row-parallel linear layers. Each one resolves a quantize method, allocates its per-rank weight through it, cuts checkpoint tensors in weight_loader or weight_loader_v2, and calls the TP all-gather or all-reduce in forward.
  • The model runner (Model Runner V2)Model Runner V2 keeps every running request in a fixed row of GPU tensors, gathers each step's inputs from those rows with GPU kernels, runs the model (CUDA graph or eager), and samples in a second call that returns an AsyncOutput without a GPU wait.
