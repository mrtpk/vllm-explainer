Plugins in the API server

IntermediatevLLM conceptsabout 10 min read + 3 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • How vLLM finds and loads plugins Intermediate
  • All the ways to extend vLLM Intermediate

In one sentence

Five plugin kinds act in the API server: HTTP routes, pooling IO processors, text parsers, LoRA resolvers and stat loggers.

The idea#

The front end of vllm serve is the API server process. It parses HTTP requests, renders prompts, talks to the engine core and turns the engine output into OpenAI responses (The OpenAI-compatible server: launch modes, app, serving classes and streaming). Several parts of this work are open to plugins, because deployments differ in these places. Examples are extra routes, output formats, model-specific parsing, adapter storage and metrics systems.

Each front-end extension point reaches vLLM in its own way:

  • Endpoint plugins (group vllm.endpoint_plugins) add HTTP routes, and can replace an existing route. They load only when VLLM_PLUGINS names them.
  • IO processor plugins (group vllm.io_processor_plugins) change the input and output of a pooling model.
  • Tool parsers and reasoning parsers are registries. A flag imports your module: --tool-parser-plugin or --reasoning-parser-plugin.
  • LoRA resolvers are a registry that a general plugin fills.
  • Stat loggers (group vllm.stat_logger_plugins) receive the statistics of each engine step.

An everyday comparison. Think of the reception of a hotel. A partner company can add a service desk (an endpoint) or bring a translator for some guests (a parser). It can give the porters a list of storage rooms for unknown luggage (a resolver), or put a counter on the door (a stat logger). The comparison stops here: in vLLM the receptionist does not ask the partner; each plugin must be installed and, for routes, named in an allowlist.

Loading has a stricter rule than the other groups. With VLLM_PLUGINS unset, vLLM loads none and warns:

  1. Lines 122-131. Not set: a WARNING names the discovered plugins, and nothing loads. VLLM_PLUGINS="" is an allowlist that matches nothing (vllm/plugins/__init__.py:107-109).

Step 2: IO processor plugins (pooling only)#

An IO processor converts a custom request into pooling inputs and the pooling output into a custom response. The abstract methods are pre_process and post_process (vllm/plugins/io_processors/interface.py:18-66). The plugin entry point is a function that returns the dotted class name, or None:

vLLM selects one plugin by name. The name comes from --io-processor-plugin, or from the key io_processor_plugin in the model's HF config:

Only the pooling entry points ask for it (vllm/entrypoints/pooling/factories.py:73-84). A plugin function that raises gives a WARNING. No usable plugin, or the wrong name, raises ValueError (lines 74-84).

Step 3: tool parser and reasoning parser plugins#

ToolParserManager keeps two dicts: classes and lazy entries (module path, class name) (vllm/tool_parsers/abstract_tool_parser.py:243-244). vLLM registers its own parsers lazily at import (vllm/tool_parsers/__init__.py:264-270). A lookup tries the classes first, then imports a lazy entry and caches it:

register_module has two forms (vllm/tool_parsers/abstract_tool_parser.py:327-370). With module=... it registers the class at once; force=False raises KeyError for a taken name. As a decorator it only stores a lazy entry with the class's module and name, and overwrites any entry with that name. ReasoningParserManager has the same shape (vllm/reasoning/abs_reasoning_parsers.py:225-373).

Your module reaches the manager through a flag:

  1. Lines 579-583. The value is imported only if it is longer than 3 characters. The code does not say why.
  2. import_plugin tries a module name first, then a file path. A file that fails to import is logged, not raised (vllm/utils/import_utils.py:81-98). The file is loaded under its file name as a module and put into sys.modules (vllm/utils/import_utils.py:101-116), so a decorator entry that points to it works.
  3. Lines 589-594. With --enable-auto-tool-choice, an unknown --tool-call-parser raises KeyError at start-up. So a plugin that failed to import shows up here.

The API server calls init_parser_plugin in setup_server and again in run_server_worker (vllm/entrypoints/launchers/launcher.py:369-370, vllm/entrypoints/launchers/api_server/entry.py:183). The reasoning parser is also needed in the engine core, for structured outputs. So the engine core imports the reasoning parser plugin itself, with the same length rule:

The page Tool and reasoning parsers: from model text to tool_calls and reasoning explains what the parsers do with the text.

The docs example registers a module path that does not exist

The tool calling guide ends its plugin example with register_lazy_module(name="example", module_path="vllm.tool_parsers.example", ...) (docs/features/tool_calling.md:676-681). There is no such module in vllm/tool_parsers/, so the lookup of "example" would fail to import. Use the decorator @ToolParserManager.register_module("example") on your class instead; it records your module. (Derived from vllm/tool_parsers/abstract_tool_parser.py:353-366 and the folder listing.)

Step 4: LoRA resolvers#

A resolver finds a LoRA adapter by name when a request asks for a model name that the server does not know. The registry holds instances by name; a second registration overwrites with a WARNING (vllm/lora/resolver.py:52-72). vLLM ships two resolvers, as general plugins:

  • Filesystem resolver. It registers only when VLLM_LORA_RESOLVER_CACHE_DIR is set, and raises ValueError if that is not a directory (vllm/plugins/lora_resolvers/filesystem_resolver.py:49-61).
  • HF Hub resolver. It needs VLLM_LORA_RESOLVER_HF_REPO_LIST and the name lora_hf_hub_resolver in VLLM_PLUGINS, "because it allows remote downloads" (vllm/plugins/lora_resolvers/hf_hub_resolver.py:129-147).

The serving layer copies all resolvers when it starts (vllm/entrypoints/openai/models/serving.py:113-117). It asks them only when VLLM_ALLOW_RUNTIME_LORA_UPDATING is on:

The resolvers run in registration order. The first one that finds the adapter and loads it wins. If a found adapter fails to load, vLLM logs a WARNING and asks the next resolver. When adapters were found but none loads, the answer is HTTP 400 (vllm/entrypoints/openai/models/serving.py:315-359). The page Serving LoRA adapters: from the model name to the wrapped layer covers adapters in general.

Step 5: stat logger plugins#

A stat logger implements StatLoggerBase: a constructor with vllm_config and engine_index, record, and log_engine_initialized (vllm/v1/metrics/loggers.py:54-81). The plugin group gives the class itself:

AsyncLLM.__init__ loads them, after any loggers that the caller passed (vllm/v1/engine/async_llm.py:155-165). A plugin turns on stats even with --disable-log-stats, but then without the default loggers (lines 158-165). StatLoggerManager wraps a per-engine class in an adapter, and always adds PrometheusStatLogger unless one of the loggers is a Prometheus logger (vllm/v1/metrics/loggers.py:1398-1419). The test plugin is a minimal example (tests/plugins/vllm_add_dummy_stat_logger/dummy_stat_logger/dummy_stat_logger.py:7-30).

Deep dive

How an endpoint plugin replaces a route

attach_endpoint_plugins rebuilds the route list after the plugins have attached their routes (vllm/plugins/endpoint_plugins/interface.py:108-146):

  1. Remember the ids of all routes that exist before the plugins run (line 109).
  2. Call attach_router(app) for each plugin, in discovery order (lines 110-111).
  3. Walk all routes. A new APIRoute removes the methods it shares with an earlier route of the same path. An earlier route with no methods left is dropped; one with other methods stays, as a copy (lines 121-139).
  4. Insert the new route at the place of the first route it replaced, so it stays ahead of mounts (lines 133, 140).
  5. Reset the OpenAPI schema, and keep the plugin list in app.state.endpoint_plugins for phase B (lines 144-146).

So a later plugin also replaces an earlier plugin's route for the same method. A test checks this (tests/plugins_tests/test_endpoint_plugins.py:280).

Deep dive

Lazy parser entries, step by step

Example: your file /opt/acme_parser.py has @ToolParserManager.register_module("acme") on class AcmeToolParser(ToolParser). You start vllm serve ... --enable-auto-tool-choice --tool-call-parser acme --tool-parser-plugin /opt/acme_parser.py.

  1. init_parser_plugin sees a value longer than 3 characters and calls import_plugin (vllm/entrypoints/common/cli_args.py:579-580).
  2. importlib.import_module("/opt/acme_parser.py") raises ModuleNotFoundError, so vLLM loads the file as module acme_parser (vllm/utils/import_utils.py:88-93).
  3. The decorator stores lazy_parsers["acme"] = ("acme_parser", "AcmeToolParser") (vllm/tool_parsers/abstract_tool_parser.py:353-366).
  4. validate_api_server_args finds "acme" in list_registered() (vllm/tool_parsers/abstract_tool_parser.py:373-375).
  5. The first lookup imports acme_parser from sys.modules, checks the subclass and caches the class (vllm/tool_parsers/abstract_tool_parser.py:263-274).

A name like "hermes" exists as a lazy built-in entry. Your decorator with that name replaces the lazy entry, unless the built-in class was already loaded into tool_parsers, which the lookup checks first (lines 254-255). (Derived.)

What can go wrong#

An installed endpoint plugin does nothing by default

Without VLLM_PLUGINS, vLLM only warns "Found endpoint plugin(s) ... but VLLM_PLUGINS is not set" (vllm/plugins/__init__.py:125-130). Set VLLM_PLUGINS to the entry-point name. Remember that this list then also filters the general, platform and stat logger plugins.

  • A short parser plugin value is ignored. Three characters or fewer are not imported (vllm/entrypoints/common/cli_args.py:579).
  • A broken parser file only logs. The ERROR log "Failed to load module ..." is easy to miss. Start-up then fails later with "invalid tool call parser" only when auto tool choice is on (vllm/utils/import_utils.py:94-98, vllm/entrypoints/common/cli_args.py:589-594).
  • The resolver never runs. VLLM_ALLOW_RUNTIME_LORA_UPDATING is off, or VLLM_PLUGINS filtered out the general plugin that registers it.
  • A stat logger class is wrong. A non-StatLoggerBase entry raises TypeError in AsyncLLM.__init__ and stops start-up (vllm/v1/metrics/loggers.py:88-94).
  • An IO processor plugin is missing. A pooling model that names a plugin fails with "The model requires the ... IO Processor plugin but it is not installed" (vllm/plugins/io_processors/__init__.py:79-84).

Why it matters. These plugins change what clients see: routes, response formats, parsed tool calls and metrics. They all live in the API server, so they cost no GPU time, but a mistake in them shows up directly in the HTTP responses.

Check yourself#

  1. 1
    Which front-end plugin group loads only when VLLM_PLUGINS names it?
    easy
    Show answer

    vllm.endpoint_plugins. With VLLM_PLUGINS unset, load_endpoint_plugins returns an empty list after a warning (vllm/plugins/__init__.py:122-131).

  2. 2
    What must the object behind a vllm.stat_logger_plugins entry point be?
    easy
    Show answer

    A class that subclasses StatLoggerBase, else TypeError (vllm/v1/metrics/loggers.py:87-94).

  3. 3
    You pass --reasoning-parser-plugin my.py --reasoning-parser mine. In which processes does vLLM import my.py?
    medium
    Show answer

    In two processes. "my.py" has 5 characters, so it passes the length rule. The API server imports it (vllm/entrypoints/common/cli_args.py:582-583), and the engine core imports it again for structured outputs (vllm/v1/structured_output/__init__.py:103-104).

  4. 4
    Your endpoint plugin registers POST /v1/completions. What happens to vLLM's own route, and to a GET on the same path?
    medium
    Show answer

    The plugin route replaces the core POST route; other methods of the path stay (vllm/plugins/endpoint_plugins/interface.py:121-141, docstring vllm/plugins/endpoint_plugins/interface.py:72-74).

  5. 5
    A request asks for model "sql-lora", which the server does not know. You set VLLM_LORA_RESOLVER_CACHE_DIR=/loras and VLLM_PLUGINS=acme_admin. Is the adapter found?
    hard
    Show answer

    No. The filesystem resolver registers from the general plugin lora_filesystem_resolver (pyproject.toml:45-46), and VLLM_PLUGINS=acme_admin filters it out (vllm/plugins/__init__.py:63-64). Also, resolvers run only with VLLM_ALLOW_RUNTIME_LORA_UPDATING=1 (vllm/entrypoints/serve/engine/serving.py:62-66). The request gets "The model `sql-lora` does not exist."
