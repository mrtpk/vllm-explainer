How vLLM finds and loads plugins

IntermediatevLLM conceptsabout 14 min read + 8 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Python entry points Beginner
  • Processes, ZMQ and shared memory Beginner

In one sentence

vLLM finds plugins as Python entry points in named groups. Each vLLM process loads only the groups that it needs, when it needs them.

The idea#

A plugin is code in another Python package that changes vLLM. For example, a plugin can add a model architecture, a hardware platform or a new HTTP route. vLLM does not import your package by its name. Your package publishes an entry point in its metadata, under a plugin group such as vllm.general_plugins. vLLM asks Python which installed packages publish a name in that group, and then imports the object that the name points to. The page Python entry points explains entry points in general.

vllm serve runs as several processes. The front end runs the HTTP server. The EngineCore process runs the scheduler. Each worker process owns one GPU. With tensor parallelism, one model runs on several GPUs, so there are several workers (Parallelism basics↗).

Python objects live in one process. When a plugin registers a model in the front end, the registry in a worker does not change. So each process must load the plugins itself. But not every process needs every group. Only the front end needs HTTP routes, and only the workers run the model. So vLLM loads each group in the processes that use it, at the moment that it needs it.

An everyday comparison. Think of a company with three offices: sales, planning and the factory. Each office has its own copy of the rule book. When a new rule comes, each office must add it to its own copy. The sales office reads the rules for customers. The factory does not need them. The comparison stops here. In vLLM, each process reads the same central list: the installed entry points. No process sends the rules to the next one.

Three rules control the loading:

  1. One allowlist for five groups. The environment variable VLLM_PLUGINS lists the plugin names to load. If it is not set, vLLM loads every plugin that it finds, but not the endpoint plugins. The group vllm.logits_processors does not use this list (Step 7).
  2. Once per process. General plugins run at most once in each process. A module-level flag stops the second load.
  3. A broken import is skipped. A broken plugin function stops start-up. vLLM logs and skips an entry point that fails to import. It does not catch an error that a general plugin function raises.

Step 2: one loader for five groups#

Five groups use one function, load_plugins_by_group(). It finds the entry points of one group, filters them by name, and imports them:

The function returns a dict from plugin name to the loaded object (vllm/plugins/__init__.py:62). It does not call the objects. The caller decides what to do: load_general_plugins() calls each function, and the platform code calls each detector function (vllm/platforms/__init__.py:254-257).

Step 3: the allowlist VLLM_PLUGINS#

VLLM_PLUGINS is one list for all groups

If you set VLLM_PLUGINS to enable one plugin, vLLM skips every plugin that is not in the list, in every group except vllm.logits_processors. This includes vLLM's own LoRA resolver plugins and your platform plugin. Put the names of all the plugins that you need into the list.

Line 64 of the loader compares plugin.name with the list. This is the name on the left side of the entry point, for example lora_filesystem_resolver in pyproject.toml. It is not the name of the Python package.

The module-level flag plugins_loaded makes a second call in the same process return at once (lines 83-84). The function sets the flag before it calls any plugin function (line 85). Then it calls each function, with no try block (lines 89-90). The docstring warns that a plugin can load several times, in different processes (lines 78-80). Step 5: which process loads what, and when#

Five call sites run load_general_plugins(), in four kinds of process: the front end (two calls), the engine core, the worker and the model registry subprocess.

Front end. The CLI builds the parsers of all subcommands before it reads your flags (vllm/entrypoints/cli/main.py:100-110). The serve parser calls make_arg_parser (vllm/entrypoints/cli/serve.py:172), which calls AsyncEngineArgs.add_cli_args (vllm/entrypoints/common/cli_args.py:466). That function loads the general plugins first:

Later, EngineArgs.__post_init__ calls load_general_plugins() again (vllm/engine/arg_utils.py:921-924). In the front end of vllm serve, this second call returns at once because of the flag. It is still useful: the offline LLM class makes an EngineArgs object (vllm/entrypoints/llm.py:295) and does not build a CLI parser.

Engine core process. EngineCore.__init__ loads the general plugins before it makes the executor and the scheduler:

The executor comes later, at vllm/v1/engine/core.py:147. So the plugins are ready before any worker starts.

Worker. Each worker loads them in WorkerWrapperBase.init_worker, before it makes the worker class:

A worker process calls init_worker from WorkerProc.__init__ (vllm/v1/executor/multiproc_executor.py:672). With one GPU, the default executor is uni (vllm/config/parallel.py:1099-1100). It calls init_worker inside the engine core process (vllm/v1/executor/uniproc_executor.py:68). There, the flag is already set, so nothing loads twice.

Model registry subprocess. Every built-in model is a lazy registry entry (vllm/model_executor/models/registry.py:1565-1573). An out-of-tree model is lazy too when you register it as a string "module:Class" (vllm/model_executor/models/registry.py:1187-1193). To read the capabilities of a lazy model without an import in the main process, vLLM may run a new Python process:

This happens only on a cache miss (vllm/model_executor/models/registry.py:1086-1109). A miss is a missing cache file, or a hash that does not match the model's source file. vLLM also skips the cache when it cannot find the source file. The command is python -m vllm.model_executor.models.registry (vllm/model_executor/models/registry.py:823). The page Out-of-tree models and the model registry explains this cache.

Step 6: platform plugins load on first use#

Platform plugins do not use load_general_plugins(). They load the first time that code in a process reads vllm.platforms.current_platform:

resolve_current_platform_cls_qualname() then loads the group vllm.platform_plugins (vllm/platforms/__init__.py:250). It calls each detector function, and one activated out-of-tree platform wins over the built-in platforms (vllm/platforms/__init__.py:277-279). If VLLM_TARGET_DEVICE is cpu, the function returns the CPU platform before it loads this group (vllm/platforms/__init__.py:244-248). The default value is cuda (vllm/envs.py:622). The page Platform plugins and current_platform explains the detection order.

Step 7: groups that only the front end loads#

  • Stat loggers. AsyncLLM.__init__ adds the plugin classes to its stat loggers (vllm/v1/engine/async_llm.py:155-156). The group comment says "only when serve vLLM with async mode" (vllm/plugins/__init__.py:24-26).
  • Endpoints. build_app attaches endpoint plugins after the core routes (vllm/entrypoints/launchers/app.py:47-51). These plugins load only when VLLM_PLUGINS is set and names them (vllm/plugins/__init__.py:122-131).
  • IO processors. get_io_processor() loads the group only when it gets a plugin name (vllm/plugins/io_processors/__init__.py:42-61). The name comes from the io_processor_plugin setting of the model config, or from the same field in the Hugging Face config. The pooling serving code calls it (vllm/entrypoints/pooling/pooling/io_processor.py:51-55).

Logits processors take their own path

vllm.logits_processors does not use load_plugins_by_group(). The Model Runner V2 loader calls entry_points() directly (vllm/v1/worker/gpu/sample/logits_processor/loader.py:46), so VLLM_PLUGINS does not filter this group. The worker loads it in the model runner's load_model (vllm/v1/worker/gpu/model_runner.py:463-466). The front end loads it too, to check request parameters (vllm/v1/engine/input_processor.py:58-62, vllm/v1/engine/input_processor.py:99-107). For a pooling model, the worker does not load it (vllm/v1/worker/gpu/sample/logits_processor/loader.py:172-179).

Deep dive#

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Deep dive

load_plugins_by_group(), line by line

  1. Line 38. The import of importlib.metadata.entry_points is inside the function, so it runs only on a call.
  2. Line 40. envs.VLLM_PLUGINS reads the environment variable on each call (vllm/envs.py:2297-2298). After enable_envs_cache(), the value is cached (vllm/envs.py:2308-2326). The engine core and the workers call it at the end of their start-up (vllm/v1/engine/core.py:243, vllm/v1/executor/multiproc_executor.py:710).
  3. Lines 42-45. entry_points(group=group) returns the entry points of all installed packages in that group. If there are none, the function returns {} with a debug log.
  4. Lines 48-60. The log level is DEBUG for vllm.general_plugins and INFO for the other groups. The default log level is INFO (vllm/envs.py:860). So by default, the log lists the platform, stat logger and IO processor plugins that it finds, but not the general plugins.
  5. Lines 63-64. An entry point passes when VLLM_PLUGINS is None, or when its name is in the list. The check is an exact string match.
  6. Lines 68-72. plugin.load() imports the module and gets the attribute, for example vllm_add_dummy_model:register. Any Exception is logged with its traceback, and the loop continues with the next entry point.
  7. Line 74. The result is a dict[str, Callable] from the entry-point name to the object. The order is the order of entry_points().

The function has no guard. Each call reads the metadata and imports the objects again. Python caches imported modules, so a second load() of the same module does not run the module code again. The guard of load_general_plugins() is about the plugin functions, which have side effects.

Deep dive

VLLM_PLUGINS: values and edge cases

The value comes from os.environ["VLLM_PLUGINS"].split(",") (vllm/envs.py:1163-1167). The comment above it says: "if this is set to an empty string, no plugins will be loaded" (vllm/envs.py:1160-1162).

not setNoneLoads every plugin in the group. Endpoint plugins are the exception: none load (vllm/plugins/__init__.py:122-131).
""[""]No name matches, so no plugin loads. A test checks this for endpoint plugins (tests/plugins_tests/test_endpoint_plugins.py:107-115).

Extra rules in single plugins.

  • The built-in Hugging Face Hub LoRA resolver registers itself only when VLLM_LORA_RESOLVER_HF_REPO_LIST is set and VLLM_PLUGINS names lora_hf_hub_resolver. When VLLM_LORA_RESOLVER_HF_REPO_LIST is set but the name is missing, it logs a warning, because the resolver downloads files (vllm/plugins/lora_resolvers/hf_hub_resolver.py:129-145).
  • An endpoint plugin also needs a matching task. If its required_tasks does not meet the tasks of the server, vLLM skips it with an INFO log (vllm/plugins/__init__.py:143-154).
  • vllm.logits_processors ignores VLLM_PLUGINS (previous section).

Each group handles errors in its own way. "Logged" means that start-up continues without the plugin.

The guard and a failed plugin. load_general_plugins() sets plugins_loaded = True before it calls the functions (vllm/plugins/__init__.py:85). If a function raises and some code catches the exception, a later call in the same process returns at once. The plugin functions after the failed one then never run in that process. (Derived from lines 82-90.) In the normal start-up, the process logs the exception and ends. The engine core process logs "EngineCore failed to start." and raises the exception again (vllm/v1/engine/core.py:1570-1576). A worker process logs "WorkerProc failed to start." (vllm/v1/executor/multiproc_executor.py:950-957).

The platform detector runs twice. When exactly one out-of-tree platform is active, line 278 calls its function again to get the class name, outside the try block (vllm/platforms/__init__.py:277-279). So a detector must give the same result on each call.

Deep dive

fork, spawn and the once-per-process guard

plugins_loaded is a module global (vllm/plugins/__init__.py:33). What a child process sees depends on how the parent starts it:

  • spawn: the child is a new Python interpreter. It imports vllm.plugins again, so the flag is False and the registries are empty. The child loads the plugins itself.
  • fork: the child gets a copy of the parent's memory. If the parent made them, the copy has the flag, the filled registries and the platform object. Then a call to load_general_plugins() in the child returns at once. (Derived from the fork semantics of the operating system and lines 82-85.)

Which method does vllm serve use?

  1. The CLI calls cli_env_setup() (vllm/entrypoints/cli/main.py:67-68). It sets VLLM_WORKER_MULTIPROC_METHOD=spawn if you did not set the variable (vllm/entrypoints/common/startup.py:147-149).
  2. The default of the variable is fork (vllm/envs.py:938-940). This matters when you use vLLM as a library.
  3. get_mp_context() calls _maybe_force_spawn() (vllm/utils/system_utils.py:185-200). That function forces spawn, for example when CUDA is already initialized or under WSL (vllm/utils/system_utils.py:145-162).
  4. Both the engine core processes (vllm/v1/engine/utils.py:256) and the worker processes (vllm/v1/executor/multiproc_executor.py:723) use this context.

So with vllm serve and the default settings, each engine core and each worker is a spawned child, and it loads the general plugins again. fork applies only when you set VLLM_WORKER_MULTIPROC_METHOD=fork yourself, or when you use vLLM as a library. On a machine with 1 front end, 1 engine core and 4 workers (TP=4), a general plugin function runs 6 times. It runs once more in each model registry subprocess, which runs only on a cache miss (Step 5). (Derived from the call sites in Step 5.)

The model registry subprocess is always a new interpreter. It starts with subprocess.run and sys.executable, not with multiprocessing (vllm/model_executor/models/registry.py:1591-1593).

Deep dive

Platform plugins and general plugins: which loads first?

In every process of vllm serve, the platform resolves before the first general plugin runs. The cause is a module-level from vllm.platforms import current_platform. The name is not a real module attribute, so this import calls the module __getattr__ (PEP 562), and that resolves the platform (vllm/platforms/__init__.py:299-319). (Derived from the imports below.)

  • Front end. vllm/engine/arg_utils.py has this import (vllm/engine/arg_utils.py:122). Both front-end calls of load_general_plugins() are in the same file (lines 924 and 3243), so the import has already run.
  • Engine core process. The spawned child imports the module of its target function, EngineCoreProc.run_engine_core (vllm/v1/engine/utils.py:282-284), before it runs it. To import vllm.v1.engine.core, Python first runs the package file vllm/v1/engine/__init__.py. That file imports from vllm.config (vllm/v1/engine/__init__.py:14). The vllm.config package imports vllm.config.compilation (vllm/config/__init__.py:7), which has the import (vllm/config/compilation.py:22). EngineCore.__init__ runs later.
  • Worker process. The target is WorkerProc.worker_main (vllm/v1/executor/multiproc_executor.py:745-750). To import its module, Python first runs vllm/v1/executor/__init__.py, which imports abstract.py (vllm/v1/executor/__init__.py:3). That file imports vllm.config (vllm/v1/executor/abstract.py:11), so the same chain resolves the platform. The module itself also has the import (vllm/v1/executor/multiproc_executor.py:46). init_worker runs later.
  • Model registry subprocess. registry.py imports vllm.config at module level (vllm/model_executor/models/registry.py:26), before _run() calls load_general_plugins().

So a general plugin cannot change which platform vLLM detects. A platform package that also needs general setup publishes two entry points. vLLM's test platform does this: one in vllm.platform_plugins and one in vllm.general_plugins that registers custom ops (tests/plugins/vllm_add_dummy_platform/setup.py:10-17).

What can go wrong#

An allowlist for one plugin disables the others

Example: you set VLLM_PLUGINS=my_endpoint to enable an endpoint plugin. Then the built-in LoRA resolvers do not load, and your out-of-tree platform plugin does not load. vLLM then uses a built-in platform, or UnspecifiedPlatform (vllm/platforms/__init__.py:285-292). Nothing fails at once. List every plugin name that you need.

  • A plugin is missing, with no error. If the import of a plugin fails, vLLM writes "Failed to load plugin ..." with a traceback, and continues (vllm/plugins/__init__.py:71-72). Look for this line in the log of each process.
  • Start-up stops in one process. An exception in a general plugin function stops the process that runs it (vllm/plugins/__init__.py:89-90). vLLM's own filesystem LoRA resolver raises ValueError when VLLM_LORA_RESOLVER_CACHE_DIR is set to a path that is not a folder (vllm/plugins/lora_resolvers/filesystem_resolver.py:51-57).
  • Side effects run many times. A plugin function runs in each process (previous deep dive). Write it so that it can run again: check before you register, as the test plugin does.
  • A second registration replaces the first. ModelRegistry.register_model overwrites an architecture that is already registered, with only a DEBUG log (vllm/model_executor/models/registry.py:1179-1185).
  • CUDA starts too early. If a plugin imports model code that touches CUDA, the front end can initialize CUDA. Register models as "module:Class" strings. The docstring names the error that this avoids: "Cannot re-initialize CUDA in forked subprocess" (vllm/model_executor/models/registry.py:1167-1174).
  • The docs say "every process". The design doc says that every process created by vLLM needs to load the plugin (docs/design/plugin_system.md:7). In the code, this is true for general and platform plugins only. Three groups load only in the front end (Step 7).

Why it matters. Every extension of vLLM starts with this loading step. To debug a plugin, you must know which process loads it and when. A model plugin that loads in the front end but fails in a worker gives an error only in the worker log. An allowlist that is too short gives no error at all.

    easy

    Only in the front end, in AsyncLLM.__init__ (vllm/v1/engine/async_llm.py:156). The engine core and the workers do not load this group.

  3. 3

    medium
    Show answer

    The first one is skipped with a log line "Failed to load plugin ...", because load() is inside try (vllm/plugins/__init__.py:68-72). The second one stops start-up of the process, because func() is not inside try (vllm/plugins/__init__.py:89-90).

  5. 5
    You run vllm serve with TP=2 and the default settings. How many times does a general plugin function run, and why not only once? Ignore the model registry subprocess.
    hard
    Show answer

    Four times: once in the front end, once in the engine core process, and once in each of the 2 worker processes. The CLI sets the start method to spawn (vllm/entrypoints/common/startup.py:147-149). So each child is a new interpreter with plugins_loaded = False, and it loads again in EngineCore.__init__ (vllm/v1/engine/core.py:132) or init_worker (vllm/v1/worker/worker_base.py:284). With one GPU and no DP, the default executor is uni (vllm/config/parallel.py:1099-1100). It runs the worker inside the engine core process, so the count is two.
