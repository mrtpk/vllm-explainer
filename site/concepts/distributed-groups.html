Process groups: how vLLM slices its ranks

AdvancedvLLM conceptsabout 11 min read + 8 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Tensor and pipeline parallelism in practice Intermediate
  • Executors and workers: from the engine core to the GPUs Intermediate

In one sentence

Each worker arranges all ranks in one grid and cuts it into groups; every collective of the model runs inside one of these groups.

The idea#

Parallel inference splits one model over several GPUs, and the GPUs exchange tensors with collectives such as all-reduce (Parallelism basics↗). A collective always runs inside a process group: a fixed set of ranks that take part together. Tensor parallelism needs one group, pipeline parallelism another, and expert parallelism a third.

vLLM builds all its groups in the same way, in every worker. It numbers the ranks and puts them into a grid with one dimension per kind of parallelism. Then it reads each group off one line of the grid. This order is the rank layout. TP is the last dimension, so the ranks of one TP group are neighbours, and they normally sit on one node.

Each group becomes a GroupCoordinator. It holds two PyTorch groups for the same ranks: a gloo group for small CPU messages and an NCCL group for GPU tensors. When the group has more than one rank, it also holds a device communicator. On CUDA, this object picks the fastest all-reduce for each tensor: for example the custom all-reduce, symmetric memory or plain NCCL.

An everyday comparison. Think of the seat plan of a large exam hall. Each seat has a row and a column. "Row 3" and "column 5" are two different teams, but each seat belongs to exactly one row and one column. The hall manager does not invent the teams one by one; she reads them off the plan. The comparison stops here: a vLLM rank belongs to one group of each kind at the same time. Some groups (EP) also span several rows and columns.

In the code#

Step 1: the worker sets up the groups in init_device#

Each worker builds its groups in init_device, before it takes the memory snapshot. The comment says why: the NCCL buffers must exist before vLLM measures the free memory:

init_worker_distributed_environment first prepares the batch-invariant mode and the EPLB environment variables. Then it does four things in order. It sets the custom all-reduce switch from --disable-custom-all-reduce, creates the world group, creates the model-parallel groups, and starts the EC connector (vllm/v1/worker/gpu_worker.py:1678-1720). The rank and the init method come from the multiproc executor: the global rank of a worker is local_world_size × node_rank_within_dp + local_rank (vllm/v1/executor/multiproc_executor.py:179-192). On one node, the init method is a file:// store in the temp folder, unless AITER needs a TCP store (vllm/v1/executor/multiproc_executor.py:139-144).

Step 2: init_distributed_environment makes the world group#

The first call joins all ranks of this engine into PyTorch's default group. With DP > 1 or several nodes, it first widens the world across the data parallel ranks:

  1. Line 1869. The rank is shifted by data_parallel_rank × world_size. So DP rank 1 of a 4-rank engine starts at global rank 4.
  2. Line 1871. The world grows to world_size_across_dp = TP × PP × PCP × DP (vllm/config/parallel.py:626-629).
  3. Lines 1874-1876. With several nodes, the rendezvous goes to --master-addr and --master-port. Otherwise it goes to the DP master address with a fresh port (lines 1878-1920).

A dense model never takes this branch for DP

For a model without experts, each engine core sets its DP size to 1 before it starts the executor (vllm/v1/engine/core.py:1534-1543, vllm/config/parallel.py:1192-1201). So with -dp 2 and a dense model, each engine core has its own world of TP × PP ranks, and the two worlds never talk. Only a MoE model builds one world over all DP ranks.

The world group itself is a GroupCoordinator over all ranks, with no device communicator (vllm/distributed/parallel_state.py:1507-1516, vllm/distributed/parallel_state.py:2010-2012).

Step 3: initialize_model_parallel reads the groups off the grid#

  1. Lines 2148-2156. The comment gives the layout order: ExternalDP × DP × PP × PCP × TP. ExternalDP is for frameworks that run several independent copies of vLLM in one world.
  2. Lines 2157-2163. One tensor of all ranks, shaped (-1, DP, PP, PCP, TP).
  3. Line 2168. TP groups are rows of the last dimension. No transpose is needed.
  4. Lines 2173-2180. The comment says that only the TP group uses a MessageQueue broadcaster. The DCP group also asks for one, but it has one rank by default (vllm/distributed/parallel_state.py:2248-2254).

The other groups use the comment's recipe: move the dimension to the end, reshape, and unbind. PP uses transpose(2, 4) (vllm/distributed/parallel_state.py:2278-2280), DP uses transpose(1, 4) (vllm/distributed/parallel_state.py:2295). The EP group is only built for MoE models, and it spans DP × PCP × TP ranks of one PP stage:

An EPLB group with the same ranks follows only with --enable-eplb. The comment explains the separate group: EPLB weight transfers must not deadlock with the MoE collectives of the forward pass (vllm/distributed/parallel_state.py:2347-2368). At the end, every rank logs its position, for example "rank 5 in world size 8 is assigned as DP rank 1, …" (vllm/distributed/parallel_state.py:2372-2385).

Step 4: one GroupCoordinator per group#

By default, the constructor makes a PyTorch group for every row, so all ranks take part in every new_group call. Each rank keeps the pair for its own row: an NCCL device_group and a gloo cpu_group (vllm/distributed/parallel_state.py:501-518). Then it adds the optional parts:

  1. Lines 549-560. The device communicator class comes from the platform: CudaCommunicator on CUDA and ROCm (vllm/platforms/cuda.py:581-584). A group with one rank gets none.
  2. Lines 564-567. The shared-memory broadcaster has 6 chunks of 4 MiB (1 << 22). broadcast_object uses it when it exists (vllm/distributed/parallel_state.py:855-866).
  3. Lines 571-574. On platforms that opt in, the collectives go through registered custom ops. CUDA opts in (vllm/platforms/cuda.py:707-709).

Step 5: the CUDA device communicator picks an all-reduce#

CudaCommunicator always makes a PyNcclCommunicator for a group with more than one rank (vllm/distributed/device_communicators/cuda_communicator.py:106-113). The faster kernels are only for TP groups:

At run time, all_reduce tries the implementations in a fixed order and takes the first that accepts the tensor (vllm/distributed/device_communicators/cuda_communicator.py:362-446). On CUDA the chain has six links. They are NCCL symmetric memory (only with VLLM_USE_NCCL_SYMM_MEM=1), the FlashInfer PCIe all-reduce (opt-in), FlashInfer, the custom all-reduce, PyTorch symmetric memory, and pynccl. The size and dtype checks live in each implementation. The start-up log names the enabled ones for each group: "Using [...] all-reduce backends (in dispatch order) for group 'tp:0'" (vllm/distributed/device_communicators/cuda_communicator.py:353-360). The log puts NCCL symmetric memory after the two FlashInfer entries, but all_reduce tries it first (vllm/distributed/device_communicators/cuda_communicator.py:307-337, vllm/distributed/device_communicators/cuda_communicator.py:372-379).

Step 6: the collectives that the model calls#

Model code does not use the groups directly. It calls helpers such as tensor_model_parallel_all_reduce, which forward to the TP group (vllm/distributed/communication_op.py:12-21). The group then calls the registered op:

  1. Lines 740-741. With one rank, the call returns the input. No kernel runs.
  2. Lines 743-744. torch.ops.vllm.all_reduce carries only the group name, a string. The docstring explains why: Dynamo cannot pass the Python object into a custom op (lines 726-737). The op looks the group up by name and calls the device communicator (vllm/distributed/parallel_state.py:199-204, vllm/distributed/parallel_state.py:399-403).
  3. Lines 748-751. The op is out-of-place: it returns a new tensor.

all_gather and reduce_scatter work the same way (vllm/distributed/parallel_state.py:753-798). Pipeline stages use a different pair: isend_tensor_dict and irecv_tensor_dict on the PP group. The worker sends the IntermediateTensors without waiting, and the next stage receives them at the start of its step (vllm/v1/worker/gpu_worker.py:1336-1347, vllm/v1/worker/gpu_worker.py:1371-1378). broadcast_tensor_dict also exists, as a TP-group helper (vllm/distributed/communication_op.py:38-43); no code of Model Runner V2 calls it (derived from git grep).

Deep dive

Worked example: TP = 2 × PP = 2 × DP = 2 on 8 GPUs

vllm serve <an MoE model> -tp 2 -pp 2 -dp 2      # one node, 8 GPUs

Each engine core has world_size = TP × PP = 4 workers. Engine core d gets GPUs 4d to 4d + 3 (vllm/v1/engine/utils.py:441-445). The global rank of a worker is 4 × dp_rank + local rank (Step 2). The grid is arange(8).reshape(1, 2, 2, 1, 2), so rank = 4·dp + 2·pp + tp.

How each column is computed (derived from the lines in Step 3):

  1. TP: view(-1, 2) cuts the flat order 0…7 into pairs.
  2. PP: transpose(2, 4) swaps the PP and TP axes. The rows of length 2 are then (dp, tp) fixed, pp varying: [0, 2], [1, 3], [4, 6], [5, 7].
  3. DP: transpose(1, 4) swaps DP and TP. The rows are (tp, pp) fixed, dp varying: [0, 4], [2, 6], [1, 5], [3, 7].
  4. EP: transpose(1, 2) puts PP before DP. Then each row of DP × PCP × TP = 4 ranks is one PP stage: [0, 1, 4, 5] and [2, 3, 6, 7].
  5. PCP and DCP: both sizes are 1, so there are eight groups of one rank each. They have no device communicator.

The same command with a dense model. Each engine core is reconfigured to DP = 1 (Step 2). So each engine core has its own world arange(4).reshape(1, 1, 2, 1, 2). It has TP groups [0, 1] and [2, 3], PP groups [0, 2] and [1, 3], DP groups of one rank, and no EP group. Rank numbers start at 0 in both engines, and the two engines have separate NCCL communicators.

Deep dive

Global ranks across nodes

A worker's global rank is built in two steps (derived from the cited lines):

  1. The executor of one DP rank numbers its workers across the nodes of that replica: rank = local_world_size × node_rank_within_dp + local_rank (vllm/v1/executor/multiproc_executor.py:179-192). local_world_size is world_size // nnodes_within_dp (vllm/config/parallel.py:838-840).
  2. If the world spans DP ranks or nodes, init_distributed_environment adds data_parallel_rank × world_size (Step 2).

So global = dp_rank × (TP·PP·PCP) + node_rank_within_dp × local_world_size + local_rank.

Example. -tp 8 -pp 2 --nnodes 2 with DP = 1: world_size = 16, local_world_size = 8. Local rank 3 on node 1 has global rank 8 × 1 + 3 = 11. In the grid (1, 1, 2, 1, 8), rank 11 is PP stage 1, TP rank 3. All TP groups stay inside one node; the PP groups [i, i + 8] cross the nodes (derived). The executor's output rank is 16 − 8 = 8, the first TP rank of the last stage (vllm/v1/executor/multiproc_executor.py:549-563).

Deep dive

CUDA graph capture and the groups

Collectives inside a captured CUDA graph need care, because the custom all-reduce must register the buffers that the graph uses. graph_capture() opens one capture stream and enters the capture context of the TP, PP and DP groups (vllm/distributed/parallel_state.py:1693-1726). For each group, the context enters the custom all-reduce capture, and the FlashInfer PCIe and AITER captures when they exist (vllm/distributed/parallel_state.py:673-723). With the sleep-mode cuMem graph pool, the communicators do not register graph buffers; they copy instead (vllm/distributed/device_communicators/cuda_communicator.py:123-125).

What can go wrong#

  • Custom all-reduce turns itself off. On more than two PCIe-only GPUs, or when the P2P test fails, the log says "Custom allreduce is disabled …". The chain then falls through to symmetric memory or pynccl (vllm/distributed/device_communicators/custom_all_reduce.py:270-291). The server still works, but small all-reduces are slower.
  • An unsupported TP size. TP = 3, 5 or 7 is not in the custom all-reduce list; vLLM warns and uses another implementation (vllm/distributed/device_communicators/custom_all_reduce.py:214-222).
  • The wrong network interface. On a multi-node host, get_ip() may pick an interface that the other nodes cannot reach. Set VLLM_HOST_IP on each node (vllm/utils/network_utils.py:52-63).
  • A rank that does not join. new_group is collective: every rank must make every group in the same order. If one worker fails before, the others wait until the PyTorch timeout. --distributed-timeout-seconds sets it (vllm/config/parallel.py:364-368, vllm/v1/worker/gpu_worker.py:1698-1700).
  • Calling get_ep_group() for a dense model. It asserts, because the EP group exists only for MoE models (vllm/distributed/parallel_state.py:1659-1665).

Why it matters. Every multi-GPU feature of vLLM runs on these groups. When you know the rank layout, you can predict which GPUs talk in each collective, and which of them must sit on one node.

Check yourself#

  1. 1
    In which order does vLLM lay out the ranks, and which dimension is the fastest?
    easy
    Show answer

    ExternalDP × DP × PP × PCP × TP, with TP last. So the ranks of a TP group are neighbours (vllm/distributed/parallel_state.py:2148-2163).

  2. 2
    Which group gets a device communicator?
    easy
    Show answer

    Every group with more than one rank, except the world group, which is built with use_device_communicator=False (vllm/distributed/parallel_state.py:549-560, vllm/distributed/parallel_state.py:1507-1516).

  3. 3
    Why does GroupCoordinator.all_reduce call torch.ops.vllm.all_reduce with a group name instead of calling the communicator directly?
    medium
    Show answer

    Dynamo cannot pass the Python group object into a custom op, so the op takes the group's unique name and looks it up. The custom op also stays one opaque node in the compiled graph. The docstring says this (vllm/distributed/parallel_state.py:725-746).

  4. 4
    An MoE model runs with -tp 2 -pp 2 -dp 2 on 8 GPUs. Which ranks are in the DP group and in the EP group of rank 5?
    hard
    Show answer

    Rank 5 is dp 1, pp 0, tp 1 (5 = 4·1 + 2·0 + 1). DP group: transpose(1, 4) keeps tp 1, pp 0 and varies dp: [1, 5]. EP group: the DP × PCP × TP ranks of PP stage 0: [0, 1, 4, 5] (vllm/distributed/parallel_state.py:2295, vllm/distributed/parallel_state.py:2313-2324).

  5. 5
    You serve a dense model with -tp 2 -dp 2. Do the two engine cores share one NCCL world? Why?
    hard
    Show answer

    No. A dense model's engine core calls reconfigure_for_independent_dp_rank(), which sets the DP size to 1 (vllm/v1/engine/core.py:1534-1543, vllm/config/parallel.py:1192-1201). So init_distributed_environment skips the DP widening (vllm/distributed/parallel_state.py:1857-1871), and each engine has its own world of two ranks.

QKVParallelLinear splits by heads and copies KV heads when TP is larger than their count.

API servers pick an engine for each request with a load score; a DP coordinator publishes the load counts. Dense models run independent engines; MoE models step in lockstep, in waves, with dummy batches.
  • Expert parallelism and MoE servingAn MoE layer in vLLM is an MoERunner built by FusedMoEFactory.
