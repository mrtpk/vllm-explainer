Deployment recipes: single GPU, TP, DP, multi-node, load balancers and security

AdvancedvLLM conceptsabout 15 min read + 3 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The process and thread architecture of vllm serve Intermediate
  • The OpenAI-compatible server: launch modes, app, serving classes and streaming Intermediate

In one sentence

Each deployment shape is one vllm serve command per node; the flags decide which processes start, which port answers, and what is protected.

The idea#

vllm serve has one command line, but it starts different sets of processes. The API server can run inside the CLI process or in several child processes. The EngineCore can hold the worker itself or drive one worker process per GPU. A node can also run only workers or only engine cores, with no HTTP port at all (--headless). The page The process and thread architecture of vllm serve explains the processes; this page gives the command for each common shape and what it starts.

The second half of the page is about production. It shows how a load balancer sees a server (/health), how to start and stop it, and which routes need a proxy. --api-key alone does not protect a vLLM server.

An everyday comparison. Think of a kitchen. One cook can do everything at one stove. A large dish can need several cooks at one stove (tensor parallelism). A busy restaurant opens more stoves, each with its own cooks (data parallelism), and a host at the door spreads the guests (the load balancer). The comparison stops at the door. vLLM's lock (the API key) closes only some of the entrances, so the building needs its own guard (a proxy).

The picture#

Read each shape from its command down. Blue boxes serve HTTP (or supervise), violet boxes schedule, green boxes own GPUs. The counts help you size the CPU: each box is at least one busy process.

In the code#

Step 1: how vllm serve picks the shape#

After the flags are parsed, ServeSubcommand.cmd chooses one of four launchers (entrypoints/cli/serve.py: the vllm serve subcommand and its launch modes):

  • run_server: one API server inside the CLI process. This is the default for any TP and PP with DP = 1.
  • run_multi_api_server: more than one API server. The default count is the DP size with internal load balancing (vllm/entrypoints/cli/serve.py:113-130).
  • run_headless: no API server (--headless sets the count to 0, vllm/entrypoints/cli/serve.py:69-77).
  • run_dp_supervisor: one external-LB server per local DP rank, with an aggregated health port (--data-parallel-multi-port-external-lb, vllm/engine/arg_utils.py:1284-1292).

The engine side follows the parallel sizes. The worker runs inside the engine core (the uni executor) only when TP, PP and DP are all 1 (vllm/config/parallel.py:1055, vllm/config/parallel.py:1099-1100). With any larger size, each engine core starts one worker process per GPU (Executors and workers: from the engine core to the GPUs).

Step 2: one GPU, and tensor parallelism on one node#

# Shape A: one GPU (2 processes)
vllm serve Qwen/Qwen3-8B
# Shape B: one model over 2 GPUs of one node (4 processes)
CUDA_VISIBLE_DEVICES=0,1 vllm serve Qwen/Qwen3-8B --tensor-parallel-size 2

-tp and -pp default to 1 (vllm/config/parallel.py:142, vllm/config/parallel.py:140). With TP = 2, the engine core uses the multiprocessing executor and two worker processes, Worker_TP0 and Worker_TP1 (Executors and workers: from the engine core to the GPUs). The attention heads must divide by the TP size (Tensor and pipeline parallelism in practice).

Step 3: data parallelism on one node, and DP + EP for MoE models#

# Shape C: two independent engine copies behind one port (8 processes)
vllm serve Qwen/Qwen3-8B --data-parallel-size 2
# More front-end processes for the same engines
vllm serve Qwen/Qwen3-8B --data-parallel-size 2 --api-server-count 4
# A MoE model: 8 DP ranks, experts spread over all 8 GPUs
vllm serve Qwen/Qwen3-30B-A3B --data-parallel-size 8 --enable-expert-parallel

With -dp N on one node, the CLI process becomes a supervisor. It starts N API servers on one port, a DP coordinator, and N engine cores (Data parallel serving: several engine cores behind one endpoint). For a dense model, the engine cores are independent: each rank is set up like DP = 1 (vllm/v1/engine/core.py:1534-1543). For a MoE model, the ranks are DPEngineCoreProcs that step together in waves. --enable-expert-parallel (off by default, vllm/config/parallel.py:190) shards the experts over the ranks instead of over the TP group (Expert parallelism and MoE serving). The DP coordinator runs for MoE models, and for dense models with internal or hybrid load balancing (vllm/config/vllm.py:854-874).

Step 4: one model over several nodes#

A model that does not fit one node needs TP or PP across nodes. With the default multiprocessing backend, run one command per node. The vLLM docs give this example for 2 nodes with 8 GPUs each (docs/serving/parallelism_scaling.md:143-159):

# node 0 (the head)
vllm serve /path/to/model --tensor-parallel-size 8 --pipeline-parallel-size 2 \
  --nnodes 2 --node-rank 0 --master-addr <HEAD_NODE_IP>
# node 1
vllm serve /path/to/model --tensor-parallel-size 8 --pipeline-parallel-size 2 \
  --nnodes 2 --node-rank 1 --master-addr <HEAD_NODE_IP> --headless

--nnodes, --node-rank and --master-addr are parallel flags (vllm/engine/arg_utils.py:1165-1168). --nnodes must divide the total world size, and it needs the mp DP backend (vllm/engine/arg_utils.py:2379-2402). On node 1, run_headless sees that this node is not the first node of its DP group. Then it only starts a MultiprocExecutor for the local workers, with no engine core and no API server (vllm/entrypoints/cli/serve.py:218-231). The alternative is a Ray cluster with --distributed-executor-backend ray and one command on the head node (docs/serving/parallelism_scaling.md:122-130).

Step 5: data parallelism over several nodes#

To run DP ranks on several nodes with one HTTP endpoint, start the head node with the API servers and the other nodes with --headless. The vLLM docs give this example for DP = 4 over 2 nodes (docs/serving/data_parallel_deployment.md:40-49):

# node 0, address 10.99.48.128: API servers + DP ranks 0 and 1
vllm serve $MODEL --data-parallel-size 4 --data-parallel-size-local 2 \
  --data-parallel-address 10.99.48.128 --data-parallel-rpc-port 13345
# node 1: DP ranks 2 and 3, no API server
vllm serve $MODEL --headless --data-parallel-size 4 --data-parallel-size-local 2 \
  --data-parallel-start-rank 2 \
  --data-parallel-address 10.99.48.128 --data-parallel-rpc-port 13345

The head node runs the API servers (by default one per DP rank, so 4 here), the DP coordinator, and its local engine cores (vllm/entrypoints/cli/serve.py:124-130). On node 1, run_headless starts only the local engine cores, which connect to the head address (vllm/entrypoints/cli/serve.py:235-256).

Step 6: disaggregated prefill and decode#

Disaggregated serving runs prefill and decode on separate vLLM instances and moves the KV cache with a KV connector. Each instance is one of the shapes above, with --kv-transfer-config (vllm/engine/arg_utils.py:1870-1872) and a router in front. The vLLM docs list the reasons, for example control of tail ITL (docs/features/disagg_prefill.md:8-13). The page Disaggregated prefill: prefill and decode on different instances explains the request flow, and KV connectors the connectors.

Step 7: behind a load balancer: independent servers, /health and readiness#

For a dense model, the simplest scale-out is a set of independent servers behind any HTTP load balancer. vLLM refuses the external DP flags for dense models and says why:

So run one plain vllm serve per GPU group, each with its own port or host, and no --data-parallel-* flag. For MoE models, external load balancing keeps one DP group: each server gets --data-parallel-size N --data-parallel-rank i and its own port (docs/serving/data_parallel_deployment.md:104-127).

The load balancer needs a health signal:

  • 200 while the engine runs. A render-only server has no engine and always answers 200 (line 26-28).
  • 503 after engine death: check_health() raises EngineDeadError once the engine has failed (vllm/v1/engine/async_llm.py:1129-1134). A watchdog then stops the server within about 5 s, unless VLLM_KEEP_ALIVE_ON_ENGINE_DEATH=1 (vllm/entrypoints/launchers/launcher.py:314-337). An orchestrator should restart it.
  • No answer during start-up. The API server binds its socket first, then builds the engine, and starts uvicorn last (vllm/entrypoints/launchers/launcher.py:365-379, vllm/entrypoints/launchers/api_server/entry.py:179-201). Until uvicorn runs, the socket is bound but does not listen, so no HTTP request gets an answer (derived; uvicorn calls listen() when it starts, vllm/entrypoints/launchers/launcher.py:84-94). A start-up can take minutes (model download, compile, graph capture).

The readiness probe for vllm serve is GET /health; the vLLM docs use it for both the liveness and the readiness probe in Kubernetes (docs/deployment/k8s.md:244-255). GET /v1/models also answers only when the server is up, and it confirms the served name. The docs warn that a startup probe with a low failureThreshold kills the container during start-up (docs/deployment/k8s.md:436-443). The log then shows "KeyboardInterrupt: terminated". That text comes from the SIGTERM handler that run_server installs during start-up (vllm/entrypoints/launchers/api_server/entry.py:170-175).

Shutdown. --shutdown-timeout N (default 0) lets running requests finish for up to N seconds after a stop signal; 0 aborts them (vllm/engine/arg_utils.py:1930-1935, vllm/config/vllm.py:453-457). Set it a little below the grace period of your orchestrator (a practical rule).

Step 8: Docker, Kubernetes and the recipes folder#

The repository documents containers and orchestrators; this site does not repeat them:

  • Docker: the image vllm/vllm-openai, run with --ipc=host so that processes can share memory (docs/deployment/docker.md:20-30).
  • Kubernetes: a full example with a PVC, probes and /dev/shm (docs/deployment/k8s.md:1-12). Also nginx in front of several servers (docs/deployment/nginx.md), Helm (docs/deployment/frameworks/helm.md), and integrations such as llm-d, KServe and the production stack (docs/deployment/integrations/).
  • recipes/: one YAML deployment recipe per model, at recipes/models/<org>/<repo>.yaml, rendered on recipes.vllm.ai (recipes/README.md:1-12). The schema lives in the separate vllm-project/recipes repository; manifest.yaml only declares the schema version (recipes/manifest.yaml:1-4). A recipe lists, for example, the minimum vLLM version and the extra arguments for tool calling. It also lists variants with --tensor-parallel-size and the needed GPU memory (recipes/models/ByteDance-Seed/Seed-OSS-36B-Instruct.yaml:12-48). Use it as a starting command for that model; the folder holds 186 files under models/ at this commit.

Step 9: security: what --api-key protects#

--api-key protects only four path prefixes

The authentication middleware checks the key only for paths that start with /v1, /v2, /inference or /cohere:

Every other route answers without a key (vllm/entrypoints/serve/middleware/authenticate.py:59-61). Every server registers the SageMaker routes /ping and /invocations (vllm/entrypoints/launchers/api_server/routers.py:40-44). /invocations picks a handler by the shape of the body. It runs the same serving objects as the /v1 routes, so a client without the key can still generate text (vllm/entrypoints/serve/sagemaker/api_router.py:98-132). vLLM's own help text of --api-key says this and names /invocations; it lists /v1, /v2 and /inference and leaves out /cohere (vllm/entrypoints/common/cli_args.py:326-336).

A server that serves a generative model also registers POST /scale_elastic_ep (vllm/entrypoints/launchers/api_server/routers.py:55-66). Its path is outside the guarded prefixes. The handler reads new_data_parallel_size and drain_timeout from the request body and passes them to engine_client.scale_elastic_ep (vllm/entrypoints/serve/elastic_ep/api_router.py:38-65, vllm/v1/engine/async_llm.py:1291).

Without --enable-elastic-ep, the call cannot change the engines of a default deployment. The same DP size is a no-op that answers HTTP 200 (vllm/v1/engine/async_llm.py:1301-1308, vllm/entrypoints/serve/elastic_ep/api_router.py:66-70). With one engine, the base client raises NotImplementedError, and the route answers HTTP 500 "Scale failed" (vllm/v1/engine/core_client.py:274-275, vllm/entrypoints/serve/elastic_ep/api_router.py:79-81). With DP > 1 and external load balancing, the client raises "Elastic EP scaling requires enable_elastic_ep=True." (vllm/v1/engine/core_client.py:1659-1664). With internal load balancing and the default mp backend, an assertion fails (vllm/v1/engine/core_client.py:1920-1922). Expert parallelism and MoE serving has the full table. The route is still reachable without a key.

Also open: /health, /ping, /metrics, /tokenize, /detokenize, /version, /load, and the profiler and development routes when they are on. Two more groups run the model without a key: POST /generative_scoring on every generative server (vllm/entrypoints/generate/api_router.py:52-54, vllm/entrypoints/generate/generative_scoring/api_router.py:30-31), and /pooling, /classify, /score and /rerank on a pooling server (vllm/entrypoints/pooling/pooling/api_router.py:27-28, vllm/entrypoints/pooling/classify/api_router.py:26, vllm/entrypoints/pooling/scoring/api_router.py:37-38, vllm/entrypoints/pooling/scoring/api_router.py:69-70).

A secure deployment therefore puts a proxy in front of vLLM (a practical rule that the vLLM docs also give, docs/usage/security.md:280-286):

  1. Let the proxy pass only the routes your clients need, for example /v1/chat/completions and /v1/models. Block /invocations, /ping, /scale_elastic_ep, /generative_scoring and everything else from outside.
  2. Do the authentication and rate limits in the proxy. Keep --api-key as a second check.
  3. Expose /health and /metrics only to your orchestrator and your monitoring.
  4. Bind vLLM to a private address (--host), not to all interfaces.

Traffic between nodes (PyTorch distributed, KV transfer, DP) is not encrypted; the docs require an isolated network for it (docs/usage/security.md:3-10).

Deep dive

Worked example: from one GPU to two nodes

A team serves an 8B dense model. The steps below are advice; each one names the flag and the shape.

  1. One GPU (shape A). Check the start-up log for the maximum concurrency (Tuning vLLM: throughput and latency knobs, their real defaults and what each one does). Put a proxy in front (Step 9).
  2. More traffic, one node with 4 GPUs. The model fits one GPU. So use -dp 4 for four copies behind one port (Step 3), or four independent servers behind your own load balancer (Step 7). -dp 4 gives 4 API servers by default; the log line then stops, so use /metrics (Metrics and observability: how to watch a vLLM server).
  3. Two nodes. Either one server per node behind an external load balancer, or one DP group over both nodes with --headless on node 1 (Step 5). For a dense model, the first is simpler: a failure stays on one node.
  4. A model that does not fit one node: TP inside the node, PP or TP across nodes (Step 4), on a fast and isolated network.
Deep dive

What each process of a shape logs

Each process puts a prefix on its log lines, so you can tell them apart in one container log. The prefixes are (APIServer pid=...), (EngineCore pid=...) (EngineCore_DP0 and so on with DP) and Worker_TP0 and so on for the workers (vllm/entrypoints/launchers/api_server/entry.py:166, vllm/v1/engine/core.py:1467-1472, vllm/v1/engine/utils.py:284). A worker name gets a _DP, _PP or _TP part only when that size is above 1 (vllm/v1/executor/multiproc_executor.py:1101-1112). With several API servers, they are named ApiServer_0, ApiServer_1, ... (vllm/v1/utils.py:248-254). The page Tour: Start-up of vllm serve follows the start-up log of shape A line by line.

What can go wrong#

  • "Non-MoE models do not support external data parallel mode." You used --data-parallel-rank or --data-parallel-external-lb with a dense model; start independent servers instead (Step 7).
  • Pods restart during start-up. The probe gives up before the model is loaded and compiled; raise the startup probe threshold (Step 7).
  • A dead engine stays in the pool. /health answers 503, but the load balancer checks only the TCP port. Use an HTTP health check on /health.
  • Text generation without a key. /invocations is open on every server (Step 9).
  • Multi-node hangs at start-up. Wrong network interface or blocked ports; see Troubleshooting vLLM: symptom, cause and fix.
  • Two servers on one GPU fail to start. Each --gpu-memory-utilization is a share of the whole GPU, and the second server finds too little free memory (vllm/v1/worker/utils.py:761-770).

Why it matters. The shape decides the process count, the CPU need, the failure domain and which signals you can read. The security section decides who can use your GPUs. Both are deployment decisions that no tuning flag can fix later.

Check yourself#

  1. 1
    Which paths does --api-key protect?
    easy
    Show answer

    Only paths that start with /v1, /v2, /inference or /cohere (vllm/entrypoints/serve/middleware/authenticate.py:11, vllm/entrypoints/serve/middleware/authenticate.py:59-61). /invocations, /ping, /scale_elastic_ep, /generative_scoring, /health, /metrics and the other routes need no key.

  2. 2
    What does GET /health answer after the engine core process has died?
    easy
    Show answer

    503, because check_health() raises EngineDeadError (vllm/entrypoints/serve/instrumentator/health.py:29-33, vllm/v1/engine/async_llm.py:1133-1134). Soon after, the watchdog stops the server unless VLLM_KEEP_ALIVE_ON_ENGINE_DEATH is set (vllm/entrypoints/launchers/launcher.py:325-337).

  3. 3
    You start vllm serve M -tp 8 -pp 2 --nnodes 2 --node-rank 1 --master-addr X --headless on the second node. Which processes run there?
    medium
    Show answer

    run_headless sees that this node is not the first node of its DP group. It starts only a MultiprocExecutor with the local workers: the CLI process plus 8 worker processes, with no engine core and no API server (vllm/entrypoints/cli/serve.py:218-231).

  4. 4
    Why does vllm serve M -dp 2 print no "Avg prompt throughput" log line, while vllm serve M does?
    medium
    Show answer

    -dp 2 defaults to 2 API servers (vllm/entrypoints/cli/serve.py:124-130), and with more than one API server the log-line logger is not added (vllm/v1/metrics/loggers.py:1384-1389). Prometheus still works.

  5. 5
    You want four independent copies of a dense 8B model on one 4-GPU node, behind your company's load balancer, with one port each. Which commands do you use, and why not --data-parallel-external-lb?
    hard
    Show answer

    Four plain commands, for example CUDA_VISIBLE_DEVICES=i vllm serve M --port 800i for i = 0 to 3, each without --data-parallel-* flags.
