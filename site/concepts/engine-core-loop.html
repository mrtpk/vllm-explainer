The engine core loop: threads, queues and the busy loop

IntermediatevLLM conceptsabout 16 min read + 5 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The process and thread architecture of vllm serve Intermediate
  • The engine client: AsyncLLM in the API server Intermediate

In one sentence

The engine core process decodes requests in an input thread, runs engine steps in a busy loop, and sends results from an output thread.

The idea#

The EngineCore is the part of vLLM that decides what the GPU does next. In vllm serve it runs in its own process, one per data parallel rank. The page The process and thread architecture of vllm serve shows where this process sits. This page looks inside it.

The process has one job that must never wait: keep the GPU busy with engine steps. Other work can wait a little. Requests arrive as msgpack bytes and must be decoded. Results must be encoded and sent back. So the process uses three threads:

  • The input thread receives bytes on ZMQ sockets, decodes them and builds the engine's Request objects. It puts them into input_queue.
  • The main thread runs the busy loop. It takes the requests from input_queue, gives them to the scheduler, runs one engine step, and puts the results into output_queue.
  • The output thread takes the results from output_queue, encodes them and sends them back to the front end.

With async scheduling (the default), the busy loop does not wait for a step right after it starts it. Without pipeline parallelism, it keeps up to two steps in a batch queue: it starts step N+1 first, and only then waits for step N. The idea of an engine step loop is the same as in The engine step loop↗. The page Async scheduling: overlap the CPU and the GPU explains the overlap.

An everyday comparison. Think of a kitchen with a pass-through window on each side. One person takes the order slips from the left window and sorts them. The chef cooks, and starts the next pan before the last one is ready. A third person puts the finished plates through the right window. The chef never walks to a window. The comparison stops in one place: in Python, the three people share one lock, the GIL. The design works because socket I/O releases the GIL, and the chef often waits for the GPU anyway.

The picture#

Read panel 1 from left to right: bytes come in on the left and go out on the right. Only the violet box touches the scheduler and the executor. Panel 2 shows why the first call of step_with_batch_queue returns nothing: the queue is not full yet. From the second call on, each call returns the outputs of the step before.

In the code#

Step 1: the process starts in run_engine_core#

The engine core client starts one process per local data parallel rank. Its target is EngineCoreProc.run_engine_core (vllm/v1/engine/utils.py:279-288). This static method sets the process title, installs signal handlers and picks the class:

  1. Line 1534: only an MoE model with DP > 1 gets a DPEngineCoreProc (Step 11).
  2. Line 1542: every other engine core treats itself as DP = 1. Dense DP ranks are independent.
  3. Line 1558: run_busy_loop() runs until shutdown. It never returns normally; it raises SystemExit (vllm/v1/engine/core.py:1620).

The signal handler only marks the shutdown as requested. It does not stop the process at once (vllm/v1/engine/core.py:1510-1531). The busy loop sees the flag on its next turn (Step 4).

Step 2: the handshake, the heavy start-up and the ready messages#

EngineCoreProc.__init__ makes the two queues first. The executor failure callback already points at input_queue:

Then it does a handshake with the front end on a separate ZMQ DEALER socket. The engine sends HELLO and waits up to 5 minutes for an init message with the socket addresses (vllm/v1/engine/core.py:1395-1413, vllm/v1/engine/core.py:113). Inside the with block of this handshake, it runs all the heavy start-up:

super().__init__ is EngineCore.__init__. It loads the general plugins and builds the executor, with the workers and the model. Then it profiles the memory, allocates the KV cache and makes the scheduler (vllm/v1/engine/core.py:129-185). Then it sets up the batch queue and picks the step function:

max_concurrent_batches is pp_size + 1 with async scheduling and Model Runner V2, so 2 on one GPU (vllm/config/vllm.py:586-597). Then the I/O threads start (vllm/v1/engine/core.py:1238-1265). Two "ready" messages go out:

  1. The input thread sends an EngineCoreReadyResponse on each input socket. A ROUTER socket can only send to a peer that has sent to it first (vllm/v1/engine/core.py:1961-1968). The client waits for this message, with the timeout VLLM_ENGINE_READY_TIMEOUT_S (vllm/v1/engine/core_client.py:753-771).
  2. When the with block ends, the engine sends {"status": "READY"} on the handshake socket (vllm/v1/engine/core.py:1364-1386). The start-up code of the front end waits for it, with no time limit. It stops only when an engine process exits (vllm/v1/engine/utils.py:1434-1470, vllm/v1/engine/utils.py:1547).

Step 3: the input thread decodes and preprocesses#

  1. Line 1978: poller.poll() blocks until a socket has a message. ZMQ releases the GIL while it waits.
  2. Line 1980: the first frame is the request type, one byte: ADD, ABORT, START_DP_WAVE or UTILITY (vllm/v1/engine/__init__.py:300-312).
  3. Lines 1991-1993: an ADD is decoded into an EngineCoreRequest. Then preprocess_add_request makes the Request, with its block hashes, in this thread (vllm/v1/engine/core.py:1114-1136). Its docstring says why: so request set-up runs "in parallel with Model forward" (vllm/v1/engine/core.py:1115-1119).
  4. Lines 1999-2008: a request that fails here does not stop the thread. The engine sends a finish output with an error for that request only (vllm/v1/engine/core.py:2149-2167).
  5. Line 2025: an ABORT goes into aborts_queue as well (Step 9).
  6. Line 2028: everything goes into input_queue, in arrival order.

The fields of EngineCoreRequest and Request are on Data contracts between the parts of vLLM.

Step 4: the busy loop#

_handle_shutdown() returns true while the engine runs. After a signal it aborts or drains the requests, and it returns false when no work is left (vllm/v1/engine/core.py:1691-1737). Each turn has two parts: drain the input queue, then run one step. _maybe_publish_request_counts does something only for data parallel load balancing (vllm/v1/engine/core.py:1622-1633).

  1. Line 1671: step_fn is step_with_batch_queue by default (Step 5). It returns a dict from client index to EngineCoreOutputs, or None.
  2. Lines 1673-1674: each output goes into output_queue as a pair (client_index, outputs).
  3. Line 1676: post_step takes draft tokens from the workers, but only without async scheduling (vllm/v1/engine/core.py:689-696).
  4. Lines 1681-1682: if no model ran but requests wait (for example for remote KV), the loop sleeps 1 ms so other threads can run.

Step 5: step() and step_with_batch_queue()#

EngineCore.step() is the simple loop: schedule, run, wait, sample, update. It waits for each step before it schedules the next one:

The engine uses it only when there is no batch queue, for example with --no-async-scheduling and no pipeline parallelism (vllm/v1/engine/core.py:227-229). The default is step_with_batch_queue(). Its docstring gives the rule: "fulfilling the batch queue has a higher priority than getting model outputs" (vllm/v1/engine/core.py:701-713). The core lines:

  1. Line 725: the scheduler makes the plan of step N+1. The page The V1 scheduler: one token budget, no phases explains it.
  2. Lines 727-729 and 743-745: execute_model and sample_tokens both get non_block=True. They return futures.
  3. Line 749: with structured output, sampling can wait for the previous step (see Async scheduling: overlap the CPU and the GPU).
  4. Lines 753-759: the new step goes to the left end of the queue. If the queue is not full, the function returns None at once.
  5. Line 768: else it takes the oldest step from the right end, and line 773 waits for its result.
  6. Lines 782-783: it applies the aborts that came in meanwhile, then update_from_output makes the outputs.

The tour Tour: One engine step follows one call of this function with real numbers.

Step 6: when there is no work#

The busy loop does not spin when the engine is idle. _process_input_queue blocks on input_queue.get() while has_work() is false:

  1. Line 1638: the wait loop runs only while there is no work and no shutdown.
  2. Lines 1648-1651: process_input_queue_block is True for an engine core process (vllm/v1/engine/core.py:1217). So the thread sleeps in get() and uses no CPU.
  3. Lines 1662-1664: when there is work, the loop still takes every message that is already queued, without a wait.

has_work() is also true while the batch queue is not empty. So after the last request finishes, the loop runs until the last in-flight step is processed. A signal during an idle wait puts a WAKEUP message into the queue, so the loop can see the shutdown (vllm/v1/engine/core.py:1503-1508).

Step 7: the output thread#

  1. Line 2065: the thread blocks until an output is ready.
  2. Lines 2066-2069: ENGINE_CORE_DEAD goes to every front end, and the thread stops (Step 10).
  3. Lines 2074-2079: client index -1 means the DP coordinator (load counts and wave messages).
  4. Lines 2088-2091: encode_into writes into a reused buffer, and the message goes to the socket of the front end that sent the request. A tracker tells when ZMQ has finished with the buffer.

Step 8: utility calls#

A utility call is a remote method call from the front end, for example get_supported_tasks, sleep or collective_rpc. The input thread decodes it into (client_idx, call_id, method_name, args) (vllm/v1/engine/core.py:2009-2011). The busy loop runs it between two steps:

  1. Lines 1758-1761: the method is looked up by name on the engine object, inside the call. So a wrong name becomes a failure message, not a crash.
  2. Lines 1828-1834: a method can return a Future. Then the reply waits until the future is done. sleep() uses this when the pause is not complete yet: it frees GPU memory only after the engine has no more work (vllm/v1/engine/core.py:994-1017).
  3. Lines 1836-1838: an exception becomes failure_message in the UtilityOutput; the engine keeps running.

The reply travels in EngineCoreOutputs.utility_output to the front end that asked (vllm/v1/engine/__init__.py:254-263). The client side is on v1/engine/core_client.py: the engine core clients.

Step 9: aborts#

An abort arrives when a client disconnects or a stop string matches in the front end (The engine client: AsyncLLM in the API server). The input thread puts it into two queues. The comment explains why: aborts can act early, and the order in input_queue stays correct (vllm/v1/engine/core.py:2020-2025). The early path runs just before update_from_output:

abort_requests calls scheduler.finish_requests(..., FINISHED_ABORTED), which frees the blocks (vllm/v1/engine/core.py:554-559). The same ABORT then comes again from input_queue; this is safe because "aborting in the scheduler is idempotent" (vllm/v1/engine/core.py:2021-2024). A step that was already running for an aborted request still finishes on the GPU. update_from_output skips its results, because the request is finished (vllm/v1/core/sched/scheduler.py:2184-2192).

Step 10: errors and engine death#

Three kinds of error reach the engine core:

  • One request is bad. The input thread sends an error output for that request and continues (Step 3).
  • A worker process dies. The executor's monitor calls the failure callback, which puts EXECUTOR_FAILED into input_queue (vllm/v1/engine/core.py:1174-1176). The busy loop raises RuntimeError("Executor failed.") (vllm/v1/engine/core.py:1766-1767).
  • Any exception in the busy loop, for example from execute_model. For an error in the model launch or in the wait for its result, log_error_detail first dumps the scheduler output and stats (vllm/v1/engine/core.py:561-575).

An exception that leaves run_busy_loop reaches run_engine_core:

The engine puts ENGINE_CORE_DEAD into the output queue and gives the output thread 5 seconds to send it. The front end then raises EngineDeadError. The page The engine client: AsyncLLM in the API server shows what the API server does next. Open streams get errors, and /health returns HTTP 503 (vllm/entrypoints/serve/instrumentator/health.py:32-33). The server shuts down unless VLLM_KEEP_ALIVE_ON_ENGINE_DEATH is set (vllm/entrypoints/launchers/launcher.py:332-337).

Fault tolerance is off by default

run_busy_loop has the decorator fault_tolerant_wrapper. It re-raises at once unless enable_fault_tolerance is set (vllm/v1/fault_tolerance/engine_core_sentinel.py:172-194, vllm/config/parallel.py:466).

Step 11: DPEngineCoreProc, the data parallel variant for MoE#

With DP > 1, the ranks of a dense model are "completely independent" (the comment at vllm/v1/engine/core.py:1539). The ranks of an MoE model are not. The docs say why: the expert layers of all ranks must synchronize in every forward pass. So the forward passes of all ranks must be aligned (docs/serving/data_parallel_deployment.md:9, Expert parallelism↗). DPEngineCoreProc changes the busy loop in two ways:

  1. Dummy batches. Assume that this rank ran no step, but the group still runs. Then the rank runs execute_dummy_batch(), so the collectives of the other ranks do not hang (lines 2486-2495).
  2. Waves. All ranks agree, with an all-reduce, whether any rank has unfinished requests. They check at the first step of a wave and then only every dp_sync_interval steps, default 16 (vllm/v1/engine/core.py:2542-2559, vllm/config/parallel.py:163). When no rank has work, the wave ends and the engines pause. A new request starts the next wave (vllm/v1/engine/core.py:2360-2373).

The page Data parallel serving: several engine cores behind one endpoint explains waves, the coordinator and load balancing.

Deep dive

step_with_batch_queue(), line by line

  1. Line 720. The function must only be called when the queue has room. The busy loop guarantees this: every call that fills the queue also pops one step.
  2. Line 724. has_requests() is true for unfinished requests and for finished requests that the workers do not know yet. With a KV or EC connector, it is also true while the connector has pending push work (vllm/v1/core/sched/scheduler.py:2922-2937).
  3. Line 725. _should_throttle_prefills() is always false for a plain engine core (vllm/v1/engine/core.py:652-655). Only the DP engine overrides it.
  4. Lines 726-729. log_error_detail wraps the launch, so a launch error dumps the scheduler state.
  5. Lines 730-731. A step with zero scheduled tokens does not count as executed. A multimodal encoder-only instance never counts.
  6. Lines 733-735. A pooling model, or a step with no tokens, needs no sampling. The future of execute_model is the result.
  7. Lines 737-745. Normal case: compute the grammar bitmask now (on the CPU, while the GPU runs the forward pass), then queue sampling.
  8. Lines 746-749. Deferred case: a structured output request still waits for its previous token, so the bitmask cannot be computed yet.
  9. Lines 751-759. A queue entry is a tuple (sample future, SchedulerOutput, execute future) (vllm/v1/engine/core.py:206-208). The function returns early only if the queue has room and there is more to do.
  10. Lines 761-765. No requests and an empty queue: nothing to do.
  1. Line 768. pop() takes the right end, the oldest step, because new steps go in with appendleft.
  2. Lines 773-778. A None result from sample_tokens means that execute_model failed. The code calls exec_model_fut.result() to raise that error.
  3. Lines 789-791. The comment gives the trade-off of the deferred case: handle it here, which "slightly favors TTFT over TPOT/throughput".
  4. Lines 792-810. Now the previous token is known. The code computes the bitmask, starts sampling for the deferred step and puts it into the queue.

Worked example: the batch queue over five calls

One request decodes alone. Queue size 2. "S k" = schedule and start step k; "U k" = wait for step k and update.

CallQueue beforeWorkQueue afterReturns
1[]S 1[1]None
2[1]S 2, U 1[2]token of step 1
3[2]S 3, U 2[3]token of step 2
4 (step 3 sampled EOS)[3]S 4, U 3[4]token of step 3, finish reason
5[4]S 5 with 0 tokens (it only tells the workers that the request finished), U 4[5]nothing for the finished request
6[5]no requests; U 5 only[]nothing; then has_work() is false and the loop blocks

Call 5 still schedules, because a finished request counts in has_requests() until its id goes out in a SchedulerOutput (vllm/v1/core/sched/scheduler.py:2913-2914, vllm/v1/core/sched/scheduler.py:1597-1601). schedule() then clears the set, so call 6 finds no requests (vllm/v1/core/sched/scheduler.py:1731-1734). Step 4 ran on the GPU for a request that was already finished. Its result is ignored (vllm/v1/core/sched/scheduler.py:2184-2192). This extra step is the cost of the overlap. The scheduler avoids it only when it is sure that max_tokens is reached (vllm/v1/core/sched/scheduler.py:720-734). (Table derived from vllm/v1/engine/core.py:724-785.)

Deep dive

Shutdown, step by step

  1. SIGTERM or SIGINT sets shutdown_state = REQUESTED and triggers the wakeup callback (vllm/v1/engine/core.py:1510-1528).
  2. The next _handle_shutdown() picks a mode from shutdown_timeout: 0 (the default) aborts all requests; a positive value drains them (vllm/v1/engine/core.py:1696-1727, vllm/config/vllm.py:453).
  3. In both modes new ADD messages get an ABORT output (vllm/v1/engine/core.py:1773-1782) and utility calls fail with "Server shutting down" (vllm/v1/engine/core.py:1806-1820).
  4. When has_work() is false, the loop ends and raises SystemExit. The finally block calls engine_core.shutdown(), which shuts down the executor and the scheduler (vllm/v1/engine/core.py:824-840).

What can go wrong#

  • The engine core does not become ready. Loading, profiling and CUDA-graph capture all run inside the handshake (Step 2). With one API server, the API server starts the engine and waits with no time limit (vllm/v1/engine/core_client.py:695-710, vllm/v1/engine/utils.py:1388-1395). With more than one API server, the API server processes start before the engines are ready (vllm/entrypoints/cli/serve.py:336-382). Then a slow model load can hit VLLM_ENGINE_READY_TIMEOUT_S in each API server (vllm/v1/engine/core_client.py:756-768).
  • "EngineCore failed to start." An exception before the busy loop starts. Look at the traceback in the engine core log (vllm/v1/engine/core.py:1571-1572).
  • "EngineCore encountered a fatal error." An exception in a step, for example a CUDA error or an out-of-memory error. Every open request fails with EngineDeadError (vllm/v1/engine/core.py:1573-1575).
  • "Executor failed." A worker process died (vllm/v1/engine/core.py:1766-1767). The worker log has the cause; see Executors and workers: from the engine core to the GPUs.
  • A slow input thread. Request set-up (block hashes, multimodal features, grammar set-up) runs in the input thread, not in the busy loop. Many large prompts at once can delay new requests, but not running steps.
  • One extra step after a stop. With async scheduling, a request that stops on EOS has already a next step on the GPU. The scheduler ignores that result (Deep dive, worked example).

Why it matters. Almost every performance question about vLLM comes down to one question: is the GPU always busy? The three threads and the batch queue are vLLM's answer. In a profile, a gap between two GPU steps means that this loop waited. It waited for the scheduler, for a deferred grammar bitmask, or for the input queue.

Check yourself#

  1. 1
    Which thread of the engine core process builds the Request object of a new request?
    easy
    Show answer

    The input thread. After it decodes the EngineCoreRequest, it calls preprocess_add_request, which makes the Request with its block hashes (vllm/v1/engine/core.py:1991-1993, vllm/v1/engine/core.py:1114-1128). The main thread only calls add_request later.

  2. 2
    What does the busy loop do when no request is waiting or running?
    easy
    Show answer

    It blocks in input_queue.get(), because process_input_queue_block is True and has_work() is false (vllm/v1/engine/core.py:1638-1651, vllm/v1/engine/core.py:1217). It uses no CPU until a message arrives.

  3. 3
    The batch queue has size 2. Why does the first call of step_with_batch_queue return no outputs?
    medium
    Show answer

    After it starts step 1, the queue holds one entry, which is less than 2, and the scheduler still has requests. So the function returns None before it waits for any result (vllm/v1/engine/core.py:753-759). The outputs of step 1 come in the second call, after step 2 is started.

  4. 4
    An ABORT arrives while a step runs on the GPU. Which two paths handle it, and why is the second one harmless?
    medium
    Show answer

    The input thread puts it into aborts_queue and into input_queue (vllm/v1/engine/core.py:2020-2028). _process_aborts_queue applies it just before update_from_output (vllm/v1/engine/core.py:780-782). The copy in input_queue calls finish_requests again, which is idempotent (vllm/v1/engine/core.py:2021-2024).

  5. 5
    A request has structured output and async scheduling is on. Why can step_with_batch_queue not call sample_tokens right after execute_model, and what does it do instead?
    hard
    Show answer

    The grammar bitmask of step N+1 depends on the token of step N, which is still in flight. AsyncScheduler marks this with pending_structured_output_tokens (vllm/v1/core/sched/async_scheduler.py:37-39). The engine then keeps the scheduler output as deferred_scheduler_output, first processes step N, and only then computes the bitmask and queues sampling (vllm/v1/engine/core.py:746-749, vllm/v1/engine/core.py:792-810).
