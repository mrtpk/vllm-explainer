Hooks in the engine core and the workers

AdvancedvLLM conceptsabout 10 min read + 2 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • All the ways to extend vLLM Intermediate
  • Executors and workers: from the engine core to the GPUs Intermediate

In one sentence

The engine core and the workers read class names from config fields and registries. That is how you replace the scheduler, the worker or the loader.

The idea#

The EngineCore process runs the scheduler. Each worker owns one GPU, builds the model and runs it (Executors and workers: from the engine core to the GPUs). These parts have extension points of two kinds:

  • Config hooks. A field of VllmConfig holds a class name, for example --scheduler-cls my_pkg.sched.MyScheduler. The front end parses it, the other processes get it inside the pickled config, and each process imports the class itself. No registration is needed.
  • Registries. A module-level table maps a name to a class, for example --load-format values to model loaders. A general plugin fills it in every process.

One more extension point is an entry-point group: vllm.logits_processors. vLLM loads it in the workers, and in the front end for a request check.

An everyday comparison. Think of a theatre production. The director's script names the actors for the main roles: the scheduler, the worker, an extra helper. Every theatre that plays the script hires these actors itself. The prop room has labelled shelves (registries) that a stage manager fills before the show. The comparison stops here: in vLLM each process is its own theatre, and a shelf filled in one process is empty in the next.

The picture#

Read the numbers in order. Violet items are config fields, blue items are registries, green items load plugins. With one GPU, the uni executor runs panel 2 inside the engine core process.

In the code#

Step 1: scheduler_cls#

The field takes a class or a dotted name (vllm/config/scheduler.py:175-180). The engine core resolves it after the KV cache plan (vllm/v1/engine/core.py:160-164):

  1. Lines 232-239. Not set: AsyncScheduler when async scheduling is on, else Scheduler. VllmConfig turns async scheduling on when no option conflicts with it (vllm/config/vllm.py:1664-1698).
  2. Lines 243-253. A class object, or a string that does not start with vllm., logs a WARNING once. It says that the interface "is not public", and that a subclass of Scheduler instead of AsyncScheduler turns async scheduling off.
  3. Lines 254-256. A class object is used as it is; a string is split at the last dot (vllm/utils/import_utils.py:119-123). From the CLI the value is always a string, so write pkg.module.Class, not pkg.module:Class.

The test passes a class object, because it builds the engine in the same process:

With vllm serve, the engine core is a separate process, so pass a dotted name that the engine core can import.

Step 2: worker_cls and worker_extension_cls#

Both are strings in ParallelConfig; worker_cls defaults to "auto", which the platform replaces (vllm/config/parallel.py:306-312, vllm/platforms/cuda.py:330-331). The worker wrapper resolves both in init_worker:

  1. Lines 293-302. worker_cls must be a string. A class object raises ValueError "passing worker_cls is no longer supported".
  2. Lines 310-321. Each attribute of the extension must be new, except names that start with __. An assert stops start-up when the worker class has it already. Callable attributes are listed as "extended collective_rpc calls".
  3. Lines 323-325. The extension becomes an extra base class of the worker class. The worker object made at line 347 has its methods.

The wrapper also calls an optional hook init_worker_extension(worker) after init_device (vllm/v1/worker/worker_base.py:356-363).

The extension's methods are reached with collective_rpc by name. In each worker, run_method looks the name up on the wrapper, which forwards unknown names to the worker (vllm/v1/serial_utils.py:485-508, vllm/v1/worker/worker_base.py:365-366). AsyncLLM has collective_rpc (vllm/v1/engine/async_llm.py:1247). Over HTTP, the route POST /collective_rpc exists only with VLLM_SERVER_DEV_MODE, and its comment says that it passes only serialized string arguments (vllm/entrypoints/launchers/api_server/routers.py:46-49, vllm/entrypoints/serve/dev/rpc/api_router.py:43-50). An endpoint plugin is the normal way to expose such a method (Plugins in the API server).

vllm serve Qwen/Qwen3-0.6B --worker-extension-cls my_pkg.ext.WeightSync
# an endpoint plugin, or code with the engine client, then calls:
#   await engine_client.collective_rpc("update_weights_from", args=("s3://...",))

Step 3: logits processors#

A logits processor changes the logits of the batch before sampling. Two sources feed Model Runner V2, and the loader combines them:

  • The group vllm.logits_processors. The loader calls entry_points() directly, so VLLM_PLUGINS does not filter it. A failed import raises RuntimeError; a class that is not a V2 LogitsProcessor raises ValueError (vllm/v1/worker/gpu/sample/logits_processor/loader.py:37-74).
  • The field logits_processors (--logits-processors): classes or "module:Class" strings, with exactly one colon (vllm/config/model.py:407-409, vllm/v1/worker/gpu/sample/logits_processor/loader.py:99-104).

The model runner builds them in load_model (vllm/v1/worker/gpu/model_runner.py:463-466). A pooling model with custom processors raises (vllm/v1/worker/gpu/sample/logits_processor/loader.py:172-179). The front end loads the same classes once, to call validate_params for each request (vllm/v1/engine/input_processor.py:93-107, vllm/v1/worker/gpu/sample/logits_processor/loader.py:186-211).

The V2 interface has five methods:

BatchUpdate belongs to the V1 interface

BatchUpdate is part of the older interface in vllm/v1/sample/logits_processor/ (vllm/v1/sample/logits_processor/interface.py:37). Model Runner V2 does not use it. A processor sees each new request in add_request, keyed by a recycled slot index. It sees the batch layout in apply (vllm/v1/worker/gpu/sample/logits_processor/interface.py:92-107). A plugin written for the V1 interface is rejected at load (loader lines 67-72). The page Sampling and logits processors in Model Runner V2 explains where apply runs in the sampler.

Step 4: model loaders#

A model loader builds the model and loads its weights for one --load-format. The table and the register function:

A taken name logs a WARNING and is overwritten; a class that is not a BaseModelLoader raises ValueError. load_format accepts any string and is lower-cased (vllm/config/load.py:30, vllm/config/load.py:136-138). The worker calls get_model_loader in load_model (vllm/v1/worker/gpu/model_runner.py:398-406). A loader implements download_model and load_weights (vllm/model_executor/model_loader/base_loader.py:38-47); the test is a minimal one (tests/model_executor/model_loader/test_registry.py:19-33). The page "Weight loading: from checkpoint files to GPU parameters" explains the default loader.

Step 5: sleep-mode backends#

Sleep mode frees GPU memory of an idle engine. --enable-sleep-mode turns it on (vllm/config/model.py:370-372). The field docstring says "only cuda and hip", but the platform check also accepts XPU (vllm/config/model.py:666-668, vllm/platforms/interface.py:231-236). The mechanism is a backend class with suspend(level) and resume(tags) (vllm/device_allocator/sleep_mode_backend.py:37-69). The factory mirrors the KV connector factory:

The worker makes the backend on first use, from model_config.sleep_mode_backend (vllm/v1/worker/gpu_worker.py:249-259), and calls suspend and resume (vllm/v1/worker/gpu_worker.py:317, vllm/v1/worker/gpu_worker.py:339). The field defaults to "cumem" (vllm/config/model.py:379-383).

No CLI flag selects the sleep-mode backend

EngineArgs passes enable_sleep_mode and the other sleep fields to ModelConfig, but not sleep_mode_backend (vllm/engine/arg_utils.py:2039-2043). At this commit no other line in vllm/ sets the field. So vllm serve always uses cumem, unless your code changes model_config.sleep_mode_backend, for example a platform in check_and_update_config. A plugin also cannot replace "cumem": the factory raises ValueError for a taken name (vllm/device_allocator/sleep_mode_backend.py:173-174). (Derived from a search of the repository.)

Step 6: register_kv_cache_dtype#

A new --kv-cache-dtype value needs a handler with a name, a torch_dtype() and a quant_mode() (vllm/config/cache.py:73-103). The decorator adds the name to the mutable list KV_CACHE_DTYPES and writes the torch dtype into the shared dtype table:

The docstring says that it "Runs at platform activation time (first current_platform access)" (vllm/config/cache.py:112-116). No code in vllm/ calls it at this commit; only a test does (tests/config/test_kv_cache_dtype.py:35). The KV cache code reads the handlers through get_kv_cache_dtype_handler (vllm/v1/kv_cache_interface.py:110-112). A platform plugin or a general plugin would have to call it in every process that parses or uses the dtype. (Derived.)

Deep dive

Worked example: a worker extension for weight sync, with TP = 2

You start vllm serve ... --tensor-parallel-size 2 --worker-extension-cls my_pkg.ext.WeightSync. WeightSync defines update_weights_from(path) and init_worker_extension(worker).

  1. The front end stores the string in parallel_config.worker_extension_cls. The workers get it in the pickled VllmConfig.
  2. Each of the 2 worker processes runs init_worker: it imports my_pkg.ext, checks that Worker has no attribute update_weights_from, and adds WeightSync to Worker.__bases__ (vllm/v1/worker/worker_base.py:304-331). It logs "Injected ... for extended collective_rpc calls ['init_worker_extension', 'update_weights_from']". (The list holds every callable name that does not start with __.)
  3. After init_device, the wrapper calls WeightSync.init_worker_extension(worker) (vllm/v1/worker/worker_base.py:361-363).
  4. Later, collective_rpc("update_weights_from", args=(path,)) runs the method in both workers and returns a list of 2 results. With TP = 1 the uni executor calls run_method on its one in-process worker (vllm/v1/executor/uniproc_executor.py:103).

Note that line 323 changes the class Worker itself, not one object. Every worker object of that process gets the methods. (Derived.)

Deep dive

Edge cases

  • Extension already a base. If the extension class is already in worker_class.__bases__, the injection and the clash check are skipped (line 310).
  • Unknown RPC method. run_method raises NotImplementedError("Method ... is not implemented.") (vllm/v1/serial_utils.py:499-505).
  • Mixed-case load format. load_format is lower-cased (vllm/config/load.py:136-138), but register_model_loader stores the name as given. A loader registered as "My_Format" is never found. (Derived.)
  • Logits processors and VLLM_PLUGINS. An allowlist does not stop a logits processor plugin. To keep one out, uninstall its package.
  • Unsupported sleep backend. A backend whose is_supported() is false raises "Sleep-mode backend ... is not supported on this platform." on first use (vllm/device_allocator/sleep_mode_backend.py:198-201).

What can go wrong#

A custom scheduler can switch async scheduling off

vLLM's default is AsyncScheduler. For a class that subclasses Scheduler, vLLM only warns of "degraded performance due to async scheduling being disabled" (vllm/config/scheduler.py:247-253). Subclass AsyncScheduler unless you need the synchronous behaviour.

  • The class does not import in the child process. Config hooks are imported in the engine core or the workers. A class that exists only in your launch script fails there. Put it in an installed package.
  • Colon instead of dot. scheduler_cls, worker_cls and worker_extension_cls need pkg.module.Class; logits_processors strings need pkg.module:Class (vllm/utils/import_utils.py:119-123, vllm/v1/worker/gpu/sample/logits_processor/loader.py:99-104).
  • A name clash in the extension. An attribute that the worker class has already stops start-up with an AssertionError (vllm/v1/worker/worker_base.py:315-319).
  • A V1 logits processor. Model Runner V2 rejects it with ValueError at model load (vllm/v1/worker/gpu/sample/logits_processor/loader.py:67-72).

Why it matters. These hooks change the engine itself: the scheduling policy, the worker code, the sampler input and the weight source. They are powerful, and most of them are not public, stable interfaces. Read the code of the version that you run before you rely on one.

Check yourself#

  1. 1
    Which class does the engine core use when --scheduler-cls is not set and async scheduling is on?
    easy
    Show answer

    AsyncScheduler (vllm/config/scheduler.py:232-236).

  2. 2
    How do the methods of a worker extension class become callable with collective_rpc?
    easy
    Show answer

    init_worker adds the extension class to the bases of the worker class (vllm/v1/worker/worker_base.py:323-325). run_method then finds the method by name with getattr (vllm/v1/serial_utils.py:499-501).

  3. 3
    You set VLLM_PLUGINS=acme_admin. Does an installed vllm.logits_processors plugin still load in the workers?
    medium
    Show answer

    Yes. The Model Runner V2 loader calls entry_points(group=...) directly and does not read VLLM_PLUGINS (vllm/v1/worker/gpu/sample/logits_processor/loader.py:46).

  4. 4
    A general plugin calls SleepModeBackendFactory.register_backend("cumem", ...) to replace the built-in backend. What happens?
    medium
    Show answer

    The factory raises ValueError "Sleep-mode backend 'cumem' is already registered." because vLLM registered cumem at import (vllm/device_allocator/sleep_mode_backend.py:173-174, vllm/device_allocator/sleep_mode_backend.py:210-214). The general plugin does not catch it, so start-up stops (vllm/plugins/__init__.py:89-90).

  5. 5
    You register a model loader with @register_model_loader("Fast_Load") and start with --load-format Fast_Load. What happens, and why?
    hard
    Show answer

    Start-up fails with "Load format `fast_load` is not supported". The config lower-cases load_format (vllm/config/load.py:136-138), but the table stores "Fast_Load" as given (vllm/model_executor/model_loader/__init__.py:112), so get_model_loader does not find it (vllm/model_executor/model_loader/__init__.py:126-127). Register lower-case names. (Derived from these lines.)

Related pages

  • All the ways to extend vLLMvLLM has about twenty extension points of three kinds - six entry-point groups, a dozen registries that a general plugin fills, and config fields that name your class. This page maps each one to its process and its page.
  • Executors and workers: from the engine core to the GPUsThe executor starts the workers and runs each call on all of them. The uni executor calls one worker in the engine core process; the multiproc executor sends calls to one worker process per GPU through a shared-memory queue.
  • The V1 scheduler: one token budget, no phasesIn each engine step, Scheduler.schedule() shares one token budget: first among the running requests, then among the waiting ones. It has no prefill or decode phase, it preempts the last running request when KV blocks run out, and update_from_output() appends the sampled tokens.
  • Sampling and logits processors in Model Runner V2How the Model Runner V2 sampler turns logits into tokens - the order of the built-in stages, where custom logits processors plug in, when the fused FlashInfer sampler runs and when the Gumbel sampler runs, how seeds work, and what logprobs and prompt_logprobs cost.
  • "Weight loading: from checkpoint files to GPU parameters"Each worker picks a model loader by --load-format, builds the model with empty per-rank parameters on its GPU, streams every checkpoint tensor once, renames it with a WeightsMapper, and lets the parameter's weight_loader copy only this rank's slice.
  • The Platform interfaceThe Platform class is the contract between vLLM and a hardware vendor. Identity attributes describe the device; config hooks change VllmConfig in the front end; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation.
  • Quantization methods as pluginsA quantization method is a QuantizationConfig subclass registered under a name. The front end picks the name from the checkpoint or --quantization and makes one config object; each layer in the worker asks it for a quantize method that makes the weights and runs the forward.
