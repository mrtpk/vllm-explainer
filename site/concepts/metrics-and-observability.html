Metrics and observability: how to watch a vLLM server

IntermediatevLLM conceptsabout 14 min read + 4 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Serving metrics: TTFT, TPOT, ITL, throughput, goodput Beginner
  • The engine client: AsyncLLM in the API server Intermediate

In one sentence

The engine core sends timestamps and counters; the API server turns them into Prometheus metrics, a log line, traces and per-request fields.

The idea#

A running vllm serve has four places where you can see what it does. All four get their numbers from the same source. The EngineCore sends events, timestamps and counters with its outputs, and the front end computes the metrics from them. Serving metrics: TTFT, TPOT, ITL, throughput, goodput defines TTFT, ITL, TPOT and E2E latency.

  • Prometheus: GET /metrics on the API server port, with about 130 vllm:* metrics (Prometheus metrics lists them all).
  • The log line: every 10 seconds, "Avg prompt throughput ... Running ... Waiting ... GPU KV cache usage ...".
  • Per request: an optional metrics object in each response, and an optional OpenTelemetry span per request.
  • Profiles: the torch profiler, started and stopped with two HTTP routes.

This page shows where each signal is made, what it really measures, and which flag turns it on or off. It ends with the known gaps, because several metrics do not mean what their names suggest.

An everyday comparison. Think of a car. The engine sends raw pulses from its sensors; the dashboard computes the speed and the fuel use from them. A trip computer can also print one summary every few minutes. The comparison stops at the clock. In vLLM, the dashboard (the API server) and the engine (the engine core) use two different clocks. Some times come from the front-end clock, others from the engine clock.

The picture#

Read the panels from top to bottom. Green boxes run in the engine core process, blue boxes in the API server. The engine core never computes a latency. It sends time.monotonic() timestamps, and the API server adds its own time.time() clock for TTFT and E2E latency.

In the code#

Step 1: the /metrics endpoint#

The API server mounts the endpoint when it registers its routes (vllm/entrypoints/serve/instrumentator/__init__.py:16-18):

  1. Lines 64-74: the external library prometheus_fastapi_instrumentator adds http_* metrics for every route except the six excluded ones. Its expose() call adds a /metrics route.
  2. Line 77: a second route mounts the prometheus_client ASGI app at /metrics; line 80 makes it also match /metrics/ and longer paths. Both routes read the same registry (line 58).

With one API server, the registry is the default prometheus_client registry (vllm/v1/metrics/prometheus.py:47-53). With --api-server-count above 1, each API server is its own process. Then vllm serve sets PROMETHEUS_MULTIPROC_DIR to a new temporary folder before it starts them (vllm/entrypoints/cli/serve.py:282-283, vllm/v1/metrics/prometheus.py:17-36). Each process writes its values there, and every /metrics answer merges all processes. If you set the variable yourself, vLLM warns that you must clean the folder between runs (vllm/v1/metrics/prometheus.py:30-36).

Almost every engine metric has the labels model_name (the first served name) and engine (the DP rank as text, for example "0") (vllm/v1/metrics/loggers.py:499-504). The label rules are on Prometheus metrics.

Step 3: PromQL recipes#

These queries use only the exported names above. Add model_name or engine to the by clauses when you serve several models or DP ranks.

# p99 TTFT over 5 minutes, all engines together
histogram_quantile(0.99, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m])))

# p50 ITL per engine
histogram_quantile(0.5, sum by (le, engine) (rate(vllm:inter_token_latency_seconds_bucket[5m])))

# mean E2E latency
rate(vllm:e2e_request_latency_seconds_sum[5m]) / rate(vllm:e2e_request_latency_seconds_count[5m])

# output tokens per second
sum(rate(vllm:generation_tokens_total[1m]))

# prefix cache hit rate (tokens)
rate(vllm:prefix_cache_hits_total[5m]) / rate(vllm:prefix_cache_queries_total[5m])

# preemptions per second
sum(rate(vllm:num_preemptions_total[5m]))

# KV cache usage in percent (the gauge is 0-1)
100 * vllm:kv_cache_usage_perc

# finished requests per second by reason
sum by (finished_reason) (rate(vllm:request_success_total[5m]))

A practical rule: quantiles are estimates

histogram_quantile interpolates inside one bucket, so a p99 is only as exact as the bucket edges. The default TTFT buckets go from 1 ms to 2,560 s (vllm/v1/metrics/buckets.py:57-80). --custom-histogram-buckets replaces a bucket family; each extra bucket adds one time series per label set (vllm/config/observability.py:70-81).

Step 4: the periodic log line#

When stats are on, the API server starts a task that calls do_log_stats() every VLLM_LOG_STATS_INTERVAL seconds (vllm/entrypoints/launchers/utils/server_utils.py:75-89). The default is 10.0; a value of 0 or below becomes 10.0 (vllm/envs.py:874-878). The LoggingStatLogger builds the line:

  1. Line 280: an idle server logs at DEBUG, so the line disappears at the default INFO level. Idle means no prompt or output tokens in the last two intervals (vllm/v1/metrics/loggers.py:255-265).
  2. Lines 283-286: the two throughputs are tokens since the last line divided by the elapsed time (vllm/v1/metrics/loggers.py:168-173). The prompt throughput counts computed prompt tokens, not prefix-cache hits (vllm/v1/metrics/loggers.py:162-163).
  3. Lines 288-301: "Waiting" includes deferred requests, and "Deferred" appears only when there are some.
  4. Lines 310-312: "Preemptions: N" appears only when there were preemptions in the interval. The scheduler itself logs nothing when it preempts (The V1 scheduler: one token budget, no phases).

The line continues with "GPU KV cache usage: x%" and, after the first lookup, "Prefix cache hit rate: y%" (vllm/v1/metrics/loggers.py:314-323). The hit rate here covers about the last 1,000 requests, not the whole run (vllm/v1/metrics/stats.py:47). Each line starts with the engine index, for example "Engine 000: ", also with one engine (vllm/v1/metrics/loggers.py:176-178, vllm/v1/metrics/loggers.py:336). With several engines behind one API server, each engine gets its own line, unless --aggregate-engine-logging gives one line "N Engines Aggregated: " (vllm/v1/metrics/loggers.py:371-373, vllm/v1/metrics/loggers.py:1390-1395). With speculative decoding, a second line "SpecDecoding metrics: ..." follows (vllm/v1/metrics/loggers.py:340).

No log line with more than one API server

With --api-server-count above 1 (the default for -dp N), each API server sees only its own requests. So the stat logger manager does not add the log-line logger and warns "disabling stats logging to avoid incomplete stats" (vllm/v1/metrics/loggers.py:1384-1389). Prometheus stays on. Use /metrics for such servers.

Step 5: per-request metrics in the response#

--enable-per-request-metrics (off by default, vllm/entrypoints/common/cli_args.py:150-151) adds a metrics object to each chat or completion response. It needs the stats: with --disable-log-stats, start-up stops with ValueError (vllm/entrypoints/common/cli_args.py:536-542). The fields come from the engine-core timestamps of the request:

Note line 74: this time_to_first_token_ms runs from the first SCHEDULED event to the first token. It is the prefill time on the engine clock, without the queue and without the time in the API server. It is shorter than the Prometheus TTFT of the same request, because its interval lies inside the Prometheus interval (derived). In a stream, the object comes only in the final usage chunk, so the client must ask for usage (stream_options.include_usage) (vllm/entrypoints/openai/chat_completion/serving.py:873-885). For n > 1, the chat server sends no metrics, because the stats belong to one of the n outputs only (vllm/entrypoints/openai/chat_completion/serving.py:1173-1176).

Step 6: OpenTelemetry traces#

--otlp-traces-endpoint URL turns tracing on (vllm/config/observability.py:38-39). The value is checked at start-up: without the OpenTelemetry packages, it raises ValueError (vllm/config/observability.py:153-165). AsyncLLM then sets up a tracer (vllm/v1/engine/async_llm.py:149-151). The exporter uses gRPC by default; OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf switches to HTTP (vllm/tracing/otel.py:94-101).

When a request finishes, the output processor makes one span named llm_request. It starts at arrival_time and carries the queue, prefill, decode and inference times, the token counts and some sampling parameters (vllm/v1/engine/output_processor.py:957-1001). The serving classes pass the traceparent and tracestate headers of the HTTP request, so the span joins the caller's trace (vllm/tracing/utils.py:12, vllm/entrypoints/openai/chat_completion/serving.py:378-382). A request with trace headers to a server without tracing logs one warning and drops the headers (vllm/v1/engine/async_llm.py:421-423). --collect-detailed-traces model,worker adds model forward and execute times, with a cost in speed (vllm/config/observability.py:41-48).

Keep stats on when you trace

The span is built from the request stats, and do_tracing asserts that they exist (vllm/v1/engine/output_processor.py:947-948). The stats exist only when stats are on (vllm/v1/engine/output_processor.py:236). A search of otlp_traces_endpoint at the pinned commit finds no start-up check for this pair of flags. So the assertion can fail when a request finishes (derived). Do not combine --otlp-traces-endpoint with --disable-log-stats unless a stat logger plugin keeps the stats on.

Step 7: stat logger plugins#

A plugin in the entry-point group vllm.stat_logger_plugins adds its own stat logger (vllm/v1/metrics/loggers.py:84-98; Plugins in the API server). AsyncLLM loads the plugins in every API server process. When a plugin is found, stats stay on even with --disable-log-stats; only the default log-line logger is left out (vllm/v1/engine/async_llm.py:154-164). The manager adds a PrometheusStatLogger unless a custom logger already is one (vllm/v1/metrics/loggers.py:1396-1419). The plugin's record() runs once per batch of engine outputs, and log() every log interval.

Step 8: the profiler routes#

POST /start_profile and POST /stop_profile exist only when --profiler-config names a profiler; the server then logs that this "should ONLY be used for local development" (vllm/entrypoints/serve/profile/api_router.py:56-65). The profilers are torch, cuda and proton (vllm/config/profiler.py:15, vllm/config/profiler.py:70-76). The torch profiler needs torch_profiler_dir (vllm/config/profiler.py:235-241). A start request can pass profile_prefix, delay_iterations and max_iterations (vllm/entrypoints/serve/profile/api_router.py:18-28). An example (not in the repository):

vllm serve Qwen/Qwen3-0.6B --profiler-config '{"profiler": "torch", "torch_profiler_dir": "/tmp/vllm_profile"}'
curl -X POST localhost:8000/start_profile -H "Content-Type: application/json" -d '{"max_iterations": 20}'
# send some requests, then:
curl -X POST localhost:8000/stop_profile

Step 9: what --disable-log-stats turns off#

--disable-log-stats sets log_stats to False (vllm/engine/arg_utils.py:1909-1914). Without a stat logger plugin, AsyncLLM then makes no stat logger manager (vllm/v1/engine/async_llm.py:203-213), and:

  • /metrics has no vllm:* engine metrics; the http_* metrics stay (Prometheus metrics);
  • the log line stops, because the log task starts only with stats on (vllm/entrypoints/launchers/utils/server_utils.py:78);
  • the engine core records no QUEUED, SCHEDULED or PREEMPTED events (vllm/v1/core/sched/scheduler.py:2746-2747);
  • requests carry no stats, so per-request metrics and traces have no data.

The engine core stamps one time.monotonic() value on each batch of outputs (vllm/v1/engine/__init__.py:296-297). So ITL is a gap between two engine steps that produced a token for the request. It does not include the time of the HTTP stream. --stream-interval changes how often the client gets a chunk, not the Prometheus ITL. The docs describe ITL as a wall-clock gap between streamed outputs (docs/design/metrics.md:69-70); the code uses engine timestamps. A preemption does not restart the queue time: only the first SCHEDULED event counts (vllm/v1/metrics/stats.py:576-577).

Deep dive

Known gaps and traps

  • --show-hidden-metrics-for-version has no effect. The Prometheus logger stores the value (vllm/v1/metrics/loggers.py:494), and no code reads it after that. The docs describe hidden deprecated metrics (docs/usage/metrics.md:132-136). See Prometheus metrics.
  • Preempted requests are not in the prefix-cache counters. A request that comes back after a preemption looks up the cache again, but PrefixCacheStats.record puts it into preempted_* fields, which no metric exports (vllm/v1/metrics/stats.py:146-156). So vllm:prefix_cache_queries_total counts first admissions only.
  • Two clocks. TTFT and E2E use the front-end clock; queue, prefill, decode, ITL and TPOT use the engine clock. Do not subtract a front-end time from an engine time.
  • Client disconnects. A request that the client aborts does not add finished-request stats (E2E, TPOT, request_success) (vllm/v1/engine/async_llm.py:807-809).
  • KV usage is not cache fullness. vllm:kv_cache_usage_perc counts blocks outside the free queue; cached prefix blocks with no user are free (vllm/v1/core/block_pool.py:881-892).
  • Log-line hit rate vs. PromQL hit rate. The log line uses about the last 1,000 requests (vllm/v1/metrics/stats.py:47); a PromQL rate uses your time window.
  • Waiting includes deferred. vllm:num_requests_waiting adds requests that wait for a LoRA slot, a KV transfer or another blocked state (vllm/v1/metrics/loggers.py:1150-1154).
Deep dive

Worked example: one log line and the same numbers in PromQL

An illustrative log line from one engine (the numbers are made up; the format is from vllm/v1/metrics/loggers.py:276-337):

(APIServer pid=4121) INFO ... Engine 000: Avg prompt throughput: 5120.4 tokens/s, Avg generation throughput: 1835.0 tokens/s, Running: 64 reqs, Waiting: 12 reqs, Preemptions: 3, GPU KV cache usage: 97.8%, Prefix cache hit rate: 41.2%
  1. Prompt throughput 5,120 tokens/s counts computed prompt tokens only. Hits in the prefix cache are not in it.
  2. Running 64, waiting 12: requests wait while the batch has room for more sequences. The cause is not max_num_seqs.
  3. KV usage 97.8 % and "Preemptions: 3": the block pool is full, and the scheduler preempted running requests in the last interval. Waiting requests do not start because their tokens do not fit (vllm/v1/core/kv_cache_manager.py:522-539).
  4. The same view in PromQL: vllm:num_requests_running, vllm:num_requests_waiting, 100 * vllm:kv_cache_usage_perc, rate(vllm:num_preemptions_total[1m]).

Conclusion: this server is limited by KV memory, not by the token budget. Tuning vLLM: throughput and latency knobs, their real defaults and what each one does lists the memory knobs.

What can go wrong#

  • /metrics has only http_* metrics. The server runs with --disable-log-stats (Step 9).
  • No log line. More than one API server (Step 4), an idle server (DEBUG level), or VLLM_LOGGING_LEVEL above INFO.
  • A dashboard shows KV usage of 0.98 %. The gauge is a fraction; multiply by 100 (vllm/v1/metrics/loggers.py:621).
  • Old metrics files after a restart. You set PROMETHEUS_MULTIPROC_DIR yourself and did not clean it (vllm/v1/metrics/prometheus.py:30-36).
  • Per-request TTFT disagrees with the dashboard. They measure different intervals (Step 5).
  • /start_profile answers 404. No --profiler-config with a profiler (Step 8).
  • The client and the server disagree on TTFT. The client clock starts earlier and stops later; see Benchmarking vLLM: vllm bench serve, throughput, latency and startup.

Why it matters. You can tune and debug a server only through these signals. Each one has a start point, a clock and a switch. If you know them, you can compare the right numbers and find the binding limit (Troubleshooting vLLM: symptom, cause and fix).

Check yourself#

  1. 1
    Which flag removes all vllm:* metrics from /metrics, and which metrics stay?
    easy
    Show answer

    --disable-log-stats without a stat logger plugin: AsyncLLM makes no stat logger manager (vllm/v1/engine/async_llm.py:203-213). The http_* metrics of the instrumentator stay (vllm/entrypoints/serve/instrumentator/metrics.py:64-74).

  2. 2
    The gauge vllm:kv_cache_usage_perc shows 0.5. How full is the KV cache?
    easy
    Show answer

    Half of the usable blocks are outside the free queue: the gauge is a fraction from 0 to 1 (vllm/v1/metrics/loggers.py:619-623). Cached free blocks count as free, so the prefix cache can hold more data than this suggests.

  3. 3
    You run vllm serve M -dp 4 and see no "Avg prompt throughput" line. Why, and where do you look instead?
    medium
    Show answer

    The API server count defaults to the DP size, 4 (vllm/entrypoints/cli/serve.py:124-130). With more than one API server, the log-line logger is not added (vllm/v1/metrics/loggers.py:1384-1389). /metrics still works and merges all API servers through the multiprocess directory (vllm/entrypoints/cli/serve.py:282-283).

  4. 4
    A response has "time_to_first_token_ms": 42, but the Prometheus TTFT p50 is 300 ms at low load. Is one of them wrong?
    medium
    Show answer

    No. The per-request value runs from the first SCHEDULED event to the first token on the engine clock (vllm/entrypoints/generate/base/serving.py:73-74). The Prometheus TTFT starts at arrival_time before the chat template, and ends when the API server handles the output (vllm/renderers/base.py:1380, vllm/v1/metrics/stats.py:525). It adds rendering, tokenization, the queue and the trip back to the front end.

  5. 5
    During heavy preemption, the prefix cache hit rate from PromQL stays high, but prefill throughput rises. How can both be true?
    hard
    Show answer

    A preempted request loses its blocks and computes its prompt again (recompute). Its new cache lookup is recorded in preempted_queries and preempted_hits, which no metric exports (vllm/v1/metrics/stats.py:146-156). So the exported counters see only first admissions, while the recomputed prompt tokens add to the prompt throughput (vllm/v1/metrics/loggers.py:162-163).
