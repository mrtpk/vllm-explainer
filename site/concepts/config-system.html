How configuration works

IntermediatevLLM conceptsabout 16 min read + 6 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The process and thread architecture of vllm serve Intermediate
  • vllm serve flags

In one sentence

The front end parses the flags into EngineArgs, builds one VllmConfig from them, and sends a pickled copy of it to every other process.

The idea#

vllm serve has about 300 flags (vllm serve flags) and more than 300 VLLM_* environment variables (Environment variables). The engine does not read the flags directly. It reads one object, the VllmConfig. The config system is the code that makes this object. It has three layers:

  1. Config classes. Each part of the engine has one class in vllm/config/, for example CacheConfig or SchedulerConfig. The @config decorator makes each class a checked dataclass (Config classes).
  2. EngineArgs. One flat dataclass has a field for each flag. The parser fills it (EngineArgs).
  3. VllmConfig. create_engine_config() builds the sub-configs from EngineArgs and puts them into one VllmConfig. Its __post_init__ then checks them together and sets the late defaults.

Many flags have the default None. None means "vLLM decides later", from the model, the GPU, the platform or other settings. So the real default of a setting is often not the dataclass default. This page ends with a recipe to find it.

An everyday comparison. Think of an order form in a restaurant. The guest fills some boxes and leaves others empty: an empty box means "the chef decides". The head chef fills the empty boxes from the menu and the kitchen stock, and writes one final ticket. Each station gets a copy of the ticket. The comparison stops in two places. A station can write on its own copy. The copies do not go back to the head chef, except for a few values in the ready message.

The picture#

Read the panels from top to bottom. Panels 1 and 2 run only in the API server process. Panel 3 shows that the other processes do not parse flags. They get the finished object.

In the code#

Step 1: the @config decorator#

Every config class uses the decorator config (vllm/config/utils.py:51-61). It wraps the class in a pydantic dataclass with extra="forbid":

  1. Line 71. An unknown key is an error. So -cc '{"mod": 3}' stops start-up, and a typo does not pass in silence.
  2. Lines 75-76. dataclass is pydantic.dataclasses.dataclass (vllm/config/utils.py:20). Pydantic checks the types and limits such as Field(ge=1) when the object is made.

Each field has a docstring, a string literal on the line after the field. The parser uses these strings as the --help text. The page Config classes lists every class and field; this page does not repeat the tables.

Step 2: VllmConfig holds the top-level configs#

VllmConfig has 34 attributes (vllm/config/vllm.py:355-453). Most use a default factory, so a plain VllmConfig() makes default sub-configs. model_config is None by default, because a default ModelConfig would download a model (comment at lines 353-354). Optional features, for example lora_config and speculative_config, are None when they are off (vllm/config/vllm.py:381-384). Model code reads the config through get_current_vllm_config(), inside a set_current_vllm_config() block (vllm/config/vllm.py:3516-3540).

Step 3: EngineArgs, one flat dataclass#

EngineArgs has one field for each flag. Most fields copy their default from a config class:

A field with a default factory uses get_field, which copies the factory of the config field (vllm/config/utils.py:85-114). Some fields do not copy a default. They start as None, so that create_engine_config can decide:

enable_chunked_prefill is also None (vllm/engine/arg_utils.py:707). EngineArgs.__post_init__ turns dict values into config objects, for example a compilation_config dict, and loads the general plugins (vllm/engine/arg_utils.py:873-924).

Step 4: add_cli_args makes the flags from the config classes#

EngineArgs.add_cli_args makes one argument group for most config classes. Each group has the class name as its title and the class docstring as its description:

The flag name is written by hand. All other argparse settings come from get_kwargs(ModelConfig)["model"]. get_kwargs returns a deep copy of a cached result (vllm/engine/arg_utils.py:443-453). The cached function reads each dataclass field (vllm/engine/arg_utils.py:324-440):

  • Default: the field default, or the result of its default factory (lines 339-352).
  • Help: the field docstring. The parser reads the docstrings only when the command line contains --help, because that is slow (vllm/engine/arg_utils.py:285-288, vllm/engine/arg_utils.py:327).
  • JSON: a field whose type is a dataclass takes a JSON string, which pydantic checks (lines 367-378).
  • Booleans: a bool field gets BooleanOptionalAction (lines 384-386). FlexibleArgumentParser replaces it with EnableDisableAction, which pairs --enable-x with --disable-x (vllm/utils/argparse_utils.py:120-145, vllm/utils/argparse_utils.py:179).

Some flags replace the field default with None, for example --max-num-seqs (vllm/engine/arg_utils.py:1743-1749). The VllmConfig group holds the JSON flags of whole sub-configs, for example --compilation-config and its short form -cc (vllm/engine/arg_utils.py:1880-1882).

Step 5: the parser rewrites the command line#

FlexibleArgumentParser.parse_args changes the list of arguments before argparse sees it:

  1. Lines 371-372. --config file.yaml inserts the keys of a YAML file as flags (next step).
  2. Lines 379-394. In a flag name, _ becomes -, up to the first dot. So --max_num_seqs works. Keys after a dot keep their underscores.
  3. Lines 395-406. -O3, -O=3 and -O 3 become --optimization-level 3.

Then a flag with a dot becomes a JSON value: -cc.mode=3 becomes -cc '{"mode": 3}'. Several dotted flags with the same prefix merge into one dict (vllm/utils/argparse_utils.py:462-500). A key that ends with + appends list items (lines 472-474). The help text of the JSON flags shows these forms (vllm/utils/argparse_utils.py:159-167).

Config files. The parser supports YAML only: another file extension raises ValueError (vllm/utils/argparse_utils.py:633-637). A true value becomes --key, a list becomes --key v1 v2, and a nested dict becomes a JSON string (vllm/utils/argparse_utils.py:653-671). The file arguments go right after serve and the model. So a flag on the command line wins: "cli > config > defaults" (vllm/utils/argparse_utils.py:563-600).

Step 7: defaults from the usage context and the GPU#

_set_default_max_num_seqs_and_batched_tokens_args fills the two batch limits when they are None:

get_batch_defaults gives one dict per limit, keyed by the usage context (vllm/engine/arg_utils.py:2926-3026). Take OPENAI_API_SERVER on a GPU with 70 GiB or more and less than 160 GiB. If it is not an A100 or GB10, the values are 8192 tokens and 1024 requests (vllm/engine/arg_utils.py:2970-2983). A usage context that is not in the dict falls back to the SchedulerConfig constants 2048 and 128 (vllm/config/scheduler.py:41-43). The table vllm serve flags lists all tiers.

Then caps apply, only to values that you did not set. Without chunked prefill, the budget is at least max_model_len tokens. The budget is at most max_num_seqs × max_model_len tokens, and the request limit is at most the budget (vllm/engine/arg_utils.py:3177-3221). A multimodal prefix-LM model can also raise the budget, so that one multimodal item fits in one step (lines 3191-3202).

Step 8: VllmConfig.__post_init__, the late defaults#

The __post_init__ of VllmConfig is about 830 lines long (vllm/config/vllm.py:1492-2318). Its phases, in code order:

  1. Model hooks. try_verify_and_update_config runs the per-architecture config class of the model, once (vllm/config/vllm.py:1521, vllm/config/vllm.py:2714-2743).
  2. Quantization. It builds quant_config from the model (vllm/config/vllm.py:1586-1589).
  3. Async scheduling. When async_scheduling is None, it turns it on unless a pooling model, the executor or another option conflicts (vllm/config/vllm.py:1664-1698). See Async scheduling: overlap the CPU and the GPU.
  4. Eager mode. --enforce-eager sets the compilation mode and the CUDA graph mode to NONE (vllm/config/vllm.py:1745-1747).
  5. Platform defaults and compilation. apply_config_platform_defaults, then the compilation mode from the optimization level, then the defaults table of that level (vllm/config/vllm.py:1804-1810, vllm/config/vllm.py:1833-1834).
  6. CUDA graph sizes on platforms with static graphs (vllm/config/vllm.py:1929-1995).
  7. The platform's last word. current_platform.check_and_update_config(self) (vllm/config/vllm.py:2046). CUDA sets the worker class here (vllm/platforms/cuda.py:330-331).
  8. Model runner checks and compile ranges (vllm/config/vllm.py:2071-2083).
  9. KV transfer and the hybrid KV cache manager (vllm/config/vllm.py:2199, vllm/config/vllm.py:2236-2273).

The defaults of an optimization level fill only fields that are still None. A value that you set is never overwritten:

So -O1 -cc.cudagraph_mode=FULL_AND_PIECEWISE keeps your graph mode, and takes the other O1 defaults (vllm/config/vllm.py:275-295). The page config/vllm.py: VllmConfig, __post_init__ and compute_hash walks through every phase.

Step 9: how the config reaches the other processes#

The front end does not send flags to the EngineCore. It sends the finished VllmConfig object as an argument of the new process:

The CLI selects the spawn start method (vllm/entrypoints/common/startup.py:147-149). With spawn, Python pickles the process arguments at start(); a comment in the same class relies on this (vllm/v1/engine/utils.py:295-298). The executor does the same for each worker process (vllm/v1/executor/multiproc_executor.py:731-750). With TP = 1 there is no worker process: the worker object lives in the engine core and uses its copy (vllm/v1/executor/uniproc_executor.py:54-68).

The engine core runs __post_init__ again

After the start-up handshake, the engine core calls vllm_config.__post_init__() on its own copy. The comment says: "Update config which may have changed from the handshake":

This line is in the context manager that wraps EngineCore.__init__, after the yield. So it runs after the engine is built and READY is sent (derived from the indentation of lines 1190-1226 and 1317-1337). The platform hooks of __post_init__, for example check_and_update_config, therefore run again in each engine core process.

Values do not flow back, with one exception. The ready response of each engine core carries values that it found at start-up. The front end copies max_model_len (the smaller one), num_gpu_blocks (the sum over engines) and block_size into its own config (vllm/v1/engine/core_client.py:847-879).

Step 10: compute_hash, one key for compiled code#

VllmConfig.compute_hash() collects the hash of each sub-config and adds the vLLM version. It keeps the first 10 hex digits of an MD5 hash (SHA-256 in FIPS mode):

Each sub-config decides which fields count. The docstring says that the hash covers the configs "that affect the structure of the computation graph" (vllm/config/vllm.py:464-468). SchedulerConfig counts max_num_batched_tokens and max_num_seqs, because compiled graphs capture buffer sizes that depend on them (vllm/config/scheduler.py:271-284). Three users of the hash:

  • The compile cache folder name, when compilation_config.cache_dir is empty: a SHA-256 of the env hash, the config hash, the code hash and the compiler hash (vllm/compilation/backends.py:1059-1063, vllm/compilation/backends.py:1086-1098).
  • The AOT compile cache, keyed by the env hash and the config hash (vllm/compilation/caching.py:572-588).
  • The optional start-up memory plan of VLLM_ENABLE_STARTUP_PLAN (vllm/v1/worker/startup_plan.py:61-74).

So a change of --max-num-seqs gives a new hash, and the next start compiles again. The page torch.compile and CUDA graphs in vLLM explains the cache.

Environment variables are a separate channel. They are not fields of VllmConfig. vllm/envs.py maps each name to a function, mostly a lambda (vllm/envs.py:618). A read of envs.X calls the module __getattr__, which runs the function again:

No front-end code calls it, so the API server reads the environment live. Deep dive

Recipe: find the real default of any setting

A setting can get its value in up to seven places. Check them in this order. The last place that writes the value wins.

  1. The config field. Find the field and its docstring in Config classes. A docstring that says "set in EngineArgs.create_engine_config" is a hint that the dataclass default is not used (vllm/config/scheduler.py:48-53).
  2. The flag. Find the add_argument call in EngineArgs.add_cli_args. Look for "default": None, which hides the field default (vllm/engine/arg_utils.py:1729-1749).
  3. The EngineArgs field. A field that is None (vllm/engine/arg_utils.py:591-592) is filled later.
  4. create_engine_config and its helpers. Search for the field name in _set_default_* and get_batch_defaults (vllm/engine/arg_utils.py:2926-3227).
  5. The sub-config's own validators. For example, CacheConfig turns block_size=None into 16 (vllm/config/cache.py:452-462).
  6. VllmConfig.__post_init__ and the optimization level table (vllm/config/vllm.py:254-344).
  7. The platform and the engine core. apply_config_platform_defaults and check_and_update_config in the platform class; update_block_size_for_backend after the model loads (vllm/v1/executor/uniproc_executor.py:74-75); the KV cache planner in the engine core, which can lower max_model_len (vllm/v1/engine/core.py:308-322).

A shortcut: read the logs. The API server logs "non-default args: {...}", which shows what you set (vllm/entrypoints/common/startup.py:94-96). The engine core logs "Initializing a V1 LLM engine (v...) with config: ..." after __post_init__ (vllm/v1/engine/core.py:135-140). That line prints 33 resolved fields, among them enable_prefix_caching, enable_chunked_prefill and the full compilation_config (vllm/config/vllm.py:2788-2823). It does not print max_num_seqs; the batch limits are only in DEBUG logs (vllm/engine/arg_utils.py:3213-3227).

Deep dive

The parser in detail: one command line, step by step

Take this command and a file serve.yaml with the keys max-model-len: 8192, enforce-eager: true and compilation-config: {mode: 0}:

vllm serve Qwen/Qwen3-0.6B --config serve.yaml --max_model_len 4096 -O1 -cc.cudagraph_mode=PIECEWISE
  1. YAML. load_config_file returns ["--max-model-len", "8192", "--enforce-eager", "--compilation-config", "{\"mode\": 0}"] (vllm/utils/argparse_utils.py:653-671). The model is on the command line, so the list goes after Qwen/Qwen3-0.6B (vllm/utils/argparse_utils.py:585-592).
  2. Names. --max_model_len becomes --max-model-len (vllm/utils/argparse_utils.py:387-394).
  3. -O1. It becomes --optimization-level 1 (vllm/utils/argparse_utils.py:395-399).
  4. Duplicates. --max-model-len now appears twice. The parser logs "Found duplicate keys --max-model-len" (vllm/utils/argparse_utils.py:450-459, vllm/utils/argparse_utils.py:494-495). argparse keeps the last value, 4096, from the command line.
  5. Dotted key. -cc.cudagraph_mode=PIECEWISE becomes -cc '{"cudagraph_mode": "PIECEWISE"}' at the end of the list (vllm/utils/argparse_utils.py:462-500). It does not merge with the --compilation-config value from the file, because the prefixes differ. argparse sees two values for the same destination and keeps the last one, so the file's {"mode": 0} is lost. (Derived: argparse keeps the last value of an option.)
  6. Types. The JSON goes through TypeAdapter(CompilationConfig).validate_json, so an unknown key or value raises an argparse error (vllm/engine/arg_utils.py:369-376).

The result: max_model_len=4096, enforce_eager=True, optimization_level=1, compilation_config.cudagraph_mode=PIECEWISE. Then __post_init__ sees enforce_eager and sets the mode and the graph mode to NONE anyway (vllm/config/vllm.py:1745-1747).

Use one form for a JSON flag

Write all keys of one sub-config with the same prefix, for example only -cc.x forms, or one complete JSON value. Mixed forms do not merge.

Deep dive

compute_hash in numbers

  1. The factor list starts with the vLLM version, then one hash per sub-config, in a fixed order (vllm/config/vllm.py:474-570).
  2. A missing optional config adds the text "None", so turning LoRA on changes the list (lines 525-528).
  3. additional_config, a free dict for platforms, is hashed as sorted JSON (lines 559-567).
  4. str(factors) goes through safe_hash: MD5, or SHA-256 when MD5 is not allowed (vllm/utils/hashing.py:106-121). The first 10 hex digits are the result, for example 3f2a9c41d0 (an illustrative value).

The compile cache folder torch_compile_cache/<10 hex> uses its own SHA-256 over four hashes, of which this is one (vllm/compilation/backends.py:1091-1097). The env hash covers every variable of envs.py that is not in the ignore list (vllm/envs.py:2451-2466). For example, VLLM_ENGINE_READY_TIMEOUT_S is not in the list, so a new timeout value also gives a new cache folder. (Derived from the list at vllm/envs.py:2356-2447.)

What can go wrong#

A dataclass default is often not the real default

SchedulerConfig says max_num_seqs = 128, but vllm serve on a large GPU uses 1024. Use the recipe in the deep dive, or read the "Initializing a V1 LLM engine" log line.

  • A typo in a JSON key. extra="forbid" rejects it, and argparse stops with the pydantic error (vllm/engine/arg_utils.py:369-374). This is a feature: fix the key.
  • A typo in an environment variable. It is only a warning, unless you add --fail-on-environ-validation (vllm/engine/arg_utils.py:1922-1928).
  • --config=serve.yaml. The parser expands the file only when --config is a separate word (vllm/utils/argparse_utils.py:371-372). No code in vllm/ reads the value of args.config, so the file is ignored with no error. Write --config serve.yaml. (Derived from a search of the repository.)
  • A file with another extension. serve.json raises "Config file must be of a yaml/yml type" (vllm/utils/argparse_utils.py:633-637).
  • A change of the environment after start-up. It does not reach the engine core or the workers: they inherited the environment at spawn and cache it after start-up.
  • An unexpected recompile. A change of --max-num-seqs, --max-num-batched-tokens or most VLLM_* variables gives a new cache key (Step 10).

Why it matters. To tune a server, you must know the value that the engine really uses. The value can come from a flag, the model, the GPU, the platform or the engine core. The config system decides it in a fixed order, and only in the front end, except for the steps in the engine core.

Check yourself#

  1. 1
    Which object do the engine core and the workers read their settings from, and how do they get it?
    easy
    Show answer

    From VllmConfig. The front end builds it and passes it as an argument of each spawned process, so each process gets a pickled copy (vllm/v1/engine/utils.py:256-288, vllm/v1/executor/multiproc_executor.py:731-750).

  2. 2
    What does -cc.mode=3 become before argparse sees it?
    easy
    Show answer

    -cc '{"mode": 3}'. The parser turns a flag with a dot into a nested dict and adds it back as JSON (vllm/utils/argparse_utils.py:462-500).

  3. 3
    You start vllm serve with -O1 -cc.cudagraph_mode=FULL_AND_PIECEWISE. Which CUDA graph mode do you get, and why?
    medium
    Show answer

    FULL_AND_PIECEWISE. The O1 table would set PIECEWISE, but _set_config_default writes a default only when the field is still None (vllm/config/vllm.py:1014-1019). Your value is already set.

  4. 4
    Why does vllm serve on an 80 GB A100 get a smaller token budget than on an 80 GB H100?
    medium
    Show answer

    get_batch_defaults uses the large tier only when the device name does not contain "a100" (vllm/engine/arg_utils.py:2970-2983). The A100 gets 2048 tokens and 256 requests for OPENAI_API_SERVER (vllm/engine/arg_utils.py:2986-2993).

  5. 5
    A platform plugin changes a field in check_and_update_config. In which processes of a TP = 1 vllm serve does the hook run, and when?
    hard
    Show answer

    In the API server, inside VllmConfig.__post_init__ during create_engine_config (vllm/config/vllm.py:2046). It runs again in the engine core, because the engine core calls vllm_config.__post_init__() after the handshake (vllm/v1/engine/core.py:1336-1337). That second call comes after EngineCore.__init__, so the model is already built at that time (derived from the context manager at vllm/v1/engine/core.py:1190-1226). With TP = 1 there is no worker process.
