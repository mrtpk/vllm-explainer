The V1 scheduler: one token budget, no phases

AdvancedvLLM conceptsabout 18 min read + 8 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Tour: Life of a chat request Beginner
  • The engine core loop: threads, queues and the busy loop Intermediate

In one sentence

In each step, the scheduler gives each request the tokens it misses, running requests first, until the token budget or the KV blocks run out.

The idea#

The scheduler lives in the EngineCore process. Once per engine step, it decides which requests run and how many of their tokens. DeepInfer Explained teaches the basics: continuous batching and chunked prefill (Batching↗), and KV blocks and preemption (The KV cache↗). It also shows a scheduler with both (The scheduler↗). This page explains what vLLM does differently.

The vLLM scheduler has no prefill phase and no decode phase. Each request has two numbers: num_computed_tokens (tokens whose KV values are in the cache) and its number of tokens (prompt plus output). The scheduler gives each request the difference, as far as the token budget allows. A new prompt asks for many tokens, so it gets a prefill. A request in the middle of its answer asks for one token, so it gets a decode. A long prompt that does not fit gets a part of it: that is chunked prefill. One rule covers all three cases.

Each call of schedule() has two passes. The first pass serves the running queue, from the front. The second pass starts requests from the waiting queue, but only if the first pass did not preempt anything. Each scheduled request also needs KV blocks. When the blocks run out, the scheduler takes away all the blocks of the last running request. That request must compute its tokens again later: this is recompute preemption. After the GPU step, update_from_output() appends the sampled tokens and finishes the requests that must stop.

An everyday comparison. Think of a print shop that can print 16 pages per hour. Each job asks for the pages that it still needs. The shop serves the jobs that it already started first, then new jobs. A job also needs paper trays (the KV blocks). When the trays run out, the shop takes all the trays of the newest job, and that job must start again later. The comparison stops here. In vLLM, a restarted request can often get some of its old work back from the prefix cache. Also, a print job does not make its own next input.

The picture#

Read the panels from top to bottom. Blue boxes are the running pass, violet boxes the waiting pass, and the amber box is preemption. Note the two exits that differ: in the running pass, a request with 0 tokens is skipped (continue). In the waiting pass, the first request that does not fit stops the whole pass (break).

A worked example: three steps#

Simplified

The figure and the simulator below run each step synchronously: the token of step k is known before step k+1 is scheduled. Try it yourself#

The simulator follows these rules of the real code. It leaves out everything in the box above.

  1. The running pass goes first, from the front of self.running, while budget is left (vllm/v1/core/sched/scheduler.py:713-715).
  2. A request gets num_tokens - num_computed_tokens tokens, at most the rest of the budget (vllm/v1/core/sched/scheduler.py:759-768).
  3. A request needs ceil((num_computed_tokens + new) / block_size) blocks in total (vllm/v1/core/single_type_kv_cache_manager.py:214, vllm/v1/core/single_type_kv_cache_manager.py:401-402).
  4. If blocks are short, the scheduler preempts the last running request, and stops the pass if that was the request itself (vllm/v1/core/sched/scheduler.py:857-858, vllm/v1/core/sched/scheduler.py:889-904).
  5. The waiting pass runs only if nothing was preempted (vllm/v1/core/sched/scheduler.py:957), and only while fewer than max_num_seqs requests run (vllm/v1/core/sched/scheduler.py:979-981).
  6. A waiting request starts only if all its tokens fit in free blocks (vllm/v1/core/kv_cache_manager.py:522-539). If not, or if chunked prefill is off and the prompt does not fit the budget, the pass stops (vllm/v1/core/sched/scheduler.py:1222-1229, vllm/v1/core/sched/scheduler.py:1339-1346).
  7. Freed blocks go to the front of the free queue in reverse order (vllm/v1/core/single_type_kv_cache_manager.py:597-598, vllm/v1/core/block_pool.py:797-807).
  8. A request that reaches the end of its known tokens samples one token. It stops at max_tokens (vllm/v1/core/sched/utils.py:114-119).

In the code#

Step 1: the request state that the scheduler reads#

The scheduler works on Request objects (vllm/v1/request.py). Three counters drive every decision:

num_tokens is the prompt plus the output tokens so far. num_tokens_with_spec adds the draft tokens of speculative decoding. num_computed_tokens starts at 0 (vllm/v1/request.py:184). The comment at the top of schedule() states the rule with these names:

The status of a request is an IntEnum. Every value after PREEMPTED means "finished":

A request with structured output starts in WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR, not WAITING (vllm/v1/request.py:116-117). Its grammar compiles in a thread pool, and the waiting pass skips the request until the grammar is ready (Step 5).

Step 2: the token budget and max_num_seqs#

The budget of one step is max_num_scheduled_tokens. When you do not set it, the scheduler uses max_num_batched_tokens:

The dataclass defaults (2048 tokens, 128 sequences) are only test values (vllm/config/scheduler.py:41-43, vllm/config/scheduler.py:48-53). For vllm serve, the engine arguments pick the real defaults from the GPU memory (vllm/engine/arg_utils.py:2960-2993):

GPU memorymax_num_batched_tokensmax_num_seqs
160 GiB or more (for example B200)163841024
70 GiB or more, not A100, not GB10 (for example H100)81921024
other GPUs (for example A100)2048256

--performance-mode throughput doubles both values when you did not set them (vllm/engine/arg_utils.py:3171-3175). Some later rules can change an unset value again, for example when chunked prefill is off, the token default is at least max_model_len (vllm/engine/arg_utils.py:3177-3221). TPU and CPU have their own defaults (vllm/engine/arg_utils.py:2995-3024). max_num_seqs limits the length of the running queue: the scheduler asserts it after each call (vllm/v1/core/sched/scheduler.py:1496). The waiting pass uses max_num_active_seqs, which is max_num_seqs unless you set a smaller value (vllm/v1/core/sched/scheduler.py:133-137). The page Tuning vLLM: throughput and latency knobs, their real defaults and what each one does explains how to choose these values.

Step 3: the running pass#

The running pass walks self.running from the front while budget is left (vllm/v1/core/sched/scheduler.py:713-715). For each request it computes the missing tokens and caps them:

  1. Lines 759-763. The missing tokens. num_output_placeholders counts tokens that a started step will sample; it is 0 without async scheduling.
  2. Lines 764-765. The long_prefill_token_threshold. Its default is 0, which means no cap (vllm/config/scheduler.py:79-84). The scheduler also ignores it when only one request is running or waiting (vllm/v1/core/sched/scheduler.py:677-683).
  3. Lines 766-768. The rest of the budget. input_budget is max_num_batched_tokens. draft_slots is 0 without speculative decoding and for most drafting methods. It is 1 for a separate draft model, and more for parallel drafting (vllm/v1/core/sched/scheduler.py:644-645, vllm/config/speculative.py:1977-1995).
  4. Lines 772-777. The position must stay below max_model_len; one slot stays free for the sampled token.

When the result is 0, the scheduler skips the request and goes on to the next one. The comment explains the choice:

With async scheduling, a request can skip a step for one more reason. When its in-flight tokens surely reach max_tokens, the scheduler plans no extra step (vllm/v1/core/sched/scheduler.py:720-734).

Step 4: KV blocks, and preemption when they run out#

Each request then asks the KV cache manager for blocks with allocate_slots (vllm/v1/core/sched/scheduler.py:833-842). The page The KV cache manager: blocks, the block pool and memory sizing explains that call. If it returns None, the scheduler picks a victim:

With the default policy (fcfs), the victim is the last request in the running queue. That is usually the request that started last. With the priority policy, it is the request with the largest (priority, arrival_time): the lowest priority, and among equals the latest arrival. The victim leaves the running queue, and _preempt_request resets it:

  1. Line 1676. All KV blocks of the request go back to the block pool. Only with a consumer KV connector and overlapping steps does the scheduler hold them until the running step ends (vllm/v1/core/sched/scheduler.py:187-193, vllm/v1/core/sched/scheduler.py:2866-2875).
  2. Lines 1679-1680. The status becomes PREEMPTED, and num_computed_tokens becomes 0. The output tokens stay in the request. So when it runs again, it computes the prompt and its output tokens again: this is recompute.
  3. Lines 1683-1694. With async scheduling, tokens of a started step can still arrive. They are marked stale, so they do not change the reset counters.
  4. Lines 1700-1701. The request goes to the front of the waiting queue, and its id goes into preempted_req_ids of the next SchedulerOutput.

Then the scheduler tries allocate_slots again. If the victim was the request itself, the running pass stops (vllm/v1/core/sched/scheduler.py:898-904). The blocks keep their hashes when prefix caching is on. So the preempted request can find its own full blocks again in the prefix cache, if no other request has reused them (Prefix caching in the engine core: hashes, lookup, caching, eviction and KV events).

Step 5: the waiting pass#

  1. Line 957. The waiting pass runs only if the running pass preempted nothing. It makes no sense to start a new request when a running one just lost its blocks.
  2. Lines 972-974. Waiting requests that still hold KV blocks (for example after a remote KV load) go first, from kv_holding_waiting.
  3. Lines 979-981. The max_num_seqs limit (through max_num_active_seqs).
  4. Lines 986-989. A request whose grammar is not compiled yet, or whose remote KV has not arrived, is skipped for this step. The pass continues with the next request (vllm/v1/core/sched/scheduler.py:3275-3310).

A LoRA request is also skipped when max_loras different adapters already run and its adapter is not one of them (vllm/v1/core/sched/scheduler.py:998-1009). A request with num_computed_tokens == 0 then looks up the prefix cache (vllm/v1/core/sched/scheduler.py:1016-1024). A KV connector can add tokens from an external cache. An asynchronous load parks the request in WAITING_FOR_REMOTE_KVS until the data arrives (vllm/v1/core/sched/scheduler.py:1384-1411, KV connectors). Next, the number of tokens, and the rule for chunked prefill:

With chunked prefill on, the request takes the rest of the budget and continues in the next step. With chunked prefill off, a prompt that does not fit stops the pass. Chunked prefill is on by default for generative models that are not encoder-decoder models (vllm/engine/arg_utils.py:3031-3035, vllm/config/model.py:2229-2236).

The request then calls allocate_slots with full_sequence_must_fit=True by default, so all its tokens must fit in free blocks, not only the first chunk (vllm/config/scheduler.py:190-194, vllm/v1/core/sched/scheduler.py:1320-1337). If the call fails, the pass stops (vllm/v1/core/sched/scheduler.py:1339-1346). If it succeeds, the request moves to the running queue:

Step 6: speculative tokens use the same budget#

Draft tokens are part of num_tokens_with_spec (Step 1), so the running pass counts them in the same budget. After the request is scheduled, the scheduler keeps only the draft tokens that fit and moves them into scheduled_spec_decode_tokens:

Rejected drafts roll back num_computed_tokens later, in update_from_output (vllm/v1/core/sched/scheduler.py:2206-2221). The page Speculative decoding in vLLM serving explains the methods.

Step 7: the SchedulerOutput, then the counters move#

At the end, schedule() builds the SchedulerOutput:

With Model Runner V2, a resumed request travels as a new request, with all its block ids (vllm/v1/core/sched/scheduler.py:1505-1516). Only after the output exists does _update_after_schedule advance the counters:

A request is a prefill chunk when it still has tokens to compute after this step (line 1721). With the default AsyncScheduler, every request that is not a prefill chunk also gets an output placeholder for the token that the step will sample (vllm/v1/core/sched/async_scheduler.py:32-47). That is why the running pass adds num_output_placeholders (Step 3). The page Async scheduling: overlap the CPU and the GPU explains the overlap. All fields of the output are on Data contracts between the parts of vLLM.

Step 8: update_from_output appends tokens and finishes requests#

When the step's result arrives, the engine core calls update_from_output. For each scheduled request, it takes the sampled tokens and checks for a stop:

check_stop tests in this order: EOS, a stop token id, the length limits (max_model_len or max_tokens), then min_tokens and repetition detection (vllm/v1/core/sched/utils.py:98-140). A finished request frees its blocks (vllm/v1/core/sched/scheduler.py:2316-2323), and leaves the running queue (vllm/v1/core/sched/scheduler.py:2390-2391). The scheduler makes an EngineCoreOutput only for requests with new tokens, a pooler output or a stop (vllm/v1/core/sched/scheduler.py:2293-2295). So a prefill chunk sends nothing to the front end. Tour Tour: One engine step follows this method with real numbers.

Step 9: the scheduling policy#

The scheduling policy is --scheduling-policy, with fcfs as the default (vllm/config/scheduler.py:159-165). It selects the class of the waiting queue:

The FCFS queue is a deque: new requests go to the end, preempted requests to the front (vllm/v1/core/sched/request_queue.py:78-94). The priority queue is a heap ordered by Request.__lt__: smaller priority first, then earlier arrival_time, then the request id (vllm/v1/core/sched/request_queue.py:131-157, vllm/v1/request.py:357-367).

A client sets the priority with the priority field of the request body. The header X-Vllm-Priority overrides the field when it holds an integer (vllm/entrypoints/generate/base/serving.py:254-265).

A priority without the priority policy is ignored, not rejected

The field description says that a priority other than 0 raises an error when the server does not use priority scheduling (vllm/entrypoints/openai/chat_completion/protocol.py:393-402). No code raises this error. With fcfs, the queue simply appends the request (vllm/v1/core/sched/request_queue.py:78-80), and the priority has no effect.

Step 10: replace the scheduler with scheduler_cls#

--scheduler-cls takes a class or a "module.Class" path. Without it, vLLM picks AsyncScheduler when async scheduling is on, else Scheduler:

The engine core builds the class in EngineCore.__init__ (vllm/v1/engine/core.py:164, vllm/v1/engine/core.py:177-185). The warning on lines 247-253 is a real trap: a custom class that subclasses Scheduler instead of AsyncScheduler loses the placeholders of async scheduling. The page Hooks in the engine core and the workers lists this hook with the other engine hooks.

Deep dive

The running pass, line by line

Lines of vllm/v1/core/sched/scheduler.py, in the order that they run for one running request:

  1. 642-648. token_budget = max_num_scheduled_tokens; input_budget = max_num_batched_tokens. A full pause (PAUSED_ALL) sets the budget to 0.
  2. 666. kv_cache_manager.new_step_starts() tells the managers that a step begins.
  3. 670-711. Prefill throttling for data parallel MoE and the local prefill_schedule_interval (default 1, so off) (vllm/config/scheduler.py:203-209). When it is active, running prefill chunks wait for a later step, and decodes still run (lines 742-746).
  4. 713-718. The loop. It breaks when input_budget cannot hold one more token plus the draft slots.
  5. 720-734. Async scheduling: skip a request whose in-flight tokens already reach max_tokens.
  6. 736-740. Model Runner V2 with PP and async scheduling: a request decodes at most every pp_size steps.
  7. 748-757. An encoder-cache connector can hold a multimodal request back.
  8. 759-777. The token count and its four caps (Step 3).
  9. 780-809. Mamba block alignment, encoder inputs and the MTP lookahead can lower the count further.
  10. 811-829. A count of 0: continue.
  11. 831-904. allocate_slots and the preemption loop. With a KV connector that has pending block frees, the loop stops without a preemption (lines 844-848).
  12. 906-914. The request is scheduled: num_scheduled_tokens[req_id] = num_new_tokens; both budgets go down.
  13. 916-943. Draft tokens (Step 6) and encoder inputs.
  14. 945-954. The LoRA ids of all running requests, for the max_loras check of the waiting pass.

With the priority policy, the victim can be a request that this pass already scheduled. Then the scheduler gives its tokens back to both budgets and removes its blocks and draft tokens from the plan (lines 864-888). With FCFS this cannot happen: the victim is the last request, and the pass has not reached it yet.

Deep dive

The waiting pass, line by line

  1. 958-967. skip_request moves a request out of the queue for this step only. Skipped requests go back to the front of their queue at the end (lines 1469-1473), so they keep their place.
  2. 969-981. Loop while budget is left; queue choice; max_num_active_seqs.
  3. 986-996. Blocked statuses, and stale output of a preempted request that is still in flight.
  4. 998-1009. LoRA: skip.
  5. 1016-1146. First admission (num_computed_tokens == 0): local prefix-cache hit, then the KV connector hit, then bookkeeping for statistics.
  6. 1147-1158. A request that already has computed tokens (after a remote KV load, or a streaming-input session) uses them.
  7. 1171-1283. The token count. An async KV load schedules 0 tokens. With speculative decoding, a waiting request with only 1 token to compute can be padded to 1 + num_spec_tokens. This happens only when no prefill chunk runs in the step, and keeps a uniform batch for CUDA graphs (lines 1196-1215). Then the long-prefill cap, the chunked-prefill rule and the budget.
  8. 1320-1346. allocate_slots, with the prefix-cache hit and full_sequence_must_fit. None: break.
  9. 1378-1382. Prefix-cache statistics are recorded only for admitted requests.
  10. 1413-1467. The request moves to running. Its status before the move decides the list: WAITING goes to scheduled_new_reqs, PREEMPTED to scheduled_resumed_reqs.

Note the asymmetry. In the waiting pass, a request that does not fit stops the pass. A smaller request behind it does not get a chance in this step. Only skipped requests (blocked, LoRA, 0 tokens) let the pass continue.

Deep dive

Preemption: cost, metrics and what comes back

What the victim loses. All its KV blocks and its num_computed_tokens. It keeps its prompt and output tokens. Take a victim with a 1000-token prompt and 200 output tokens. Without a prefix-cache hit, it must compute 1200 tokens again when it resumes (derived from lines 1680 and 1191). The waiting pass treats it like a new request. It looks up the prefix cache, because num_computed_tokens is 0, and all its tokens must fit.

What comes back. _free_request_blocks frees the blocks in reverse order (vllm/v1/core/sched/scheduler.py:2866-2875, vllm/v1/core/single_type_kv_cache_manager.py:597-598). Blocks with a hash go to the end of the free queue. Blocks without a hash, for example the partial last block, go to the front (vllm/v1/core/block_pool.py:776-807). So the full blocks stay in the prefix cache as long as nobody needs their memory. If they survive, the resumed request hits them and computes only the rest.

How you see it. The scheduler records a PREEMPTED event when stats are on (vllm/v1/core/sched/scheduler.py:1696-1697). The front end counts these events in vllm:num_preemptions (vllm/v1/metrics/loggers.py:738-745). The periodic log line adds "Preemptions: N" when N is above 0 (vllm/v1/metrics/loggers.py:310-312).

Docs and code. docs/configuration/optimization.md shows a WARNING line "Sequence group 0 is preempted by PreemptionMode.RECOMPUTE mode ..." (docs/configuration/optimization.md:33-35). The V1 scheduler does not log a line per preemption: _preempt_request has no log call (vllm/v1/core/sched/scheduler.py:1658-1701). Watch the metric or the "Preemptions" field instead. The same page says that recompute is the default mode in V1 (docs/configuration/optimization.md:47). In the V1 code it is the only mode: _preempt_request always frees the blocks and resets num_computed_tokens (vllm/v1/core/sched/scheduler.py:1676-1680).

Other preemptions. reset_prefix_cache(reset_running_requests=True) preempts every running request, from the end, with their stale output dropped (vllm/v1/core/sched/scheduler.py:2950-2960).

The worked example, continued

The simulator continues the figure with the same rules. Values right after each step (budget 16, block size 4, 8 blocks):

StepScheduled (tokens)Free blocks afterWhat happens
1A 10, B 63A finishes its prompt and samples token 1. B is a chunk. C waits: no budget left.
2A 1, B 6, C 60B ends its prompt; C starts. 13 of 16 tokens used.
3A 1, B 11B needs block 4 of its 13 tokens: preempt C. No waiting pass.
4A 1, B 14A needs a 4th block and takes the last free one. C needs 2 blocks for its 7 tokens: 0 free, the pass stops. A reaches max_tokens and frees 4 blocks.
5B 1, C 76C resumes and recomputes 7 tokens (6 prompt + 1 output). B finishes.

The real engine has prefix caching on. After step 3, C's first block (block 7: 4 prompt tokens, full and hashed) waits at the end of the free queue. But in step 4, A takes the last free block, and that is block 7: get_new_blocks evicts its hash (vllm/v1/core/block_pool.py:681-691). So in this example C computes all 7 tokens again in the real engine too. With one more free block, block 7 would survive, and C would compute only 3 tokens (derived).

Deep dive

Parts of schedule() that this page skips

  • Encoder inputs (images, audio): a separate encoder compute budget and encoder cache; a chunk can stop before an image that does not fit (vllm/v1/core/sched/scheduler.py:1876-1903).
  • Mamba "align" mode: chunks end on block boundaries so that states can be cached (vllm/v1/core/sched/scheduler.py:474-488). See The hybrid KV cache: specs, groups and one manager per layer type.
  • Pause states: PAUSED_ALL schedules nothing; PAUSED_NEW admits only requests that hold blocks (vllm/v1/core/sched/scheduler.py:646-648, vllm/v1/core/sched/scheduler.py:970-974).
  • Streaming-input sessions (resumable requests): a stopped turn waits in WAITING_FOR_STREAMING_REQ for the next input (vllm/v1/core/sched/scheduler.py:2564-2589).
  • KV load failures of a connector: the scheduler recomputes the bad blocks or fails the request, by kv_load_failure_policy (vllm/v1/core/sched/scheduler.py:184-185, vllm/v1/core/sched/scheduler.py:3444-3457).

What can go wrong#

  • Many preemptions. The KV cache is too small for the running requests. Each preemption throws away computed work. Watch vllm:num_preemptions. Raise --gpu-memory-utilization, or lower --max-num-seqs (The KV cache manager: blocks, the block pool and memory sizing).
  • Decodes slow down during a long prompt. A prompt chunk can take the whole rest of the budget, so the step gets long for every request in it. --long-prefill-token-threshold caps one request's share (vllm/v1/core/sched/scheduler.py:764-765).
  • Head-of-line blocking. The first waiting request that does not fit stops the waiting pass (vllm/v1/core/sched/scheduler.py:1339-1346). With chunked prefill off, a long prompt at the front stops it too (vllm/v1/core/sched/scheduler.py:1222-1229).
  • Requests wait with free memory. max_num_seqs requests already run (vllm/v1/core/sched/scheduler.py:979-981), or the LoRA requests wait for an adapter slot (vllm/v1/core/sched/scheduler.py:998-1009).
  • The priority field does nothing. The server runs fcfs. Start it with --scheduling-policy priority.
  • A custom scheduler is slower. It subclasses Scheduler, so async scheduling is lost (vllm/config/scheduler.py:247-253).

Why it matters. The scheduler sets the shape of every step: how many tokens, which requests, how much of a prompt. TTFT, inter-token latency and throughput all follow from these choices. When you tune max_num_batched_tokens or max_num_seqs, or read the preemption metric, you change or watch this one function.

Check yourself#

  1. 1
    Does the vLLM scheduler have a prefill phase and a decode phase?
    easy
    Show answer

    No. Each request asks for num_tokens_with_spec - num_computed_tokens tokens, and the scheduler gives them from one budget. A new prompt asks for many tokens, a decoding request for one (vllm/v1/core/sched/scheduler.py:624-633, vllm/v1/core/sched/scheduler.py:759-768).

  2. 2
    With the default policy, which request does the scheduler preempt when a running request cannot get blocks?
    easy
    Show answer

    The last request in the running queue: self.running.pop() (vllm/v1/core/sched/scheduler.py:889-890). With the priority policy, it is the request with the largest (priority, arrival_time) (vllm/v1/core/sched/scheduler.py:852-856).

  3. 3
    In a step, the running pass preempts one request. A short new request waits, and 2000 tokens of budget are left. Does the short request start in this step?
    medium
    Show answer

    No. The waiting pass runs only when nothing was preempted in this step (vllm/v1/core/sched/scheduler.py:957). The budget stays unused.

  4. 4
    Why does the running pass use continue for a request with 0 tokens, while the waiting pass uses break when allocate_slots fails?
    medium
    Show answer

    A running request with 0 tokens (for example, all its tokens are in flight) must not block the requests behind it. The comment says that the scheduler gives up strict FCFS for this (vllm/v1/core/sched/scheduler.py:825-829). In the waiting pass, a failed allocation means the free blocks are short, so the scheduler stops admitting new requests (vllm/v1/core/sched/scheduler.py:1339-1346).

  5. 5
    A request has a 1000-token prompt and 200 output tokens when it is preempted. Prefix caching is on, block size 16, and no other request reused its blocks. How many tokens does it compute when it resumes, at the minimum?
    hard
    Show answer

    _preempt_request sets num_computed_tokens to 0 (vllm/v1/core/sched/scheduler.py:1680), so the waiting pass looks up the prefix cache again (vllm/v1/core/sched/scheduler.py:1017-1024). The request has 1200 tokens. Its full blocks were cached and stay cached until reused. The lookup returns full blocks only, up to num_tokens - 1 = 1199 tokens (vllm/v1/core/kv_cache_manager.py:289-300): 74 blocks = 1184 tokens. So it computes at least 1200 − 1184 = 16 tokens. This assumes that every full block was cached; with async scheduling, the blocks of the last in-flight tokens may not be cached yet (derived).
