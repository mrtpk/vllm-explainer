The process and thread architecture of vllm serve

IntermediatevLLM conceptsabout 12 min read + 7 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Processes, ZMQ and shared memory Beginner
  • What vLLM is today Beginner

In one sentence

vllm serve splits its work over processes: API servers for HTTP and text, engine cores for scheduling, and workers for the GPUs.

The idea#

An inference server does two kinds of work. CPU work: parse HTTP, apply the chat template, tokenize, detokenize and write the stream. GPU work: plan a batch, run the model and sample tokens. The GPU must never wait for the CPU work of the server. So vLLM puts the two kinds of work into different processes. The design doc says the multi-process architecture "separate[s] concerns and maximize[s] throughput" (docs/design/arch_overview.md:69).

vllm serve has three kinds of process:

  • The API server process (the front end). It runs FastAPI on uvicorn, the renderer and AsyncLLM. AsyncLLM is the EngineClient of the server.
  • The engine core process. It runs the scheduler, the KV cache manager and the executor in a busy loop. There is one engine core process for each data parallel rank.
  • The worker processes. Each one owns one GPU and holds a model runner. With one GPU and no parallelism, there is no worker process: the worker is an object inside the engine core process.

The processes talk through three channels. ZMQ sockets with msgpack bytes connect the API servers and the engine cores. A shared-memory queue connects an engine core with its workers. NCCL connects the GPUs of one model copy. The page Processes, ZMQ and shared memory explains processes, sockets and serialization in general.

An everyday comparison. Think of an airport. The check-in desks (API servers) talk to the passengers and print the tickets. The control tower (engine core) decides which plane takes off next, but it does not fly a plane. The pilots (workers) fly the planes (GPUs). A large airport adds more desks, more towers and more pilots. The comparison stops here: in vLLM, each tower has its own fixed group of pilots, and every desk can send passengers to every tower.

In the code#

Step 1: the API server process and AsyncLLM#

With one API server, vllm serve runs the server in the CLI process itself. With more than one, the CLI process starts the API servers as children:

Each API server builds its engine client with AsyncLLM.from_vllm_config (vllm/entrypoints/launchers/api_server/entry.py:93-103). The constructor makes all front-end parts of the engine:

The serving classes, for example the chat completion handler, take the renderer and the input processor from the engine client (vllm/entrypoints/generate/base/serving.py:150-151). So there is one renderer per API server process. The page The engine client: AsyncLLM in the API server explains AsyncLLM in full.

Step 2: the engine core process starts#

With one API server, the engine core client binds its sockets first. Then it starts the engine core processes and waits for them. (With several API servers, the CLI process binds the sockets and starts the engines; see Step 6.)

launch_core_engines makes one process per local data parallel rank. Its target is EngineCoreProc.run_engine_core, and its name is EngineCore or EngineCore_DP<rank> (vllm/v1/engine/utils.py:281-288). The client then waits for one ready message from each engine core. The wait has a timeout of VLLM_ENGINE_READY_TIMEOUT_S seconds, 600 by default (vllm/v1/engine/core_client.py:753-771, vllm/envs.py:812-814).

The ready message is an EngineCoreReadyResponse (vllm/v1/engine/__init__.py:73-110). It carries values that the engine core computes at start-up, for example the number of KV cache blocks. The client copies them into its own config (vllm/v1/engine/core_client.py:847-873).

Step 3: inside the engine core process#

EngineCore.__init__ makes its parts in this order: executor (with workers and model), KV caches, structured output manager, scheduler:

The scheduler owns the KV cache manager (vllm/v1/core/sched/scheduler.py:329). EngineCoreProc adds the sockets and two I/O threads. The comment explains why: the threads release the GIL during socket I/O, so I/O and (de)serialization overlap with the GPU work:

The main thread runs the busy loop: it takes messages from input_queue, runs one engine step and puts the outputs into output_queue (vllm/v1/engine/core.py:1609-1620). The page The engine core loop: threads, queues and the busy loop explains the loop.

Step 4: workers, in the same process or in their own#

The executor backend decides where the workers run. The config chooses it in ParallelConfig.__post_init__:

The first test uses world_size_across_dp, which is world_size × data_parallel_size (vllm/config/parallel.py:627-629). The world_size is PP × TP × PCP (vllm/config/parallel.py:965-969). So the "uni" backend applies only when TP, PP and DP are all 1 (and PCP too). Then UniProcExecutor builds the worker in its own process, the engine core process (vllm/v1/executor/uniproc_executor.py:51-75).

In all other single-node cases on CUDA, the default backend is "mp". Ray replaces it when Ray is active with a placement group, or when the data parallel backend is Ray (vllm/config/parallel.py:1061-1096). MultiprocExecutor starts one process per local rank, named VllmWorker-<rank> (vllm/v1/executor/multiproc_executor.py:191-207, vllm/v1/executor/multiproc_executor.py:745-750). The page Executors and workers: from the engine core to the GPUs explains both executors.

DP > 1 also makes worker processes

With --data-parallel-size 2 and TP = 1, world_size is 1 but world_size_across_dp is 2. So the backend is "mp", and each engine core gets one worker process. A dense engine core later sets its own DP size to 1, but it does not change the backend (vllm/config/parallel.py:1192-1201). (Derived from vllm/config/parallel.py:1055, vllm/v1/executor/abstract.py:80-83 and vllm/v1/executor/multiproc_executor.py:191.) The worker runs inside the engine core process only when DP is 1 too.

Step 5: the three channels#

ZMQ between API servers and engine cores. The client binds a ROUTER socket for requests and a PULL socket for outputs (Step 2). The engine core connects a DEALER socket with its identity, one for each API server (vllm/v1/engine/core.py:1935-1943). It also connects one PUSH socket for each API server (vllm/v1/engine/core.py:2046-2052). The identity is the engine index as 2 little-endian bytes (vllm/v1/engine/core.py:1178-1179). The addresses are ipc:// paths when the API server sends only to engines on its own node, and TCP addresses otherwise (vllm/v1/engine/utils.py:1137-1151). The client encodes requests with MsgpackEncoder and decodes EngineCoreOutputs with MsgpackDecoder (vllm/v1/engine/core_client.py:731-732).

Shared memory between an engine core and its workers. MultiprocExecutor makes one MessageQueue with a reader for each worker (vllm/v1/executor/multiproc_executor.py:165-171). Every call, for example execute_model, goes into this queue once and reaches all workers (vllm/v1/executor/multiproc_executor.py:428). The queue pickles the object (vllm/distributed/device_communicators/shm_broadcast.py:934-940). Only one worker replies to execute_model: the first TP rank of the last PP stage (vllm/v1/executor/multiproc_executor.py:549-563).

NCCL between GPUs. Inside the forward pass, the workers of one TP group exchange activations with collectives. On CUDA, each device communicator with more than one rank makes a PyNcclCommunicator (vllm/distributed/device_communicators/cuda_communicator.py:106-111). With PP, each stage after the first receives the intermediate tensors of the stage before it. Each stage before the last sends them on (vllm/v1/worker/gpu_worker.py:1337-1342, vllm/v1/worker/gpu_worker.py:1375-1378). The page Process groups: how vLLM slices its ranks explains the groups.

Step 6: how the counts change with TP, PP, DP and API servers#

TP and PP are explained in Parallelism basics↗. In vLLM they change only the number of workers per engine core. DP changes the number of engine cores. --api-server-count changes the number of API servers. Its default depends on the load balancing mode:

So with internal load balancing, the default is one API server per DP rank. Each API server gets a client_index and the client_count (vllm/v1/utils.py:230-238). With DP > 1 and internal load balancing, the client is a DPLBAsyncMPClient that can send each request to any engine core (vllm/v1/engine/core_client.py:158-169). So the API servers and the engine cores form a many-to-many network.

The model is dense, so each DP rank is an independent copy of the model. The DP coordinator exists because the API servers balance the load with its counts. The deep dive below gives the rules for each process type.

Deep dive

Data parallel: engine cores, GPUs and the coordinator

  1. Engine class. For a MoE model with DP > 1, the engine core is a DPEngineCoreProc. For every other model, it is a plain EngineCoreProc, and the config of the rank is changed to DP = 1. The comment says: "Non-MoE DP ranks are completely independent, so treat like DP=1" (vllm/v1/engine/core.py:1533-1543).
  2. GPUs per rank. Local DP rank r gets the visible devices r × world_size to r × world_size + local_world_size − 1, mapped to physical ids through CUDA_VISIBLE_DEVICES. The docstring gives the example "[2, 3] for local_dp_rank=1" with world_size=2 and 4 devices (vllm/v1/engine/utils.py:444-445, vllm/v1/engine/utils.py:462-469).
  3. Coordinator. The engines send their counts of waiting and running requests and the KV cache usage when the counts change (vllm/v1/engine/core.py:1622-1633). The coordinator publishes them to the API servers every 100 ms by default when they changed, else every 5 s (vllm/v1/engine/coordinator.py:152, vllm/v1/engine/coordinator.py:264-267). Wave coordination is on only for MoE models (vllm/v1/engine/utils.py:1261-1265).
  4. MoE lock-step. A DPEngineCoreProc runs a dummy batch when it has no work but other ranks have work. A collective tells all ranks if any rank has unfinished requests (vllm/v1/engine/core.py:2485-2505).
  5. Outputs and stats. The engine core sends each output to the socket of the API server that sent the request: client_index selects the socket (vllm/v1/engine/core.py:2071, vllm/v1/engine/core.py:2089-2091). It sends the scheduler stats of a step to only one front end (vllm/v1/core/sched/scheduler.py:2516-2521).

The page Data parallel serving: several engine cores behind one endpoint explains load balancing modes and waves.

Deep dive

Start-up order and the ready handshake

  1. The API server process makes AsyncLLM (vllm/entrypoints/launchers/api_server/entry.py:93-103).
  2. The engine core client binds the ROUTER and PULL sockets and starts the engine core processes (vllm/v1/engine/core_client.py:670-702).
  3. Each engine core loads the general plugins, builds the executor and the workers, profiles memory and builds the KV cache, then the scheduler (vllm/v1/engine/core.py:129-185).
  4. The engine core starts its I/O threads. The input thread sends the ready payload on each DEALER socket. A ROUTER can only send to a peer that has sent to it first (vllm/v1/engine/core.py:1961-1968).
  5. The client receives one ready message per engine, with timeout VLLM_ENGINE_READY_TIMEOUT_S, and applies the values from the engine (vllm/v1/engine/core_client.py:753-771). For example, it takes the smaller max_model_len and adds up num_gpu_blocks over the engines (vllm/v1/engine/core_client.py:865-873).
  6. The client starts MPClientEngineMonitor (vllm/v1/engine/core_client.py:776-777). Then AsyncLLM makes the stat loggers and starts the output handler if an event loop runs (vllm/v1/engine/async_llm.py:203-224).

Deep dive

Docs and code: four differences

  • "1 worker process per GPU". The design doc says so for every GPU (docs/design/arch_overview.md:89-91). In the code, with TP = PP = DP = 1, the backend is "uni" and the worker is an object in the engine core process (vllm/config/parallel.py:1099-1100). So the doc's formula A + DP + N gives 3 processes for a single GPU (docs/design/arch_overview.md:113), but the code runs 2.
  • "1 DP coordinator process (only when data parallelism is enabled)". The doc gives this rule (docs/design/arch_overview.md:97-99). The code does not start it for a dense model with external load balancing (vllm/config/vllm.py:868-874).
  • The process total. The doc counts 17 processes for -tp=2 -dp=4 (docs/design/arch_overview.md:123-125). With more than one API server, the CLI process stays alive as a supervisor (vllm/entrypoints/cli/serve.py:384-390). So the real total is 18. (Derived.)
  • AsyncLLMEngine. The doc says the OpenAI-compatible server uses AsyncLLMEngine (docs/design/arch_overview.md:166). The server makes AsyncLLM (vllm/entrypoints/launchers/api_server/entry.py:94); AsyncLLMEngine is only an old alias.

The docs images are useful as a second view: TP = 4 and TP = 2, DP = 4.

What can go wrong#

  • The engine core does not become ready. A large model can load for a long time. After VLLM_ENGINE_READY_TIMEOUT_S (600 s by default) the client raises TimeoutError with a message that names the variable (vllm/v1/engine/core_client.py:756-768).
  • A worker process dies. The worker monitor of the executor logs "Worker proc ... died unexpectedly" and calls the failure callback (vllm/v1/executor/multiproc_executor.py:314-326). The callback puts EXECUTOR_FAILED into the input queue of the engine core (vllm/v1/engine/core.py:1174-1176). The busy loop raises RuntimeError("Executor failed.") (vllm/v1/engine/core.py:1766-1767).
  • The engine core dies. On a fatal error it sends ENGINE_CORE_DEAD to every API server (vllm/v1/engine/core.py:1570-1576, vllm/v1/engine/core.py:2066-2069). The client then raises EngineDeadError (vllm/v1/engine/core_client.py:581-584). The API server shuts down, unless VLLM_KEEP_ALIVE_ON_ENGINE_DEATH is set (vllm/entrypoints/launchers/launcher.py:325-337).
  • Not enough GPUs. When the world size is larger than the number of GPUs on the node, the config raises ValueError (vllm/config/parallel.py:1067-1078).
  • Flags that do not combine. --api-server-count > 0 with --headless raises ValueError (vllm/entrypoints/cli/serve.py:69-75). Runtime LoRA updates with more than one API server raise ValueError (vllm/entrypoints/cli/serve.py:315-318).

Why it matters. To size a server, you must know how many processes and CPU threads it needs. To debug it, you must know which process logs what. A tokenizer error appears in an API server, a scheduler error in an engine core, and a CUDA error in a worker. To scale it, you must know which flag adds which process.

Check yourself#

  1. 1
    You run vllm serve with one GPU and default flags. How many vLLM processes run, and where does the worker run?
    easy
    Show answer

    Two: the API server (the CLI process) and one engine core process. The world size across DP is 1, so the executor backend is "uni" (vllm/config/parallel.py:1099-1100). UniProcExecutor builds the worker inside the engine core process (vllm/v1/executor/uniproc_executor.py:51-75).

  2. 2
    Which socket types carry requests and outputs between an API server and an engine core?
    easy
    Show answer

    Requests: the API server's ROUTER sends to the engine core's DEALER. Outputs: the engine core's PUSH sends to the API server's PULL (vllm/v1/engine/core_client.py:673-682, vllm/v1/engine/core.py:1935-1943, vllm/v1/engine/core.py:2046-2052).

  3. 3
    Why does the engine core process have an input thread and an output thread, and not only the busy loop?
    medium
    Show answer

    ZMQ socket I/O releases the GIL, and the main thread often waits for the GPU. So the I/O threads can receive, send and (de)serialize messages while the GPU runs the step. The comment at vllm/v1/engine/core.py:1238-1242 gives this reason. The input thread even builds the Request object, with its block hashes, in parallel with the model (vllm/v1/engine/core.py:1114-1128).

  4. 4
    You run vllm serve with -dp 2, TP = 1 and a dense model on one node. How many processes run, and is there a worker process?
    hard
    Show answer

    Eight: the CLI supervisor, two API servers, one DP coordinator, two engine cores and two worker processes. The default API server count is the DP size (vllm/entrypoints/cli/serve.py:124-125). Internal load balancing needs the coordinator (vllm/config/vllm.py:870-874). The backend test uses world_size_across_dp = 2, so the backend is "mp", not "uni" (vllm/config/parallel.py:1055-1061). MultiprocExecutor starts one process for its one local rank (vllm/v1/executor/multiproc_executor.py:191-207).

  5. 5
    With TP = 2, which worker answers execute_model, and how does the call reach the other worker?
    hard
    Show answer

    The executor puts the call once into the shared-memory MessageQueue, which every worker reads (vllm/v1/executor/multiproc_executor.py:428). Only the output rank replies. It is world_size − TP × PCP = 2 − 2 = 0, the first TP rank of the last PP stage (vllm/v1/executor/multiproc_executor.py:549-563).

  • The engine core loop: threads, queues and the busy loopThe engine core process runs three threads. An input thread decodes requests, the main thread runs the busy loop with the scheduler and the executor, and an output thread sends the results back.
  • Executors and workers: from the engine core to the GPUsThe executor starts the workers and runs each call on all of them. The uni executor calls one worker in the engine core process; the multiproc executor sends calls to one worker process per GPU through a shared-memory queue.
  • Data parallel serving: several engine cores behind one endpointWith --data-parallel-size N, vllm serve runs N engine cores with their own KV caches. API servers pick an engine for each request with a load score; a DP coordinator publishes the load counts. Dense models run independent engines; MoE models step in lockstep, in waves, with dummy batches.
  • Process groups: how vLLM slices its ranksEach worker puts all ranks into one grid of shape (DP, PP, PCP, TP) and cuts it into process groups. Each group is a GroupCoordinator with a gloo CPU group, an NCCL device group and, for groups of more than one rank, a device communicator that picks the all-reduce implementation.
  • Tour: Life of a chat requestFollow one streaming POST /v1/chat/completions request through vllm serve in 16 stops: FastAPI route, chat template, AsyncLLM, ZMQ, engine core, scheduler, Model Runner V2, sampler, detokenizer and the SSE chunks.
  • Tour: One step across GPUsFollow two requests through vllm serve -tp 2 -dp 2 in 13 stops: the API servers pick an engine each, two independent engine cores schedule, each broadcasts the step to its two workers through shared memory, the workers meet in 65 all-reduces on their TP group, only rank 0 replies, and the coordinator publishes the new load.
  • Tour: Start-up of vllm serveFollow vllm serve on one GPU in 18 stops, from the console script to "Application startup complete" - the parsers, create_engine_config, VllmConfig, AsyncLLM, the spawned engine core, model loading, the memory profile, compilation, CUDA graph capture, the READY handshake and uvicorn - with the log line of each stop.
  • v1/engine/core_client.py: the engine core clientsvllm/v1/engine/core_client.py holds the clients that the front end uses to talk to the engine core: an in-process client, and ZMQ clients for blocking, asyncio and data parallel use. It binds the sockets, waits for the engines, reads the outputs and runs utility calls.
  • v1/engine/async_llm.py: AsyncLLM, the engine client of vllm servevllm/v1/engine/async_llm.py defines AsyncLLM, the EngineClient of the API server. It builds the front-end parts of the engine, turns each request into an async stream of RequestOutputs, and runs the one output handler task.
