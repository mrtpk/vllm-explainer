Executors and workers: from the engine core to the GPUs

IntermediatevLLM conceptsabout 12 min read + 3 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The process and thread architecture of vllm serve Intermediate
  • The engine core loop: threads, queues and the busy loop Intermediate

In one sentence

The executor starts the workers and runs every engine call on all of them. Each worker owns one GPU and holds the model runner.

The idea#

The EngineCore does not touch a GPU itself. It talks to an executor, and the executor talks to the workers. A worker owns one GPU: it sets up the device and the process groups, loads its part of the model, and holds the model runner. With tensor parallelism, one model runs on several GPUs, so there are several workers (Parallelism basics↗).

The engine core asks the executor for things like "run this step" or "how much memory is free?". The executor turns each request into a collective_rpc: it calls the same worker method on every worker, and collects the results. How it reaches the workers depends on the backend:

  • The uni executor keeps the one worker as an object in the engine core process. A call is a plain Python call. By default, vLLM uses it only when TP = PP = DP = 1.
  • The multiproc executor starts one worker process per GPU on the node. It writes each call once into a shared-memory MessageQueue, and all workers read it.
  • The Ray executor uses the same message queues, but its workers are Ray actors (vllm/v1/executor/ray_executor_v2.py:239-247).

An everyday comparison. Think of a conductor and an orchestra. The conductor (the engine core) gives one sign, and every musician (worker) plays the same bar on their own instrument (GPU). One musician, the first violin, reports when the bar is done. The comparison stops here: the musicians in vLLM also talk to each other during the bar (NCCL collectives), and the conductor never hears that.

The picture#

Read panel 2 from left to right and back. The call goes out once and reaches every worker. Only one result comes back. Panel 3 explains how a worker keeps the overlap of Async scheduling: overlap the CPU and the GPU: its main thread never waits for the GPU result.

In the code#

Step 1: which backend#

distributed_executor_backend has the default None (vllm/config/parallel.py:290-292). ParallelConfig.__post_init__ fills it in:

world_size_across_dp is world_size × data_parallel_size (vllm/config/parallel.py:626-629), and world_size is PP × TP × PCP (vllm/config/parallel.py:965-969). So, when you do not set a backend, "uni" applies only when TP, PP, DP (and the prefill context parallel size) are all 1. With DP = 2 and TP = 1, each engine core gets one worker process (see The process and thread architecture of vllm serve). Ray replaces "mp" only after three earlier tests (vllm/config/parallel.py:1063-1078). TPU with SPMD picks "uni". CUDA with more than one node (--nnodes) keeps "mp". Too few GPUs on the node raise ValueError. Then Ray is used when the data parallel backend is Ray, or when Ray is installed and a Ray placement group is set or active (vllm/config/parallel.py:1079-1095). Executor.get_class then maps the name to a class:

You can also pass your own Executor subclass, as a class or as a qualified name (lines 69-75 and 92-98). The Hooks in the engine core and the workers page lists this extension point.

Step 2: the executor interface#

Every executor implements collective_rpc. The docstring defines it: run a method "on all workers", by name or as a callable that gets the worker as self (vllm/v1/executor/abstract.py:209-242). The base class builds the step calls on top of it:

With non_block=True, the call returns a Future instead of the result. The default loop, step_with_batch_queue, uses this for both calls of a step (vllm/v1/engine/core.py:727-729, vllm/v1/engine/core.py:743-745). In step(), only execute_model uses it (vllm/v1/engine/core.py:668, vllm/v1/engine/core.py:676). Start-up and control calls go the same way. For example, determine_available_memory is collective_rpc("determine_available_memory") (vllm/v1/executor/abstract.py:156-157), and sleep is collective_rpc("sleep", ...) (vllm/v1/executor/abstract.py:393-403).

Step 3: UniProcExecutor, one worker in the same process#

The executor wraps the worker in a WorkerWrapperBase, then runs the three start-up steps directly: init_worker, init_device and load_model. A call is run_method on the wrapper, which calls getattr(wrapper, method) (vllm/v1/serial_utils.py:485-508). The wrapper's own methods, such as execute_model, run first; other names go to the worker through __getattr__ (vllm/v1/worker/worker_base.py:365-366):

With non_block=True, the method still runs at once, in the engine core's main thread. Only an AsyncModelRunnerOutput result becomes a future that waits later, in get_output() (vllm/v1/executor/uniproc_executor.py:32-48). So non_block does not make the call faster. It moves the wait for the GPU result to the moment when the engine core pops the step from its batch queue.

Step 4: MultiprocExecutor starts the worker processes#

_init_executor does four things in order (vllm/v1/executor/multiproc_executor.py:119-268):

  1. It makes the broadcast queue, with one reader per worker and a chunk size from VLLM_MQ_MAX_CHUNK_BYTES_MB (16 MiB by default):
  2. It starts one process per local rank with WorkerProc.make_worker_process (vllm/v1/executor/multiproc_executor.py:191-207). The process name is VllmWorker-<rank>, and it uses the context of get_mp_context(), normally spawn (vllm/v1/executor/multiproc_executor.py:723-750).
  3. It waits until every worker sends READY through a pipe, with the handle of its reply queue (vllm/v1/executor/multiproc_executor.py:786-822).
  4. It starts the worker monitor (Step 6), connects the reply queues, and computes output_rank (vllm/v1/executor/multiproc_executor.py:224-268).

Step 5: collective_rpc over shared memory#

  1. Line 428: the call goes into the broadcast queue once, as (method, args, kwargs, output_rank). The queue pickles it (vllm/distributed/device_communicators/shm_broadcast.py:925-941).
  2. Lines 430-432: with an output_rank, the executor reads only that worker's reply queue.
  3. Lines 444-448: when the worker that replies failed, it sends a FAILURE status, and the executor raises RuntimeError with the error text.
  4. Lines 452-456: the reply is read later, in FutureWrapper.result().

For execute_model and sample_tokens, the output_rank is the first TP worker of the last PP stage (vllm/v1/executor/multiproc_executor.py:342-366, vllm/v1/executor/multiproc_executor.py:549-563). The other workers run the same method but send nothing back. With a KV or EC connector, all workers reply, and an aggregator merges their outputs (vllm/v1/executor/multiproc_executor.py:405-419, vllm/v1/engine/core.py:191-194).

The replies come back in call order, and FutureWrapper uses that. Each future joins a shared deque. When you ask a future for its result, it first reads the replies of all older futures (vllm/v1/executor/multiproc_executor.py:79-110). So the engine core can wait for the sample_tokens future of step N, and the execute_model reply of step N is read on the way.

Step 6: detecting a dead worker#

Two threads watch the processes. In the engine core, MultiprocWorkerMonitor waits on the sentinels of all worker processes:

The callback puts EXECUTOR_FAILED into the engine core's input queue, and the busy loop raises (The engine core loop: threads, queues and the busy loop, Step 10). In each worker, DeathPipeMonitor blocks on a pipe from the parent. When the parent process ends, the pipe returns EOFError, and the worker shuts down its queues (vllm/v1/executor/multiproc_executor.py:835-859). The wait for a call that hangs also ends: execute_model and sample_tokens use the timeout VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS, 300 s by default (vllm/v1/executor/multiproc_executor.py:350, vllm/envs.py:1861-1863). The engine core then gets TimeoutError (vllm/v1/executor/multiproc_executor.py:440-443); the hung worker keeps running.

Step 7: WorkerProc, the worker process#

The process target is WorkerProc.worker_main. It installs signal handlers, builds the WorkerProc, sends READY and enters the busy loop (vllm/v1/executor/multiproc_executor.py:861-948). The constructor is the same start-up as in the uni executor:

init_worker loads the general plugins and makes the worker class from parallel_config.worker_cls (vllm/v1/worker/worker_base.py:268-347). On CUDA that is vllm.v1.worker.gpu_worker.Worker, when worker_cls is "auto" (vllm/platforms/cuda.py:330-331). The busy loop reads calls forever:

Line 1070: only the output rank (or every worker when output_rank is None) sends a reply. With async scheduling, handle_output passes the result to the WorkerAsyncOutputCopy thread, which waits for the GPU copy and then writes the reply (vllm/v1/executor/multiproc_executor.py:1000-1002, vllm/v1/executor/multiproc_executor.py:1019-1039).

Step 9: the worker builds Model Runner V2#

use_v2_model_runner is true by default when Triton is present and no unsupported feature is set (vllm/config/vllm.py:713-748). A multimodal encoder-only instance gets MMEncoderModelRunner (lines 570-573). Otherwise the worker falls back to Model Runner V1 (lines 581-583); the page The model runner (Model Runner V2) names the cases.

Step 10: Ray in one paragraph#

RayExecutorV2 subclasses MultiprocExecutor. Its docstring says it reuses "the MQ-based control plane and NCCL data plane", with Ray actors as workers (vllm/v1/executor/ray_executor_v2.py:239-247). Each actor runs a RayWorkerProc, a WorkerProc that learns its GPU after Ray places it (vllm/v1/executor/ray_executor_v2.py:79-100). So steps 5, 8 and 9 of this page also hold for Ray, and so does the worker busy loop. Process creation, placement and the monitoring differ: Ray has its own RayWorkerMonitor thread (vllm/v1/executor/ray_executor_v2.py:487-537), and RayWorkerProc.run() calls worker_busy_loop without worker_main (vllm/v1/executor/ray_executor_v2.py:223-231). The inherited supports_async_scheduling() is true, so async scheduling stays on.

What can go wrong#

  • "World size (...) is larger than the number of available GPUs". With the mp backend, all workers of one engine must fit on the node (vllm/config/parallel.py:1067-1078).
  • "RPC call to execute_model timed out." A step took more than 300 s, or a worker hangs in a collective. Check the logs of every worker; the hung rank is often not the one that reports (vllm/v1/executor/multiproc_executor.py:440-443).
  • "Worker proc VllmWorker-1 died unexpectedly". Often the kernel OOM killer or a CUDA crash. The engine then fails all requests (The engine core loop: threads, queues and the busy loop, Step 10).
  • The error message has no stack trace. The reply carries only str(exception) (vllm/v1/executor/multiproc_executor.py:1007-1008). The traceback is in the worker's own log line "WorkerProc hit an exception.".
  • An out-of-tree executor turns off async scheduling. See Async scheduling: overlap the CPU and the GPU.

Why it matters. The executor is the boundary between "what to run" and "where it runs". To debug a multi-GPU server, you must know that every worker runs every call, that only one replies, and which thread waits where. To size a server, you must know that TP = 1 and DP = 1 give no worker process at all.

Check yourself#

  1. 1
    Which executor backend does vllm serve use with one GPU and default flags, and why is there no worker process?
    easy
    Show answer

    "uni", because world_size is 1 and DP is 1 (vllm/config/parallel.py:1099-1100). UniProcExecutor makes the worker as an object in the engine core process and calls it directly (vllm/v1/executor/uniproc_executor.py:51-75).

  2. 2
    With TP = 4, how many times does the executor write one execute_model call into shared memory, and how many replies does it read?
    medium
    Show answer

    Once, into rpc_broadcast_mq, which all four workers read (vllm/v1/executor/multiproc_executor.py:428). It reads one reply, from output_rank = world_size - TP × PCP = 0 (vllm/v1/executor/multiproc_executor.py:549-563). With a KV connector, it reads all four and aggregates them (vllm/v1/executor/multiproc_executor.py:405-419).

  3. 3
    The engine core waits only for the sample_tokens future of a step. How does the execute_model reply of the same step get read from the reply queue?
    medium
    Show answer

    FutureWrapper.result() first drains all older futures in the shared futures_queue, in order (vllm/v1/executor/multiproc_executor.py:92-100). The execute_model future is older, so its reply is read first.

  4. 4
    Async scheduling is on and the executor is mp. Which thread of the worker process waits for the copy of the sampled tokens to the CPU? Why not the main thread?
    hard
    Show answer

    The WorkerAsyncOutputCopy thread. handle_output puts the result into async_output_queue (vllm/v1/executor/multiproc_executor.py:1014-1022), and that thread calls enqueue_output, which calls get_output() (vllm/v1/executor/multiproc_executor.py:995-1002, vllm/v1/executor/multiproc_executor.py:1037-1039). So the main thread can dequeue and start the next call at once, which keeps the GPU stream full.

Related pages

  • Async scheduling: overlap the CPU and the GPUWith async scheduling, the engine core schedules and starts step N+1 before it waits for the token of step N. Placeholders in the scheduler and a GPU-side token buffer in Model Runner V2 make this possible.
  • The model runner (Model Runner V2)Model Runner V2 keeps every running request in a fixed row of GPU tensors, gathers each step's inputs from those rows with GPU kernels, runs the model (CUDA graph or eager), and samples in a second call that returns an AsyncOutput without a GPU wait.
  • Process groups: how vLLM slices its ranksEach worker puts all ranks into one grid of shape (DP, PP, PCP, TP) and cuts it into process groups. Each group is a GroupCoordinator with a gloo CPU group, an NCCL device group and, for groups of more than one rank, a device communicator that picks the all-reduce implementation.
  • The KV cache manager: blocks, the block pool and memory sizingIn the engine core, the KVCacheManager hands out KV blocks to the scheduler through a coordinator, one single-type manager per KV cache group and one BlockPool. The workers only receive block ids. The number of blocks comes from a memory profile at start-up.
  • Hooks in the engine core and the workersSeveral extension points of the engine core and the workers are config fields or registries, not entry-point groups - scheduler_cls, worker_cls and worker_extension_cls, logits processors, model loaders, sleep-mode backends and KV cache dtypes. This page shows where each one is read and what your class must do.
  • v1/executor/multiproc_executor.py: MultiprocExecutor and WorkerProcvllm/v1/executor/multiproc_executor.py starts one worker process per local GPU, broadcasts every call to them through a shared-memory MessageQueue, reads the reply of one output rank, and watches the processes for failures.
  • v1/worker/gpu_worker.py: the GPU Workervllm/v1/worker/gpu_worker.py defines Worker, the object that owns one GPU. It sets up the device and NCCL, builds Model Runner V2, profiles memory to size the KV cache, warms up the model, and forwards each step to the model runner.
