Sampling and logits processors in Model Runner V2

AdvancedvLLM conceptsabout 10 min read + 4 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The model runner (Model Runner V2) Advanced
  • The OpenAI-compatible API Beginner

In one sentence

The sampler copies the logits to FP32 only when needed and runs a fixed chain of processors. Then it draws one token per row.

The idea#

Sampling picks the next token from the logits. Temperature, top-k and top-p shape the distribution, and a seed makes the random draw repeatable (Sampling: temperature, top-k, top-p, seeds↗). This page shows how vLLM's sampler does these steps for a whole batch, and where your own code can change the logits.

Each request brings its SamplingParams. When a request enters the batch, the sampler writes its settings into per-slot GPU buffers, one row per request slot. In every step, it works on all logits rows at once. First come the logits processors (logit bias, penalties, bad words, then yours). Then come temperature, min_p, top-k and top-p, and then the draw. A stage that no request in the batch uses is skipped, without a kernel launch.

An everyday comparison. Think of a mail sorting line. Each letter (a logits row) passes the same stations in a fixed order: stamps, weight check, address check, then the bin. Each letter carries a slip that says which stations apply to it. The comparison stops being true in one place. vLLM runs a whole tray through each station at once, and a station turns on when one letter needs it.

The picture#

Read the panels from top to bottom. Teal stages are built in, violet is where custom processors run, and emerald is the token draw. The dashed arrow in panel 3 means "or": one batch takes one path.

In the code#

Step 1: the sampling parameters of a request#

The OpenAI server turns the request into a SamplingParams object. Unset fields take the server default, which comes from the model's generation_config.json with the default --generation-config auto (The OpenAI-compatible API). These fields change the sampler:

FieldDefaultStage
temperature1.0 (vllm/sampling_params.py:308)scaling; 0 means greedy
top_p, top_k, min_p1.0, 0 (all), 0.0 (vllm/sampling_params.py:315-321)filtering
seedNone (vllm/sampling_params.py:325)Gumbel noise; forces the non-fused path
presence_penalty, frequency_penalty, repetition_penalty0.0, 0.0, 1.0 (vllm/sampling_params.py:296-304)PenaltiesState
min_tokens0 (vllm/sampling_params.py:339)LogitBiasState masks stop tokens
logit_bias, allowed_token_idsNone (vllm/sampling_params.py:409-412)LogitBiasState
bad_wordsNone (vllm/sampling_params.py:420)BadWordsState
thinking_token_budgetNone (vllm/sampling_params.py:427)forcing the end of thinking
logprobs, prompt_logprobsNone (vllm/sampling_params.py:342-352)extra outputs
extra_argsNone (vllm/sampling_params.py:415)free-form; custom processors read it

A temperature below 1e-5 means greedy: vLLM resets top_p, top_k and min_p and requires n = 1 (vllm/sampling_params.py:615-620, vllm/sampling_params.py:769-773). In the OpenAI API, vllm_xargs becomes extra_args (vllm/entrypoints/openai/chat_completion/protocol.py:770).

Step 2: per-slot state, written once per request#

The sampler is built in load_model, only on the last pipeline rank and only for generative models (vllm/v1/worker/gpu/model_runner.py:463-467). Its constructor fixes the list of processors:

When the model runner adds a new request, the sampler calls add_request(slot, params) on every stage. Each stage returns whether it changes the logits of this request; the OR of all answers is stored per slot (vllm/v1/worker/gpu/sample/sampler.py:96-107). The sampling state itself returns true only for a non-zero temperature together with a temperature other than 1, or a set min_p, top-k or top-p:

The writes are staged on the CPU. The model runner calls sampler.apply_staged_writes() once per step, which copies them to the GPU buffers (vllm/v1/worker/gpu/model_runner.py:1251-1255, vllm/v1/worker/gpu/sample/sampler.py:109-116).

Step 3: the processing chain#

In each step the model runner computes the logits for the sampled rows and applies the grammar bitmask (Structured outputs: JSON schemas, grammars and token bitmasks in vLLM). Then the sampler runs apply_sampling_params:

  1. Lines 238-239: if no request in the batch needs processing, the raw logits go straight to the draw. There is no copy.
  2. Line 242: else the logits are copied into a new FP32 tensor, [rows, vocab].
  3. Lines 255-256: the processors run in list order. LogitBiasState does allowed token ids, logit_bias and min_tokens in one kernel. PenaltiesState does the three penalties. BadWordsState masks the last token of a bad word when the earlier ones match. Then come the custom processors.
  4. Line 260: thinking-budget forcing runs after all processors, so no processor can overwrite it (the code comment at lines 258-259).
  5. Lines 263-268: temperature and min_p, in place. Each skips its kernel when no request in the batch uses it (vllm/v1/worker/gpu/sample/states.py:87-103).

The order matters. The code comment says that bias adds and penalties scale, "so the two do not commute" (vllm/v1/worker/gpu/sample/sampler.py:69-70).

Step 4: the draw - fused FlashInfer or Gumbel#

  • Fused path (lines 307-315, 339-343). It runs only when the batch uses top-k or top-p, and no request is greedy, has a seed, or asks for processed logprobs. The sampling mask must be off, which is the default. FlashInfer's sampler must also support the GPU: CUDA, a supported compute capability, more than 16 SMs, and a working JIT build. VLLM_USE_FLASHINFER_SAMPLER must be on, the default (vllm/v1/worker/gpu/sample/sampler.py:88-90, vllm/v1/sample/ops/topk_topp_sampler.py:102-150, vllm/envs.py:886-890). The Tour: One forward pass (stop 14) walks through this for a default request.
  • Fallback (lines 347-359). vLLM masks top-k and top-p itself and runs the Gumbel sampler. Gumbel-max adds noise to logits / T and takes the argmax; at temperature 0 it is a plain argmax (vllm/v1/worker/gpu/sample/gumbel.py:182-187).

The conditions are for the whole batch. One greedy or seeded request sends every request of that step to the fallback path.

Step 5: seeds without generators#

Model Runner V2 keeps no torch.Generator per request. The Gumbel noise is a hash of the request's seed, the token position and the token id (vllm/v1/worker/gpu/sample/gumbel.py:197-209). A request without a seed gets a random 64-bit seed when it enters the batch (vllm/v1/worker/gpu/sample/states.py:54-58). So the noise of a seeded request does not depend on the other rows of the batch (derived from the hash inputs above). Its logits must still be the same; see Determinism and batch invariance↗.

Step 6: custom logits processors#

A custom processor subclasses the Model Runner V2 LogitsProcessor:

The methods are validate_params (class method, at admission), add_request(req_idx, params), apply_staged_writes() and apply(logits, ctx) (vllm/v1/worker/gpu/sample/logits_processor/interface.py:118-158). ctx is a LogitsContext: the slot of each row, the positions, the input ids and a CPU bound of the sequence lengths (vllm/v1/worker/gpu/sample/logits_processor/interface.py:63-89). Rows are reordered every step, so a processor must find its rows through ctx.expanded_idx_mapping.

There are two sources, and the loader puts entry-point plugins first (vllm/v1/worker/gpu/sample/logits_processor/loader.py:136-146):

  • the entry-point group vllm.logits_processors, which VLLM_PLUGINS does not filter;
  • --logits-processors (ModelConfig.logits_processors), with "module:Class" strings (vllm/config/model.py:407).

Hooks in the engine core and the workers (Step 3) covers loading, errors and the front-end check. The repository has a full example, a DRY repetition penalty that reads extra_args (examples/features/logits_processor/dry.py:659-688).

add_request returns True by default

The base add_request returns True (vllm/v1/worker/gpu/sample/logits_processor/interface.py:126-134). A processor that does not override it marks every request as "needs processing". Then every step copies the logits to FP32, and the fast skip of Step 3 never happens (derived from vllm/v1/worker/gpu/sample/sampler.py:101-103). Return False for requests that your processor ignores.

The Model Runner V2 interface has no "argmax invariant" flag. The legacy V1 interface has is_argmax_invariant, and a BatchUpdate object with the added, removed and moved rows of the batch. Model Runner V2 rejects such classes (vllm/v1/sample/logits_processor/interface.py:37-40, vllm/v1/sample/logits_processor/interface.py:86-87, vllm/v1/worker/gpu/sample/logits_processor/loader.py:67-72).

Deep dive#

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Deep dive

Worked example: temperature 0.6, top_p 0.9, repetition_penalty 1.1, seed 7

Request (example), alone in the batch on an H100, Llama-3.1-8B (vocabulary 128,256):

{"model": "meta-llama/Llama-3.1-8B-Instruct",
 "messages": [{"role": "user", "content": "Name three rivers."}],
 "temperature": 0.6, "top_p": 0.9, "seed": 7,
 "repetition_penalty": 1.1}

At add_request (once):

  1. SamplingStates: temperature 0.6, top_p 0.9, top_k 0 → 128,256 (no limit), min_p 0, seed 7 with seeds_set = True. It returns True, because 0.6 is not 0 or 1.
  2. LogitBiasState: no allowed ids, no bias, min_tokens 0 → False.
  3. PenaltiesState: repetition 1.1 → True. It queues the request for a bincount of its prompt into prompt_bin_mask (vllm/v1/worker/gpu/sample/penalties.py:53-82).
  4. BadWordsState: no bad words → False. No custom processors, no thinking budget.

In each decode step:

  1. Logits [1, 128256] BF16 → copy to FP32: 513,024 bytes.
  2. Bias stage: no request in the batch uses it → skipped.
  3. Penalties: take each token that is in the prompt or the output so far. Its logit is divided by 1.1 if positive, else multiplied by 1.1 (vllm/v1/worker/gpu/sample/penalties.py:174-177). A logit of 5.5 becomes 5.0; a logit of -2.0 becomes -2.2.
  4. Bad words: skipped. Temperature: all logits divided by 0.6. min_p: skipped.
  5. Top-p is set, but the request has a seed. So the fused path is not eligible (any_explicit_seed), even on an H100. vLLM applies top-p itself and runs the Gumbel sampler with seed 7 and the position of the token.
  6. After the draw, post_update adds the new token to output_bin_counts, so the next step penalises it too (vllm/v1/worker/gpu/input_batch.py:588-602).

Without "seed": 7, the same request would take the fused FlashInfer path on an H100. Penalties and temperature still run first, on the FP32 copy.

Deep dive

logprobs and prompt_logprobs: what they return and what they cost

  • Limit. --max-logprobs defaults to 20; -1 means no cap (vllm/config/model.py:286-290). A request above the cap gets a validation error (vllm/sampling_params.py:922-937). logprobs: -1 means the whole vocabulary (vllm/v1/worker/gpu/sample/states.py:60-65).
  • Raw or processed. --logprobs-mode defaults to raw_logprobs: values before any processor. processed_* modes return values after all processors, temperature and top-k/top-p (vllm/config/model.py:291-299). The sampler picks the tensor in lines vllm/v1/worker/gpu/sample/sampler.py:171-186. A processed mode with any logprobs request disables the fused sampler for the batch (Step 4).
  • Output logprobs cost one top-k over the vocabulary per sampled row, on the GPU.
  • prompt_logprobs cost much more. The worker computes logits for every prompt token, not only the last, in chunks of 1,024 rows (vllm/v1/worker/gpu/sample/prompt_logprob.py:20, vllm/v1/worker/gpu/sample/prompt_logprob.py:283-301). Take a 4,000-token prompt and a 128,256-token vocabulary. That is 4 chunks of up to 1,024 × 128,256 logits, about 263 MB in BF16 each. Such a request also skips reading the prefix cache (vllm/sampling_params.py:624-632).

Worked number. output_bin_counts exists even when no request uses penalties. The code comment warns that it can take "GBs of GPU memory" (vllm/v1/worker/gpu/sample/penalties.py:46-50). With max_num_seqs = 1024 and a 128,256-token vocabulary: 1,024 × 128,256 × 4 bytes = 525 MB. With a 151,936-token vocabulary: 622 MB. This memory is taken before the KV cache gets its share.

Other limits: VLLM_MAX_NUM_BAD_WORDS 128 and VLLM_MAX_BAD_WORDS_TOTAL_TOKENS 1024 (vllm/envs.py:1152-1159); stop tokens for min_tokens at most 128 (vllm/v1/worker/gpu/sample/logit_bias.py:22, vllm/v1/worker/gpu/sample/logit_bias.py:98-104).

What can go wrong#

  • The model's defaults change your sampling. A request without temperature uses the value from generation_config.json, not 1.0. Use --generation-config vllm for vLLM's neutral defaults (The OpenAI-compatible API).
  • One seeded request slows the batch. A seed, a greedy request or a processed-logprobs request makes the whole step skip the fused sampler (Step 4).
  • A V1 logits processor plugin stops the start-up. Model Runner V2 raises ValueError at model load (vllm/v1/worker/gpu/sample/logits_processor/loader.py:67-72).
  • --logits-processors on a pooling model. It raises ValueError. Entry-point processors are skipped for pooling models, with only a debug log (vllm/v1/worker/gpu/sample/logits_processor/loader.py:172-179).
  • Too many ids. More than 1,024 allowed ids or bias entries, or more than 128 stop tokens with min_tokens, raise ValueError in the worker (vllm/v1/worker/gpu/sample/logit_bias.py:63-104).

Why it matters. The sampler runs in every step for every request. Know which stage runs and which settings force the slower path. Then you can choose good server defaults, and write processors that cost nothing for other requests.

Check yourself#

  1. 1
    In which order do the built-in processors run?
    easy
    Show answer

    LogitBiasState, PenaltiesState, BadWordsState, then the custom processors (vllm/v1/worker/gpu/sample/sampler.py:71-76). Temperature and min_p come after them (vllm/v1/worker/gpu/sample/sampler.py:262-268).

  2. 2
    A batch has 63 requests with temperature 0.7 and top_p 0.95, and one request with temperature 0. Which sampler draws the tokens on an H100?
    medium
    Show answer

    The Gumbel fallback for all 64. One greedy request makes any_greedy true, so the fused path is not eligible for the batch (vllm/v1/worker/gpu/sample/sampler.py:307-315). The greedy request gets a plain argmax inside the Gumbel kernel (vllm/v1/worker/gpu/sample/gumbel.py:182-187).

  3. 3
    Your processor changes the logits only for requests with extra_args["boost"]. Why should add_request return False for the others?
    medium
    Show answer

    The sampler stores the OR of all stages per slot. If any stage says True, the step copies the logits to FP32 and runs the chain (vllm/v1/worker/gpu/sample/sampler.py:101-103, vllm/v1/worker/gpu/sample/sampler.py:238-242). The default add_request returns True (vllm/v1/worker/gpu/sample/logits_processor/interface.py:126-134).

  4. 4
    Two servers run the same seeded request (seed 7), one alone and one in a batch of 200. Why can the sampled tokens match, and what must also be true?
    hard
    Show answer

    The Gumbel noise depends only on the seed, the position and the token id (vllm/v1/worker/gpu/sample/gumbel.py:197-209), not on the other rows, so the noise is the same. The logits must also be the same in both batches, which needs batch-invariant kernels.

  5. 5
    How much GPU memory does output_bin_counts take with max_num_seqs = 512 and a 151,936-token vocabulary, and does it depend on penalty use?
    hard
    Show answer

    512 × 151,936 × 4 bytes = 311 MB. It is allocated in the constructor, whether or not a request uses penalties (vllm/v1/worker/gpu/sample/penalties.py:46-50).
