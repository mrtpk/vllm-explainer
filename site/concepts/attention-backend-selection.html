How vLLM chooses an attention backend

AdvancedvLLM conceptsabout 17 min read + 7 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The Platform interface Advanced
  • CustomOp, out-of-tree ops and IR op providers Advanced

In one sentence

When the worker builds the model, each attention layer asks the platform for a backend; CUDA takes the first valid entry of a priority list.

The idea#

Attention computes softmax(QKT)V for every head; MHA, GQA and MLA differ in how many key and value heads they store (Attention basics↗). vLLM has many implementations of this step. Each one is an attention backend: FlashAttention, FlashInfer, Triton, FlashMLA and more. A backend is fast only for some GPUs, head sizes and KV cache formats, so vLLM must choose one for each kind of layer.

The choice happens in the worker, while it builds the model. Each attention layer calls one function, the selector, with its own facts. Examples are the head size, the data type, the KV cache data type and MLA or not. The selector adds facts from the config and asks the platform. The platform method get_attn_backend_cls is a component picker: it returns the dotted name of a backend class.

On NVIDIA GPUs, CudaPlatform has a backend priority list list for each case: MLA or not, and the GPU generation. It asks each backend in the list whether it can serve this layer. The first backend that says yes wins. If the user names a backend with --attention-backend, vLLM checks only that one, and an invalid choice stops start-up.

All backend names are members of one enum, the AttentionBackendEnum. A plugin can replace the class behind a member, or add a new member, with register_backend. An out-of-tree platform can return any class name.

An everyday comparison. Think of a hospital that needs a surgeon for one operation. The head nurse has a ranked list of surgeons for each kind of operation. She asks each surgeon in order whether they can do this one. Each surgeon checks a fixed list of conditions and answers yes or no, with reasons. The first yes gets the job. If a patient asks for one surgeon by name, the nurse asks only that surgeon. The comparison stops here: vLLM asks every surgeon on the list, even after a yes, and it remembers the answer for the same question.

Simplified

The visual is a simplified model. It assumes that the CUDA wheels have vllm_flash_attn with FA3 on SM90 and FA4 on SM100, and that FlashInfer and FlashMLA import. On ROCm, VLLM_ROCM_USE_AITER is not set. The CPU is x86 with AVX-512 and no AMX. There is no VLLM_BATCH_INVARIANT, no --block-size, no KV connector, no sliding window and no attention sinks. It uses these rules from the code:

  1. C1. --enforce-eager sets the compilation mode to NONE (vllm/config/vllm.py:1745-1746). Otherwise level O2 sets VLLM_COMPILE (vllm/config/vllm.py:1806-1810).
  2. C2. An empty compile backend becomes the platform default, "inductor" (vllm/config/compilation.py:1080-1081, vllm/platforms/interface.py:172).
  3. C3. If the list has neither "all" nor "none", vLLM appends "none" for Inductor with a compile mode, else "all" (vllm/config/vllm.py:1819-1826). The CPU platform changes the mode later, in check_and_update_config (vllm/platforms/cpu.py:368-379, called at vllm/config/vllm.py:2046).
  4. C4. An op is enabled when the base mode is "all" or +name is set, and -name is not set (vllm/model_executor/custom_op.py:282-290).
  5. C5. A disabled op uses forward_native; an enabled op uses the method of the platform (vllm/model_executor/custom_op.py:189-205). RMSNorm's forward_cuda calls forward_native when batch invariance is off (vllm/model_executor/layers/layernorm.py:120). The default forward_hip calls forward_cuda; the default forward_cpu and forward_oot call forward_native (vllm/model_executor/custom_op.py:147-149, vllm/model_executor/custom_op.py:156-159, vllm/model_executor/custom_op.py:167-170).
  6. C6. RMSNorm's forward_native calls the IR op rms_norm, or fused_add_rms_norm with a residual (vllm/model_executor/layers/layernorm.py:79-99). Both ops get the same provider list. On CUDA its provider list is ["native"] with Inductor and a compile mode, else ["vllm_c", "native"] (vllm/platforms/cuda.py:716-734).
  7. A1. CUDA validates an explicit backend alone and raises ValueError if it is invalid (vllm/platforms/cuda.py:430-449).
  8. A2. Without one, CUDA validates its priority list and takes the valid entry with the smallest index (vllm/platforms/cuda.py:84-181, vllm/platforms/cuda.py:479-485).
  9. A3. A backend rejects a layer when it does not accept the head size or the KV dtype, or when use_mla does not match is_mla() (vllm/v1/attention/backend.py:302-307, vllm/v1/attention/backend.py:314-318). An MLA layer has head size 576. FLASH_ATTN and FLASHINFER reject it; TRITON_ATTN takes any head size from 32 (vllm/v1/attention/backends/flash_attn.py:423-433, vllm/v1/attention/backends/flashinfer.py:662-664, vllm/v1/attention/backends/triton_attn.py:378-379).
  10. A4. FLASH_ATTN needs capability 8.0 or higher. Its fp8 KV cache needs FA3 on SM90 or FA4 on SM100 (vllm/v1/attention/backends/flash_attn.py:456-457, vllm/v1/attention/backends/fa_utils.py:306-312).
  11. A5. FLASHINFER takes head sizes 64, 128, 256 and 512 on capability 8.0 to 12.1, with fp8 KV (vllm/v1/attention/backends/flashinfer.py:544-553, vllm/v1/attention/backends/flashinfer.py:662-675). TRITON_ATTN runs on any capability, with fp8 KV (vllm/v1/attention/backends/triton_attn.py:325-334, vllm/v1/attention/backends/triton_attn.py:404-405).
  12. A6-A9. FLASH_ATTN_MLA: KV auto, float16 or bfloat16 only, capability major 9 (vllm/v1/attention/backends/mla/flashattn_mla.py:42-46, vllm/v1/attention/backends/mla/flashattn_mla.py:69-70). FLASHMLA: fp8 KV, dense only on Hopper (vllm/v1/attention/backends/mla/flashmla.py:48-54, vllm/v1/attention/ops/flashmla.py:56-57). FLASHINFER_MLA: capability major 10, fp8 KV (vllm/v1/attention/backends/mla/flashinfer_mla.py:195-201, vllm/v1/attention/backends/mla/flashinfer_mla.py:220-221).
  13. A10. ROCm starts its MHA list with ROCM_ATTN; without AITER MLA its MLA list is only TRITON_MLA (vllm/platforms/rocm.py:499-526). An invalid explicit backend raises (vllm/platforms/rocm.py:781-785).
  14. A11. CPU ignores an explicit backend with an INFO log (vllm/platforms/cpu.py:183-184). MLA with fp8 KV raises; without AMX, MLA uses CPU_MLA (vllm/platforms/cpu.py:152-182). fp8 KV needs AMX or AVX-512 (vllm/v1/attention/backends/cpu_attn.py:69-75).
  15. A12. An out-of-tree platform decides alone. The test platform returns its own class for every layer (tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/dummy_platform.py:25-32).

The CustomOp half models RMSNorm in a Llama-like model only. It ignores these exceptions from CustomOp, out-of-tree ops and IR op providers:

  • +name entries that vLLM adds itself, for example +quant_fp8 for block-quantized weights (vllm/config/vllm.py:1799-1802), and the additions of ROCm and of ARM CPUs;
  • layers built with enforce_enable=True, and classes that override enabled();
  • two more ways to get compile mode NONE: TORCH_COMPILE_DISABLE=1 (vllm/config/vllm.py:1765-1770) and breakable CUDA graphs, which vLLM turns on by default for some architectures (vllm/config/vllm.py:849-851).

The visual does not show the block size choice, the ROCm results for an explicit FLASH_ATTN or FLASHINFER, or a library that fails to import. The deep dives explain them.

Step 2: register_backend changes the table#

  1. Lines 400-404. A string name such as "CUSTOM_MLA" calls AttentionBackendEnum.register. That method raises ValueError if the name exists already, or if it is not a valid identifier (vllm/v1/attention/backends/registry.py:180-187). It logs "Registered new attention backend" at INFO level (vllm/v1/attention/backends/registry.py:197).
  2. Lines 406-411. As a decorator, the override is the module and qualified name of the decorated class.
  3. Lines 413-418. With class_path, the override is that string. An enum member that has an override already gets the new one with no log and no error.

Step 4: one cached call to the platform#

  1. Line 206. @cache keys on all arguments. The 32 decoder layers of a Llama model ask the same question, so the platform runs once. The run-wide KV dtype is in the key too (lines 214-215).
  2. Lines 218-222. The platform gets the requested backend (an enum member or None), the AttentionSelectorConfig and the head count.
  3. Lines 223-226. An empty answer raises "Invalid attention backend for ...". The base Platform returns "" (vllm/platforms/interface.py:388-396).
  4. Line 227. The dotted name is imported. The layer keeps the class.

Step 5: CUDA checks an explicit backend alone#

The flag --attention-backend fills attention_config.backend (vllm/engine/arg_utils.py:1103-1105, vllm/engine/arg_utils.py:2716-2726). The validator turns "auto" into None and any other string into an enum member, case-insensitive (vllm/config/attention.py:208-220). An unknown name raises "Unknown attention backend: ... Valid options are: ..." (vllm/v1/attention/backends/registry.py:21-31). The comment at line 451 says "or the selected backend is invalid", but the code above raises in that case and does not fall back.

Step 6: the priority lists#

_get_backend_priorities builds the list. The non-MLA branch:

Blackwell (capability major 10) puts FlashInfer first, unless the model uses non-causal attention. Other GPUs put FlashAttention first. A multimodal prefix model gets a Triton variant in front. The major 10 causal list adds TRITON_FLASHINFER; the other list adds TRITON_FLASH_ATTN only on major 9 (lines 162, 171-175). The MLA branch has three cases: major 10, major 12 and all others (vllm/platforms/cuda.py:96-155). The third deep dive lists every case.

Step 7: each candidate validates itself#

get_valid_backends asks every entry, not only until the first success:

An entry whose module fails to import gets the reason "ImportError: ..." or "OSError: ..." and a DEBUG log. So a missing optional library only removes that backend. Each backend class answers with validate_configuration, which collects reasons:

The rest of the method checks sliding window, R-SWA, non-causal attention, batch invariance and the KV connector. It also checks PCP, DCP and adaptive verification, then calls supports_combination for backend-specific rules (vllm/v1/attention/backend.py:332-369). A backend class changes the answer by overriding the small supports_* methods. For example, FlashAttention accepts capability 8.0 and higher (vllm/v1/attention/backends/flash_attn.py:456-457). ROCM_ATTN returns False from supports_kv_connector (vllm/v1/attention/backends/rocm_attn.py:184-188).

Step 8: pick the winner, or fail with every reason#

All reasons go into one string, so the error message tells why each backend said no. The winner is the valid entry with the smallest index. vLLM logs it once at INFO level: "Using FLASH_ATTN attention backend out of potential backends: ['FLASH_ATTN', 'FLASHINFER', ...]" (vllm/platforms/cuda.py:508-516). If the user set --block-size and that excluded a better backend, vLLM warns (vllm/platforms/cuda.py:487-506).

Step 9: other platforms, and how to add a backend#

Each platform implements the hook in its own way:

  • ROCm has the same shape: an explicit backend first, then a list (vllm/platforms/rocm.py:731-836). Its list depends on AITER and on the KV connector (vllm/platforms/rocm.py:489-526). It tolerates an invalid explicit backend only in TurboQuant and UltraQuant runs. Even there, the one reason must be the KV dtype or the packed layout. Then it uses the list (vllm/platforms/rocm.py:765-795).
  • CPU has no list. It returns CPU_ATTN, or AMX_MLA / CPU_MLA for MLA. It logs an explicit backend that it cannot use and goes on (vllm/platforms/cpu.py:143-192).
  • An out-of-tree platform overrides get_attn_backend_cls and returns any dotted class path. The test platform does exactly this (tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/dummy_platform.py:25-32).

So there are three ways to bring your own backend:

  1. Replace a built-in member. register_backend(AttentionBackendEnum.FLASH_ATTN, "my_pkg.attn.MyFlash"). CUDA reads members through get_class() (vllm/platforms/cuda.py:189-190), so the priority list uses your class in that slot. Your class then validates itself.
  2. Fill CUSTOM. CUSTOM is in no priority list, so the user must select it: --attention-backend CUSTOM.
  3. Own the platform. A platform plugin returns its class from get_attn_backend_cls, as the test platform does. The page The Platform interface explains the hook.

Choices 1 and 2 need the register call in every process that builds the model, so put it in a general plugin.

Deep dive

Worked example: Llama-3-8B and DeepSeek-V3 on H100 and B200

All four cases use vllm serve defaults: --kv-cache-dtype auto, BF16 weights, no --block-size. They assume three things. vllm_flash_attn has FA3 for SM90 (case 3). FlashInfer imports (cases 2 and 4). The FlashMLA extension is built (the fp8 variant of case 3). An ImportError or a missing build only makes that backend invalid, and the next entry wins. (Model sizes come from the model configs, not from this repository.)

  1. Llama-3-8B, H100 (capability 9.0). 32 query heads of size 128, 8 KV heads. The list is FLASH_ATTN, FLASHINFER, TRITON_ATTN, FLEX_ATTENTION, TURBOQUANT. FLASH_ATTN accepts head size 128 (a multiple of 8, at most 256), BF16, KV auto, capability 9.0 (vllm/v1/attention/backends/flash_attn.py:423-427, vllm/v1/attention/backends/flash_attn.py:456-457). It has index 0, so it wins.
  2. Llama-3-8B, B200 (capability 10.0). The list starts with FLASHINFER. It accepts head size 128 and capability 10.0 (vllm/v1/attention/backends/flashinfer.py:662-675), so it wins.
  3. DeepSeek-V3, H100. MLA layers, head size 512 + 64 = 576. The list starts with FLASH_ATTN_MLA. It needs FA3 on SM90 (vllm/v1/attention/backends/fa_utils.py:334-336) and accepts KV auto. It wins. With --kv-cache-dtype fp8 it says "kv_cache_dtype not supported", and FLASHMLA (index 1) wins.
  4. DeepSeek-V3, B200. The list starts with FLASHINFER_MLA. It needs capability major 10 and qk_nope_head_dim in 64, 128 or 192 (vllm/v1/attention/backends/mla/flashinfer_mla.py:240-249). DeepSeek-V3 has 128, so it wins.

The block size follows. After load_model, update_block_size_for_backend picks a block size for the chosen backends, when the user did not set one (vllm/platforms/interface.py:771-781). With one backend, it is that backend's preferred size (vllm/platforms/interface.py:721-722). FLASHMLA supports only 64 (vllm/v1/attention/backends/mla/flashmla.py:57-58), so case 3 with fp8 runs with block size 64 instead of 16. FLASHINFER_MLA supports 32 and 64 (vllm/v1/attention/backends/mla/flashinfer_mla.py:204-205), so case 4 gets 32, the smallest one (vllm/v1/attention/backend.py:155-163). (Derived from these lines.)

Edge cases of register_backend and the cache

  • Re-registration. An enum member gets the new override silently. A string name that exists raises ValueError and suggests the enum form (vllm/v1/attention/backends/registry.py:180-185). So two general plugins that override FLASH_ATTN do not fail; the last one wins.
  • Timing. _cached_get_attn_backend keeps its first answer for the process (vllm/v1/attention/selector.py:206). A registration after the model build has no effect on that model. (Derived.)
  • The front end parses the name. --attention-backend MY_NAME becomes an enum member while the front end parses the config (vllm/config/attention.py:216-219). A string-registered name must therefore exist in the front end too. Whether such a dynamic member survives the pickled VllmConfig in the engine core and the workers is not traced here (open question). The CUSTOM member exists in every process.
  • CUSTOM without registration. get_path() raises "Backend CUSTOM must be registered before use" (vllm/v1/attention/backends/registry.py:211-215).
  • Mamba. register_backend(..., is_mamba=True) writes _MAMBA_ATTN_OVERRIDES (vllm/v1/attention/backends/registry.py:407-417). Mamba layers do not use the priority lists; they ask get_mamba_attn_backend (vllm/v1/attention/selector.py:231-250).

What can go wrong#

An explicit backend does not fall back

With --attention-backend, CUDA validates only that backend. If it does not fit one layer type, start-up stops with "Selected backend ... is not valid for this configuration. Reason: [...]" (vllm/platforms/cuda.py:442-446). For a model with mixed layers, use backend_per_kind instead.

  • No backend fits. The message lists every backend and its reasons: "No valid attention backend found for cuda with AttentionSelectorConfig(...). Reasons: {...}" (vllm/platforms/cuda.py:471-475). Read the reasons: a wrong KV dtype, an unsupported head size or a missing library is the usual cause.
  • A library is missing. An import error makes only that backend invalid, with a DEBUG log (vllm/platforms/cuda.py:405-409). The server starts with a slower backend and says so only in the INFO line "Using X attention backend".
  • A block size excludes the best backend. vLLM warns "--block-size ... precluded higher-priority backend(s)" (vllm/platforms/cuda.py:498-506). Remove --block-size.
  • Your custom backend is never chosen. CUSTOM and new string names are in no priority list. Select them with --attention-backend, or override an existing member.
  • CPU ignores your choice. The CPU platform logs "Cannot use ... backend on CPU." and uses its own backend (vllm/platforms/cpu.py:183-184).

Why it matters. The attention backend sets the speed of every step and also the block size and the KV cache layout. The startup log line "Using X attention backend" is the first thing to check when a deployment is slower than expected.

Check yourself#

  1. 1
    In which process, and when, does vLLM choose the attention backend?
    easy
    Show answer

    In the worker (or in the engine core process with the uni executor), while the model is built. Each attention layer calls get_attn_backend in its constructor (vllm/model_executor/layers/attention/attention.py:349-360).

  2. 2
    You start Llama-3-8B on an H100 with no flags. Which backend runs, and why not FlashInfer?
    easy
    Show answer

    FLASH_ATTN. On capability major 9 the non-MLA list puts FLASH_ATTN before FLASHINFER (vllm/platforms/cuda.py:170-181), and the valid entry with the smallest index wins (vllm/platforms/cuda.py:479-482).

  3. 3
    You run a DeepSeek-V3-style MLA model on H100 with --kv-cache-dtype fp8. Which backend wins, and what block size follows?
    medium
    Show answer

    FLASHMLA. FLASH_ATTN_MLA is first but accepts only auto, float16 and bfloat16 KV (vllm/v1/attention/backends/mla/flashattn_mla.py:42-46). FlashMLA supports only block size 64 (vllm/v1/attention/backends/mla/flashmla.py:57-58), so update_block_size_for_backend sets 64 when you did not set --block-size (vllm/platforms/interface.py:721-722).

  4. 4
    A general plugin calls register_backend(AttentionBackendEnum.CUSTOM, "acme.attn.Fast"). Will vLLM use it on CUDA with no other flag?
    medium
    Show answer

    No. CUSTOM is in no CUDA priority list (vllm/platforms/cuda.py:84-181). Start with --attention-backend CUSTOM, which CUDA then validates alone (vllm/platforms/cuda.py:430-449). Or override a member that is in the list, such as FLASH_ATTN.

  5. 5
    You set --attention-backend FLASH_ATTN for a model whose layers are MLA. What is the error, and why is there no fallback?
    hard
    Show answer

    ValueError: "Selected backend AttentionBackendEnum.FLASH_ATTN is not valid for this configuration. Reason: [...]". The list has "MLA not supported", because FlashAttentionBackend.is_mla() is False while use_mla is True (vllm/v1/attention/backend.py:314-316). For a DeepSeek layer (head size 576) it starts with "head_size not supported", because FlashAttention accepts at most 512 (vllm/v1/attention/backends/flash_attn.py:423-433, vllm/v1/attention/backend.py:302-303). The explicit branch raises and returns before the priority list (vllm/platforms/cuda.py:442-449), although the comment at line 451 suggests a fallback.

Related pages

  • Attention backends: backend, metadata builder and implementationAn attention backend is three classes. The backend class describes what it supports, the metadata builder turns the common batch description of a KV cache group into backend metadata once per step, and the implementation writes the KV cache and runs the kernel for one layer. The builders also report how much CUDA graph capture they allow.
  • The Platform interfaceThe Platform class is the contract between vLLM and a hardware vendor. Identity attributes describe the device; config hooks change VllmConfig in the front end and again in each engine core; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation.
  • CustomOp, out-of-tree ops and IR op providersA CustomOp is a layer with one forward method per platform. It picks one method when it is built - forward_native when disabled, the platform's method when enabled. Plugins replace whole classes with register_oot, and vllm.ir adds a second, per-op provider choice.
  • All the ways to extend vLLMvLLM has about twenty extension points of three kinds - six entry-point groups, a dozen registries that a general plugin fills, and config fields that name your class. This page maps each one to its process and its page.
  • The hybrid KV cache: specs, groups and one manager per layer typeModels that mix full attention with sliding-window, chunked-local or Mamba layers get one KV cache group per layer type. Each group has its own block table and single-type manager, all groups share one block pool, and so every group must use the same page size. Prefix caching finds one hit length that is valid for all groups.
  • KV connectorsA KV connector moves KV cache blocks between vLLM and something outside it. One connector class runs as two objects - a scheduler-side object in the engine core that plans loads and saves, and a worker-side object in each worker that moves the bytes. KVConnectorFactory finds the class by name.
  • "v1/attention/backend.py and selector.py: the backend interfaces and the selector"vllm/v1/attention/backend.py defines the abstract classes of every attention backend (AttentionBackend, AttentionMetadataBuilder, AttentionImpl, MLAAttentionImpl), CommonAttentionMetadata and AttentionCGSupport. vllm/v1/attention/selector.py turns a layer's facts into one backend class through the platform, with a cache.
