Data contracts between the parts of vLLM

IntermediatevLLM conceptsabout 11 min read + 5 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The process and thread architecture of vllm serve Intermediate
  • Tour: Life of a chat request Beginner

In one sentence

Each boundary in vLLM has a fixed message type: msgspec structs over ZMQ, dataclasses between scheduler and worker, pydantic models over HTTP.

The idea#

A request crosses two process boundaries in vllm serve, and more with several GPUs. At each boundary the sender turns a Python object into bytes. The receiver turns the bytes back into an object of a known type. So vLLM defines one type for each hop. We call these types the data contracts. If you know them, you can read any log line, debug any hop, and write a plugin that touches a hop.

There are three families:

  • msgspec structs cross the ZMQ boundary between the API server and the engine core: EngineCoreRequest one way and EngineCoreOutputs the other way. They are encoded as msgpack.
  • dataclasses stay inside the engine core, or go to the workers: SchedulerOutput and ModelRunnerOutput. With one GPU they are passed by a plain call; with worker processes they are pickled into shared memory.
  • pydantic models describe the HTTP JSON: the OpenAI request and response objects.

Two more types never cross a boundary: the engine core's own Request, and the front end's RequestOutput. The page The process and thread architecture of vllm serve shows the processes and channels.

An everyday comparison. Think of the forms in international shipping. The shop fills in an order form, customs needs a fixed declaration form, and the receiver gets a delivery note. Each form has fixed fields in a fixed order, so every office can read it. The comparison stops here: in vLLM, the "declaration" (EngineCoreRequest) is written as a list without field names. So both sides must agree on the field order, not only on the names.

In the code#

Step 1: EngineCoreRequest, the message into the engine core#

  • array_like=True: msgpack writes the fields as an array in this order, without names. So a new field must go at the end, as comments in EngineCoreOutput say (vllm/v1/engine/__init__.py:231-235).
  • omit_defaults=True has no effect on an array_like struct: msgspec still writes every field. The decoder accepts a shorter array and fills the missing last fields with their defaults. gc=False: the garbage collector does not track the object. (This is msgspec behaviour, not vLLM code; we checked it with msgspec 0.21.1 and 0.22.0.)
  • The input processor makes it (vllm/v1/engine/input_processor.py:538-555). The client sets client_index just before it sends (vllm/v1/engine/core_client.py:1333-1335).

The rest of the fields are optional: current_wave and priority, trace_headers, resumable, external_req_id, the reasoning fields, abort_immediately, session_id and kv_hints (vllm/v1/engine/__init__.py:143-165). SamplingParams and LoRARequest inside it are msgspec structs too (vllm/sampling_params.py:271-277, vllm/lora/request.py:8-11).

Step 2: Request, the engine core's own object#

The input thread of the engine core turns the struct into a Request (vllm/v1/engine/core.py:1128, vllm/v1/request.py:243-270). This object never leaves the engine core process. It holds the counters that the scheduler uses:

Three properties read the token lists: num_tokens (prompt plus output), num_tokens_with_spec (plus draft tokens) and num_output_tokens (vllm/v1/request.py:294-304). The status is an integer enum. Every status after PREEMPTED counts as finished:

A finished status maps to a FinishReason. FINISHED_IGNORED (a prompt that is too long) maps to LENGTH, like in the OpenAI API (vllm/v1/request.py:400-412).

Step 3: SchedulerOutput, the plan of one step#

The scheduler makes one SchedulerOutput per step (vllm/v1/core/sched/scheduler.py:1588-1609). The comments give the design: a new request travels in full once, and later steps send only the difference.

NewRequestData carries the prompt, the sampling parameters, the block ids and the computed-token count (vllm/v1/core/sched/output.py:40-56). With Model Runner V2 it also carries prefill_token_ids: all token ids of the request (vllm/v1/core/sched/scheduler.py:1505-1516). CachedRequestData is column-wise: one list per field, indexed like req_ids (vllm/v1/core/sched/output.py:137-152). Its new_token_ids is used only with pipeline parallelism (line 144).

Step 4: ModelRunnerOutput, the result of one step#

The comment at the top says why the fields are lists: the object is sent to the scheduler process, and tensors are expensive to send. sampled_token_ids has one list per request, because spec decoding can accept several tokens in one step. Model Runner V2 does not return it directly. On the last pipeline stage, sample_tokens wraps it in an AsyncOutput, a subclass of AsyncModelRunnerOutput (vllm/v1/worker/gpu/model_runner.py:2209-2218, vllm/v1/worker/gpu/async_utils.py:115). Its get_output() waits for the GPU copy and then gives the ModelRunnerOutput (vllm/v1/outputs.py:353-363). Model Runner V2 fills req_id_to_index only for compatibility; the comment says that it does not use it (vllm/v1/worker/gpu/model_runner.py:2197-2199).

Step 5: EngineCoreOutput and EngineCoreOutputs, the message back#

The output carries token ids, never text. The scheduler adds an EngineCoreOutput only when a request has new tokens, a pooling output, or has stopped (vllm/v1/core/sched/scheduler.py:2293-2295, vllm/v1/core/sched/scheduler.py:2356-2380). The outputs of one step are grouped by API server:

  • outputs holds one entry per request with news. The scheduler builds one EngineCoreOutputs per client_index (vllm/v1/core/sched/scheduler.py:2486-2491).
  • scheduler_stats goes to only one API server per step (vllm/v1/core/sched/scheduler.py:2516-2521).
  • timestamp is time.monotonic() of the engine core process, set when the object is made (lines 295-297).
  • utility_output carries the reply to a utility call. Such a message has no request outputs.

Events and finish reasons are small integer enums, so the message stays short. EngineCoreEvent has a type (QUEUED, SCHEDULED, PREEMPTED) and a monotonic timestamp (vllm/v1/engine/__init__.py:176-200). FinishReason is STOP = 0 to REPETITION = 4, and str() gives the OpenAI string (vllm/v1/engine/__init__.py:37, vllm/v1/engine/__init__.py:49-70).

Step 6: RequestOutput and CompletionOutput, the result in the front end#

The output processor makes a RequestOutput per request and step (vllm/v1/engine/output_processor.py:459-473). It holds the external request id, the prompt, and one CompletionOutput per sequence:

finish_reason is now a string such as "stop" (vllm/v1/engine/output_processor.py:525). The other fields of RequestOutput are the prompt, the prompt token ids, the prompt logprobs, finished, metrics, num_cached_tokens and the KV transfer parameters (vllm/outputs.py:169-209).

Step 7: the OpenAI response objects#

The chat handler turns each RequestOutput into pydantic objects. For a stream, the chunk is a ChatCompletionStreamResponse with one ChatCompletionResponseStreamChoice per sequence; each choice has a DeltaMessage (vllm/entrypoints/openai/chat_completion/protocol.py:162-193, vllm/entrypoints/generate/base/protocol.py:356-360). Without a stream, the handler builds one ChatCompletionResponse with a ChatMessage per choice and a UsageInfo (vllm/entrypoints/openai/chat_completion/protocol.py:137-145, vllm/entrypoints/serve/engine/protocol.py:135-140). The fields stop_reason and token_ids are vLLM additions that are not in the OpenAI spec (vllm/entrypoints/openai/chat_completion/protocol.py:118-122).

Deep dive

How msgspec and msgpack encode the structs

  1. The client encoder is MsgpackEncoder. encode() returns a list of buffers: the msgpack message first, then the large arrays as extra frames (vllm/v1/serial_utils.py:165-175).
  2. A NumPy array or a tensor smaller than VLLM_MSGPACK_ZERO_COPY_THRESHOLD (256 bytes by default) goes inline. A larger one goes as its own frame, with no copy (vllm/v1/serial_utils.py:236-254, vllm/envs.py:1704-1706).
  3. Any other type that msgspec does not know raises TypeError. Only with VLLM_ALLOW_INSECURE_SERIALIZATION=1 does the encoder fall back to pickle or cloudpickle (vllm/v1/serial_utils.py:220-234).
  4. On the engine side, the input thread uses a typed decoder for ADD messages, MsgpackDecoder(EngineCoreRequest), and a generic decoder for the rest (vllm/v1/engine/core.py:1930-1933).
  5. The output thread encodes into reused bytearray buffers, to avoid a new allocation per step (vllm/v1/engine/core.py:2081-2096).

The message frames are: the engine identity (added by the ROUTER), one request-type byte, then the encoded buffers (vllm/v1/engine/core_client.py:1284-1294). The type bytes are ADD = b"\x00", ABORT = b"\x01", START_DP_WAVE = b"\x02" and UTILITY = b"\x03" (vllm/v1/engine/__init__.py:300-312).

Simplified

Multimodal tensors can take another path: with mm_tensor_ipc="torch_shm" they go through a torch shared-memory queue, not through ZMQ (vllm/v1/engine/core_client.py:723-731). The page Multimodal serving: images, audio and video in vLLM explains it.

What can go wrong#

  • A plugin adds an object that msgpack cannot encode. The encoder raises TypeError and names VLLM_ALLOW_INSECURE_SERIALIZATION (vllm/v1/serial_utils.py:220-225). Do not turn the flag on in production: it lets the peer send pickled objects.
  • Field order of an array_like struct. A field in the middle of EngineCoreRequest or EngineCoreOutput shifts all later fields. Front end and engine core must run the same vLLM version. The comments ask developers to append new fields last (vllm/v1/engine/__init__.py:231-235).
  • The wrong request id. The engine core logs the internal id with the random suffix, but the client knows only the external id. Search the logs by the prefix. VLLM_DISABLE_REQUEST_ID_RANDOMIZATION removes the suffix, but then duplicate ids can break the engine (vllm/v1/engine/input_processor.py:364-369).
  • Engine timestamps compared with wall-clock time. Event and output timestamps are monotonic values of the engine core process. The docstring says that they must not be compared with timestamps of other processes (vllm/v1/engine/__init__.py:184-190).

Why it matters. The contracts are the seams of vLLM. A custom scheduler reads Request and writes SchedulerOutput. A KV connector rides in SchedulerOutput and ModelRunnerOutput. A stat logger reads what EngineCoreOutputs carries. Each extension starts with the right type.

Check yourself#

  1. 1
    Which type crosses the ZMQ boundary from the API server to the engine core, and how is it encoded?
    easy
    Show answer

    EngineCoreRequest, a msgspec.Struct with array_like=True, encoded as msgpack (vllm/v1/engine/__init__.py:113-118, vllm/v1/engine/core_client.py:731).

  2. 2
    Does EngineCoreOutput contain the generated text?
    easy
    Show answer

    No. It carries new_token_ids (vllm/v1/engine/__init__.py:209-210). The text appears only in the front end, where the detokenizer of the output processor makes it (vllm/v1/engine/output_processor.py:823-827).

  3. 3
    In step 2 of our example, the request is a decode. Is it in scheduled_new_reqs or in scheduled_cached_reqs, and what does the worker receive for it?
    medium
    Show answer

    In scheduled_cached_reqs. The worker already has the request's data from step 1. So it gets only the difference: new block ids, num_computed_tokens and num_output_tokens (vllm/v1/core/sched/output.py:137-152, comments at vllm/v1/core/sched/output.py:233-240).

  4. 4
    Right after schedule() in step 1, num_computed_tokens is 61, but no token has come back yet. What tells the next schedule() that one token is in flight, and when does that counter go back to 0?
    hard
    Show answer

    num_output_placeholders. The async scheduler adds 1 after a step that samples a token (vllm/v1/core/sched/async_scheduler.py:32-47). update_from_output removes it when the token arrives (vllm/v1/core/sched/async_scheduler.py:71-73). The running pass adds the placeholders to the token count (vllm/v1/core/sched/scheduler.py:759-763).

  5. 5
    A request finishes with an EOS token. Which finish values do the engine core, the front end and the HTTP client see?
    hard
    Show answer

    The engine core sets status FINISHED_STOPPED, which maps to FinishReason.STOP (vllm/v1/request.py:404-405). On the wire this is the integer 0 (vllm/v1/engine/__init__.py:63). The output processor writes str(finish_reason), which is "stop", into CompletionOutput (vllm/v1/engine/output_processor.py:525, vllm/v1/engine/__init__.py:69-70). The client sees "finish_reason": "stop" and stop_reason null.

Related pages

  • The engine client: AsyncLLM in the API serverAsyncLLM implements the EngineClient interface of the API server. It turns requests into EngineCoreRequests, sends them to the engine core, and streams RequestOutputs back through one background task and one collector per request.
  • The engine core loop: threads, queues and the busy loopThe engine core process runs three threads. An input thread decodes requests, the main thread runs the busy loop with the scheduler and the executor, and an output thread sends the results back.
  • The V1 scheduler: one token budget, no phasesIn each engine step, Scheduler.schedule() shares one token budget: first among the running requests, then among the waiting ones. It has no prefill or decode phase, it preempts the last running request when KV blocks run out, and update_from_output() appends the sampled tokens.
  • The model runner (Model Runner V2)Model Runner V2 keeps every running request in a fixed row of GPU tensors, gathers each step's inputs from those rows with GPU kernels, runs the model (CUDA graph or eager), and samples in a second call that returns an AsyncOutput without a GPU wait.
  • The OpenAI-compatible server: launch modes, app, serving classes and streamingHow vllm serve builds its HTTP front end: the launch modes, the FastAPI app with its middleware, routers and exception handlers, the serving objects in app.state, the request flow down to AsyncLLM, streaming, n > 1, request ids, priorities and admission limits.
  • v1/engine/input_processor.py: from engine input to EngineCoreRequestvllm/v1/engine/input_processor.py checks a rendered prompt and its sampling or pooling parameters, fills in defaults such as max_tokens and the EOS stop ids, and builds the EngineCoreRequest that goes to the engine core. It also makes the internal request id.
  • v1/engine/output_processor.py: from token ids to RequestOutputsvllm/v1/engine/output_processor.py turns the EngineCoreOutputs of each step into RequestOutputs. It keeps one RequestState per request, detokenizes incrementally, checks stop strings, collects logprobs, merges n > 1 children and feeds the per-request collectors.
  • v1/engine/core_client.py: the engine core clientsvllm/v1/engine/core_client.py holds the clients that the front end uses to talk to the engine core: an in-process client, and ZMQ clients for blocking, asyncio and data parallel use. It binds the sockets, waits for the engines, reads the outputs and runs utility calls.
