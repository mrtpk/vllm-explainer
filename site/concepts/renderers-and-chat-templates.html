Renderers and chat templates: from messages to token ids

IntermediatevLLM conceptsabout 13 min read + 4 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The OpenAI-compatible API Beginner
  • The OpenAI-compatible server: launch modes, app, serving classes and streaming Intermediate

In one sentence

A renderer turns the messages of a request into token ids. It fills the chat template, tokenizes in a thread pool and checks the length.

The idea#

The model reads one list of token ids. A chat request has a list of messages, maybe images, maybe tools. Something in between must write the messages into one text with the model's special markers and turn that text into ids. The chat template (a Jinja program from the model's files) does the writing; the tokenizer does the cutting (Tokens and tokenizers↗). In vLLM, the object that drives both is the renderer.

The renderer has two layers. OnlineRenderer knows the OpenAI API: it checks tool_choice, refuses untrusted templates, merges the template variables and lets the parsers adjust the request (vllm/renderers/online_renderer.py:225-318). Under it, a BaseRenderer subclass knows the model family: HfRenderer for Hugging Face tokenizers, MistralRenderer for mistral-common, and a few others. Both layers run in the API server process (front end); the engine core gets token ids only.

The renderer also starts the clock. arrival_time is taken at the start of rendering, before the template runs. The TTFT metric of vLLM starts there (Serving metrics: TTFT, TPOT, ITL, throughput, goodput).

An everyday comparison. Think of a clerk who copies a customer's letter onto a fixed form, then types the form into a machine code. The form layout comes from the model's owner, not from the clerk. The comparison stops being true in one place: the "form" is a small program (Jinja) that can branch on variables such as add_generation_prompt or tools. So the same messages can give different prompts.

Read each panel from left to right. Violet boxes run in the renderer's thread pool. The amber box is the length check; it can stop the request with HTTP 400 before the engine sees it.

In the code#

Step 1: which renderer#

AsyncLLM makes one renderer at start-up (vllm/v1/engine/async_llm.py:167). The choice uses the tokenizer mode as the renderer mode:

The default --tokenizer-mode auto is resolved in two places:

  1. ModelConfig sets a family mode for some architectures: for example DeepseekV32ForCausalLM → deepseek_v32, DeepseekV4ForCausalLM → deepseek_v4, KimiK3ForConditionalGeneration → kimi_k3 (vllm/config/model.py:746-766).
  2. If the mode is still auto, a Mistral repository with tekken.json or tokenizer.model.v* files gets mistral. Everything else gets hf (vllm/tokenizers/registry.py:145-164).

So most models use HfRenderer; a few families get their own renderer without a flag, and cohere needs --tokenizer-mode cohere. RendererRegistry.register can add or overwrite a mode, with a warning (vllm/renderers/registry.py:42-54).

Step 2: OnlineRenderer prepares the chat#

OpenAIServingChat calls OnlineRenderer.render_chat after the model and engine checks (vllm/entrypoints/openai/chat_completion/serving.py:278-285). Before any template work, it checks the tools and the template:

  1. Lines 260-281: without a tool parser, tool_choice "auto", "required" or a named function gives an error response. Mistral tokenizers and gpt-oss (Harmony) models skip this check (vllm/renderers/online_renderer.py:253-258). The page Tool and reasoning parsers: from model text to tool_calls and reasoning explains when the parser exists.
  2. Lines 283-288: the tool definitions become plain dicts for the template. With tool_choice: "none" and --exclude-tools-when-tool-choice-none, the template gets no tools.
  3. Lines 292-296: a template in the request (field chat_template, or the key chat_template in chat_template_kwargs) is refused unless the server runs with --trust-request-chat-template (vllm/renderers/online_renderer.py:679-698).

preprocess_chat then merges the variables and calls the model-level renderer (vllm/renderers/online_renderer.py:774-815). After rendering, it builds a parser object and calls its adjust_request, if a tool or reasoning parser is set (vllm/renderers/online_renderer.py:824-859). A tool parser can add a structured-output constraint there (Structured outputs: JSON schemas, grammars and token bitmasks in vLLM).

Step 3: render_chat_async, step by step#

  1. Line 1380: arrival_time = time.time(), before anything else.
  2. Lines 1385-1394: render_messages_async for each conversation (the chat route sends one). It parses the content parts and applies the template; the result is a dict prompt with text or ids.
  3. Line 1396: tokenize_prompts_async. A prompt that already has prompt_token_ids skips the tokenizer, but still gets the length check (vllm/renderers/base.py:756-769).
  4. Lines 1398-1400: the extras cache_salt, mm_processor_kwargs and media_io_kwargs go into the prompt.
  5. Lines 1402-1409: process_for_engine_async runs the multimodal processor if needed and writes arrival_time into the engine input (vllm/renderers/base.py:1255-1276).

Step 4: which template#

HfRenderer resolves the template for every request, in this order:

  1. Given. The request template (only when trusted) or --chat-template (vllm/entrypoints/openai/chat_completion/protocol.py:656). A name such as tool_use selects a named template of the tokenizer (line 275).
  2. Processor. The template of the model's AutoProcessor, but only when the request has no tools (lines 278-290). Multimodal models often keep their template there.
  3. Tokenizer. The template in the tokenizer files (line 294).
  4. Fallback. A template that vLLM ships, chosen by model type, for example template_basic.jinja for CLIP or template_chatml.jinja for older MiniCPM-V (vllm/transformers_utils/chat_templates/registry.py:25-40).

No template at all raises ChatTemplateResolutionError, a client error, so the request gets HTTP 400 (vllm/renderers/hf.py:842-847, vllm/exceptions.py:65-68). --chat-template accepts a file path, a built-in file name, or the template text itself (vllm/renderers/chat_utils/chat_template.py:56-101). A path-like value that does not exist stops the server at start-up (vllm/renderers/chat_utils/chat_template.py:21-53, vllm/entrypoints/common/cli_args.py:510-511).

Step 5: the template variables#

The template sees messages, tools and a set of keyword variables. The request builds them first:

  • add_generation_prompt (default true) and continue_final_message (default false) always go in. A request that sets both to true gets HTTP 400 (vllm/entrypoints/openai/chat_completion/protocol.py:1045-1055).
  • reasoning_effort also sets enable_thinking: false for "none", true for any other value. This does not happen when the request sets enable_thinking itself (lines 652-653).
  • chat_template_kwargs from the request win over --default-chat-template-kwargs. The merge drops request values that are None or "auto" (vllm/renderers/params.py:36-48, vllm/renderers/params.py:104-134).

Before the call, resolve_chat_template_kwargs keeps only the names that the template reads, that apply_chat_template accepts, or that the Hugging Face base class knows (vllm/renderers/hf.py:778-789). So a misspelled kwarg is dropped with no error. Two more fixes happen in safe_apply_chat_template. A developer message becomes a system message when the template does not know that role. An exception inside the template becomes VLLMValidationError, HTTP 400 (vllm/renderers/hf.py:848-861, vllm/renderers/hf.py:871-886).

Content format. Some templates read message.content as a string; others loop over a list of parts in OpenAI form. vLLM parses the template's syntax tree to find out, unless --chat-template-content-format sets it (vllm/renderers/hf.py:537-554, vllm/renderers/hf.py:678-710). With the string format, all text parts of a message are joined with newlines (vllm/renderers/chat_utils/chat_message.py:396-411).

Step 6: the thread pool and the timeout#

Template rendering and tokenization are blocking Python work. The renderer runs them in a thread pool, so the event loop stays free for other requests:

  • The pool has --renderer-num-workers threads, 1 by default (vllm/config/model.py:412-421). With one thread, renders of different requests queue behind each other. Multimodal work has its own one-thread pool.
  • The HF tokenizer gets a pool of renderer_num_workers + 1 deep copies, so that calls from several threads do not share one Rust tokenizer object (vllm/renderers/hf.py:1015-1018, vllm/tokenizers/hf.py:27-47).
  • The template call has a timeout: VLLM_CHAT_TEMPLATE_RENDER_TIMEOUT, 30 s by default, 0 or less for none (vllm/envs.py:817-819). On a timeout, the pool's threads are replaced, because Python cannot stop the stuck thread. The client gets a TimeoutError, which the generic handler turns into HTTP 500 (vllm/entrypoints/serve/exception_handling/error_response.py:93-96).
  • Only HfRenderer has this timeout wrapper. MistralRenderer calls its template through the same pool with no timeout (vllm/renderers/mistral.py:58-60, vllm/renderers/mistral.py:104-108).

At start-up, init_app_state renders one warm-up message to compile the template (vllm/entrypoints/launchers/api_server/app_state.py:104, vllm/renderers/base.py:356-383). A model with no template only logs this at DEBUG level, so the first chat request is where the error shows.

Step 7: tokenization and the length check#

For chat, the tokenizer adds no special tokens of its own, because the template already writes them (vllm/entrypoints/openai/chat_completion/protocol.py:342-351). The request field add_special_tokens can turn them on. The limit is the context length:

A prompt of exactly max_model_len tokens passes this check. Then get_max_tokens computes 0 tokens of room (vllm/entrypoints/serve/utils/api_utils.py:248-253), and the sampling parameters reject max_tokens 0 with HTTP 400 (vllm/sampling_params.py:691-696). With truncate_prompt_tokens, the prompt is cut first, from the side that truncation_side names (left by default for generate models, vllm/tokenizers/registry.py:137-143). Generative requests keep one token free (vllm/renderers/params.py:225-244).

Step 8: multimodal content parts#

An image_url, input_audio or video_url part is fetched and stored in a tracker. The tracker asks the model class for its placeholder text, for example <image> (vllm/renderers/chat_utils/item_tracker.py:294). With the string content format and --interleave-mm-strings off (the default, vllm/config/multimodal.py:420), the placeholders go in front of the message text (vllm/renderers/chat_utils/chat_message.py:188-195). With the OpenAI format, the parts stay a list, and the template places them. The data goes into the prompt as multi_modal_data (vllm/renderers/hf.py:1263-1266). Later, the multimodal processor expands each placeholder into the real number of tokens. The page Multimodal serving: images, audio and video in vLLM covers that part.

Step 9: the derenderer and token-in token-out#

The renderer has a mirror image, OnlineDerenderer (vllm/renderers/online_derenderer.py:69-86). It turns generated token ids back into an OpenAI response: detokenization plus reasoning and tool parsing, with no GPU. It serves /v1/chat/completions/derender and /v1/completions/derender (vllm/entrypoints/scale_out/derender/api_router.py:31-33, vllm/entrypoints/scale_out/derender/api_router.py:81-83). Together with /v1/chat/completions/render and the token-in token-out route /inference/v1/generate, it splits serving into render, generate and derender. A front end on another machine can then do the CPU work.

These scale-out routes are off on a normal vllm serve. Without --enable-scale-out (or --tokens-only), they answer HTTP 403 (vllm/entrypoints/scale_out/factories.py:94-127). The docs describe the request formats: docs/serving/online_serving/renderer.md, derenderer.md and token_in_token_out.md (docs/serving/online_serving/token_in_token_out.md:1-9).

Two other ways skip the template on the normal routes. /v1/completions accepts token ids as the prompt (vllm/entrypoints/openai/completion/protocol.py:53-59). A chat request in disaggregated serving can carry the prefill's ids in kv_transfer_params["prompt_token_ids"]; the renderer then skips templating and tokenization, but not the checks (vllm/renderers/online_renderer.py:106-151, vllm/renderers/online_renderer.py:794-803).

Deep dive

Worked example: three messages, one ChatML template, 31 tokens

The example uses the ChatML template of the repository (start the server with --chat-template examples/template_chatml.jinja) and the Qwen2.5 tokenizer. This is the whole template:

The request has three messages and asks the model to continue the last one (a "prefill" of the answer):

{"messages": [
   {"role": "system",    "content": "You are a helpful assistant."},
   {"role": "user",      "content": "What is the capital of France?"},
   {"role": "assistant", "content": "The capital of France is"}],
 "continue_final_message": true, "add_generation_prompt": false}
  1. build_chat_params sets add_generation_prompt=False and continue_final_message=True. Both pass the kwargs filter, because the template reads add_generation_prompt and the Hugging Face base method knows both names (vllm/renderers/hf.py:778-789).
  2. Line 1 of the template writes each message as <|im_start|>role\ncontent. It adds <|im_end|>\n after every message except the last one, because loop.last and add_generation_prompt is false and not loop.last is false.
  3. Line 2 adds no new assistant turn, because add_generation_prompt is false.

The prompt string is (newlines shown as \n):

<|im_start|>system\nYou are a helpful assistant.<|im_end|>\n<|im_start|>user\nWhat is the capital of France?<|im_end|>\n<|im_start|>assistant\nThe capital of France is

The tokenizer gives 31 ids (measured with the Qwen2.5 tokenizer.json, outside the repo):

[151644, 8948, 198, 2610, 525, 264, 10950, 17847, 13, 151645, 198,
 151644, 872, 198, 3838, 374, 279, 6722, 315, 9625, 30, 151645, 198,
 151644, 77091, 198, 785, 6722, 315, 9625, 374]
 <|im_start|> = 151644   <|im_end|> = 151645   "\n" = 198

Now take the default flags instead (add_generation_prompt: true) and drop the assistant message. The last user turn then ends with <|im_end|>\n, and line 2 adds <|im_start|>assistant\n. That prompt has 26 tokens: the same first 26 ids as above. The model starts a new answer instead of continuing "The capital of France is".

Simplified

The token ids depend on the tokenizer. Another model with a ChatML template (for example a Qwen chat model) gives the same structure; a model with another template gives another string. Hugging Face's apply_chat_template also has its own handling of continue_final_message; it is library code and not described here.

Deep dive

Precedence of template variables, with numbers

Server started with --default-chat-template-kwargs '{"enable_thinking": false, "documents_style": "short"}'. A request sends "chat_template_kwargs": {"enable_thinking": true, "foo": 1} and "reasoning_effort": null.

  1. build_chat_params merges the request kwargs with add_generation_prompt=True, continue_final_message=False, documents=None, reasoning_effort=None. Values that are None are dropped by merge_kwargs (vllm/renderers/params.py:48). Result: {enable_thinking: true, foo: 1, add_generation_prompt: true, continue_final_message: false}.
  2. with_defaults puts the server defaults under it: enable_thinking stays true (request wins); documents_style: "short" is added (vllm/renderers/params.py:117-123).
  3. preprocess_chat adds tools and tokenize=False as defaults under that (vllm/renderers/online_renderer.py:774-792).
  4. resolve_chat_template_kwargs keeps enable_thinking only if the template reads it, and drops foo and documents_style unless the template reads them (vllm/renderers/hf.py:778-789).

The same merged dict also goes to the reasoning parser of the request (vllm/entrypoints/openai/chat_completion/serving.py:310-313). So enable_thinking: false changes both the prompt and how the parser reads the output.

What can go wrong#

  • The model answers in the wrong format or rambles. The template may not be the one the model was trained with, for example a processor template chosen over the tokenizer template. Pass the right one with --chat-template (Step 4).
  • A template variable has no effect. Misspelled or unused names in chat_template_kwargs are dropped with no error (vllm/renderers/hf.py:778-789).
  • "Cannot set both continue_final_message and add_generation_prompt". To continue an assistant message, send "add_generation_prompt": false too (vllm/entrypoints/openai/chat_completion/protocol.py:1050-1054).
  • Slow first token under many concurrent requests. With the default single render thread, long templates or long prompts queue. Raise --renderer-num-workers or add API servers (The OpenAI-compatible server: launch modes, app, serving classes and streaming).
  • HTTP 500 after 30 seconds. The template render timed out; a complex request template is the usual cause (Step 6).
  • A double BOS token. "add_special_tokens": true on a chat request adds the tokenizer's BOS in front of the template's BOS (vllm/entrypoints/openai/chat_completion/protocol.py:342-351).

Why it matters. The prompt that the model sees is made here, and so is the start of the latency clock. Wrong templates give wrong answers with HTTP 200, and slow rendering shows up as TTFT that the engine cannot explain.

Check yourself#

  1. 1
    Which renderer class does a normal Hugging Face model use, and how is it chosen?
    easy
    Show answer

    HfRenderer. The renderer mode is the tokenizer mode (vllm/renderers/registry.py:84-90). For an architecture without a family mode, auto becomes hf, unless the repository is a Mistral repository with Mistral tokenizer files (vllm/config/model.py:746-766, vllm/tokenizers/registry.py:145-164).

  2. 2
    A request has tools, and the model has both a processor template and a tokenizer template. No --chat-template is set. Which template renders it, and why?
    medium
    Show answer

    The tokenizer template. The processor template is tried only when tools is None (vllm/renderers/hf.py:277-290); with tools, resolution goes on to the tokenizer template (vllm/renderers/hf.py:292-294).

  3. 3
    Why does the chat route tokenize with add_special_tokens=False, while /v1/completions uses True?
    medium
    Show answer

    The chat template already writes the special tokens, such as BOS and the turn markers. Adding them again would double them (vllm/entrypoints/openai/chat_completion/protocol.py:342-351). A raw completion prompt has no template, so the completion request's field add_special_tokens defaults to true (vllm/entrypoints/openai/completion/protocol.py:118-124, vllm/entrypoints/openai/completion/protocol.py:299-310).

  4. 4
    With the ChatML template, a request sends two messages (system and user) with the default flags. How many tokens does the prompt of the worked example have, and what is the last token?
    hard
    Show answer

    26 tokens with the Qwen2.5 tokenizer. The last user turn ends with <|im_end|>\n because add_generation_prompt is true, and line 2 of the template adds <|im_start|>assistant\n (examples/template_chatml.jinja:1-2). So the last token is \n (198), after the assistant token 77091 (deep dive "Worked example").

  5. 5
    The server runs with the default --renderer-num-workers. 50 chat requests arrive at the same moment, and each needs 20 ms of pool work (template plus tokenizer). About how long does the last request wait before its own render starts, and is that wait inside vLLM's TTFT metric?
    hard
    Show answer

    About 49 × 20 ms ≈ 1 s. The pool has one thread by default, and the template and the tokenizer of every request run in it (vllm/config/model.py:412, vllm/renderers/base.py:143-158, vllm/renderers/hf.py:1011-1013). The wait is inside the metric, because arrival_time is taken at the start of render_chat_async, before the request waits for the pool (vllm/renderers/base.py:1380). (Derived; real render times depend on the template and the prompt.)

  • Serving metrics: TTFT, TPOT, ITL, throughput, goodputServing metrics tell how fast a server answers one user (TTFT, TPOT, ITL, E2E latency) and how much work it does for all users (throughput, goodput). vLLM measures them in the API server and the engine core, and vllm bench serve measures them at the client.
  • entrypoints/openai/chat_completion/serving.py: OpenAIServingChatvllm/entrypoints/openai/chat_completion/serving.py defines OpenAIServingChat, the serving class of POST /v1/chat/completions. It renders the chat, makes the sampling parameters, starts AsyncLLM.generate and turns the RequestOutputs into SSE chunks or one ChatCompletionResponse.
