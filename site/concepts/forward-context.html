The forward context: how layers find per-step data

AdvancedvLLM conceptsabout 10 min read + 3 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • How a vLLM model file is written (llama.py) Advanced
  • PyTorch for serving: custom ops and torch.compile Intermediate
  • The model runner (Model Runner V2) Advanced

In one sentence

An attention layer gets no KV cache or metadata arguments. It looks them up by its own name in a context that the runner sets.

The idea#

A model file calls self.attn(q, k, v) and nothing else (How a vLLM model file is written (llama.py)). But attention needs more: the KV cache tensor of this layer, where to write the new keys and values, and the shape of the batch. vLLM passes these through two dictionaries keyed by the layer name, the prefix (of a layer) such as model.layers.0.self_attn.attn:

  • The static_forward_context maps each name to its layer object. A layer adds itself when it is built. At start-up, the runner binds each layer's KV cache tensor to the object, as layer.kv_cache.
  • The forward context exists only during one forward pass. The model runner sets it with the attention metadata per layer name, the slot mapping per layer name, the CUDA graph mode and a BatchDescriptor.

The attention custom op gets the tensors q, k, v and output, plus the layer name. Inside, it looks up the layer, the KV cache, the metadata and the slot mapping. Why so indirect? For torch.compile, the op is one opaque node with plain inputs (PyTorch for serving: custom ops and torch.compile). The graph does not depend on Python objects that change every step, so vLLM can compile it once and split it at these ops.

An everyday comparison. Think of a theater with a prop table. Each actor has a spot on the table, labeled with the actor's name. Before each show, the stage manager puts that night's props on each labeled spot. During the show, an actor walks to the table and takes the props under the label. The script never lists the props. The comparison stops here: in vLLM, the label also leads to the actor's own permanent locker, the KV cache, which nobody refills between shows.

The picture#

Follow the name model.layers.0.self_attn.attn through the three panels. It is a key in every dictionary. The violet parts happen once at start-up; the blue parts happen in every step.

In the code#

Step 1: the layer registers itself by name#

  1. Line 440. use_direct_call is false on platforms that want "one giant opaque custom op" for attention. CUDA, ROCm, CPU and XPU return true from opaque_attention_op() (vllm/platforms/cuda.py:595-596, vllm/platforms/rocm.py:1231-1232, vllm/platforms/cpu.py:640-641, vllm/platforms/xpu.py:609-610); the base Platform returns false (vllm/platforms/interface.py:1286-1290).
  2. Lines 443-445. The prefix is the key. A second layer with the same prefix raises ValueError: Duplicate layer name.

The dict is a field of the compilation config. Its docstring says: "Map from layer name to layer objects that need to be accessed outside model code" (vllm/config/compilation.py:757-760). Attention is not the only user. MLA attention (vllm/model_executor/layers/attention/mla_attention.py:620), the MoE runner (vllm/model_executor/layers/fused_moe/runner/moe_runner.py:68), Mamba layers (vllm/model_executor/layers/mamba/mamba_mixer2.py:528) and LoRA linear layers (vllm/lora/layers/base_linear.py:102) also register.

The runner reads this dict to find all attention layers. get_layers_from_vllm_config filters it by type (vllm/config/vllm.py:3596-3617), and the KV cache spec of the model comes from these layers (vllm/v1/worker/gpu/attn_utils.py:138-155).

Step 2: the runner binds the KV cache tensor#

When the KV cache is allocated, init_kv_cache gets compilation_config.static_forward_context as its first argument (vllm/v1/worker/gpu/model_runner.py:794-797). It allocates one backing buffer and makes a view per layer, then binds each view to its layer:

The default bind_kv_cache just stores the view: self.kv_cache = kv_cache (vllm/model_executor/layers/attention_layer_base.py:27-33). Until then, the layer holds an empty placeholder tensor (vllm/model_executor/layers/attention/attention.py:461-464). The binding happens once; the tensor stays the same for the whole life of the server. How the views are laid out is on Attention backends: backend, metadata builder and implementation.

Step 3: the runner sets the forward context each step#

For PIECEWISE and eager steps, Model Runner V2 wraps the model call:

set_forward_context builds a ForwardContext and installs it in a module-level variable for the duration of the with block:

  • no_compile_layers is the static dict itself, not a copy: create_forward_context passes the same object (vllm/forward_context.py:247-248).
  • attn_metadata and slot_mapping are dicts from layer name to value. They are built fresh each step (The model runner (Model Runner V2), Step 6).
  • cudagraph_runtime_mode and batch_descriptor tell the CUDA graph wrappers inside the compiled model what to do (torch.compile and CUDA graphs in vLLM).

The context manager restores the previous context on exit (vllm/forward_context.py:262-274). Any code inside the forward pass reads it with get_forward_context() (vllm/forward_context.py:208-214).

Step 4: the attention layer calls a custom op with its name#

  1. Line 563. The name is wrapped by _encode_layer_name. On PyTorch 2.11 or newer with VLLM_USE_LAYERNAME=1 (the default), it becomes a LayerName object; else it stays a str (vllm/utils/torch_utils.py:990-995, vllm/utils/torch_utils.py:1045-1047).
  2. Lines 564-572. Only when the backend does not write the KV cache inside its own forward, a first op writes k and v into the cache. It returns an empty tensor, the "dummy dependency".
  3. Lines 573-580. The attention op takes the dummy as an argument, so the compiler cannot move it before the cache write (vllm/model_executor/layers/attention/attention.py:779-782). It returns nothing and writes into output.

At this commit, the FlashAttention, FlashInfer and Triton backends set forward_includes_kv_cache_update = False, so they use the separate update op (vllm/v1/attention/backends/flash_attn.py:367, vllm/v1/attention/backends/flashinfer.py:708, vllm/v1/attention/backends/triton_attn.py:347). The base class default is True (vllm/v1/attention/backend.py:69-70).

Step 5: get_attention_context resolves the name#

  1. Line 709. The normal case: attn_metadata is a dict, and the layer's entry is taken.
  2. Line 713. A list of dicts: the comment says index 0 holds the base model's metadata in speculative decoding.
  3. Lines 716-717. The layer object comes from no_compile_layers, and the KV cache from the attribute bound in Step 2.
  4. Line 722. The slot mapping may be None; then unified_kv_cache_update writes nothing (vllm/model_executor/layers/attention/attention.py:736).

Then the two ops call the backend: impl.do_kv_cache_update(...) (vllm/model_executor/layers/attention/attention.py:740-746) and impl.forward(self, query, key, value, kv_cache, attn_metadata, output=...) (vllm/model_executor/layers/attention/attention.py:786-796). The backend classes are on Attention backends: backend, metadata builder and implementation.

Step 6: why a name and not the tensors#

The two ops are registered once, at import, in the vllm library (vllm/model_executor/layers/attention/attention.py:759-764, vllm/model_executor/layers/attention/attention.py:799-803). For the compiler, three facts follow:

  • Opaque. Dynamo records one node per call and does not trace into the backend code. The node has only tensors and a name as inputs.
  • A splitting point. The op names are in the default splitting ops, so vLLM cuts the graph here. Attention then runs eagerly between piecewise CUDA graphs and can use any batch shape (vllm/config/compilation.py:768-770, vllm/config/compilation.py:1184).
  • One graph for 32 layers. A str argument is a constant in the graph. The LayerName class is an opaque type. torch.compile "lifts [it] as a graph input instead of baking it as a constant", which avoids "per-layer recompilation" (vllm/utils/torch_utils.py:1003-1010).

The code also says that the string in unified_kv_cache_update "prevents Inductor from reusing piecewise graphs"; this is why that op is a splitting op too (vllm/config/compilation.py:1186-1213).

Step 7: FULL CUDA graph steps do not read the context#

In FULL mode the runner replays one graph and does not call set_forward_context (vllm/v1/worker/gpu/model_runner.py:2024-2032). No Python code of the model runs, so no layer looks anything up. The comment says the inputs "are already copied to the CUDA graph input buffers" (lines 2026-2027). The context was used at capture time: the capture runs the model inside set_forward_context, with the dummy metadata of that batch shape (vllm/v1/worker/gpu/cudagraph_utils.py:754-771).

Deep dive#

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Deep dive

Worked example: Llama-3-8B, one step

Llama-3-8B has 32 decoder layers. So the static dict has 32 attention entries, from model.layers.0.self_attn.attn to model.layers.31.self_attn.attn (prefix rules on How a vLLM model file is written (llama.py)). All 32 layers use full attention and one backend, so there is one KV cache group and one attention group (derived).

  1. Metadata dict. build_attn_metadata builds one metadata object for the group and stores the same object under all 32 names (vllm/v1/worker/gpu/attn_utils.py:574-580).
  2. Slot mapping dict. build_slot_mappings_by_layer stores the same row tensor of group 0 under all 32 names (vllm/v1/worker/gpu/attn_utils.py:447-455).
  3. Lookups. Each layer does three dict lookups and one attribute read per op call. With two ops per layer, a step does 64 calls of get_attention_context (derived, eager or PIECEWISE mode).

A model with several KV cache groups, for example sliding-window and full layers, gets one metadata object per group. Each layer name points to the object of its group (The hybrid KV cache: specs, groups and one manager per layer type).

Deep dive

set_forward_context, step by step

  1. If batch-size logging is on and attn_metadata is not None, take the start time (vllm/forward_context.py:295-297).
  2. For an MoE model with DP > 1 (or sequence-parallel MoE), make DPMetadata. If the caller gave no token counts across ranks, they are computed with a collective here, and padding across ranks is off (vllm/forward_context.py:308-322).
  3. If num_tokens is given and no descriptor, make BatchDescriptor(num_tokens=num_tokens) (lines 331-332).
  4. Ask the platform for extra fields (lines 334-343).
  5. Build the context and install it with override_forward_context (lines 345-360).
  6. On exit, in the same case, synchronize the device and record the forward time per batch size. Every VLLM_LOG_BATCHSIZE_INTERVAL seconds, log the median time per size (vllm/forward_context.py:362-392).

VLLM_LOG_BATCHSIZE_INTERVAL defaults to -1, which turns the logging off (vllm/envs.py:1445-1447). The module reads it once, at import (vllm/forward_context.py:22-25).

Deep dive

KV sharing and the KV connector hooks

KV sharing. A layer built with kv_sharing_target_layer_name reuses the cache of an earlier layer. The constructor checks the target in the static dict: it must exist, come before this layer and have the same attention type (vllm/model_executor/layers/attention/attention.py:61-91). Such a layer skips the cache write (line 566), and its KV cache entry points to the target's tensor (vllm/v1/worker/gpu/attn_utils.py:427-428).

KV connector. unified_attention_with_output has the decorator @maybe_transfer_kv_layer. With a KV connector, it waits for the layer's KV to load before the attention and saves it after (vllm/model_executor/layers/attention/kv_transfer_utils.py:15-55). It finds the layer data through the same get_attention_context. See KV connectors.

What can go wrong#

  • A model call outside a context. get_forward_context() asserts "Forward context is not set. Please use `set_forward_context` to set the forward context." (vllm/forward_context.py:210-213). This happens when you call the model directly in a test or a script.
  • Two layers with one prefix. ValueError: Duplicate layer name at model build time (vllm/model_executor/layers/attention/attention.py:443-444).
  • A wrong KV sharing target. ValueError "must come before the current layer", "is not a valid Attention layer in the model" or "must be the same type" (vllm/model_executor/layers/attention/attention.py:80-91).
  • Batch-size logging slows the server. With VLLM_LOG_BATCHSIZE_INTERVAL >= 0, every forward pass that runs inside set_forward_context with metadata ends with a device synchronize (vllm/forward_context.py:295, vllm/forward_context.py:363-370). In Model Runner V2 these are the eager and PIECEWISE steps; FULL replays have no context. That removes the CPU/GPU overlap of Async scheduling: overlap the CPU and the GPU. The comment above it still says "we use synchronous scheduling right now" (line 365); with the default async scheduling this is no longer true.
  • A backend without a separate cache write. If a backend says forward_includes_kv_cache_update = False but has no do_kv_cache_update, the update op fails its assertion (vllm/model_executor/layers/attention/attention.py:737-739).

Why it matters. The forward context is the contract between the model runner, the model code and the attention backends. A model file stays free of serving details, the compiler sees a clean graph, and a new backend only needs to read its metadata. When you write a model or a backend plugin, keep the layer name unique, and read per-step data from the context, never from arguments.

Check yourself#

  1. 1
    Which key does the first Llama attention layer use in static_forward_context?
    easy
    Show answer

    Its prefix, model.layers.0.self_attn.attn. The constructor stores static_forward_context[prefix] = self (vllm/model_executor/layers/attention/attention.py:445).

  2. 2
    Where does unified_attention_with_output get the KV cache tensor from?
    medium
    Show answer

    From get_attention_context: it takes the layer object from forward_context.no_compile_layers[layer_name] and reads layer.kv_cache (vllm/model_executor/layers/attention/attention.py:716-717). The runner set that attribute once, in bind_kv_cache_to_layers (vllm/v1/worker/utils.py:879-880).

  3. 3
    Why does unified_kv_cache_update return an empty tensor?
    medium
    Show answer

    As a data dependency. The attention op takes it as kv_cache_dummy_dep, so torch.compile keeps the cache write before the attention (vllm/model_executor/layers/attention/attention.py:731-733, vllm/model_executor/layers/attention/attention.py:779-782).

  4. 4
    In a FULL CUDA graph step, how many times is get_attention_context called in Python, and why?
    hard
    Show answer

    Zero. The runner replays the captured graph without set_forward_context and without Python model code (vllm/v1/worker/gpu/model_runner.py:2024-2032). The lookups ran once, at capture time, inside set_forward_context (vllm/v1/worker/gpu/cudagraph_utils.py:754-771).

  5. 5
    On PyTorch 2.14, how does the layer name reach the attention op, and what would go wrong with a plain string?
    hard
    Show answer

    As a LayerName object, because PyTorch is 2.11 or newer and VLLM_USE_LAYERNAME defaults to 1 (vllm/utils/torch_utils.py:990-995, vllm/envs.py:1451). It is a hoisted opaque type that becomes a graph input. A plain string is baked in as a constant, which the code says causes per-layer recompilation (vllm/utils/torch_utils.py:1003-1010).
