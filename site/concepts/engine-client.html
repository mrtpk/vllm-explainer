The engine client: AsyncLLM in the API server

IntermediatevLLM conceptsabout 12 min read + 4 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The process and thread architecture of vllm serve Intermediate
  • Processes, ZMQ and shared memory Beginner

In one sentence

AsyncLLM is the engine client of the API server. It sends each request to the engine core and streams the outputs back through a per-request collector.

The idea#

The OpenAI-compatible routes do not talk to the engine core process directly. They call one object, the EngineClient, through a fixed set of methods: generate(), abort(), check_health() and some more. In vllm serve this object is AsyncLLM. It lives in the API server process, the front end.

AsyncLLM does three jobs. On the way in, it checks the rendered prompt and makes an EngineCoreRequest. In the middle, its engine core client sends the request over ZMQ and receives EngineCoreOutputs. On the way out, its OutputProcessor detokenizes the token ids and makes a RequestOutput for each request.

Many requests run at the same time, but the engine core sends one message per step for all of them. So AsyncLLM has one background task, the output handler, that reads all outputs. It puts each request's output into a small queue for that request, the RequestOutputCollector. The task that serves the HTTP request waits only on its own collector.

An everyday comparison. Think of a post office with mailboxes. A truck (the engine core) brings one bag of letters after each step. One clerk (the output handler) sorts the bag into the mailboxes. Each customer (a generate() task) waits at its own mailbox. The comparison stops in one place: a mailbox holds only one item. When a new letter arrives before the customer takes the old one, the clerk staples the two letters together.

In the code#

Step 1: the EngineClient interface#

EngineClient is an abstract class in vllm/engine/protocol.py. It declares four attributes and the state properties that the server checks:

The main abstract methods are generate (vllm/engine/protocol.py:93-115), encode for pooling models, abort (vllm/engine/protocol.py:132-141) and check_health (vllm/engine/protocol.py:163-166). Sleep, wake-up, LoRA, cache resets and pause are abstract too (vllm/engine/protocol.py:184-256). collective_rpc and the weight-transfer methods have a default that raises NotImplementedError (vllm/engine/protocol.py:275-283, vllm/engine/protocol.py:303-335). In the vllm/ package, AsyncLLM is the one class that implements it (vllm/v1/engine/async_llm.py:93).

The serving classes use the attributes too. They take the renderer and the input processor from the engine client (vllm/entrypoints/generate/base/serving.py:150-151). Before they start a response, they check errored and call check_admission (vllm/entrypoints/generate/base/serving.py:169-181).

Step 2: construction#

The API server calls AsyncLLM.from_vllm_config (vllm/entrypoints/launchers/api_server/entry.py:93-103). This class method picks the executor class from the config and turns disable_log_stats into log_stats:

The constructor then builds the parts in this order: the renderer, the InputProcessor, the output processor and the engine core client (vllm/v1/engine/async_llm.py:167-201). With one API server, the engine core client also starts the engine core processes. In every case it waits until each engine core is ready (page The process and thread architecture of vllm serve, Step 2). Then the constructor makes the stat loggers when log_stats is on (vllm/v1/engine/async_llm.py:203-214). Stat logger plugins can turn on log_stats even when you disable the default loggers (vllm/v1/engine/async_llm.py:155-165).

At the end, the constructor starts the output handler, but only if an event loop already runs. Otherwise the first add_request starts it (vllm/v1/engine/async_llm.py:218-224, vllm/v1/engine/async_llm.py:523-526).

Step 3: generate() and add_request()#

The chat handler calls self.engine_client.generate(...) with the rendered engine input and the sampling parameters (vllm/entrypoints/openai/chat_completion/serving.py:396-408). generate() is an async generator, so this call only makes the generator object. The code runs when the HTTP stream asks for the first chunk (see Tour 1, stop 4):

add_request does the work before the loop. For a request with n = 1, the important lines are:

  1. Line 521: assign_request_id keeps the caller's id as external_req_id and adds 8 random characters to request_id (vllm/v1/engine/input_processor.py:353-371).
  2. Line 529: one collector per request. Its mode depends on output_kind: DELTA for a stream.
  3. Line 535: _add_request registers the request in the output processor first, and then sends it (vllm/v1/engine/async_llm.py:580-584). So an output can never arrive for a request that the output processor does not know.

Step 4: the output handler and its chunks#

One task serves all requests. It loops for the whole life of the server:

  • Line 880 waits for the next EngineCoreOutputs from the engine core client.
  • Lines 891-893 cut the list into slices of VLLM_V1_OUTPUT_PROC_CHUNK_SIZE outputs, 128 by default (vllm/envs.py:1474-1476).
  • Lines 915-916 give the event loop to other tasks between two slices. The comment at lines 887-889 gives the reason: one large step must not block the event loop for too long.
  • Lines 919-922 abort the requests that the detokenizer stopped with a stop string. The engine core cannot know about stop strings, because it has no text.

Aborts are sent for each slice

process_outputs makes a new reqs_to_abort list for each call (vllm/v1/engine/output_processor.py:756). The abort call is inside the slice loop, so the handler sends the aborts of each slice before it processes the next slice (vllm/v1/engine/async_llm.py:891-922). A stop string in any slice stops the request in the engine core.

After all slices, the handler updates the LoRA state and records the scheduler and iteration stats (vllm/v1/engine/async_llm.py:924-935).

Step 5: the collector hands the output over#

The collector has one slot (self.output) and an asyncio.Event. When the slot is full and a new RequestOutput comes, put() merges it into the old one (line 79). With DELTA, the merge appends the new text and token ids (vllm/outputs.py:220-225). So a slow HTTP writer gets one larger chunk, and no token is lost. An exception in the slot replaces any output, and get() raises it (lines 71 and 91-92).

Step 6: abort when the client goes away#

When the HTTP client disconnects, Starlette cancels the response task. The cancel reaches generate() as CancelledError or GeneratorExit:

abort() first removes the request from the output processor. It returns the internal ids, which include the children of an n > 1 request (vllm/v1/engine/output_processor.py:599-661). Then it sends one ABORT message with these ids to the engine core. Before a streaming response starts, the route decorator with_cancellation watches for the disconnect itself (vllm/entrypoints/serve/utils/api_utils.py:85-109).

Step 7: errors and engine death#

vLLM has two engine exceptions. EngineGenerateError is for one request and "Recoverable". EngineDeadError means that the engine core died, and it is "Unrecoverable" (vllm/v1/engine/exceptions.py:6-22). The death becomes visible in four places:

  1. The engine core sends ENGINE_CORE_DEAD. The client sets engine_dead and raises EngineDeadError (vllm/v1/engine/core_client.py:581-584). The monitor thread sets the same flag when an engine core process exits (vllm/v1/engine/core_client.py:829-838).
  2. The exception reaches the output handler, which puts it into every collector (vllm/v1/engine/async_llm.py:936-944, vllm/v1/engine/output_processor.py:593-597). Each waiting generate() raises it again, without an abort (vllm/v1/engine/async_llm.py:814-818).
  3. errored becomes true when the flag is set or the output handler task has ended (vllm/v1/engine/async_llm.py:1373-1384). New requests then fail at once (vllm/v1/engine/async_llm.py:418-419), and /health returns 503 (vllm/entrypoints/serve/instrumentator/health.py:29-33).
  4. A watchdog task checks every 5 seconds and stops uvicorn, unless VLLM_KEEP_ALIVE_ON_ENGINE_DEATH is set (vllm/entrypoints/launchers/launcher.py:314-337).

Step 8: which engine core client#

AsyncLLM always uses a multiprocess client: make_async_mp_client chooses the class by the data parallel settings:

  • AsyncMPClient (DP = 1): one engine core, one ZMQ identity.
  • DPLBAsyncMPClient (DP > 1, internal load balancing): picks an engine core for each request by load (vllm/v1/engine/core_client.py:1743-1804).
  • DPAsyncMPClient (DP > 1, external load balancer): sends everything to its own engine core (vllm/v1/engine/core_client.py:1611-1612).

The page v1/engine/core_client.py: the engine core clients reads these classes line by line. The page Data parallel serving: several engine cores behind one endpoint explains the load balancing modes.

Step 9: sleep, wake-up and collective RPCs at a glance#

Control methods do not go through generate(). AsyncLLM forwards them as utility calls. For example, sleep() clears the multimodal cache and calls engine_core.sleep_async (vllm/v1/engine/async_llm.py:1196-1202). collective_rpc forwards any worker method name (vllm/v1/engine/async_llm.py:1247-1257). In the engine core, the utility method collective_rpc calls the executor, which runs the method on every worker (vllm/v1/engine/core.py:1098-1105).

The HTTP routes /sleep, /wake_up and /collective_rpc exist only when VLLM_SERVER_DEV_MODE is set (vllm/entrypoints/launchers/api_server/routers.py:46-49, vllm/entrypoints/serve/__init__.py:43-65).

Offline inference: LLMEngine and SyncMPClient

The offline LLM class uses LLMEngine, not AsyncLLM. It has the same input and output processors (vllm/v1/engine/llm_engine.py:101-104). With VLLM_ENABLE_V1_MULTIPROCESSING on (the default), it uses SyncMPClient: a blocking client with a background output thread (vllm/v1/engine/llm_engine.py:186-188, vllm/v1/engine/core_client.py:1015-1021). There is no collector: process_outputs returns the outputs as a list (vllm/v1/engine/output_processor.py:864-866).

Deep dive

add_request(), line by line

  1. Lines 418-419. A dead engine fails the request at once with EngineDeadError.
  2. Lines 421-423. Trace headers without an OTLP endpoint only log a warning, and the headers are dropped.
  3. Lines 427-436. --kv-sharing-fast-prefill with prompt logprobs raises VLLMValidationError, which becomes HTTP 400.
  1. Line 481. A dict with a "type" key is a rendered engine input. This is the normal path of vllm serve: the renderer has already tokenized. So process_inputs runs in the event loop, with no thread hop (line 483).
  2. Lines 497-513. A raw prompt still needs tokenization. process_inputs_async runs the same function in the renderer's thread pool (vllm/v1/engine/input_processor.py:82-84).
  3. Line 487. get_supported_tasks() is a utility call to the engine core, but only the first time. AsyncLLM caches the result (vllm/v1/engine/async_llm.py:390-395).
  4. Line 514. The prompt text is kept for the output, for example for RequestOutput.prompt.
  1. Line 542. With n > 1, a ParentRequest makes n child requests. Child i gets the id f"{i}_{request_id}" and a copy of the parameters with n = 1 (vllm/v1/engine/parallel_sampling.py:84-96). With a seed, child i gets the seed seed + i (vllm/v1/engine/parallel_sampling.py:76-81).
  2. Line 551. Admission control counts the request as n slots.
  3. Lines 553-559. All children are registered with the same collector, then sent one by one. The engine core sees n independent requests.
  4. Lines 562-564. If a send fails, the parent and all its children are aborted.
Deep dive

A worked example: a step with 300 outputs

Assume 300 requests are running, and one engine step produces one token for each. The engine core sends one EngineCoreOutputs with 300 entries in outputs.

  1. EngineCoreOutputQueueTask receives the frames, decodes them and puts the object into outputs_queue (vllm/v1/engine/core_client.py:1211-1254).
  2. The output handler gets it. num_outputs = 300, and with stats on it makes one IterationStats (vllm/v1/engine/async_llm.py:880-885).
  3. With the default chunk size 128, the loop runs for start = 0, 128 and 256. The slices have 128, 128 and 44 outputs.
  4. After the first and the second slice, end (128, then 256) is smaller than 300, so the handler calls asyncio.sleep(0). After the third slice, end = 384 is not smaller than 300, so there is no sleep. (Derived from lines 891-916.)
  5. Between the slices, other tasks can run: for example, 128 generate() tasks wake up and write their SSE chunks before the next slice is detokenized.

A smaller chunk size gives more fairness on the event loop and more task switches. The code gives no measured numbers for this trade-off.

Deep dive

Admission control before the stream starts

check_admission rejects a request with HTTP 503 before any response starts. It applies two optional limits from the scheduler config (vllm/v1/engine/async_llm.py:325-383):

  • max_num_queued_reqs: the number of unfinished requests, waiting plus running. A request with n = 4 needs 4 slots.
  • max_num_queued_tokens: the sum of the prompt lengths of the requests that are still in prefill.

The docstring warns that the token count overestimates the work. The API server does not see chunked prefill progress or prefix-cache hits until the prefill is complete (vllm/v1/engine/async_llm.py:337-341). The count comes from the output processor: prompt_len of every request whose is_prefilling is still true (vllm/v1/engine/output_processor.py:579-588).

What can go wrong#

  • The server exits after an engine error. This is the default for EngineDeadError: the watchdog stops uvicorn (vllm/entrypoints/launchers/launcher.py:325-337). Read the log of the engine core process for the root cause. The message of the exception says "See stack trace (above) for the root cause" (vllm/v1/engine/exceptions.py:19-21).
  • A stop string ends the text, but the engine still runs a step. The engine core does not see stop strings. The output handler sends an ABORT after the detokenizer finds one (vllm/v1/engine/async_llm.py:918-922). The default loop schedules the next step before it processes the output of the current one (vllm/v1/engine/core.py:724-759, vllm/v1/engine/core.py:767-785). So the next step for that request is usually already on the GPU, and more steps can start before the ABORT arrives. (Derived.) The front end ignores these outputs, because the request state is gone (vllm/v1/engine/output_processor.py:759-762).
  • The event loop is busy. All requests share one event loop and one output handler. A very large batch, long stop strings or many logprobs make process_outputs slow, and all streams wait. More API servers (--api-server-count) split this CPU work (The process and thread architecture of vllm serve).
  • The 503 errors come early. With max_num_queued_tokens set, the admission check counts full prompt lengths, so it can reject requests while the GPU still has room (vllm/v1/engine/async_llm.py:337-341).

Why it matters. Every request of vllm serve goes through AsyncLLM twice: once on the way in and once on the way out. Its single event loop and its error handling decide how the server behaves under load and after a crash.

Check yourself#

  1. 1
    Which class implements EngineClient for vllm serve, and which method does the chat route call to start a request?
    easy
    Show answer

    AsyncLLM (vllm/v1/engine/async_llm.py:93). The chat handler calls self.engine_client.generate(...) (vllm/entrypoints/openai/chat_completion/serving.py:396).

  2. 2
    Why does _add_request call output_processor.add_request before engine_core.add_request_async?
    medium
    Show answer

    So the output processor knows the request before its first output can arrive, and before any other task runs. The comment says "Register locally before the first await so concurrent tasks see this request" (vllm/v1/engine/async_llm.py:580-584). The output processor ignores outputs of unknown requests (vllm/v1/engine/output_processor.py:759-762).

  3. 3
    The engine core produces two tokens for a stream before the HTTP writer reads the first one. What does the writer get?
    medium
    Show answer

    One RequestOutput with both tokens. The collector has one slot. With DELTA output, put() merges the second output into the first (vllm/v1/engine/output_processor.py:74-79), and the merge appends the text and the token ids (vllm/outputs.py:220-225).

  4. 4
    A step returns 200 outputs. With the default settings, how many slices does the output handler process, and how often does it call asyncio.sleep(0)?
    hard
    Show answer

    Two slices: 128 and 72 outputs, because VLLM_V1_OUTPUT_PROC_CHUNK_SIZE is 128 (vllm/envs.py:1474-1476). It sleeps once, after the first slice, because end = 128 < 200. After the second slice end = 256, so there is no sleep (vllm/v1/engine/async_llm.py:891-916).

  5. 5
    The engine core process crashes while 10 streams run. Trace what each stream sees and what the server does.
    hard
    Show answer

    The engine core sends ENGINE_CORE_DEAD, and the client raises EngineDeadError (vllm/v1/engine/core_client.py:581-584). The output handler puts it into all 10 collectors (vllm/v1/engine/async_llm.py:936-944). Each generate() raises it without an abort (vllm/v1/engine/async_llm.py:814-818). Each stream generator writes an error chunk, because the 200 status is already sent (vllm/entrypoints/openai/chat_completion/serving.py:941-943). Within 5 seconds the watchdog stops the server, unless VLLM_KEEP_ALIVE_ON_ENGINE_DEATH is set (vllm/entrypoints/launchers/launcher.py:314-337).
