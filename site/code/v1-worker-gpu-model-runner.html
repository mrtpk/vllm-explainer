"v1/worker/gpu/model_runner.py: Model Runner V2"

Purpose#

vllm/v1/worker/gpu/model_runner.py is the GPU half of an engine step: it keeps the request states on the GPU, builds each step's inputs, runs the model and samples the next tokens.

Filevllm/v1/worker/gpu/model_runner.py, 2,483 lines. The header asks contributors to keep the file "minimal" and to put model-specific code elsewhere (vllm/v1/worker/gpu/model_runner.py:3-17).
Main classGPUModelRunner(LoRAModelRunnerMixin) (vllm/v1/worker/gpu/model_runner.py:199).
Runs inEach worker process, or the engine core process with the uni executor. The Python code runs on the CPU and only queues GPU work; one extra CUDA stream copies outputs back.
Called byWorker in v1/worker/gpu_worker.py, which builds it when use_v2_model_runner is true (vllm/v1/worker/gpu_worker.py:567-580).
Callsstates.py, input_batch.py, block_table.py, attn_utils.py, cudagraph_utils.py, async_utils.py, the model states, the sampler, the speculators and the model itself (vllm/v1/worker/gpu/model_runner.py:90-190).
Not in this fileKernels for input preparation (in input_batch.py and block_table.py), CUDA graph capture details (torch.compile and CUDA graphs in vLLM), attention (Attention backends: backend, metadata builder and implementation), the sampler (gpu/sample/).

The page The model runner (Model Runner V2) explains the design. This page is a map of the file and a walk through its main methods.

Where it sits#

Who calls it#

  • Start-up, through the worker. load_model (vllm/v1/worker/gpu_worker.py:591-598), profile_run during memory profiling (vllm/v1/worker/gpu_worker.py:697), initialize_kv_cache (vllm/v1/worker/gpu_worker.py:898), warm-up _dummy_run calls and capture_model (vllm/v1/worker/gpu_worker.py:961-985).
  • Every step. Worker.execute_model and Worker.sample_tokens forward the engine core's calls (vllm/v1/worker/gpu_worker.py:1318-1321, vllm/v1/worker/gpu_worker.py:1350-1353).
  • Subclasses. The CPU runner subclasses this class (vllm/v1/worker/cpu/model_runner.py:10). An out-of-tree runner can pick its own PCP manager through pcp_manager_cls (vllm/v1/worker/gpu/model_runner.py:2433-2437).

What it calls#

  • RequestState for the persistent batch (vllm/v1/worker/gpu/model_runner.py:286-295), InputBuffers and InputBatch for the per-step tensors, BlockTables for block tables and slot mappings.
  • init_attn_backend, init_kv_cache and build_slot_mappings_by_layer from attn_utils.py.
  • ModelCudaGraphManager and dispatch_cg_and_sync_dp for CUDA graphs.
  • set_forward_context around the model call ("forward_context.py: the per-step context of the forward pass").
  • Sampler, RejectionSampler, StructuredOutputsWorker, the speculator, AsyncOutput.

Walk through the main methods#

load_model#

  1. Line 398. get_model_loader picks the loader for --load-format ("Weight loading: from checkpoint files to GPU parameters").
  2. Lines 402-406. The loader builds the model and loads the weights. JIT warm-up providers chosen during the build are recorded.
  3. Lines 407-410. With LoRA, the model's layers are wrapped.

After loading, it builds the model state and decode_query_len (vllm/v1/worker/gpu/model_runner.py:438-445). On the last PP rank of a generative model it builds the Sampler, a RejectionSampler with speculative decoding, the prompt-logprobs worker and the structured-output worker (vllm/v1/worker/gpu/model_runner.py:464-532). A pooling model gets a PoolingRunner instead (lines 534-535). In STOCK_TORCH_COMPILE mode the whole model is compiled here (lines 554-555).

initialize_kv_cache#

init_attn_backend returns the attention groups, the weakest CUDA graph support and the kernel block sizes. Then the method builds BlockTables (lines 716-728), resolves the CUDA graph mode with the backend support, and builds the CUDA graph manager:

Last, it allocates the KV cache and binds each view to its layer through static_forward_context (vllm/v1/worker/gpu/model_runner.py:792-808), and creates the KV connector unless this is a profiling call (vllm/v1/worker/gpu/model_runner.py:813-823).

execute_model#

The state updates (lines 1753-1771) and the input steps are on The model runner (Model Runner V2). The core of the method:

  1. Lines 1806-1821. Pick the CUDA graph descriptor; with DP > 1 the ranks agree on one padded size.
  2. Lines 1823-1826. If every DP rank has zero tokens, return an empty output.
  3. Lines 1835-1838. Build the step tensors, then the block tables and slot mappings.

Then the method builds the attention metadata (lines 1924-1951), the model inputs (lines 1984-2010), and runs the model in FULL, PIECEWISE or eager mode (lines 2024-2070). It stores an ExecuteModelState and returns None, or IntermediateTensors on a non-last PP rank (vllm/v1/worker/gpu/model_runner.py:2090-2110).

sample_tokens#

  1. Lines 2117-2119. No stored state means execute_model failed; return None.
  2. Line 2131. The state is used once and cleared.
  3. Line 2133. A non-last PP rank only receives the sampled tokens from the last rank and updates its counters (lines 2134-2153).

On the last rank: sample() (line 2163), prompt logprobs (lines 2176-2192), the ModelRunnerOutput shell with sampled_token_ids=None (lines 2195-2204), the AsyncOutput that starts the copy (lines 2210-2218), postprocess_sampled (lines 2249-2255), and the speculator (lines 2257-2293). It returns the AsyncOutput (line 2311).

prepare_inputs#

Two of the four GPU steps: positions and sequence lengths, then the input tokens from the last sampled tokens and the drafts. The returned logits_indices select the rows for the sampler. The method ends with an InputBatch of more than 30 fields (vllm/v1/worker/gpu/model_runner.py:1532-1574).

capture_model#

  1. Line 1092. Garbage collection is frozen during capture.
  2. Lines 1097-1098. A multimodal model can capture its encoder too.
  3. Lines 1104-1118. The decoder graphs: PIECEWISE and FULL descriptors (torch.compile and CUDA graphs in vLLM).
  4. Lines 1119-1127. Model-state graphs and the speculator's graphs.

The method returns the graph memory and logs "Graph capturing finished in ... secs, took ... GiB" (vllm/v1/worker/gpu/model_runner.py:1144-1153).

Processes, threads and streams

  • One thread calls the runner: the engine core main thread (uni executor) or the worker main thread (multiproc executor). The runner has no threads of its own.
  • Two CUDA streams. The main stream, cached as main_stream (vllm/v1/worker/gpu/model_runner.py:601-604), and output_copy_stream for the copy to the CPU (line 235). The structured-output worker uses its own stream for the bitmask copy (vllm/v1/worker/gpu/structured_outputs.py:67).
  • The waiter. AsyncOutput.get_output() is called later, outside this file (The model runner (Model Runner V2), Step 9).

Check yourself#

  1. 1
    Which method returns the AsyncOutput, and what does execute_model return on the last PP rank?
    easy
    Show answer

    sample_tokens returns it (vllm/v1/worker/gpu/model_runner.py:2311). execute_model returns None and keeps its results in execute_model_state (vllm/v1/worker/gpu/model_runner.py:2090-2110).

  2. 2
    Where is the CUDA graph mode of the run finally decided, and with which inputs?
    medium
    Show answer

    In initialize_kv_cache, by resolve_cudagraph_mode_and_sizes with the weakest attention support, its backend name, decode_query_len, the KV cache config and piecewise_capture_available (vllm/v1/worker/gpu/model_runner.py:754-763).

  3. 3
    Why does sample_tokens create the AsyncOutput before postprocess_sampled?
    medium
    Show answer

    So the copy event is recorded first and the copy to the CPU does not wait for the post-processing kernels (vllm/v1/worker/gpu/model_runner.py:2244-2248).

  4. 4
    A dummy run for the profile uses skip_attn=True. Why can a FULL capture not do the same?
    hard
    Show answer

    A FULL graph records the attention kernels too, so it needs real attention metadata at capture; the code asserts this (vllm/v1/worker/gpu/model_runner.py:1877-1881). The profile run only measures memory and may skip attention (vllm/v1/worker/gpu/model_runner.py:1022-1027).

Related pages

  • The model runner (Model Runner V2)Model Runner V2 keeps every running request in a fixed row of GPU tensors, gathers each step's inputs from those rows with GPU kernels, runs the model (CUDA graph or eager), and samples in a second call that returns an AsyncOutput without a GPU wait.
  • The forward context: how layers find per-step dataAttention layers register themselves by name when the model is built, get their KV cache tensor bound at start-up, and read the per-step metadata from a global forward context that the model runner sets around each forward pass. The attention custom ops take only the layer name, so torch.compile sees them as opaque.
  • Attention backends: backend, metadata builder and implementationAn attention backend is three classes. The backend class describes what it supports, the metadata builder turns the common batch description of a KV cache group into backend metadata once per step, and the implementation writes the KV cache and runs the kernel for one layer. The builders also report how much CUDA graph capture they allow.
  • torch.compile and CUDA graphs in vLLMvLLM compiles the inner model once with torch.compile and its own Inductor backend, splits the graph at the attention ops, caches the result on disk, and captures CUDA graphs at start-up. Each step, Model Runner V2 replays a FULL graph for uniform decode batches, PIECEWISE graphs for other batches up to the largest capture size, and runs eagerly above it.
  • Async scheduling: overlap the CPU and the GPUWith async scheduling, the engine core schedules and starts step N+1 before it waits for the token of step N. Placeholders in the scheduler and a GPU-side token buffer in Model Runner V2 make this possible.
  • v1/worker/gpu_worker.py: the GPU Workervllm/v1/worker/gpu_worker.py defines Worker, the object that owns one GPU. It sets up the device and NCCL, builds Model Runner V2, profiles memory to size the KV cache, warms up the model, and forwards each step to the model runner.
  • "forward_context.py: the per-step context of the forward pass"vllm/forward_context.py defines ForwardContext, BatchDescriptor and DPMetadata, and the context manager set_forward_context that the model runner wraps around each model call. Code inside the forward pass reads it with get_forward_context().
  • Tour: One engine stepFollow one call of step_with_batch_queue in 12 stops, with two requests in the batch (a 1-token decode and an 8191-token prefill chunk): schedule, launch, sample, pop the previous step, update and send.
