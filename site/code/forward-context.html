"forward_context.py: the per-step context of the forward pass"

AdvancedCode mapabout 4 min read + 2 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The forward context: how layers find per-step data Advanced

Purpose#

vllm/forward_context.py holds one global object during each forward pass, so that layers and CUDA graph wrappers can read per-step data without function arguments.

Filevllm/forward_context.py, 392 lines.
Main classForwardContext (vllm/forward_context.py:140-202); the entry point is set_forward_context (vllm/forward_context.py:277-392).
Runs inEach worker process (or the engine core with the uni executor), in the thread that calls the model. The context is a module-level variable, not a thread-local (vllm/forward_context.py:205).
Called byModel Runner V2 for eager and PIECEWISE steps (vllm/v1/worker/gpu/model_runner.py:2041-2053) and for CUDA graph capture (vllm/v1/worker/gpu/cudagraph_utils.py:762-771); the speculators (vllm/v1/worker/gpu/spec_decode/standalone_ar/speculator.py:140) and the KV connector (vllm/v1/worker/gpu/kv_connector.py:126) too.
Read byThe attention ops through get_attention_context (vllm/model_executor/layers/attention/attention.py:705), CUDAGraphWrapper (vllm/compilation/cuda_graph.py:242-244), MoE layers and others.
Not in this fileThe static dict of layers (in CompilationConfig, vllm/config/compilation.py:757-760); building the attention metadata (Attention backends: backend, metadata builder and implementation).

The page The forward context: how layers find per-step data explains the idea with the attention layer as the example.

Where it sits#

Who calls it#

  • GPUModelRunner.execute_model, around the model call in PIECEWISE and eager mode (FULL mode replays a graph without a context) (vllm/v1/worker/gpu/model_runner.py:2024-2053).
  • ModelCudaGraphManager.capture, around each capture run (vllm/v1/worker/gpu/cudagraph_utils.py:754-771).
  • Any code inside the forward pass that needs step data: get_forward_context().

What it calls#

  • coordinate_batch_across_dp when an MoE model with DP > 1 has no token counts yet (vllm/forward_context.py:311-322).
  • The platform hook set_additional_forward_context (vllm/forward_context.py:334-343).
  • current_platform.synchronize, only when batch-size logging is on (vllm/forward_context.py:368-370).

Walk through the main methods#

ForwardContext#

  1. Line 143. no_compile_layers: the comment says "copy", but create_forward_context passes the same dict object (vllm/forward_context.py:248).
  2. Lines 144-145. attn_metadata and slot_mapping: dicts by layer name, or a list of two dicts for dual-batch overlap.
  3. Lines 157-158. The CUDA graph mode and the descriptor for the wrappers.
  4. Line 165. is_padding: which token rows are padding.
  5. Line 168. skip_compiled: call forward() directly, bypassing the compiled model (vllm/compilation/decorators.py:540-544).

set_forward_context#

  1. Lines 300-307. DP metadata only for MoE models with DP > 1 or sequence-parallel MoE.
  2. Lines 311-322. Without counts from the caller, a collective computes them; the assert says micro-batching must be off.
  3. Lines 331-332. A default descriptor with only num_tokens.
  4. Lines 345-356. Build the context.
  5. Line 359. Install it; the finally block of override_forward_context restores the previous one.

get_forward_context#

An assert, not an exception class: with python -O the check disappears and the function returns None. Code that may run outside a forward pass uses is_forward_context_available() first, like CUDAGraphWrapper (vllm/compilation/cuda_graph.py:236-240).

Deep dive

Data flow: what the runner passes in one PIECEWISE step

ArgumentValue from Model Runner V2
attn_metadatadict of layer name to backend metadata (vllm/v1/worker/gpu/model_runner.py:1940-1951)
num_tokensinput_batch.num_tokens_after_padding, the padded size

is_paddingbool tensor [padded tokens]

Example: a batch of 300 tokens runs as PIECEWISE with 304 padded tokens. The descriptor is BatchDescriptor(num_tokens=304, has_lora=False, num_active_loras=0), which is also the key that each piece wrapper captured at start-up (derived from torch.compile and CUDA graphs in vLLM).

Deep dive

BatchDescriptor fields and the uniform flag

The descriptor has five fields (vllm/forward_context.py:36-56). Model Runner V2 sets only num_tokens, has_lora and num_active_loras; num_reqs stays None and uniform stays False, because PIECEWISE graphs do not depend on them. The FULL graph choice uses a separate class, BatchExecutionDescriptor, in gpu/cudagraph_utils.py (vllm/v1/worker/gpu/cudagraph_utils.py:70-85).

Deep dive

Threads and processes

_forward_context is one module-level variable (vllm/forward_context.py:205). Each worker process has its own copy. Inside a process, the model runs in one thread at a time. Dual-batch overlap uses threads that hand off one compute stream (vllm/v1/worker/gpu/attn_utils.py:301-303); it passes the list form of attn_metadata and slot_mapping, one dict per micro-batch (vllm/forward_context.py:146-150).

Check yourself#

  1. 1
    Which function do layers call to read the current step data?
    easy
    Show answer

    get_forward_context(), which returns the module-level _forward_context (vllm/forward_context.py:208-214).

  2. 2
    Is no_compile_layers a copy of static_forward_context?
    medium
    Show answer

    No. The field comment says "copy", but create_forward_context passes the dict object itself (vllm/forward_context.py:142-143, vllm/forward_context.py:248).

  3. 3
    Why can VLLM_LOG_BATCHSIZE_INTERVAL=0 make a server slower, and when is the setting read?
    hard
    Show answer

    When it is 0 or more, every forward pass inside set_forward_context with attention metadata ends with current_platform.synchronize() (vllm/forward_context.py:295, vllm/forward_context.py:363-370), which removes the CPU/GPU overlap. In Model Runner V2 these are the eager and PIECEWISE steps. The module reads the variable once, at import (vllm/forward_context.py:22-25).

Related pages

  • The forward context: how layers find per-step dataAttention layers register themselves by name when the model is built, get their KV cache tensor bound at start-up, and read the per-step metadata from a global forward context that the model runner sets around each forward pass. The attention custom ops take only the layer name, so torch.compile sees them as opaque.
  • "model_executor/layers/attention/attention.py: the Attention layer and its custom ops"vllm/model_executor/layers/attention/attention.py defines the Attention layer that model files use for standard attention, the two custom ops unified_kv_cache_update and unified_attention_with_output, and get_attention_context, which resolves a layer name to its metadata, layer object, KV cache and slot mapping.
  • "v1/worker/gpu/model_runner.py: Model Runner V2"vllm/v1/worker/gpu/model_runner.py holds GPUModelRunner, the default model runner (MRV2). It loads the model, sets up the KV cache, attention backends and CUDA graphs, and per step turns a SchedulerOutput into GPU inputs, runs the forward pass and samples into an AsyncOutput.
  • torch.compile and CUDA graphs in vLLMvLLM compiles the inner model once with torch.compile and its own Inductor backend, splits the graph at the attention ops, caches the result on disk, and captures CUDA graphs at start-up. Each step, Model Runner V2 replays a FULL graph for uniform decode batches, PIECEWISE graphs for other batches up to the largest capture size, and runs eagerly above it.
  • Data parallel serving: several engine cores behind one endpointWith --data-parallel-size N, vllm serve runs N engine cores with their own KV caches. API servers pick an engine for each request with a load score; a DP coordinator publishes the load counts. Dense models run independent engines; MoE models step in lockstep, in waves, with dummy batches.
