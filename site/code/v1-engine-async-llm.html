v1/engine/async_llm.py: AsyncLLM, the engine client of vllm serve

Purpose#

vllm/v1/engine/async_llm.py defines AsyncLLM: the object that the API server uses as its EngineClient. It accepts requests, sends them to the engine core process, and streams the results back as async generators.

Filevllm/v1/engine/async_llm.py, 1,445 lines of Python. One exception class and one large class.
Main classAsyncLLM(EngineClient) (vllm/v1/engine/async_llm.py:93). The old name AsyncLLMEngine is only an alias (vllm/engine/async_llm_engine.py:4-6).
Runs inThe API server process (the front end), on its asyncio event loop. Raw-prompt preprocessing runs in the renderer's thread pool.
Called byThe API server start-up (from_vllm_config), the serving classes (generate, encode, abort, check_admission), the health route and the dev routes.
CallsThe renderer, InputProcessor, OutputProcessor, the engine core client (AsyncMPClient or a DP variant), StatLoggerManager.
Not in this fileSockets and message framing (core_client.py), detokenization and stop strings (output_processor.py, detokenizer.py), parameter checks (input_processor.py), the HTTP routes (vllm/entrypoints/), the offline LLMEngine (llm_engine.py).

The page The engine client: AsyncLLM in the API server explains the ideas. This page reads the file method by method.

Where it sits#

Who calls it#

  • API server start-up. build_async_engine_client_from_engine_args calls AsyncLLM.from_vllm_config with the client index and count of this API server (vllm/entrypoints/launchers/api_server/entry.py:89-103). The gRPC server does the same (vllm/entrypoints/launchers/grpc_server.py:77-82).
  • Serving classes. The chat handler calls generate() (vllm/entrypoints/openai/chat_completion/serving.py:396-408). Before any response starts, _preflight reads errored and calls check_admission (vllm/entrypoints/generate/base/serving.py:179-181).
  • Health and errors. /health calls check_health() (vllm/entrypoints/serve/instrumentator/health.py:29-33). The watchdog reads errored and is_running (vllm/entrypoints/launchers/launcher.py:325-337).
  • Dev routes (only with VLLM_SERVER_DEV_MODE): /sleep calls sleep(), /wake_up calls wake_up() (vllm/entrypoints/serve/dev/sleep/api_router.py:26-55).

What it calls#

  • renderer_from_config, InputProcessor, OutputProcessor and EngineCoreClient.make_async_mp_client in the constructor (vllm/v1/engine/async_llm.py:167-201).
  • load_stat_logger_plugin_factories and StatLoggerManager (vllm/v1/engine/async_llm.py:155-156, vllm/v1/engine/async_llm.py:204-214).
  • ParentRequest for n > 1 (vllm/v1/engine/async_llm.py:542).
  • The *_async methods of the engine core client for every request and control call, for example add_request_async, abort_requests_async, sleep_async (vllm/v1/engine/async_llm.py:584, vllm/v1/engine/async_llm.py:956, vllm/v1/engine/async_llm.py:1199).

Walk through the main methods#

__init__: build the front-end parts#

  1. Line 167. One renderer per AsyncLLM. It holds the tokenizer, the chat template and the thread pools.
  2. Line 170. The input processor shares this renderer.
  3. Lines 172-177. Shared admission counters exist only when several API servers share an engine and a queue limit is set. The API server manager creates them (vllm/v1/utils.py:207-214).
  4. Lines 180-186. The output processor gets the tokenizer for detokenization and the server-wide stream_interval.
  5. Lines 193-201. make_async_mp_client picks the client class by the data parallel settings. With no client_addresses, it also starts the engine core processes, and it returns only when they are ready.

After this block, the constructor makes the stat loggers if log_stats is true, and tries to start the output handler (vllm/v1/engine/async_llm.py:203-224). asyncio.get_running_loop() raises RuntimeError outside a loop; the code catches it and starts the handler later.

add_request: from prompt to collector#

  1. Line 481. A dict with a "type" key is a rendered engine input. This is the normal path of vllm serve, because the serving classes render the prompt first.
  2. Line 483. process_inputs runs in the event loop. It only checks and copies, so it is fast.
  3. Line 487. The supported tasks come from the engine core once, then from a cache (vllm/v1/engine/async_llm.py:390-395).
  4. Line 500. A raw prompt still needs tokenization, so it goes to the thread pool with process_inputs_async.
  1. Lines 516-519. Reasoning flags from the serving layer go into the struct; the engine core uses them for structured output.
  2. Line 521. The internal request id gets 8 random characters.
  3. Line 526. The output handler starts here if the constructor could not start it. The comment gives the reason: the constructor can then run before the event loop.
  4. Line 529. One collector per request, keyed by the internal id.
  5. Line 532. From here on, the code uses the cloned parameters of the request, which process_inputs may have changed (for example max_tokens).
  6. Line 535. The common case, n == 1, returns after one _add_request.

generate: the async generator#

  1. Line 773. add_request runs on the first iteration, not on the call. The tour shows why this matters: the HTTP 200 goes out first (Tour 1, stop 2).
  2. Line 795. get_nowait() takes a ready output without a task switch. Only an empty slot leads to await q.get().
  3. Lines 800-802. The loop ends after the output with finished = True. The STREAM_FINISHED sentinel ends a streaming-input session and is not yielded.
  4. Lines 807-812. A client disconnect cancels the task. The request is aborted with its internal id, and the exception goes on.
  5. Lines 815-818. When the engine is dead, there is no abort, because no engine can receive it.

_run_output_handler: the one background task#

No reference to self

The handler copies engine_core, output_processor and the other parts into local variables before it makes the task. The comment says why: a task that refers to self keeps AsyncLLM alive, so it is never garbage-collected (vllm/v1/engine/async_llm.py:861-871).

  1. Line 880. Waits for the next EngineCoreOutputs. Errors of the socket task arrive here as exceptions.
  2. Lines 883-885. One IterationStats per engine message, only with stats on and only if there are outputs.
  3. Lines 891-893. Slices of chunk_size outputs (VLLM_V1_OUTPUT_PROC_CHUNK_SIZE, line 874).
  4. Lines 894-902. Multimodal only: hashes that the engine core's cache missed are marked invalid in the front-end cache.
  5. Lines 905-910. process_outputs puts each RequestOutput into its collector, so the returned list must be empty (line 912).
  1. Lines 915-916. asyncio.sleep(0) between slices lets the generate() tasks run.
  2. Lines 918-922. Requests that a stop string finished are aborted in the engine core. This block is inside the slice loop, so the aborts of each slice are sent before the next slice is processed (vllm/v1/engine/async_llm.py:891-922).
  3. Line 924. LoRA request counts come from the scheduler stats.
  4. Lines 929-935. The stat loggers record once per engine message. logger_ref is a one-element list, so elastic EP can swap the logger manager.
  5. Lines 943-944. Any error is logged and put into every collector. Then the task ends, so is_running becomes false (vllm/v1/engine/async_llm.py:1373-1376).

abort#

  1. Lines 952-954. One id or many ids.
  2. Line 955. The output processor removes the requests and returns all internal ids, including children of a parent request. With internal=False (the default), it also accepts external ids.
  3. Line 956. One ABORT message to the engine core.

Deep dive

Processes, tasks and threads

All code of this file runs in the API server process, on one event loop. Three kinds of asyncio task use it:

  • One response task per HTTP request. It iterates generate() and so runs add_request and the collector reads.
  • The output handler task, made at vllm/v1/engine/async_llm.py:946.
  • The socket task of the engine core client, which feeds get_output_async() (vllm/v1/engine/core_client.py:1260-1262).

The only thread hop in this file is process_inputs_async for raw prompts (line 500), and asyncio.to_thread for the front-end profiler (vllm/v1/engine/async_llm.py:1169). The output processor has no lock. It does not need one, because all its callers run on the same event loop. (Derived from the call sites above.)

With several API servers, each one has its own AsyncLLM, output processor and collectors. Each engine core sends a request's outputs only to the API server that sent the request (vllm/v1/engine/core.py:2089-2091).

Deep dive

Worked example: n = 2 fan-out

A client sends a chat request with "n": 2, no seed and stream: true. The external id is chatcmpl-X; assign_request_id makes the internal id chatcmpl-X-k3m9q2zv (8 random characters).

  1. params.n == 2, so the code skips line 535 and makes a ParentRequest (vllm/v1/engine/async_llm.py:534-542).
  2. The loop makes two children. Child 0 is a shallow copy of the request; child 1 (the last) reuses the original object (vllm/v1/engine/async_llm.py:544-549).
  3. The child ids are 0_chatcmpl-X-k3m9q2zv and 1_chatcmpl-X-k3m9q2zv. Without a seed, both children share one cached copy of the parameters with n = 1 (vllm/v1/engine/parallel_sampling.py:69-96).
  4. check_admission(2, ...) counts two slots (vllm/v1/engine/async_llm.py:551).
  5. Both children are registered with the same collector, index 0 and 1, and then sent (vllm/v1/engine/async_llm.py:553-561).
  6. The engine core sees two independent requests with the same prompt.
  7. In the front end, each child output becomes a CompletionOutput with its index. The collector merges outputs with the same index and keeps different indexes apart (vllm/outputs.py:217-255).

Check yourself#

  1. 1
    Where does AsyncLLM start the output handler task?
    easy
    Show answer

    In the constructor when an event loop already runs (vllm/v1/engine/async_llm.py:218-224); otherwise on the first add_request (vllm/v1/engine/async_llm.py:523-526). _run_output_handler returns at once when the task exists (vllm/v1/engine/async_llm.py:858-859).

  2. 2
    Why does the output handler call asyncio.sleep(0), and when does it skip it?
    medium
    Show answer

    To give the event loop to other tasks between slices, so one large step does not block it (vllm/v1/engine/async_llm.py:887-889, vllm/v1/engine/async_llm.py:914-916). It skips the sleep after the last slice, when end is not smaller than the number of outputs.

  3. 3
    A client disconnects during a stream. Which id does generate() pass to abort(), and with which flag?
    medium
    Show answer

    The internal id of the collector, q.request_id, with internal=True (vllm/v1/engine/async_llm.py:807-809). The collector was made with the internal id (vllm/v1/engine/async_llm.py:529).

  4. 4
    A request has n = 3 and seed 7. Which ids and seeds do the children get, and which object is not a copy?
    hard
    Show answer

    The ids are 0_<id>, 1_<id>, 2_<id> (vllm/v1/engine/parallel_sampling.py:94). With a seed, each child gets its own copy of the parameters with seed 7, 8 and 9 (vllm/v1/engine/parallel_sampling.py:69-81). The last child reuses the original EngineCoreRequest object; the first two are shallow copies (vllm/v1/engine/async_llm.py:546).
