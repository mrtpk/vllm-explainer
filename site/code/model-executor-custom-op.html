model_executor/custom_op.py: CustomOp, PluggableLayer and their registries

Purpose#

vllm/model_executor/custom_op.py gives layers a way to pick a forward method per platform, and gives plugins a way to replace a layer class without a change to the model code.

Filevllm/model_executor/custom_op.py, 356 lines of Python. Two module dicts, one helper function, two classes.
Main classesPluggableLayer (vllm/model_executor/custom_op.py:32) and CustomOp (vllm/model_executor/custom_op.py:102), both subclasses of nn.Module.
Runs inEvery process that builds a model: each worker process, or the EngineCore process with the uni executor. The decorators also run at import time in any process that imports a layer module or a plugin.
Called byThe layer modules that subclass the two classes (50 files in vllm/ import from this module, from git grep), model constructors that build these layers, plugins that call register_oot, the LoRA layers (maybe_get_oot_by_class) and CompilationConfig.custom_op_log_check (op_registry).
Callsget_cached_compilation_config() (vllm/model_executor/custom_op.py:9), current_platform (vllm/model_executor/custom_op.py:12), maybe_disable_graph_partition (vllm/model_executor/custom_op.py:11), torch.compile and torch._dynamo.mark_dynamic.
Not in this fileThe default of the custom_ops list (config/vllm.py), its validation (config/compilation.py), the op implementations (the layer files), the second copy for hardware-agnostic layers (hw_agnostic/custom_op.py) and the IR op system (vllm/ir).

The page CustomOp, out-of-tree ops and IR op providers explains the ideas, the default switches and the IR ops, with a worked example. This page reads the file from top to bottom.

Where it sits#

The file has three layers. At the top are the two registries (lines 16-29). PluggableLayer (lines 32-99) has only the class swap. CustomOp (lines 102-356) has the class swap and the per-platform dispatch.

Who calls it#

  • Layer definitions. For example @CustomOp.register("rms_norm") on RMSNorm (vllm/model_executor/layers/layernorm.py:38-39) and @PluggableLayer.register("column_parallel_linear") (vllm/model_executor/layers/linear.py:434-435).
  • Model constructors. They build the layers inside set_current_vllm_config (vllm/model_executor/model_loader/utils.py:100-101). Construction runs __new__ and __init__ of this file.
  • Plugins. @RotaryEmbedding.register_oot in the test platform (tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/dummy_custom_ops.py:10-11).
  • LoRA. maybe_get_oot_by_class(QKVParallelLinear) and similar calls (vllm/lora/layers/column_parallel_linear.py:448).
  • Config check. custom_op_log_check imports op_registry to tell a missing op from an op that is not in the model (vllm/config/compilation.py:1343-1352).

What it calls#

  • get_cached_compilation_config(): the current CompilationConfig, cached until the config context changes (vllm/config/vllm.py:3570-3573).
  • current_platform.is_rocm(), is_cpu(), is_tpu(), is_xpu(), is_out_of_tree() (vllm/model_executor/custom_op.py:194-205), and simple_compile_backend (vllm/model_executor/custom_op.py:230-233).
  • maybe_disable_graph_partition: {"graph_partition": False} for Inductor on torch 2.9 or newer (vllm/model_executor/utils.py:190-194).

Walk through the main methods#

CustomOp.__new__: the class swap#

  1. Lines 108-115. The try block reads cls.__name__. Every Python class has __name__, so the AttributeError branch, with its text about the name attribute, cannot run for a class. (Derived from Python semantics.)
  2. Line 117. The key is the class name of the object that the code builds, for example "RotaryEmbedding". A subclass with another name, such as a scaling variant of rotary embedding, is not swapped (derived).
  3. Lines 120-125. The OOT class is used, with a DEBUG log.
  4. Line 126. The parent __new__ makes an object of the chosen class. Python calls __init__ next only if that object is an instance of the called class, so the OOT class must subclass the in-tree class (general Python rule).

dispatch_forward: the decision#

  1. Line 175. The comment above says that vLLM is built for one backend and has no dynamic dispatch. The config comes from the current config context.
  2. Line 183. enforce_enable from __init__ overrides the list. The comment says it exists for the vision encoder of multimodal models and will be removed (lines 177-182).
  3. Lines 184-187. The counters enabled_custom_ops and disabled_custom_ops record self.__class__.name.
  4. Lines 189-192. Disabled: forward_native, compiled only with compile_native=True.
  5. Lines 194-205. Enabled: the first matching platform test wins; CUDA is the final else. An UnspecifiedPlatform therefore gets forward_cuda (derived).

enabled and default_on#

  1. Line 273. A class with no name attribute was never registered: WARNING once, and the base mode decides.
  2. Lines 282-289. Both +name and -name: ValueError. CompilationConfig already rejects this earlier (vllm/config/compilation.py:1027-1034).
  3. Line 290. (default_on() or enabled) and not disabled.
  4. Lines 300-305. Exactly one base mode, else ValueError.
  5. Line 307. not count_none > 0 or count_all > 0: true for "all", false for "none".

register_oot: the two working forms#

  1. Line 337. The key is name, or the name of the class on which the decorator is called. On CustomOp.register_oot() without name, the key would be "CustomOp" (derived).
  2. Line 338. A duplicate key fails the assert.
  3. Line 339. The OOT class's name becomes the key. The +name switch for it is then +RotaryEmbedding, not the in-tree op name (derived; see CustomOp, out-of-tree ops and IR op providers).
  4. Lines 343-356. None → return the decorator; a class → decorate it now; anything else (a string) → TypeError.

PluggableLayer.register_oot (lines 82-99) has the same structure, with the text "Duplicate layer name".

Both dicts are module globals, so each process has its own. A plugin must register in every process that builds a model: a general plugin does this (How vLLM finds and loads plugins). Because name is a class attribute, a subclass without its own register call uses the parent's name. RotaryEmbedding is such a subclass: the decorator is on RotaryEmbeddingBase (vllm/model_executor/layers/rotary_embedding/base.py:14-15, vllm/model_executor/layers/rotary_embedding/base.py:139).

Deep dive

maybe_compile, line by line

  1. Lines 218-228. Return fn unchanged when compilation is off for this call, for the whole config (mode NONE), or with the "eager" backend.
  2. Lines 230-233. The backend is the platform's simple_compile_backend ("inductor" by default, vllm/platforms/interface.py:172), with graph partition off.
  3. Lines 235-258. With dynamic_arg_dims: dynamic=False, and each call marks the listed dimensions as dynamic. A negative index counts from the end (line 254). An argument that is not a tensor is skipped (line 251).
  4. Lines 261-266. Else dynamic=True.

Example: mla_decode_concat_quant_fp8 registers dynamic_arg_dims={"decode_ql_nope": 0, "decode_q_pe": 0} (vllm/model_executor/layers/attention/mla_attention.py:1561-1564): dimension 0 (tokens) of both tensors is dynamic.

Deep dive

Processes and timing

  • Import time. register runs when Python imports a layer module. register_oot runs when the plugin module is imported.
  • Model build. __new__, __init__ and dispatch_forward run once per layer object, inside set_current_vllm_config. A CustomOp built when no config is set raises AssertionError (vllm/config/vllm.py:3576-3586).
  • Forward. forward only calls _forward_method. No config lookup happens per step.
  • Threads. The registries have no lock. Registration happens at import and plugin time, before the model build. (Derived; the file has no comment about threads.)

  1. 1
    Which dict does __new__ read, and with which key?

    Show answer

    op_registry_oot, with cls.__name__ (vllm/model_executor/custom_op.py:109, vllm/model_executor/custom_op.py:117-120).

  2. 2
    An enabled op runs on ROCm. The subclass defines only forward_native and forward_cuda. Which method runs?
    medium
    Show answer

    dispatch_forward returns forward_hip (vllm/model_executor/custom_op.py:194-195). Its default body calls forward_cuda (vllm/model_executor/custom_op.py:147-149).

  3. 3
    What is the difference between PluggableLayer and CustomOp?
    medium
    Show answer

    Both swap the class in __new__ through op_registry_oot. Only CustomOp has the forward_* methods and dispatch_forward (vllm/model_executor/custom_op.py:33-44).

  4. 4
    An op registered with dynamic_arg_dims={"x": -1} is disabled and built with compile_native=True under VLLM_COMPILE. What does a call with a 2-D tensor x do?
    hard
    Show answer

    maybe_compile compiled forward_native with dynamic=False. The wrapper binds the arguments, turns -1 into x.ndim - 1 = 1, calls mark_dynamic(x, 1), then calls the compiled function (vllm/model_executor/custom_op.py:235-258).

Related pages

  • CustomOp, out-of-tree ops and IR op providersA CustomOp is a layer with one forward method per platform. It picks one method when it is built - forward_native when disabled, the platform's method when enabled. Plugins replace whole classes with register_oot, and vllm.ir adds a second, per-op provider choice.
  • The Platform interfaceThe Platform class is the contract between vLLM and a hardware vendor. Identity attributes describe the device; config hooks change VllmConfig in the front end and again in each engine core; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation.
  • All the ways to extend vLLMvLLM has about twenty extension points of three kinds - six entry-point groups, a dozen registries that a general plugin fills, and config fields that name your class. This page maps each one to its process and its page.
  • platforms/interface.py: the Platform base classvllm/platforms/interface.py defines Platform, the base class of every hardware platform, with 12 class attributes and 90 methods, plus PlatformEnum, CpuArchEnum, DeviceCapability, the device-id helpers and UnspecifiedPlatform.
  • "model_executor/layers/linear.py: tensor-parallel linear layers"vllm/model_executor/layers/linear.py holds LinearBase and the replicated, column-parallel, merged-column, QKV and row-parallel linear layers. Each one resolves a quantize method, allocates its per-rank weight through it, cuts checkpoint tensors in weight_loader or weight_loader_v2, and calls the TP all-gather or all-reduce in forward.
  • torch.compile and CUDA graphs in vLLMvLLM compiles the inner model once with torch.compile and its own Inductor backend, splits the graph at the attention ops, caches the result on disk, and captures CUDA graphs at start-up. Each step, Model Runner V2 replays a FULL graph for uniform decode batches, PIECEWISE graphs for other batches up to the largest capture size, and runs eagerly above it.
