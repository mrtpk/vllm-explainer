"v1/attention/backend.py and selector.py: the backend interfaces and the selector"

AdvancedCode mapabout 6 min read + 2 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

  • Attention backends: backend, metadata builder and implementation Advanced

Purpose#

These two files define what an attention backend must provide (backend.py) and how a layer gets one (selector.py).

Filesvllm/v1/attention/backend.py, 1,150 lines; vllm/v1/attention/selector.py, 250 lines.
Main classesAttentionBackend (vllm/v1/attention/backend.py:59-379), CommonAttentionMetadata (vllm/v1/attention/backend.py:389-554), AttentionMetadataBuilder (vllm/v1/attention/backend.py:592-761), AttentionImpl (vllm/v1/attention/backend.py:890-1031), MLAAttentionImpl (vllm/v1/attention/backend.py:1034-1128); get_attn_backend (vllm/v1/attention/selector.py:109-203).
Runs inEach worker: the selector while the model is built; the builders at KV cache init and in every step; the impls in every step.
Called byAttention and MLAAttention constructors (selector), attn_utils.py of Model Runner V2 (builders), the unified attention ops (impls).
Implemented byThe backend modules in vllm/v1/attention/backends/, for example flash_attn.py, and out-of-tree backends.
Not in this fileThe backend enum and its registry (backends/registry.py), the platform priority lists (How vLLM chooses an attention backend), the KV cache layout resolver (backends/utils.py), kernels.

Where it sits#

Who calls it#

  • Selector. Attention.__init__ calls get_attn_backend (vllm/model_executor/layers/attention/attention.py:349-360). The MLA layer does the same with use_mla=True.
  • Builders. AttentionGroup.create_metadata_builders instantiates them (vllm/v1/worker/utils.py:330-339); build_attn_metadata calls build (vllm/v1/worker/gpu/attn_utils.py:574-576).
  • Impls. The unified ops call impl.forward and impl.do_kv_cache_update ("model_executor/layers/attention/attention.py: the Attention layer and its custom ops").
  • Platforms. CUDA calls validate_configuration on each candidate (vllm/platforms/cuda.py:389-417).

What it calls#

  • current_platform.get_attn_backend_cls and resolve_obj_by_qualname (selector, vllm/v1/attention/selector.py:218-228).
  • get_kv_quant_mode for the impl's KV quantization mode (vllm/v1/attention/backend.py:895-898).
  • ops.concat_and_cache_mla in the MLA cache write (vllm/v1/attention/backend.py:1118-1128).

Walk through the main methods#

AttentionBackend.validate_configuration#

Each failed check adds a human-readable reason; an empty list means "valid". The rest of the method checks sliding window, R-SWA, non-causal attention, batch invariance, the KV connector, PCP, DCP and adaptive verification, then the backend's own supports_combination (vllm/v1/attention/backend.py:332-369). The page How vLLM chooses an attention backend shows how CUDA uses the reasons.

AttentionMetadataBuilder.__init__ and build#

  1. Line 595. CUDA graph support defaults to NEVER; read it through get_cudagraph_support() (line 594).
  2. Line 599. reorder_batch_threshold: the query length up to which the builder treats a request as a decode.
  3. Lines 602, 604, 610. Feature flags: block-table update, block-table width, capture-safe draft updates.
  4. Lines 613-624. The constructor gets the KV cache spec, the layer names of the group, the config and the device.

build(common_prefix_len, common_attn_metadata, fast_build=False) is abstract (vllm/v1/attention/backend.py:686-704). build_for_cudagraph_capture and build_for_drafting call it by default (lines 720-751).

AttentionImpl.forward#

The constructor takes the same ten arguments that Attention.__init__ passes. forward gets the layer (for its scales), the tensors, the KV cache view, the metadata and the output buffer. The fused hooks (do_rope_and_kv_cache_update and others, lines 973-1031) are used only by Inductor fusion passes when the impl says it supports them.

get_attn_backend (selector.py)#

  1. Lines 158-180. The selector config mixes the layer's facts with run-wide facts: KV connector, PCP, DCP, batch invariance, adaptive verification and R-SWA.
  2. Lines 184-192. A per-kind override wins over the global backend.
  3. Lines 196-203. The cached call. The run-wide KV cache dtype is part of the cache key.

The block size goes into the config only when the user set --block-size (vllm/v1/attention/selector.py:134-138). _cached_get_attn_backend is decorated with @cache, so each set of facts asks the platform once per process (vllm/v1/attention/selector.py:206-228).

Deep dive

CommonAttentionMetadata helpers

  • naive_query_lens(): query_start_loc[1:] - query_start_loc[:-1], "naive" because it assumes that one query ends where the next starts (vllm/v1/attention/backend.py:482-484).
  • compute_num_computed_tokens(): seq_lens - query_lens on the device, cached (vllm/v1/attention/backend.py:489-494).
  • token_to_req_indices(buffer): the request index of each token, built from the device query_start_loc, cached (vllm/v1/attention/backend.py:496-518).
  • unpadded(num_actual_tokens, num_actual_reqs): slice every field back to the real sizes, marked "remove once we have FULL-CG spec-decode support" (vllm/v1/attention/backend.py:520-554).
Deep dive

AttentionImplBase.__new__ and context parallelism

Every impl gets its DCP and PCP rank and world size in __new__, so subclasses need not call a base constructor (vllm/v1/attention/backend.py:853-878). need_to_return_lse_for_decode is true only with DCP > 1 and an impl that can return the softmax LSE. The comment on lse_base_on_e warns that a wrong base "silently corrupts the cross-shard softmax denominator" (vllm/v1/attention/backend.py:808-818).

Deep dive

Writing a backend: the minimum

  1. A subclass of AttentionBackend with get_name, get_impl_cls and get_builder_cls (vllm/v1/attention/backend.py:81-94), plus the supports_* answers that differ from the defaults.
  2. A metadata dataclass and a builder with __init__ and build; set _cudagraph_support if graphs are safe.
  3. An impl with __init__ and forward; if forward_includes_kv_cache_update = False, also do_kv_cache_update.
  4. Registration through register_backend and selection by the platform or --attention-backend (How vLLM chooses an attention backend).

Related pages

  • Attention backends: backend, metadata builder and implementationAn attention backend is three classes. The backend class describes what it supports, the metadata builder turns the common batch description of a KV cache group into backend metadata once per step, and the implementation writes the KV cache and runs the kernel for one layer. The builders also report how much CUDA graph capture they allow.
  • How vLLM chooses an attention backendEach attention layer asks the selector for a backend class when the worker builds the model. The selector asks current_platform. CUDA validates a priority list for the GPU generation and takes the first valid backend; an explicit --attention-backend is validated alone.
  • "model_executor/layers/attention/attention.py: the Attention layer and its custom ops"vllm/model_executor/layers/attention/attention.py defines the Attention layer that model files use for standard attention, the two custom ops unified_kv_cache_update and unified_attention_with_output, and get_attention_context, which resolves a layer name to its metadata, layer object, KV cache and slot mapping.
  • torch.compile and CUDA graphs in vLLMvLLM compiles the inner model once with torch.compile and its own Inductor backend, splits the graph at the attention ops, caches the result on disk, and captures CUDA graphs at start-up. Each step, Model Runner V2 replays a FULL graph for uniform decode batches, PIECEWISE graphs for other batches up to the largest capture size, and runs eagerly above it.
  • The Platform interfaceThe Platform class is the contract between vLLM and a hardware vendor. Identity attributes describe the device; config hooks change VllmConfig in the front end and again in each engine core; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation.
  • The hybrid KV cache: specs, groups and one manager per layer typeModels that mix full attention with sliding-window, chunked-local or Mamba layers get one KV cache group per layer type. Each group has its own block table and single-type manager, all groups share one block pool, and so every group must use the same page size. Prefix caching finds one hit length that is valid for all groups.
