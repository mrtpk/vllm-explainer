v1/worker/gpu_worker.py: the GPU Worker

AdvancedCode mapabout 10 min read + 3 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Executors and workers: from the engine core to the GPUs Intermediate

Purpose#

vllm/v1/worker/gpu_worker.py defines Worker, the CUDA worker. One Worker object owns one GPU. The executor calls its methods by name, and most of them forward to the model runner.

Filevllm/v1/worker/gpu_worker.py, 1,720 lines of Python.
Main classWorker(WorkerBase) (vllm/v1/worker/gpu_worker.py:196). The CUDA platform sets worker_cls to it when worker_cls is "auto" (vllm/platforms/cuda.py:330-331).
Runs inA worker process (VllmWorker-<rank>), or the engine core process with the uni executor. Always in the main thread of that process.
Called byWorkerWrapperBase, which the executor drives: directly (vllm/v1/executor/uniproc_executor.py:68-74) or through worker_busy_loop (vllm/v1/executor/multiproc_executor.py:1041-1047), which looks up the method by name (vllm/v1/executor/multiproc_executor.py:1057-1059).
CallsModel Runner V2 (vllm/v1/worker/gpu/model_runner.py), init_distributed_environment, the memory profiler (vllm/utils/mem_utils.py), the sleep-mode backend, KV and EC connectors.
Not in this fileInputs, attention metadata, the forward pass and sampling (the model runner); the KV cache planning (v1/core/kv_cache_planning.py); the process loop (multiproc_executor.py).

This page reads the methods that vllm serve uses. The page Executors and workers: from the engine core to the GPUs explains where the worker sits.

Where it sits#

Who calls it#

  • Construction. WorkerWrapperBase.init_worker resolves parallel_config.worker_cls and makes the object (vllm/v1/worker/worker_base.py:292-347).
  • Start-up. The executor calls init_device and load_model. Then EngineCore._initialize_kv_caches calls get_kv_cache_spec, determine_available_memory, initialize_from_config and compile_or_warm_up_model through collective_rpc (vllm/v1/engine/core.py:253-379).
  • Every step. execute_model, then sample_tokens (vllm/v1/executor/abstract.py:261-287). With MoE data parallelism, idle ranks call execute_dummy_batch (vllm/v1/engine/core.py:2493-2495).
  • Control. sleep, wake_up, LoRA and profiling calls come as utility calls from the front end.

What it calls#

  • init_worker_distributed_environment: process groups and NCCL (vllm/v1/worker/gpu_worker.py:1678-1716).
  • _make_model_runner: Model Runner V2 by default (vllm/v1/worker/gpu_worker.py:567-583).
  • memory_profiling and model_runner.profile_run (vllm/v1/worker/gpu_worker.py:682-697).
  • model_runner.execute_model, model_runner.sample_tokens (vllm/v1/worker/gpu_worker.py:1318-1353).

Walk through the main methods#

init_device: the GPU, NCCL and the memory baseline#

  1. Lines 492-493. The worker binds its thread to its GPU.
  2. Lines 501-507. NCCL and the process groups start before the snapshot, as the comment says, so their buffers count as baseline.
  3. Lines 523-526. A tiny mm and linear make the cuBLAS handles now. The comment (lines 516-522) explains the reason: cuBLAS memory is invisible to torch's cache, so it must exist before the snapshot.
  4. Lines 538-541. The snapshot records free and total memory. request_memory computes the budget and fails at once if the GPU has less free memory than that (vllm/v1/worker/utils.py:724-726, vllm/v1/worker/utils.py:761-772).
  5. Line 549. The model runner is built here, before the weights load.

_make_model_runner: Model Runner V2#

use_v2_model_runner is the default when Triton is present and no unsupported feature is set (vllm/config/vllm.py:713-748). Lines 581-583 are the Model Runner V1 fallback; the page The model runner (Model Runner V2) names its cases.

determine_available_memory: size the KV cache#

  1. Lines 683-686. memory_profiling clears the cache, resets the peak counter and measures before and after the block.
  2. Line 697. The profile run: one forward pass with max_num_batched_tokens dummy tokens, then a dummy sampler run (vllm/v1/worker/gpu/model_runner.py:1010-1040). Attention is skipped in this pass (skip_attn=True, line 1024 there).
  3. Lines 704-708. When CUDA graphs will be captured, the runner estimates their memory.
  4. Lines 711-715. The estimate counts only with VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=1, the default (vllm/envs.py:2217-2219).

The two numbers in line 746 come from the profiler:

So the formula is:

requested_memory  = ceil(total_memory × gpu_memory_utilization)
total_consumed    = free(snapshot in init_device) − free(after profile run)
peak_headroom     = torch_peak − torch_allocated            (after profile run)
available_kv      = requested_memory − (total_consumed + peak_headroom) − cudagraph_estimate

Simplified

This formula is for the normal case. When some weights are held outside the process, the budget becomes requested_memory minus those weights, with its own ValueError (vllm/v1/worker/utils.py:728-759).

The default gpu_memory_utilization is 0.92 (vllm/config/cache.py:212). The result goes back to the engine core, which divides it by the bytes per block (vllm/v1/core/kv_cache_planning.py:678-681). See the worked example in the deep dive.

--kv-cache-memory-bytes skips the budget

With kv_cache_memory_bytes set, the worker still runs the profile run, but it returns that value. Only a multimodal reservation can take some bytes off it (vllm/v1/worker/gpu_worker.py:674-678). The log says that this "does not respect the gpu_memory_utilization config" (vllm/v1/worker/gpu_worker.py:653-678).

initialize_from_config: allocate the KV cache#

  1. Line 861. The worker learns the final number of blocks.
  2. Line 878. A KV connector starts here, because it needs the KV cache config.
  3. Lines 883-889. The KV cache goes into the "kv_cache" memory pool, so sleep mode can free it on its own.
  4. Lines 898-901. The model runner allocates and binds the tensors. The page The KV cache manager: blocks, the block pool and memory sizing explains the layout.

compile_or_warm_up_model: the last start-up step#

  1. Lines 961-968. One dummy run per extra compile size, largest first.
  2. Line 973. Kernel warm-up and tuning before capture.
  3. Lines 983-985. CUDA graph capture, unless --enforce-eager. See torch.compile and CUDA graphs in vLLM.

After capture, when --kv-cache-memory-bytes is not set, the worker logs a suggested KV cache size that includes the real CUDA graph memory and a 150 MiB buffer (vllm/v1/worker/gpu_worker.py:1003-1057). The log line writes the flag as --kv-cache-memory=; the flag that the parser defines is --kv-cache-memory-bytes (vllm/engine/arg_utils.py:1385). Then it resets the random seed, freezes the GC heap and turns on the GPU sync check (vllm/v1/worker/gpu_worker.py:1085-1110).

execute_model and sample_tokens: every step#

  1. Lines 1317 and 1324. with_gpu_sync_check can report any GPU-to-CPU wait in these calls (only with VLLM_GPU_SYNC_CHECK; see Async scheduling: overlap the CPU and the GPU).
  2. Line 1321. sample_tokens is a plain forward to the model runner. On the last PP rank it returns an AsyncOutput.
  3. Lines 1330-1348. PP only: wait for the previous send, and start receiving the activations of the stage before.
  4. Lines 1351-1353. The model runner does the step. With Model Runner V2 on the last rank, it returns None (vllm/v1/worker/gpu/model_runner.py:2103-2110).
  5. Lines 1360-1363. None or an output goes straight back. Only a non-last PP rank continues: it sends its IntermediateTensors to the next stage without a wait (lines 1375-1379).

sleep and wake_up in brief#

Sleep mode frees GPU memory while the engine is not in use. It needs enable_sleep_mode. On CUDA this turns on the CuMem allocator; on a platform without sleep mode it raises ValueError (vllm/config/model.py:666-673). The engine core docstring gives the levels: level 0 only pauses scheduling; level 1 offloads the weights to the CPU and discards the KV cache; level 2 discards all GPU memory (vllm/v1/engine/core.py:984-992, vllm/v1/engine/core.py:997-998).

For level 2, the worker first copies the model buffers (and the parameters named in sleep_preserve_parameter_names, and the buffers of a draft model) to the CPU (lines 303-313). wake_up restores them (vllm/v1/worker/gpu_worker.py:345-362). The backend decides what to offload: runtime state and graph pools at every level, and the weights only at level 1. Everything else, for example the KV cache, is discarded (vllm/device_allocator/sleep_mode_backend.py:127-137, vllm/device_allocator/cumem.py:233-241). So the code does not discard all GPU memory at level 2, as the docstring says: it keeps the runtime and CUDA graph pools.

Worked example: memory profiling on an 80 GiB GPU

Assumptions (illustrative, not measured): an 8B model with 32 layers, 8 KV heads, head size 128, BF16 weights of about 15 GiB; one GPU with 80 GiB; default settings.

  1. requested_memory = ceil(80 × 0.92) = 73.6 GiB (vllm/v1/worker/utils.py:724-726).
  2. The snapshot in init_device saw 79.0 GiB free. The weights loaded after it. After the profile run, 63.0 GiB are free. So total_consumed = 16.0 GiB: 15.0 GiB of weights and 1.0 GiB of runner buffers and non-torch memory (vllm/utils/mem_utils.py:312-314).
  3. During the run, torch's peak was 2.5 GiB above what stays allocated: peak_headroom = 2.5 GiB.
  4. CUDA graph estimate: 0.5 GiB.
  5. available = 73.6 − 16.0 − 2.5 − 0.5 = 54.6 GiB (vllm/v1/worker/gpu_worker.py:744-748).
  6. One block holds 16 tokens in all 32 layers: 32 × 2 × 16 × 8 × 128 × 2 bytes = 2 MiB. The planner adds up the page sizes of all layers in a group (vllm/v1/core/kv_cache_planning.py:574-593).
  7. num_blocks = 54.6 GiB // 2 MiB = 27,955 (vllm/v1/core/kv_cache_planning.py:681), so the KV cache holds 447,280 tokens. (Derived.)

The real values are in the log: "Available KV cache memory: ... GiB" (vllm/v1/worker/gpu_worker.py:763-766). The KV size math in general is in The KV cache↗.

Check yourself#

  1. 1
    Which class does the GPU worker build as its model runner by default?
    easy
    Show answer

    Model Runner V2, vllm.v1.worker.gpu.model_runner.GPUModelRunner, when use_v2_model_runner is true and the instance is not encoder-only (vllm/v1/worker/gpu_worker.py:569-580).

  2. 2
    Why does init_device start NCCL and make the cuBLAS handles before it takes the memory snapshot?
    medium
    Show answer

    So their memory counts as the baseline and not as memory that the model consumed. The comments say this for NCCL (vllm/v1/worker/gpu_worker.py:497-500) and for cuBLAS, whose memory torch cannot free on demand (vllm/v1/worker/gpu_worker.py:516-522).

  3. 3
    On an 80 GiB GPU with --gpu-memory-utilization 0.92, the profile run consumes 16 GiB, the peak headroom is 2.5 GiB and the CUDA graph estimate is 0.5 GiB. How much memory goes to the KV cache, and what changes with VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0?
    hard
    Show answer

    73.6 − 16 − 2.5 − 0.5 = 54.6 GiB (vllm/v1/worker/gpu_worker.py:744-748, vllm/v1/worker/utils.py:724-726). With the variable at 0, the estimate is not subtracted, so the KV cache gets 55.1 GiB, and the worker warns that you may need a lower utilization to avoid OOM (vllm/v1/worker/gpu_worker.py:711-715, vllm/v1/worker/gpu_worker.py:790-805).

  4. 4
    What does Worker.execute_model return for a normal step with Model Runner V2 and no PP, and where does the sampled token come from then?
    medium
    Show answer

    None: the model runner stores the hidden states and returns nothing (vllm/v1/worker/gpu/model_runner.py:2089-2110). The engine core then calls sample_tokens, which returns an AsyncOutput (vllm/v1/worker/gpu_worker.py:1318-1321, vllm/v1/worker/gpu/model_runner.py:2210-2218).

Related pages

  • Executors and workers: from the engine core to the GPUsThe executor starts the workers and runs each call on all of them. The uni executor calls one worker in the engine core process; the multiproc executor sends calls to one worker process per GPU through a shared-memory queue.
  • The model runner (Model Runner V2)Model Runner V2 keeps every running request in a fixed row of GPU tensors, gathers each step's inputs from those rows with GPU kernels, runs the model (CUDA graph or eager), and samples in a second call that returns an AsyncOutput without a GPU wait.
  • The KV cache manager: blocks, the block pool and memory sizingIn the engine core, the KVCacheManager hands out KV blocks to the scheduler through a coordinator, one single-type manager per KV cache group and one BlockPool. The workers only receive block ids. The number of blocks comes from a memory profile at start-up.
  • torch.compile and CUDA graphs in vLLMvLLM compiles the inner model once with torch.compile and its own Inductor backend, splits the graph at the attention ops, caches the result on disk, and captures CUDA graphs at start-up. Each step, Model Runner V2 replays a FULL graph for uniform decode batches, PIECEWISE graphs for other batches up to the largest capture size, and runs eagerly above it.
  • Tuning vLLM: throughput and latency knobs, their real defaults and what each one doesWhich vllm serve flags change throughput and latency, where in the code each one acts, and its real default. With a KV cache playground that computes blocks and the maximum-concurrency log line from the code's formulas, and a symptom-to-knob table.
  • v1/executor/multiproc_executor.py: MultiprocExecutor and WorkerProcvllm/v1/executor/multiproc_executor.py starts one worker process per local GPU, broadcasts every call to them through a shared-memory MessageQueue, reads the reply of one output rank, and watches the processes for failures.
  • "v1/worker/gpu/model_runner.py: Model Runner V2"vllm/v1/worker/gpu/model_runner.py holds GPUModelRunner, the default model runner (MRV2). It loads the model, sets up the KV cache, attention backends and CUDA graphs, and per step turns a SchedulerOutput into GPU inputs, runs the forward pass and samples into an AsyncOutput.
