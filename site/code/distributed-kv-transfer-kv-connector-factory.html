distributed/kv_transfer/kv_connector/factory.py: the KV connector registry

Purpose#

vllm/distributed/kv_transfer/kv_connector/factory.py turns the connector name in --kv-transfer-config into a KV connector class, and makes one object of it in a given connector role.

Filevllm/distributed/kv_transfer/kv_connector/factory.py, 249 lines of Python. One class with five class methods, and 17 module-level register_connector calls.
Main classKVConnectorFactory (vllm/distributed/kv_transfer/kv_connector/factory.py:27)
Runs inEvery process that imports it, on the CPU: the front end (class lookups for config checks and metrics), the EngineCore process (the scheduler-side object) and each worker (the worker-side object).
Called byThe scheduler constructor, ensure_kv_transfer_initialized in the worker, VllmConfig checks, the KV connector metrics classes, MultiConnector and a layout helper (see "Who calls it").
Callsimportlib.import_module, supports_hma (vllm/distributed/kv_transfer/kv_connector/factory.py:13-16), supports_kw (vllm/distributed/kv_transfer/kv_connector/factory.py:18) and the connector constructor.
Not in this fileThe base class KVConnectorBase_V1 and the role enum (kv_connector/v1/base.py), the connectors themselves (kv_connector/v1/), the config (vllm/config/kv_transfer.py), the EC connector factory (vllm/distributed/ec_transfer/ec_connector/factory.py).

The page KV connectors explains connectors from the reader's side. This page reads the factory from top to bottom.

Where it sits#

The file has three parts. The class body has the registry and the lookups (lines 27-146). After it, 17 calls register the built-in connectors (lines 149-249). A comment says why they live here and not in each connector file: "we want to only load the files corresponding to the current connector" (lines 149-151).

Who calls it#

  • The scheduler makes the SCHEDULER object in its constructor (vllm/v1/core/sched/scheduler.py:177-181).
  • Each worker makes the WORKER object once, in ensure_kv_transfer_initialized (vllm/distributed/kv_transfer/kv_transfer_state.py:73-92), called from Worker after the KV cache config is known (vllm/v1/worker/gpu_worker.py:873-878).
  • VllmConfig in the front end reads the class for three checks: HMA support (vllm/config/vllm.py:2243), sleep mode (vllm/config/vllm.py:1242-1249) and PIECEWISE CUDA graphs (vllm/config/vllm.py:1966-1980).
  • Metrics. KVConnectorLogging and the Prometheus metrics class read the class (vllm/distributed/kv_transfer/kv_connector/v1/metrics.py:57, vllm/distributed/kv_transfer/kv_connector/v1/metrics.py:161); the stat logger makes the first one in the front end (vllm/v1/metrics/loggers.py:132).
  • Other code. A layout helper asks for the required KV cache layout (vllm/distributed/kv_transfer/kv_connector/utils.py:56-57). MultiConnector resolves its children (vllm/distributed/kv_transfer/kv_connector/v1/multi_connector.py:150, vllm/distributed/kv_transfer/kv_connector/v1/multi_connector.py:168, vllm/distributed/kv_transfer/kv_connector/v1/multi_connector.py:694).
  • Tests and plugins call register_connector, for example tests/v1/kv_connector/unit/test_multi_connector.py:146.

What it calls#

  • importlib.import_module in the loader and for the module path (vllm/distributed/kv_transfer/kv_connector/factory.py:37, vllm/distributed/kv_transfer/kv_connector/factory.py:108).
  • supports_kw(connector_cls, "kv_cache_config") to reject old constructors (vllm/distributed/kv_transfer/kv_connector/factory.py:116).
  • supports_hma, an issubclass check against SupportsHMA (vllm/distributed/kv_transfer/kv_connector/v1/base.py:132-136), and MultiConnector.all_children_support_hma (vllm/distributed/kv_transfer/kv_connector/v1/multi_connector.py:156-170).
  • The connector constructor connector_cls(config, role, kv_cache_config) (line 75).

Walk through the main methods#

register_connector: a lazy entry#

  1. Line 28. The registry is a class attribute, so there is one per process.
  2. Lines 33-34. A second registration of any name raises. There is no override form.
  3. Lines 36-38. The loader is a closure. It imports the module only when it is called, so the front end can register NIXL or Mooncake without importing their libraries.

get_connector_class: module path wins#

  1. Lines 100-102. No kv_connector: ValueError.
  2. Lines 103-105. An empty string as module path is an error; None means "not set".
  3. Lines 106-114. With a module path, kv_connector is the class name inside that module. A missing class raises AttributeError with the module path.
  4. Lines 116-124. The constructor must accept kv_cache_config. The message says that the "2-argument constructor signature" is deprecated; vLLM logs it at ERROR level and raises.
  5. Lines 125-128. Without a module path, the registry; else "Unsupported connector type".

The EC connector factory uses the opposite order: registry first, module path as the fallback (vllm/distributed/ec_transfer/ec_connector/factory.py:66-73).

create_connector: one role, one object#

  1. Lines 49-52. The config must have a KV transfer config; the class comes from get_connector_class.
  2. Lines 55-60. If the hybrid KV cache manager is on and the connector does not support it, ValueError asks for --disable-hybrid-kv-cache-manager. VllmConfig normally turns the manager off first (vllm/config/vllm.py:2236-2259), so this raises only when the user forced the manager on.
  3. Lines 62-66. An INFO log names the class and the engine id.
  4. Lines 67-75. The comment explains the two roles: the scheduler connector "should only be used inside the Scheduler class", the worker connector "inside the forward context & attention layer". The same class is built with the role as an argument.

supports_hma_config: the MultiConnector case#

A normal connector supports HMA when its class subclasses SupportsHMA. MultiConnector subclasses it too, but the docstring says that "effective support depends on every configured child". So the factory asks all_children_support_hma, which returns False for an empty child list.

Deep dive

Processes and import time

The 17 built-in names enter the registry when Python imports the module, in each process that imports it. For vllm serve, the front end imports it at start-up: the CLI module imports the multiprocess executor, which imports the connector utilities, which import the factory (vllm/entrypoints/cli/serve.py:29, vllm/v1/executor/multiproc_executor.py:33, vllm/distributed/kv_transfer/kv_connector/utils.py:17). The imports inside VllmConfig are lazy (vllm/config/vllm.py:2239-2241). The scheduler, the worker-side state module and the metrics module import it at module level (vllm/v1/core/sched/scheduler.py:21, vllm/distributed/kv_transfer/kv_transfer_state.py:6, vllm/distributed/kv_transfer/kv_connector/v1/metrics.py:9).

A plugin's register_connector must therefore run after the factory module is imported and before the lookup. A general plugin that imports KVConnectorFactory and calls register_connector satisfies both: its own import loads the built-ins first. It runs in the front end, the engine core and each worker (How vLLM finds and loads plugins).

With TP = 2 one vllm serve makes 3 connector objects: 1 SCHEDULER in the engine core and 1 WORKER in each of the 2 workers. The front end makes none; it only gets the class. (Derived from "Who calls it".)

Deep dive

Worked example: a connector from a module path

You write acme_kv/connector.py with class AcmeConnector(KVConnectorBase_V1) and start:

vllm serve Qwen/Qwen3-8B --kv-transfer-config \
  '{"kv_connector":"AcmeConnector","kv_role":"kv_both","kv_connector_module_path":"acme_kv.connector"}'
  1. The front end checks HMA: get_connector_class imports acme_kv.connector and takes AcmeConnector (lines 106-110). It does not subclass SupportsHMA, so VllmConfig turns the hybrid manager off with a WARNING (vllm/config/vllm.py:2243-2256).
  2. supports_kw finds kv_cache_config in the constructor (line 116); the base class has it (vllm/distributed/kv_transfer/kv_connector/v1/base.py:214-219).
  3. The engine core imports the module again and makes AcmeConnector(config, KVConnectorRole.SCHEDULER, kv_cache_config).
  4. Each worker does the same with WORKER.

No registration is needed, because every lookup imports the module itself. An offline example in the repository uses the same field (examples/disaggregated/kv_load_failure_recovery_offline/decode_example.py:44).

Deep dive

Environment variables and flags

The factory reads no environment variable. Its inputs come from --kv-transfer-config (vllm/engine/arg_utils.py:1871), and indirectly from --kv-offloading-size, which fills kv_connector with OffloadingConnector or SimpleCPUOffloadConnector (vllm/config/vllm.py:1149-1157). VLLM_USE_SIMPLE_KV_OFFLOAD (default 0) picks between the two (vllm/envs.py:2239-2241).

Check yourself#

  1. 1
    What does the registry store for each name: a class, an object or something else?
    easy
    Show answer

    A function with no arguments that imports the module and returns the class (vllm/distributed/kv_transfer/kv_connector/factory.py:36-40). The module is imported only at the first lookup.

  2. 2
    With a module path set, what must kv_connector contain?
    medium
    Show answer

    The class name inside that module: getattr(connector_module, connector_name) (vllm/distributed/kv_transfer/kv_connector/factory.py:108-114). The registry is not used.

  3. 3
    Why can create_connector raise for a hybrid model even though VllmConfig checks HMA first?
    medium
    Show answer

    VllmConfig turns the manager off only when disable_hybrid_kv_cache_manager is None (vllm/config/vllm.py:2236-2259). If the user forced the manager on, create_connector still finds HMA on and raises (vllm/distributed/kv_transfer/kv_connector/factory.py:55-60).

  4. 4
    You serve with TP = 4 and a connector registered by a general plugin. How many times does register_connector run, and how many connector objects exist?
    hard
    Show answer

    The general plugin runs once in each process: front end, engine core and 4 workers, so 6 registrations, one per process registry (vllm/plugins/__init__.py:82-90). Objects: 1 SCHEDULER in the engine core (vllm/v1/core/sched/scheduler.py:177-181) and 1 WORKER per worker (vllm/distributed/kv_transfer/kv_transfer_state.py:88-92), so 5. The front end only reads the class. (A model registry subprocess, if one runs, adds one more registration.)

Related pages

  • KV connectorsA KV connector moves KV cache blocks between vLLM and something outside it. One connector class runs as two objects - a scheduler-side object in the engine core that plans loads and saves, and a worker-side object in each worker that moves the bytes. KVConnectorFactory finds the class by name.
  • All the ways to extend vLLMvLLM has about twenty extension points of three kinds - six entry-point groups, a dozen registries that a general plugin fills, and config fields that name your class. This page maps each one to its process and its page.
  • Disaggregated prefill: prefill and decode on different instancesIn P/D disaggregation one vLLM instance computes the prompt, a second one decodes, and a KV connector moves the KV blocks between them. vLLM ships the connectors and the kv_transfer_params plumbing; a router outside vLLM sends each request to both instances.
  • The hybrid KV cache: specs, groups and one manager per layer typeModels that mix full attention with sliding-window, chunked-local or Mamba layers get one KV cache group per layer type. Each group has its own block table and single-type manager, all groups share one block pool, and so every group must use the same page size. Prefix caching finds one hit length that is valid for all groups.
  • v1/core/sched/scheduler.py: the Schedulervllm/v1/core/sched/scheduler.py holds the Scheduler class (3,539 lines). schedule() shares the token budget between running and waiting requests and builds the SchedulerOutput; update_from_output() appends the sampled tokens, stops requests and builds the EngineCoreOutputs.
  • plugins/__init__.py: the plugin loadersvllm/plugins/__init__.py names the five plugin entry-point groups and has the three loaders: the shared group loader, the once-per-process general loader and the strict endpoint loader.
