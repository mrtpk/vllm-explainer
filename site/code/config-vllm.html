config/vllm.py: VllmConfig, __post_init__ and compute_hash

AdvancedCode mapabout 10 min read + 2 min deep dives

Purpose#

vllm/config/vllm.py defines the VllmConfig: one object that holds every top-level config of the engine. Its __post_init__ turns a set of separate sub-configs into one consistent configuration.

Filevllm/config/vllm.py, 3,617 lines of Python. One class, VllmConfig, of about 3,160 lines; an enum, four level tables, eight fusion helpers, and the "current config" functions.
Main classVllmConfig (vllm/config/vllm.py:347-348).
Runs in__post_init__ runs where a VllmConfig is made: the API server process of vllm serve, and again in each engine core process after the handshake. The properties and compute_hash run in every process that holds a copy.
Called byEngineArgs.create_engine_config (construction); the engine core, the workers, the model runner and the compile backend (properties, compute_hash, get_current_vllm_config).
CallsThe platform hooks, Executor.get_class, the model registry and config classes, the KV connector factory (class lookup only).
Not in this fileThe sub-config classes (vllm/config/*.py), the flag parser and the batch defaults (engine/arg_utils.py: EngineArgs, the flags and create_engine_config), the compile backend that uses the hash (vllm/compilation/).

Where it sits#

Panel 2 of the diagram on How configuration works shows VllmConfig(...) at the end of create_engine_config, and the phases of __post_init__. Panel 3 shows the copies in the other processes.

Who calls it#

  • EngineArgs.create_engine_config makes the object (vllm/engine/arg_utils.py:2870-2903).
  • The engine core calls vllm_config.__post_init__() a second time after the handshake (vllm/v1/engine/core.py:1336-1337).
  • vLLM's replace() helper makes a new object with the constructor, so __post_init__ runs again (vllm/config/utils.py:121-129).
  • The compile backend calls compute_hash() for its cache folder (vllm/compilation/backends.py:1062).
  • Model code reads the active config with get_current_vllm_config() (vllm/config/vllm.py:3576-3586).

What it calls#

  • The platform hooks apply_config_platform_defaults and check_and_update_config (vllm/config/vllm.py:1804, vllm/config/vllm.py:2046).
  • Executor.get_class(self), to ask whether the executor supports async scheduling (vllm/config/vllm.py:1622-1623).
  • The per-architecture config hooks in MODELS_CONFIG_MAP (vllm/config/vllm.py:2727-2743).

Walk through the main methods#

The fields#

Most fields are sub-configs with a default factory (vllm/config/vllm.py:357-422). The top-level settings are additional_config, instance_id, optimization_level (default O2), performance_mode (default "balanced") and shutdown_timeout (vllm/config/vllm.py:428-457). The generated table of all fields is on Config classes.

The optimization level tables#

O0 turns all fusions off and sets CUDA graphs to NONE; O1 uses PIECEWISE; O2 and O3 use FULL_AND_PIECEWISE and are equal at this commit (vllm/config/vllm.py:254-337). The docstring of O3 says "Currently the same as -O2s." (vllm/config/vllm.py:142-143). A value is either a constant or a function of the config, for example enable_allreduce_rms_fusion (vllm/config/vllm.py:178-202). apply_recursive walks the nested table. For each leaf it calls _set_config_default, which calls the function and writes the result only when the field is None (vllm/config/vllm.py:1014-1019):

So the tables never overwrite a value that the user or an earlier phase set. The page torch.compile and CUDA graphs in vLLM explains what each pass and mode does.

Docs and code differ on O0 custom ops

The design doc says that -O0 sets -cc.mode=NONE "(also resulting in -cc.custom_ops=["none"])" (docs/design/optimization_levels.md:37). The code does the opposite: with the mode NONE, the base entry of the list is "all", so all custom ops are on (vllm/config/vllm.py:1819-1826).

__post_init__, phase by phase#

The method is about 830 lines long. Its docstring is "Verify configs are valid & consistent with each other." (vllm/config/vllm.py:1493). We read it in nine phases.

Phase 1: early exits and model hooks.

  1. Line 1495. instance_id from the clock, for profile names.
  2. Lines 1497-1501. A sub-model view made by with_hf_config skips all checks.
  3. Lines 1505-1516. An instance that runs only the multimodal encoder turns prefix caching off.
  4. Line 1521. The per-architecture hooks run once; a flag on the model config stops a second run (vllm/config/vllm.py:2718-2721).
  5. Lines 1531-1534. The model checks itself against the parallel config, and the parallel config learns if the model is MoE.

Phase 2: quantization and weights. quant_config comes from the model and load configs (vllm/config/vllm.py:1586-1589). For most load formats, the model config may untie the word embeddings (lines 1594-1599).

Phase 3: async scheduling.

An explicit --async-scheduling raises on a conflict; an unset value only switches it off, with a log (lines 1647-1663). The page Async scheduling: overlap the CPU and the GPU explains the feature.

Phase 4: eager mode and compile switches. --enforce-eager sets the compile mode and the CUDA graph mode to NONE (vllm/config/vllm.py:1745-1763). TORCH_COMPILE_DISABLE=1 sets the compile mode to NONE (lines 1765-1770). For some architectures, _maybe_enable_breakable_cudagraph writes VLLM_USE_BREAKABLE_CUDAGRAPH=1 into os.environ and turns compilation off (vllm/config/vllm.py:824-851).

Phase 5: platform defaults, compile mode, level defaults.

  1. Line 1804. The first platform hook. It runs before the level defaults, so a platform can set a field and keep it.
  2. Lines 1806-1810. No mode set: VLLM_COMPILE above O0, else NONE.
  3. Lines 1819-1826. The base entry of the custom op list: "none" with Inductor and compilation, else "all" (CustomOp, out-of-tree ops and IR op providers).
  4. Line 1831. The IR op priorities, before the fusion defaults that depend on them.
  5. Lines 1833-1834. The level table.

Phase 6: CUDA graphs. Piecewise modes need VLLM_COMPILE, else the mode falls back (vllm/config/vllm.py:1111-1131, vllm/config/vllm.py:1909-1911). On a platform with static graphs, pooling models get PIECEWISE, encoder-decoder models FULL_DECODE_ONLY, and some KV connectors PIECEWISE (vllm/config/vllm.py:1929-1980). With --enforce-eager, the eager branch clears the sizes. Then _set_cudagraph_sizes runs in both cases (vllm/config/vllm.py:1982-1992).

Phase 7: the platform's last word. current_platform.check_and_update_config(self) (vllm/config/vllm.py:2046). A comment right after it says that the platform "has the last word on async scheduling" (line 2048).

Phase 8: model runner and compile ranges.

An unsupported feature normally selects Model Runner V1 (the use_v2_model_runner property below). It raises ValueError only when Model Runner V2 is forced, for example with VLLM_USE_V2_MODEL_RUNNER=1 (vllm/config/vllm.py:3283-3292, vllm/config/vllm.py:730-732). The compile ranges are computed again, because the platform hook can change max_num_batched_tokens (comment at lines 2081-2082).

Phase 9: KV transfer, hybrid KV cache manager, final checks. _post_init_kv_transfer_config resolves KV offloading (vllm/config/vllm.py:2199). The hybrid KV cache manager is turned off when the platform or the KV connector does not support it; an explicit --enable-hybrid-kv-cache-manager then raises (vllm/config/vllm.py:2236-2273). The last line logs the enabled compile passes (vllm/config/vllm.py:2318).

compute_hash#

The method collects one hash per sub-config in a fixed order; a missing optional config adds "None". additional_config is hashed as sorted JSON (vllm/config/vllm.py:559-567). The result is the first 10 hex digits of safe_hash(str(factors)) (vllm/config/vllm.py:572-575), which is MD5, or SHA-256 when MD5 is not available (vllm/utils/hashing.py:106-121). The docstring warns that a new field must join the list if it changes the computation graph (vllm/config/vllm.py:460-468).

use_v2_model_runner and max_concurrent_batches#

  1. Lines 714-728. HiSparse and watermarking need Model Runner V2. HiSparse with VLLM_USE_V2_MODEL_RUNNER=0 raises; watermarking ignores the 0.
  2. Lines 730-732. Otherwise the variable decides, if it is set.
  3. Lines 734-747. No Triton, or a feature from _get_v2_model_runner_unsupported_features: Model Runner V1, with a warning (The model runner (Model Runner V2)).

max_concurrent_batches is pp_size + 1 with async scheduling and Model Runner V2, so 2 on one GPU (vllm/config/vllm.py:586-597). The engine core makes a batch queue only when the value is above 1 (vllm/v1/engine/core.py:205-211).

set_current_vllm_config#

The context manager puts the config into a module global for the time of the block, for example while the worker builds the model (vllm/v1/worker/gpu_worker.py:592-598). get_current_vllm_config() raises an AssertionError outside such a block (lines 3576-3586). A CustomOp made at import time hits this error, as the message says.

Deep dive

__post_init__ also writes the environment

Two places in __post_init__ write os.environ:

  • VLLM_USE_BREAKABLE_CUDAGRAPH=1 for the default breakable-graph architectures, or for some batch-invariant BF16 models (vllm/config/vllm.py:824-843).
  • NCCL_GRAPH_REGISTER=0 when the CUDA graph pool uses cumem, with a warning if the user set another value (vllm/config/vllm.py:2309-2316).

In vllm serve, this runs in the API server before the engine core starts. A spawned child gets a copy of the parent environment, so the engine core and the workers see the values (derived; see How configuration works, Step 9). So in vLLM some configuration travels in the environment, not in the config object.

Check yourself#

  1. 1
    What does -O3 change compared to the default at this commit?
    easy
    Show answer

    Nothing. The O3 table has the same values as the O2 table (vllm/config/vllm.py:296-337), and the docstring says "Currently the same as -O2s." (vllm/config/vllm.py:142-143).

  2. 2
    A platform plugin wants a different default CUDA graph mode, but it must not override a user's value. Which hook should it use?
    medium
    Show answer

    apply_config_platform_defaults. It runs before the level defaults (vllm/config/vllm.py:1804, vllm/config/vllm.py:1833-1834). If the hook sets the mode only when it is None, the level table then keeps the value, because it fills only None fields (vllm/config/vllm.py:1014-1019).

  3. 3
    Why does a change of --max-num-seqs make the next start compile again?
    medium
    Show answer

    SchedulerConfig.compute_hash includes max_num_seqs (vllm/config/scheduler.py:282-284). VllmConfig.compute_hash includes that hash (vllm/config/vllm.py:500-501), and the compile cache folder name depends on it (vllm/compilation/backends.py:1091-1097).

  4. 4
    You start vllm serve with --enforce-eager -O2. Which CUDA graph capture sizes does the config end with, and which lines decide it?
    hard
    Show answer

    An empty list, with max_cudagraph_capture_size = 0. Phase 4 sets the graph mode to NONE (vllm/config/vllm.py:1745-1747); the O2 table does not override it, because the field is not None (vllm/config/vllm.py:1014-1019). On a static-graph platform, the eager branch then clears the sizes (vllm/config/vllm.py:1983-1988).

  • Config classesvLLM keeps its configuration in about 40 pydantic dataclasses in vllm/config/, made with the @config decorator. VllmConfig holds the top-level ones. This page tells how the decorator works, what VllmConfig.__post_init__ and compute_hash do, and lists every config class with its fields.
  • torch.compile and CUDA graphs in vLLMvLLM compiles the inner model once with torch.compile and its own Inductor backend, splits the graph at the attention ops, caches the result on disk, and captures CUDA graphs at start-up. Each step, Model Runner V2 replays a FULL graph for uniform decode batches, PIECEWISE graphs for other batches up to the largest capture size, and runs eagerly above it.
  • Async scheduling: overlap the CPU and the GPUWith async scheduling, the engine core schedules and starts step N+1 before it waits for the token of step N. Placeholders in the scheduler and a GPU-side token buffer in Model Runner V2 make this possible.
  • The model runner (Model Runner V2)Model Runner V2 keeps every running request in a fixed row of GPU tensors, gathers each step's inputs from those rows with GPU kernels, runs the model (CUDA graph or eager), and samples in a second call that returns an AsyncOutput without a GPU wait.
  • The Platform interfaceThe Platform class is the contract between vLLM and a hardware vendor. Identity attributes describe the device; config hooks change VllmConfig in the front end; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation.
