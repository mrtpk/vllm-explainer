"model_executor/layers/linear.py: tensor-parallel linear layers"

AdvancedCode mapabout 8 min read + 3 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The tensor-parallel layers (linear.py and vocab_parallel_embedding.py) Advanced

Purpose#

vllm/model_executor/layers/linear.py gives model files linear layers that know their tensor-parallel rank: each layer stores only its slice of the weight, loads that slice from a full checkpoint tensor, and does the communication of its split.

Filevllm/model_executor/layers/linear.py, 1,819 lines of Python.
Main classesLinearBase, ReplicatedLinear, ColumnParallelLinear, MergedColumnParallelLinear, QKVParallelLinear, RowParallelLinear; the quantize methods LinearMethodBase and UnquantizedLinearMethod.
Runs inEach worker. Constructors and loaders run once at model load; forward runs on the GPU in every step.
Called byModel files (for example vllm/model_executor/models/llama.py:95-111), quantization methods that subclass LinearMethodBase, and LoRA wrappers. About 315 files in vllm/ name this module (git grep at this commit).
Callsresolve_quant_method, the TP helpers divide, split_tensor_along_last_dim, tensor_model_parallel_all_gather and tensor_model_parallel_all_reduce, and the parameter classes of parameter.py (vllm/model_executor/layers/linear.py:14-45).
Not in this fileThe embedding and LM head (vocab_parallel_embedding.py), the GEMM kernels (chosen by each quantize method), the communicators (Process groups: how vLLM slices its ranks), and the per-parameter load methods (parameter.py).

The page The tensor-parallel layers (linear.py and vocab_parallel_embedding.py) explains the ideas. This page maps the file and reads the forward and loader methods line by line.

Where it sits#

Who calls it#

  • Model constructors build the layers with full sizes, a quant_config and a prefix (vllm/model_executor/models/llama.py:165-181).
  • AutoWeightsLoader calls load_weights of the merged and QKV layers, and the weight_loader of other parameters (vllm/model_executor/models/utils.py:387-424).
  • Quantization methods subclass LinearMethodBase, for example Fp8LinearMethod (vllm/model_executor/layers/quantization/fp8.py:225).
  • LoRA wraps these layers; it finds a replaced class with maybe_get_oot_by_class (vllm/lora/layers/column_parallel_linear.py:169).

What it calls#

  • resolve_quant_method(quant_config, layer, prefix) in LinearBase.__init__ (vllm/model_executor/layers/linear.py:293).
  • quant_method.create_weights(...) and quant_method.apply(...) (vllm/model_executor/layers/linear.py:536-544, vllm/model_executor/layers/linear.py:623).
  • The collectives in forward (vllm/model_executor/layers/linear.py:627, vllm/model_executor/layers/linear.py:1804).
  • The parameter methods load_column_parallel_weight, load_merged_column_weight, load_qkv_weight and load_row_parallel_weight in the v2 loaders (vllm/model_executor/parameter.py:145-226).

Walk through the main methods#

ColumnParallelLinear.__init__: sizes and the loader choice#

  1. Lines 484-495. The rank and size come from the TP group, unless disable_tp or explicit values are given. DCPGroupColumnParallelLinear uses the explicit values to split across groups.
  2. Lines 496-503. The full input and output_size / tp_size. If the subclass set output_sizes (merged and QKV), each part is divided separately.
  3. Lines 524-534. The v2 loader if the quantize method's class name is in the list; an online-quantization method is judged by its source method.
  4. Lines 536-544. The quantize method makes the weight parameters and gives each one the chosen loader. For UnquantizedLinearMethod this is one ModelWeightParameter of shape [sum(output_partition_sizes), input_size] (vllm/model_executor/layers/linear.py:192-205).

ColumnParallelLinear.forward and weight_loader#

  1. Lines 595-598. v1 loader: if the parameter has output_dim and is not already sharded, cut shard_size rows at tp_rank × shard_size. shard_size is the parameter's own size, so the cut needs no TP size.
  2. Lines 602-603. A scalar scale from the checkpoint becomes a 1-element tensor.
  3. Lines 608-614. The v2 loader gives the work to param.load_column_parallel_weight.
  4. Line 623. quant_method.apply(self, input_, bias): the GEMM. Every rank gets the same full input.
  5. Lines 625-627. The all-gather only with gather_output and TP > 1; else the output stays a slice [T, out / tp_size].

QKVParallelLinear.weight_loader (v1)#

  1. Lines 1282-1290. Offset and size of the shard inside this rank's parameter: q first, then k, then v, all in per-rank head counts.
  2. Lines 1292-1309. Fixes for block scales and packed or Marlin weights (see the deep dive).
  3. Line 1312. The view of the parameter for this shard.
  4. Lines 1313-1317. The slice index in the checkpoint tensor: tp_rank for q, tp_rank // num_kv_head_replicas for k and v.
  5. Lines 1319-1320. The cut of the checkpoint tensor; then the assertion and the copy at lines 1336-1337.

A None shard id means the checkpoint already stores QKV fused (Phi-3 style). Then the loader cuts the full tensor into q, k and v by the total head counts and calls itself once per part (lines 1225-1276). The v2 loader does the same through param.load_qkv_weight, with num_heads=self.num_kv_head_replicas (vllm/model_executor/layers/linear.py:1191-1209).

RowParallelLinear.weight_loader and forward#

  1. Lines 1763-1766. The cut is along input_dim (dimension 1 of [out, in]) at tp_rank × shard_size.
  2. Lines 1770-1774. Scalars become 1-element tensors; then a shape assertion and the copy.

The bias is a full [output_size] parameter with the v1 loader (lines 1742-1753). Its output_dim is 0 and it has no input_dim, so the row loader copies it whole on every rank. In forward, only rank 0 adds it (vllm/model_executor/layers/linear.py:1798-1801). forward is on The tensor-parallel layers (linear.py and vocab_parallel_embedding.py): optional split of the input, GEMM, and the all-reduce when reduce_results and TP > 1 (vllm/model_executor/layers/linear.py:1785-1811).

Data flow: types and shapes

LayerInput (per rank)Weight (per rank, unquantized)Output (per rank)Collective
ReplicatedLinear[T, in][out, in][T, out]none
ColumnParallelLinear[T, in][out / tp, in][T, out / tp], or [T, out] with gatherall-gather if gather_output

h_q and h_kv are the per-rank head counts and d the head size (vllm/model_executor/layers/linear.py:1065-1077). Every forward returns (output, output_bias) unless return_bias=False; output_bias is not None only with skip_bias_add (for example vllm/model_executor/layers/linear.py:631-634). This is why llama.py writes x, _ = self.gate_up_proj(x).

Deep dive

Worked example: gate_up_proj and down_proj of Llama-3-8B, TP = 2

From the Llama-3-8B config.json on the Hugging Face Hub: hidden 4,096, intermediate 14,336. llama.py builds MergedColumnParallelLinear(4096, [14336, 14336]) and RowParallelLinear(14336, 4096).

  1. gate_up, constructor. output_partition_sizes = [7168, 7168] (lines 500-503). The weight is [14336, 4096], 112 MiB in BF16.
  2. Load gate_proj (shard 0) on rank 1. Offset 0, size 7168 in the parameter; checkpoint rows 7168-14335 (lines 966-983 and load_merged_column_weight).
  3. Load up_proj (shard 1) on rank 1. Offset 14336 / 2 = 7168, size 7168 in the parameter; checkpoint rows 7168-14335 of up_proj.
  4. down, constructor. input_size_per_partition = 7168; the weight is [4096, 7168], 56 MiB.
  5. Load down_proj on rank 1. Columns 7168-14335 of the checkpoint tensor (lines 1763-1766, or load_row_parallel_weight).
  6. Forward with T = 2048. gate_up gives [2048, 14336]; SiluAndMul gives [2048, 7168]; down gives a partial [2048, 4096]; the all-reduce moves 2048 × 4096 × 2 B = 16 MiB.

These are the numbers of Tensor and pipeline parallelism in practice, now with the line of each step (derived).

Deep dive

Quantized storage in the loaders

  • Packed weights. INT4 formats pack several values into one element. A parameter with packed_dim == output_dim divides the offset and size by packed_factor (vllm/model_executor/layers/linear.py:1301-1304).
  • Marlin. adjust_marlin_shard multiplies offset and size by marlin_tile_size when the parameter has one (vllm/model_executor/layers/linear.py:73-82).
  • Block scales. For BlockQuantScaleParameter, offsets and sizes are rounded up to whole blocks of weight_block_size[0] rows (vllm/model_executor/layers/linear.py:85-94). _maybe_allow_fp8_block_shape_mismatch allows parts that do not fill whole blocks, with a DEBUG log (vllm/model_executor/layers/linear.py:562-587).
  • Per-part scalars. A stacked layer with per-tensor scales keeps one scale per part; adjust_scalar_to_fused_array picks slot 0, 1 or 2 from the shard id (vllm/model_executor/layers/linear.py:97-121).
  • After the copy. A quantize method may replace parameters in process_weights_after_loading. update_param_tp_status then resets the rank fields of the new parameters (vllm/model_executor/layers/linear.py:311-324, vllm/model_executor/model_loader/utils.py:187-193).

Check yourself#

  1. 1
    What is the default of gather_output in ColumnParallelLinear, and why?
    easy
    Show answer

    False (vllm/model_executor/layers/linear.py:473). The next layer is usually row-parallel and wants the slice; a gather would only add traffic.

  2. 2
    Which loader does a BF16 QKVParallelLinear weight use, and where is the cut done?
    medium
    Show answer

    weight_loader_v2, because UnquantizedLinearMethod is in WEIGHT_LOADER_V2_SUPPORTED (vllm/model_executor/layers/linear.py:50-51, vllm/model_executor/layers/linear.py:530-534). It calls param.load_qkv_weight, which cuts the parameter and the checkpoint tensor (vllm/model_executor/parameter.py:175-198).

  3. 3
    Why does every linear forward return a tuple?
    medium
    Show answer

    With return_bias=True (the default), it returns (output, output_bias). output_bias is the bias only with skip_bias_add, so a caller can fuse the bias into a later op (vllm/model_executor/layers/linear.py:631-634).

  4. 4
    A checkpoint stores qkv_proj.weight already fused, for a model with 32 query heads, 8 KV heads and head size 128, and TP = 2. Which rows of the fused tensor does rank 1 copy for its k part?
    hard
    Show answer

    For a BF16 weight the v2 loader runs. The shard id is None, so it calls _load_fused_module_from_checkpoint (vllm/model_executor/layers/linear.py:1174-1189). That method cuts the fused tensor by total head counts: k is rows 4096-5119 (vllm/model_executor/layers/linear.py:1130-1143). It then loads that part with shard id k. Rank 1 takes slice 1 // 1 = 1 of size 512 (vllm/model_executor/parameter.py:191-195): rows 512-1023 of the k part, which are rows 4608-5119 of the fused tensor. The v1 loader gives the same rows (lines 1237-1320).

Related pages

  • The tensor-parallel layers (linear.py and vocab_parallel_embedding.py)vLLM's linear and embedding layers know their tensor-parallel rank. They resolve a quantization method per layer, allocate only their slice, cut checkpoint tensors when they load, and call the all-reduce or all-gather in forward. QKVParallelLinear splits by heads and copies KV heads when TP is larger than their count.
  • "Weight loading: from checkpoint files to GPU parameters"Each worker picks a model loader by --load-format, builds the model with empty per-rank parameters on its GPU, streams every checkpoint tensor once, renames it with a WeightsMapper, and lets the parameter's weight_loader copy only this rank's slice.
  • Quantization methods as pluginsA quantization method is a QuantizationConfig subclass registered under a name. The front end picks the name from the checkpoint or --quantization and makes one config object; each layer in the worker asks it for a quantize method that makes the weights and runs the forward.
  • CustomOp, out-of-tree ops and IR op providersA CustomOp is a layer with one forward method per platform. It picks one method when it is built - forward_native when disabled, the platform's method when enabled. Plugins replace whole classes with register_oot, and vllm.ir adds a second, per-op provider choice.
  • "model_executor/models/llama.py: the Llama model"vllm/model_executor/models/llama.py defines LlamaMLP, LlamaAttention, LlamaDecoderLayer, LlamaModel and LlamaForCausalLM from tensor-parallel layers, plus two bidirectional wrappers. It is the reference model file of vLLM; nine registry names and many other model files reuse it.
  • model_executor/custom_op.py: CustomOp, PluggableLayer and their registriesvllm/model_executor/custom_op.py defines the CustomOp base class (one forward method per platform, chosen once per object), the PluggableLayer base class (whole-layer replacement), the two name registries and the register_oot decorators.
  • Process groups: how vLLM slices its ranksEach worker puts all ranks into one grid of shape (DP, PP, PCP, TP) and cuts it into process groups. Each group is a GroupCoordinator with a gloo CPU group, an NCCL device group and, for groups of more than one rank, a device communicator that picks the all-reduce implementation.
