Purpose#

vllm/platforms/interface.py defines the contract that every hardware platform implements: the base class Platform with a default for almost every method.

Filevllm/platforms/interface.py, 1495 lines of Python. Three small types, three module functions, the class Platform (lines 137-1490) and UnspecifiedPlatform.
Main classPlatform (vllm/platforms/interface.py:137): 12 class attributes and 90 methods, 84 of them without a leading underscore. Most methods are class methods.
Runs inEvery vLLM process, through its current_platform object. The methods run on the CPU, in the thread of the caller. They must not start a device context unless their job needs one.
Called byvLLM code all over the tree, through current_platform: the config code in the front end, the engine core, the workers, the layers and the compiler (see the hook table on The Platform interface).
Callstorch (dtypes, torch.<device_type>), os.environ for the device-control variable, and lazy imports of attention backends, KV cache specs and config classes inside some methods.
Not in this fileThe detection of the platform (__init__.py, page platforms/__init__.py: platform detection and current_platform) and the vendor classes (cuda.py, rocm.py, cpu.py, xpu.py, tpu.py, zen_cpu.py).

The page The Platform interface explains the hooks in start-up order. This page maps the file and reads its most important methods.

Where it sits#

Who calls it#

  • The config code (front end). EngineArgs calls pre_register_and_update and validate_environ (vllm/engine/arg_utils.py:2246-2250). add_cli_args also calls pre_register_and_update, once for each parser that the front end builds (vllm/engine/arg_utils.py:3257). VllmConfig.__post_init__ calls apply_config_platform_defaults and check_and_update_config (vllm/config/vllm.py:1804, vllm/config/vllm.py:2046). Each engine core runs __post_init__ again after its handshake, so these two hooks run there too (vllm/v1/engine/core.py:1336-1337).
  • The executors. They call update_block_size_for_backend after the model is loaded (vllm/v1/executor/multiproc_executor.py:702, vllm/v1/executor/uniproc_executor.py:75).
  • Component builders. The attention selector (vllm/v1/attention/selector.py:218), the process groups (vllm/distributed/parallel_state.py:551), the LoRA wrapper selector (vllm/lora/punica_wrapper/punica_selector.py:14), the compiler (vllm/compilation/backends.py:691, vllm/compilation/backends.py:876) and the KV cache planner (vllm/v1/core/kv_cache_config_builder.py:101).
  • Subclasses. Vendor classes call super() for some methods, for example ROCm for import_kernels (vllm/platforms/rocm.py:654) and XPU for update_block_size_for_backend (vllm/platforms/xpu.py:477).
  • The worker process. It calls set_assigned_physical_gpu_ids when the config has assigned GPU ids (vllm/v1/executor/multiproc_executor.py:889-895).

What it calls#

  • torch.<device_type> in the fallback __getattr__ (vllm/platforms/interface.py:1306-1312).
  • The device-control variable, for example CUDA_VISIBLE_DEVICES, in the device-id helpers (vllm/platforms/interface.py:307-313).
  • Attention backend classes inside the block size methods (vllm/platforms/interface.py:678-697) and the MLA prefill registry (vllm/platforms/interface.py:453-456).
  • vllm.envs.environment_variables in validate_environ (vllm/platforms/interface.py:1457-1460).
  • Kernel libraries: vllm._C (vllm/platforms/interface.py:369) and vllm.kernels (vllm/platforms/interface.py:264).

Walk through the main methods#

The three config hooks#

  1. Lines 639-651. pre_register_and_update gets the CLI parser, or None. The docstring names the use case: an out-of-tree quantization config. vllm serve calls it five times in the front end: four times with a parser (vllm/engine/arg_utils.py:3257) and once without (vllm/engine/arg_utils.py:2246).
  2. Lines 654-664. apply_config_platform_defaults runs "after parsing cli arguments" and can change defaults, for example custom_ops.
  3. Lines 667-676. check_and_update_config can raise or change the config "in place". All three return None; their effect is the change to the object.

update_block_size_for_backend: one block size for all backends#

  1. Lines 760-765. Return early with no model config, or with no attention backend except SSM ones. _find_non_ssm_backends reads the backend of each attention layer, so the model must be built first (vllm/platforms/interface.py:678-697).
  2. Lines 771-781. Phase 1, only when the user did not set --block-size: pick a size that every backend accepts, with the default 16 (CacheConfig.DEFAULT_BLOCK_SIZE) as the start value (next section). Log at INFO when the result is not the default.
  3. Lines 785-787. Phase 2, hybrid models (attention + Mamba): align the block and Mamba page sizes. The comment says that this may override the user's setting.
  4. Lines 792-794. Phase 3, KV cache dtype skip layers: align pages of mixed dtypes. Then check that the aligned size is still valid for every backend (vllm/platforms/interface.py:796-823).

_preferred_block_size_for_backends: the common size#

  1. Lines 721-722. One backend: ask it for its preferred size.
  2. Lines 723-724. All backends accept the default: use it.
  3. Lines 726-736. Take one supported size per backend (the base of a MultipleOf, or a fixed size; no sizes means 1). Every combination gives one candidate, the least common multiple. Sort the candidates.
  4. Lines 737-739. Return the first candidate that every backend accepts.
  5. Line 740. None fits: ValueError with each backend's sizes.

Device ids: logical to physical#

  1. Lines 296-303. If the worker set assigned GPU ids, the logical id (a local rank) indexes that list. An id past its end raises IndexError.
  2. Lines 307-313. Else, if the device-control variable is set and not empty, the logical id indexes its comma list. Example: CUDA_VISIBLE_DEVICES=4,5 and local rank 1 give physical device 5.
  3. Lines 314-315. Else the ids are the same.

The comment above the method names three id spaces: logical, visible and physical (vllm/platforms/interface.py:277-285). torch.device("cuda:N") needs a visible id; NVML needs a physical id.

Kernel hooks#

  1. Lines 368-371. A failed import of vllm._C logs a warning once and does not raise.
  2. Lines 372-373. The MoE library is optional: its import error is ignored.
  3. Line 386. register_triton_kernel_overrides does nothing by default. The docstring says that it runs "during model runner init, before any kernel launch"; the caller is init_worker (vllm/v1/worker/worker_base.py:286-290).

get_mla_prefill_backend_cls: a default with a priority list#

  1. Lines 459-460. No device capability (the base class): FlashAttention.
  2. Lines 462-480. Blackwell (major 10): TRT-LLM ragged first for one head layout (192 + 64 / 256), else FlashAttention first.
  3. Lines 481-482. Hopper and older: FlashAttention only.
  4. Lines 486-495. Return the first backend that imports and accepts the config. If none does, the method raises ValueError with all reasons (vllm/platforms/interface.py:498-514).

This is one of few pickers with real logic in the base class. A platform with one MLA prefill backend can override it and return that class.

__getattr__: the fallback to torch#

  1. Lines 1303-1304. Dunder names raise at once, so pickle does not get None for __getstate__.
  2. Lines 1306-1312. Look up the name in torch.<device_type>; return it when it is not None.
  3. Lines 1314-1319. Else warn once and return None.
  4. Lines 1324-1325. get_global_graph_pool uses the fallback: graph_pool_handle is not a Platform method, so on CUDA it is torch.cuda.graph_pool_handle. The pool is stored on the class, so all objects of one platform class share it.

A worked example: block size with two backends

Two made-up attention backends are in one model. Backend A declares MultipleOf(16). Backend B declares the fixed sizes [64, 128]. The user did not set --block-size, so the default is 16.

  1. Two backends, so the single-backend shortcut (line 721) does not apply.
  2. B does not accept 16, so line 723 fails.
  3. Per-backend sizes: A gives [16] (the base of MultipleOf), B gives [64, 128] (lines 726-733).
  4. Candidates: lcm(16, 64) = 64 and lcm(16, 128) = 128, sorted [64, 128] (lines 734-736).
  5. 64 is a multiple of 16 and is in B's list, so both accept it. The result is 64 (lines 737-739), and line 776 logs "Setting kv cache block size to 64".

(The acceptance test is each backend's supports_block_size; this example assumes that it accepts the multiples and the listed sizes. The real rules of each backend are on How vLLM chooses an attention backend.)

Deep dive

Processes and threads

The class has no lock and almost no state. The state that exists:

  • _assigned_physical_gpu_ids: a module global, set once per worker process; a second call with other ids raises RuntimeError (vllm/platforms/interface.py:50-58). The docstring expects a single thread (vllm/platforms/interface.py:49).
  • _global_graph_pool: a class attribute, so one pool per platform class and process (vllm/platforms/interface.py:1321-1326).
  • supported_quantization: a class-level list. register_quantization_config appends to it when it is not empty (vllm/model_executor/layers/quantization/__init__.py:98-100). The base list is one object shared by every subclass that does not set its own. (Derived.)

Which process calls which method is in the hook table of The Platform interface: config hooks in the front end (the two __post_init__ hooks also in each engine core), pickers in the workers and the engine core.

    A platform does not define Stream, and its device_type is "privateuseone". What does current_platform.Stream give, if torch.privateuseone does not exist?
    medium
    Show answer

    None, with a one-time warning "Current platform privateuseone does not have 'Stream' attribute". getattr(torch, "privateuseone", None) is None, so the method skips the lookup and returns None (vllm/platforms/interface.py:1306-1319).

  4. 4
    A model has two attention backends: one declares MultipleOf(16), the other the fixed sizes [64, 128]. The user does not set --block-size. Which block size does vLLM pick, and in which process is it computed with TP = 2?
    hard
    Show answer

    64: the smallest least common multiple that both accept (the worked example in the deep dive; vllm/platforms/interface.py:726-739). Each of the 2 worker processes computes it after load_model (vllm/v1/executor/multiproc_executor.py:701-702).

Related pages

  • The Platform interfaceThe Platform class is the contract between vLLM and a hardware vendor. Identity attributes describe the device; config hooks change VllmConfig in the front end and again in each engine core; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation.
  • Platform plugins and current_platformEach vLLM process makes one Platform object, current_platform, the first time code reads it. Five built-in detectors and the out-of-tree detectors from vllm.platform_plugins decide its class; one out-of-tree platform wins over the built-in ones.
  • All the ways to extend vLLMvLLM has about twenty extension points of three kinds - six entry-point groups, a dozen registries that a general plugin fills, and config fields that name your class. This page maps each one to its process and its page.
  • platforms/__init__.py: platform detection and current_platformvllm/platforms/__init__.py holds the five built-in platform detectors, the detection function that also runs the out-of-tree platform plugins, and the lazy module attribute current_platform.
  • How vLLM chooses an attention backendEach attention layer asks the selector for a backend class when the worker builds the model. The selector asks current_platform. CUDA validates a priority list for the GPU generation and takes the first valid backend; an explicit --attention-backend is validated alone.
  • CustomOp, out-of-tree ops and IR op providersA CustomOp is a layer with one forward method per platform. It picks one method when it is built - forward_native when disabled, the platform's method when enabled. Plugins replace whole classes with register_oot, and vllm.ir adds a second, per-op provider choice.
