entrypoints/cli/serve.py: the vllm serve subcommand and its launch modes

IntermediateCode mapabout 8 min read + 3 min deep dives

Purpose#

vllm/entrypoints/cli/serve.py turns vllm serve ... into running processes: it decides how many API servers to start and which function starts them.

Filevllm/entrypoints/cli/serve.py, 407 lines of Python. One class and three functions.
Main classServeSubcommand(CLISubcommand) (vllm/entrypoints/cli/serve.py:48-174).
Main functionscmd_init (vllm/entrypoints/cli/serve.py:177-178), run_headless (vllm/entrypoints/cli/serve.py:181-266), run_multi_api_server (vllm/entrypoints/cli/serve.py:269-407).
Runs inThe CLI process, the first process of vllm serve, on the main thread. With one API server, this process then becomes the API server.
Called byvllm/entrypoints/cli/main.py: it collects the subcommands, parses sys.argv, validates and dispatches (vllm/entrypoints/cli/main.py:100-117).
Callsmake_arg_parser, validate_parsed_serve_args, run_server, run_dp_supervisor, serve_grpc, CoreEngineProcManager, launch_core_engines, APIServerProcessManager, RustFrontendProcessManager, wait_for_completion_or_failure.
Not in this fileThe flags themselves (FrontendArgs and EngineArgs), the HTTP server (launchers/api_server/entry.py, launchers/launcher.py), the engine start (v1/engine/utils.py), the API server processes (v1/utils.py).

The page The OpenAI-compatible server: launch modes, app, serving classes and streaming explains what each launch mode serves. This page reads the file line by line.

Where it sits#

Who calls it#

  • cli/main.py imports this module at start-up (vllm/entrypoints/cli/main.py:43-51) and calls cmd_init() for the subcommand object (vllm/entrypoints/cli/main.py:100-109).
  • subparser_init is called for every vllm command, not only for serve, because all subparsers are built before parsing (same lines). Building the serve parser loads the general plugins, through make_arg_parser and AsyncEngineArgs.add_cli_args (How vLLM finds and loads plugins).
  • After parsing, main calls validate(args) and then args.dispatch_function(args), which is ServeSubcommand.cmd (vllm/entrypoints/cli/main.py:111-117).

What it calls#

  • make_arg_parser: the positional model_tag, --headless, --api-server-count, --config, --grpc, then all FrontendArgs and AsyncEngineArgs flags (vllm/entrypoints/common/cli_args.py:422-468).
  • validate_parsed_serve_args: early checks that need no model (vllm/entrypoints/common/cli_args.py:503-549).
  • One of the five starters, by mode (vllm/entrypoints/cli/serve.py:147-156).

Walk through the main methods#

cmd, part 1: model, gRPC, headless#

  1. Lines 56-57. The positional model (vllm serve MODEL) wins over --model.
  2. Lines 59-63. --grpc runs the gRPC server and returns; none of the checks below apply to it.
  3. Lines 65-67. The Rust frontend path is set only when VLLM_USE_RUST_FRONTEND is on.
  4. Lines 69-77. --headless forces the API server count to 0; an explicit positive count with it raises ValueError.

cmd, part 2: the data-parallel load-balancing mode#

  1. Lines 83-85. External load balancing: --data-parallel-external-lb, or any --data-parallel-rank.
  2. Lines 90-97. Hybrid load balancing: --data-parallel-hybrid-lb, or --data-parallel-start-rank when neither hybrid nor multi-port is set.
  3. Lines 99-105. Two modes at once raise ValueError.

cmd, part 3: the API server count and the dispatch#

  1. Lines 114-115. Multi-port, external load balancing and the Rust frontend default to 1 API server.
  2. Lines 116-117. Hybrid: the local DP size.
  3. Lines 124-125. Otherwise (internal load balancing, the normal case): the full DP size. So -dp 4 on one node gives 4 API servers.
  4. Lines 131-136. The Rust frontend ignores an explicit count above 1, with a warning.
  5. Lines 139-145. Elastic EP caps the count at 1.
  6. Lines 147-156. The dispatch. Only the last branch keeps the server in this process; it sets the count back to None first.

run_headless#

  1. Lines 185-186. A reasoning parser plugin is imported here, because the engine cores need the reasoning parser for structured outputs (Structured outputs: JSON schemas, grammars and token bitmasks in vLLM).
  2. Lines 189-194. The config is made with headless=True and the API server usage context.
  3. Lines 202-203. A node with no local DP ranks cannot run headless.
  4. Lines 218-233. On a secondary node of one DP rank (multi-node TP or PP), this process starts only the workers of its node, through MultiprocExecutor, and blocks in the worker monitor.

Otherwise it starts the local engine cores with CoreEngineProcManager, which connect to the head node's handshake address, and waits on their liveness (vllm/entrypoints/cli/serve.py:235-266). SIGTERM and SIGINT raise SystemExit once, and the shutdown then waits up to shutdown_timeout seconds (lines 205-216 and 260-266).

run_multi_api_server#

  1. Lines 282-283. More than one API server needs Prometheus multiprocess mode; a temporary directory is made unless the user set PROMETHEUS_MULTIPROC_DIR (vllm/v1/metrics/prometheus.py:17-36).
  2. Line 298. One listen socket, with SO_REUSEPORT when there are several servers (vllm/entrypoints/launchers/launcher.py:340-355).
  3. Lines 307-310. The engine config records the API process count; rank -1 marks the parent.
  4. Line 313. The VllmConfig is made here, in the supervisor, once.
  5. Lines 315-318. Runtime LoRA updates are refused with several API servers.
  1. Line 333. One input and one output ZMQ listener per API server, bound here.
  2. Lines 336-338. launch_core_engines is a context manager: it starts the engine cores (and the DP coordinator if needed) on entry, and waits for their handshake on exit (vllm/v1/engine/utils.py:1384-1395).
  3. Line 354 / lines 368-377. Inside the block, the Rust frontend or the Python API servers start. So the API servers start while the engines load.
  4. Line 382. If an API server dies during the engine start-up, the start-up is aborted.
  5. Lines 386-390. The supervisor waits; any child that exits with a non-zero code raises RuntimeError (vllm/v1/utils.py:575-594).

The finally block shuts down the API servers, then the engines, then the coordinator, all within one shutdown_timeout deadline after a signal (vllm/entrypoints/cli/serve.py:391-407).

Deep dive

Worked example: vllm serve M -dp 2 on one node

A dense model, one node, two GPUs, -dp 2, no other DP flags.

  1. cmd: no gRPC, no Rust, not headless. is_external_lb, is_hybrid_lb and is_multi_port are all false (lines 83-97).
  2. api_server_count is None, so it becomes the DP size, 2, and the log says "Defaulting api_server_count to data_parallel_size (2)." (lines 124-130).
  3. 2 > 1, so run_multi_api_server runs (line 152).
  4. The supervisor makes the Prometheus directory, binds port 8000 with SO_REUSEPORT, and builds the VllmConfig with _api_process_count = 2 (lines 282-313).
  5. bind_engine_zmq_listeners(vllm_config, 2) binds two input and two output listeners (line 333).
  6. launch_core_engines starts 2 engine core processes and, because this is internal load balancing, the DP coordinator (vllm/v1/engine/utils.py:1226-1232). Each engine core starts one worker process (TP = 1 with DP > 1).
  7. APIServerProcessManager spawns ApiServer_0 and ApiServer_1, each with its listener pair and client_index 0 or 1 (vllm/v1/utils.py:230-254).
  8. On leaving the with block, the supervisor waits for both engines' ready messages, while it watches the two API server processes (line 382).
  9. Each API server builds its own AsyncLLM, which connects to both engines, and then serves HTTP.

Result: 8 processes: the supervisor, 2 API servers, the DP coordinator, 2 engine cores and 2 workers. This matches the count in The process and thread architecture of vllm serve.

Check yourself#

  1. 1
    With vllm serve M and no DP flags, where does the HTTP server run?
    easy
    Show answer

    In the CLI process itself: api_server_count defaults to the DP size, 1, so the last branch runs uvloop.run(run_server(args)) (vllm/entrypoints/cli/serve.py:124-125, vllm/entrypoints/cli/serve.py:153-156).

  2. 2
    What is the default number of API servers for -dp 4 --data-parallel-external-lb, and why?
    medium
    Show answer

    1. With an external load balancer, each vllm serve serves its own rank, so the default is one API server (vllm/entrypoints/cli/serve.py:83-85, vllm/entrypoints/cli/serve.py:114-115).

  3. 3
    In run_multi_api_server, do the API server processes start before or after the engines are ready?
    medium
    Show answer

    Before. They start inside the with launch_core_engines(...) block, and the wait for the engines' ready messages runs when the block exits (vllm/entrypoints/cli/serve.py:336-382, vllm/v1/engine/utils.py:1384-1395).

  4. 4
    On a second node you run vllm serve M --headless --data-parallel-size 4 --data-parallel-size-local 2 --data-parallel-start-rank 2 --data-parallel-address HEAD (TP = 1). What does this process start, and what does it not start?
    hard
    Show answer

    --headless sets the API server count to 0 before the load-balancing checks, so the dispatch runs run_headless (vllm/entrypoints/cli/serve.py:69-77, vllm/entrypoints/cli/serve.py:149-150). The start rank makes the local variable is_hybrid_lb true, but the count is already set, and run_headless checks only the explicit --data-parallel-hybrid-lb flag (vllm/entrypoints/cli/serve.py:90-94, vllm/entrypoints/cli/serve.py:196-197). With TP = 1 this node is the first node of its DP ranks, so it starts the two local engine cores with CoreEngineProcManager; they connect to the head's handshake address (vllm/entrypoints/cli/serve.py:235-256). It starts no API server and opens no HTTP socket.
