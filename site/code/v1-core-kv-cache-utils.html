Purpose#

vllm/v1/core/kv_cache_utils.py is the toolbox under the block pool and the single-type managers. It holds data types, the hash chain, and small helpers for the start-up of the engine core.

Filevllm/v1/core/kv_cache_utils.py, 1,217 lines of Python. Four classes and 28 top-level functions.
Main classesKVCacheBlock (vllm/v1/core/kv_cache_utils.py:161-224), FreeKVCacheBlockQueue (vllm/v1/core/kv_cache_utils.py:258-519), BlockHashListWithBlockSize (vllm/v1/core/kv_cache_utils.py:1111-1181), KVCacheBlockCopy (vllm/v1/core/kv_cache_utils.py:253-255).
Runs inThe EngineCore process. The request hasher runs on its input thread when a request arrives, and on the main thread when tokens are appended. Some KV connectors also call the block-size helpers in the workers. CPU only.
Called byEngineCore at start-up, Request, BlockPool, the single-type managers, KVCacheManager, the scheduler, and many KV connectors (29 files in vllm/ import it).
CallsThe xxhash functions of vllm/utils/hashing.py (only to tell them apart), get_mm_features_in_window, KVCacheSpecRegistry and the spec classes of kv_cache_interface.py (vllm/v1/core/kv_cache_utils.py:21-37).
Not in this fileThe hash functions themselves (vllm/utils/hashing.py), the block pool and the hash map (block_pool.py), the hit search (single-type managers), the grouping and memory planning (kv_cache_planning.py).

Where it sits#

Who calls it#

  • EngineCore resolves the block sizes, makes the hasher, and logs the capacity (vllm/v1/engine/core.py:57-65, vllm/v1/engine/core.py:173-175, vllm/v1/engine/core.py:216-225, vllm/v1/engine/core.py:324-354).
  • Request calls the hasher in its constructor and after each new token (vllm/v1/request.py:225-230, vllm/v1/request.py:285-288).
  • BlockPool makes all KVCacheBlocks and the free queue, and uses the hash-key helpers (vllm/v1/core/block_pool.py:16-29, vllm/v1/core/block_pool.py:172-178).
  • The single-type managers use resolve_block_hashes, BlockHashListWithBlockSize and trim_null_head (vllm/v1/core/single_type_kv_cache_manager.py:13-20).
  • The workers use KVCacheBlockCopy for copy-on-write (vllm/v1/worker/utils.py:30). A P2P offload tier reads the NONE_HASH seed (vllm/v1/kv_offload/tiering/p2p/manager.py:714).

What it calls#

  • xxhash and xxhash_cbor, only to know which hash functions are not cryptographic (vllm/v1/core/kv_cache_utils.py:110-111).
  • get_mm_features_in_window to find the first image that touches a block (vllm/v1/core/kv_cache_utils.py:976-983).
  • KVCacheSpecRegistry.get_manager_class to check if every group supports fine-grained hits (vllm/v1/core/kv_cache_utils.py:936-942).
  • envs.VLLM_KV_EVENTS_USE_INT_BLOCK_HASHES for the hash format of KV events (vllm/v1/core/kv_cache_utils.py:82-85).

Walk through the main methods#

KVCacheBlock: one record per block#

  1. Line 161. slots=True: no __dict__ per block. A large GPU has tens of thousands of these objects.
  2. Lines 166-168. The id indexes the KV tensors of every worker. ref_cnt counts the requests that hold the block.
  3. Lines 170-172. The pool of the block. A deferred free can hold blocks of two pools (the GPU pool and a HiSparse host pool).
  4. Lines 175-178. The hash key, set only when the block is cached. _block_hash_num_tokens is the prefix length that the key covers. It can end inside a block for fine-grained (partial) entries.
  5. Lines 182-183. The two links of the free queue. Only FreeKVCacheBlockQueue changes them.
  6. Line 186. is_null marks block 0, the null block.
  7. Lines 201-203. A second hash on the same block is a bug, so the method asserts. BlockPool calls reset_hash() first on eviction.

FreeKVCacheBlockQueue: O(1) remove from the middle#

A Python deque cannot remove an element from the middle in O(1). A prefix-cache hit on a free block must do exactly that. So the queue links the blocks themselves, with two fake ends that are never popped:

  1. Lines 285-289. At start-up the queue links the blocks in id order: block 0, 1, 2, ...
  2. Lines 297-305. Fake head and tail blocks with id −1. Every real block in the queue then has a previous and a next block, so no method needs a special case for the ends.
  3. Lines 400-403. remove() on a block that is not in the queue raises RuntimeError: a caller bug.
  4. Lines 406-412. Two pointer changes and a counter: O(1). BlockPool.touch() uses it for hits (vllm/v1/core/block_pool.py:766-767).

popleft_n() takes n blocks from the front, prepend_n() puts blocks at the front, and append_n() at the back (vllm/v1/core/kv_cache_utils.py:347-389, vllm/v1/core/kv_cache_utils.py:438-484). None of them makes a Python object; they only change the links (docstring, vllm/v1/core/kv_cache_utils.py:258-279).

get_request_block_hasher: the chain for one request#

The engine core makes the closure once (vllm/v1/engine/core.py:223-225). The basics page reads it line by line (Prefix caching: the idea, deep dive "The hash chain in the code"). The key points:

It starts after the last existing hash and stops before a block that is not full (vllm/v1/core/kv_cache_utils.py:988-993). It returns only the new hashes; Request.update_block_hashes() appends them (vllm/v1/request.py:285-288).

resolve_kv_cache_block_sizes: three sizes for several groups#

  1. Lines 840-858. One group: both sizes are the block size (times the decode context parallel size when the cache is sharded). Another prefix_match_unit raises ValueError when hashing is active.
  2. Lines 860-863. Several groups: the scheduler works in units of the least common multiple of the group block sizes.
  3. Lines 871-873. No prefix caching and no connector: nobody reads the hashes, so the hash size equals the scheduler size.

Otherwise the hash size is prefix_match_unit, or the greatest common divisor of the prefix-cacheable group sizes. Every such group size must divide by it (vllm/v1/core/kv_cache_utils.py:885-898). The engine core passes both sizes to the scheduler (vllm/v1/engine/core.py:173-185).

BlockHashListWithBlockSize: coarse hashes for free#

Each fine hash already names its whole prefix. So the hash of a 32-token block is simply the second 16-token hash:

The view computes nothing ahead of time; it reads one list element per access.

Worked example: the free queue at start-up and after one request

A pool of 6 blocks (ids 0-5), prefix caching on. (Derived from the methods above and vllm/v1/core/block_pool.py:172-188.)

  1. FreeKVCacheBlockQueue([b0..b5]): head ⇄ 0 ⇄ 1 ⇄ 2 ⇄ 3 ⇄ 4 ⇄ 5 ⇄ tail, num_free_blocks = 6.
  2. The pool pops block 0 as the null block: head ⇄ 1 ⇄ 2 ⇄ 3 ⇄ 4 ⇄ 5 ⇄ tail, 5 free.
  3. A request of 40 tokens with block size 16 takes 3 blocks with popleft_n(3): blocks 1, 2, 3. Queue: 4 ⇄ 5. The links of 1, 2 and 3 are None.
  4. Blocks 1 and 2 are full and get hashes; block 3 has 8 tokens.
  5. The request ends. The pool frees [3, 2, 1]: prepend_n([3]), then append_n([2, 1]). Queue: 3 ⇄ 4 ⇄ 5 ⇄ 2 ⇄ 1.
  6. A new request hits h0: remove(block 1) links 2 to the tail. Queue: 3 ⇄ 4 ⇄ 5 ⇄ 2.
Deep dive

Worked example: block sizes for two groups

Assume a hybrid model with a full-attention group of block size 16 and a sliding-window group of block size 32. Prefix caching is on, there is no decode context parallelism, and --prefix-match-unit is unset. (Derived from vllm/v1/core/kv_cache_utils.py:860-918.)

  1. group_block_sizes = [16, 32], so scheduler_block_size = lcm(16, 32) = 32.
  2. Both groups are prefix-cacheable: hash_block_size = gcd(16, 32) = 16. 16 and 32 both divide by 16, so no error.
  3. The request hasher makes one hash per 16 tokens. The sliding-window group reads them through BlockHashListWithBlockSize(scale_factor=2): its hash i is fine hash 2i + 1.
  4. The log shows "kv cache group sizes (16, 32)" and "kv lcm block sizes 32" (vllm/v1/core/kv_cache_utils.py:865-866).

Check yourself#

  1. 1
    Why does vLLM implement its own linked list instead of using collections.deque for free blocks?
    easy
    Show answer

    A prefix-cache hit must take a block out of the middle of the free queue. The linked list does this in O(1), a deque does not (vllm/v1/core/kv_cache_utils.py:258-266, vllm/v1/core/kv_cache_utils.py:391-412).

  2. 2
    How many bytes is one key of the prefix-cache map with the default hash algorithm, and what are its parts?
    medium
    Show answer

    36 bytes: the 32-byte SHA-256 digest of the block plus the KV cache group id as 4 big-endian bytes (vllm/v1/core/kv_cache_utils.py:60-69, vllm/utils/hashing.py:40-41).

  3. 3
    A request has 47 tokens and 2 hashes (block size 16). It gets one more token. What does the hasher return?
    medium
    Show answer

    One new hash. It starts at 2 × 16 = 32 tokens; 32 + 16 = 48 ≤ 48, so block 2 is full now (vllm/v1/core/kv_cache_utils.py:967-972, vllm/v1/core/kv_cache_utils.py:989-1008). The request appends it to block_hashes (vllm/v1/request.py:285-288).

  4. 4
    Look at the deep dive "Worked example: block sizes for two groups". Why is the hash of sliding-window block 1 the fine hash 3, not a new hash of tokens 32-63?
    hard
    Show answer

    Each fine hash chains over its whole prefix, so fine hash 3 (tokens 48-63) already names tokens 0-63. That is exactly the prefix of sliding-window block 1. The view returns block_hashes[(idx + 1) × scale_factor − 1] = block_hashes[3] (vllm/v1/core/kv_cache_utils.py:1178-1181).

Related pages

  • Prefix caching in the engine core: hashes, lookup, caching, eviction and KV eventsThe mechanics of prefix caching in the engine core. The input thread hashes each new request, the scheduler looks the hashes up in the block pool and touches the hits, allocate_slots hashes blocks that become full, and the free queue decides what to evict. KV events tell an external router what each engine holds.
  • The hybrid KV cache: specs, groups and one manager per layer typeModels that mix full attention with sliding-window, chunked-local or Mamba layers get one KV cache group per layer type. Each group has its own block table and single-type manager, all groups share one block pool, and so every group must use the same page size. Prefix caching finds one hit length that is valid for all groups.
  • The KV cache manager: blocks, the block pool and memory sizingIn the engine core, the KVCacheManager hands out KV blocks to the scheduler through a coordinator, one single-type manager per KV cache group and one BlockPool. The workers only receive block ids. The number of blocks comes from a memory profile at start-up.
  • Prefix caching: the ideaChat requests often start with the same tokens. Prefix caching keeps the KV cache blocks of earlier requests under a chain of hashes, so a new request with the same prefix skips the prefill of those blocks and gets a shorter TTFT.
  • v1/core/block_pool.py: BlockPool and the prefix-cache mapvllm/v1/core/block_pool.py holds BlockPool, the owner of every KVCacheBlock of an engine core. It hands out blocks from the free queue, frees them in eviction order, keeps the hash-to-block map of the prefix cache, emits KV cache events and computes the KV cache usage.
  • v1/core/kv_cache_manager.py: KVCacheManager and KVCacheBlocksvllm/v1/core/kv_cache_manager.py is the KV cache API of the scheduler. KVCacheManager looks up prefix-cache hits, allocates slots, caches full blocks, frees requests and reports usage; KVCacheBlocks carries the result per KV cache group.
  • v1/engine/core.py: EngineCore and the engine core processvllm/v1/engine/core.py defines EngineCore (scheduler + executor + step functions), EngineCoreProc (the process with its ZMQ threads and busy loop) and DPEngineCoreProc (the lock-step variant for MoE data parallelism).
