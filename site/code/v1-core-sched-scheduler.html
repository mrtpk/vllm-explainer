v1/core/sched/scheduler.py: the Scheduler

Before you read

Purpose#

vllm/v1/core/sched/scheduler.py decides, once per engine step, which requests run and how many tokens each gets, and it applies the results of each step to the requests.

Filevllm/v1/core/sched/scheduler.py, 3,539 lines of Python. One class, Scheduler (vllm/v1/core/sched/scheduler.py:85), with 64 methods.
Main classScheduler(SchedulerInterface). The default subclass for serving is AsyncScheduler in async_scheduler.py (vllm/v1/core/sched/async_scheduler.py:14).
Runs inThe EngineCore process, in its main thread (the busy loop). One scheduler per engine core, so one per data parallel rank. Pure Python on the CPU.
Called byEngineCore in vllm/v1/engine/core.py: schedule, update_from_output, add_request, finish_requests, get_grammar_bitmask, statistics.
CallsKVCacheManager, the request queues, EncoderCacheManager, StructuredOutputManager, the KV and EC connectors (scheduler side), check_stop, the KV event publisher.
Not in this filePlaceholders for async scheduling (async_scheduler.py), the queues (request_queue.py), check_stop (sched/utils.py), the output dataclasses (sched/output.py), all block logic (kv_cache_manager.py and below), the busy loop (core.py).

The page The V1 scheduler: one token budget, no phases explains the algorithm with figures and a simulator. This page is a map of the file and a line-by-line reading of its two main methods.

Who calls it#

  • Every step. step_with_batch_queue (the default) and step call schedule(), get_grammar_bitmask() and update_from_output() (vllm/v1/engine/core.py:725, vllm/v1/engine/core.py:740-742, vllm/v1/engine/core.py:783; vllm/v1/engine/core.py:667-681).
  • New requests and aborts. EngineCore.add_request and abort_requests (vllm/v1/engine/core.py:548, vllm/v1/engine/core.py:554-559).
  • Speculative decoding. update_draft_token_ids and update_draft_token_ids_in_output (vllm/v1/engine/core.py:696, vllm/v1/engine/core.py:801).
  • Load reporting. get_request_counts and get_kv_cache_usage for the DP coordinator (vllm/v1/engine/core.py:1627-1631).
  • Utilities. reset_prefix_cache (vllm/v1/engine/core.py:874).

The interface of all these methods is the abstract class SchedulerInterface (vllm/v1/core/sched/interface.py:38). A custom class from --scheduler-cls must implement it (Hooks in the engine core and the workers).

Walk through the main methods#

__init__: the limits#

  1. Line 130. max_num_running_reqs is max_num_seqs. The end of schedule() asserts it (vllm/v1/core/sched/scheduler.py:1496).
  2. Lines 133-137. max_num_active_reqs: the admission limit of the waiting pass.
  3. Lines 138-142. The token budget. See the real defaults on The V1 scheduler: one token budget, no phases.
  4. Lines 153-160. Generative models keep one slot for the sampled token; pooling and diffusion models do not.

The rest of __init__ builds the queues (vllm/v1/core/sched/scheduler.py:216-232) and the KVCacheManager (vllm/v1/core/sched/scheduler.py:329-347). It raises ValueError for an unknown policy (vllm/v1/core/sched/scheduler.py:217-222).

schedule: an overview#

The method is about 1,000 lines. The deep dive below reads it in parts. In short:

  1. Set the two budgets: token_budget and input_budget (vllm/v1/core/sched/scheduler.py:642-648).
  2. Running pass: tokens, blocks, preemption (vllm/v1/core/sched/scheduler.py:713-943).
  3. Waiting pass, only without preemption (vllm/v1/core/sched/scheduler.py:956-1479).
  4. Checks, the SchedulerOutput, connector metadata (vllm/v1/core/sched/scheduler.py:1481-1634).
  5. _update_after_schedule (vllm/v1/core/sched/scheduler.py:1641-1643).

_update_after_schedule: the counters move#

  1. Lines 1704-1712. The comment gives the reason for the order: the output must carry the old counts, and the counters move now so that a prefill can continue in the next step at once.
  2. Lines 1716-1717. num_computed_tokens moves forward optimistically; num_in_flight_tokens remembers what is not confirmed.
  3. Lines 1721-1723. A prefill chunk is a request that still misses tokens after this step.
  4. Lines 1734-1735. New sets, not clear(): the output that just left still points to the old sets.

update_from_output: an overview#

For each request in num_scheduled_tokens, the method:

  1. skips requests that finished during the step (for example, aborted) (vllm/v1/core/sched/scheduler.py:2184-2192);
  2. rolls back rejected draft tokens (vllm/v1/core/sched/scheduler.py:2203-2221);
  3. appends the new tokens and checks for a stop (vllm/v1/core/sched/scheduler.py:2258-2262);
  4. lets the grammar accept the tokens (vllm/v1/core/sched/scheduler.py:2279-2290);
  5. frees stopped requests and makes an EngineCoreOutput when there is something to send (vllm/v1/core/sched/scheduler.py:2293-2295, vllm/v1/core/sched/scheduler.py:2316-2341).

After the loop it removes stopped requests from the queues, fails requests with errors, updates the connectors, publishes KV events and attaches the stats (vllm/v1/core/sched/scheduler.py:2388-2523).

_update_request_with_output: append and stop#

  1. Line 2599. Each token is appended alone; the request updates its block hashes (vllm/v1/request.py:272-283).
  2. Line 2603. check_stop runs after every token, so a stop in the middle of several accepted tokens is found (vllm/v1/core/sched/utils.py:98-140).
  3. Lines 2607-2609. Tokens after the stop are cut, and num_computed_tokens drops by their number.

AsyncScheduler overrides this method: it removes the placeholders of the new tokens and caches the full blocks (vllm/v1/core/sched/async_scheduler.py:59-80).

add_request and finish_requests#

A new request goes into the waiting queue (or into kv_holding_waiting when it already holds blocks) and into the requests dict (vllm/v1/core/sched/scheduler.py:2556-2562). Its QUEUED event is recorded only when stats are on.

finish_requests handles aborts from outside. It removes the requests from all queues at once, sets the finished status, and frees them (vllm/v1/core/sched/scheduler.py:2776-2812). With None it finishes every request. A request that waits for a remote KV load may keep its blocks until the load ends (lines 2802-2807).

Deep dive#

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Deep dive

schedule(), part 1: setup and the running pass

  1. Lines 635-641. The lists and dicts that the method fills: new, resumed and running requests, preempted requests, new blocks and token counts per request.
  2. Lines 642-648. token_budget limits the scheduled tokens; input_budget limits the input rows, which include draft_slots per request: 1 for a separate draft model, more for parallel drafting, else 0 (vllm/config/speculative.py:1977-1995). A full pause sets the budget to 0.
  3. Lines 664-666. One monotonic timestamp for all SCHEDULED and PREEMPTED events of this call.
  4. Lines 670-672. Data parallel prefill throttling: on a throttled step, defer prefills while decodes run.
  5. Lines 677-689. The long-prefill cap is 0 when only one request exists, and the adaptive mode raises it to a fair share.
  1. Lines 715-718. The loop runs while budget is left, over self.running by index, because preemption shortens the list.
  2. Lines 720-734. Async scheduling: a request whose in-flight tokens already reach max_tokens gets no extra step.
  3. Lines 736-757. Three more skips: PP decode cadence, deferred prefill chunks, and encoder data that a connector has not delivered.
  4. Lines 759-777. The number of tokens and its caps.
  1. Lines 833-842. allocate_slots with the lookahead tokens of the drafter. Success leaves the loop.
  2. Lines 844-848. A KV connector may free blocks soon; then the scheduler does not preempt and gives up on this request for now.
  3. Lines 852-858. The victim: highest (priority, arrival_time), or the last running request.
  4. Lines 861-862. With deferred block freeing (a KV consumer with overlapping steps), a victim whose blocks cannot be freed yet does not help.
  5. Lines 864-888. Priority only: if the victim was already scheduled in this step, its tokens, blocks, drafts and encoder budget go back.
  6. Lines 892-900. Preempt; stop retrying when the victim is the request itself.
  7. Lines 902-904. Still no blocks: the running pass ends.
  8. Lines 906-914. Record the request and reduce both budgets.
Deep dive

schedule(), part 2: the waiting pass

Only a request with num_computed_tokens == 0 looks up the prefix cache. shared_prefix_boundary matters only for hybrid models. The connector part (lines 1026-1099) asks for an external hit, aligned to whole blocks, and decides whether the load is asynchronous.

  1. Lines 1171-1174. An asynchronous KV load schedules 0 tokens now.
  2. Lines 1175-1178. Deferred prefill on a throttled step stops the pass.
  3. Line 1191. num_tokens, not num_prompt_tokens: a resumed request recomputes its output tokens too.
  4. Lines 1196-1215. With speculative decoding, a 1-token request in a decode-only step is padded to 1 + num_spec_tokens rows, to keep a uniform batch.
  5. Lines 1222-1229. Chunked prefill off and too many tokens: stop the pass.
  1. Lines 1305-1315. An async load reserves the blocks that other in-flight prefills still need, so two loads cannot block each other.
  2. Lines 1320-1337. allocate_slots adopts the prefix hit and checks the whole sequence (full_sequence_must_fit).
  3. Lines 1339-1346. No blocks: stop the waiting pass, after a cleanup of the encoder cache.

Lines 1413-1467 move the request to the running queue (see The V1 scheduler: one token budget, no phases, Step 5). Lines 1469-1473 put skipped requests back at the front of their queues.

Deep dive

schedule(), part 3: checks and the output

  1. Line 1483. The sum of all scheduled tokens never exceeds the budget.
  2. Lines 1494-1502. Invariants: no negative budget, no more running requests than max_num_seqs.
  3. Lines 1505-1516. Model Runner V2: resumed requests travel as new requests, with all their token ids (req._all_token_ids) and block ids.

Lines 1527-1534 build CachedRequestData for running and resumed requests: the new block ids (or None), the computed tokens and the output count (vllm/v1/core/sched/scheduler.py:1780-1837). Lines 1561-1570 collect copy-on-write block copies of partial prefix hits. Lines 1588-1609 build the SchedulerOutput. Then the connectors add their metadata (1615-1631), and _update_after_schedule runs last (1641-1643).

Deep dive

update_from_output(), line by line

  1. Line 2175. The tokens of this step are no longer in flight.
  2. Lines 2176-2180. A request preempted after this step started gets "stale" output: it is delivered but does not change the counters.
  3. Lines 2181-2192. Skip failed KV loads and requests that finished meanwhile (an abort during the step).
  4. Line 2198. req_id_to_index maps the request to its row of the runner output.

Accepted drafts = sampled tokens − 1 (the bonus token). The rejected drafts roll back num_computed_tokens and the placeholders.

  1. Lines 2259-2262. Generation: append and check_stop.
  2. Lines 2263-2266. Pooling: the request stops as soon as it has output.
  3. Lines 2279-2290. If the grammar rejects a sampled token, the request ends with FINISHED_ERROR and an error log.
  4. Lines 2293-2295. Output only for new tokens, pooler output or a stop. A prefill chunk sends nothing.

The finish reason is read before _handle_stopped_request, because a streaming session can go back to waiting. A finished request is freed at once; its id goes into finished_req_ids for the next SchedulerOutput, so the workers drop its state (vllm/v1/core/sched/scheduler.py:2836).

The stopped requests leave the queues in one pass, which is cheaper than one removal per request. Then come errors (2399-2425), connector updates (2427-2467), KV events (2469-2484) and the result: one EngineCoreOutputs per front end (client_index), with the stats on only one of them (vllm/v1/core/sched/scheduler.py:2486-2523).

Check yourself#

  1. 1
    In which process and thread does Scheduler.schedule() run?
    easy
    Show answer

    In the engine core process, in its main thread, called by the step function of the busy loop (vllm/v1/engine/core.py:725). There is one scheduler per engine core.

  2. 2
    Why does _update_after_schedule run after the SchedulerOutput is built, and not before?
    medium
    Show answer

    The output must carry the counts from before the step, so that the worker knows which input ids and positions to use. The comment at vllm/v1/core/sched/scheduler.py:1704-1712 gives this reason. The call is the last line of schedule() (vllm/v1/core/sched/scheduler.py:1641-1643).

  3. 3
    A request samples 3 tokens in one step (2 accepted drafts and a bonus token). The second token is EOS. What does update_from_output send?
    medium
    Show answer

    Two tokens. _update_request_with_output runs check_stop after each token, finds EOS at the second, and cuts the list there (vllm/v1/core/sched/scheduler.py:2598-2610). The request is freed and the output carries finish_reason stop.

  4. 4
    With the priority policy, the victim of a preemption was already scheduled earlier in the same running pass. What does the scheduler undo?
    hard
    Show answer

    It removes the victim from scheduled_running_reqs, gives its tokens back to token_budget and input_budget (with the draft slots), drops its new blocks and draft tokens from the plan, and restores the encoder budget. It also moves req_index back when the victim was before the current request (vllm/v1/core/sched/scheduler.py:864-888). With FCFS this cannot happen, because the victim is the last request.

It has no prefill or decode phase, it preempts the last running request when KV blocks run out, and update_from_output() appends the sampled tokens.
