distributed/parallel_state.py: process groups and GroupCoordinator

AdvancedCode mapabout 9 min read + 3 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Process groups: how vLLM slices its ranks Advanced

Purpose#

vllm/distributed/parallel_state.py owns the process groups of a worker process: it creates them from the rank layout, keeps them in module globals such as _TP, and gives model code one object per group, the GroupCoordinator, with all collectives.

Filevllm/distributed/parallel_state.py, 2,767 lines of Python. The header says it is adapted from Megatron-LM (vllm/distributed/parallel_state.py:4-23).
Main classGroupCoordinator (vllm/distributed/parallel_state.py:427).
Main functionsinit_distributed_environment (vllm/distributed/parallel_state.py:1836), initialize_model_parallel (vllm/distributed/parallel_state.py:2078), ensure_model_parallel_initialized (vllm/distributed/parallel_state.py:2388), the getters get_tp_group … get_eplb_group, graph_capture, destroy_model_parallel, cleanup_dist_env_and_memory.
Runs inEach worker process (or the engine core process with the uni executor), main thread. The groups are per process.
Called byinit_worker_distributed_environment in the GPU worker (vllm/v1/worker/gpu_worker.py:1678-1720); model layers through vllm.distributed, which re-exports this module (vllm/distributed/__init__.py:4-6).
Callstorch.distributed (init_process_group, new_group, send/recv), the platform's device communicator class, MessageQueue from shm_broadcast.py, direct_register_custom_op.
Not in this fileThe all-reduce kernels and their selection (device_communicators/cuda_communicator.py and friends), the ring buffer (shm_broadcast.py), the MoE all2all managers (device_communicators/all2all.py), the stateless DP group of the engine core (config/parallel.py), the helpers tensor_model_parallel_all_reduce etc. (communication_op.py).

The page Process groups: how vLLM slices its ranks explains the ideas and the rank layout. This page reads the file function by function.

Where it sits#

Who calls it#

  • The GPU worker, in init_device, before the memory snapshot (vllm/v1/worker/gpu_worker.py:497-507). Its helper calls set_custom_all_reduce, init_distributed_environment and ensure_model_parallel_initialized in that order (vllm/v1/worker/gpu_worker.py:1694-1716).
  • Model layers call the getters at construction and the collectives at run time, for example RowParallelLinear through tensor_model_parallel_all_reduce (vllm/model_executor/layers/linear.py:1803-1806, vllm/distributed/communication_op.py:12-14).
  • Model Runner V2 wraps CUDA graph capture in graph_capture, and the worker uses the PP group for isend_tensor_dict/irecv_tensor_dict (vllm/v1/worker/gpu_worker.py:1336-1347).
  • Shutdown: the worker process calls destroy_model_parallel and destroy_distributed_environment (vllm/v1/executor/multiproc_executor.py:824-833); the engine core calls cleanup_dist_env_and_memory (vllm/v1/engine/core.py:837-839).

What it calls#

  • torch.distributed.init_process_group for the world, then new_group twice per group: device backend and gloo (vllm/distributed/parallel_state.py:1973-1982, vllm/distributed/parallel_state.py:501-518).
  • current_platform.get_device_communicator_cls(), only for groups with more than one rank (vllm/distributed/parallel_state.py:549-560).
  • MessageQueue.create_from_process_group for the groups that ask for a broadcaster (vllm/distributed/parallel_state.py:562-567).
  • direct_register_custom_op for all_reduce, reduce_scatter, all_gather and a patched scaled-matmul reduce-scatter, at import time (vllm/distributed/parallel_state.py:399-425).

Walk through the main methods#

GroupCoordinator.__init__: two PyTorch groups per row#

  1. Lines 498-499. Optional timeouts for the device and CPU groups (from --distributed-timeout-seconds and its CPU twin).
  2. Lines 501-512. For every row of group_ranks, the process makes a device group and a gloo group. new_group is collective, so all ranks must make all rows in the same order, even rows they are not in.
  3. Lines 513-518. The process keeps the pair for its own row, and records its rank inside the group.

The class comment shows the difference between rank, local_rank and rank_in_group with a 4-rank group over two nodes (vllm/distributed/parallel_state.py:436-449). With VLLM_DISTRIBUTED_USE_SPLIT_GROUP=1, the groups come from PyTorch split_group instead (vllm/distributed/parallel_state.py:480-491). The rest of the constructor picks the device, then adds the optional parts:

  1. Lines 549-559. A device communicator only for more than one rank. use_all2all is passed through; the communicator honours it only for groups named ep (vllm/distributed/device_communicators/base_device_communicator.py:244-245).
  2. Lines 563-567. The broadcaster: a MessageQueue of 6 chunks × 4 MiB, writer = the group's first rank.
  3. Lines 571-573. use_custom_op_call decides whether the collectives go through torch.ops.vllm.*.

all_reduce and friends#

  1. Lines 740-741. A group of one returns the input; no kernel runs.
  2. Lines 743-746. The registered op takes the group's unique name (a string), because Dynamo cannot pass the Python object. The op body looks the group up in _groups (vllm/distributed/parallel_state.py:199-204).
  3. Lines 748-751. The real work is in the device communicator; without one this raises "No device communicator found".

all_gather and reduce_scatter follow the same pattern and check the dim argument (vllm/distributed/parallel_state.py:753-798). gather, all_gatherv and reduce_scatterv go straight to the communicator (vllm/distributed/parallel_state.py:774-838). broadcast uses torch.distributed.broadcast on the device group (vllm/distributed/parallel_state.py:840-853); broadcast_object prefers the shared-memory broadcaster (vllm/distributed/parallel_state.py:855-877).

isend_tensor_dict and irecv_tensor_dict: the PP hand-off#

  1. Line 1211. Clean up finished earlier sends before posting new ones.
  2. Line 1212. The metadata (keys, dtypes, shapes, plain values) goes first, pickled on the gloo group by isend_object.
  3. Lines 1219-1222. The all-gather trick: with all_gather_group (the TP group), each TP rank sends only its 1/TP slice; the receiver rebuilds the full tensor with an all-gather.
  4. Lines 1224-1229. Each tensor goes by isend on the device group (CPU tensors on gloo). record_stream keeps the CUDA memory alive until the send finishes.
  5. Lines 1240-1243. The handles are also kept in _pending_isends, so a caller may drop them safely.

The receiver posts irecv for each tensor and returns post-processing callbacks for the all-gather case (vllm/distributed/parallel_state.py:1285-1369). The worker uses exactly this pair with all_gather_group=get_tp_group() (vllm/v1/worker/gpu_worker.py:1336-1347, vllm/v1/worker/gpu_worker.py:1372-1378).

init_distributed_environment#

  1. Lines 1857-1865. The DP/multi-node branch runs only with a config, no external launcher, no elastic EP, and DP > 1 or several nodes. A dense model's engine reset its DP size to 1, so it never enters for DP.
  2. Lines 1869-1871. Shift the rank by dp_rank × world_size and widen the world to all DP ranks.

Then the default process group starts, with a gloo fallback when the backend is not available (vllm/distributed/parallel_state.py:1927-1982), and the world GroupCoordinator is made once. When one DP replica spans several nodes and DP > 1, an extra inner_dp_world group with a broadcaster is made for the executor's cross-node queue; with DP = 1 the name points to the world group (vllm/distributed/parallel_state.py:2022-2038).

initialize_model_parallel#

Every group comes from this one tensor: TP with view(-1, TP), PP with transpose(2, 4), DP with transpose(1, 4), PCP with transpose(3, 4), and EP (MoE only) with transpose(1, 2) into rows of DP × PCP × TP (vllm/distributed/parallel_state.py:2256-2345). With elastic EP, TP/PP/PCP use a local grid and DP/EP/EPLB become stateless groups (vllm/distributed/parallel_state.py:2122-2140, vllm/distributed/parallel_state.py:2297-2305). The function ends with one INFO log line per rank, logged once (vllm/distributed/parallel_state.py:2372-2385).

Tear-down#

destroy_model_parallel destroys the groups in the order ETP, TP, Engram DP, DCP, PCP, PP, DP, EP, EPLB (vllm/distributed/parallel_state.py:2480-2525). Each GroupCoordinator.destroy first destroys its device communicator, because communicator workspaces may need the groups for their own tear-down (vllm/distributed/parallel_state.py:1400-1413).

Worked example: what one TP = 2 worker builds

vllm serve meta-llama/Llama-3.1-8B-Instruct -tp 2, worker rank 1 (derived from the code above):

  1. init_distributed_environment(world_size=2, rank=1, "file:///tmp/vllm_dist_…", local_rank=1, "nccl"): no DP branch; default PG of 2 ranks; _WORLD = ranks [0, 1], no device communicator; _NODE_COUNT = 1.
  2. all_ranks = arange(2).reshape(1, 1, 1, 1, 2).
  3. _TP = [0, 1] (tp:0), with a CudaCommunicator and a 6 × 4 MiB MessageQueue. _ETP is the same object.
  4. _DCP, _PCP, _PP, _DP: two groups of one rank each ([0] and [1]), so this rank's object has no communicator and no broadcaster.
  5. _EP, _EPLB: None, because Llama is not an MoE model.
  6. The log: "rank 1 in world size 2 is assigned as DP rank 0, PP rank 0, PCP rank 0, TP rank 1, ETP rank 1, EP rank N/A, EPLB rank N/A".

Every new_group call above makes two PyTorch groups (NCCL and gloo), and each rank takes part in both rows of each size-1 group kind. That is 2 + 2 + 4 × 4 = 20 new_group calls for this worker: world and TP have 1 row each, DCP, PCP, PP and DP have 2 rows each, and each row needs two calls. The communicators then do their own setup (derived from lines 501-518 and the group list).

Check yourself#

  1. 1
    What does GroupCoordinator.all_reduce do in a group of one rank?
    easy
    Show answer

    It returns the input tensor; no kernel runs (vllm/distributed/parallel_state.py:739-741).

  2. 2
    Why must every rank call torch.distributed.new_group for every row, even rows it does not belong to?
    medium
    Show answer

    new_group is a collective call in PyTorch. The constructor loops over all rows of group_ranks and keeps only its own pair (vllm/distributed/parallel_state.py:501-518).

  3. 3
    A PP stage sends a hidden_states tensor of [2048, 4096] BF16 with TP = 4. How many bytes does each TP rank send for it, and how does the receiver get the full tensor?
    medium
    Show answer

    The size divides by 4, so each rank sends its 1/4 slice: 2048 × 4096 × 2 / 4 = 4 MiB (vllm/distributed/parallel_state.py:1068-1080, vllm/distributed/parallel_state.py:1219-1222). The receiver posts an irecv into its slice and runs an all-gather on the TP group in a post-processing callback (vllm/distributed/parallel_state.py:1332-1355).

  4. 4
    In the TP = 2 example of the deep dive, which groups of worker 1 have a device communicator, and why does the PP group have none?
    hard
    Show answer

    Only the TP group (and ETP, the same object). The PP, DP, PCP and DCP groups of this rank have one rank each, and the constructor makes a communicator only when world_size > 1 (vllm/distributed/parallel_state.py:549). The world group is built with use_device_communicator=False (vllm/distributed/parallel_state.py:1507-1516).

Related pages

  • Process groups: how vLLM slices its ranksEach worker puts all ranks into one grid of shape (DP, PP, PCP, TP) and cuts it into process groups. Each group is a GroupCoordinator with a gloo CPU group, an NCCL device group and, for groups of more than one rank, a device communicator that picks the all-reduce implementation.
  • The tensor-parallel layers (linear.py and vocab_parallel_embedding.py)vLLM's linear and embedding layers know their tensor-parallel rank. They resolve a quantization method per layer, allocate only their slice, cut checkpoint tensors when they load, and call the all-reduce or all-gather in forward. QKVParallelLinear splits by heads and copies KV heads when TP is larger than their count.
  • Expert parallelism and MoE servingAn MoE layer in vLLM is an MoERunner built by FusedMoEFactory. Its kernel has two exchangeable parts - a prepare/finalize object that dispatches and combines tokens, and an experts object that runs the GEMMs. With --enable-expert-parallel the experts are split over all DP x TP ranks; EPLB moves busy experts, DBO overlaps the communication.
  • Data parallel serving: several engine cores behind one endpointWith --data-parallel-size N, vllm serve runs N engine cores with their own KV caches. API servers pick an engine for each request with a load score; a DP coordinator publishes the load counts. Dense models run independent engines; MoE models step in lockstep, in waves, with dummy batches.
  • distributed/device_communicators/shm_broadcast.py: MessageQueuevllm/distributed/device_communicators/shm_broadcast.py implements MessageQueue, a one-writer, many-reader queue. Local readers share a lock-free ring of chunks in /dev/shm with one flag byte per reader; large messages and remote readers use ZMQ XPUB sockets. The executor uses it to send every call to its workers, and each worker uses one to reply.
  • v1/worker/gpu_worker.py: the GPU Workervllm/v1/worker/gpu_worker.py defines Worker, the object that owns one GPU. It sets up the device and NCCL, builds Model Runner V2, profiles memory to size the KV cache, warms up the model, and forwards each step to the model runner.
  • v1/executor/multiproc_executor.py: MultiprocExecutor and WorkerProcvllm/v1/executor/multiproc_executor.py starts one worker process per local GPU, broadcasts every call to them through a shared-memory MessageQueue, reads the reply of one output rank, and watches the processes for failures.
  • Tour: One step across GPUsFollow two requests through vllm serve -tp 2 -dp 2 in 13 stops: the API servers pick an engine each, two independent engine cores schedule, each broadcasts the step to its two workers through shared memory, the workers meet in 65 all-reduces on their TP group, only rank 0 replies, and the coordinator publishes the new load.
