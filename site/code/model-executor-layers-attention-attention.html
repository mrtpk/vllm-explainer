"model_executor/layers/attention/attention.py: the Attention layer and its custom ops"

Purpose#

vllm/model_executor/layers/attention/attention.py is the bridge between a model file and an attention backend: the model calls Attention, and this file finds the per-step data and calls the backend's impl.

Filevllm/model_executor/layers/attention/attention.py, 803 lines.
Main classAttention(nn.Module, AttentionLayerBase) (vllm/model_executor/layers/attention/attention.py:229-239).
Runs inEach worker. The constructor runs once at model build; forward and the ops run in every eager or PIECEWISE step, between the compiled pieces.
Called byModel files, for example LlamaAttention (vllm/model_executor/models/llama.py:212-222); subclasses such as EncoderOnlyAttention; Model Runner V2 for the KV cache spec through get_kv_cache_spec (vllm/v1/worker/gpu/attn_utils.py:138-155).
CallsThe selector get_attn_backend, the backend's impl class, the quantization config, and the forward context.
Not in this fileMLA attention (mla_attention.py), backend classes ("v1/attention/backend.py and selector.py: the backend interfaces and the selector"), kernels.

Where it sits#

Who calls it#

  • Model files build one Attention per decoder layer and call self.attn(q, k, v) (How a vLLM model file is written (llama.py)).
  • The runner reads the layers from the static dict to build the KV cache spec and the attention groups (vllm/v1/worker/gpu/attn_utils.py:228-234).
  • The compiled graph calls torch.ops.vllm.unified_kv_cache_update and torch.ops.vllm.unified_attention_with_output as opaque nodes.

What it calls#

  • get_attn_backend in its constructor (vllm/model_executor/layers/attention/attention.py:349-360); see How vLLM chooses an attention backend.
  • impl_cls(...) of the backend (vllm/model_executor/layers/attention/attention.py:419-432).
  • resolve_quant_method for KV cache scales (vllm/model_executor/layers/attention/attention.py:194-198).
  • get_forward_context() inside get_attention_context (vllm/model_executor/layers/attention/attention.py:705).

Walk through the main methods#

Attention.__init__: data type and backend#

  1. Lines 276-279. The KV cache dtype comes from --kv-cache-dtype, else "auto".
  2. Lines 287-291. A checkpoint with an FP8 kv_cache_scheme turns "auto" into "fp8". The comment says this case "is normally resolved upstream".
  3. Lines 294-297. A scheme with strategy == "attn_head" needs per-head scales; the selector checks backend support for it.

Then the constructor stores the head counts and asserts that num_heads divides by num_kv_heads (vllm/model_executor/layers/attention/attention.py:327-338). It selects the backend unless the caller passed one (lines 349-362). It rejects options the backend cannot do, for example use_alibi_sqrt (vllm/model_executor/layers/attention/attention.py:363-370).

Attention.__init__: impl, registration, placeholder#

  1. Lines 419-432. The impl gets ten positional arguments plus backend extras.
  2. Line 440. use_direct_call is false on CUDA, ROCm, CPU and XPU, which want the opaque op.
  3. Lines 443-445. Register in static_forward_context by prefix; a duplicate raises.
  4. Lines 448-453. Validate a KV sharing target.
  5. Line 464. An empty placeholder until the runner binds the real cache view. The comment says the attribute is not read with direct calls; in this file the direct path also reads it, through get_attention_context (lines 553, 716-717).
  6. Line 467. KV cache quantization scales.

Attention.forward#

  1. Lines 525-530. Allocate the output: [num_tokens, num_heads × head_size_v] unless the model gives a shape.
  2. Lines 533-540. Reshape q, k and v to [tokens, heads, head_size] outside the op, "to minimize the CPU overheads from the non-CUDA-graph regions".
  3. Lines 542-552. The direct-call path; the cache write runs only if the backend does not write in its forward and the layer does not share another layer's cache.
  4. Lines 553-560. The attention call. The opaque path (lines 561-580) is the same with torch.ops.vllm.* and an encoded name.

get_kv_cache_spec#

A normal decoder layer returns a FullAttentionSpec with the current block size, per-rank KV heads, head sizes and the KV dtype. Encoder and encoder-only layers return None: they keep no KV cache (vllm/model_executor/layers/attention/attention.py:616-617). A sliding-window layer returns a SlidingWindowSpec and may choose its own block size (vllm/model_executor/layers/attention/attention.py:620-670); see The hybrid KV cache: specs, groups and one manager per layer type.

get_attention_context and the two ops#

  1. Lines 767-768. Two decorators: @eager_break_during_capture makes the op a break point of breakable CUDA graphs; @maybe_transfer_kv_layer adds the KV connector's per-layer load and save. The breakable decorator must be outermost (vllm/compilation/breakable_cudagraph.py:82-96).
  2. Line 782. The dummy dependency is dropped; it only ordered the ops.
  3. Line 784. One lookup gives metadata, layer, KV cache (the slot mapping is not needed here).
  4. Lines 786-796. The impl call; the result lands in output.
  5. Lines 799-803. Registration: mutates_args=["output", "output_block_scale"] tells the compiler which inputs change.

get_attention_context itself is explained line by line on The forward context: how layers find per-step data (Step 5).

Deep dive

Interaction with prefix caching, compile and KV transfer

  • Prefix caching. With VLLM_BATCH_INVARIANT and the FlashInfer or Triton MLA backend, the constructor turns prefix caching off and logs a warning (vllm/model_executor/layers/attention/attention.py:373-388).
  • torch.compile. The ops are splitting ops (torch.compile and CUDA graphs in vLLM). The query quantization in forward uses a plain torch op so that the compiler can fuse it (vllm/model_executor/layers/attention/attention.py:512-517).
  • KV transfer. @maybe_transfer_kv_layer calls wait_for_layer_load before and saves after the attention, only with an active KV connector and connector metadata (vllm/model_executor/layers/attention/kv_transfer_utils.py:37-55).

Check yourself#

  1. 1
    What does Attention.forward return, and where is the attention result written first?
    easy
    Show answer

    It returns output.view(-1, hidden_size) (vllm/model_executor/layers/attention/attention.py:581). The impl writes into the output tensor that forward allocated, because the op mutates output (vllm/model_executor/layers/attention/attention.py:799-803).

  2. 2
    When does Attention.forward skip the cache write op?
    medium
    Show answer

    When the backend writes the cache inside its own forward (forward_includes_kv_cache_update), when the layer shares another layer's cache, or when key or value is None (vllm/model_executor/layers/attention/attention.py:564-572).

  3. 3
    Which decorator must be outermost on unified_attention_with_output, and why?
    hard
    Show answer

    @eager_break_during_capture. The KV connector's wait and save calls in @maybe_transfer_kv_layer must run in the eager segment; inside a captured graph they would hang on replay (vllm/compilation/breakable_cudagraph.py:82-96).

Related pages

  • The forward context: how layers find per-step dataAttention layers register themselves by name when the model is built, get their KV cache tensor bound at start-up, and read the per-step metadata from a global forward context that the model runner sets around each forward pass. The attention custom ops take only the layer name, so torch.compile sees them as opaque.
  • Attention backends: backend, metadata builder and implementationAn attention backend is three classes. The backend class describes what it supports, the metadata builder turns the common batch description of a KV cache group into backend metadata once per step, and the implementation writes the KV cache and runs the kernel for one layer. The builders also report how much CUDA graph capture they allow.
  • How vLLM chooses an attention backendEach attention layer asks the selector for a backend class when the worker builds the model. The selector asks current_platform. CUDA validates a priority list for the GPU generation and takes the first valid backend; an explicit --attention-backend is validated alone.
  • "forward_context.py: the per-step context of the forward pass"vllm/forward_context.py defines ForwardContext, BatchDescriptor and DPMetadata, and the context manager set_forward_context that the model runner wraps around each model call. Code inside the forward pass reads it with get_forward_context().
  • "v1/attention/backend.py and selector.py: the backend interfaces and the selector"vllm/v1/attention/backend.py defines the abstract classes of every attention backend (AttentionBackend, AttentionMetadataBuilder, AttentionImpl, MLAAttentionImpl), CommonAttentionMetadata and AttentionCGSupport. vllm/v1/attention/selector.py turns a layer's facts into one backend class through the platform, with a cache.
  • How a vLLM model file is written (llama.py)A vLLM model file rebuilds the Hugging Face architecture from vLLM layers. Every constructor takes vllm_config and a prefix, linear layers are tensor-parallel, attention is an Attention layer object, and pipeline stages use PPMissingLayer and IntermediateTensors. llama.py is the example.
  • The hybrid KV cache: specs, groups and one manager per layer typeModels that mix full attention with sliding-window, chunked-local or Mamba layers get one KV cache group per layer type. Each group has its own block table and single-type manager, all groups share one block pool, and so every group must use the same page size. Prefix caching finds one hit length that is valid for all groups.
