v1/core/kv_cache_manager.py: KVCacheManager and KVCacheBlocks

AdvancedCode mapabout 7 min read + 3 min deep dives

Before you read

This page uses ideas from these pages:

  • The KV cache manager: blocks, the block pool and memory sizing Advanced

Purpose#

vllm/v1/core/kv_cache_manager.py gives the scheduler one small API for KV blocks, and hides the coordinator, the per-group managers and the block pool behind it.

Filevllm/v1/core/kv_cache_manager.py, 922 lines of Python. Two classes.
Main classesKVCacheBlocks (vllm/v1/core/kv_cache_manager.py:35) and KVCacheManager (vllm/v1/core/kv_cache_manager.py:131).
Runs inThe EngineCore process, main thread, inside the scheduler. CPU only: it keeps Python objects, never GPU tensors.
Called byScheduler (vllm/v1/core/sched/scheduler.py) and AsyncScheduler; KV connectors through bind_kv_cache_manager.
CallsA KVCacheCoordinator (kv_cache_coordinator.py), and through it the SingleTypeKVCacheManagers and the BlockPool.
Not in this fileThe block hash and the free queue (kv_cache_utils.py), the hit search per attention type (single_type_kv_cache_manager.py), the pool (block_pool.py), the start-up sizing (kv_cache_planning.py).

The page The KV cache manager: blocks, the block pool and memory sizing explains the ideas with a figure. This page reads the file.

Where it sits#

Who calls it#

  • Scheduler.__init__ builds it (vllm/v1/core/sched/scheduler.py:329-347).
  • The waiting pass calls get_computed_blocks through _get_local_prefix_cache_hit (vllm/v1/core/sched/scheduler.py:589-599), and allocate_slots with the hit (vllm/v1/core/sched/scheduler.py:1320-1337).
  • The running pass calls allocate_slots with new tokens only (vllm/v1/core/sched/scheduler.py:834-838).
  • _free_request_blocks calls free or pop_blocks_for_free (vllm/v1/core/sched/scheduler.py:2866-2875).
  • AsyncScheduler calls cache_blocks when sampled tokens arrive (vllm/v1/core/sched/async_scheduler.py:75-79).
  • make_stats and get_kv_cache_usage read usage and make_prefix_cache_stats (vllm/v1/core/sched/scheduler.py:2709-2711, vllm/v1/core/sched/scheduler.py:3025).
  • A KV connector gets the manager after construction (vllm/v1/core/sched/scheduler.py:359-361).

What it calls#

  • get_kv_cache_coordinator (vllm/v1/core/kv_cache_manager.py:167-180), which picks KVCacheCoordinatorNoPrefixCache, UnitaryKVCacheCoordinator or HybridKVCacheCoordinator (vllm/v1/core/kv_cache_coordinator.py:995-1038).
  • The coordinator methods find_longest_cache_hit, get_num_blocks_to_allocate, allocate_new_computed_blocks, allocate_new_blocks, cache_blocks, remove_skipped_blocks, free (vllm/v1/core/kv_cache_coordinator.py:190-473).
  • BlockPool directly for usage, events and evictions (vllm/v1/core/kv_cache_manager.py:197, vllm/v1/core/kv_cache_manager.py:234).

Walk through the main methods#

KVCacheBlocks: the result type#

  1. Line 41. A tuple with one sequence per KV cache group. A model with only full attention has one group.
  2. Lines 43-48. The group is the outer level, because groups may get different block sizes.
  3. Lines 50-53. An empty result is a tuple of empty tuples, made once and shared, to save garbage collection work.

get_computed_blocks: the prefix-cache hit#

  1. Lines 286-287. No lookup when prefix caching is off, or when the request skips the cache read (for example a request with prompt logprobs) (vllm/v1/core/kv_cache_manager.py:249-251).
  2. Line 295. At most num_tokens - 1 tokens: the last prompt token must run to produce logits. The comment says that this can cost a whole block of recompute.
  3. Lines 296-300. The coordinator searches the hash chain. How the search works is on Prefix caching in the engine core: hashes, lookup, caching, eviction and KV events.

allocate_slots: count, then change#

The concept page reads this method in two parts (The KV cache manager: blocks, the block pool and memory sizing, Steps 3 and 4). The order of its stages, line by line:

  1. Lines 474-482. ValueError for a call with nothing to do.
  2. Lines 484-497. Take the new hit blocks, cut for groups that keep a longer hit.
  3. Lines 501-507. num_local_computed_tokens and total_computed_tokens.
  4. Lines 509-516. Watermark blocks, only for waiting or preempted requests while others run.
  5. Lines 522-539. full_sequence_must_fit: the whole request must fit, or None.
  6. Lines 541-544. num_tokens_need_slot, with the lookahead, capped at max_model_len.
  7. Lines 555-559. Free blocks outside the attention window, on the processed tokens only.
  8. Lines 561-579. Count the blocks, compare with the free blocks minus reservations, or None.
  9. Lines 581-593. Adopt the hit blocks and allocate blocks for connector tokens.
  10. Lines 595-600. Allocate the new blocks.
  11. Lines 602-616. Cache full blocks, unless a KV load is still running.
  12. Line 618. Return only the new blocks.

The check uses reserved_blocks, which the scheduler sets only for asynchronous KV loads (vllm/v1/core/sched/scheduler.py:1305-1315).

free and usage#

The docstring describes the reverse order, but the reverse happens in the single-type manager (vllm/v1/core/single_type_kv_cache_manager.py:597-598). usage forwards to BlockPool.get_usage: 1 - free / (num_gpu_blocks - 1) (vllm/v1/core/block_pool.py:881-892).

Worked example: one request from admission to free

Block size 16, one group, prefix caching on. The request of Tour 1: 61 prompt tokens, 48 of them hit in blocks 7, 3 and 12; the generation stops after 10 output tokens. (Block ids illustrative; derived from the code below.)

  1. Waiting pass. get_computed_blocks → 3 blocks, 48 tokens. allocate_slots(req, 13, 48, hit): need cdiv(61, 16) = 4, have 3, take 1: block 40. Cache up to 61: 3 full blocks, all cached already. Block table [7, 3, 12, 40].
  2. Decode steps 1-3. Tokens 62-64 fit in block 40 (slots 48-63). allocate_slots takes nothing. Step 3 computes token 64, so block 40 becomes full and gets its hash. The synchronous scheduler hashes it when it schedules step 3 (vllm/v1/core/kv_cache_manager.py:612-616). AsyncScheduler hashes it later, when the output of step 3 arrives (vllm/v1/core/sched/async_scheduler.py:75-79).
  3. Decode step 4. The request needs slot 65: cdiv(65, 16) = 5 blocks, 1 new. Block table [7, 3, 12, 40, 58].
  4. Stop. After 10 output tokens the request has 71 tokens, 70 of them computed. free returns [58, 40, 12, 3, 7] to the pool. Block 58 (6 tokens, no hash) goes to the front of the free queue. The others (hashed) go to the end, if no other request holds them.

Check yourself#

  1. 1
    What does allocate_slots return when the blocks do not fit, and what has it changed then?
    easy
    Show answer

    None, and nothing has changed: both checks come before any touch or allocation (vllm/v1/core/kv_cache_manager.py:538-539, vllm/v1/core/kv_cache_manager.py:577-579, then vllm/v1/core/kv_cache_manager.py:581-600).

  2. 2
    Why does get_computed_blocks never return a hit for the whole prompt?
    medium
    Show answer

    The engine must run at least the last prompt token to get logits, so the hit is at most num_tokens - 1 tokens (vllm/v1/core/kv_cache_manager.py:289-295). Because hits are whole blocks, a prompt of exactly 64 tokens with all 4 blocks cached gets a hit of 48 tokens.

  3. 3
    A new request comes with a draft-token lookahead of 4 and a 30-token prompt; block size 16. How many slots and blocks does allocate_slots reserve, and how many full blocks does it cache?
    hard
    Show answer

    Slots: min(0 + 30 + 4, max_model_len) = 34, so cdiv(34, 16) = 3 blocks (vllm/v1/core/kv_cache_manager.py:541-544). Cached: up to min(30, request.num_tokens) = 30 tokens, so 1 full block (vllm/v1/core/kv_cache_manager.py:612-616). The lookahead slots are allocated but never cached.

Related pages

  • The KV cache manager: blocks, the block pool and memory sizingIn the engine core, the KVCacheManager hands out KV blocks to the scheduler through a coordinator, one single-type manager per KV cache group and one BlockPool. The workers only receive block ids. The number of blocks comes from a memory profile at start-up.
  • Prefix caching in the engine core: hashes, lookup, caching, eviction and KV eventsThe mechanics of prefix caching in the engine core. The input thread hashes each new request, the scheduler looks the hashes up in the block pool and touches the hits, allocate_slots hashes blocks that become full, and the free queue decides what to evict. KV events tell an external router what each engine holds.
  • The hybrid KV cache: specs, groups and one manager per layer typeModels that mix full attention with sliding-window, chunked-local or Mamba layers get one KV cache group per layer type. Each group has its own block table and single-type manager, all groups share one block pool, and so every group must use the same page size. Prefix caching finds one hit length that is valid for all groups.
  • The V1 scheduler: one token budget, no phasesIn each engine step, Scheduler.schedule() shares one token budget: first among the running requests, then among the waiting ones. It has no prefill or decode phase, it preempts the last running request when KV blocks run out, and update_from_output() appends the sampled tokens.
  • v1/core/sched/scheduler.py: the Schedulervllm/v1/core/sched/scheduler.py holds the Scheduler class (3,539 lines). schedule() shares the token budget between running and waiting requests and builds the SchedulerOutput; update_from_output() appends the sampled tokens, stops requests and builds the EngineCoreOutputs.
  • v1/core/block_pool.py: BlockPool and the prefix-cache mapvllm/v1/core/block_pool.py holds BlockPool, the owner of every KVCacheBlock of an engine core. It hands out blocks from the free queue, frees them in eviction order, keeps the hash-to-block map of the prefix cache, emits KV cache events and computes the KV cache usage.
  • v1/core/kv_cache_utils.py: block hashes, KVCacheBlock and the free queuevllm/v1/core/kv_cache_utils.py holds the building blocks of the KV cache manager. It defines the block hash types, NONE_HASH, the extra keys and the request block hasher, the KVCacheBlock record, the FreeKVCacheBlockQueue linked list, the block-size resolution for several KV cache groups, and the capacity log line.
