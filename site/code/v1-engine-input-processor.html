v1/engine/input_processor.py: from engine input to EngineCoreRequest

Purpose#

vllm/v1/engine/input_processor.py turns one rendered prompt and its parameters into one EngineCoreRequest. On the way, it rejects requests that the engine cannot run and fills in the defaults that the engine core needs.

Filevllm/v1/engine/input_processor.py, 657 lines of Python. One class.
Main classInputProcessor (vllm/v1/engine/input_processor.py:41).
Runs inThe API server process. process_inputs runs on the event loop for rendered inputs, and in the renderer's thread pool for raw prompts (process_inputs_async).
Called byAsyncLLM.add_request and LLMEngine.add_request; the beam search code reads its fields.
CallsSamplingParams.verify, clone, update_from_generation_config, update_from_tokenizer; PoolingParams.verify; the renderer (raw prompts, token-id checks); current_platform.validate_request; the logits processor validator.
Not in this fileChat templates and tokenization (vllm/renderers/), the multimodal processor, the sending of the request (core_client.py), the engine core's Request (vllm/v1/request.py).

The name says "processor", but for vllm serve the heavy work is already done: the renderer has applied the chat template and tokenized the prompt. The input processor checks and packs.

Where it sits#

The input processor stands between the renderer and the engine core client: renderer → EngineInput dict → InputProcessor.process_inputs → EngineCoreRequest → assign_request_id → engine core client. The page Data contracts between the parts of vLLM shows the types on both sides.

Who calls it#

  • AsyncLLM.__init__ makes one instance and gives it the shared renderer (vllm/v1/engine/async_llm.py:170). LLMEngine does the same (vllm/v1/engine/llm_engine.py:101).
  • AsyncLLM.add_request calls process_inputs for rendered inputs and process_inputs_async for raw prompts, then assign_request_id (vllm/v1/engine/async_llm.py:481-521).
  • The serving classes keep a reference to it as self.input_processor (vllm/entrypoints/generate/base/serving.py:151). Online beam search calls resolve_watermarking and reads generation_config_fields (vllm/entrypoints/generate/beam_search/online.py:49, vllm/entrypoints/generate/beam_search/online.py:78).

What it calls#

  • SamplingParams.verify and PoolingParams.verify for the parameter rules (vllm/v1/engine/input_processor.py:157-162, vllm/v1/engine/input_processor.py:245).
  • The logits processor validator, built once in the constructor. With Model Runner V2 it loads the custom logits processor classes (vllm/v1/engine/input_processor.py:93-113).
  • current_platform.validate_request, a hook for platform plugins (vllm/v1/engine/input_processor.py:430).
  • renderer.validate_token_ids, which rejects token ids outside the vocabulary (vllm/v1/engine/input_processor.py:646-647, vllm/renderers/base.py:453-458).

Walk through the main methods#

process_inputs, part 1: checks and the engine input#

  1. Lines 389-390. Check the parameters and the LoRA request first. _validate_params returns the watermark decision; the code applies it later to its own copy.
  2. Lines 392-400. An explicit data_parallel_rank must be in range. The range is the local DP size with hybrid or external load balancing, else the full DP size.
  3. Lines 402-406. The vllm serve path: the prompt is already an engine input. Its arrival_time, set by the renderer, wins over a new time.time().
  4. Lines 407-428. The old path for raw prompts logs a deprecation warning once and renders the prompt here.
  5. Line 430. The platform can reject the request.
  6. Lines 432-433. Split encoder and decoder inputs, and check their lengths and token ids.

process_inputs, part 2: sampling parameters and defaults#

  1. Line 449. clone(): the caller's SamplingParams object can be shared by many requests, so the code changes only a copy. The comment at lines 450-451 says so.
  2. Lines 457-475. Two range checks for rarely used fields: routed_experts_prompt_start and the rows of prompt_logprob_token_ids.
  3. Lines 476-487. No max_tokens: use all the room that is left, max_model_len − prompt_len. Only now can min_tokens be checked against it.
  4. Lines 489-492. update_from_generation_config sets the EOS token id and adds the eos_token_id values of the model's generation config to stop_token_ids. With ignore_eos, it changes neither (vllm/sampling_params.py:775-803).
  5. Lines 493-494. update_from_tokenizer turns bad_words into token ids (vllm/sampling_params.py:805-847).
  6. Line 498. Pooling parameters are cloned too, but get no defaults here.

Not the sampling defaults

This file does not apply the default temperature or top_p of the model's generation config. The chat serving layer does that when it builds SamplingParams: "Priority: user -> server default -> OpenAI default" (vllm/entrypoints/openai/chat_completion/protocol.py:740-748). The input processor reads the generation config only for EOS ids (line 490 and vllm/v1/engine/input_processor.py:64).

process_inputs, part 3: the struct#

Every field comes from the steps above. cache_salt comes from the decoder input (line 548): a client can set it to keep its prefix-cache entries apart from other clients. client_index, current_wave and external_req_id keep their defaults here. The client and assign_request_id set them later.

assign_request_id#

  1. Lines 358-362. A caller must not set external_req_id itself.
  2. Line 363. The caller's id becomes the external id. The output processor returns it in RequestOutput.request_id.
  3. Lines 364-369. With VLLM_DISABLE_REQUEST_ID_RANDOMIZATION, the id stays unchanged, with a warning about duplicates.
  4. Line 371. Else the first 8 characters of a new UUID are appended after a dash.

_validate_params for sampling#

  1. Lines 151-155. A SamplingParams request needs a model with a generation task.
  2. Lines 157-162. SamplingParams.verify checks the fields against the model, the spec decoding config, the structured output config and the tokenizer.
  3. Lines 163-175. prompt_logprob_token_ids needs Model Runner V2 and does not work with --kv-sharing-fast-prefill.
  4. Line 177. Custom logits processors can check their own request arguments.

Further checks follow for diffusion models, sampling-mask replay, thinking_token_budget (needs a reasoning config) and trace replay (vllm/v1/engine/input_processor.py:179-220). Watermarking is resolved last, so a missing feature is reported before an incompatibility with watermarking (vllm/v1/engine/input_processor.py:221-223).

_validate_prompt_len#

  1. Lines 565-566. An empty decoder prompt is an error.
  2. Lines 569-573. The limit is max_model_len for the decoder and the encoder cache size for an encoder prompt.
  3. Lines 574-591. Longer than the limit: error, with a hint for multimodal models.
  4. Lines 593-602. Exactly the limit, for a generative model: error too, because no room is left for one output token.

Deep dive

Processes and threads

The class lives in the API server process. It has no lock and no thread of its own. process_inputs_async is make_async(process_inputs) with the renderer's executor (vllm/v1/engine/input_processor.py:79-84). So raw-prompt requests run in the same thread pool as the tokenizer. The comment explains why: tokenization and multimodal processing block, and must not block the event loop.

The engine core repeats a few checks. For example, it checks the pooling task again in EngineCore.add_request (vllm/v1/engine/core.py:520-529). Structured-output grammars are compiled only in the engine core. The input thread starts the compilation in a thread pool of the structured output manager (vllm/v1/engine/core.py:1129-1135, vllm/v1/structured_output/__init__.py:196-197).

Worked example: three prompts and max_model_len = 32768

Assume a generative model with max_model_len = 32768 and a request with no max_tokens and no min_tokens.

Prompt lengthResultWhy
61max_tokens = 3270732768 − 61 (lines 477-480)
32768VLLMValidationError: "plus the number of requested output tokens (at least 1) is longer"equal to the limit, generative model (lines 593-602)
40000VLLMValidationError: "longer than the maximum model length of 32768"line 574

With vllm serve, the renderer usually rejects a too-long prompt first, during tokenization (vllm/renderers/params.py:518-538). The checks here also protect the paths that skip the renderer.

The EOS ids work like this (illustrative ids). The tokenizer's EOS id is 151645, and the generation config lists eos_token_id: [151645, 151643]. Then _eos_token_id = 151645, and 151643 is added to stop_token_ids, because the code removes the primary EOS id from the set (vllm/sampling_params.py:789-803).

Check yourself#

  1. 1
    A chat request has no max_tokens. The prompt has 1,000 tokens, and max_model_len is 8192. Which max_tokens reaches the engine core?
    easy
    Show answer

    7192, if the server and the platform set no smaller limit. The chat serving layer computes it with get_max_tokens, the smallest of max_model_len − prompt_len and the other limits (vllm/entrypoints/serve/utils/api_utils.py:253-270). process_inputs would fill the same value if it were still None (vllm/v1/engine/input_processor.py:476-480).

  2. 2
    Why does process_inputs clone the SamplingParams?
    medium
    Show answer

    The caller's object can be shared across prompts, requests and engines. The code then changes the copy: watermarking, max_tokens, EOS and stop ids (vllm/v1/engine/input_processor.py:447-453, vllm/v1/engine/input_processor.py:476-494).

  3. 3
    The client sends the id abc. Which ids do the output processor and the engine core use?
    medium
    Show answer

    The engine core uses abc- plus 8 random characters, for example abc-1f2e3d4c. The output processor keeps abc as external_req_id and puts it into RequestOutput.request_id (vllm/v1/engine/input_processor.py:363-371). (For chat, the serving layer has already added the prefix chatcmpl-.)

  4. 4
    A model has max_model_len = 4096. A prompt of exactly 4096 tokens reaches process_inputs. What happens, and would an embedding model behave the same?
    hard
    Show answer

    The generative model rejects it: the prompt length equals the limit, and the runner type is "generate", so no room is left for one output token (vllm/v1/engine/input_processor.py:593-602). An embedding model has another runner type, so a prompt of exactly 4096 tokens passes; only a longer one fails (vllm/v1/engine/input_processor.py:574).
