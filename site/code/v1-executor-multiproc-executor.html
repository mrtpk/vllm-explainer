v1/executor/multiproc_executor.py: MultiprocExecutor and WorkerProc

Before you read

Purpose#

vllm/v1/executor/multiproc_executor.py implements the multiproc executor: the default executor when an engine core needs more than one worker on a node, or when DP > 1. It also defines WorkerProc, the code that runs inside each worker process.

Filevllm/v1/executor/multiproc_executor.py, 1,147 lines of Python.
Main classesMultiprocExecutor(Executor) (vllm/v1/executor/multiproc_executor.py:112), WorkerProc (vllm/v1/executor/multiproc_executor.py:608), FutureWrapper(Future) (vllm/v1/executor/multiproc_executor.py:79).
Runs inMultiprocExecutor: the engine core process (main thread, plus the thread MultiprocWorkerMonitor). WorkerProc: each worker process (main thread, WorkerAsyncOutputCopy, DeathPipeMonitor).
Called byEngineCore.__init__ makes it (vllm/v1/engine/core.py:147); the busy loop calls execute_model and sample_tokens; utility calls reach collective_rpc.
CallsMessageQueue (shared memory), multiprocessing processes and pipes, WorkerWrapperBase and through it the GPU Worker.
Not in this fileThe ring buffer itself (distributed/device_communicators/shm_broadcast.py), the worker methods (v1/worker/gpu_worker.py), the uni executor (uniproc_executor.py), the base interface (abstract.py), Ray (ray_executor_v2.py, which subclasses this file's classes).

The page Executors and workers: from the engine core to the GPUs explains the ideas. This page reads the file method by method.

Where it sits#

Who calls it#

  • Executor.get_class returns MultiprocExecutor for the backend "mp" (vllm/v1/executor/abstract.py:80-83). When you do not set a backend, the config picks "mp" when world_size_across_dp > 1, unless a Ray case applies (vllm/config/parallel.py:1055-1096).
  • EngineCore builds it and registers the failure callback (vllm/v1/engine/core.py:147-150).
  • RayExecutorV2 and RayWorkerProc subclass the two main classes (vllm/v1/executor/ray_executor_v2.py:79, vllm/v1/executor/ray_executor_v2.py:239).
  • The spawned child process runs WorkerProc.worker_main (vllm/v1/executor/multiproc_executor.py:745-750).

What it calls#

  • MessageQueue(...), export_handle, create_from_handle, enqueue, dequeue (vllm/v1/executor/multiproc_executor.py:165-172, vllm/v1/executor/multiproc_executor.py:615-625).
  • get_mp_context() for processes, locks and pipes (vllm/v1/executor/multiproc_executor.py:174-175, vllm/v1/executor/multiproc_executor.py:723-727).
  • WorkerWrapperBase.init_worker, then init_device and load_model in the worker (vllm/v1/executor/multiproc_executor.py:659-688).
  • set_multiprocessing_worker_envs, which forces spawn when needed and sets OMP_NUM_THREADS (vllm/v1/executor/multiproc_executor.py:1119-1147).

Walk through the main methods#

_init_executor: start the workers#

  1. Lines 174-175. One lock is shared by all workers of this executor; the worker uses it for the multimodal receiver cache (vllm/v1/worker/worker_base.py:339-343).
  2. Lines 191-193. One process per local rank. is_driver_worker is true when rank % TP == 0 (vllm/v1/executor/multiproc_executor.py:297-298).
  3. Lines 197-206. Each child gets the handle of the broadcast queue, not the queue object.
  4. Line 216. The executor blocks until every worker has loaded its model. The comment at lines 212-213 explains the order: all workers must exist first, because init_device synchronizes the devices.
  1. Line 222. The engine core process sets its torch thread count for run time. The comment gives the reason: this process only schedules, and more threads only compete with the workers for the CPU.
  2. Lines 229-241. One reply queue per rank. Local workers write to their own MessageQueue(1, 1); remote ranks reach the leader node through worker 0.
  3. Lines 247-251. Both sides must call wait_until_ready() in the same order. The comment warns that another order deadlocks.
  4. Lines 258-266. On any failure, the executor closes the death pipes and terminates the processes it started.

collective_rpc: one call to all workers#

  1. Lines 396-398. Only the leader node of a DP rank owns the broadcast queue.
  2. Lines 399-400. After a worker death, every call fails at once.
  3. Line 402. One deadline for the whole call; each reply read gets the time that is left.
  4. Lines 405-422. With a KV or EC connector aggregator, output_rank becomes None: all workers reply, and the aggregator merges their outputs onto the reply of unique_reply_rank.
  1. Lines 425-427. A callable is sent as cloudpickle bytes; the worker calls it with the worker object as the first argument (vllm/v1/executor/multiproc_executor.py:1059-1060).
  2. Line 428. The single write into shared memory.
  3. Lines 437-443. A reply that does not come in time becomes TimeoutError.
  4. Lines 452-456. non_block returns the FutureWrapper; else the method waits at once.

FutureWrapper: replies in order#

  1. Line 90. Each new future goes to the left end of the shared deque.
  2. Lines 97-99. result() pops from the right end, the oldest future, and reads its reply, until its own future is done. The reply queues are FIFO, so the reply of the oldest call always comes first.
  3. Lines 104-109. An error goes into the future that owns it, not into the caller's future.

WorkerProc.__init__: inside the worker process#

  1. Lines 659-672. WorkerWrapperBase.init_worker loads the general plugins and makes the worker class. Only this rank's kwargs are filled in.
  2. Line 680. init_device: CUDA device, NCCL groups, memory snapshot, model runner.
  3. Line 688. The weights load here, before the worker reports READY.
  4. Lines 691-699. With async scheduling, a second thread will wait for the GPU results.
  5. Line 702. The platform may change the block size for the chosen attention backend.
  6. Line 706. The queues come last, because a multi-node setup needs the process groups.

worker_busy_loop and _execute_worker_rpc#

  1. Lines 1045-1046. Wait for the next call without a timeout. The stack-dump watchdog is off during this wait, so an idle worker does not look stuck.
  2. Lines 1057-1060. A name is looked up on the worker wrapper; bytes are a pickled function.
  3. Lines 1070-1071. Only the reply rank (or every rank when output_rank is None) sends the result.
  4. Lines 1076-1080. An exception is logged with its traceback and sent as a FAILURE reply. The loop goes on.

handle_output: the async copy thread#

  1. Lines 1000-1005. An AsyncModelRunnerOutput is resolved with get_output(), which waits for the copy to the CPU.
  2. Lines 1019-1022. With async scheduling, this wait happens in the extra thread, not in the main thread.
  3. Lines 1034-1035. The thread sets its CUDA device first. A new thread does not inherit it, and a CUDA call on device 0 would make a second CUDA context.

Deep dive

Worked example: TP = 2, one step

  1. The busy loop calls execute_model(so, non_block=True). collective_rpc enqueues ("execute_model", (so,), {}, 0) and returns future F1 (vllm/v1/executor/multiproc_executor.py:342-353).
  2. Both workers dequeue the same message. Both run Worker.execute_model; their forward passes meet in the NCCL all-reduces of the TP layers.
  3. Worker 0 is the output rank (2 - 2 × 1 = 0). It replies (SUCCESS, None) through its copy thread. Worker 1 replies nothing.
  4. The busy loop computes the grammar bitmask, then calls sample_tokens(grammar, non_block=True): message ("sample_tokens", (grammar,), {}, 0), future F2.
  5. Both workers sample. Worker 0 gives its AsyncOutput to the copy thread, which waits for the copy and replies (SUCCESS, ModelRunnerOutput).
  6. One call later, the busy loop pops this step and calls F2.result(). FutureWrapper first reads the reply of F1 (None), then the reply of F2.

(Derived from the methods above and vllm/v1/engine/core.py:724-773.)

Check yourself#

  1. 1
    What is the name of a worker process before it renames itself, and which method is its target?
    easy
    Show answer

    VllmWorker-<rank>, with the target WorkerProc.worker_main (vllm/v1/executor/multiproc_executor.py:745-750).

  2. 2
    With TP = 8 and PP = 4, which rank replies to execute_model?
    medium
    Show answer

    Rank world_size - TP × PCP = 32 - 8 = 24, the first TP rank of the last PP stage. The comment in _get_output_rank uses this example (vllm/v1/executor/multiproc_executor.py:549-563).

  3. 3
    A worker method raises ValueError("bad"). What does the engine core see, and where is the traceback?
    medium
    Show answer

    The worker logs "WorkerProc hit an exception." with the traceback. If it is the reply rank (or the call has no output_rank), it replies (FAILURE, "bad") (vllm/v1/executor/multiproc_executor.py:1072-1080). The executor raises RuntimeError("Worker failed with error 'bad', ...") (vllm/v1/executor/multiproc_executor.py:444-448). The traceback is only in the worker's log.

  4. 4
    Why does async_output_busy_loop call current_platform.set_device before its loop, and what goes wrong without it?
    hard
    Show answer

    A new thread does not inherit the current CUDA device of the main thread. The first CUDA call in the thread, here the event synchronize in get_output(), would then make a new CUDA context on device 0, which costs extra memory. The comment says this (vllm/v1/executor/multiproc_executor.py:1026-1035).

Related pages

  • Executors and workers: from the engine core to the GPUsThe executor starts the workers and runs each call on all of them. The uni executor calls one worker in the engine core process; the multiproc executor sends calls to one worker process per GPU through a shared-memory queue.
  • Async scheduling: overlap the CPU and the GPUWith async scheduling, the engine core schedules and starts step N+1 before it waits for the token of step N. Placeholders in the scheduler and a GPU-side token buffer in Model Runner V2 make this possible.
  • The engine core loop: threads, queues and the busy loopThe engine core process runs three threads. An input thread decodes requests, the main thread runs the busy loop with the scheduler and the executor, and an output thread sends the results back.
  • v1/engine/core.py: EngineCore and the engine core processvllm/v1/engine/core.py defines EngineCore (scheduler + executor + step functions), EngineCoreProc (the process with its ZMQ threads and busy loop) and DPEngineCoreProc (the lock-step variant for MoE data parallelism).
  • v1/worker/gpu_worker.py: the GPU Workervllm/v1/worker/gpu_worker.py defines Worker, the object that owns one GPU. It sets up the device and NCCL, builds Model Runner V2, profiles memory to size the KV cache, warms up the model, and forwards each step to the model runner.
  • distributed/device_communicators/shm_broadcast.py: MessageQueuevllm/distributed/device_communicators/shm_broadcast.py implements MessageQueue, a one-writer, many-reader queue. Local readers share a lock-free ring of chunks in /dev/shm with one flag byte per reader; large messages and remote readers use ZMQ XPUB sockets. The executor uses it to send every call to its workers, and each worker uses one to reply.
  • Tour: One step across GPUsFollow two requests through vllm serve -tp 2 -dp 2 in 13 stops: the API servers pick an engine each, two independent engine cores schedule, each broadcasts the step to its two workers through shared memory, the workers meet in 65 all-reduces on their TP group, only rank 0 replies, and the coordinator publishes the new load.
