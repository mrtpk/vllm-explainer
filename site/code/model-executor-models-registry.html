model_executor/models/registry.py: the model registry

IntermediateCode mapabout 9 min read + 3 min deep dives

Purpose#

vllm/model_executor/models/registry.py maps an architecture name from config.json to a model class, and tells the rest of vLLM what that class supports, without an import of the model in the front end.

Filevllm/model_executor/models/registry.py, 1,623 lines of Python. About 820 lines are data tables (lines 73-887).
Main objectsModelRegistry, the one _ModelRegistry object (vllm/model_executor/models/registry.py:1565); classes _ModelInfo, _RegisteredModel, _LazyRegisteredModel, _ModelRegistry.
Runs inEvery process that imports it. In vllm serve: the front end inspects (in ModelConfig); each worker resolves and imports the class; plugins call register_model everywhere. The file is also a script: python -m vllm.model_executor.models.registry is the inspection subprocess.
Called byModelConfig through its registry property (vllm/config/model.py:1165-1168), the model loader (vllm/model_executor/model_loader/utils.py:310), the speculative config for draft models (vllm/config/speculative.py:1779), some platform and KV-planning code, and general plugins through from vllm import ModelRegistry (vllm/__init__.py:26).
CallsThe detector functions of interfaces.py and interfaces_base.py (vllm/model_executor/models/registry.py:47-69), importlib, subprocess with cloudpickle, transformers (Transformers backend checks), safe_hash, current_platform.verify_model_arch.
Not in this fileThe model classes, the capability protocols (interfaces.py, page Model capability protocols (SupportsPP, SupportsLoRA, ...)), the conversion adapters for --convert (adapters.py), and the plugin loader.

The page Out-of-tree models and the model registry explains the registry from the user's side, with a plugin example. This page reads the file section by section.

Who calls it#

  • Front end, config time. ModelConfig.__post_init__ asks is_text_generation_model and is_pooling_model, then calls inspect_model_cls and stores the record (vllm/config/model.py:703-744). PP and HC-SP checks call is_pp_supported_model and is_hc_sp_supported_model (vllm/config/model.py:1552, vllm/config/model.py:1570).
  • Worker, model build. _get_model_architecture calls resolve_model_cls (vllm/model_executor/model_loader/utils.py:305-313).
  • Other readers. The CPU platform (vllm/platforms/cpu.py:66), the Mamba page-size code of Platform (vllm/platforms/interface.py:1043) and model-owned KV cache grouping (vllm/v1/core/kv_cache_planning.py:1677).
  • Plugins. register_model and get_supported_archs (tests/plugins/vllm_add_dummy_model/vllm_add_dummy_model/__init__.py:11-12).

What it calls#

  • 20 detector and getter functions to build _ModelInfo (vllm/model_executor/models/registry.py:917-954).
  • importlib.import_module and importlib.util.find_spec (vllm/model_executor/models/registry.py:1082, vllm/model_executor/models/registry.py:1121).
  • subprocess.run(_SUBPROCESS_COMMAND, ...) (vllm/model_executor/models/registry.py:1591-1593).
  • current_platform.verify_model_arch before each class import (vllm/model_executor/models/registry.py:1132); the base method accepts all models (vllm/platforms/interface.py:1142-1150).
  • try_get_class_from_dynamic_module and the transformers package, for the Transformers backend (vllm/model_executor/models/registry.py:1270-1282).

Walk through the main methods#

_LazyRegisteredModel: the disk cache#

  1. Line 997. The directory is $VLLM_CACHE_ROOT/modelinfos.
  2. Lines 1000-1001. The file name is module-Class.json with every dot replaced by "-".
  3. Lines 1005-1009. For a package __init__.py, all .py files below the package are hashed, sorted; else only the one file.
  4. Lines 1014-1020. The hash takes the relative path, a zero byte, the file bytes and a zero byte, for each file. safe_hash is md5, or sha256 where md5 is not allowed (vllm/utils/hashing.py:118-121).
  5. Lines 1036-1042. A different hash means "stale": DEBUG log, None.
  6. Line 1045. A hit rebuilds _ModelInfo from the JSON dict. Any other error also returns None with a DEBUG log (lines 1046-1052).

The save writes {"hash": ..., "modelinfo": asdict(mi)} through atomic_writer, and only logs an exception on failure (vllm/model_executor/models/registry.py:1054-1069). The method that uses both is inspect_model_cls (vllm/model_executor/models/registry.py:1071-1118), walked on Out-of-tree models and the model registry.

_try_inspect_model_cls: the error filter#

  1. Lines 1125, 1140. lru_cache(maxsize=128) keyed by (name, entry). Entries are frozen dataclasses, so they are hashable and compare by value. A new registration with another target is a new key; the same module and class strings give an equal key.
  2. Line 1132. Before an import, the platform may reject the architecture.
  3. Lines 1135-1137, 1147-1149. Any exception is logged with its traceback ("Error in loading/inspecting model architecture"), and the result is None. The caller then tries the next step of the lookup.

resolve_model_cls: the worker's lookup#

  1. Lines 1414-1425. transformers or terratorch implementation first.
  2. Lines 1427-1437. Transformers fallback when no name is registered and no conversion is set.
  3. Lines 1439-1443. Each name, normalized; the first class that imports wins. The returned name is the original one, not the normalized one.
  4. Lines 1445-1454. The fallback again, without the conversion condition.
  5. Line 1456. _raise_for_unsupported.

inspect_model_cls (lines 1351-1402) is the same with _try_inspect_model_cls, except one detail: for terratorch it asserts that inspection worked (line 1370).

_raise_for_unsupported: four messages#

The order matters: a registered name that failed always gets "failed to be inspected" (lines 1208-1212), even when it is also in a removed-models table. The last message lists all supported names, so it can be long (lines 1233-1236).

Deep dive

Processes: who runs what

  • Every process builds ModelRegistry at import, with 406 lazy entries and no model import (vllm/model_executor/models/registry.py:1565-1573).
  • Every process that loads general plugins runs the plugins' register_model calls. The registry is a module global, so each process has its own copy.
  • The front end inspects. On a cache miss it starts one extra Python process per lazy entry; that child loads the general plugins too (vllm/model_executor/models/registry.py:1608-1612).
  • Each worker imports the chosen class through resolve_model_cls.

The child gets its command from _SUBPROCESS_COMMAND, a module list that the comment allows other packagers to change (vllm/model_executor/models/registry.py:819-823). The comment at lines 1589-1590 says why it uses -m: the module uses relative imports.

A worked example: the cache file of an out-of-tree package

A plugin registers register_model("MyLlava", "vllm_add_dummy_model.my_llava:MyLlava") (tests/plugins/vllm_add_dummy_model/vllm_add_dummy_model/__init__.py:26-27).

  1. The module name does not start with vllm.model_executor.models., so find_spec("vllm_add_dummy_model.my_llava") finds the file (lines 1080-1085). This imports the package vllm_add_dummy_model, but not my_llava (Python rule).
  2. The file is my_llava.py, not __init__.py, so the hash covers one file, with the relative path "my_llava.py".
  3. The cache file is $VLLM_CACHE_ROOT/modelinfos/vllm_add_dummy_model-my_llava-MyLlava.json (dots replaced; underscores stay).
  4. On a miss, the child imports my_llava and returns the record. supports_multimodal is then true if MyLlava inherits the multimodal protocol. (The class content is not shown here.)

  1. 1
    How many names does the built-in registry hold at this commit, and what kind of entry is each?
    easy
    Show answer

    406 names in _VLLM_MODELS (derived count). Each becomes a _LazyRegisteredModel (vllm/model_executor/models/registry.py:1565-1573).

  2. 2
    Why does _try_inspect_model_cls return None instead of raising?
    medium
    Show answer

    So that the lookup can try the next step (another name, or the Transformers fallback). The exception is logged with its traceback (vllm/model_executor/models/registry.py:1141-1150); if all steps fail, _raise_for_unsupported raises "failed to be inspected" for a registered name.

  3. 3
    What is the cache file name for vllm.models.deepseek_v4:DeepseekV4ForCausalLM, and what does its hash cover?
    medium
    Show answer

    vllm-models-deepseek_v4-DeepseekV4ForCausalLM.json (vllm/model_executor/models/registry.py:999-1001). The source is the package __init__.py, so the hash covers every .py file under vllm/models/deepseek_v4/ (vllm/model_executor/models/registry.py:1005-1009).

  4. 4
    Config says ["MyForSequenceClassification"], only MyForCausalLM is registered, and the user passes --convert classify. Which class do the workers build?
    hard
    Show answer

    The Transformers fallback before the loop is skipped because a conversion is set (vllm/model_executor/models/registry.py:1427-1437). In the loop, _normalize_arch matches the suffix ForSequenceClassification and finds MyForCausalLM (vllm/model_executor/models/registry.py:1335-1347). The loader then wraps it with as_seq_cls_model (vllm/model_executor/model_loader/utils.py:331-333).

Related pages

  • Out-of-tree models and the model registryModelRegistry maps the architecture name in config.json to a model class. A plugin adds or replaces an entry with register_model; a "module:Class" string keeps the import lazy, and a cached subprocess inspects the class.
  • Model capability protocols (SupportsPP, SupportsLoRA, ...)A model class tells vLLM what it can do through base classes from models/interfaces.py. Detector functions turn them into a _ModelInfo record, and start-up checks use that record to allow or reject PP, LoRA, multimodal input and more.
  • How vLLM finds and loads pluginsvLLM finds plugins as Python entry points in six groups. Each process of vllm serve loads only the groups that it needs, at its own time. One environment variable, VLLM_PLUGINS, filters five of them.
  • How a vLLM model file is written (llama.py)A vLLM model file rebuilds the Hugging Face architecture from vLLM layers. Every constructor takes vllm_config and a prefix, linear layers are tensor-parallel, attention is an Attention layer object, and pipeline stages use PPMissingLayer and IntermediateTensors. llama.py is the example.
  • plugins/__init__.py: the plugin loadersvllm/plugins/__init__.py names the five plugin entry-point groups and has the three loaders: the shared group loader, the once-per-process general loader and the strict endpoint loader.
  • Hugging Face checkpointsA Hugging Face model folder holds config.json, generation_config.json, tokenizer files and safetensors weights. vLLM reads config.json to pick the model class and the limits, the generation config for default sampling values, the tokenizer files for the chat template, and the safetensors files for the weights.
