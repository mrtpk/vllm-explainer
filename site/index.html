vLLM Explained

Code version: vLLM @ 3e44c0d · 2026-10-22

vLLM is "a fast and easy-to-use library for LLM inference and serving" (README.md:24). Its main use is online serving: the command vllm serve starts an OpenAI-compatible server that answers HTTP requests (vllm/entrypoints/cli/serve.py:39-40). Behind the HTTP routes, a scheduler runs one engine step after the other and batches the requests of many clients on the GPUs. Outside code can change much of this through plugins.

Who this site is for. You know Python. You read DeepInfer Explained↗, or you know the LLM basics that it teaches. Now you want to become proficient in online serving with the latest vLLM: what happens to a request inside vllm serve, how to configure, tune, monitor and scale a deployment, and how plugins extend vLLM. This site does not teach the basics again. When a page needs one, it gives a one-line recap and a link to DeepInfer Explained. The site explains the code at commit 3e44c0d. To get exactly this version of the code, read The code version this site explains.

What it runs"200+ model architectures on Hugging Face": decoder-only and Mixture-of-Experts LLMs, hybrid and state-space models, multimodal models, embedding and reward models (README.md:53-60). The default model of vllm serve is Qwen/Qwen3-0.6B (vllm/config/model.py:155, vllm/engine/arg_utils.py:486, vllm/entrypoints/cli/serve.py:39-40).
HardwareBuilt-in platform detectors: TPU, CUDA (NVIDIA), ROCm (AMD), XPU (Intel) and CPU (vllm/platforms/__init__.py:231-237). The TPU platform class comes from the separate package tpu_inference (vllm/platforms/tpu.py:9-19). Other hardware comes as platform plugins, for example Intel Gaudi, IBM Spyre and Huawei Ascend (README.md:51).
Code size8,357 files. Python: 5,471 files, about 2.0 million lines; the package vllm/ has 2,907 Python files and about 1.13 million lines; the Python files in tests/ have about 0.77 million lines. C++ and CUDA: 313 files, about 143,000 lines (kernels, not explained here). Rust: 375 files, about 152,000 lines (an experimental front end). Method: the files of git ls-files at the pinned commit, grouped by extension (.py; .cpp .cu .cuh .h .hpp; .rs); a line is a newline, plus a last line without one. See Code map: the folder tree.
Run itvllm serve <model>, for example vllm serve Qwen/Qwen3-0.6B. The command vllm is a console script (pyproject.toml:42-43). The server listens on port 8000 by default (vllm/entrypoints/common/cli_args.py:286).

vllm/renderers/ (online_renderer.py · base.py · hf.py)

3 · AsyncLLM adds the request

vllm/v1/engine/async_llm.py · input_processor.py

The input processor makes an EngineCoreRequest. AsyncLLM registers a queue for the outputs of this request, then sends it to the engine core.

Code: process_inputs · queue and send · Also: async_llm.py · data contracts

EngineCoreRequest

From the API server to the engine core

4 · ZMQ and msgpack carry the request

vllm/v1/engine/core_client.py → vllm/v1/engine/core.py

The engine core client encodes the request with msgpack and sends it on a ZMQ ROUTER socket. An input thread in the engine core process receives it.

Code: send · msgpack · ROUTER · input thread · Also: processes and IPC

the request in the waiting queue

Engine core process

5 · EngineCore runs a step: the scheduler picks the work

vllm/v1/engine/core.py · vllm/v1/core/sched/scheduler.py

Each step schedules, executes the model and updates the requests. By default, async scheduling is on, and the loop runs step_with_batch_queue. The scheduler gives each request a number of tokens from the token budget and KV cache blocks for them.

Code: step_with_batch_queue · step_fn · async default · batch queue size · Also: the core loop · async scheduling · one step

SchedulerOutput: a direct call with one GPU; a shared-memory message queue to every worker process with more GPUs

Worker: engine core process (1 GPU) or one process per GPU

6 · The worker and Model Runner V2 run the model

vllm/v1/executor/uniproc_executor.py · multiproc_executor.py · vllm/v1/worker/gpu_worker.py · vllm/v1/worker/gpu/model_runner.py

The model runner builds the input tensors and the attention metadata. Then it runs the forward pass. At the default level O2, a decode batch with 1 token per request replays a FULL CUDA graph, and another batch uses PIECEWISE graphs. A batch larger than the largest captured size runs without a graph. The attention backend can lower the mode at start-up.

Code: execute_model · graph or eager · O2 mode · dispatch · lower mode · Also: executors · attention backends · one forward pass

logits

Worker: same process as box 6

7 · The sampler picks the next token

vllm/v1/worker/gpu/sample/sampler.py

Picks one token per request from the logits. With speculative decoding, a rejection sampler checks the draft tokens.

Code: sampler call · Also: speculative decoding · structured outputs

sampled token ids → update_from_output in the engine core → EngineCoreOutputs over ZMQ to the API server

API server process

8 · The output processor and the SSE stream

vllm/v1/engine/output_processor.py · chat_completion/serving.py

An output task in AsyncLLM detokenizes the new tokens and fills the queue of each request. The stream generator writes SSE chunks, and at the end data: [DONE].

Code: output_handler · process_outputs · [DONE] · Also: tool and reasoning parsers

How to read the map. Follow the left column from 1 to 8. Boxes 1 to 3 and 8 run in the API server process, the front end. Box 5 runs in the EngineCore process. Boxes 6 and 7 run in a worker, which owns one GPU. With one GPU, the worker runs inside the engine core process. With more GPUs, each worker is a separate process. Simplified

The map shows the default layout of vllm serve with one API server and one data-parallel rank. The full truth has more parts:

  • In vllm serve, the engine core always runs in its own process: AsyncLLM always makes a multiprocess client (vllm/v1/engine/async_llm.py:193). The variable VLLM_ENABLE_V1_MULTIPROCESSING (default 1, vllm/envs.py:1442-1443) decides this only for the offline LLMEngine (vllm/v1/engine/llm_engine.py:170, vllm/v1/engine/llm_engine.py:186-188).
  • With one GPU, the executor is uni (vllm/config/parallel.py:1099-1100). It runs the worker inside the engine core process (vllm/v1/executor/uniproc_executor.py:68). With more GPUs on one node, the executor is mp. It sends each step to all worker processes through a shared-memory message queue (vllm/v1/executor/multiproc_executor.py:342-353, vllm/v1/executor/multiproc_executor.py:428).
  • Async scheduling is on by default. It is off for pooling models and with some incompatible options (vllm/config/vllm.py:1664-1698). With async scheduling and Model Runner V2, the batch queue holds 2 steps on one GPU (vllm/config/vllm.py:587-597). So the engine core runs step_with_batch_queue instead of step (vllm/v1/engine/core.py:205-211, vllm/v1/engine/core.py:227-229). This version does not wait for a step right after it starts it, so the CPU work of the next step overlaps the GPU work. Async scheduling: overlap the CPU and the GPU explains it.
  • Not shown: several API servers, one engine core per data-parallel rank, the data-parallel coordinator, Ray, and the KV transfer between instances. The pages Data parallel serving: several engine cores behind one endpoint and Disaggregated prefill: prefill and decode on different instances explain them.

How to use this site#

  • Levels. Each page has a badge: Beginner, Intermediate or Advanced. A "Before you read" box lists the pages to read first.
  • Two depths on each page. A page starts with one sentence, a plain explanation and a diagram. Then it shows the real code. Deep dive boxes give the full detail: types, shapes, edge cases and environment variables.
  • Check yourself. Most pages end with 3 to 5 questions. Answer each one, then click "Show answer".
  • Search. Press /, then type a word, a file name or an environment variable.
  • Glossary. Words with a dotted line, such as EngineCore, are glossary terms. Point to them, or tap them on a phone, to see a short definition. Glossary lists all terms.
  • Code. The build copies every code excerpt from the repository. Every citation opens the file on GitHub at commit 3e44c0d.
  • DeepInfer links. A link with a small "↗" opens DeepInfer Explained or GitHub in a new tab.
  • Grey entries in the menu are pages that are not written yet. Diagrams open at full size when you click them.

What this site does not explain#

  • Kernel internals. The site shows how vLLM selects and calls a kernel (a device program), but not how the kernel works inside: not csrc/ (csrc/), and not the Triton, CUDA, CuTe or Helion kernel code.
  • Legacy code. V0 is gone; only aliases remain, for example AsyncLLMEngine = AsyncLLM (vllm/engine/async_llm_engine.py:6). Model Runner V2 is the default. Model Runner V1 (vllm/v1/worker/gpu_model_runner.py) gets one note on The model runner (Model Runner V2).
  • Outside libraries such as PyTorch, FlashAttention, FlashInfer, NCCL, Ray, ZMQ and FastAPI.
  • One paragraph only (on What vLLM is today): the experimental Rust front end (rust/) and the per-family model packages in vllm/models/ (vllm/models/). The special code of single model families is also out of scope; llama.py is the one model example.
