Tour: One forward pass

AdvancedGuided toursabout 27 min read + 8 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Tour: One engine step Advanced
  • The model runner (Model Runner V2) Advanced
  • The forward context: how layers find per-step data Advanced
  • torch.compile and CUDA graphs in vLLM Advanced

In one sentence

We follow one batch of 300 tokens from execute_model, through 32 Llama decoder layers and FlashAttention, to three sampled tokens.

The idea#

The tour Tour: One engine step shows one engine step from the side of the engine core. There, the forward pass is one line: the executor calls execute_model, and later sample_tokens. This tour opens that line. It walks the real code in the order it runs. It goes from the model runner into the model file, into one attention layer and the backend, and back to the sampler.

The forward pass has three layers of code. Model Runner V2 turns the plan of the scheduler into GPU tensors. The model code (llama.py) runs 32 decoder layers on these tensors. Inside each layer, the attention layer calls the attention backend, here FlashAttention. The transformer layers themselves are the ones of Inside a transformer↗; this tour shows only what vLLM adds around them.

Each stop links to the concept page that explains its part in depth. The tour does not repeat those deep dives. It shows how the parts connect, with the real shapes of one step.

An everyday comparison. Think of a car factory with a recorded robot line. The planning office (the model runner) prints the work order and lays out the parts in fixed bins. The robot line (the compiled pieces) replays its recorded moves. Between two robot cells, a human worker (the attention op) does the one task that changes with every car. At the end, the inspector (the sampler) picks the next order. The comparison stops here. The robots record their moves for a fixed list of batch sizes, so a batch is padded up to the next recorded size.

The example#

vllm serve meta-llama/Meta-Llama-3-8B-Instruct     # one H100 80 GiB GPU, default settings
  • Model. These values come from the model's Hugging Face config.json, not from the vLLM repository. 32 layers, hidden size 4096, intermediate size 14336. 32 query heads and 8 KV heads of size 128, vocabulary 128256, BF16 weights.
  • Engine. TP = 1, so the uni executor runs the worker inside the engine core process (vllm/config/parallel.py:1099-1100). Model Runner V2 is the default runner (vllm/config/vllm.py:713-748).
  • Compile and graphs. The default optimization level is O2 (vllm/config/vllm.py:434). It gives the compile mode VLLM_COMPILE and the CUDA graph mode FULL_AND_PIECEWISE (vllm/config/vllm.py:1806-1810, vllm/config/vllm.py:310).
  • Attention backend. On an H100 (compute capability 9.0) the priority list starts with FLASH_ATTN, and it accepts this layer (vllm/platforms/cuda.py:170-181). FlashAttention prefers version 3 on Hopper (vllm/v1/attention/backends/fa_utils.py:99-101). The page How vLLM chooses an attention backend explains the choice.
  • Budget. max_num_seqs = 1024 and max_num_batched_tokens = 8192, because the GPU has 70 GiB or more and is not an A100 (vllm/engine/arg_utils.py:2960-2993).

The batch of our step. Three requests are scheduled, 300 tokens in total:

RequestStateTokens this stepPositionsRequest slot
R1decodes; 540 tokens have KV in the cache15401023
R2decodes; 129 tokens have KV in the cache11291022
R3new; a 298-token prompt, no prefix cache hit298 (the whole prompt in one chunk)0 to 2971021

Simplified

The prompt lengths, the positions and the slot numbers are illustrative. The slots assume that R1, R2 and R3 arrived in this order on a fresh server. Slots are taken from the end of a free list (The model runner (Model Runner V2)). We assume block size 16, no LoRA, no speculative decoding, no structured output and no KV connector. The rules and the shapes are from the code.

What you will see#

  • Why this batch runs as a PIECEWISE CUDA graph of 304 tokens. Why the mode is chosen before any input exists (stop 2).
  • How the inputs are built on the GPU from the persistent request rows (stops 3 to 5).
  • Where the forward context is set, and how the call reaches the compiled model (stop 6).
  • One decoder layer with its shapes, and which implementation runs for each small op by default (stops 7 to 12).
  • Why the logits have only 3 rows, and which sampler draws the tokens (stops 13 and 14).

1execute_model starts and applies the plan#

We are at stop 5 of Tour: One engine step. The uni executor called Worker.execute_model, which hands the SchedulerOutput to the model runner (vllm/v1/worker/gpu_worker.py:1350-1353). Model Runner V2 keeps every running request in a fixed row, its request slot. So it first applies the changes of the plan to those rows:

  • R3 is new. add_requests gives it a slot, stores its 298 prompt ids, overwrites its block table row, and registers its sampling parameters with the sampler (vllm/v1/worker/gpu/model_runner.py:1214-1220, vllm/v1/worker/gpu/model_runner.py:1238-1245).
  • R1 and R2 run already. update_requests writes their computed-token counts into the CPU mirror. It appends new block ids only when the scheduler gave new blocks (vllm/v1/worker/gpu/model_runner.py:1257-1269).
  • Block tables. apply_staged_writes() copies all staged rows to the GPU tables in one go (line 1760).

The step has 300 tokens, so it does not return early at line 1766. The persistent rows and the staged writes are explained on The model runner (Model Runner V2).

What the data looks like now:

req_states.req_id_to_index = {"R1": 1023, "R2": 1022, "R3": 1021}
num_computed_tokens_np[[1023, 1022, 1021]] = [540, 129, 0]
prefill_len[1021] = 298                       # R3 has a prompt to fill
block table row 1021 = 19 block ids           # ceil(298 / 16) = 19 (derived)

2Sort the batch, then pick the CUDA graph mode#

Next, gather_batch_req_state puts the requests in batch order: requests with draft tokens first, then decodes, then the others by size (vllm/v1/worker/gpu/model_runner.py:2471-2483). R1 and R2 have 1 token each, which equals the decode query length, so the order is R1, R2, R3. The function also maps each batch row to its slot (idx_mapping_np) and finds that R3 is still in its prefill (vllm/v1/worker/gpu/model_runner.py:1310-1326).

A batch with a real prefill is not eligible for a decode graph, so the uniform decode token count is None (vllm/v1/worker/gpu/model_runner.py:1343-1373, vllm/v1/worker/utils.py:967-975). Then the runner asks the CUDA graph manager for a descriptor, before it builds any input:

With DP = 1 this is one call of CudaGraphManager.dispatch (vllm/v1/worker/gpu/dp_utils.py:265-279). The manager keeps a list of candidates for every token count up to 512. For 300 tokens, the candidates are the graphs of the next capture size, 304: the FULL decode graph first, then the PIECEWISE graph (vllm/v1/worker/gpu/cudagraph_utils.py:380-394).

  1. FULL, 304 tokens. Its uniform_token_count is 1, but our batch has None. Line 128 fails.
  2. PIECEWISE, 304 tokens. It has no uniform count and no request limit, and 304 ≥ 300. It matches.

So the step runs as a piecewise CUDA graph of 304 tokens. The capture sizes on this GPU go up to min(1024 × 1 × 2, 512) = 512, in steps of 16 above 256 (vllm/config/vllm.py:2440-2449, vllm/config/vllm.py:2566-2570). A batch above 512 tokens has no candidate and runs eagerly (lines 547-553 there). The rule and its reasons are on torch.compile and CUDA graphs in vLLM.

What the data looks like now:

req_ids        = ["R1", "R2", "R3"]
idx_mapping_np = [1023, 1022, 1021]
has_prefill    = True;  uniform_tok_count = None
batch_desc     = BatchExecutionDescriptor(cg_mode=PIECEWISE, num_tokens=304, num_reqs=None, ...)

Why the mode comes first

The padded size decides the length of every input slice, and the FULL mode needs metadata with padded sizes. So dispatch runs before prepare_inputs, and both later stops read batch_desc (vllm/v1/worker/gpu/model_runner.py:1835-1838, vllm/v1/worker/gpu/model_states/default.py:179-186).

3prepare_inputs builds the input tensors on the GPU#

prepare_inputs fills the persistent input buffers. Only two small arrays come from the CPU: idx_mapping, copied as int64 (vllm/v1/worker/gpu/model_runner.py:1393-1395), and query_start_loc:

The PIECEWISE descriptor has no request count, so num_reqs_padded stays 3 (line 1448). The token count is padded to 304 (vllm/v1/worker/gpu/model_runner.py:1383). Without draft tokens, each request gets exactly one logits row (vllm/v1/worker/gpu/model_runner.py:1401-1412). Then three GPU kernels read the request rows through idx_mapping:

  1. Lines 1470-1479. The batch has a prefill, so a kernel copies R3's 298 prompt ids from all_token_ids into input_ids.
  2. Lines 1482-1488. A kernel writes the positions and seq_lens = num_computed_tokens + query_len of each request.
  3. Lines 1493-1504. A kernel writes the last sampled token of R1 and R2 into input_ids, from last_sampled_tokens on the GPU. It also returns logits_indices, the last row of each request.

The CPU does not know the last tokens of R1 and R2 yet; the step before writes them on the GPU (engine-step tour, stop 6). The varlen layout is the one of Input metadata↗.

What the data looks like now (derived from our numbers):

query_start_loc int32 [4]   = [0, 1, 2, 300]           # entries 4..1024 of the buffer are also 300
input_ids       int32 [304] = [last token of R1, last token of R2, R3 prompt ids 0..297, 4 padding rows]
positions       int64 [304] = [540, 129, 0, 1, ..., 297, 4 padding rows]
seq_lens        int32 [3]   = [541, 130, 298]
logits_indices  int64 [3]   = [0, 1, 299]
is_padding      bool  [304] = 300 x False, 4 x True

The kernels do not write the 4 padding rows. is_padding marks them when VLLM_MOE_SKIP_PADDING is on, which is the default (vllm/v1/worker/gpu/model_runner.py:1385-1388, vllm/envs.py:1640), and the input buffers have fixed addresses, which the CUDA graphs need (vllm/v1/worker/gpu/input_batch.py:19-31).

4prepare_attn: block tables and slot mappings#

Llama-3-8B has one KV cache group, so both results have one entry. gather_block_tables copies the block table rows of slots 1023, 1022 and 1021 into a second tensor, in batch order. compute_slot_mappings gives each token its slot in the KV cache: block_number × block_size + offset (vllm/v1/worker/gpu/block_table.py:409). The 4 padding rows get PAD_SLOT_ID = -1 (vllm/v1/worker/gpu/block_table.py:257-260, vllm/v1/attention/backends/utils.py:53).

What the data looks like now (block size 16, derived):

block_tables[0]  int32 [3, max_num_blocks]    # rows of R1, R2, R3
slot_mappings    int64 [1, 304]
  R1, position 540 -> block index 33, offset 12  (540 = 33 x 16 + 12)
  R2, position 129 -> block index 8,  offset 1   (129 = 8 x 16 + 1)
  R3, positions 0..297 -> block indexes 0..18, the last one holds 10 tokens
  rows 300..303 -> -1

The block ids themselves come from the scheduler's block pool (The KV cache manager: blocks, the block pool and memory sizing). The runner only mirrors them.

5The attention metadata: one object for 32 layers#

Back in execute_model, the runner makes a dict from layer name to slot mapping (vllm/v1/worker/gpu/model_runner.py:1924-1928, vllm/v1/worker/gpu/attn_utils.py:447-455). Then the default model state builds the attention metadata (vllm/v1/worker/gpu/model_runner.py:1940-1951). In PIECEWISE and eager mode it uses the unpadded sizes, 3 requests and 300 tokens (vllm/v1/worker/gpu/model_states/default.py:179-186). For each KV cache group, build_attn_metadata makes one CommonAttentionMetadata:

The metadata builder of the FlashAttention backend turns it into FlashAttentionMetadata. It copies most fields straight from the common metadata (vllm/v1/attention/backends/flash_attn.py:812-829). All 32 layers share one backend and one KV cache spec, so they form one attention group. The same object goes under all 32 layer names (vllm/v1/worker/gpu/attn_utils.py:574-580).

What the data looks like now:

CommonAttentionMetadata(num_reqs=3, num_actual_tokens=300,
    query_start_loc=[0, 1, 2, 300], seq_lens=[541, 130, 298],
    max_query_len=298, max_seq_len=541,
    block_table_tensor=int32 [3, max_num_blocks], slot_mapping=int64 [304], causal=True)
attn_metadata = {"model.layers.0.self_attn.attn": m, ..., "model.layers.31.self_attn.attn": m}

max_query_len and max_seq_len come from CPU arrays, so this stop needs no GPU-to-CPU copy (vllm/v1/worker/gpu/model_states/default.py:191-199). The three classes of a backend are explained on Attention backends: backend, metadata builder and implementation.

6set_forward_context, and the call into the model#

The model inputs are the ids and the positions; inputs_embeds and intermediate_tensors are None, and the model state adds nothing for Llama (vllm/v1/worker/gpu/model_runner.py:1984-1992). The metadata does not go into the call. The runner puts it into the forward context around the call:

  1. Lines 2035-2039. The BatchDescriptor holds the padded token count, 304, and the LoRA flags.
  2. Lines 2041-2053. set_forward_context installs the metadata dict, the slot mapping dict, the mode PIECEWISE and the descriptor for the duration of the with block (vllm/forward_context.py:345-360).
  3. Lines 2060-2067. In PIECEWISE mode, run_pw_graph calls the model object directly, because breakable CUDA graphs are off for Llama (vllm/v1/worker/gpu/cudagraph_utils.py:578-583). They turn on by default only for the architectures in a fixed list, and LlamaForCausalLM is not in it (vllm/config/vllm.py:75-107, vllm/config/vllm.py:824-833).

self.model is LlamaForCausalLM. Its forward only calls the inner LlamaModel with the four arguments (vllm/model_executor/models/llama.py:534-544). The page The forward context: how layers find per-step data explains the two dicts and why the attention ops read them by name.

7The compiled LlamaModel: embedding and layer loop#

LlamaModel carries @support_torch_compile, with dimension 0 of the ids and positions dynamic (vllm/model_executor/models/llama.py:337-346). The first call, in the profile run at start-up, compiled the model (vllm/v1/worker/gpu_worker.py:680-697, torch.compile and CUDA graphs in vLLM). So this call goes to the compiled code (vllm/compilation/decorators.py:533-551). The compiled graph is cut at the attention ops into 33 pieces. Each piece sits in a CUDAGraphWrapper. A wrapper replays its graph only when the forward context says PIECEWISE (vllm/compilation/cuda_graph.py:242-256):

So the GPU work of this stop is 33 graph replays for the 304-token descriptor, with 32 eager attention calls between them (stop 10). The source code that was traced is this:

  • Line 418. On TP = 1, the embedding is a plain lookup (vllm/model_executor/layers/vocab_parallel_embedding.py:522-525). It turns input_ids [304] into hidden_states [304, 4096] BF16.
  • Line 419. There is no residual yet. Layer 0 starts it (stop 8).
  • Lines 432-438. The loop runs all 32 layers, because with PP = 1 this rank owns layers 0 to 31. Each layer returns (hidden_states, residual).

Piece 0 holds the embedding and the start of layer 0. Each later piece holds the end of one layer and the start of the next; the facts are on torch.compile and CUDA graphs in vLLM. The diagram below shows one layer.

8Inside a decoder layer: fused add + RMSNorm#

The layer keeps the residual outside the norm. Layer 0 has no residual, so it calls a plain RMSNorm (lines 320-322). Layers 1 to 31 call input_layernorm(hidden_states, residual), which adds and normalizes in one call (line 324). post_attention_layernorm does the same after attention (line 328).

RMSNorm is a CustomOp. With Inductor compilation, the default of vllm serve, vLLM adds "none" to the custom op list, so the op is disabled (vllm/config/vllm.py:1819-1826). A disabled op uses forward_native (vllm/model_executor/custom_op.py:189-192). For RMSNorm, that method calls an IR op:

The IR op is one node in the traced graph. During compilation, a lowering pass replaces each IR node with the implementation that the priority list selects (vllm/compilation/passes/ir/lowering_pass.py:41-67, vllm/compilation/passes/pass_manager.py:122-124). On CUDA with Inductor, the list for fused_add_rms_norm is ["native"] (vllm/platforms/cuda.py:716-732). So the native PyTorch body runs, compiled by Inductor inside the piece, and not the vllm_c kernel. The native body adds in FP32, keeps the sum as the new residual, and normalizes (vllm/ir/ops/layernorm.py:43-62).

What the data looks like now: x [304, 4096] BF16 (normalized) and residual [304, 4096] BF16 (the sum). The two switches are explained on CustomOp, out-of-tree ops and IR op providers.

9QKVParallelLinear and the rotary embedding#

  1. Line 229. qkv_proj is a QKVParallelLinear. With TP = 1 its weight is [6144, 4096]: 32 query heads plus 2 × 8 KV heads, times 128 (The tensor-parallel layers (linear.py and vocab_parallel_embedding.py)). The forward is one GEMM through the quantize method, and no collective (vllm/model_executor/layers/linear.py:616-634). For BF16 on CUDA, the default GEMM is torch.nn.functional.linear (vllm/model_executor/layers/utils.py:83-89, vllm/model_executor/layers/utils.py:689-691).
  2. Line 230. The split uses the per-rank sizes: q_size = 32 × 128 = 4096, kv_size = 8 × 128 = 1024 (vllm/model_executor/models/llama.py:156-161).
  3. Line 231. The rotary embedding rotates q and k by the positions of stop 3. It is a CustomOp too (vllm/model_executor/layers/rotary_embedding/base.py:14-15), so by default it runs forward_native: a lookup in cos_sin_cache by position, then the rotation of each head (vllm/model_executor/layers/rotary_embedding/base.py:160-219). The model's config.json on the Hugging Face Hub has no rope_scaling, so get_rope takes the default branch and builds a plain RotaryEmbedding (vllm/model_executor/layers/rotary_embedding/__init__.py:63-65, vllm/model_executor/layers/rotary_embedding/__init__.py:147-155).

What the data looks like now: qkv [304, 6144] → q [304, 4096], k [304, 1024], v [304, 1024], all BF16. RoPE keeps the shapes. RoPE itself is explained in Inside a transformer↗.

10Attention: two custom ops, a lookup by name, and FlashAttention#

self.attn(q, k, v) calls Attention.forward. It makes the output buffer [304, 4096] and views the inputs per head: q as [304, 32, 128], k and v as [304, 8, 128] (vllm/model_executor/layers/attention/attention.py:525-540). CUDA wants one opaque op for attention, so use_direct_call is false (vllm/model_executor/layers/attention/attention.py:436-440), and the layer calls two registered ops:

These two ops are splitting ops, so this part runs eagerly between piece i and piece i + 1. Both ops resolve the layer name in the forward context of stop 6:

  1. unified_kv_cache_update. FlashAttention writes the cache in a separate op (vllm/v1/attention/backends/flash_attn.py:367). The op calls impl.do_kv_cache_update with the slot mapping of stop 4 (vllm/model_executor/layers/attention/attention.py:734-748). That method scatters the new keys and values into this layer's cache view by slot (vllm/v1/attention/backends/flash_attn.py:1443-1464). A comment there says that the slot mapping is not padded (lines 1450-1454). This comment is stale: here the slot mapping has 304 entries, and rows 300 to 303 hold -1 (stop 4).
  2. unified_attention_with_output. It takes the empty tensor of the first op as a dummy argument, so the compiler keeps the order. Then it calls impl.forward(self, query, key, value, kv_cache, attn_metadata, output=output) (vllm/model_executor/layers/attention/attention.py:779-796).

FlashAttentionImpl.forward splits the cache view [num_blocks, 8, 16, 256] into a key half and a value half (vllm/v1/attention/backends/flash_attn.py:1254-1255). It reads the batch layout from the metadata, then calls the kernel with the first num_actual_tokens rows only:

The arguments come from stop 5: cu_seqlens_q is query_start_loc, seqused_k is seq_lens, and the block table maps each request to its blocks (vllm/v1/attention/backends/flash_attn.py:1279-1284). The wrapper object ends in flash_attn_varlen_func (vllm/v1/attention/backends/flash_attn.py:275-283, vllm/v1/attention/backends/flash_attn.py:113-116). The kernel itself is out of scope. For our batch it computes causal attention for 300 query rows: R1 reads 541 keys, R2 130 keys and R3 298 keys. Attention itself is explained in Attention↗.

What the data looks like now: the KV cache of this layer holds the new keys and values at the 300 slots. output [304, 4096] holds the attention result in its first 300 rows. In this step, get_attention_context runs 64 times: two ops in each of 32 layers.

11o_proj and the MLP#

o_proj starts piece i + 1. It is a row-parallel linear layer layer with weight [4096, 4096]. It calls the all-reduce only with TP > 1, so on our one GPU it is one GEMM (vllm/model_executor/layers/linear.py:1797-1806). Then post_attention_layernorm does the second fused add + RMSNorm (stop 8), and the MLP runs:

  1. Line 119. gate_up_proj is a column-parallel linear layer MergedColumnParallelLinear with weight [28672, 4096]: gate and up stacked. Output [304, 28672].
  2. Line 120. maybe_fused_act_quant fuses the activation with a quantization of the next input only when down_proj wants a quantized input. For BF16 it just calls act_fn(x) (vllm/model_executor/layers/fusion/fused_act_quant.py:206-213). SiluAndMul is a disabled CustomOp, so it runs forward_native: silu(x[..., :d]) * x[..., d:] (vllm/model_executor/layers/activation.py:140-144). Output [304, 14336].
  3. Line 121. down_proj is row-parallel with weight [4096, 14336]. Output [304, 4096], again without an all-reduce.

The layer returns (hidden_states, residual), both [304, 4096], to the loop of stop 7. Stops 8 to 11 repeat for each of the 32 layers. The layer classes and their slices are on The tensor-parallel layers (linear.py and vocab_parallel_embedding.py); the weights in them were loaded at start-up ("Weight loading: from checkpoint files to GPU parameters").

12The final norm; the hidden states are kept#

After layer 31, the last piece applies the final norm. It is the last fused add + RMSNorm, and the new residual is not used (vllm/model_executor/models/llama.py:452-457). The model returns hidden_states [304, 4096], not logits: compute_logits is a method of the outer class and stays outside the compiled graph (How a vLLM model file is written (llama.py)).

Back in the runner, the forward context closes. The runner does not return the hidden states. It stores them with the input batch and the metadata, and returns None:

The Python code returns as soon as all kernels are queued. The GPU may still run the first layers. The uni executor wraps None in a finished future, and the engine core goes on (engine-step tour, stops 7 and 8).

What the data looks like now:

execute_model_state = ExecuteModelState(input_batch=..., attn_metadata={32 names: m},

13sample_tokens: logits for three rows#

The engine core calls sample_tokens(None) (no grammar bitmask). The runner takes the stored state, and on the last PP rank it calls self.sample (vllm/v1/worker/gpu/model_runner.py:2117-2131, vllm/v1/worker/gpu/model_runner.py:2163-2165). Batch-sharded sampling is off, so the plain path runs:

hidden_states[logits_indices] keeps rows 0, 1 and 299: the last row of each request. The other 301 rows never become logits. compute_logits calls the LogitsProcessor with the LM head (vllm/model_executor/models/llama.py:546-551):

The head runs in the model dtype by default for a generation model (vllm/config/model.py:2540-2545, vllm/model_executor/layers/logits_processor.py:143-146). With TP = 1 there is no gather (line 193). The vocabulary 128256 is a multiple of 64, so the slice at line 198 cuts nothing (The tensor-parallel layers (linear.py and vocab_parallel_embedding.py)).

What the data looks like now: sample_hidden_states [3, 4096] and logits [3, 128256] BF16 (769,536 bytes).

14The sampler and the AsyncOutput#

Without draft tokens, the plain Sampler runs (vllm/v1/worker/gpu/model_runner.py:1663-1665). Our requests send no sampling fields, so the server defaults come from the model's generation_config.json (The OpenAI-compatible API). For this model that file sets temperature 0.6 and top-p 0.9 (from the Hugging Face Hub, not from the vLLM repository). Temperature 0.6 needs processing, so the sampler copies the logits to FP32 and applies the temperature (vllm/v1/worker/gpu/sample/states.py:67-72, vllm/v1/worker/gpu/sample/sampler.py:238-265). Then it picks the sampling method:

  • Top-p is set, and no request is greedy, seeded or asks for processed logprobs. So the batch is eligible for the fused sampler.
  • use_flashinfer needs two things. First, the sampling mask is off, which is the default. Second, FlashInfer's sampler supports the GPU: CUDA, a supported compute capability, more than 16 SMs, and a working FlashInfer JIT build. VLLM_USE_FLASHINFER_SAMPLER defaults to on (vllm/v1/worker/gpu/sample/sampler.py:88-90, vllm/envs.py:886-890, vllm/v1/sample/ops/topk_topp_sampler.py:118-150). An H100 has more than 100 SMs. Then FlashInfer's fused top-k/top-p sampler draws the tokens (vllm/v1/worker/gpu/sample/sampler.py:339-343).
  • Otherwise, top-k/top-p masking and the Gumbel sampler run (lines 346-359).

R3's sequence length equals its prompt length, so R3 is not in a chunked prefill and samples its first token. All three rows count (vllm/v1/worker/gpu/sample/sampler.py:190-199). The runner then starts the copy to the CPU before it updates its own state, and returns the AsyncOutput:

The copy waits for the main stream on a second stream, copies into pinned CPU memory, and records copy_event (vllm/v1/worker/gpu/async_utils.py:137-171). postprocess_sampled writes the three new tokens into last_sampled_tokens on the GPU, for the next step (vllm/v1/worker/gpu/model_runner.py:2244-2255). The function returns async_output without a wait (vllm/v1/worker/gpu/model_runner.py:2311). The engine core calls get_output() later, which is the only wait for the GPU (vllm/v1/worker/gpu/async_utils.py:173-184; engine-step tour, stop 10). Sampling methods are explained in Sampling↗.

What changes with TP = 2

With --tensor-parallel-size 2, two worker processes run stops 1 to 14, one per GPU. Only worker 0 replies (Tour: One engine step, its deep dive "What changes with TP = 2"). Each rank holds half of the heads and half of the MLP (The tensor-parallel layers (linear.py and vocab_parallel_embedding.py)). Per rank, for T = 304:

So one step has 2 × 32 + 1 = 65 all-reduces of [304, 4096] BF16 (2.375 MiB each) and one all-gather of the logits. Every built-in platform uses the all-gather (vllm/platforms/interface.py:1275-1278). Batch-sharded sampling, which would change the logits step, is off by default (vllm/config/parallel.py:192-198). On CUDA the all-reduce is the registered op torch.ops.vllm.all_reduce, so it sits inside the compiled pieces as one opaque node (vllm/distributed/parallel_state.py:740-746).

At O2, the pass fuse_allreduce_rms turns on only with TP > 1 on CUDA with FlashInfer and compute capability 9.0 or the 10.x family (vllm/config/vllm.py:178-202, vllm/config/vllm.py:301). On an H100 with FlashInfer installed, the pass can fuse an all-reduce with the RMSNorm after it. For TP = 2 on compute capability 9.0 its size limit is 64 MiB, which covers all batches up to 8192 tokens (vllm/compilation/passes/fusion/allreduce_rms_fusion.py:104-108, vllm/compilation/passes/fusion/allreduce_rms_fusion.py:1023-1028, vllm/compilation/passes/fusion/allreduce_rms_fusion.py:1128-1132). The tour Tour: One step across GPUs follows such a step across the processes.

Deep dive

What changes with --enforce-eager

--enforce-eager sets the compile mode and the CUDA graph mode to NONE (vllm/config/vllm.py:1745-1747). Four stops change:

  1. Stop 2. The CUDA graph manager builds no candidates when the mode is NONE (vllm/v1/worker/gpu/cudagraph_utils.py:256-260), and the worker does not capture graphs (vllm/v1/worker/gpu_worker.py:983-985). So dispatch returns NONE for every batch, and the token count is not padded: T = 300.
  2. Stop 6. The runner calls self.model(**model_inputs) directly (line 2070). The forward context is still set, with mode NONE.
  3. Stop 7. With compile mode NONE, @support_torch_compile sets do_not_compile (vllm/compilation/decorators.py:411-418). So LlamaModel.forward runs as Python, op by op, and there are no pieces.
  4. Stops 8, 9 and 11. Without Inductor, the custom op list gets "all" (vllm/config/vllm.py:1819-1826). So the CustomOps are enabled and use forward_cuda (vllm/model_executor/custom_op.py:194-205):
    • RMSNorm: forward_cuda calls forward_native, which calls the IR op at run time (vllm/model_executor/layers/layernorm.py:101-120). The CUDA priority is now ["vllm_c", "native"], so the vllm_c kernel runs when it accepts the arguments (vllm/platforms/cuda.py:716-720).
    • SiluAndMul: torch.ops._C.silu_and_mul writes into a new [300, 14336] tensor (vllm/model_executor/layers/activation.py:138, vllm/model_executor/layers/activation.py:146-151).
    • RoPE: ops.rotary_embedding changes q and k in place (vllm/model_executor/layers/rotary_embedding/base.py:221-250).

The attention ops of stop 10 do not change: they are the same custom ops, called through torch.ops.vllm. Every kernel is now a separate launch from Python, so the CPU cost of a step grows. The page torch.compile and CUDA graphs in vLLM compares the levels.

Deep dive

What changes in a FULL decode-only step

Take the next step: R1, R2 and R3 all decode, so the batch has 3 tokens, 1 per request. (Derived from stop 14: R3 sampled its first token.)

  1. Stop 2. The batch has no prefill and a uniform count of 1, which equals the decode query length. The candidates for 3 tokens are the graphs of size 4. The FULL graph has uniform_token_count = 1 and 4 request slots, so it matches first (vllm/v1/worker/gpu/cudagraph_utils.py:125-138).
  2. Stop 3. The FULL descriptor has a request count, so num_reqs_padded = 4 (vllm/v1/worker/gpu/model_runner.py:1448). The positions are [541, 130, 298]; the fourth request is padding with seq_len = 0 (vllm/v1/worker/gpu/input_batch.py:393-394).
  3. Stop 5. The metadata is built with the padded sizes: 4 requests, 4 tokens (vllm/v1/worker/gpu/model_states/default.py:179-182).
  4. Stops 6 to 12. The runner replays one captured graph and does not call set_forward_context (vllm/v1/worker/gpu/model_runner.py:2024-2032). No Python code of the model runs, so get_attention_context runs 0 times. The graph reads the persistent input buffers, which stops 3 and 4 just wrote (comment at lines 2026-2027).
  5. Stops 13 and 14. No change: logits for 3 rows, 3 sampled tokens.

FlashAttention 3 reports ALWAYS as its CUDA graph support, so the FULL graphs stay after start-up (vllm/v1/attention/backends/flash_attn.py:617-621). The page The forward context: how layers find per-step data explains why the context is not needed during replay.

Deep dive

What changes with a prefix-cache hit

Suppose an earlier request had the same first 288 prompt tokens as R3. Prefix caching in the engine core: hashes, lookup, caching, eviction and KV events then finds 18 full cached blocks. The hit never covers the whole prompt, because the last token must be computed again for its logits (vllm/v1/core/kv_cache_manager.py:289-295).

  1. Scheduler. R3 arrives with num_computed_tokens = 288 and gets 10 tokens. The batch has 1 + 1 + 10 = 12 tokens.
  2. Stop 1. add_requests stores 288 as the computed count of slot 1021 (vllm/v1/worker/gpu/model_runner.py:1214-1220). R3's block table row lists the 18 cached blocks first, then 1 new block (derived). The scheduler sends all blocks of the request (vllm/v1/core/sched/scheduler.py:1432-1434). The KV cache manager adds the cached blocks before the new ones (vllm/v1/core/single_type_kv_cache_manager.py:314, vllm/v1/core/single_type_kv_cache_manager.py:407).
  3. Stop 2. 12 tokens, still a prefill: PIECEWISE with the next capture size, 16.
  4. Stop 3. query_start_loc = [0, 1, 2, 12], R3's positions 288 to 297, seq_lens = [541, 130, 298], logits_indices = [0, 1, 11] (derived).
  5. Stop 10. For R3, the update op writes only 10 new key and value rows per layer, into block index 18. The attention for R3 still reads all 298 keys: 288 from the cached blocks and 10 new ones.

The model computes 16 rows (12 real, 4 padding) instead of 304 in every linear layer. R3 still samples its first token in this step, because the step ends its prompt.

Deep dive

What changes with an MLA model

Models with multi-head latent attention, such as DeepSeek-V3, do not use the Attention layer. Their attention module builds an MLAAttention layer (vllm/model_executor/layers/mla.py:122). On an H100 the MLA priority list picks FLASH_ATTN_MLA (How vLLM chooses an attention backend). Stop 10 changes most:

  • The custom ops are unified_mla_kv_cache_update and unified_mla_attention_with_output (vllm/model_executor/layers/attention/mla_attention.py:1475-1479, vllm/model_executor/layers/attention/mla_attention.py:1524-1530). They are splitting ops too, so the piece structure stays.
  • The cache holds one compressed latent vector per token, with a head size of 576 = 512 + 64 (vllm/v1/attention/backends/fa_utils.py:338-339).
  • The layer sends the first num_decode_tokens rows to forward_mqa and the rest to forward_mha (vllm/model_executor/layers/attention/mla_attention.py:984-985, vllm/model_executor/layers/attention/mla_attention.py:1017-1020, vllm/model_executor/layers/attention/mla_attention.py:1132). The builder finds the split with split_decodes_and_prefills (vllm/model_executor/layers/attention/mla_attention.py:2605-2612).

For our batch, R1 and R2 would be the 2 decode rows, and R3's 298 rows would take the prefill path. This works only because stop 2 puts the decodes first (vllm/v1/worker/gpu/model_runner.py:2476-2483). The two paths are described on Attention backends: backend, metadata builder and implementation.

What can go wrong#

  • A large batch loses its CUDA graph. A step above 512 tokens has no candidate and runs eagerly (vllm/v1/worker/gpu/cudagraph_utils.py:547-553). Each of the 33 pieces then launches its Inductor kernels one by one, without a graph. For long prefill chunks the GPU time is much larger, so this costs little.
  • A model call outside the runner. If you call the model in a script without set_forward_context, the attention op fails: "Forward context is not set" (vllm/forward_context.py:210-213).
  • A GPU-to-CPU wait in the forward path. A .item() or .cpu() in stops 1 to 14 stops the CPU until the GPU is done, and the overlap of async scheduling is lost. The worker methods have a debug check for this (vllm/v1/worker/gpu_worker.py:1316-1327). Batch-size logging with VLLM_LOG_BATCHSIZE_INTERVAL also synchronizes, in the eager and PIECEWISE steps (vllm/forward_context.py:295, vllm/forward_context.py:363-370).
  • An IR op that does not lower. If the lowering pass leaves an IR node in the graph, it logs the warning "Failed to lower vLLM IR ops" (vllm/compilation/passes/ir/lowering_pass.py:99-111).
  • Another activation. LlamaMLP accepts only silu; any other hidden_act raises ValueError when the model is built (vllm/model_executor/models/llama.py:112-115).

Why it matters. Every token that vllm serve returns comes out of this path. When you read a profile, you can now map each kernel to a stop. Stops 1 to 5 give small kernels and copies. Stops 7 to 12 give graph replays and eager attention. Stops 13 and 14 give logits and sampling. When you change TP, --enforce-eager or the batch size, the deep dives tell you which stops change.

    Why does the step of this tour run as a PIECEWISE graph and not as a FULL graph?

    R3 is in its prefill, so the batch is not eligible for a decode graph, and the uniform decode token count is None (vllm/v1/worker/gpu/model_runner.py:1343-1373). The FULL graph of size 304 needs a uniform count of 1, so _is_compatible fails. The PIECEWISE graph of 304 has no such condition and matches (vllm/v1/worker/gpu/cudagraph_utils.py:125-138).

  2. 2
    How many rows of logits does the step compute, and which rows of the hidden states are they?
    medium
    Show answer

    Three: rows 0, 1 and 299 of hidden_states [304, 4096], the last row of each request. combine_sampled_and_draft_tokens returns them as logits_indices, and sample calls compute_logits on hidden_states[logits_indices] only (vllm/v1/worker/gpu/model_runner.py:1493-1504, vllm/v1/worker/gpu/model_runner.py:1636-1638).

  3. 3
    Which implementation of the fused add + RMSNorm runs by default, and why not the vllm_c kernel?
    medium
    Show answer

    The native PyTorch body of the IR op fused_add_rms_norm, compiled by Inductor inside the piece. RMSNorm is a disabled CustomOp under Inductor, so it uses forward_native, which calls the IR op (vllm/config/vllm.py:1819-1826, vllm/model_executor/layers/layernorm.py:79-99). The lowering pass picks the provider from the priority list, which is ["native"] on CUDA with Inductor (vllm/platforms/cuda.py:716-732).

  4. 4
    How does unified_attention_with_output find the KV cache and the metadata, when LlamaAttention.forward passes only q, k and v?
    hard
    Show answer

    The layer passes its name to the op. get_attention_context reads the metadata from forward_context.attn_metadata[name], the layer from no_compile_layers[name], and the KV cache from layer.kv_cache (vllm/model_executor/layers/attention/attention.py:705-723). The runner set the context around the model call (vllm/v1/worker/gpu/model_runner.py:2041-2053), and the same metadata object is stored under all 32 names (vllm/v1/worker/gpu/attn_utils.py:579-580).

  5. 5
    With TP = 2, how many all-reduces does our step need, and what happens to the logits?
    hard
    Show answer

    65: two per layer (o_proj and down_proj, vllm/model_executor/layers/linear.py:1803-1806) times 32, plus one in the embedding (vllm/model_executor/layers/vocab_parallel_embedding.py:558-563). Each rank computes logits [3, 64128] for its half of the vocabulary, and an all-gather makes [3, 128256] on every rank (vllm/model_executor/layers/logits_processor.py:122-134).
