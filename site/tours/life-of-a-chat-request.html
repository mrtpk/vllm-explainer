Tour: Life of a chat request

BeginnerGuided toursabout 29 min read + 18 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

  • The OpenAI-compatible API Beginner

In one sentence

We follow one streaming chat request from the FastAPI route, through the engine core process and the GPU, to the last SSE chunk.

The idea#

vllm serve starts an OpenAI-compatible server. A client sends a chat request as JSON and gets the answer back as a stream of small pieces. This tour follows one such request through the code, from the HTTP route to the last piece, data: [DONE].

The request crosses two processes. The front end is the API server process: FastAPI, the chat template, the tokenizer and AsyncLLM. The engine core process holds the scheduler and, with one GPU, also the worker and the model runner. The two processes talk through ZMQ sockets. The messages are msgpack bytes.

The engine core does not run one request from start to end. It runs steps. In each step it selects a batch of requests, runs the model once for all of them and adds one new token to each request. So our request goes through the engine step once for each output token. Each new token goes back to the front end and becomes one SSE chunk. The idea of steps and continuous batching is not new: see Batching↗.

An everyday comparison. Think of a restaurant with a waiter and a kitchen. The waiter (the front end) writes the order on a ticket and passes it through a window (ZMQ). The kitchen (the engine core) cooks in rounds for all open orders. After each round, the waiter carries the new part of the dish to the table at once (streaming). The comparison stops being true in two places. A round adds only one token to each order, so an order needs hundreds of rounds. And the waiter must translate each part (token ids) into text before the guest can read it.

The example request#

We start the server on one GPU with a chat model, and run the example client of the repository with --stream:

vllm serve Qwen/Qwen2.5-1.5B-Instruct          # any chat model; one GPU, default settings
python examples/basic/online_serving/openai_chat_completion_client.py --stream

The client sends four messages: a system message, a user question, an assistant answer and a second user question (examples/basic/online_serving/openai_chat_completion_client.py:16-24). It calls client.chat.completions.create(..., stream=args.stream) (examples/basic/online_serving/openai_chat_completion_client.py:46-50). On the wire this is one HTTP request:

POST /v1/chat/completions
{"model": "Qwen/Qwen2.5-1.5B-Instruct", "stream": true,
 "messages": [{"role": "system", "content": "You are a helpful assistant."},
              {"role": "user", "content": "Who won the world series in 2020?"},
              {"role": "assistant", "content": "The Los Angeles Dodgers won the World Series in 2020."},
              {"role": "user", "content": "Where was it played?"}]}

The model name and all numbers in this tour (61 prompt tokens, 48 cached tokens, the token ids) are illustrative. The tour assumes a ChatML-style chat template, like the one in examples/template_chatml.jinja. Other models have other templates, so their prompts have other lengths.

1The route receives POST /v1/chat/completions#

We are in vllm/entrypoints/openai/chat_completion/api_router.py. With one API server, vllm serve runs the server in the CLI process itself (uvloop.run(run_server(args)), vllm/entrypoints/cli/serve.py:154-156). FastAPI parses the JSON body into a ChatCompletionRequest object and calls the route function:

2OpenAIServingChat makes the sampling parameters and a generator#

We are in vllm/entrypoints/openai/chat_completion/serving.py, in OpenAIServingChat._create_chat_completion. It renders the prompt (stop 3), makes the request id, computes max_tokens and the SamplingParams, and asks the engine client for a result generator:

  1. Line 314: render_chat_request first checks the model name and runs _preflight, then calls the renderer (vllm/entrypoints/openai/chat_completion/serving.py:278-285).
  2. Lines 320-322: the request id is "chatcmpl-" + request_id.
  3. Line 349: get_max_tokens takes the smallest of max_model_len - prompt_len, the request value (or the server default), an optional override and a platform limit (vllm/entrypoints/serve/utils/api_utils.py:253-270). The client sends no max_tokens. So, if the generation config of the model sets no default either, the model length limits the answer.
  4. Line 366: to_sampling_params sets output_kind = DELTA because stream is true (vllm/entrypoints/openai/chat_completion/protocol.py:797-799). DELTA means: each output carries only the new tokens.
  5. Line 396: self.engine_client.generate(...) is AsyncLLM.generate. It is an async generator function, so this call does not run it. It only makes the generator object.
  6. Lines 415-416: the serving class returns another generator, chat_completion_stream_generator, which wraps the first one.

The 200 status goes out before the engine sees the request

AsyncLLM.generate() has not run yet. (Only the admission check of _preflight has asked the engine client.) The route returns the StreamingResponse, and the HTTP response starts. The request reaches the engine only when the stream pulls its first chunk (stop 4). So errors after this point arrive as data: chunks, not as HTTP error codes. The docstring of _preflight gives this reason for its early checks (vllm/entrypoints/generate/base/serving.py:169-181).

Stop 2 in detail: where the sampling defaults come from

For each sampling field, to_sampling_params uses the request value, then the server default, then the OpenAI default: "Priority: user -> server default -> OpenAI default" (vllm/entrypoints/openai/chat_completion/protocol.py:740-748). Server-default stop token ids are merged with the request stop ids (vllm/entrypoints/openai/chat_completion/protocol.py:754-764). The request can ask for a larger stream interval with stream_interval. The field description says values below the server setting are clamped up to it (vllm/entrypoints/openai/chat_completion/protocol.py:543-551). The server default --stream-interval is 1 (vllm/config/scheduler.py:216).

_preflight raises the engine's dead error if the engine has failed, and calls check_admission (vllm/entrypoints/generate/base/serving.py:179-181). Admission control rejects a request with HTTP 503 when max_num_queued_reqs or max_num_queued_tokens is set and full (vllm/v1/engine/async_llm.py:325-383).

The example in the code block uses max_model_len = 32768. That value comes from the model config, not from vLLM, so it is illustrative.

3The chat template and the tokenizer make token ids#

The model reads one sequence of token ids, not a list of messages. The chat template (a Jinja template from the tokenizer files) writes the messages into one text, with special marker tokens. Then the tokenizer cuts the text into ids. Tokens and tokenizers are explained in Tokens and tokenizers↗.

We are in the renderer. OnlineRenderer.preprocess_chat calls renderer.render_chat_async (vllm/renderers/online_renderer.py:805-808). For a Hugging Face tokenizer, it asks the template for text, not ids: tokenize is true only for Mistral tokenizers or prompt embeddings (vllm/renderers/online_renderer.py:774-781).

  1. Line 1380: arrival_time is set here. The TTFT metric of vLLM starts at this moment (see Deep dive, timing).
  2. Line 1386: render_messages_async applies the chat template.
  3. Line 1396: tokenize_prompts_async turns the text into ids.
  4. Line 1404: process_for_engine_async makes the engine input and stores arrival_time in it (vllm/renderers/base.py:1255-1276).

Both blocking jobs run in a thread pool, so they do not block the asyncio event loop. The HF renderer wraps safe_apply_chat_template with make_async (vllm/renderers/hf.py:1011-1013) and calls it with a timeout:

The tokenizer call goes to the same kind of pool: _tokenize_prompt_async = make_async(self._tokenize_prompt, executor=self._executor) (vllm/renderers/base.py:156-158). _tokenize_prompt calls tokenizer(prompt["prompt"], **kwargs) (vllm/renderers/base.py:663-678).

Stop 3 in detail: template resolution, timeout and errors

  • safe_apply_chat_template resolves the template in four steps (vllm/renderers/hf.py:264-319). The order is: the given template (trusted request or --chat-template), the processor template (no tools only), the tokenizer template, a built-in fallback. With no template it raises ChatTemplateResolutionError (vllm/renderers/hf.py:836-847). Details: Renderers and chat templates: from messages to token ids.
  • A developer message becomes a system message when the template does not know that role (vllm/renderers/hf.py:848-856).
  • The render timeout is VLLM_CHAT_TEMPLATE_RENDER_TIMEOUT, default 30 seconds (vllm/envs.py:817-818). On a timeout the renderer replaces its thread pool, because the stuck thread cannot be stopped (vllm/renderers/hf.py:1038-1056).
  • The pool size is model_config.renderer_num_workers. Multimodal work has its own one-thread pool, so tokenization never waits behind image processing (vllm/renderers/base.py:140-150).
  • The ChatML example template adds <|im_end|> after each message and <|im_start|>assistant at the end when add_generation_prompt is true (examples/template_chatml.jinja:1-2).

5add_request: the input processor makes an EngineCoreRequest#

The engine core needs a small, fixed object that it can send as bytes. This is the EngineCoreRequest. AsyncLLM.add_request gets a rendered engine input (a dict with a "type" key). So it calls the synchronous process_inputs of the input processor. No tokenization is left to do (vllm/v1/engine/async_llm.py:481-496).

process_inputs also does the last checks and fills in defaults:

  • It clones the sampling parameters, so a shared object of the caller does not change (vllm/v1/engine/input_processor.py:447-449).
  • It adds the generation config and the EOS token id of the model to the sampling parameters (vllm/v1/engine/input_processor.py:489-494).
  • It takes arrival_time from the engine input of stop 3 (vllm/v1/engine/input_processor.py:403-404).

Then add_request makes the request id unique. It keeps the client id as external_req_id and adds 8 random characters:

Stop 6 in detail: the sockets and the encoder

  • The front end binds a ZMQ ROUTER socket for input and a PULL socket for output (vllm/v1/engine/core_client.py:670-682). With all engines on this machine, the addresses are ipc:// paths; else they are TCP (vllm/v1/engine/utils.py:1139-1151).
  • The engine identity is the DP rank as 2 little-endian bytes (vllm/v1/engine/core_client.py:749-751). The ROUTER socket uses the first frame to select the engine.
  • The request types are single bytes: ADD = b"\x00", ABORT = b"\x01", UTILITY = b"\x03" (vllm/v1/engine/__init__.py:300-313).
  • MsgpackEncoder.encode returns a list of buffers. The first is the msgpack message. Large tensors and arrays go as extra frames without a copy (vllm/v1/serial_utils.py:135-177). Our request has no tensors, so it is one frame.
  • The front end uses MsgpackEncoder for requests and MsgpackDecoder(EngineCoreOutputs) for outputs (vllm/v1/engine/core_client.py:731-732).
  • The output processor makes a RequestState with an incremental detokenizer and the collector queue (vllm/v1/engine/output_processor.py:663-693).

7The engine core input thread decodes the request#

We are now in the engine core process, vllm/v1/engine/core.py. EngineCoreProc has two I/O threads beside the main thread. The comment explains why: socket I/O and (de)serialization then overlap with the GPU work (vllm/v1/engine/core.py:1238-1263). The input thread connects a DEALER socket to the ROUTER of the front end (vllm/v1/engine/core.py:1935-1942) and waits:

  1. Line 1980: one message: the type frame and the data frames.
  2. Line 1991: add_request_decoder is a MsgpackDecoder(EngineCoreRequest) (vllm/v1/engine/core.py:1930-1932), so the result is a typed struct again.
  3. Line 1993: preprocess_add_request makes the engine's own Request object in this thread, so it runs in parallel with the model (vllm/v1/engine/core.py:1114-1136).
  4. Line 2028: the thread puts (ADD, (request, wave)) into input_queue for the main thread.

The Request starts as WAITING with num_computed_tokens = 0 (vllm/v1/request.py:100, vllm/v1/request.py:184). At the end of __init__ it computes the hashes of its full blocks for the prefix cache (vllm/v1/request.py:225-230).

Stop 7 in detail: hashes, failures and the ready message

  • The block hasher exists when prefix caching is on or a KV connector is set. Prefix caching is on by default for a decoder-only generative model: the engine arguments use model_config.is_prefix_caching_supported (vllm/engine/arg_utils.py:3062-3063, vllm/config/model.py:2289-2291). An engine step has three parts: schedule, execute and update. With async scheduling, the engine uses the batch queue. This version does not wait for a step right after it starts it. It starts the next step first:

12The forward pass: CUDA graph or eager#

Now the model runs on the GPU. The runner chooses one of three ways, by the CUDA-graph mode of the batch:

  1. Line 2032: FULL mode replays a captured CUDA graph of the whole model. The comment says the inputs are already in the graph's input buffers.
  2. Line 2041: the other modes run inside set_forward_context(...). The forward context gives each attention layer its metadata and slot mapping.
  3. Line 2065: PIECEWISE runs a graph with the attention parts outside of it.
  4. Line 2070: NONE calls the model eagerly.

CUDA graphs remove the CPU cost of many kernel launches: see CUDA graphs↗. In step 1 our batch has 13 query tokens of one prefill. In later steps it has 1 query token (a decode). The default optimization level is O2 (vllm/config/vllm.py:434), and O2 sets cudagraph_mode = FULL_AND_PIECEWISE (vllm/config/vllm.py:310). With this mode the runner picks the graph by the batch shape (vllm/v1/worker/gpu/cudagraph_utils.py:523-553):

  • A uniform decode batch gets a FULL graph, if it has no more tokens than the largest captured size. In such a batch every request has exactly 1 query token (no spec decoding). Our decode steps are of this kind.
  • Another batch, for example our 13-token prefill, gets a PIECEWISE graph, padded to the next captured size (vllm/v1/worker/gpu/cudagraph_utils.py:352-370).
  • A batch with more tokens than the largest captured size runs eagerly (NONE).

The loop: one engine step per output token#

Stops 9 to 16 repeat. Our request gets one step for the prompt (or more with chunked prefill) and then one step per new token. Each step gives one SSE chunk. The prefill step already samples the first token, so a request with 40 output tokens (EOS included) needs 40 engine steps. With async scheduling, one more step for the request is often already scheduled when it stops; the scheduler ignores its result.

The overlap. With async scheduling, the engine core does not wait between steps. It schedules and starts step k+1 first, and only then waits for the token of step k (stop 9). The scheduler can plan step k+1 because AsyncScheduler counts a placeholder for the token in flight (panel 3). The model runner then reads the real token from last_sampled_tokens on the GPU (stop 11). So the CPU work of scheduling and output handling hides behind the GPU work. DeepInfer uses the same idea: see Zero-overhead scheduling↗. The page Async scheduling: overlap the CPU and the GPU explains the vLLM version in full.

The time to first token and the inter-token latency metrics of vLLM are measured in the front end, in IterationStats.update_from_output:

  1. TTFT start: arrival_time = time.time() in render_chat_async (stop 3, vllm/renderers/base.py:1380). So it does not include the HTTP transfer, the JSON parse and the model check before rendering.
  2. TTFT end: iteration_timestamp, the wall-clock time when the output handler makes the IterationStats object for a batch of outputs (vllm/v1/metrics/stats.py:477-478, vllm/v1/engine/async_llm.py:883-885). That is after ZMQ, before detokenization and before the SSE write.
  3. ITL: the difference between the EngineCoreOutputs.timestamp values of two outputs. These are time.monotonic() values from the engine core process (vllm/v1/engine/__init__.py:295-297).

A client measures TTFT from its own send time to the first content chunk. Its value is larger: it adds the network, the HTTP parse, the work before arrival_time (model check, _preflight), the detokenization and the SSE write. Remember also that the first SSE chunk only has the role; the first text comes in the same RequestOutput (stop 16). The page Serving metrics: TTFT, TPOT, ITL, throughput, goodput defines the metrics, and Metrics and observability: how to watch a vLLM server lists the Prometheus names.

The stats exist only when log_stats is true. disable_log_stats is False by default (vllm/engine/arg_utils.py:624).

Deep dive

What changes with TP > 1

With --tensor-parallel-size 2, the world size is 2, so the executor is "mp" on one node (vllm/config/parallel.py:1055-1096). Each GPU gets its own worker process. Stops 1 to 10 and 14 to 16 do not change. Stop 11 changes: the engine core does not call the worker directly. MultiprocExecutor.execute_model sends the call to all workers through a shared-memory message queue (rpc_broadcast_mq.enqueue, vllm/v1/executor/multiproc_executor.py:342-353, vllm/v1/executor/multiproc_executor.py:428). Only one worker replies, the first TP rank of the last PP stage (vllm/v1/executor/multiproc_executor.py:549-560). The workers exchange activations with all-reduce inside the forward pass (tensor parallelism). The tour Tour: One step across GPUs follows this path.

Deep dive

What changes with DP > 1

With --data-parallel-size 2, there are two engine core processes, one per DP rank. The front end then uses DPLBAsyncMPClient (internal load balancing) or DPAsyncMPClient (external load balancer) (vllm/v1/engine/core_client.py:158-169). For each new request, DPLBAsyncMPClient picks the engine with the lowest score. The score is the larger of two counts: waiting plus running requests, and the in-flight requests of this client. Waiting requests add a penalty when the KV cache usage is above 50% (vllm/v1/engine/core_client.py:1763-1789). An X-data-parallel-rank header can force a rank (vllm/entrypoints/generate/base/serving.py:215-227). For a dense model the DP ranks are independent. For an MoE model the engine core is a DPEngineCoreProc, which keeps the ranks in step (vllm/v1/engine/core.py:1537-1547). See Data parallel serving: several engine cores behind one endpoint and Tour: One step across GPUs.

Deep dive

What changes with more API servers

By default api_server_count is the DP size with internal load balancing. It is the local DP size with hybrid load balancing, and 1 with an external load balancer (vllm/entrypoints/cli/serve.py:113-130). With more than one, run_multi_api_server starts several front-end processes that share one listen socket with reuse_port (vllm/entrypoints/cli/serve.py:269, vllm/entrypoints/cli/serve.py:298). So stops 1 to 6 and 15 to 16 run in one of N processes. The engine core opens one input socket and one output socket for each front end (vllm/v1/engine/core.py:1936-1943, vllm/v1/engine/core.py:2047-2052). It sends each output to the socket of the client that sent the request: client_index selects the socket (vllm/v1/engine/core.py:2089-2091). So each front end detokenizes only its own requests, and N processes share this work.

Deep dive

Cancellation: when the client disconnects

The client can close the connection at any time. Two mechanisms find out:

  1. Before the route returns, with_cancellation runs the handler and listen_for_disconnect as two tasks and cancels the other when one ends (vllm/entrypoints/serve/utils/api_utils.py:93-109).
  2. After the route returns a StreamingResponse, the response itself listens for the disconnect. The docstring of with_cancellation says this (vllm/entrypoints/serve/utils/api_utils.py:85-87). The stream generator is then stopped.

When the stream stops, AsyncLLM.generate() gets CancelledError or GeneratorExit and calls abort(q.request_id, internal=True) (vllm/v1/engine/async_llm.py:807-812). abort removes the request from the output processor and sends ABORT to the engine core (vllm/v1/engine/async_llm.py:948-956, vllm/v1/engine/core_client.py:1338-1340). In the engine core, abort_requests calls finish_requests(..., FINISHED_ABORTED), which frees the blocks (vllm/v1/engine/core.py:554-560). The engine core also checks aborts_queue before each update_from_output, so an abort that arrives during the forward pass acts at once (vllm/v1/engine/core.py:780-782).

Simplified

The exact way Starlette stops the generator (a cancelled task, or a closed generator) is Starlette code and is not in this repository. Both cases reach the same except branch in generate().

What can go wrong#

An HTTP 200 does not mean that the request worked

A streaming response starts before the engine sees the request (stop 2). Clients must read the error chunks in the stream, not only the status code (vllm/entrypoints/openai/chat_completion/serving.py:937-943, vllm/entrypoints/openai/chat_completion/serving.py:497-503).

  • Slow first token under load. The new request waits in the waiting queue until running requests leave room in the token budget and the KV cache (stop 10). Watch the waiting count and the cache usage; see Tuning vLLM: throughput and latency knobs, their real defaults and what each one does.
  • A long prompt delays all streams. With chunked prefill, a long prompt takes a large part of the token budget for several steps. Every running request then gets its next token later. long_prefill_token_threshold limits the tokens of one prompt per step (vllm/v1/core/sched/scheduler.py:764-765).
  • Preemption. When blocks run out, the scheduler preempts a running request and computes it again later (vllm/v1/core/sched/scheduler.py:850-858). The stream of that request pauses.
  • Chat template timeout. A very slow template fails after VLLM_CHAT_TEMPLATE_RENDER_TIMEOUT seconds (default 30, vllm/renderers/hf.py:1044-1056).
  • Prompt too long. HTTP 400 "This model's maximum context length is ... tokens. However, your prompt contains ... input tokens" (vllm/renderers/params.py:524-538).
  • Busy front end. One front end does rendering, detokenization and JSON for all streams in one event loop. At high load it can be the bottleneck; more API servers share this work (Deep dive).

Why it matters. Most questions about a slow or broken stream start with "which stop is it?". A slow first token is often a scheduling question (stop 10). A slow stream with a fast GPU can be the front end (stops 15 and 16). A missing token can be a stop-string question (stop 15). With the map of this tour you can open the right file at once.

Check yourself#

  1. 1
    In which process does the chat template run, and in which thread?
    easy
    Show answer

    In the API server process (the front end), in a thread pool. HfRenderer wraps safe_apply_chat_template with make_async(..., executor=self._executor) (vllm/renderers/hf.py:1011-1013). So the template does not block the asyncio event loop.

  2. 2
    Which two objects cross the ZMQ sockets, and how are they encoded?
    easy
    Show answer

    EngineCoreRequest goes from the front end to the engine core, and EngineCoreOutputs comes back. Both are msgspec structs with array_like=True, encoded as msgpack (vllm/v1/engine/__init__.py:113-118, vllm/v1/engine/__init__.py:266-271, vllm/v1/engine/core_client.py:731-732).

  3. 3
    The client gets HTTP 200, but the stream holds only an error and data: [DONE]. How can this happen?
    medium
    Show answer

    The route returns the StreamingResponse before AsyncLLM.generate() runs, because engine_client.generate(...) only makes an async generator (stop 2). The status line is already sent when the request reaches the engine. Later errors become data: chunks, followed by data: [DONE] (vllm/entrypoints/openai/chat_completion/serving.py:937-943, vllm/entrypoints/openai/chat_completion/serving.py:497-508).

  4. 4
    With async scheduling, how can the scheduler schedule the next decode step of our request before it knows the token of the current step? And where does the model runner get that token?
    hard
    Show answer

    AsyncScheduler adds a placeholder per token in flight (num_output_placeholders, vllm/v1/core/sched/async_scheduler.py:45-47). The running pass computes num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens, which is 1 (vllm/v1/core/sched/scheduler.py:759-763). The model runner reads the real token from req_states.last_sampled_tokens on the GPU in combine_sampled_and_draft_tokens (vllm/v1/worker/gpu/model_runner.py:1493-1500). postprocess_sampled wrote it there in the step before (vllm/v1/worker/gpu/model_runner.py:1715-1726).

  5. 5
    A user measures TTFT in the client as 180 ms, but the vLLM TTFT metric says 120 ms. Name three parts of the 60 ms that the vLLM metric does not include.
    hard
    Show answer

    The vLLM metric starts at arrival_time = time.time() in render_chat_async (vllm/renderers/base.py:1380) and ends when the output handler makes IterationStats for the batch with the first token (vllm/v1/metrics/stats.py:525, vllm/v1/engine/async_llm.py:883-885). It leaves out the network and the HTTP parse before the route, and the model check before rendering. It also leaves out the work after that moment: detokenization (stop 15), the JSON and the SSE write (stop 16), and the network.
