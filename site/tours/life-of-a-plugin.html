Tour: Life of a plugin

AdvancedGuided toursabout 25 min read + 6 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • How vLLM finds and loads plugins Intermediate
  • Platform plugins and current_platform Intermediate
  • CustomOp, out-of-tree ops and IR op providers Advanced

In one sentence

We follow one plugin package from pip install to a ready server, through the front end, the engine core and two worker processes.

The idea#

A hardware vendor ships vLLM support as a plugin package. A typical package publishes two entry points. One is a platform detector that tells vLLM "this machine has my device". The other is a general plugin that registers extra parts, for example a faster version of a layer or a new model. The concept pages explain each part on its own. This tour follows one package through one real start-up, in the order of the code.

vllm serve with tensor parallelism 2 runs four processes: the front end, the EngineCore process and one worker process per GPU (Parallelism basics↗). Python objects do not travel between processes. So each process finds the plugins again, and each plugin does its work again. Of the state that plugins change, only the VllmConfig object travels, as a pickled copy. The tour shows which stop runs in which process, and what travels to the next one.

An everyday comparison. Think of a new employee who works in three buildings of one company. In each building, the receptionist looks at the same staff list, gives the employee a badge and shows the desk. The employee unpacks the same toolbox again at each desk. The comparison stops in one place. Only one building writes the work plan (the config), and it sends copies of the plan to the other buildings.

The example package#

The dummy vendor package is a test fixture, not a real vendor

This tour uses two test packages from the vLLM repository as one imaginary vendor package. We call it the dummy vendor package. vLLM's CI installs the two packages one at a time, never together (.buildkite/test_areas/plugins.yaml:16-18, .buildkite/test_areas/plugins.yaml:48-51). The platform test only checks the detection and the op swap (tests/plugins_tests/test_platform_plugins.py:13-64). So the tour follows the code path, not a recorded run. Where the test platform is not a complete platform, the tour says so and names what a real vendor adds (stops 12 and 13).

  • tests/plugins/vllm_add_dummy_platform: a platform plugin with the class DummyPlatform, and a general plugin that replaces the rotary embedding layer with DummyRotaryEmbedding.
  • tests/plugins/vllm_add_dummy_model: a general plugin that registers four model architectures, among them MyOPTForCausalLM.

We serve the OPT checkpoint of the tests under the plugin's architecture name, with TP = 2. A vLLM test starts this server with tp=2 (tests/distributed/test_distributed_oot.py:13-14), and a second test uses --hf-overrides to rename the architecture (tests/distributed/test_distributed_oot.py:20-21):

pip install -e tests/plugins/vllm_add_dummy_platform     # as in CI, from the repo root
pip install -e tests/plugins/vllm_add_dummy_model
vllm serve facebook/opt-125m -tp 2 --hf-overrides '{"architectures": ["MyOPTForCausalLM"]}'

Simplified

The command is illustrative. The tests copy facebook/opt-125m and write MyOPTForCausalLM into its config.json (tests/conftest.py:1542-1556); --hf-overrides has the same effect on the architecture name. All counts on this page assume the default spawn start method of vllm serve.

What you will see#

  • Why installing a package does not run any of its code (stop 1).
  • How the out-of-tree detector beats the CUDA detector, and why the platform is known before any general plugin runs (stop 3).
  • Which platform hooks run in the front end, and which run again in the engine core. How the results reach the workers (stops 5 to 8).
  • Why the engine core process registers a model that it never builds (stop 9).
  • Where a worker gets its class, its attention backend and its replacement layers (stops 11 to 15).

1pip install writes the entry points#

We are not in vLLM yet. The installer reads the package description and writes the entry points into the entry-point metadata of each package. The platform package publishes two entry points in two plugin groups:

The model package publishes one more general plugin, register_dummy_model (tests/plugins/vllm_add_dummy_model/setup.py:10-12). vLLM itself publishes two general plugins, the LoRA resolvers (pyproject.toml:45-47). No function of the packages runs at install time. The page Python entry points explains the format.

What the data looks like now (the general group across all installed packages):

[vllm.general_plugins]

Simplified

Each package has its own entry_points.txt. The block above merges them into one view; importlib.metadata.entry_points() makes the same merge when vLLM asks for a group.

2vllm serve starts, and the CLI selects spawn#

The command vllm is a console script for vllm.entrypoints.cli.main:main (pyproject.toml:42-43). main() imports the module of each subcommand, then sets up the environment:

cli_env_setup() sets VLLM_WORKER_MULTIPROC_METHOD=spawn when you did not set it (vllm/entrypoints/common/startup.py:147-149). This matters for the whole tour: each child process of vllm serve is a new Python interpreter (spawn). It has empty registries and no platform object, so it must load every plugin again. The page How vLLM finds and loads plugins explains fork and spawn.

3An import resolves current_platform: the dummy detector wins#

The imports of stop 2 reach a module-level from vllm.platforms import current_platform. One such line is in vllm/engine/arg_utils.py (vllm/engine/arg_utils.py:122), which the serve module imports through cli_args.py (vllm/entrypoints/cli/serve.py:13, vllm/entrypoints/common/cli_args.py:16). current_platform is not a real module attribute. So Python calls the module __getattr__, which resolves the platform on first use (vllm/platforms/__init__.py:303-322):

  1. Line 250 loads the group vllm.platform_plugins. It imports dummy_platform_plugin, but does not call it yet.
  2. Line 254 calls the five built-in detectors first, then the dummy detector. On a host with an NVIDIA GPU, the CUDA detector answers too.
  3. Lines 277-279: exactly one out-of-tree detector is active, so it wins over CUDA. vLLM calls it a second time to get the class name, and logs "Platform plugin dummy_platform_plugin is activated" at INFO level.

The detector itself is short. A real detector checks for its device and returns None when the device is missing (docs/design/plugin_system.md:50). The test detector always answers:

Line 319 of platforms/__init__.py imports the class and makes one object. Its identity fields mark it as out-of-tree:

What the data looks like now (front end, NVIDIA host):

activated_plugins = ["cuda", "dummy_platform_plugin"]     # order of line 254
vllm.platforms._current_platform = DummyPlatform()        # is_out_of_tree() is True
plugins_loaded = False                                    # no general plugin has run yet

The platform is fixed before any general plugin runs. So a general plugin cannot change the platform choice. The page Platform plugins and current_platform explains the detection rules.

4The general plugins run for the first time#

The CLI builds the parsers of all subcommands before it reads your flags (vllm/entrypoints/cli/main.py:100-110). The serve parser calls make_arg_parser (vllm/entrypoints/cli/serve.py:172), which calls AsyncEngineArgs.add_cli_args (vllm/entrypoints/common/cli_args.py:466). That function loads the general plugins first:

load_general_plugins() sets the once-per-process flag, then calls each function of the group, in the order of entry_points() (vllm/plugins/__init__.py:82-90). Two of the four functions belong to our package:

  • register_ops imports the module with the replacement layer (tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/__init__.py:12-13). The import runs the decorator register_oot:
  • register registers four architectures in the model registry. MyOPTForCausalLM uses the class form, so the function imports my_opt at once (tests/plugins/vllm_add_dummy_model/vllm_add_dummy_model/__init__.py:9-12). MyLlava uses the string form, a lazy registration (tests/plugins/vllm_add_dummy_model/vllm_add_dummy_model/__init__.py:26-27).

The two LoRA resolver functions also run. They register a resolver only when their environment variables are set (Plugins in the API server).

What the data looks like now (front end):

plugins_loaded = True
op_registry_oot = {"RotaryEmbedding": DummyRotaryEmbedding}           # custom_op.py:22
ModelRegistry.models["MyOPTForCausalLM"] = _RegisteredModel(...)      # model info computed now

The key of op_registry_oot is the class name of the in-tree layer, because the decorator was called on RotaryEmbedding (vllm/model_executor/custom_op.py:337-340). The model info of an eager entry is computed at registration (vllm/model_executor/models/registry.py:974-979).

Deep dive

Stop 4 in detail: the second call in EngineArgs

After the CLI parses the flags, ServeSubcommand.cmd runs the API server in this process (vllm/entrypoints/cli/serve.py:153-156). build_async_engine_client makes the engine arguments with AsyncEngineArgs.from_cli_args(args) (vllm/entrypoints/launchers/api_server/entry.py:52). EngineArgs.__post_init__ calls load_general_plugins() again (vllm/engine/arg_utils.py:921-924). Here it returns at once, because the flag is set (vllm/plugins/__init__.py:83-84). The call exists for the offline LLM class, which builds no CLI parser.

At the default log level INFO, the loader prints nothing for this group: it logs the general group only at DEBUG level (vllm/plugins/__init__.py:48-50).

5pre_register_and_update runs five times#

This is the first platform hook of the start-up. The first call is at the end of add_cli_args, with the parser: current_platform.pre_register_and_update(parser) (vllm/engine/arg_utils.py:3257). The docstring names one use: an out-of-tree platform can import and register its own quantization config here (vllm/platforms/interface.py:642-650).

The CLI also builds the parsers of vllm launch render and vllm run-batch before it parses the flags. Both parsers call AsyncEngineArgs.add_cli_args too (vllm/entrypoints/cli/launch.py:99-106, vllm/entrypoints/cli/launch.py:39, vllm/entrypoints/cli/run_batch.py:62, vllm/entrypoints/launchers/run_batch.py:294-296). So the hook runs three times with a parser, once for each parser. (Derived from the parser loop of stop 4.) The general plugins do not run again in these calls, because the flag is already set.

The fourth call comes after the flags are parsed. setup_server logs the non-default flags (vllm/entrypoints/launchers/launcher.py:368). To find the defaults, it builds the whole parser once more, and add_cli_args calls the hook again (vllm/entrypoints/common/startup.py:70-71).

The fifth call comes next. build_async_engine_client_from_engine_args calls create_engine_config (vllm/entrypoints/launchers/api_server/entry.py:82), which starts like this:

DummyPlatform does not override this hook, so the base method runs, and it does nothing (vllm/platforms/interface.py:638-651). Line 2248 makes the device config from device_type, which is "privateuseone" for the dummy platform. The docstring says that the hook runs "before ... cli arguments are parsed" (vllm/platforms/interface.py:644-645). That is true for the first three calls, but not for the fourth and the fifth call. So a real hook must give the same result when it runs again.

6ModelConfig asks the model registry#

Next, create_engine_config makes the model config (vllm/engine/arg_utils.py:2269). ModelConfig.__post_init__ reads the architecture name and asks the registry what the class can do (vllm/config/model.py:703-706). Then it resolves the architecture:

The architecture is MyOPTForCausalLM, from --hf-overrides. The front end registered it at stop 4 with the class form, so the registry already has its model info. The eager entry returns it with no new process (vllm/model_executor/models/registry.py:981-982). The log shows "Resolved architecture: MyOPTForCausalLM" at INFO level.

A lazy entry would start a subprocess here

If we served MyLlava, the entry would be lazy. The registry would look for a cached model info file. On a miss, it would run the inspection in a new Python process "to avoid initializing CUDA" (vllm/model_executor/models/registry.py:1088-1109). That subprocess loads the general plugins first (vllm/model_executor/models/registry.py:1608-1612), so our two plugin functions would run in a fifth process. The page Out-of-tree models and the model registry explains the cache.

7VllmConfig.__post_init__: the platform config hooks#

At the end, create_engine_config builds one VllmConfig from all parts (vllm/engine/arg_utils.py:2870). Its __post_init__ calls two more platform hooks. First, apply_config_platform_defaults runs (vllm/config/vllm.py:1804); the dummy platform keeps the base method, which does nothing (vllm/platforms/interface.py:653-664). Then vLLM adds the base mode of the CustomOp list:

With the default compilation (mode VLLM_COMPILE, backend inductor), the list becomes ["none"]: all custom ops are off. Later, the platform gets the last word (vllm/config/vllm.py:2046). The dummy platform turns all ops on:

A real platform must also set the worker class here. CUDA shows the pattern:

The default of worker_cls is "auto" (vllm/config/parallel.py:306). The dummy platform does not change it. That has a cost at stop 12.

What the data looks like now (the config that goes to the other processes):

vllm_config.compilation_config.custom_ops      = ["all"]   # dummy hook replaced ["none"]
vllm_config.parallel_config.worker_cls         = "auto"    # a real platform sets a class here

8AsyncLLM loads the stat loggers and starts the engine core#

The front end now makes AsyncLLM (vllm/entrypoints/launchers/api_server/entry.py:94). Its constructor loads one more plugin group:

Our package has no stat logger, so the group is empty. The loader logs "No plugins for group ... found." at DEBUG level and returns (vllm/plugins/__init__.py:42-45). Then AsyncLLM starts the engine core (vllm/v1/engine/async_llm.py:193). The process manager uses the multiprocessing context, so the child is a spawned process:

Only the config crosses the process boundary

The child gets vllm_config as a pickled argument. It does not get op_registry_oot, the model registry, the flag plugins_loaded or the platform object. Those are module globals of the front end. So stops 3 and 4 must happen again in the child. A change that a platform hook makes outside vllm_config is lost here.

9The engine core detects the platform and runs the general plugins#

The spawned child imports the module of its target, vllm.v1.engine.core. On the way, Python runs the package file vllm/v1/engine/__init__.py, which imports vllm.config.kv_events (vllm/v1/engine/__init__.py:14). So Python runs the package vllm/config/__init__.py, which imports compilation.py, which has a module-level from vllm.platforms import current_platform (vllm/config/__init__.py:7, vllm/config/compilation.py:22). So stop 3 repeats in this process: the dummy detector runs twice more and wins again. Then EngineCore.__init__ runs:

Line 132 repeats stop 4 in this process. register_ops registers DummyRotaryEmbedding again, in this process's own op_registry_oot. register imports my_opt and computes its model info again. The engine core never builds the model, because the workers do. The eager form of the registration costs this import anyway. The lazy form would avoid it.

Line 147 makes the executor. This happens after the plugins, so the plugins are ready before any worker starts.

10The executor starts two worker processes#

The backend "mp" from stop 7 selects the multiproc executor (vllm/v1/executor/abstract.py:80-83). Its _init_executor starts one process for each local rank:

make_worker_process takes the same multiprocessing context, so each worker is spawned too (vllm/v1/executor/multiproc_executor.py:723). The target is WorkerProc.worker_main, and the pickled vllm_config goes with it (vllm/v1/executor/multiproc_executor.py:731-750). The page Executors and workers: from the engine core to the GPUs explains the executor.

11Each worker detects the platform, runs the plugins and the Triton hook#

Each worker child imports multiproc_executor.py to find its target. On the way, Python runs vllm/v1/executor/__init__.py, which imports abstract.py, which imports vllm.config (vllm/v1/executor/__init__.py:3, vllm/v1/executor/abstract.py:11). So the platform resolves in this process too. Then WorkerProc.__init__ calls init_worker (vllm/v1/executor/multiproc_executor.py:659-672):

  1. Line 284 repeats stop 4 a third and a fourth time, once in each worker. Now this worker has DummyRotaryEmbedding in its registry, before it builds any layer.
  2. Line 290 is a kernel hook. A platform can replace core Triton kernels here, "before any worker or model code can launch them". The dummy platform keeps the base method, which does nothing (vllm/platforms/interface.py:375-386).

12The worker resolves worker_cls#

The test platform cannot go past this stop

DummyPlatform leaves worker_cls as "auto" (stop 7). resolve_obj_by_qualname splits the name at the last dot (vllm/utils/import_utils.py:119-123). "auto" has no dot, so the split gives one part, and the unpacking at line 121 raises ValueError. The worker fails here. (Derived.) A real vendor sets its own worker class in check_and_update_config; the design doc lists the methods that the class must implement (docs/design/plugin_system.md:109-117).

The worker class is the main hook of a hardware plugin: it owns the device, the model runner and the KV cache. Lines 345-347 of the same file then make the worker object inside set_current_vllm_config. Next, WorkerProc.__init__ calls init_device and load_model (vllm/v1/executor/multiproc_executor.py:680-688). With TP = 2, the device setup also asks the platform for its communicator class, because the tensor-parallel group has two ranks (vllm/distributed/parallel_state.py:549-552).

Simplified

For stops 13 to 15, we assume a vendor worker class that builds the model with vLLM's model loader. vLLM's own GPU worker does this: Worker.load_model calls the model runner (vllm/v1/worker/gpu_worker.py:591-598), which calls model_loader.load_model (vllm/v1/worker/gpu/model_runner.py:403-406). Stops 13 to 15 happen in layer constructors, so they run for any worker that builds vLLM model classes.

13The model is built, and attention asks the platform for a backend#

The loader finds the class in the registry of this worker (vllm/model_executor/model_loader/utils.py:305-313). The entry is there because of line 284 in stop 11. Then initialize_model calls the constructor inside set_current_vllm_config:

Each OPT decoder layer builds an OPTAttention, and its constructor builds an attention layer (vllm/model_executor/models/opt.py:137-144, vllm/model_executor/models/opt.py:106). The attention layer asks for its backend in __init__ (vllm/model_executor/layers/attention/attention.py:349-350). The selector asks the platform, a component picker:

DummyPlatform.get_attn_backend_cls returns one class for every layer:

Line 227 of the selector imports that class. @cache keeps one answer for each set of arguments. The arguments are the backend name, the AttentionSelectorConfig, num_heads and the KV cache data type (vllm/v1/attention/selector.py:158-180, vllm/v1/attention/selector.py:196-203). All OPT attention layers pass the same values, so each process asks the platform only once. (Derived from vllm/model_executor/models/opt.py:106-113.)

The test backend is a stub: it subclasses a placeholder backend and changes only its name (tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/dummy_attention_backend.py:7-10). At this commit, the file imports its parent class from vllm.attention.backends.placeholder_attn, a module that the repository does not contain (tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/dummy_attention_backend.py:4). A real vendor returns a backend that computes attention on its device. See How vLLM chooses an attention backend.

14CustomOp.__new__ swaps the replaced class#

The same constructors also build small layers such as norms and rotary embeddings. Each of them is a CustomOp. Before Python runs __init__, the class method __new__ looks at the op registry of out-of-tree classes:

  1. Line 109 takes the Python class name of the class that the model code builds, for example "RotaryEmbedding".
  2. Lines 117-120: the name is in op_registry_oot, so vLLM makes the object from DummyRotaryEmbedding, and logs "Instantiating custom op" at DEBUG level.
  3. Line 126 returns an object of the replacement class. It is a subclass of the in-tree class, so Python then runs its __init__, which sets addition_config = True.

For our model, the swap does not happen. OPT has learned position embeddings and builds no RotaryEmbedding (vllm/model_executor/models/opt.py:217). Its norm layer is LayerNorm (vllm/model_executor/models/opt.py:35, vllm/model_executor/models/opt.py:147). "LayerNorm" is not in op_registry_oot, so line 118 keeps the in-tree class. A model with standard RoPE, such as Llama, gets its rotary layer from get_rope, which builds RotaryEmbedding for the default rope type (vllm/model_executor/layers/rotary_embedding/__init__.py:147-155). There the swap happens. A test checks it (tests/plugins_tests/test_platform_plugins.py:51-64).

The lookup uses the exact class name. MRotaryEmbedding, which get_rope builds for an mrope_section, has another name, so it is not swapped (vllm/model_executor/layers/rotary_embedding/__init__.py:113-114). (Derived from line 109.)

15The op picks forward_oot, because the platform enabled it#

CustomOp.__init__ calls dispatch_forward once and keeps the result (vllm/model_executor/custom_op.py:128-134):

The worker's copy of the config has custom_ops = ["all"] from stop 7. So the default enabled() returns true for every op (vllm/model_executor/custom_op.py:290, vllm/model_executor/custom_op.py:307). The platform is out-of-tree, so lines 202-203 select forward_oot. For OPT's LayerNorm, that is the default forward_oot, which calls forward_native (vllm/model_executor/custom_op.py:167-170). In a RoPE model, DummyRotaryEmbedding.forward_oot calls the parent's forward_oot (stop 4 excerpt, lines 18-19). RotaryEmbedding does not override that method, so the call ends in the same forward_native.

Without the dummy hook of stop 7, the list would be ["none"]. Then every op without a +name switch would be disabled and would use forward_native (line 192), and the vendor's forward_oot would not run for it. The page CustomOp, out-of-tree ops and IR op providers explains the switches.

16Block size, environment cache, and the server is ready#

After load_model, each worker finishes its start-up:

  1. Line 702 runs a config hook. It picks a block size that all attention backends of the model accept, when the user did not set one (vllm/platforms/interface.py:767-774, The Platform interface).
  2. Line 710 freezes the environment variables. From now on, VLLM_PLUGINS and the other variables are read from a cache in this worker (vllm/envs.py:2308-2326).

The engine core does the same with enable_envs_cache() at the end of its own start-up (vllm/v1/engine/core.py:241-243). The front end then builds the HTTP app. build_app looks for endpoint plugins; our package has none (vllm/entrypoints/launchers/app.py:51). From the first request on, the forward method of each custom op calls the method that stop 15 chose (vllm/model_executor/custom_op.py:133-134). The tour Tour: Life of a chat request follows that request.

  • The decorator runs once per process. Python caches an imported module, so a second import in register_ops does not run the decorator again. Also, vLLM calls register_ops only once per process (vllm/plugins/__init__.py:83-85). A second register_oot with the same key would fail the assert at vllm/model_executor/custom_op.py:338.
  • The config hooks run in VllmConfig.__post_init__. The front end runs it when it builds the config. The EAGLE drafter loader in a worker is one such case (vllm/v1/worker/gpu/spec_decode/eagle/utils.py:90-91).
  • The hook pre_register_and_update runs four times with a parser: for serve, launch render, run-batch and setup_server. It runs once more in create_engine_config (stop 5).
  • The world group has no device communicator (vllm/distributed/parallel_state.py:1510-1514). For OPT with TP = 2, only the tensor-parallel group has two ranks. The pipeline, context-parallel and data-parallel groups have one rank. vLLM makes no expert-parallel group for a dense model (vllm/distributed/parallel_state.py:2313-2314). So each worker asks once. (Derived.)
  • The OPT count for get_attn_backend_cls assumes that all layers pass the same arguments, so @cache hits after the first layer (vllm/v1/attention/selector.py:206).
  • Not counted: the model registry subprocess. It does not run for MyOPTForCausalLM (stop 6). For a lazy entry with a cache miss, it adds one process that runs the general plugins once more (vllm/model_executor/models/registry.py:1612). It imports vllm.config at module level (vllm/model_executor/models/registry.py:26), so it also resolves the platform.
Deep dive

What changes with TP = 1

With one GPU (TP = 1, and PP and DP keep their default 1), the world size is 1, and the executor is "uni" (vllm/config/parallel.py:1099-1100). The uni executor makes the worker object inside the engine core process:

  1. Stops 1 to 9 do not change.
  2. Stop 10 starts no process. Stops 11 to 16 run in the engine core process.
  3. Stop 11: load_general_plugins() in init_worker returns at once, because EngineCore.__init__ already set the flag in this process (vllm/plugins/__init__.py:83-84). The platform is not detected again: the engine core already has the object. register_triton_kernel_overrides still runs.
  4. Stop 12: the tensor-parallel group has one rank, so the worker does not ask for a device communicator (vllm/distributed/parallel_state.py:549).
  5. Stop 16: the engine core calls update_block_size_for_backend (line 75 above).

So the general plugin functions run twice in total, and the detector runs four times.

What changes with VLLM_PLUGINS

VLLM_PLUGINS is one allowlist of entry-point names for five groups (vllm/envs.py:1160-1167, vllm/plugins/__init__.py:63-64). Three cases for our package:

Deep dive

What changes with VLLM_TARGET_DEVICE=cpu

The CPU target is a short-circuit in every process. resolve_current_platform_cls_qualname returns the CPU platform before it loads vllm.platform_plugins (vllm/platforms/__init__.py:244-248). The value is lower-cased, so CPU works too (vllm/envs.py:622).

  • Stop 3: dummy_platform_plugin is never imported or called, in any process.
  • Stop 4: the general plugins still run. They are a separate group. So DummyRotaryEmbedding is still registered, and stop 14 still swaps the class in a RoPE model.
  • Stop 7: the CPU platform sets worker_cls to CPUWorker (vllm/platforms/cpu.py:355-356) and changes the compilation settings (vllm/platforms/cpu.py:368-379).
  • Stop 15: an enabled op calls forward_cpu, not forward_oot (vllm/model_executor/custom_op.py:196-197). The swapped class inherits forward_cpu from RotaryEmbedding (vllm/model_executor/layers/rotary_embedding/base.py:298). The vendor's forward_oot never runs.

This shows a design point. A layer replacement and a platform are independent. A general plugin registers the class on every platform; the platform decides which forward_* method of that class runs.

What can go wrong#

A platform hook that changes a global is lost

In a plain start-up of vllm serve, check_and_update_config runs in the front end, where VllmConfig is built (vllm/config/vllm.py:2046, vllm/engine/arg_utils.py:2870). It runs again in each engine core, but only after the engine core has started its workers (vllm/v1/engine/core.py:1336-1337). It never runs in a worker. Only changes to vllm_config reach the workers (stop 8). Register classes in a general plugin, not in a config hook.

  • The worker class is missing. A platform that leaves worker_cls as "auto" fails in each worker at stop 12 (vllm/v1/worker/worker_base.py:293-296). The front end and the engine core start normally, so read the worker log: "WorkerProc failed to start." (vllm/v1/executor/multiproc_executor.py:956-957).
  • The platform plugin is skipped with no warning. A VLLM_PLUGINS list without the detector name gives a built-in platform (deep dive). Look for "Platform plugin ... is activated" in the log (vllm/platforms/__init__.py:279).
  • Two platform plugins answer. Start-up stops with "Only one platform plugin can be activated" in the first process (vllm/platforms/__init__.py:272-276).
  • The replacement never builds. register_oot keys on the class name. If the model does not build that exact class, as OPT does not build RotaryEmbedding, nothing happens and nothing is logged (stop 14).
  • The vendor kernels never run. Without "all" or +name in custom_ops, a compiled server disables the ops, and forward_oot does not run (stop 15).
  • A general plugin fails in one process only. The function runs in each process, and vLLM does not catch its errors (vllm/plugins/__init__.py:89-90). The engine core logs "EngineCore failed to start." (vllm/v1/engine/core.py:1570-1572).
  • Eager registration costs imports everywhere. The class form imports the model module in the front end, the engine core and every worker (stops 4, 9 and 11). The registry docstring recommends the string form to avoid starting CUDA too early (vllm/model_executor/models/registry.py:1167-1173).

Why it matters. A vendor plugin touches every process of the server, at different moments. When a plugin "does not work", the question is: in which process, and at which stop? A wrong platform shows up at stop 3, a missing worker class at stop 12, a silent op at stop 14 or 15. The tour Tour: Build a toy plugin uses these stops to check a plugin of your own.

Check yourself#

  1. 1
    In which processes does dummy_platform_plugin run with -tp 2, and why more than once?
    easy
    Show answer

    In all four: the front end, the engine core and both workers. Each one is a separate Python process with its own _current_platform = None; the three children are spawned (vllm/platforms/__init__.py:296, vllm/entrypoints/common/startup.py:147-149). The first read of current_platform in each process runs the detection again (vllm/platforms/__init__.py:317-319).

  2. 2
    The engine core never builds the model. Why does it import my_opt.py?
    medium
    Show answer

    EngineCore.__init__ runs the general plugins (vllm/v1/engine/core.py:132). The plugin registers MyOPTForCausalLM with the class form, so it imports the module inside the function (tests/plugins/vllm_add_dummy_model/vllm_add_dummy_model/__init__.py:9-12). The class form also computes the model info at once (vllm/model_executor/models/registry.py:1194-1195). The string form would avoid this import.

  3. 3
    The dummy platform sets custom_ops = ["all"] in the front end. How does that value reach a worker?
    medium
    Show answer

    Inside the pickled VllmConfig. The hook changes the config object (vllm/config/vllm.py:2046), and the front end passes that object to the spawned engine core (vllm/v1/engine/utils.py:256-287), which passes it to each worker (vllm/v1/executor/multiproc_executor.py:731-750). The hook itself does not run in the worker. It runs again in the engine core after the handshake (vllm/v1/engine/core.py:1336-1337).

  4. 4
    We serve MyOPTForCausalLM on the dummy platform with custom_ops = ["all"]. Does DummyRotaryEmbedding.forward_oot ever run? Which forward_* method does OPT's LayerNorm use?
    hard
    Show answer

    No. OPT builds no RotaryEmbedding, and CustomOp.__new__ swaps only the exact class name in op_registry_oot (vllm/model_executor/custom_op.py:109-120). LayerNorm keeps its in-tree class. It is enabled by "all", and the platform is out-of-tree, so it uses forward_oot (vllm/model_executor/custom_op.py:202-203). The default forward_oot calls forward_native (vllm/model_executor/custom_op.py:167-170).

  5. 5
    With TP = 1 (one GPU), how many times does register_ops run, and how many times does the dummy detector run? Ignore the model registry subprocess.
    hard
    Show answer

    register_ops runs twice: in the front end and in the engine core. The uni executor calls init_worker inside the engine core process (vllm/v1/executor/uniproc_executor.py:68), and the flag is already set there (vllm/plugins/__init__.py:83-84). The detector runs four times: twice in each of the two processes, once in the loop and once for the winner (vllm/platforms/__init__.py:257, vllm/platforms/__init__.py:278).

  • The Platform interfaceThe Platform class is the contract between vLLM and a hardware vendor. Identity attributes describe the device; config hooks change VllmConfig in the front end and again in each engine core; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation.
