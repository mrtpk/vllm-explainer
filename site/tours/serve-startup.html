Tour: Start-up of vllm serve

IntermediateGuided toursabout 22 min read + 8 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • The process and thread architecture of vllm serve Intermediate
  • How configuration works Intermediate
  • Executors and workers: from the engine core to the GPUs Intermediate

In one sentence

We follow vllm serve on one GPU from the shell command to "Application startup complete", in two processes and 18 stops.

The idea#

A cold start of vllm serve can take minutes. The log shows many lines, from two processes. This tour connects each part of the log to the code that writes it. Then you can read your own server log and see where the time goes.

With one GPU (TP = PP = DP = 1), vllm serve runs two processes. The API server process is the vllm command itself: it parses the flags, builds the VllmConfig and later runs the HTTP server. The EngineCore process is a child. With one GPU, the uni executor runs the worker inside that process, so it also loads the model and owns the GPU (The process and thread architecture of vllm serve).

An everyday comparison. Think of a theatre before the first show. The front office prints the tickets and the cast list, and it opens the doors only when the stage manager calls "ready". Backstage, the crew builds the set, tunes the lights and rehearses each scene once. The comparison stops in one place. Here the front office writes the full script (the config) before the crew starts, and the crew gets a copy.

The tour Tour: Life of a plugin walks the same start-up from the side of the plugins, with TP = 2. This tour follows the config, the processes and the GPU work.

The example#

vllm serve meta-llama/Llama-3.1-8B-Instruct     # one 80 GB H100, no other flags
  • Usage context OPENAI_API_SERVER, so the token budget is 8192 and max_num_seqs is 1024 when the driver reports 70 GiB or more (vllm/engine/arg_utils.py:2970-2983).
  • Optimization level O2: torch.compile and CUDA graph mode FULL_AND_PIECEWISE (vllm/config/vllm.py:434, vllm/config/vllm.py:310).
  • The executor backend is uni, because the world size is 1 (vllm/config/parallel.py:1099-1100).

Simplified

The model and the GPU are an example. Numbers such as GiB values and times are illustrative; the log texts and the order are from the code. We assume a cold start: no compile cache, weights already downloaded.

1The console script starts, and the CLI selects spawn#

The command vllm is a console script for vllm.entrypoints.cli.main:main (pyproject.toml:42-43). main() first imports the module of each subcommand, then prepares the environment:

  1. Lines 43-51. The imports already do work. cli/serve.py imports common/cli_args.py, which imports engine/arg_utils.py. That module has a module-level from vllm.platforms import current_platform, so the platform is detected now (vllm/entrypoints/cli/serve.py:13, vllm/entrypoints/common/cli_args.py:16, vllm/engine/arg_utils.py:122). The page Platform plugins and current_platform explains the detection.
  2. Lines 67-68. cli_env_setup() sets VLLM_WORKER_MULTIPROC_METHOD=spawn when you did not set it (vllm/entrypoints/common/startup.py:147-149). So the engine core of stop 10 is a new Python interpreter, a spawned process.

2The parsers are built, and argv is parsed#

The CLI builds the parser of every subcommand before it reads your flags:

The serve parser calls make_arg_parser, which ends with AsyncEngineArgs.add_cli_args (vllm/entrypoints/cli/serve.py:172, vllm/entrypoints/common/cli_args.py:465-466):

  1. Line 3243. The general plugins run for the first time in this process. Later calls return at once (vllm/plugins/__init__.py:82-85).
  2. Line 3245. About 300 flags are made from the config classes (How configuration works, Step 4). The help text is read only with --help, which saves time (vllm/engine/arg_utils.py:285-288).
  3. Line 3257. The platform hook pre_register_and_update(parser). The parsers of launch render and run-batch call add_cli_args too, so the hook runs three times here (vllm/entrypoints/cli/launch.py:39, vllm/entrypoints/cli/run_batch.py:62).

Line 110 of main.py parses the command line. FlexibleArgumentParser first inserts a --config YAML file, changes _ to -, expands -O3 and turns -cc.key=value into JSON (vllm/utils/argparse_utils.py:313-502). Line 113 configures logging; line 114 checks the serve flags.

3ServeSubcommand.cmd picks one API server#

args.dispatch_function is ServeSubcommand.cmd. It moves the positional model into args.model and decides how many API server processes to run (vllm/entrypoints/cli/serve.py:54-57). --api-server-count is not set, so it becomes the data parallel size, 1 (vllm/entrypoints/cli/serve.py:113-130):

One API server runs in this process, inside a uvloop event loop (lines 155-156). With more API servers, the CLI process would stay a supervisor and start them as children (line 152, deep dive "DP = 2").

4setup_server binds the port before the engine starts#

run_server names the process for the log, catches an early SIGTERM, and calls setup_server (vllm/entrypoints/launchers/api_server/entry.py:164-176):

  1. Line 367. The banner: "vLLM server version %s, serving model %s", or an ASCII logo with the same values (vllm/entrypoints/common/startup.py:16-38).
  2. Line 368. "non-default args: {...}" lists every flag that differs from its default, with secrets shown as *** (vllm/entrypoints/common/startup.py:49-60, vllm/entrypoints/common/startup.py:94-96). To find the defaults, it builds the whole parser once more (vllm/entrypoints/common/startup.py:70-74). So pre_register_and_update(parser) runs a fourth time.
  3. Lines 372-379. The socket is bound now, before the engine starts. The comment names a race with Ray as the reason. A busy port therefore fails in seconds, not after the model loads.

The API server only binds the port here. It does not accept connections until uvicorn runs at stop 18.

5The Namespace becomes EngineArgs#

run_server_worker enters build_async_engine_client, which makes the EngineArgs:

from_cli_args copies each parsed value into the dataclass field of the same name (vllm/engine/arg_utils.py:1961-1970). Then EngineArgs.__post_init__ runs. It turns dict values into config objects and calls load_general_plugins(), which returns at once here (vllm/engine/arg_utils.py:873-924). The call is for the offline LLM class, which builds no parser.

6create_engine_config: the model config first#

build_async_engine_client_from_engine_args calls create_engine_config() with the usage context OPENAI_API_SERVER (vllm/entrypoints/launchers/api_server/entry.py:68-82):

  1. Line 2246. pre_register_and_update() runs a fifth time, now without a parser.
  2. Line 2250. validate_environ warns about each VLLM_* name in the environment that vLLM does not know (Environment variables).
  3. Line 2269. ModelConfig reads the Hugging Face config. It asks the model registry and logs "Resolved architecture: LlamaForCausalLM" (vllm/config/model.py:741-744). Later in the same __post_init__, it computes max_model_len and logs "Using max model len 131072" (vllm/config/model.py:824, vllm/config/model.py:2170).
  4. Line 2275. Chunked prefill and prefix caching get their defaults from the model: both on for Llama (vllm/engine/arg_utils.py:3028-3068).

Simplified

131,072 is the context length of Llama 3.1 in its Hugging Face config (inferred, not in the vLLM repository). On a cold machine, this stop also downloads config.json and the tokenizer files. The registry can start a short subprocess on a cache miss (Out-of-tree models and the model registry).

7create_engine_config: the other sub-configs#

The function builds CacheConfig, ParallelConfig, the speculative config, the batch defaults, SchedulerConfig and the rest, in this order (vllm/engine/arg_utils.py:2296, vllm/engine/arg_utils.py:2558, vllm/engine/arg_utils.py:2624-2672). Three values of our example are decided here:

  • Executor backend. ParallelConfig.__post_init__ sets "uni", because the world size is 1 (vllm/config/parallel.py:1099-1100).
  • Batch limits. 8192 tokens and 1024 requests, from get_batch_defaults (vllm/engine/arg_utils.py:3153-3168).
  • Block size. None becomes 16 in a CacheConfig validator (vllm/config/cache.py:452-462). The platform can change it after the model loads (stop 13).

The function ends with one constructor call:

8VllmConfig.__post_init__ sets the late defaults#

The constructor runs the __post_init__ of VllmConfig (vllm/config/vllm.py:1492-2318). For our example, it turns async scheduling on (vllm/config/vllm.py:1697-1698) and sets the compilation defaults:

  1. Line 1804. The platform hook apply_config_platform_defaults.
  2. Lines 1806-1810. O2 is above O0, so the compilation mode is VLLM_COMPILE.
  3. Lines 1819-1826. With Inductor, the custom op list gets "none" (CustomOp, out-of-tree ops and IR op providers).
  4. Lines 1833-1834. The O2 table fills the fields that are still None: CUDA graph mode FULL_AND_PIECEWISE and the fusion passes (vllm/config/vllm.py:296-316).

Later in the method, _set_cudagraph_sizes picks the capture sizes, at most 512 here: min(1024 × 1 × 2, 512) (vllm/config/vllm.py:2439-2449). Then the platform has the last word: CUDA sets worker_cls to vllm.v1.worker.gpu_worker.Worker (vllm/config/vllm.py:2046, vllm/platforms/cuda.py:330-331). The config is now complete in the API server.

9AsyncLLM: tokenizer, processors, then the engine core#

The API server makes AsyncLLM (vllm/entrypoints/launchers/api_server/entry.py:93-103). from_vllm_config picks the executor class from the config: UniProcExecutor for "uni" (vllm/v1/engine/async_llm.py:264-276, vllm/v1/executor/abstract.py:84-87). The constructor loads the stat logger plugins, the renderer with the tokenizer, and the input and output processors (vllm/v1/engine/async_llm.py:155-186). Then it starts the engine core:

AsyncLLM always uses a multiprocess client, so the engine core always runs in its own process for vllm serve. With DP = 1, the client class is AsyncMPClient (vllm/v1/engine/core_client.py:158-173).

10MPClient binds the sockets and spawns the engine core#

MPClient.__init__ binds two ZMQ sockets: a ROUTER for requests to the engines, and a PULL for their outputs. Then it launches the engines:

launch_core_engines binds a third socket, the handshake ROUTER, and starts the process:

  1. Lines 1362-1373. CoreEngineProcManager makes a process with the target EngineCoreProc.run_engine_core and the name EngineCore, and starts it (vllm/v1/engine/utils.py:279-288, vllm/v1/engine/utils.py:330). The vllm_config is a keyword argument, so spawn pickles it (vllm/v1/engine/utils.py:257-264).
  2. Line 1387. The yield returns to MPClient, which starts the multimodal warm-up of the front end (vllm/v1/engine/core_client.py:710).
  3. Lines 1388-1395. When the with block of MPClient ends, wait_for_engine_startup runs. The API server now waits for stop 17.

11The engine core process: handshake and EngineCore.__init__#

We are now in the new process. run_engine_core sets the process title and the log prefix EngineCore (vllm/v1/engine/core.py:1462-1472), installs signal handlers, and makes an EngineCoreProc (vllm/v1/engine/core.py:1538-1543). Its constructor first does the start-up handshake with the front end:

The engine sends HELLO and waits at most 5 minutes for the init message with the socket addresses (vllm/v1/engine/core.py:113). The front end answers at once (vllm/v1/engine/utils.py:1512-1546). Inside the handshake context, EngineCore.__init__ runs (vllm/v1/engine/core.py:1190-1226):

  1. Line 132. The general plugins run again: this is a new interpreter.
  2. Lines 135-140. The log line "Initializing a V1 LLM engine (v...) with config: model='meta-llama/Llama-3.1-8B-Instruct', ...". It prints 33 resolved fields of the config (vllm/config/vllm.py:2788-2823).
  3. Line 147. The executor constructor. Stops 12 and 13 run inside it.

12The uni executor: init_device#

The uni executor makes the worker object in this process and starts it:

init_worker resolves worker_cls from stop 8 and makes the GPU worker (vllm/v1/worker/worker_base.py:292-302, Hooks in the engine core and the workers). init_device then prepares the GPU:

  1. Lines 501-507. torch.distributed starts with a world size of 1. The comment says that this must happen before the memory snapshot, so that NCCL buffers count as used memory.
  2. Line 510. The log line "Using V2 Model Runner".

Then the worker makes cuBLAS handles, takes the memory snapshot and computes the requested memory, gpu_memory_utilization × total (vllm/v1/worker/gpu_worker.py:523-541). It builds Model Runner V2 (vllm/v1/worker/gpu_worker.py:567-580).

13load_model: the weights#

Worker.load_model calls the model runner (vllm/v1/worker/gpu_worker.py:591-598). The runner builds the model and loads the weights:

The log shows four lines here. The first is "Loading model from scratch...". Then the constructors log "Initializing model took 0.412310 seconds" (vllm/model_executor/model_loader/base_loader.py:82-85). The default loader logs "Loading weights took 4.12 seconds" (vllm/model_executor/model_loader/default_loader.py:505-508). The last is "Model loading took 14.99 GiB memory and 5.031062 seconds" (illustrative values; the code prints the seconds with six decimals).

14_initialize_kv_caches: the profile run, compilation and the KV cache size#

Back in EngineCore.__init__, the engine sizes the KV cache (vllm/v1/engine/core.py:160):

  • "Dynamo bytecode transform time: 6.10 s" (vllm/compilation/backends.py:1186-1190);
  • "Compiling a graph for compile range ... takes 20.31 s", once per compile range (vllm/compilation/backends.py:415-422);

Then the worker measures the memory and logs "Available KV cache memory: 54.6 GiB" (vllm/v1/worker/gpu_worker.py:744-748, vllm/v1/worker/gpu_worker.py:763-766). Line 311 turns the bytes into blocks. With 2 MiB per block for Llama-3.1-8B, that is 27,955 blocks (v1/worker/gpu_worker.py: the GPU Worker). Then the engine core logs the capacity:

GPU KV cache size: 447,280 tokens, Maximum concurrency for 131,072 tokens per request: 3.41x

15initialize_from_config: the KV cache tensors#

The engine core sends the KV cache config to the worker (vllm/v1/engine/core.py:362). The worker allocates the tensors:

A KV connector would start here too (vllm/v1/worker/gpu_worker.py:878). In our example there is none. After this stop, about 54.6 GiB of the GPU belong to the KV cache.

16compile_or_warm_up_model: warm-up and CUDA graph capture#

The last GPU stop (vllm/v1/engine/core.py:378-379):

  1. Lines 956-968. Each compile range that has no captured size gets one warm-up run at its end size. Each size in compile_sizes that is not a capture size gets one too (lines 941-948). In our example, the capture sizes cover the one compile range, so this loop does not run. The log is "Compile and warming up model for size %d".
  2. Line 973. Kernel warm-up and tuning before capture.
  3. Lines 983-985. CUDA graph capture, unless --enforce-eager. The log is "Graph capturing finished in 9 secs, took 0.46 GiB" (vllm/v1/worker/gpu/model_runner.py:1146-1152). The comment there says it "usually takes 5~20 seconds".

Then the worker logs "CUDA graph pool memory: ..." and a long line "Free memory on device ... Replace gpu_memory_utilization config with --kv-cache-memory=..." (vllm/v1/worker/gpu_worker.py:994-1057). The real flag name is --kv-cache-memory-bytes (vllm/engine/arg_utils.py:1385). The short form also works, because argparse accepts a unique prefix of a flag name by default (derived; no allow_abbrev=False in vllm/). Back in the engine core, one line sums up stops 14 to 16:

For example: "init engine (profile, create kv cache, warmup model) took 52.40 s (compilation: 29.70 s)". EngineCore.__init__ then builds the scheduler with the final block count, picks step_with_batch_queue, and turns on the environment variable cache (vllm/v1/engine/core.py:177-185, vllm/v1/engine/core.py:227-229, vllm/v1/engine/core.py:241-243).

17READY: the front end continues#

EngineCore.__init__ has returned. When the handshake context ends, the engine sends READY:

Before READY, still inside the with block, the engine core starts its input and output threads (vllm/v1/engine/core.py:1243-1265). The input thread connects to the front end and sends the ready response as its first message (vllm/v1/engine/core.py:1961-1968). The constructor waits for the input thread, then the block ends and READY goes out (vllm/v1/engine/core.py:1267-1272). After READY, the engine core calls vllm_config.__post_init__() again on its copy (vllm/v1/engine/core.py:1336-1337; see How configuration works, Step 9).

In the API server, wait_for_engine_startup has polled the handshake socket every 10 seconds (vllm/v1/engine/utils.py:43):

A poll with no event logs at DEBUG level and continues, so this wait has no time limit. Only a dead process stops it, with "Engine core initialization failed. See root cause above." (lines 1448-1477). The READY message moves the engine to the state READY (lines 1547-1578). Then MPClient waits for the ready response on its ROUTER socket, now with the limit VLLM_ENGINE_READY_TIMEOUT_S, 600 s by default (vllm/v1/engine/core_client.py:753-771, vllm/envs.py:810-814). It copies max_model_len, num_gpu_blocks and block_size from the response into its own config (vllm/v1/engine/core_client.py:865-879).

VLLM_ENGINE_READY_TIMEOUT_S and one API server

The timeout error text says that a timeout "is often caused by slow weight loading" (vllm/v1/engine/core_client.py:760-768). With one API server, the weights load during the wait of wait_for_engine_startup, which has no limit. The 600 s limit starts only after READY. At that time the ready response is already on the socket, because the engine core sends it before READY. The limit matters when several API servers start before the engines (deep dive "DP = 2").

18build_and_serve: the app, then uvicorn#

AsyncLLM exists now. Back in run_server_worker, the API server builds the HTTP app and serves it:

  1. Line 132. A utility call asks the engine core for its tasks. The log shows a tuple, for example "Supported tasks: ('generate',)" (vllm/v1/engine/async_llm.py:390).
  2. Line 136. build_app makes the FastAPI app with the routes, endpoint plugins, exception handlers and middleware (vllm/entrypoints/launchers/app.py:19-56). See The OpenAI-compatible server: launch modes, app, serving classes and streaming.
  3. Line 137. init_app_state makes the serving objects, for example the chat serving class (vllm/entrypoints/launchers/api_server/app_state.py:24-30).
  4. Line 139. "Starting vLLM server on http://0.0.0.0:8000".

serve_http logs "Available routes are:" and one line per route (vllm/entrypoints/launchers/launcher.py:188-208). Then it starts uvicorn on the socket from stop 4:

uvicorn runs the app's lifespan function. It starts the periodic stats log and freezes the start-up heap for the garbage collector (vllm/entrypoints/launchers/utils/server_utils.py:76-96). uvicorn then prints "Application startup complete." What changes with TP = 2

vllm serve meta-llama/Llama-3.1-8B-Instruct -tp 2
  1. Stop 7. The world size is 2, so ParallelConfig picks "mp" when Ray is not active (vllm/config/parallel.py:1055-1061, vllm/config/parallel.py:1096). Stop 9 picks MultiprocExecutor (vllm/v1/executor/abstract.py:80-83).
  2. Stop 12. The executor makes a shared-memory broadcast queue and spawns one process per rank, named VllmWorker-0 and VllmWorker-1 (vllm/v1/executor/multiproc_executor.py:165-216, vllm/v1/executor/multiproc_executor.py:745-750). Each worker gets its own pickled vllm_config (lines 731-743).
  3. Stops 12-13 in parallel. Each worker runs init_device and load_model at the same time. The log prefixes become Worker_TP0 and Worker_TP1 after the process groups exist (vllm/v1/executor/multiproc_executor.py:1083-1116). Each worker sends READY over a pipe (vllm/v1/executor/multiproc_executor.py:930-937), and the executor waits for both (vllm/v1/executor/multiproc_executor.py:787-811).
  4. Stop 14. Each worker measures its own memory. The planner uses the smallest block count of all ranks (vllm/v1/core/kv_cache_planning.py:1619-1634).
  5. Stop 13. Each worker turns on its own environment cache at the end of WorkerProc.__init__, after load_model and before the profile run (vllm/v1/executor/multiproc_executor.py:680-688, vllm/v1/executor/multiproc_executor.py:708-710).

So the server has four vLLM processes: API server, engine core and two workers. The page Executors and workers: from the engine core to the GPUs lists every executor call. Tensor parallelism itself is explained in Parallelism basics↗.

What changes with DP = 2

vllm serve meta-llama/Llama-3.1-8B-Instruct -dp 2
  1. Stop 3. --api-server-count defaults to the DP size, 2 (vllm/entrypoints/cli/serve.py:124-130). So run_multi_api_server runs, not run_server (vllm/entrypoints/cli/serve.py:151-152).
  2. Stops 4-8 in the CLI process. It binds the port with SO_REUSEPORT, builds its own VllmConfig and binds the ZMQ listeners for both API servers (vllm/entrypoints/cli/serve.py:298, vllm/entrypoints/cli/serve.py:307-334).
  3. Stop 10. launch_core_engines starts a DP coordinator process, because the internal load balancer needs its queue statistics (vllm/v1/engine/utils.py:1230-1274). It starts two engine core processes, EngineCore_DP0 and EngineCore_DP1 (vllm/v1/engine/utils.py:284).
  4. Inside the with block, before the engines are ready, the CLI process starts two API server processes, ApiServer_0 and ApiServer_1 (vllm/entrypoints/cli/serve.py:366-377, vllm/v1/utils.py:248-254). Each one runs stops 5-9 again: its own EngineArgs, create_engine_config and AsyncLLM, which connects to the existing engines (vllm/v1/utils.py:509-529, vllm/v1/engine/core_client.py:643-669).
  5. Engines. Llama is not a MoE model, so each engine core is an independent EngineCoreProc (vllm/v1/engine/core.py:1534-1543). The world size across DP is 2, so the backend is "mp" and each engine core has one worker process.
  6. Stop 17. The API server processes did not launch the engines, so they skip wait_for_engine_startup. They wait for the ready responses with the 600 s limit of VLLM_ENGINE_READY_TIMEOUT_S (vllm/v1/engine/core_client.py:753-768). If the engines load for longer than that, the API servers fail with the timeout error.

The count of vLLM processes is 8: the CLI supervisor, 2 API servers, the coordinator, 2 engine cores and 2 workers (derived). Helper processes of Python's multiprocessing are not counted. See Data parallel serving: several engine cores behind one endpoint.

Deep dive

What changes with --enforce-eager

  1. Stop 8. __post_init__ sets the compilation mode and the CUDA graph mode to NONE and turns off the JIT kernel warm-up. It logs "Enforce eager set, disabling torch.compile, CUDAGraphs, and JIT kernel warmup ..." (vllm/config/vllm.py:1745-1763). Later it clears the capture sizes (vllm/config/vllm.py:1982-1988).
  2. Stop 14. The profile run runs the model eagerly: no "torch.compile took" line.
  3. Stop 16. No capture (vllm/v1/worker/gpu_worker.py:983-985). The summary line has no "(compilation: ...)" part, because the compile time is 0 (vllm/v1/engine/core.py:401-405).

Start-up is faster, but each decode step pays the full Python and kernel launch cost. -O0 has the same effect on compilation and graphs (vllm/config/vllm.py:254-274, vllm/config/vllm.py:1806-1810). The CUDA graph idea is in GPUs and kernels↗.

Deep dive

A warm start: the compile cache

Start the same command a second time, with the same config, code and environment. Stop 14 changes:

  • The AOT path finds its file under $VLLM_CACHE_ROOT/torch_compile_cache/torch_aot_compile/<sha256>/rank_0_0/model (vllm/compilation/decorators.py:570-596). It logs "Directly load AOT compilation from path ..." (vllm/compilation/decorators.py:326-330) and still logs the total time, now small (vllm/compilation/decorators.py:302-307).
  • The key of that folder is a hash of the env factors, VllmConfig.compute_hash() and, with the mega artifact, the Inductor factors (vllm/compilation/caching.py:572-588).
  • A changed source file or a load error falls back to a full compile, with "Compiling model again due to a load failure from ..." (vllm/compilation/decorators.py:332-348).

Stop 16 does not change: CUDA graphs are captured at every start (vllm/v1/worker/gpu_worker.py:983-985). Weight loading does not change either. The page torch.compile and CUDA graphs in vLLM explains both cache folders.

Where start-up time goes, and how to reduce it

Phase (stop)Log line to readWhat reduces it
Imports and parsers (1-4)time to "non-default args"Nothing to tune; --help is slow because it reads all docstrings (vllm/engine/arg_utils.py:285-288).
Config, tokenizer, registry (6-9)"Resolved architecture"Keep the Hugging Face cache and $VLLM_CACHE_ROOT/modelinfos between starts (Out-of-tree models and the model registry).
Weights (13)"Loading weights took", "Model loading took"A fast local disk; download the weights before the start; --load-format for a faster loader ("Weight loading: from checkpoint files to GPU parameters"); vllm preload, which keeps weights in GPU memory for fast restarts (vllm/entrypoints/cli/preload.py:342-349).
Compile (14)"torch.compile took ... in total"Keep $VLLM_CACHE_ROOT (a container volume); do not change the hashed settings; -O0 or --enforce-eager skip it.
Memory profile (14)"Available KV cache memory"VLLM_ENABLE_STARTUP_PLAN=1 reuses the measured value on the same hardware and config (vllm/v1/worker/startup_plan.py:3-18). The profile run itself still runs.
Capture (16)"Graph capturing finished in ..."-O1 (piecewise graphs only); fewer sizes with -cc.max_cudagraph_capture_size; --enforce-eager skips it.
Wait for READY (17)(none at INFO)With one API server there is no limit. With several API servers, raise VLLM_ENGINE_READY_TIMEOUT_S when the engines load slowly.

A faster start can cost speed per step

-O0 and --enforce-eager remove compilation and CUDA graphs for the whole life of the server. Use them for a quick test, not for production. A warm compile cache gives most of the gain with no cost per step.

What can go wrong#

  • The port is busy. sock.bind fails at stop 4, before any GPU work (vllm/entrypoints/launchers/launcher.py:349-353).
  • The engine core fails. It logs "EngineCore failed to start." with the stack trace (vllm/v1/engine/core.py:1570-1572). The API server then raises "Engine core initialization failed. See root cause above." (vllm/v1/engine/utils.py:1468-1477). Read the EngineCore lines above it for the real error, for example a CUDA out-of-memory error.
  • Not enough free memory. The worker checks at start that the free memory is at least gpu_memory_utilization × total, and raises ValueError if not (vllm/v1/worker/utils.py:761-770). Another process on the same GPU is the usual cause.
  • The KV cache is too small for max_model_len. The planner raises ValueError at stop 14: "To serve at least one request with the model's max seq len ...". The message gives an estimated maximum length (vllm/v1/core/kv_cache_planning.py:68-88).
  • The front end waits for a long time with no log. With one API server, the wait at stop 17 logs only at DEBUG level. Read the EngineCore lines to see the progress.
  • A timeout with several API servers. "Timed out waiting for engine core processes to start" after VLLM_ENGINE_READY_TIMEOUT_S (vllm/v1/engine/core_client.py:757-768).

Why it matters. A server that does not start, or starts slowly, costs capacity during each deploy and each restart. When you know the 18 stops, you can read the log, find the slow phase, and pick the setting that shortens it.

Check yourself#

  1. 1
    In which process does the model load when you run vllm serve on one GPU?
    easy
    Show answer

    In the engine core process. The uni executor makes the worker object in that process and calls load_model on it (vllm/v1/executor/uniproc_executor.py:54-74).

  2. 2
    Why does a busy port fail in seconds and not after the model loads?
    easy
    Show answer

    setup_server binds the socket before the engine starts, at stop 4 (vllm/entrypoints/launchers/launcher.py:372-379).

  3. 3
    Which stop runs torch.compile on a cold start, and why there?
    medium
    Show answer

    Stop 14. The profile run in determine_available_memory is the first call of the compiled model, so the compilation happens inside it (vllm/v1/worker/gpu_worker.py:682-697). The memory profile then also measures the compiled model.

  4. 4
    You set VLLM_ENGINE_READY_TIMEOUT_S=60 and start a single-GPU server whose weights take 5 minutes to load. What happens?
    medium
    Show answer

    The server starts normally. With one API server, the front end waits in wait_for_engine_startup, which has no time limit (vllm/v1/engine/utils.py:1434-1447). The 60 s limit applies only to the ready response after READY (vllm/v1/engine/core_client.py:753-768).

  5. 5
    How many times does pre_register_and_update run in the API server process for vllm serve <model>, and where?
    hard
    Show answer

    Five times. Three parser builds at stop 2 (serve, launch render, run-batch) each call AsyncEngineArgs.add_cli_args (vllm/engine/arg_utils.py:3257). log_non_default_args at stop 4 builds a fourth parser (vllm/entrypoints/common/startup.py:70-71). create_engine_config calls the hook a fifth time, without a parser (vllm/engine/arg_utils.py:2246).
