Tour: One engine step

AdvancedGuided toursabout 16 min read + 2 min deep dives

Code version: vLLM @ 3e44c0d · 2026-10-22

Before you read

This page uses ideas from these pages:

  • Tour: Life of a chat request Beginner
  • The engine core loop: threads, queues and the busy loop Intermediate
  • Async scheduling: overlap the CPU and the GPU Advanced

In one sentence

We follow one call of step_with_batch_queue: it plans and starts step k for two requests, then finishes step k-1 and sends its token.

The idea#

Tour 1 (Tour: Life of a chat request) follows one request through the whole server. This tour stays in one place, the engine core process, and looks at one engine step in detail. A real server has many requests in each step, so we take two that need different work:

  • Request B is a chat answer in progress. It decodes: it needs 1 new token per step.
  • Request A has a long prompt of 20,000 tokens. The prompt does not fit into one step, so the scheduler runs it in chunks (chunked prefill↗).

With async scheduling, one call of step_with_batch_queue does two things. It plans and starts step k, and then it finishes step k-1, which is already on the GPU. So the token that this call sends belongs to the step before. The page Async scheduling: overlap the CPU and the GPU explains why.

An everyday comparison. Think of a bakery with one oven. The baker puts the next tray into the queue of the oven before the current tray is done. Then the baker takes out the finished tray and packs it. One tray holds rolls (one each, the decodes) and a big part of a cake (the prefill chunk). The comparison stops in one place. The cake leaves the oven unfinished and goes back in the next round. Only a finished cake is packed. A prefill chunk gives no token.

The example#

vllm serve meta-llama/Llama-3.1-8B-Instruct     # one H100 80 GiB GPU, default settings
  • One GPU, TP = 1, DP = 1: the uni executor runs the worker in the engine core process (vllm/config/parallel.py:1099-1100).
  • Token budget: max_num_batched_tokens = 8192 and max_num_seqs = 1024, because the GPU has 70 GiB or more and is not an A100 (vllm/engine/arg_utils.py:2960-2993). An A100 would get 2048 and 256.
  • Async scheduling is on, and the batch queue has 2 slots (vllm/config/vllm.py:1664-1698, vllm/config/vllm.py:586-597).
  • Step k-1 is already on the GPU. In it, B decoded its 41st output token, and A ran its first chunk: prompt positions 0 to 8190.

Simplified

The model, the prompt lengths and the positions are illustrative. The scheduler and model runner rules are from the code. We assume a block size of 16 tokens, no prefix cache hit for A, no structured output, no speculative decoding, and no LoRA.

1The busy loop calls step_with_batch_queue#

We are in the main thread of the engine core process, in EngineCoreProc._process_engine_step. The input queue is empty, and the scheduler has two running requests, so the busy loop does not block (vllm/v1/engine/core.py:1596-1602). It calls the step function:

step_fn is step_with_batch_queue, because the batch queue exists (vllm/v1/engine/core.py:227-229). Right now the queue holds one entry: step k-1.

What the data looks like now:

batch_queue = deque([(future_sample[k-1], scheduler_output[k-1], future_exec[k-1])], maxlen=2)
scheduler.running = [B, A]       # B first: it was running before A arrived

2Scheduler.schedule(): sharing 8192 tokens#

We are in vllm/v1/core/sched/scheduler.py. The scheduler has no prefill phase and no decode phase. It gives every running request the tokens it still needs, until the budget is used (see The V1 scheduler: one token budget, no phases). The running pass computes the need of each request:

  1. B. B knows 540 tokens (500 prompt + 40 output). Token 41 is in flight, so B has 1 output placeholder, and num_computed_tokens = 540. So 540 + 1 - 540 = 1. The budget drops from 8192 to 8191.
  2. A. A has 20,000 prompt tokens, no placeholder, and 8191 computed tokens. Its need is 20000 - 8191 = 11809, but line 766 caps it at the budget: 8191. The budget is now 0.

The order matters: the running pass goes through self.running from the front (vllm/v1/core/sched/scheduler.py:713-716). B was first, so the decode gets its token before the prefill takes the rest. long_prefill_token_threshold could cap A further, but its default is 0, which means no cap (vllm/config/scheduler.py:79-84). The waiting pass has no budget left, so no new request starts in this step.

Then allocate_slots reserves KV cache slots for the new tokens (vllm/v1/core/sched/scheduler.py:831-838). With blocks of 16 tokens, A needs ceil(16382 / 16) = 1024 blocks; it had 512, so it gets 512 new blocks. B needs ceil(541 / 16) = 34 blocks, the same as before. (Derived.) The KV cache and its blocks are explained in The KV cache↗.

3The SchedulerOutput, and the placeholder for B#

Both requests ran before, so they travel as CachedRequestData, which carries only the changes (vllm/v1/core/sched/output.py:137-152). The scheduler builds it before it advances the counters (vllm/v1/core/sched/scheduler.py:1527-1534), then builds the SchedulerOutput (vllm/v1/core/sched/scheduler.py:1588-1609), and only then calls _update_after_schedule (vllm/v1/core/sched/scheduler.py:1641-1643). That method advances num_computed_tokens and decides whether each request is still in a prefill chunk:

For A: 8191 + 8191 = 16382 < 20000, so A is still a prefill chunk. For B: 541 < 540 + 1 is false, so B is not. AsyncScheduler then adds placeholders only for B:

What the data looks like now (illustrative ids):

SchedulerOutput(
    scheduled_new_reqs=[],
    scheduled_cached_reqs=CachedRequestData(
        req_ids=["B", "A"],
        new_block_ids=[None, ([b512, ..., b1023],)],   # 512 new block ids for A
        num_computed_tokens=[540, 8191],               # values before this step
        num_output_tokens=[41, 0], ...),               # 40 known + 1 placeholder for B
    num_scheduled_tokens={"B": 1, "A": 8191},

    scheduled_spec_decode_tokens={}, finished_req_ids=set(), ...)
B.num_computed_tokens = 541;   B.num_output_placeholders = 2    # tokens 41 and 42 in flight

num_output_tokens includes the placeholders (vllm/v1/core/sched/scheduler.py:1825-1827). The page Data contracts between the parts of vLLM lists all fields.

4The executor starts execute_model, without a wait#

Back in step_with_batch_queue, the engine core passes the plan to the executor:

model_executed is true, because 8192 tokens are scheduled. The uni executor runs the worker method at once, in this thread:

The call goes through WorkerWrapperBase.execute_model (vllm/v1/worker/worker_base.py:378-383) to Worker.execute_model, which calls the model runner:

With one GPU there is no message queue. With TP = 2, this stop would put the call into a shared-memory queue for two worker processes instead (Executors and workers: from the engine core to the GPUs).

5Model Runner V2: update states, sort the batch, pick a CUDA graph mode#

We are in vllm/v1/worker/gpu/model_runner.py. Model Runner V2 keeps its own copy of each request's state. First it applies the changes from the plan:

update_requests stores the computed-token counts and appends A's 512 new block ids to its block table (vllm/v1/worker/gpu/model_runner.py:1257-1269). Then the runner sorts the batch: decodes first, then prefills (vllm/v1/worker/gpu/model_runner.py:1312-1314, vllm/v1/worker/gpu/model_runner.py:2471-2483). B has 1 token, which equals the decode query length, so B is row 0 and A is row 1.

Next it picks a CUDA graph mode for the batch shape (vllm/v1/worker/gpu/model_runner.py:1806-1821). Our batch has 8192 tokens and contains a prefill. On an H100 the largest captured size is 512 tokens: min(max_num_seqs × 1 × 2, 512) with max_num_seqs = 1024 (vllm/config/vllm.py:2439-2449). No captured graph matches 8192 tokens, so dispatch returns mode NONE: eager (vllm/v1/worker/gpu/cudagraph_utils.py:535-553). With DP = 1, no padding across ranks changes this result (vllm/v1/worker/gpu/dp_utils.py:270-279).

A pure decode step looks different

When A has finished its prefill, a step with B and A both decoding has 2 tokens. That batch is a uniform decode batch below 512 tokens, so it can replay a FULL CUDA graph. The page torch.compile and CUDA graphs in vLLM explains the modes.

6prepare_inputs and prepare_attn: the flat batch#

The runner packs both requests into one flat batch of 8192 tokens, as in Input metadata↗. query_start_loc marks where each request starts:

A is in a prefill, so its prompt tokens are copied on the GPU from the request state (vllm/v1/worker/gpu/model_runner.py:1469-1479). B's input token is token 41, which the CPU does not know yet. It comes from last_sampled_tokens on the GPU, which step k-1 will write before step k runs on the same stream:

Without speculative decoding, each request gets one logits row (vllm/v1/worker/gpu/model_runner.py:1401-1408): the last token of its query. Then prepare_attn builds the block tables and the slot of each new token, and the model state builds the attention metadata (vllm/v1/worker/gpu/model_runner.py:1838, vllm/v1/worker/gpu/model_runner.py:1940-1951).

What the data looks like now (step k, derived from our numbers):

num_scheduled_tokens = [1, 8191]              # row 0 = B, row 1 = A
query_start_loc  int32 [3]    = [0, 1, 8192]
positions        int64 [8192] = [540, 8191, 8192, ..., 16381]
seq_lens         int32 [2]    = [541, 16382]
input_ids        int32 [8192] = [token 41 of B (from GPU), A's prompt tokens 8191..16381]
logits_indices   [2]          = [0, 8191]
slot_mappings    one slot per token: B -> its block index 33, offset 12 (540 = 33 x 16 + 12)
                 A -> its block indexes 511 .. 1023 (positions 8191 .. 16381)

The block indexes are positions in each request's own block table. The table maps them to physical block ids in the block pool, and the slot of a token is block_id × 16 + offset (vllm/v1/worker/gpu/block_table.py:409).

7The forward pass is queued, and execute_model returns None#

In mode NONE, the runner calls the model eagerly, inside the forward context that gives each attention layer its metadata:

The Python code returns as soon as all kernels are queued; the GPU runs them later, after step k-1. The runner keeps the hidden states for the sampler and returns None:

Back in the uni executor, the future is already done with the value None (vllm/v1/executor/uniproc_executor.py:112-113). The tour Tour: One forward pass goes inside the model call.

Simplified

"Queued" ignores small CPU work that PyTorch does per kernel. The point is that this stop does not wait for the GPU: Model Runner V2 has no GPU-to-CPU synchronization in execute_model (docs/design/model_runner_v2.md:47).

8The grammar bitmask: not needed this time#

Back in step_with_batch_queue. Before sampling, the engine core may compute a grammar bitmask for structured output requests, on the CPU, while the GPU works:

Our requests do not use structured output, so has_structured_output_requests is false and get_grammar_bitmask returns None at once (vllm/v1/core/sched/scheduler.py:2091-2092). If B used a JSON schema, its token 41 would still be in flight. Then pending_structured_output_tokens would be true, and sampling would wait until stop 11 (vllm/v1/core/sched/async_scheduler.py:37-39, vllm/v1/engine/core.py:792-810).

9sample_tokens: logits for two rows, one token, an AsyncOutput#

sample_tokens(None, non_block=True) takes the same path as stop 4 and reaches the runner. It computes logits only for the two rows in logits_indices, and samples:

The comment gives the rule: a request in a chunked prefill "produce[s] no output token". So num_sampled = [1, 0]: B gets token 42, A gets nothing. The runner starts the copy of the result to the CPU on a separate stream. Then it writes token 42 into last_sampled_tokens for step k+1:

The uni executor wraps the AsyncOutput in an AsyncOutputFuture; nothing waits yet (vllm/v1/executor/uniproc_executor.py:109-111). The sampling methods are in Sampling↗.

What the data looks like now (on the GPU, step k):

logits             [2, vocab_size]       # rows of B and A
sampled_token_ids  [2, 1] = [[t42], [x]] # x is ignored
num_sampled        [2]    = [1, 0]
last_sampled_tokens[B] = t42             # input of B in step k+1

10The batch queue is full: pop step k-1 and wait#

Step k goes into the queue. Now the queue has 2 entries, which is full, so the function does not return early:

pop() takes step k-1 from the right end. future.result() calls AsyncOutput.get_output() (vllm/v1/executor/uniproc_executor.py:38-48). This is the one place where the engine core waits for the GPU:

If the GPU has already finished step k-1, the wait returns at once. Meanwhile, step k is already queued behind it on the GPU. Line 183 trims each row to its sampled count, so A's row becomes an empty list.

What the data looks like now (step k-1):

ModelRunnerOutput(req_ids=["B", "A"],
                  sampled_token_ids=[[t41], []],   # A ran its first chunk in step k-1
                  logprobs=None, ...)

11update_from_output for step k-1#

Before the update, the engine core applies any aborts that arrived during the step (vllm/v1/engine/core.py:780-785). Then the scheduler walks over the requests of step k-1:

  1. B. It has a new token, so _update_request_with_output appends t41 and runs check_stop (vllm/v1/core/sched/scheduler.py:2598-2603). t41 is not EOS, so B keeps running. AsyncScheduler removes one placeholder: 2 becomes 1 (vllm/v1/core/sched/async_scheduler.py:71-73). It caches full blocks up to 541 - 1 = 540 tokens for the prefix cache (lines 76-79 there).
  2. A. No new tokens, no pooler output, no stop: the scheduler makes no output for A (vllm/v1/core/sched/scheduler.py:2293-2295).

The outputs are grouped by front end (vllm/v1/core/sched/scheduler.py:2486-2491). With stats on, the scheduler stats go into the same object (vllm/v1/core/sched/scheduler.py:2507-2521).

What the data looks like now:

{0: EngineCoreOutputs(
        outputs=[EngineCoreOutput(request_id="B", new_token_ids=[t41], finish_reason=None, ...)],
        scheduler_stats=SchedulerStats(num_running_reqs=2, num_waiting_reqs=0, ...))}
B: num_tokens = 541, num_computed_tokens = 541, num_output_placeholders = 1   # t42 still in flight

12The outputs go to the output thread#

step_with_batch_queue returns the dict and model_executed = True. _process_engine_step puts each pair into output_queue (stop 1, lines 1673-1674) and calls post_step, which does nothing with async scheduling (vllm/v1/engine/core.py:689-696). The output thread takes the pair, encodes it with msgpack, and sends it on the PUSH socket of front end 0:

From here, Tour 1 continues: the front end detokenizes t41 and writes one SSE chunk (Tour 1, stop 15). The busy loop goes back to stop 1. The next call schedules step k+1: B again 1 token, and A its last chunk of 20000 - 16382 = 3618 tokens. That chunk ends the prompt, so A samples its first token there.

Deep dive

In S k+1, A's need is 20000 + 0 - 16382 = 3618, so the budget is not full: 8192 − 1 − 3618 = 4573 tokens remain for waiting requests. In S k+2, A decodes for the first time, with its first token still in flight.

Deep dive

Where the time goes in this call

  • Stops 2-3 run in Python in the scheduler. Their cost grows with the number of running requests, not with the number of tokens. The comment in update_from_output warns that its loop "can be a performance bottleneck" with 1K or more requests (vllm/v1/core/sched/scheduler.py:2163-2165).
  • Stops 5-7 and 9 run on the CPU but only queue GPU work. Their cost is the Python code of the model runner and the kernel launches. A CUDA graph replaces many launches with one; our eager step does not have this help.
  • Stop 10 is the only wait for the GPU. When the GPU step takes longer than all the CPU work of a call, the main thread waits here, and the GPU never waits. That is the goal of async scheduling.
  • Stop 12 encoding and sending run in the output thread, in parallel with the next call.
Deep dive

What changes with TP = 2

Stops 1-3, 8 and 10-12 do not change. In stops 4 and 9, the multiproc executor writes the call once into the shared-memory queue. Both worker processes run stops 5-7 and 9 on their own GPU, and they meet in NCCL all-reduces. Only worker 0 replies (vllm/v1/executor/multiproc_executor.py:549-563). The wait of stop 10 then happens in worker 0's WorkerAsyncOutputCopy thread, which calls get_output(), and the engine core waits for the reply message (vllm/v1/executor/multiproc_executor.py:1000-1002, vllm/v1/executor/multiproc_executor.py:1019-1039). See Executors and workers: from the engine core to the GPUs and Tour: One step across GPUs.

What can go wrong#

  • A long prompt slows every stream. In our step, B shares a step of 8192 tokens with A's chunk. B's next token comes only when that large step ends. long_prefill_token_threshold limits one prompt's share of a step (vllm/v1/core/sched/scheduler.py:764-765).
  • No KV blocks for the chunk. If allocate_slots fails, the scheduler preempts a running request to free blocks. With the default first-come-first-served policy, the victim is the last request in self.running (vllm/v1/core/sched/scheduler.py:850-858, vllm/v1/core/sched/scheduler.py:889-900). In our batch this is A itself: A loses its KV cache and must compute it again later, and B keeps running.
  • An exception in the model. log_error_detail dumps the SchedulerOutput of the failed step, and the engine core dies with ENGINE_CORE_DEAD (vllm/v1/engine/core.py:561-575, The engine core loop: threads, queues and the busy loop).
  • A request aborted during the step. Its row still runs on the GPU. _process_aborts_queue finishes it before the update, and the update skips it (vllm/v1/engine/core.py:780-782, vllm/v1/core/sched/scheduler.py:2184-2192).

Why it matters. Every performance number of vLLM comes from this loop. The size of each step comes from stop 2, the CPU cost from stops 2-9, and the GPU cost from stop 7. When you tune max_num_batched_tokens or read a profile, you can now map each part to a stop.

Check yourself#

  1. 1
    In this tour, which step's token does the call send to the front end?
    easy
    Show answer

    The token of step k-1 (B's token 41). The call schedules and starts step k first, then pops step k-1 from the batch queue and updates the scheduler with it (vllm/v1/engine/core.py:753-785).

  2. 2
    Why does A get 8191 tokens and not 11809?
    medium
    Show answer

    The running pass caps each request at the remaining token budget (vllm/v1/core/sched/scheduler.py:766-768). B came first and took 1 token of the 8192, so 8191 remained. long_prefill_token_threshold is 0 by default, so it does not cap A further (vllm/config/scheduler.py:79-84).

  3. 3
    Where does B's input token for step k come from, given that the CPU has not received it yet?
    medium
    Show answer

    From req_states.last_sampled_tokens on the GPU. combine_sampled_and_draft_tokens copies it into input_ids in prepare_inputs (vllm/v1/worker/gpu/model_runner.py:1493-1500). Step k-1 writes it in postprocess_sampled, earlier on the same CUDA stream (vllm/v1/worker/gpu/model_runner.py:1715-1726).

  4. 4
    A has a logits row in step k. Why does it have no token in the ModelRunnerOutput, and why does the scheduler send nothing for A?
    hard
    Show answer

    Without spec decoding, every request gets one logits row (vllm/v1/worker/gpu/model_runner.py:1401-1408). The sampler sets num_sampled = 0 for a chunked-prefill request (vllm/v1/worker/gpu/sample/sampler.py:190-199), and get_output() trims the row to an empty list (vllm/v1/worker/gpu/async_utils.py:182-183). With no new tokens, no pooler output and no stop, the scheduler makes no EngineCoreOutput (vllm/v1/core/sched/scheduler.py:2293-2295).

  5. 5
    Which CUDA graph mode does step k use, and what would a step with only B and A decoding use?
    hard
    Show answer

    Step k has 8192 tokens and a prefill. The largest captured size on this GPU is 512 (vllm/config/vllm.py:2439-2449), so no captured graph matches, and dispatch returns NONE (eager) (vllm/v1/worker/gpu/cudagraph_utils.py:535-553). A step with two 1-token decodes is a uniform decode batch of 2 tokens. So it can replay a FULL graph under the default mode FULL_AND_PIECEWISE (vllm/config/vllm.py:310).

  • The engine core loop: threads, queues and the busy loopThe engine core process runs three threads. An input thread decodes requests, the main thread runs the busy loop with the scheduler and the executor, and an output thread sends the results back.
  • Async scheduling: overlap the CPU and the GPUWith async scheduling, the engine core schedules and starts step N+1 before it waits for the token of step N. Placeholders in the scheduler and a GPU-side token buffer in Model Runner V2 make this possible.
  • Executors and workers: from the engine core to the GPUsThe executor starts the workers and runs each call on all of them. The uni executor calls one worker in the engine core process; the multiproc executor sends calls to one worker process per GPU through a shared-memory queue.
  • The V1 scheduler: one token budget, no phasesIn each engine step, Scheduler.schedule() shares one token budget: first among the running requests, then among the waiting ones. It has no prefill or decode phase, it preempts the last running request when KV blocks run out, and update_from_output() appends the sampled tokens.
  • The model runner (Model Runner V2)Model Runner V2 keeps every running request in a fixed row of GPU tensors, gathers each step's inputs from those rows with GPU kernels, runs the model (CUDA graph or eager), and samples in a second call that returns an AsyncOutput without a GPU wait.
  • Data contracts between the parts of vLLMThe typed messages between the parts of vllm serve: EngineCoreRequest, Request, SchedulerOutput, ModelRunnerOutput, EngineCoreOutput(s), RequestOutput and the OpenAI response objects. Their fields, who makes them, and how they travel.
  • v1/engine/core.py: EngineCore and the engine core processvllm/v1/engine/core.py defines EngineCore (scheduler + executor + step functions), EngineCoreProc (the process with its ZMQ threads and busy loop) and DPEngineCoreProc (the lock-step variant for MoE data parallelism).
  • v1/worker/gpu_worker.py: the GPU Workervllm/v1/worker/gpu_worker.py defines Worker, the object that owns one GPU. It sets up the device and NCCL, builds Model Runner V2, profiles memory to size the KV cache, warms up the model, and forwards each step to the model runner.
  • Tour: One forward passFollow one forward pass of Llama-3-8B on one H100 in 14 stops, for a batch of two decodes and one 298-token prompt: Model Runner V2 inputs, the PIECEWISE CUDA graph, one decoder layer with its shapes, FlashAttention, logits and the sampler.
  • Tour: One step across GPUsFollow two requests through vllm serve -tp 2 -dp 2 in 13 stops: the API servers pick an engine each, two independent engine cores schedule, each broadcasts the step to its two workers through shared memory, the workers meet in 65 all-reduces on their TP group, only rank 0 replies, and the coordinator publishes the new load.
