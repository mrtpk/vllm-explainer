vLLM and DeepInfer compared

Referenceabout 10 min read

Code version: vLLM @ 3e44c0d · 2026-10-22

In one sentence

DeepInfer is a small, offline, one-model engine with a C++ scheduler; vLLM is a general online serving engine with a Python scheduler and many extension points.

DeepInfer "was originally built primarily on vLLM" (DeepInfer Explained↗). So most ideas have the same name on both sites. This page lists where the two engines differ. Use it when a DeepInfer page gives a number or a rule, and you want to know if it holds in vLLM.

  • Each vLLM cell cites the vLLM code at the pinned commit, or links the page of this site that explains it.
  • Each DeepInfer cell links the DeepInfer Explained page that states it. This site does not cite DeepInfer code.

The short table on What vLLM is today has the main rows. The page What you need from DeepInfer Explained gives the differences for each of the 12 basics.

How you use itOffline only. Your script calls LLM.generate(), which calls step() until no request is left (Offline API and the step loop↗). The release has no online-serving wrapper (DeepInfer FAQ↗, "What is not in this release?").Online first. vllm serve starts an OpenAI-compatible HTTP server (vllm/entrypoints/cli/serve.py:39-40). The offline LLM class also exists and uses its own usage context (vllm/entrypoints/llm.py:341-343). See The OpenAI-compatible server: launch modes, app, serving classes and streaming.
ProcessesThe engine and the driver worker run in your script process; context-parallel followers run in their own processes (Worker↗). Each data-parallel replica is its own process with its own engine, started by the example launcher (Data parallelism and step votes↗).The API server process and an engine core process, joined by ZMQ sockets (vllm/v1/engine/core_client.py:672-682). AsyncLLM always starts the engine core in a background process (vllm/v1/engine/async_llm.py:188-193). With TP = PP = DP = 1 the worker runs inside the engine core (vllm/config/parallel.py:1099-1100); otherwise one worker process per GPU. See The process and thread architecture of vllm serve.
Data-parallel replicasReplicas vote with all-reduces, so that all run a prefill step or all run a decode step (Data parallelism and step votes↗).One engine core per DP rank. Dense models get independent engines; MoE models use DPEngineCoreProc (vllm/v1/engine/core.py:1534-1543). The API server balances requests over the engines (vllm/v1/engine/core_client.py:1776-1789). See Data parallel serving: several engine cores behind one endpoint.
ModelsOne model family, DeepSeek-V4.1-Flash (Model map↗).A registry of hundreds of architecture names (vllm/model_executor/models/registry.py:806-817), plus out-of-tree models (Out-of-tree models and the model registry).

Scheduler and KV cache#

TopicDeepInfervLLM
LanguageC++ scheduler (The scheduler↗).Python (vllm/v1/core/sched/). See The V1 scheduler: one token budget, no phases.
Step kindsA step is a prefill step or a decode step, never both. A prefill starts only at attempt points: every 70 or 100 decode steps (The scheduler↗).No prefill phase and no decode phase. Each request catches up from num_computed_tokens to its token count, so one step can mix prompt chunks and decode tokens (vllm/v1/core/sched/scheduler.py:624-633).
Order and preemptionDecode serves the fewest output tokens first; it preempts the sequence with the most output tokens. A preempted sequence stops or is recomputed (stop_preempted_request) (The scheduler↗).Running requests first, then waiting ones (vllm/v1/core/sched/scheduler.py:713-715, vllm/v1/core/sched/scheduler.py:956). With the default FCFS policy the victim is the last running request (vllm/v1/core/sched/scheduler.py:852-858). Preemption always recomputes: blocks freed, computed tokens set to 0, request back at the front of the queue (vllm/v1/core/sched/scheduler.py:1676-1700).
Overlap of CPU and GPUZero-overhead scheduling: the CPU prepares step N+1 while the device runs step N, and step() returns tokens one step late (Zero-overhead scheduling↗).Async scheduling is on by default when the configuration allows it (vllm/config/vllm.py:1664-1698). The engine core then runs step_with_batch_queue (vllm/v1/engine/core.py:227-229). See Async scheduling: overlap the CPU and the GPU.
Block size128 tokens (Paged KV cache↗).16 tokens by default (vllm/config/cache.py:182). When you do not set --block-size, the platform picks a size that all attention backends accept (vllm/platforms/interface.py:771-781).
Prefix cachingNone in the release (Paged KV cache↗).On by default when the model supports it (vllm/engine/arg_utils.py:3062-3063, vllm/config/model.py:2275-2291). See Prefix caching in the engine core: hashes, lookup, caching, eviction and KV events.
Cache layout for mixed layer typesOne paged byte buffer for the compressed KV and the indexer keys; the sliding-window cache is a ring per sequence in a separate state buffer, with a second block manager for state slots (Paged KV cache↗, Sliding-window attention↗).KV cache groups, one per kind of layer, with one shared block pool. The coordinator is NoPrefixCache, Unitary (one group) or Hybrid (vllm/v1/core/kv_cache_coordinator.py:995-1024). See The hybrid KV cache: specs, groups and one manager per layer type.

Numbers that change between the sites#

Examples on DeepInfer pages use DeepInfer's settings. Recompute them with the vLLM defaults:

  • Blocks per prompt. A 1,000-token prompt needs ⌈1,000 / 16⌉ = 63 blocks in vLLM and ⌈1,000 / 128⌉ = 8 blocks in DeepInfer.
  • Tokens per decode step. DeepInfer sends 1 + 5 rows per request in a decode step by default (Speculative decoding↗). vLLM sends 1 row per request when speculative decoding is off.
  • Wait for the first prefill. A new DeepInfer request waits for the next attempt point (The scheduler↗). In vLLM, a waiting request can start in the next step when the token budget and the KV cache allow it (vllm/v1/core/sched/scheduler.py:956).

Check yourself#

  1. 1
    What is the default KV block size in each engine, and which one has prefix caching?
    easy
    Show answer

    DeepInfer uses 128 tokens and has no prefix cache in its release (Paged KV cache↗). vLLM uses 16 tokens by default (vllm/config/cache.py:182) and turns prefix caching on for models that support it (vllm/engine/arg_utils.py:3062-3063).

  2. 2
    Both engines have something called DSpark. Is it on by default in vLLM?
    medium
    Show answer

    No. dspark is one value of the speculative method (vllm/config/speculative.py:70), and speculative decoding needs --speculative-config. Adaptive verification, which sizes the verification budget from per-request confidence, is a separate opt-in field (vllm/config/speculative.py:559-561).

  3. 3
    A DeepInfer page says that a step is either a prefill step or a decode step. Why can a vLLM metrics dashboard not show separate prefill-step and decode-step times?
    hard
    Show answer

    The vLLM scheduler has no phases. Each request only catches up from its computed tokens to its token count, so one step holds prompt chunks and decode tokens together (vllm/v1/core/sched/scheduler.py:624-633). The per-request metrics measure intervals of one request instead, for example the prefill interval from the first SCHEDULED event to the first token (vllm/v1/metrics/stats.py:599-601).

Related pages

  • What vLLM is todayvLLM is an inference and serving engine for LLMs. At this commit it has one engine, V1. You use it through vllm serve (an OpenAI-compatible HTTP server, the main path of this site) or through the offline LLM class. Both reach the same engine core.
  • What you need from DeepInfer ExplainedThis site does not teach the LLM basics again. This page gives a one-line recap of each of the 12 basics pages of DeepInfer Explained, with a link, and one line on what vLLM does differently.
  • The process and thread architecture of vllm servevllm serve runs API server processes for HTTP and text, one engine core process per data parallel rank for scheduling, and worker processes for the GPUs. ZMQ, shared memory and NCCL connect them.
  • The V1 scheduler: one token budget, no phasesIn each engine step, Scheduler.schedule() shares one token budget: first among the running requests, then among the waiting ones. It has no prefill or decode phase, it preempts the last running request when KV blocks run out, and update_from_output() appends the sampled tokens.
  • The KV cache manager: blocks, the block pool and memory sizingIn the engine core, the KVCacheManager hands out KV blocks to the scheduler through a coordinator, one single-type manager per KV cache group and one BlockPool. The workers only receive block ids. The number of blocks comes from a memory profile at start-up.
  • The model runner (Model Runner V2)Model Runner V2 keeps every running request in a fixed row of GPU tensors, gathers each step's inputs from those rows with GPU kernels, runs the model (CUDA graph or eager), and samples in a second call that returns an AsyncOutput without a GPU wait.
  • torch.compile and CUDA graphs in vLLMvLLM compiles the inner model once with torch.compile and its own Inductor backend, splits the graph at the attention ops, caches the result on disk, and captures CUDA graphs at start-up. Each step, Model Runner V2 replays a FULL graph for uniform decode batches, PIECEWISE graphs for other batches up to the largest capture size, and runs eagerly above it.
  • Speculative decoding in vLLM servingHow vLLM serves with draft tokens - SpeculativeConfig and the methods, how drafts take part in the token budget and in async scheduling, the Model Runner V2 speculator, verification with the RejectionSampler and its four variants, multi-token outputs, the acceptance metrics, CUDA graphs and tuning.
  • Process groups: how vLLM slices its ranksEach worker puts all ranks into one grid of shape (DP, PP, PCP, TP) and cuts it into process groups. Each group is a GroupCoordinator with a gloo CPU group, an NCCL device group and, for groups of more than one rank, a device communicator that picks the all-reduce implementation.
  • Extension pointsThe full reference of every vLLM extension point - the six entry-point groups, the registries, the config hooks and the Platform hooks - with how to register, the line that reads it, the processes, the start-up moment, what a duplicate does, whether it is on by default, and the page that explains it.
