Config classes

Referenceabout 89 min read

Code version: vLLM @ 3e44c0d · 2026-10-22

In one sentence

Each part of the engine configuration is one @config dataclass in vllm/config/, and one VllmConfig object holds the top-level ones.

Use this page in two ways. To learn the mechanism, read the first four sections. To look up one class or field, go to All config classes, or search for its name. The script tools/gen_config_classes.py makes the tables from the source of vllm/config/*.py. The text above the tables is written by hand from the code.

The @config decorator#

All config classes use the decorator config from vllm/config/utils.py. It makes a config class: a pydantic dataclass whose settings forbid extra fields:

dataclass here is pydantic.dataclasses.dataclass (vllm/config/utils.py:20). This has three effects:

  • Unknown keys are an error. extra="forbid" rejects a key that is not a field. A JSON flag such as --compilation-config is parsed with pydantic, and a ValidationError becomes an argparse error (vllm/engine/arg_utils.py:369-374). So a misspelled key stops vllm serve at start-up.
  • Field limits are checked. Fields can use Field(default=..., ge=1), and pydantic checks the value. For example, gpu_memory_utilization must be above 0 and at most 1 (vllm/config/cache.py:212).
  • A class can pass its own pydantic settings. VllmConfig uses @config(config=ConfigDict(arbitrary_types_allowed=True)) (vllm/config/vllm.py:347).

The docstring of the decorator says that all config classes in vLLM should use it (vllm/config/utils.py:61).

Field docstrings are the help text#

A config class documents each field with a string literal right after it. Python ignores these strings, but get_attr_docs reads them from the source with ast (vllm/config/utils.py:161-198, vllm/config/utils.py:201-215). The vllm serve --help text comes from them (vllm/engine/arg_utils.py:355-356). This is SchedulerConfig:

The generated tables mark these two kinds. An InitVar is not in dataclasses.fields(), so get_kwargs of its class makes no flag for it (vllm/engine/arg_utils.py:329). For example, ModelConfig takes the multimodal settings as InitVar arguments and builds a MultiModalConfig from them (vllm/config/model.py:432-434, vllm/config/model.py:572-577, vllm/config/model.py:881). The flags, for example --limit-mm-per-prompt, come from the fields of MultiModalConfig (vllm/engine/arg_utils.py:1489-1491).

VllmConfig: the container#

VllmConfig has one attribute for each sub-config, plus some top-level settings (vllm/config/vllm.py:347-457):

Most attributes have a default factory, so VllmConfig() makes default sub-configs. model_config is None by default, because a default ModelConfig would try to download a model (vllm/config/vllm.py:353-355). Optional features such as lora_config and speculative_config are None when they are off (vllm/config/vllm.py:381-384). For vllm serve, EngineArgs.create_engine_config builds each sub-config and then calls VllmConfig(...) (vllm/engine/arg_utils.py:2870). See vllm serve flags for the flag side.

What __post_init__ does#

VllmConfig.__post_init__ runs after pydantic has made the object. It is about 830 lines long (vllm/config/vllm.py:1492-2318). Its docstring says: "Verify configs are valid & consistent with each other." (vllm/config/vllm.py:1493). These are the main steps, in code order:

  1. It sets instance_id from the clock (vllm/config/vllm.py:1495).
  2. It turns off prefix caching for an instance that runs only the multimodal encoder (vllm/config/vllm.py:1505-1516).
  3. It runs the per-architecture config hooks of the model in try_verify_and_update_config (vllm/config/vllm.py:1521, vllm/config/vllm.py:2714-2733).
  4. It decides async scheduling when the flag is not set (vllm/config/vllm.py:1664-1698).
  5. With enforce_eager, it turns off torch.compile and CUDA graphs (vllm/config/vllm.py:1745-1747).
  6. It applies the platform defaults, picks the compilation mode from the optimization level, and applies the defaults of that level (vllm/config/vllm.py:1804-1810, vllm/config/vllm.py:1833-1834).
  7. It calls the platform hook current_platform.check_and_update_config(self), which can change any part of the config (vllm/config/vllm.py:2046).
  8. It resolves the KV transfer settings, for example the connector name for KV offloading (vllm/config/vllm.py:2197-2199).

Simplified

The list names only the main steps. __post_init__ also sets CUDA graph sizes, compile ranges, multimodal devices and many checks. Read config/vllm.py: VllmConfig, __post_init__ and compute_hash for the full walk-through.

compute_hash: one key for compiled code#

VllmConfig.compute_hash() collects the compute_hash() of each sub-config and adds the vLLM version. It returns the first 10 hex digits of a hash of this list (vllm/config/vllm.py:474-483, vllm/config/vllm.py:572-575). Its docstring says that the hash covers the configs that change the computation graph (vllm/config/vllm.py:460-468). Each sub-config decides which fields count. For example, SchedulerConfig adds max_num_batched_tokens, because LoRA buffer sizes in the compiled graph and the index width that Inductor selects depend on it (vllm/config/scheduler.py:271-280).

The torch.compile backend uses the hash. When compilation_config.cache_dir is not set (vllm/compilation/backends.py:1086), it hashes four values together: the environment hash, the config hash, the code hash and the compiler hash. The result is the name of the cache folder under VLLM_CACHE_ROOT/torch_compile_cache/ (vllm/compilation/backends.py:1059-1063, vllm/compilation/backends.py:1091-1097). So when you change --max-num-batched-tokens, the next start compiles again into a new folder.

How to read the tables#

  • All config classes lists each class with its file and line, the number of fields, and the first paragraph of the class docstring.
  • What each VllmConfig attribute holds maps each attribute to its class. quant_config holds a QuantizationConfig, which is not a @config class.
  • One table per class lists each annotated line of the class body: name, type and default as source text. The last column quotes the first paragraph of the field docstring as it is. (InitVar) and (ClassVar) mark lines that are not dataclass fields.
  • Defaults are dataclass defaults. They are not always the values that vllm serve uses. EngineArgs and __post_init__ change many of them. The table Flags you tune first gives the real defaults of the tuning fields.
  • Inherited fields are not copied into a subclass table. Only vllm/config/*.py is scanned, so FrontendArgs (in vllm/entrypoints/common/cli_args.py) is not here; its flags are in vllm serve flags.

Check yourself#

  1. 1
    You start vllm serve with --compilation-config '{"cudagraph_mod": "NONE"}' (one letter is missing). What happens?
    easy
    Show answer

    Start-up stops with an argument error. CompilationConfig is a @config class with extra="forbid" (vllm/config/utils.py:71), so pydantic rejects the unknown key, and parse_dataclass turns the ValidationError into an argparse.ArgumentTypeError (vllm/engine/arg_utils.py:369-374).

  2. 2
    Why does SchedulerConfig say max_num_seqs = 128, while vllm serve on an 80 GB H100 uses 1024?
    medium
    Show answer

    The dataclass default is "mainly for convenience when testing" (vllm/config/scheduler.py:62-66). The flag passes None (vllm/engine/arg_utils.py:1743-1749), and EngineArgs sets the value by GPU memory before it builds SchedulerConfig (vllm/engine/arg_utils.py:2970-2983, vllm/engine/arg_utils.py:2631-2635). This assumes that the driver reports at least 70 GiB for the card (vllm/engine/arg_utils.py:2946).

  3. 3
    You restart a server with --max-num-batched-tokens 16384 instead of 8192, and nothing else changes. Can it reuse the torch.compile cache of the first run?
    hard
    Show answer

    No. SchedulerConfig.compute_hash includes max_num_batched_tokens (vllm/config/scheduler.py:280). VllmConfig.compute_hash includes the scheduler hash (vllm/config/vllm.py:500-501). The compile backend puts the config hash into the cache folder name (vllm/compilation/backends.py:1090-1097), so the new run uses a new folder and compiles again.
