Extension points

Referenceabout 17 min read

Code version: vLLM @ 3e44c0d · 2026-10-22

In one sentence

Each row names one place where out-of-tree code changes vLLM, the line that reads it, and the processes where your code must be visible.

This page is the lookup table. The guided version, with diagrams and a start-up timeline, is All the ways to extend vLLM. Read that page first if the three kinds of extension points are new to you. Every row here cites the code at the pinned commit; open the linked page for the explanation.

Words in the tables:

  • Front end: the front end process of vllm serve (API server, AsyncLLM). With more than one API server, each one is a front end.
  • Engine core: the EngineCore process, one per data-parallel rank.
  • Workers: the worker processes. With TP = PP = DP = 1 there is no worker process: the worker runs inside the engine core process (vllm/config/parallel.py:1099-1100). Then "workers" means the engine core process.
  • Registry subprocess: a short-lived process that inspects a model class. It runs only on a cache miss of the model-info cache, and it loads the general plugins first (vllm/model_executor/models/registry.py:1608-1612).

The six entry-point groups#

vLLM finds these with importlib.metadata. Your package publishes an entry point in a plugin group; no other step is necessary. Five group names are constants in one file (vllm/plugins/__init__.py:16-30). The sixth, vllm.logits_processors, is in the sampler code of Model Runner V2 (vllm/v1/worker/gpu/sample/logits_processor/loader.py:34).

One allowlist for five groups

VLLM_PLUGINS matches entry-point names in every group that uses load_plugins_by_group (vllm/plugins/__init__.py:64). If you set it to name only an endpoint plugin, no general plugin, platform plugin or stat logger plugin loads. The general group logs its list only at DEBUG, so the missing plugins are not visible at the default INFO level (vllm/plugins/__init__.py:48-54). The page How vLLM finds and loads plugins has the details.

Pooling models and logits processors

A pooling model skips the entry-point processors in the workers, and raises ValueError only for processors named in the config (vllm/v1/worker/gpu/sample/logits_processor/loader.py:172-180). The front end also skips them for a pooling model without named processors (vllm/v1/engine/input_processor.py:100-101).

Registries that a general plugin fills#

A registry is a module-level table plus a register function. The table lives in one process, so the register call must run in each process that reads the table. A general plugin does this, because every process runs it. Code in your own launch script reaches only that process. A ValueError or AssertionError in a general plugin stops start-up

The loader calls each general plugin function without a try (vllm/plugins/__init__.py:89-90). So a name clash with a built-in KV connector, for example NixlConnector (vllm/distributed/kv_transfer/kv_connector/factory.py:177-181), stops the process. The engine core logs "EngineCore failed to start." (vllm/v1/engine/core.py:1570-1576).

Two corrections to remember

The config hooks apply_config_platform_defaults and check_and_update_config do not run only in the front end. The engine core process calls vllm_config.__post_init__() again (vllm/v1/engine/core.py:1336-1337), so both hooks run there too. Your hooks must give the same result when they run again on a config that they have already changed. And pre_register_and_update runs 5 times in the front end, not once.

How many times a general plugin runs#

A general plugin runs once in each process (the guard at vllm/plugins/__init__.py:82-85). So the count is the number of processes. Add 1 for each registry subprocess, which runs only on a cache miss of the model-info cache.

vllm serve withProcesses that run itRuns
TP = 1 (default)front end, engine core (the worker is inside it)2
TP = 2front end, engine core, 2 workers4
TP = 4front end, engine core, 4 workers6

The process layout comes from the executor choice: mp when the world size across DP is more than 1, else uni (vllm/config/parallel.py:1055, vllm/config/parallel.py:1099-1100). The page Executors and workers: from the engine core to the GPUs explains it.

    vllm.logits_processors ignores it, because its loader calls entry_points() directly (vllm/v1/worker/gpu/sample/logits_processor/loader.py:46). vllm.endpoint_plugins loads nothing when the variable is unset (vllm/plugins/__init__.py:122-131).

  2. 2
    Your platform's check_and_update_config appends "+my_op" to the custom-op list. You serve with TP = 2. How many times does the hook run at start-up, and what can go wrong?
    medium
    Show answer

    At least twice: once in the front end (vllm/config/vllm.py:2046) and once in the engine core, which runs __post_init__ again (vllm/v1/engine/core.py:1336-1337). The engine core gets the config that the front end already changed, so a hook that appends without a check adds the entry a second time. Make the hook give the same result when it runs again.

  3. 3
    A general plugin calls register_quantization_config("fp8") and register_model_loader("auto"). Neither raises. What happens to the built-in entries, and what does the log show at INFO?
    hard
    Show answer

    Both registries overwrite. The quantization registry logs at DEBUG only (vllm/model_executor/layers/quantization/__init__.py:89-95), so INFO shows nothing for it. The model loader registry logs a WARNING (vllm/model_executor/model_loader/__init__.py:101-107) and then an INFO line "Registered model loader" (vllm/model_executor/model_loader/__init__.py:113-117). The general group's own list of plugins is at DEBUG (vllm/plugins/__init__.py:48-54).

  • The Platform interfaceThe Platform class is the contract between vLLM and a hardware vendor. Identity attributes describe the device; config hooks change VllmConfig in the front end and again in each engine core; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation.
