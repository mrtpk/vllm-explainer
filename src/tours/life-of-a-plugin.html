The idea

A hardware vendor ships vLLM support as a {{term plugin-package}}. A typical package publishes two {{term entry-point | entry points}}. One is a {{term platform-detector}} that tells vLLM "this machine has my device". The other is a {{term general-plugin}} that registers extra parts, for example a faster version of a layer or a new model. The concept pages explain each part on its own. This tour follows one package through one real start-up, in the order of the code.

vllm serve with tensor parallelism 2 runs four processes: the {{term front-end}}, the {{term engine-core}} process and one {{term worker}} process per GPU ({{deepinfer learn/parallelism | Parallelism basics}}). Python objects do not travel between processes. So each process finds the plugins again, and each plugin does its work again. Of the state that plugins change, only the {{term vllm-config}} object travels, as a pickled copy. The tour shows which stop runs in which process, and what travels to the next one.

An everyday comparison. Think of a new employee who works in three buildings of one company. In each building, the receptionist looks at the same staff list, gives the employee a badge and shows the desk. The employee unpacks the same toolbox again at each desk. The comparison stops in one place. Only one building writes the work plan (the config), and it sends copies of the plan to the other buildings.

The example package

This tour uses two test packages from the vLLM repository as one imaginary vendor package. We call it the dummy vendor package. vLLM's CI installs the two packages one at a time, never together ({{cite .buildkite/test_areas/plugins.yaml:16-18}}, {{cite .buildkite/test_areas/plugins.yaml:48-51}}). The platform test only checks the detection and the op swap ({{cite tests/plugins_tests/test_platform_plugins.py:13-64}}). So the tour follows the code path, not a recorded run. Where the test platform is not a complete platform, the tour says so and names what a real vendor adds (stops 12 and 13).
  • tests/plugins/vllm_add_dummy_platform: a platform plugin with the class DummyPlatform, and a general plugin that replaces the rotary embedding layer with DummyRotaryEmbedding.
  • tests/plugins/vllm_add_dummy_model: a general plugin that registers four model architectures, among them MyOPTForCausalLM.

We serve the OPT checkpoint of the tests under the plugin's architecture name, with TP = 2. A vLLM test starts this server with tp=2 ({{cite tests/distributed/test_distributed_oot.py:13-14}}), and a second test uses --hf-overrides to rename the architecture ({{cite tests/distributed/test_distributed_oot.py:20-21}}):

pip install -e tests/plugins/vllm_add_dummy_platform     # as in CI, from the repo root
pip install -e tests/plugins/vllm_add_dummy_model
vllm serve facebook/opt-125m -tp 2 --hf-overrides '{"architectures": ["MyOPTForCausalLM"]}'

The command is illustrative. The tests copy facebook/opt-125m and write MyOPTForCausalLM into its config.json ({{cite tests/conftest.py:1542-1556}}); --hf-overrides has the same effect on the architecture name. All counts on this page assume the default spawn start method of vllm serve.

This is the first {{term platform-hook}} of the start-up. The CLI also builds the parsers of vllm launch render and vllm run-batch before it parses the flags. The same constructors also build small layers such as norms and rotary embeddings. Each of them is a CustomOp. Before Python runs __init__, the class method __new__ looks at the {{term op-registry}} of out-of-tree classes:

  1. Line 109 takes the Python class name of the class that the model code builds, for example "RotaryEmbedding".
  2. Lines 117-120: the name is in op_registry_oot, so vLLM makes the object from DummyRotaryEmbedding, and logs "Instantiating custom op" at DEBUG level.
  3. Line 126 returns an object of the replacement class. It is a subclass of the in-tree class, so Python then runs its __init__, which sets addition_config = True.

For our model, the swap does not happen. OPT has learned position embeddings and builds no RotaryEmbedding ({{cite vllm/model_executor/models/opt.py:217}}). Its norm layer is LayerNorm ({{cite vllm/model_executor/models/opt.py:35}}, {{cite vllm/model_executor/models/opt.py:147}}). "LayerNorm" is not in op_registry_oot, so line 118 keeps the in-tree class. A model with standard RoPE, such as Llama, gets its rotary layer from get_rope, which builds RotaryEmbedding for the default rope type ({{cite vllm/model_executor/layers/rotary_embedding/__init__.py:147-155}}). There the swap happens. A test checks it ({{cite tests/plugins_tests/test_platform_plugins.py:51-64}}).

The lookup uses the exact class name. MRotaryEmbedding, which get_rope builds for an mrope_section, has another name, so it is not swapped ({{cite vllm/model_executor/layers/rotary_embedding/__init__.py:113-114}}). (Derived from line 109.)

CustomOp.__init__ calls dispatch_forward once and keeps the result ({{cite vllm/model_executor/custom_op.py:128-134}}):

The worker's copy of the config has custom_ops = ["all"] from stop 7. So the default enabled() returns true for every op ({{cite vllm/model_executor/custom_op.py:290}}, {{cite vllm/model_executor/custom_op.py:307}}). The platform is out-of-tree, so lines 202-203 select forward_oot. For OPT's LayerNorm, that is the default forward_oot, which calls forward_native ({{cite vllm/model_executor/custom_op.py:167-170}}). In a RoPE model, DummyRotaryEmbedding.forward_oot calls the parent's forward_oot (stop 4 excerpt, lines 18-19). RotaryEmbedding does not override that method, so the call ends in the same forward_native.

Without the dummy hook of stop 7, the list would be ["none"]. Then every op without a +name switch would be disabled and would use forward_native (line 192), and the vendor's forward_oot would not run for it. The page {{link concepts/custom-ops}} explains the switches.

  1. Line 702 runs a config hook. It picks a block size that all attention backends of the model accept, when the user did not set one ({{cite vllm/platforms/interface.py:767-774}}, {{link concepts/platform-interface}}).
  2. Line 710 freezes the environment variables. From now on, VLLM_PLUGINS and the other variables are read from a cache in this worker ({{cite vllm/envs.py:2308-2326}}).

The engine core does the same with enable_envs_cache() at the end of its own start-up ({{cite vllm/v1/engine/core.py:241-243}}). The front end then builds the HTTP app. build_app looks for endpoint plugins; our package has none ({{cite vllm/entrypoints/launchers/app.py:51}}). From the first request on, the forward method of each custom op calls the method that stop 15 chose ({{cite vllm/model_executor/custom_op.py:133-134}}).   • The detector runs twice per process: once in the loop and once for the winner ({{cite vllm/platforms/__init__.py:257}}, {{cite vllm/platforms/__init__.py:278}}).
  • The decorator runs once per process. Python caches an imported module, so a second import in register_ops does not run the decorator again. Also, vLLM calls register_ops only once per process ({{cite vllm/plugins/__init__.py:83-85}}). A second register_oot with the same key would fail the assert at {{cite vllm/model_executor/custom_op.py:338}}.
  • The config hooks run in VllmConfig.__post_init__. The front end runs it when it builds the config. Each engine core runs it again on the unpickled config after its handshake ({{cite vllm/v1/engine/core.py:1336-1337}}). A worker gets the config through pickling, which does not call __post_init__. vLLM's replace() helper builds a new VllmConfig and so runs them again ({{cite vllm/config/utils.py:121-129}}). The EAGLE drafter loader in a worker is one such case ({{cite vllm/v1/worker/gpu/spec_decode/eagle/utils.py:90-91}}).
  • The hook pre_register_and_update runs four times with a parser: for serve, launch render, run-batch and setup_server. It runs once more in create_engine_config (stop 5).
  • The world group has no device communicator ({{cite vllm/distributed/parallel_state.py:1510-1514}}). For OPT with TP = 2, only the tensor-parallel group has two ranks. The pipeline, context-parallel and data-parallel groups have one rank. vLLM makes no expert-parallel group for a dense model ({{cite vllm/distributed/parallel_state.py:2313-2314}}). So each worker asks once. (Derived.)
  • The OPT count for get_attn_backend_cls assumes that all layers pass the same arguments, so @cache hits after the first layer ({{cite vllm/v1/attention/selector.py:206}}).
  • Not counted: the model registry subprocess. It does not run for MyOPTForCausalLM (stop 6). For a lazy entry with a cache miss, it adds one process that runs the general plugins once more ({{cite vllm/model_executor/models/registry.py:1612}}). It imports vllm.config at module level ({{cite vllm/model_executor/models/registry.py:26}}), so it also resolves the platform.

With one GPU (TP = 1, and PP and DP keep their default 1), the world size is 1, and the executor is "uni" ({{cite vllm/config/parallel.py:1099-1100}}). The {{term uni-executor}} makes the worker object inside the engine core process:

  1. Stops 1 to 9 do not change.
  2. Stop 10 starts no process. Stops 11 to 16 run in the engine core process.
  3. Stop 11: load_general_plugins() in init_worker returns at once, because EngineCore.__init__ already set the flag in this process ({{cite vllm/plugins/__init__.py:83-84}}). The platform is not detected again: the engine core already has the object. register_triton_kernel_overrides still runs.
  4. Stop 12: the tensor-parallel group has one rank, so the worker does not ask for a device communicator ({{cite vllm/distributed/parallel_state.py:549}}).
  5. Stop 16: the engine core calls update_block_size_for_backend (line 75 above).

So the general plugin functions run twice in total, and the detector runs four times.

What can go wrong

In a plain start-up of vllm serve, check_and_update_config runs in the front end, where VllmConfig is built ({{cite vllm/config/vllm.py:2046}}, {{cite vllm/engine/arg_utils.py:2870}}). It runs again in each engine core, but only after the engine core has started its workers ({{cite vllm/v1/engine/core.py:1336-1337}}). It never runs in a worker. Only changes to vllm_config reach the workers (stop 8). Register classes in a general plugin, not in a config hook.
  • The worker class is missing. A platform that leaves worker_cls as "auto" fails in each worker at stop 12 ({{cite vllm/v1/worker/worker_base.py:293-296}}). The front end and the engine core start normally, so read the worker log: "WorkerProc failed to start." ({{cite vllm/v1/executor/multiproc_executor.py:956-957}}).
  • The platform plugin is skipped with no warning. A VLLM_PLUGINS list without the detector name gives a built-in platform (deep dive). Look for "Platform plugin ... is activated" in the log ({{cite vllm/platforms/__init__.py:279}}).
  • Two platform plugins answer. Start-up stops with "Only one platform plugin can be activated" in the first process ({{cite vllm/platforms/__init__.py:272-276}}).
  • The replacement never builds. register_oot keys on the class name. If the model does not build that exact class, as OPT does not build RotaryEmbedding, nothing happens and nothing is logged (stop 14).
  • The vendor kernels never run. Without "all" or +name in custom_ops, a compiled server disables the ops, and forward_oot does not run (stop 15).
  • A general plugin fails in one process only. The function runs in each process, and vLLM does not catch its errors ({{cite vllm/plugins/__init__.py:89-90}}). The engine core logs "EngineCore failed to start." ({{cite vllm/v1/engine/core.py:1570-1572}}).
  • Eager registration costs imports everywhere. The class form imports the model module in the front end, the engine core and every worker (stops 4, 9 and 11). The registry docstring recommends the string form to avoid starting CUDA too early ({{cite vllm/model_executor/models/registry.py:1167-1173}}).

Why it matters. A vendor plugin touches every process of the server, at different moments. When a plugin "does not work", the question is: in which process, and at which stop? A wrong platform shows up at stop 3, a missing worker class at stop 12, a silent op at stop 14 or 15. The tour {{link tours/build-a-toy-plugin}} uses these stops to check a plugin of your own.

In which processes does dummy_platform_plugin run with -tp 2, and why more than once?

In all four: the front end, the engine core and both workers. Each one is a separate Python process with its own _current_platform = None; the three children are spawned ({{cite vllm/platforms/__init__.py:296}}, {{cite vllm/entrypoints/common/startup.py:147-149}}). The first read of current_platform in each process runs the detection again ({{cite vllm/platforms/__init__.py:317-319}}).

 The engine core never builds the model. Why does it import my_opt.py?

EngineCore.__init__ runs the general plugins ({{cite vllm/v1/engine/core.py:132}}). The plugin registers MyOPTForCausalLM with the class form, so it imports the module inside the function ({{cite tests/plugins/vllm_add_dummy_model/vllm_add_dummy_model/__init__.py:9-12}}). The class form also computes the model info at once ({{cite vllm/model_executor/models/registry.py:1194-1195}}). The string form would avoid this import.

 The dummy platform sets custom_ops = ["all"] in the front end. How does that value reach a worker?

Inside the pickled VllmConfig. The hook changes the config object ({{cite vllm/config/vllm.py:2046}}), and the front end passes that object to the spawned engine core ({{cite vllm/v1/engine/utils.py:256-287}}), which passes it to each worker ({{cite vllm/v1/executor/multiproc_executor.py:731-750}}). The hook itself does not run in the worker. It runs again in the engine core after the handshake ({{cite vllm/v1/engine/core.py:1336-1337}}).

 We serve MyOPTForCausalLM on the dummy platform with custom_ops = ["all"]. Does DummyRotaryEmbedding.forward_oot ever run? Which forward_* method does OPT's LayerNorm use?

No. OPT builds no RotaryEmbedding, and CustomOp.__new__ swaps only the exact class name in op_registry_oot ({{cite vllm/model_executor/custom_op.py:109-120}}). LayerNorm keeps its in-tree class. It is enabled by "all", and the platform is out-of-tree, so it uses forward_oot ({{cite vllm/model_executor/custom_op.py:202-203}}). The default forward_oot calls forward_native ({{cite vllm/model_executor/custom_op.py:167-170}}).

 With TP = 1 (one GPU), how many times does register_ops run, and how many times does the dummy detector run? Ignore the model registry subprocess.

register_ops runs twice: in the front end and in the engine core. The uni executor calls init_worker inside the engine core process ({{cite vllm/v1/executor/uniproc_executor.py:68}}), and the flag is already set there ({{cite vllm/plugins/__init__.py:83-84}}). The detector runs four times: twice in each of the two processes, once in the loop and once for the winner ({{cite vllm/platforms/__init__.py:257}}, {{cite vllm/platforms/__init__.py:278}}).
