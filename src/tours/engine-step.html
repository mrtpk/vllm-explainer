The idea

Tour 1 ({{link tours/life-of-a-chat-request}}) follows one request through the whole server. This tour stays in one place, the engine core process, and looks at one {{term engine-step}} in detail. A real server has many requests in each step, so we take two that need different work:

  • Request B is a chat answer in progress. It decodes: it needs 1 new token per step.
  • Request A has a long prompt of 20,000 tokens. The prompt does not fit into one step, so the scheduler runs it in chunks ({{deepinfer learn/batching | chunked prefill}}).

With {{term async-scheduling}}, one call of step_with_batch_queue does two things. It plans and starts step k, and then it finishes step k-1, which is already on the GPU. So the token that this call sends belongs to the step before. The page {{link concepts/async-scheduling}} explains why.

An everyday comparison. Think of a bakery with one oven. The baker puts the next tray into the queue of the oven before the current tray is done. Then the baker takes out the finished tray and packs it. One tray holds rolls (one each, the decodes) and a big part of a cake (the prefill chunk). The comparison stops in one place. The cake leaves the oven unfinished and goes back in the next round. Only a finished cake is packed. A prefill chunk gives no token.

The example

vllm serve meta-llama/Llama-3.1-8B-Instruct     # one H100 80 GiB GPU, default settings
  • One GPU, TP = 1, DP = 1: the {{term uni-executor}} runs the worker in the engine core process ({{cite vllm/config/parallel.py:1099-1100}}).
  • {{term token-budget | Token budget}}: max_num_batched_tokens = 8192 and max_num_seqs = 1024, because the GPU has 70 GiB or more and is not an A100 ({{cite vllm/engine/arg_utils.py:2960-2993}}). An A100 would get 2048 and 256.
  • Async scheduling is on, and the {{term batch-queue}} has 2 slots ({{cite vllm/config/vllm.py:1664-1698}}, {{cite vllm/config/vllm.py:586-597}}).
  • Step k-1 is already on the GPU. In it, B decoded its 41st output token, and A ran its first chunk: prompt positions 0 to 8190.

The model, the prompt lengths and the positions are illustrative. The scheduler and model runner rules are from the code. We assume a block size of 16 tokens, no prefix cache hit for A, no structured output, no speculative decoding, and no LoRA.

We are in the main thread of the engine core process, in EngineCoreProc._process_engine_step. The input queue is empty, and the scheduler has two running requests, so the {{term busy-loop}} does not block ({{cite vllm/v1/engine/core.py:1596-1602}}). It calls the step function:

step_fn is step_with_batch_queue, because the batch queue exists ({{cite vllm/v1/engine/core.py:227-229}}). Right now the queue holds one entry: step k-1.

What the data looks like now:

batch_queue = deque([(future_sample[k-1], scheduler_output[k-1], future_exec[k-1])], maxlen=2)
scheduler.running = [B, A]       # B first: it was running before A arrived

We are in vllm/v1/core/sched/scheduler.py. The scheduler has no prefill phase and no decode phase. It gives every running request the tokens it still needs, until the budget is used (see {{link concepts/scheduler}}). The running pass computes the need of each request:

  1. B. B knows 540 tokens (500 prompt + 40 output). Token 41 is in flight, so B has 1 {{term output-placeholder}}, and num_computed_tokens = 540. So 540 + 1 - 540 = 1. The budget drops from 8192 to 8191.
  2. A. A has 20,000 prompt tokens, no placeholder, and 8191 computed tokens. Its need is 20000 - 8191 = 11809, but line 766 caps it at the budget: 8191. The budget is now 0.

The order matters: the running pass goes through self.running from the front ({{cite vllm/v1/core/sched/scheduler.py:713-716}}). B was first, so the decode gets its token before the prefill takes the rest. long_prefill_token_threshold could cap A further, but its default is 0, which means no cap ({{cite vllm/config/scheduler.py:79-84}}). The waiting pass has no budget left, so no new request starts in this step.

Then allocate_slots reserves KV cache slots for the new tokens ({{cite vllm/v1/core/sched/scheduler.py:831-838}}). With blocks of 16 tokens, A needs ceil(16382 / 16) = 1024 blocks; it had 512, so it gets 512 new blocks. B needs ceil(541 / 16) = 34 blocks, the same as before. (Derived.) The KV cache and its blocks are explained in {{deepinfer learn/kv-cache | The KV cache}}.

Both requests ran before, so they travel as CachedRequestData, which carries only the changes ({{cite vllm/v1/core/sched/output.py:137-152}}). The scheduler builds it before it advances the counters ({{cite vllm/v1/core/sched/scheduler.py:1527-1534}}), then builds the {{term scheduler-output}} ({{cite vllm/v1/core/sched/scheduler.py:1588-1609}}), and only then calls _update_after_schedule ({{cite vllm/v1/core/sched/scheduler.py:1641-1643}}). That method advances num_computed_tokens and decides whether each request is still in a prefill chunk:

For A: 8191 + 8191 = 16382 < 20000, so A is still a prefill chunk. For B: 541 < 540 + 1 is false, so B is not. AsyncScheduler then adds placeholders only for B:

Back in step_with_batch_queue, the engine core passes the plan to the {{term executor}}:

model_executed is true, because 8192 tokens are scheduled. The uni executor runs the worker method at once, in this thread:

The call goes through WorkerWrapperBase.execute_model ({{cite vllm/v1/worker/worker_base.py:378-383}}) to Worker.execute_model, which calls the {{term model-runner}}:

With one GPU there is no message queue. With TP = 2, this stop would put the call into a shared-memory queue for two worker processes instead ({{link concepts/executors-and-workers}}).

We are in vllm/v1/worker/gpu/model_runner.py. Model Runner V2 keeps its own copy of each request's state. First it applies the changes from the plan:

update_requests stores the computed-token counts and appends A's 512 new block ids to its block table ({{cite vllm/v1/worker/gpu/model_runner.py:1257-1269}}). Then the runner sorts the batch: decodes first, then prefills ({{cite vllm/v1/worker/gpu/model_runner.py:1312-1314}}, {{cite vllm/v1/worker/gpu/model_runner.py:2471-2483}}). B has 1 token, which equals the decode query length, so B is row 0 and A is row 1.

Next it picks a {{term cuda-graph}} mode for the batch shape ({{cite vllm/v1/worker/gpu/model_runner.py:1806-1821}}). Our batch has 8192 tokens and contains a prefill. On an H100 the largest captured size is 512 tokens: min(max_num_seqs × 1 × 2, 512) with max_num_seqs = 1024 ({{cite vllm/config/vllm.py:2439-2449}}). No captured graph matches 8192 tokens, so dispatch returns mode NONE: eager ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:535-553}}). With DP = 1, no padding across ranks changes this result ({{cite vllm/v1/worker/gpu/dp_utils.py:270-279}}).

When A has finished its prefill, a step with B and A both decoding has 2 tokens. That batch is a uniform decode batch below 512 tokens, so it can replay a FULL CUDA graph. The page {{link concepts/compile-and-cuda-graphs}} explains the modes.

The runner packs both requests into one flat batch of 8192 tokens, as in {{deepinfer concepts/input-metadata | Input metadata}}. query_start_loc marks where each request starts:

A is in a prefill, so its prompt tokens are copied on the GPU from the request state ({{cite vllm/v1/worker/gpu/model_runner.py:1469-1479}}). B's input token is token 41, which the CPU does not know yet. It comes from last_sampled_tokens on the GPU, which step k-1 will write before step k runs on the same stream:

Without speculative decoding, each request gets one logits row ({{cite vllm/v1/worker/gpu/model_runner.py:1401-1408}}): the last token of its query. Then prepare_attn builds the block tables and the slot of each new token, and the model state builds the attention metadata ({{cite vllm/v1/worker/gpu/model_runner.py:1838}}, {{cite vllm/v1/worker/gpu/model_runner.py:1940-1951}}).

The block indexes are positions in each request's own block table. The table maps them to physical block ids in the {{term block-pool}}, and the slot of a token is block_id × 16 + offset ({{cite vllm/v1/worker/gpu/block_table.py:409}}).

The Python code returns as soon as all kernels are queued; the GPU runs them later, after step k-1. The runner keeps the hidden states for the sampler and returns None:

Back in the uni executor, the future is already done with the value None ({{cite vllm/v1/executor/uniproc_executor.py:112-113}}). The tour {{link tours/forward-pass}} goes inside the model call.

"Queued" ignores small CPU work that PyTorch does per kernel. The point is that this stop does not wait for the GPU: Model Runner V2 has no GPU-to-CPU synchronization in execute_model ({{cite docs/design/model_runner_v2.md:47}}).

Before the update, the engine core applies any aborts that arrived during the step ({{cite vllm/v1/engine/core.py:780-785}}). Then the scheduler walks over the requests of step k-1:

  1. B. It has a new token, so _update_request_with_output appends t41 and runs check_stop ({{cite vllm/v1/core/sched/scheduler.py:2598-2603}}). t41 is not EOS, so B keeps running. AsyncScheduler removes one placeholder: 2 becomes 1 ({{cite vllm/v1/core/sched/async_scheduler.py:71-73}}). It caches full blocks up to 541 - 1 = 540 tokens for the prefix cache (lines 76-79 there).
  2. A. No new tokens, no pooler output, no stop: the scheduler makes no output for A ({{cite vllm/v1/core/sched/scheduler.py:2293-2295}}).

The outputs are grouped by front end ({{cite vllm/v1/core/sched/scheduler.py:2486-2491}}). With stats on, the scheduler stats go into the same object ({{cite vllm/v1/core/sched/scheduler.py:2507-2521}}).

From here, Tour 1 continues: the front end detokenizes t41 and writes one SSE chunk ({{link tours/life-of-a-chat-request#stop-15 | Tour 1, stop 15}}). The busy loop goes back to stop 1. The next call schedules step k+1: B again 1 token, and A its last chunk of 20000 - 16382 = 3618 tokens. That chunk ends the prompt, so A samples its first token there.

In S k+1, A's need is 20000 + 0 - 16382 = 3618, so the budget is not full: 8192 − 1 − 3618 = 4573 tokens remain for waiting requests. In S k+2, A decodes for the first time, with its first token still in flight.
  • Stops 2-3 run in Python in the scheduler. Their cost grows with the number of running requests, not with the number of tokens. The comment in update_from_output warns that its loop "can be a performance bottleneck" with 1K or more requests ({{cite vllm/v1/core/sched/scheduler.py:2163-2165}}).
  • Stops 5-7 and 9 run on the CPU but only queue GPU work. Their cost is the Python code of the model runner and the kernel launches. A CUDA graph replaces many launches with one; our eager step does not have this help.
  • Stop 10 is the only wait for the GPU. When the GPU step takes longer than all the CPU work of a call, the main thread waits here, and the GPU never waits. That is the goal of async scheduling.
  • Stop 12 encoding and sending run in the output thread, in parallel with the next call.

Stops 1-3, 8 and 10-12 do not change. In stops 4 and 9, the {{term multiproc-executor}} writes the call once into the shared-memory queue. Both worker processes run stops 5-7 and 9 on their own GPU, and they meet in NCCL all-reduces. Only worker 0 replies ({{cite vllm/v1/executor/multiproc_executor.py:549-563}}). The wait of stop 10 then happens in worker 0's WorkerAsyncOutputCopy thread, which calls get_output(), and the engine core waits for the reply message ({{cite vllm/v1/executor/multiproc_executor.py:1000-1002}}, {{cite vllm/v1/executor/multiproc_executor.py:1019-1039}}). See {{link concepts/executors-and-workers}} and {{link tours/multi-gpu-step}}.

What can go wrong

  • A long prompt slows every stream. In our step, B shares a step of 8192 tokens with A's chunk. B's next token comes only when that large step ends. long_prefill_token_threshold limits one prompt's share of a step ({{cite vllm/v1/core/sched/scheduler.py:764-765}}).
  • No KV blocks for the chunk. If allocate_slots fails, the scheduler preempts a running request to free blocks. With the default first-come-first-served policy, the victim is the last request in self.running ({{cite vllm/v1/core/sched/scheduler.py:850-858}}, {{cite vllm/v1/core/sched/scheduler.py:889-900}}). In our batch this is A itself: A loses its KV cache and must compute it again later, and B keeps running.
  • An exception in the model. log_error_detail dumps the SchedulerOutput of the failed step, and the engine core dies with ENGINE_CORE_DEAD ({{cite vllm/v1/engine/core.py:561-575}}, {{link concepts/engine-core-loop}}).
  • A request aborted during the step. Its row still runs on the GPU. _process_aborts_queue finishes it before the update, and the update skips it ({{cite vllm/v1/engine/core.py:780-782}}, {{cite vllm/v1/core/sched/scheduler.py:2184-2192}}).

Why it matters. Every performance number of vLLM comes from this loop. The size of each step comes from stop 2, the CPU cost from stops 2-9, and the GPU cost from stop 7. When you tune max_num_batched_tokens or read a profile, you can now map each part to a stop.

In this tour, which step's token does the call send to the front end?

The token of step k-1 (B's token 41). The call schedules and starts step k first, then pops step k-1 from the batch queue and updates the scheduler with it ({{cite vllm/v1/engine/core.py:753-785}}).

 Why does A get 8191 tokens and not 11809?

The running pass caps each request at the remaining token budget ({{cite vllm/v1/core/sched/scheduler.py:766-768}}). B came first and took 1 token of the 8192, so 8191 remained. long_prefill_token_threshold is 0 by default, so it does not cap A further ({{cite vllm/config/scheduler.py:79-84}}).

 Where does B's input token for step k come from, given that the CPU has not received it yet?

From req_states.last_sampled_tokens on the GPU. combine_sampled_and_draft_tokens copies it into input_ids in prepare_inputs ({{cite vllm/v1/worker/gpu/model_runner.py:1493-1500}}). Step k-1 writes it in postprocess_sampled, earlier on the same CUDA stream ({{cite vllm/v1/worker/gpu/model_runner.py:1715-1726}}).

 A has a logits row in step k. Why does it have no token in the ModelRunnerOutput, and why does the scheduler send nothing for A?

Without spec decoding, every request gets one logits row ({{cite vllm/v1/worker/gpu/model_runner.py:1401-1408}}). The sampler sets num_sampled = 0 for a chunked-prefill request ({{cite vllm/v1/worker/gpu/sample/sampler.py:190-199}}), and get_output() trims the row to an empty list ({{cite vllm/v1/worker/gpu/async_utils.py:182-183}}). With no new tokens, no pooler output and no stop, the scheduler makes no EngineCoreOutput ({{cite vllm/v1/core/sched/scheduler.py:2293-2295}}).

 Which CUDA graph mode does step k use, and what would a step with only B and A decoding use?

Step k has 8192 tokens and a prefill. The largest captured size on this GPU is 512 ({{cite vllm/config/vllm.py:2439-2449}}), so no captured graph matches, and dispatch returns NONE (eager) ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:535-553}}). A step with two 1-token decodes is a uniform decode batch of 2 tokens. So it can replay a FULL graph under the default mode FULL_AND_PIECEWISE ({{cite vllm/config/vllm.py:310}}).
