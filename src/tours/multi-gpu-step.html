Each lands on its own engine core, whose two workers run one step together.

The idea

The tour {{link tours/engine-step}} stays inside one engine core with one GPU. This tour adds the two other dimensions of a real deployment. They are several GPUs per engine core (tensor parallelism) and several engine cores per server (data parallelism). It shows which process does what, which channel each message takes, and where the GPUs talk to each other. The model internals are in {{link tours/forward-pass}}; here we only mark where the collectives run.

Two requests, A and B, arrive at the same time. Request A reaches API server 0 and request B reaches API server 1. Each server picks an engine core. Each engine core plans a step, writes it once into shared memory, and its two workers run the step on two GPUs. At the end, only one worker per engine answers, and the outputs flow back to the API server that sent each request.

An everyday comparison. Think of two kitchens in one restaurant, each with two cooks who prepare every dish together, half each. Two hosts at the door send guests to the kitchens. A board in the hall shows how busy each kitchen is. The comparison stops here. The two cooks of a kitchen must finish each half of each layer at the same moment (the all-reduce). The two kitchens never talk for a dense model.

The example

vllm serve meta-llama/Llama-3.1-8B-Instruct -tp 2 -dp 2      # one node, 4 GPUs, dense model
  • A dense model, so each DP rank is an independent engine core ({{link concepts/data-parallel-serving}}).
  • Default flags: internal load balancing, two API servers, async scheduling with the batch queue, Model Runner V2.
  • Both engines are idle when A and B arrive. A has a 300-token prompt, B a 200-token prompt; both are new.

The prompt lengths are illustrative. The API servers share one listen socket, so the operating system decides which one receives a connection. We assume A reaches API server 0 and B reaches API server 1.

We start after start-up; the tour {{link tours/serve-startup}} covers it. Two things decide the process layout. First, --api-server-count defaults to the DP size in internal mode, so there are two API servers and the CLI process stays as their supervisor ({{cite vllm/entrypoints/cli/serve.py:124-125}}, {{cite vllm/entrypoints/cli/serve.py:151-152}}). Second, each engine core of a dense model becomes an independent EngineCoreProc with DP size 1:

Engine 0 gets GPUs 0 and 1, engine 1 gets GPUs 2 and 3 ("[2, 3] for local_dp_rank=1", {{cite vllm/v1/engine/utils.py:441-445}}). Each engine core starts a MultiprocExecutor with two worker processes. The DP size is 1 inside each engine. So each pair of workers builds its own world of two ranks. It has TP group [0, 1], and PP and DP groups of one rank ({{link concepts/distributed-groups}}). The workers rename themselves Worker_TP0 and Worker_TP1; the name has a DP part only when the worker's DP group is larger than 1 ({{cite vllm/v1/executor/multiproc_executor.py:1101-1109}}).

So there are 10 processes: CLI supervisor, 2 API servers, 1 DP coordinator, 2 engine cores and 4 workers (derived; {{link concepts/architecture-overview}} gives the rules).

We are in API server 0, in AsyncLLM.add_request, which calls the engine core client. With DP > 1 and internal load balancing, that is a DPLBAsyncMPClient. Before it sends, it stamps the request with the current wave and its own client_index:

The engine choice is the score of {{link concepts/data-parallel-serving}}: max(client_count × in-flight, waiting + running) plus a penalty for waiting requests on a full KV cache ({{cite vllm/v1/engine/core_client.py:1777-1786}}). Both engines are idle, so every score is 0. Ties go to the first engine of the scan, because only a strictly smaller score replaces the minimum (line 1787). The scan starts at a different engine per API server:

  • API server 0: (2 × 0) // 2 = 0, so request A goes to engine 0.
  • API server 1: (2 × 1) // 2 = 1, so request B goes to engine 1.

Each server then adds client_count = 2 to the chosen engine's waiting count, adds 1 to its own in-flight count, and rotates its start index ({{cite vllm/v1/engine/core_client.py:1792-1803}}). (Derived from the cited lines.)

The engine identity is the DP rank as two little-endian bytes ({{cite vllm/v1/engine/core_client.py:748-751}}), so A's frames start with b"\x00\x00" and B's with b"\x01\x00". The ROUTER socket routes on that frame:

Each engine core connects one DEALER socket per API server. Its input thread receives the frames, decodes the EngineCoreRequest, builds the Request, and queues it for the busy loop ({{cite vllm/v1/engine/core.py:1977-1993}}). The request keeps its client_index, so the outputs can find their way back in stop 11. The page {{link learn/processes-and-ipc}} explains the frames.

Engine core 0 now has request A, engine core 1 has request B. Each runs the normal busy loop of {{link concepts/engine-core-loop}}: step_with_batch_queue schedules the 300 (or 200) prompt tokens, as in {{link tours/engine-step}}. Nothing ties the two engines together:

  • They are plain EngineCoreProc objects, not DPEngineCoreProc, so there are no waves, no dummy batches and no DP all-reduce (stop 1).
  • When an engine has no work, it blocks on its input queue: has_work() is false when nothing is running, waiting or in the batch queue ({{cite vllm/v1/engine/core.py:1596-1602}}).
  • Their steps are not aligned in time. Engine 1 may run three steps while engine 0 runs two.

The engine core calls execute_model on its {{term multiproc-executor}}. That is one {{term collective-rpc}} with a reply only from the output rank:

Line 428 is the only write. The {{term message-queue}} pickles ("execute_model", (scheduler_output,), {}, 0) once into a 16 MiB chunk of a ring in /dev/shm. Both workers read the same bytes ({{link code/distributed-device-communicators-shm-broadcast}}). Lines 431-432 already decide that the executor will read only the reply queue of rank 0. The step deadline is VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS, 300 s by default ({{cite vllm/envs.py:1861-1863}}).

We are now in one of the worker processes, in its main thread. It was blocked in the queue and wakes up with the message:

getattr(self.worker, "execute_model") leads to Worker.execute_model. With PP = 1 this worker is both the first and the last stage, so it receives no intermediate tensors and calls the model runner directly ({{cite vllm/v1/worker/gpu_worker.py:1336-1353}}). From here, both workers run the same Python code on the same batch, each with half of every weight matrix ({{link concepts/tp-layers}}). Model Runner V2 also checks for DP padding, but with a DP size of 1 there is nothing to agree on ({{cite vllm/v1/worker/gpu/dp_utils.py:278-279}}).

Each rank holds half of the vocabulary rows of the embedding table. A rank looks up only the token ids in its half and writes zeros for the others; then the two partial results are summed:

For A's 300 tokens, the tensor is [300, 4096] BF16, 2.34 MiB, and it is summed over the TP group [GPU 0, GPU 1]. Engine 1 does the same for B on GPUs 2 and 3, at its own time. The tour {{link tours/forward-pass}} gives the shapes of every layer (its deep dive "What changes with TP = 2").

Inside each of the 32 decoder layers, o_proj and down_proj are row-parallel. Each rank computes a partial sum, and the layer adds them:

tensor_model_parallel_all_reduce goes to the TP group ({{cite vllm/distributed/communication_op.py:12-14}}). On CUDA, the group calls the registered op with only its name, so the compiled graph keeps one opaque node:

The op ends in CudaCommunicator.all_reduce, which tries FlashInfer, the custom all-reduce, symmetric memory and pynccl in a fixed order ({{cite vllm/distributed/device_communicators/cuda_communicator.py:362-446}}). Which one takes our 2.34 MiB tensor depends on the GPU (derived from the size rules on {{link concepts/distributed-groups}}):

  • Compute capability 8.x (for example A100), TP = 2 on one node with P2P access: FlashInfer all-reduce has no size entry and stays off. The custom all-reduce takes the tensor, because 2.34 MiB is below its 8 MiB limit.
  • Compute capability 9.0 or 10.x with FlashInfer installed: at O2 the compile pass fuse_allreduce_rms can fuse an all-reduce with the RMSNorm after it. A fused all-reduce does not reach this method ({{cite vllm/config/vllm.py:178-202}}, {{link tours/forward-pass}}). An all-reduce that is not fused goes to FlashInfer first; its limit at TP = 2 is 64 MiB ({{cite vllm/compilation/passes/fusion/allreduce_rms_fusion.py:104-115}}).

Either way, the step has 1 + 2 × 32 = 65 all-reduces in total, all on the TP group. The DP and PP groups have one rank and run nothing.

The engine core next calls sample_tokens, the second broadcast of the step (same path as stop 5). Each rank computes logits for its half of the vocabulary; the LM head then gathers them:

Every built-in platform uses the all-gather, so both ranks hold the full [num_rows, 128256] logits ({{cite vllm/platforms/interface.py:1275-1278}}). Both ranks run the sampler. They draw the same tokens. After warm-up, every worker resets its random seed to a value that depends only on the model seed and the DP index ({{cite vllm/v1/worker/gpu_worker.py:1083-1087}}, {{cite vllm/utils/torch_utils.py:533-544}}). A different DP index gives a different seed, so engines 0 and 1 do not sample unseeded requests alike (the comment at line 536). Each worker then draws the per-request seed of an unseeded request from this same NumPy state, in the same order ({{cite vllm/v1/worker/gpu/sample/states.py:54-58}}). By default, the code has no other synchronization of the sampled tokens between TP ranks (derived). The opt-in --enable-batch-sharded-sampling changes this: each rank samples a slice of the batch, and the ranks all-gather the results ({{cite vllm/config/parallel.py:192-198}}).

The output rank is world_size − TP × PCP, the first TP rank of the last PP stage ({{cite vllm/v1/executor/multiproc_executor.py:549-563}}); here that is 2 − 2 = 0. In each worker, the reply is conditional:

Worker TP0 hands its AsyncOutput to its WorkerAsyncOutputCopy thread. That thread waits for the copy to the CPU and writes (SUCCESS, ModelRunnerOutput) into its own MessageQueue(1, 1) ({{cite vllm/v1/executor/multiproc_executor.py:1014-1039}}, {{cite vllm/v1/executor/multiproc_executor.py:1000-1012}}). Worker TP1 writes nothing; it goes back to its dequeue. The engine core reads the reply when it pops the step from its batch queue, exactly as in {{link tours/engine-step#stop-10 | stop 10 of the engine-step tour}}.

After update_from_output, the engine core groups its outputs by client_index, and its output thread sends each group on the PUSH socket of that API server:

Request A was sent by API server 0, so A's first token goes to API server 0's PULL socket; B's goes to API server 1. Each API server detokenizes only its own requests, and its DPLBAsyncMPClient lowers its in-flight count when a request finishes ({{cite vllm/v1/engine/core_client.py:1810-1817}}).

Each engine core compares its waiting and running counts with the last ones it sent. When they changed (here: one new running request), it sends them, with its KV cache usage, to client index −1, the coordinator:

Separately, the scheduler stats of each step go to only one front end, inside the normal outputs ({{cite vllm/v1/core/sched/scheduler.py:2516-2521}}). Prometheus labels them with engine="0" or engine="1" ({{cite vllm/v1/metrics/loggers.py:499-504}}).

The coordinator stores the counts per engine and publishes all of them, at most every 100 ms while they change:

Each API server's stats task replaces its lb_engines with the new counts ({{cite vllm/v1/engine/core_client.py:1578-1590}}). Real numbers now replace the local guesses of stop 2 (+2 waiting on the chosen engine). Engine 0 has 1 running request, and engine 1 has 1. The next request on either API server sees both, plus its own in-flight counts. Meanwhile, each engine core is already in its next step.

Deep dive

vllm serve <an MoE model> -tp 2 -dp 2 --enable-expert-parallel      # one node, 4 GPUs
  1. Stop 1. Each engine core is a DPEngineCoreProc ({{cite vllm/v1/engine/core.py:1534-1537}}). The four workers form one world with global rank = 2 × dp + tp. TP groups: [0, 1], [2, 3]. DP groups: [0, 2], [1, 3]. EP group: [0, 1, 2, 3] ({{link concepts/distributed-groups}}). The names become Worker_DP0_TP0 … Worker_DP1_TP1, plus _EP<rank> with EP ({{cite vllm/v1/executor/multiproc_executor.py:1101-1115}}).
  2. Stop 4. A arrives at engine 0 while both are idle. Engine 0 starts a wave and tells the coordinator, which sends START_DP_WAVE to engine 1 ({{cite vllm/v1/engine/core.py:2360-2373}}). From now on both step together. If B had not arrived, engine 1 would run a dummy batch each step ({{cite vllm/v1/engine/core.py:2486-2495}}).
  3. Stop 6. Before its forward, each worker joins a CPU all-reduce over its worker DP group. The ranks agree on a padded token count and a CUDA graph mode, so A's 300 tokens and B's 200 get one shared shape ({{cite vllm/v1/worker/gpu/dp_utils.py:65-74}}).
  4. Stop 8. The attention part is unchanged: two engines, TP = 2 each. In the MoE layers, the EP size is DP × TP = 4 ({{cite vllm/model_executor/layers/fused_moe/config.py:1105-1114}}, {{cite vllm/model_executor/layers/fused_moe/config.py:1227-1231}}). With TP > 1, DP > 1 and EP, the MoE input is sequence parallel ({{cite vllm/config/parallel.py:767-785}}). This applies only to a model that passes the setting to its MoE layer, for example Qwen3-MoE ({{cite vllm/model_executor/models/qwen3_moe.py:152}}). Then the default allgather_reducescatter dispatch and combine run on the EP group; otherwise they run on the DP group ({{cite vllm/distributed/device_communicators/all2all.py:76-86}}). So every MoE layer now adds collectives over all four GPUs, across both engines.
  5. After the step. At the first step of the wave and every 16th step, the engine cores agree on "any unfinished requests?" over their own gloo group ({{cite vllm/v1/engine/core.py:2542-2559}}). When both requests finish, the wave ends and both engines pause.

The page {{link concepts/expert-parallel-moe}} explains the MoE layer and the all2all backends.

 
vllm serve meta-llama/Llama-3.1-8B-Instruct -tp 2 -pp 2      # one engine core, 4 GPUs
  1. Groups. One engine, world size 4. TP groups [0, 1] and [2, 3]; PP groups [0, 2] and [1, 3]. Stage 0 holds layers 0-15 and the embedding; stage 1 holds layers 16-31, the final norm and the LM head ({{link learn/tp-pp-in-practice}}). Workers are named Worker_PP0_TP0 etc. ({{cite vllm/v1/executor/multiproc_executor.py:1104-1109}}).
  2. Batch queue. With async scheduling and Model Runner V2, max_concurrent_batches is pp_size + 1 = 3, so up to three steps are in flight ({{cite vllm/config/vllm.py:586-597}}).
  3. Stop 5. All four workers read every broadcast. The output rank is 4 − 2 = 2, the first TP rank of the last stage ({{cite vllm/v1/executor/multiproc_executor.py:549-563}}).
  4. Stop 6, stage 0. Ranks 0 and 1 run layers 0-15. They send {{term intermediate-tensors}} (hidden_states and residual, [T, 4096] each) to the next stage with isend_tensor_dict, without waiting. With all_gather_group = the TP group, each TP rank sends only half of each tensor ({{cite vllm/v1/worker/gpu_worker.py:1372-1378}}, {{cite vllm/distributed/parallel_state.py:1219-1222}}).
  5. Stop 6, stage 1. Ranks 2 and 3 post irecv_tensor_dict; each receives its half and all-gathers the full tensor in its TP group ({{cite vllm/v1/worker/gpu_worker.py:1336-1347}}). They run layers 16-31.
  6. Stop 9. Only the last stage samples. It broadcasts the sampled tokens to the earlier stage on a separate NCCL group, on a side stream; stage 0 consumes them pp_size steps later ({{cite vllm/v1/worker/gpu/pp_utils.py:56-62}}, {{cite vllm/v1/worker/gpu/model_runner.py:2133-2153}}, {{cite vllm/v1/worker/gpu/model_runner.py:2167-2174}}).
  7. Collectives per step (derived). Stage 0 runs 1 + 2 × 16 = 33 TP all-reduces. Stage 1 runs two TP all-gathers to rebuild the received tensors, 2 × 16 = 32 TP all-reduces and one logits all-gather. Between the stages there is one send/receive of two tensors. Then come two small broadcasts (the sampled tokens and their counts); they are skipped when no request needs them ({{cite vllm/v1/worker/gpu/pp_utils.py:254-278}}).

The slowest TP rank sets the pace of its engine, because every all-reduce waits for both ranks. The two engines of a dense model never wait for each other.

What can go wrong

  • A worker dies. The executor's monitor thread sees the process exit and fails the engine core; the API servers then report the engine as dead ({{cite vllm/v1/executor/multiproc_executor.py:314-326}}, {{link concepts/engine-core-loop}}).
  • A collective hangs. Assume one TP rank stops, for example after an exception that only rank 1 sees. Rank 0 waits in the all-reduce, and the engine core waits for rank 0's reply. After VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS (300 s) the call ends with TimeoutError ({{cite vllm/v1/executor/multiproc_executor.py:437-443}}). A failure on rank 1 is only logged, because rank 1 does not reply ({{cite vllm/v1/executor/multiproc_executor.py:1072-1080}}).
  • Small /dev/shm. Each engine core's queues need several hundred MiB of shared memory; too little raises at start-up ({{link code/distributed-device-communicators-shm-broadcast}}).
  • Unbalanced engines. The score uses counts that can be 100 ms old; a burst of long prompts can still pile up on one engine. Watch vllm:num_requests_waiting per engine label.

Why it matters. Multi-GPU serving multiplies the processes and the channels. If you know which process waits for which message, you can map a hang, a timeout or a load problem to one stop.

How many processes does vllm serve -tp 2 -dp 2 start for a dense model, and what are they?

Ten: the CLI supervisor, two API servers, the DP coordinator, two engine cores and four workers (stop 1; {{cite vllm/entrypoints/cli/serve.py:124-125}}, {{cite vllm/v1/engine/core.py:1534-1543}}).

 Which worker answers execute_model in each engine core, and why only one?

TP rank 0: the output rank is world_size − TP × PCP = 0 ({{cite vllm/v1/executor/multiproc_executor.py:549-563}}). Both ranks compute the same output, so one reply is enough; the executor reads only that reply queue ({{cite vllm/v1/executor/multiproc_executor.py:430-432}}).

 Both engines are idle. A request arrives at API server 1 of 2. Which engine gets it, and why?

Engine 1. All scores are 0, and the scan of API server 1 starts at (2 × 1) // 2 = 1. Only a strictly smaller score replaces the first one ({{cite vllm/v1/engine/core_client.py:1739-1741}}, {{cite vllm/v1/engine/core_client.py:1787-1789}}).

 How many collectives run on GPU 0 in one step of this tour, and on which group? How does that change with an MoE model and --enable-expert-parallel?

Dense: 65 all-reduces and 1 all-gather, all on the TP group [0, 1] (stops 7-9). MoE with EP: the attention part keeps its TP all-reduces. Every MoE layer adds dispatch and combine collectives. They run on the EP group of all four ranks when the model uses sequence-parallel MoE, else on the DP group. Every step adds a CPU all-reduce on the worker DP group for padding ({{cite vllm/v1/worker/gpu/dp_utils.py:65-74}}, {{cite vllm/distributed/device_communicators/all2all.py:76-86}}).
