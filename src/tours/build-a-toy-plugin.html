The idea

The tour {{link tours/life-of-a-plugin}} follows an existing package through the start-up. This tour goes the other way: you write the package. It has four parts, and each part uses one {{term extension-point}}:

  1. a model: a new architecture name in the {{term model-registry}};
  2. a layer replacement: your own subclass of RMSNorm, a {{term custom-op}};
  3. a stat logger that receives the statistics of the server;
  4. an endpoint: one new HTTP route.

The first two parts come from one {{term general-plugin}}, so they reach every process. The last two parts act only in the {{term front-end}}. Every vLLM call in the toy is one that a test plugin of the vLLM repository also makes. So each stop shows the real test plugin next to the toy.

An everyday comparison. Think of a kit that adds parts to a car. One part goes into the engine bay, one replaces a standard part, one is a gauge on the dashboard and one is a new button. The kit has one label per part, so the factory knows where each part goes. The comparison stops in one place. A vLLM server is like several copies of the car, one per process. The engine-bay parts go into every copy, and the dashboard parts go into the front copy only.

The package vllm_toy_plugin is not in the vLLM repository. Its code blocks are plain <pre> blocks, not excerpts. Each vLLM API that they use is cited to the code at {{project short_sha}}, and the matching test plugin is shown as a real excerpt. The model name and the checkpoint in the commands are examples.

vLLM itself uses the newer pyproject.toml form for its own general plugins:

The toy uses the same form, with one table per {{term plugin-group}}:

# pyproject.toml (illustrative)
[build-system]
requires = ["setuptools>=64"]
build-backend = "setuptools.build_meta"

[project]
name = "vllm-toy-plugin"

[tool.setuptools]

[project.entry-points."vllm.general_plugins"]

[project.entry-points."vllm.stat_logger_plugins"]

[project.entry-points."vllm.endpoint_plugins"]
toy_endpoint = "vllm_toy_plugin.endpoint:ToyEndpointPlugin"

The left side of each line is the entry-point name. VLLM_PLUGINS matches this name exactly, not the package name ({{cite vllm/plugins/__init__.py:63-64}}). The right side is module:attribute. Each group expects a different kind of object. The general group needs a function, the stat logger group a StatLoggerBase subclass, and the endpoint group a factory with no arguments. The table in {{link concepts/plugin-loading#in-the-code}} lists all six groups.

vLLM calls a general plugin function with no arguments, once in each process ({{cite vllm/plugins/__init__.py:82-90}}). With TP = 2 that means four processes, and the function must do the same thing each time. The model test plugin shows the pattern: check first, then register. Its last two registrations use the lazy string form:

The toy does the same for one architecture, and also imports the module with the op replacement:

# vllm_toy_plugin/__init__.py (illustrative)
def register():
    """General plugin. vLLM calls it once in every process."""
    from vllm import ModelRegistry

    # The model: a "module:Class" string. Nothing is imported now.
    if "ToyLlamaForCausalLM" not in ModelRegistry.get_supported_archs():
        ModelRegistry.register_model(
            "ToyLlamaForCausalLM", "vllm_toy_plugin.model:ToyLlamaForCausalLM"
        )

    # The op: importing the module runs @RMSNorm.register_oot (stop 4).
    import vllm_toy_plugin.ops  # noqa: F401
  • from vllm import ModelRegistry is a lazy attribute of the vllm package ({{cite vllm/__init__.py:26}}).
  • get_supported_archs() returns the keys of the registry ({{cite vllm/model_executor/models/registry.py:1157-1158}}).
  • A string must contain exactly one colon. It becomes a lazy entry, and nothing is imported ({{cite vllm/model_executor/models/registry.py:1187-1193}}). A class would be inspected at once, in every process ({{cite vllm/model_executor/models/registry.py:1194-1195}}).
  • The import of ops is inside the function. So the import, and the decorator, run only when vLLM calls the plugin. Python caches the module, so a second call in the same process does not register the op again.

The page {{link concepts/oot-models}} explains the registry and its lazy entries.

The model test plugin subclasses an in-tree model and changes one method:

The toy subclasses Llama and changes nothing, so it runs any Llama-architecture checkpoint under a new name:

# vllm_toy_plugin/model.py (illustrative)
from vllm.model_executor.models.llama import LlamaForCausalLM


class ToyLlamaForCausalLM(LlamaForCausalLM):
    """Llama under a new architecture name. Override methods here."""

The class inherits the constructor __init__(self, *, vllm_config, prefix="", ...) ({{cite vllm/model_executor/models/llama.py:484-490}}). That matters: initialize_model checks for both parameter names, and otherwise warns and guesses old arguments ({{cite vllm/model_executor/model_loader/utils.py:96-115}}). The registry also checks the structure, for example embed_input_ids and compute_logits ({{cite vllm/model_executor/models/interfaces_base.py:69-76}}, {{cite vllm/model_executor/models/interfaces_base.py:140-147}}, {{link concepts/model-interfaces}}).

vLLM finds the class by the architecture name in the checkpoint's config.json. To use a normal Llama checkpoint, rename the architecture at start-up. A vLLM test does the same for its OPT model ({{cite tests/distributed/test_distributed_oot.py:20-21}}):

--hf-overrides '{"architectures": ["ToyLlamaForCausalLM"]}'

On the first start, the front end inspects the lazy entry in a subprocess and caches the result on disk ({{cite vllm/model_executor/models/registry.py:1088-1116}}). That subprocess runs register() too ({{cite vllm/model_executor/models/registry.py:1612}}). Later starts read the cache, until model.py changes.

The platform test plugin replaces the rotary embedding layer. The decorator goes on a subclass of the in-tree class:

The toy replaces RMSNorm, which every Llama decoder layer builds ({{cite vllm/model_executor/models/llama.py:308-309}}):

# vllm_toy_plugin/ops.py (illustrative)
import torch

from vllm.model_executor.layers.layernorm import RMSNorm


@RMSNorm.register_oot            # the key is "RMSNorm", the class name
class ToyRMSNorm(RMSNorm):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.toy = True            # a visible mark: the swap happened

    def forward_cuda(self, x: torch.Tensor, residual: torch.Tensor | None = None):
        # Your CUDA kernel goes here. The toy calls the in-tree path.
        return super().forward_cuda(x, residual)

The decorator stores the class under a key and gives the class that key as its name:

  1. Line 337. Without name=, the key is the name of the class on which you call the decorator: RMSNorm.register_oot gives "RMSNorm".
  2. Lines 338-340. A second registration with the same key fails the assert. The toy class gets name = "RMSNorm".
  3. Lines 349-353. @RMSNorm.register_oot without parentheses passes the class as the first argument.
  4. Lines 354-356. A string as the first argument raises TypeError.

When a Llama layer calls RMSNorm(...), CustomOp.__new__ finds "RMSNorm" in the out-of-tree registry and makes a ToyRMSNorm instead ({{cite vllm/model_executor/custom_op.py:107-126}}). The lookup uses the Python class name of the called class (line 109). So if you use the keyword form, the value must be the class name: @CustomOp.register_oot(name="RMSNorm"), not name="rms_norm". (Derived from lines 109 and 117.)

With the default settings, vllm serve on CUDA disables ToyRMSNorm. The swapped op then runs the inherited forward_native, and your forward_cuda does not run. Turn the op on with one of the two switches below.

Each op picks one method when it is built. A disabled op takes forward_native; an enabled op takes the method of the {{term platform}} ({{cite vllm/model_executor/custom_op.py:183-205}}). Whether an op is enabled depends on the list compilation_config.custom_ops:

The base mode is "all" or "none". vLLM adds it after it parses the flags:

With the default compilation (Inductor, mode VLLM_COMPILE), the base mode is "none". The page {{link concepts/custom-ops}} gives the full rule. So you have two switches:

SettingEffect on ToyRMSNorm on CUDA
nothing (default)disabled: forward_native
--compilation-config '{"custom_ops": ["+RMSNorm"]}'enabled: ToyRMSNorm.forward_cuda. vLLM still appends "none", so the other ops stay off.
--compilation-config '{"custom_ops": ["+rms_norm"]}'disabled: forward_native, with a WARNING that the switch "has no effect"
--enforce-eagermode NONE, so base mode "all": every op enabled, the toy included ({{cite vllm/config/vllm.py:1745-1746}})

The name quirk. The in-tree class registered the op name rms_norm ({{cite vllm/model_executor/layers/layernorm.py:38-39}}). But register_oot gave ToyRMSNorm the name "RMSNorm" (stop 4, line 339), and enabled() builds the switch from that name (line 282). So +rms_norm matches nothing in this model, and custom_op_log_check warns ({{cite vllm/config/compilation.py:1341-1361}}). (Derived from the cited lines; no test covers it.)

Which method runs on an enabled op depends on the platform. On CUDA it is forward_cuda (line 205 of custom_op.py). On an out-of-tree platform it is forward_oot (lines 202-203). The test platform turns every op on in its config hook ({{cite tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/dummy_platform.py:21-23}}). A general plugin such as the toy has no config hook, so the user must set the switch.

A {{term stat-logger}} receives the scheduler and iteration statistics in the front end. The test plugin implements the minimal interface:

The base class has three abstract methods: the constructor, record and log_engine_initialized ({{cite vllm/v1/metrics/loggers.py:54-81}}). The toy counts the generated tokens and prints them:

# vllm_toy_plugin/stat_logger.py (illustrative)
from vllm.logger import init_logger
from vllm.v1.metrics.loggers import StatLoggerBase

logger = init_logger("vllm.toy_plugin")    # a child of "vllm", so INFO lines show


class ToyStatLogger(StatLoggerBase):
    def __init__(self, vllm_config, engine_index: int = 0):
        self.engine_index = engine_index
        self.generated = 0

    def record(self, scheduler_stats, iteration_stats,
               mm_cache_stats=None, engine_idx=0):
        if iteration_stats is not None:
            self.generated += iteration_stats.num_generation_tokens

    def log(self):
        logger.info("toy: engine %d generated %d tokens",
                    self.engine_index, self.generated)

    def log_engine_initialized(self):
        logger.info("toy: engine %d is ready", self.engine_index)
  • The loader checks the class. An object that is not a StatLoggerBase subclass raises TypeError and stops start-up ({{cite vllm/v1/metrics/loggers.py:84-98}}).
  • AsyncLLM.__init__ loads the group ({{cite vllm/v1/engine/async_llm.py:155-156}}). StatLoggerManager wraps a per-engine class in an adapter ({{cite vllm/v1/metrics/loggers.py:1408-1414}}). The adapter calls ToyStatLogger(vllm_config, engine_index) once for each engine ({{cite vllm/v1/metrics/loggers.py:442-445}}).
  • record runs for each batch of engine outputs ({{cite vllm/v1/engine/async_llm.py:929-935}}). IterationStats has the field num_generation_tokens ({{cite vllm/v1/metrics/stats.py:483}}). The base class docstring warns that these stats classes are not a stable interface ({{cite vllm/v1/metrics/loggers.py:55-60}}).
  • log runs every VLLM_LOG_STATS_INTERVAL seconds, default 10, when stats logging is on ({{cite vllm/entrypoints/launchers/utils/server_utils.py:78-84}}, {{cite vllm/envs.py:874-878}}).
  • The logger name starts with vllm. on purpose. vLLM's logging config attaches its handler to the logger "vllm" only ({{cite vllm/logger.py:100-105}}). A logger with another name has no level of its own and gets the level of Python's root logger, which is WARNING by default. So Python drops its INFO lines. (Derived from the config and the Python logging defaults; other code can configure the root logger.)

An {{term endpoint-plugin}} adds HTTP routes. Its entry point gives a factory with no arguments, and the object must have name, required_tasks, attach_router and init_state ({{cite vllm/plugins/endpoint_plugins/interface.py:49-94}}). The test plugin uses the class itself as the factory:

The toy route needs no engine, so its init_state does nothing:

# vllm_toy_plugin/endpoint.py (illustrative)
from fastapi import FastAPI


class ToyEndpointPlugin:
    name = "toy_endpoint"        # use the entry-point name here too
    required_tasks = None        # no task needed

    def attach_router(self, app: FastAPI) -> None:
        @app.get("/v1/toy/hello")
        async def hello():
            return {"plugin": "vllm_toy_plugin", "status": "loaded"}

    async def init_state(self, engine_client, state, args) -> None:
        pass                     # this route does not use the engine
  1. Phase A. build_app calls attach_endpoint_plugins after the core routes ({{cite vllm/entrypoints/launchers/app.py:47-51}}). A plugin route with the same path and method as a core route replaces it ({{cite vllm/plugins/endpoint_plugins/interface.py:72-74}}).
  2. Phase B. init_endpoint_plugins_state awaits init_state of each attached plugin ({{cite vllm/plugins/endpoint_plugins/interface.py:163-164}}).

With VLLM_PLUGINS unset, vLLM loads no endpoint plugin. It only warns: "Found endpoint plugin(s) ... but VLLM_PLUGINS is not set" ({{cite vllm/plugins/__init__.py:122-131}}). You must name toy_endpoint in VLLM_PLUGINS, and that list then filters every other group too (stop 8).

The interface module says that an endpoint should not open new paths into the engine. A plugin that needs engine-side code pairs the endpoint with a general plugin ({{cite vllm/plugins/endpoint_plugins/interface.py:5-16}}). The page {{link concepts/frontend-plugins}} explains the route replacement in detail.

The checkpoint is an example: any Llama-architecture checkpoint works. Three rules about VLLM_PLUGINS matter here:

  • The value is split at commas, and the parts are not stripped ({{cite vllm/envs.py:1163-1167}}). Do not put spaces after the commas.
  • The list also filters the platform group and vLLM's own general plugins. This list drops the two LoRA resolvers ({{cite pyproject.toml:45-47}}). Add lora_filesystem_resolver if you use it.
  • An empty string is a list that matches nothing ({{cite vllm/plugins/__init__.py:107-109}}).

What can go wrong

docs/design/custom_op.md writes @CustomOp.register_oot("op_name") and @CustomOp.register_oot("MMEncoderAttention") ({{cite docs/design/custom_op.md:11}}, {{cite docs/design/custom_op.md:285}}). A string as the first argument raises TypeError ({{cite vllm/model_executor/custom_op.py:354-356}}). Write @RMSNorm.register_oot or @CustomOp.register_oot(name="RMSNorm").
  • A plugin function that is not re-entrant. vLLM calls it once per process, but in every process ({{cite vllm/plugins/__init__.py:82-90}}). The design doc asks for a function that "can be called multiple times without causing issues" ({{cite docs/design/plugin_system.md:60}}). Check the registry before you register, as the test plugin does. Keep decorators at module level. A decorator inside the function body runs again when your own code or a test calls the function twice. Then register_oot fails its assert ({{cite vllm/model_executor/custom_op.py:338}}). Side effects outside the process, such as a file write, happen once in each process: four times or more with TP = 2.
  • Eager class registration. register_model("ToyLlamaForCausalLM", ToyLlamaForCausalLM) imports the model module in every process and inspects it at once ({{cite vllm/model_executor/models/registry.py:1194-1195}}). The docstring gives the main risk: an import that starts CUDA, and then "Cannot re-initialize CUDA in forked subprocess" ({{cite vllm/model_executor/models/registry.py:1167-1173}}). vllm serve uses spawn, and vLLM switches to spawn when CUDA is already started ({{cite vllm/utils/system_utils.py:145-162}}). But vLLM used as a library defaults to fork ({{cite vllm/envs.py:936-940}}). Use the string form.
  • VLLM_PLUGINS disables the LoRA resolvers. The endpoint forces you to set the list (stop 7). Every name that is not in it is skipped, also vLLM's own lora_filesystem_resolver and lora_hf_hub_resolver ({{cite pyproject.toml:45-47}}). The loader does not log a skipped name, and the general group logs its plugin list only at DEBUG level. So nothing shows at INFO ({{cite vllm/plugins/__init__.py:48-66}}).
  • The wrong switch name. +rms_norm does not enable ToyRMSNorm; +RMSNorm does (stop 5).
  • Your INFO lines do not show. A logger that is not under vllm. has no vLLM handler and gets the WARNING level of the root logger (stop 6).
  • A broken import is only logged. A typo in the entry-point value gives "Failed to load plugin ..." and the server starts without the part ({{cite vllm/plugins/__init__.py:71-72}}). An exception inside register() is not caught and stops the process ({{cite vllm/plugins/__init__.py:89-90}}).
  • A stale entry point. You renamed a function but did not install the package again. The old value is still in the {{term entry-point-metadata}}, and the import fails ({{link learn/python-entry-points}}).

Why it matters. Most plugin bugs are not in the plugin's own logic. They are in the wiring: the entry-point name, the allowlist, the switch name, the process. The log lines of stop 9 check the wiring before you debug any kernel or model code.

Which VLLM_PLUGINS value do you need for the toy with its endpoint, and why can you not leave the variable unset?

toy_register,toy_stat_logger,toy_endpoint, with no spaces. Endpoint plugins load only when VLLM_PLUGINS is set and names them ({{cite vllm/plugins/__init__.py:122-131}}). The list then filters every other group too, so the other two names must be in it ({{cite vllm/plugins/__init__.py:63-64}}).

 What is wrong with register_model("ToyLlamaForCausalLM", "vllm_toy_plugin.model.ToyLlamaForCausalLM")?

The string has no colon. The lazy form must be "module:Class" with exactly one colon, else register_model raises ValueError ({{cite vllm/model_executor/models/registry.py:1187-1191}}).

 You start the server with no compilation flags. Is ToyRMSNorm built? Does its forward_cuda run?

It is built: CustomOp.__new__ swaps every RMSNorm for it ({{cite vllm/model_executor/custom_op.py:117-126}}). Its forward_cuda does not run. The default base mode is "none" ({{cite vllm/config/vllm.py:1819-1824}}), so the op is disabled and uses forward_native ({{cite vllm/model_executor/custom_op.py:189-192}}).

 You pass --compilation-config '{"custom_ops": ["+rms_norm"]}'. What happens, and why?

ToyRMSNorm stays disabled, and vLLM warns that the switch has no effect. register_oot set the attribute name of the class to the key "RMSNorm" ({{cite vllm/model_executor/custom_op.py:337-339}}). enabled() looks for "+RMSNorm" ({{cite vllm/model_executor/custom_op.py:282}}). After the model build, rms_norm is not among the op names of the model, so custom_op_log_check logs the warning ({{cite vllm/config/compilation.py:1341-1361}}). (Derived.)

 Your ToyStatLogger uses logging.getLogger(__name__), which gives the name vllm_toy_plugin.stat_logger. Its logger.info lines never show. Why, and what is the fix?

vLLM attaches its handler only to the logger "vllm" ({{cite vllm/logger.py:100-105}}). A logger outside that tree has no level of its own. It gets the level of Python's root logger, WARNING by default, and drops INFO records. The root logger also has no handler by default, so Python prints only warnings and errors, through its last-resort handler. Use a name under vllm., for example init_logger("vllm.toy_plugin") ({{cite vllm/logger.py:328-335}}). (Derived from the logging config and the Python logging rules.)
