The idea

A cold start of vllm serve can take minutes. The log shows many lines, from two processes. This tour connects each part of the log to the code that writes it. Then you can read your own server log and see where the time goes.

With one GPU (TP = PP = DP = 1), vllm serve runs two processes. The {{term api-server}} process is the vllm command itself: it parses the flags, builds the {{term vllm-config}} and later runs the HTTP server. The {{term engine-core}} process is a child. With one GPU, the {{term uni-executor}} runs the {{term worker}} inside that process, so it also loads the model and owns the GPU ({{link concepts/architecture-overview}}).

An everyday comparison. Think of a theatre before the first show. The front office prints the tickets and the cast list, and it opens the doors only when the stage manager calls "ready". Backstage, the crew builds the set, tunes the lights and rehearses each scene once. The comparison stops in one place. Here the front office writes the full script (the config) before the crew starts, and the crew gets a copy.

The tour {{link tours/life-of-a-plugin}} walks the same start-up from the side of the plugins, with TP = 2. This tour follows the config, the processes and the GPU work.

The example

vllm serve meta-llama/Llama-3.1-8B-Instruct     # one 80 GB H100, no other flags
  • Usage context OPENAI_API_SERVER, so the token budget is 8192 and max_num_seqs is 1024 when the driver reports 70 GiB or more ({{cite vllm/engine/arg_utils.py:2970-2983}}).
  • Optimization level O2: torch.compile and CUDA graph mode FULL_AND_PIECEWISE ({{cite vllm/config/vllm.py:434}}, {{cite vllm/config/vllm.py:310}}).
  • The executor backend is uni, because the world size is 1 ({{cite vllm/config/parallel.py:1099-1100}}).

The model and the GPU are an example. Numbers such as GiB values and times are illustrative; the log texts and the order are from the code. We assume a cold start: no compile cache, weights already downloaded.

The CLI builds the parser of every subcommand before it reads your flags:

The serve parser calls make_arg_parser, which ends with AsyncEngineArgs.add_cli_args ({{cite vllm/entrypoints/cli/serve.py:172}}, {{cite vllm/entrypoints/common/cli_args.py:465-466}}):

  1. Line 3243. The general plugins run for the first time in this process. Later calls return at once ({{cite vllm/plugins/__init__.py:82-85}}).
  2. Line 3245. About 300 flags are made from the config classes ({{link concepts/config-system}}, Step 4). The help text is read only with --help, which saves time ({{cite vllm/engine/arg_utils.py:285-288}}).
  3. Line 3257. The platform hook pre_register_and_update(parser). The parsers of launch render and run-batch call add_cli_args too, so the hook runs three times here ({{cite vllm/entrypoints/cli/launch.py:39}}, {{cite vllm/entrypoints/cli/run_batch.py:62}}).

Line 110 of main.py parses the command line. FlexibleArgumentParser first inserts a --config YAML file, changes _ to -, expands -O3 and turns -cc.key=value into JSON ({{cite vllm/utils/argparse_utils.py:313-502}}). Line 113 configures logging; line 114 checks the serve flags.

args.dispatch_function is ServeSubcommand.cmd. It moves the positional model into args.model and decides how many API server processes to run ({{cite vllm/entrypoints/cli/serve.py:54-57}}). --api-server-count is not set, so it becomes the data parallel size, 1 ({{cite vllm/entrypoints/cli/serve.py:113-130}}):

One API server runs in this process, inside a uvloop event loop (lines 155-156). With more API servers, the CLI process would stay a supervisor and start them as children (line 152, deep dive "DP = 2").

run_server names the process for the log, catches an early SIGTERM, and calls setup_server ({{cite vllm/entrypoints/launchers/api_server/entry.py:164-176}}):

  1. Line 367. The banner: "vLLM server version %s, serving model %s", or an ASCII logo with the same values ({{cite vllm/entrypoints/common/startup.py:16-38}}).
  2. Line 368. "non-default args: {...}" lists every flag that differs from its default, with secrets shown as *** ({{cite vllm/entrypoints/common/startup.py:49-60}}, {{cite vllm/entrypoints/common/startup.py:94-96}}). To find the defaults, it builds the whole parser once more ({{cite vllm/entrypoints/common/startup.py:70-74}}). So pre_register_and_update(parser) runs a fourth time.
  3. Lines 372-379. The socket is bound now, before the engine starts. The comment names a race with Ray as the reason. A busy port therefore fails in seconds, not after the model loads.

The API server only binds the port here. It does not accept connections until uvicorn runs at stop 18.

run_server_worker enters build_async_engine_client, which makes the {{term engine-args}}:

from_cli_args copies each parsed value into the dataclass field of the same name ({{cite vllm/engine/arg_utils.py:1961-1970}}). Then EngineArgs.__post_init__ runs. It turns dict values into config objects and calls load_general_plugins(), which returns at once here ({{cite vllm/engine/arg_utils.py:873-924}}). The call is for the offline LLM class, which builds no parser.

build_async_engine_client_from_engine_args calls {{term create-engine-config}} with the {{term usage-context}} OPENAI_API_SERVER ({{cite vllm/entrypoints/launchers/api_server/entry.py:68-82}}):

  1. Line 2246. pre_register_and_update() runs a fifth time, now without a parser.
  2. Line 2250. validate_environ warns about each VLLM_* name in the environment that vLLM does not know ({{link reference/env-vars}}).
  3. Line 2269. ModelConfig reads the Hugging Face config. It asks the model registry and logs "Resolved architecture: LlamaForCausalLM" ({{cite vllm/config/model.py:741-744}}). Later in the same __post_init__, it computes max_model_len and logs "Using max model len 131072" ({{cite vllm/config/model.py:824}}, {{cite vllm/config/model.py:2170}}).
  4. Line 2275. Chunked prefill and prefix caching get their defaults from the model: both on for Llama ({{cite vllm/engine/arg_utils.py:3028-3068}}).

131,072 is the context length of Llama 3.1 in its Hugging Face config (inferred, not in the vLLM repository). On a cold machine, this stop also downloads config.json and the tokenizer files. The registry can start a short subprocess on a cache miss ({{link concepts/oot-models}}).

The function builds CacheConfig, ParallelConfig, the speculative config, the batch defaults, SchedulerConfig and the rest, in this order ({{cite vllm/engine/arg_utils.py:2296}}, {{cite vllm/engine/arg_utils.py:2558}}, {{cite vllm/engine/arg_utils.py:2624-2672}}). Three values of our example are decided here:

  • Executor backend. ParallelConfig.__post_init__ sets "uni", because the world size is 1 ({{cite vllm/config/parallel.py:1099-1100}}).
  • Batch limits. 8192 tokens and 1024 requests, from get_batch_defaults ({{cite vllm/engine/arg_utils.py:3153-3168}}).
  • Block size. None becomes 16 in a CacheConfig validator ({{cite vllm/config/cache.py:452-462}}). The platform can change it after the model loads (stop 13).

The function ends with one constructor call:

The constructor runs the {{term post-init}} of VllmConfig ({{cite vllm/config/vllm.py:1492-2318}}). For our example, it turns async scheduling on ({{cite vllm/config/vllm.py:1697-1698}}) and sets the compilation defaults:

  1. Line 1804. The platform hook apply_config_platform_defaults.
  2. Lines 1806-1810. O2 is above O0, so the compilation mode is VLLM_COMPILE.
  3. Lines 1819-1826. With Inductor, the custom op list gets "none" ({{link concepts/custom-ops}}).
  4. Lines 1833-1834. The O2 table fills the fields that are still None: CUDA graph mode FULL_AND_PIECEWISE and the fusion passes ({{cite vllm/config/vllm.py:296-316}}).

Later in the method, _set_cudagraph_sizes picks the capture sizes, at most 512 here: min(1024 × 1 × 2, 512) ({{cite vllm/config/vllm.py:2439-2449}}). Then the platform has the last word: CUDA sets worker_cls to vllm.v1.worker.gpu_worker.Worker ({{cite vllm/config/vllm.py:2046}}, {{cite vllm/platforms/cuda.py:330-331}}). The config is now complete in the API server.

The API server makes {{term async-llm | AsyncLLM}} ({{cite vllm/entrypoints/launchers/api_server/entry.py:93-103}}). from_vllm_config picks the executor class from the config: UniProcExecutor for "uni" ({{cite vllm/v1/engine/async_llm.py:264-276}}, {{cite vllm/v1/executor/abstract.py:84-87}}). The constructor loads the stat logger plugins, the renderer with the tokenizer, and the input and output processors ({{cite vllm/v1/engine/async_llm.py:155-186}}). Then it starts the engine core:

AsyncLLM always uses a multiprocess client, so the engine core always runs in its own process for vllm serve. With DP = 1, the client class is AsyncMPClient ({{cite vllm/v1/engine/core_client.py:158-173}}).

MPClient.__init__ binds two {{term zmq | ZMQ}} sockets: a ROUTER for requests to the engines, and a PULL for their outputs. Then it launches the engines:

The vllm_config is a keyword argument, so spawn pickles it ({{cite vllm/v1/engine/utils.py:257-264}}).
  2. Line 1387. The yield returns to MPClient, which starts the multimodal warm-up of the front end ({{cite vllm/v1/engine/core_client.py:710}}).
  3. Lines 1388-1395. When the with block of MPClient ends, wait_for_engine_startup runs. The API server now waits for stop 17.

We are now in the new process. run_engine_core sets the process title and the log prefix EngineCore ({{cite vllm/v1/engine/core.py:1462-1472}}), installs signal handlers, and makes an EngineCoreProc ({{cite vllm/v1/engine/core.py:1538-1543}}). Its constructor first does the {{term startup-handshake}} with the front end:

The engine sends HELLO and waits at most 5 minutes for the init message with the socket addresses ({{cite vllm/v1/engine/core.py:113}}). The front end answers at once ({{cite vllm/v1/engine/utils.py:1512-1546}}). Inside the handshake context, EngineCore.__init__ runs ({{cite vllm/v1/engine/core.py:1190-1226}}):

  1. Line 132. The general plugins run again: this is a new interpreter.
  2. Lines 135-140. The log line "Initializing a V1 LLM engine (v...) with config: model='meta-llama/Llama-3.1-8B-Instruct', ...". It prints 33 resolved fields of the config ({{cite vllm/config/vllm.py:2788-2823}}).
  3. Line 147. The executor constructor. Stops 12 and 13 run inside it.

The {{term uni-executor}} makes the worker object in this process and starts it:

init_worker resolves worker_cls from stop 8 and makes the GPU worker ({{cite vllm/v1/worker/worker_base.py:292-302}}, {{link concepts/engine-hooks}}). init_device then prepares the GPU:

  1. Lines 501-507. torch.distributed starts with a world size of 1. The comment says that this must happen before the memory snapshot, so that NCCL buffers count as used memory.
  2. Line 510. The log line "Using V2 Model Runner".

Then the worker makes cuBLAS handles, takes the memory snapshot and computes the requested memory, gpu_memory_utilization × total ({{cite vllm/v1/worker/gpu_worker.py:523-541}}). It builds Model Runner V2 ({{cite vllm/v1/worker/gpu_worker.py:567-580}}).

Worker.load_model calls the model runner ({{cite vllm/v1/worker/gpu_worker.py:591-598}}). The runner builds the model and loads the weights:

The log shows four lines here. The first is "Loading model from scratch...". Then the constructors log "Initializing model took 0.412310 seconds" ({{cite vllm/model_executor/model_loader/base_loader.py:82-85}}). A download of the weights, if needed, happens inside load_model: the default loader downloads a model that is not local before it reads the files ({{cite vllm/model_executor/model_loader/default_loader.py:155-157}}, {{cite vllm/model_executor/model_loader/default_loader.py:269-277}}). The page {{link concepts/weight-loading}} explains the loader.

Back in the executor, update_block_size_for_backend checks that block size 16 suits the attention backend (line 75 of the excerpt in stop 12).

Back in EngineCore.__init__, the engine sizes the KV cache ({{cite vllm/v1/engine/core.py:160}}):

determine_available_memory runs a {{term profile-run}}: one forward pass with max_num_batched_tokens dummy tokens ({{cite vllm/v1/worker/gpu_worker.py:682-697}}). This is the first call of the compiled model, so torch.compile runs now. The log shows:

  • "torch.compile took 29.70 s in total" ({{cite vllm/compilation/monitor.py:20}}, {{cite vllm/compilation/monitor.py:56-62}}).

Then the worker measures the memory and logs "Available KV cache memory: 54.6 GiB" ({{cite vllm/v1/worker/gpu_worker.py:744-748}}, {{cite vllm/v1/worker/gpu_worker.py:763-766}}). All times and GiB values are illustrative. The real compile messages depend on the cache state; with PyTorch 2.14 (the pinned version, {{cite pyproject.toml:10}}) the AOT compile path is on by default ({{cite vllm/envs.py:378-387}}). The deep dive "A warm start" shows the messages with a filled cache.

The engine core sends the KV cache config to the worker ({{cite vllm/v1/engine/core.py:362}}). The worker allocates the tensors:

A KV connector would start here too ({{cite vllm/v1/worker/gpu_worker.py:878}}). In our example there is none. After this stop, about 54.6 GiB of the GPU belong to the KV cache.

The last GPU stop ({{cite vllm/v1/engine/core.py:378-379}}):

  1. Lines 956-968. Each compile range that has no captured size gets one warm-up run at its end size. Each size in compile_sizes that is not a capture size gets one too (lines 941-948). In our example, the capture sizes cover the one compile range, so this loop does not run. The log is "Compile and warming up model for size %d".
  2. Line 973. Kernel warm-up and tuning before capture.
  3. Lines 983-985. CUDA graph capture, unless --enforce-eager. The log is "Graph capturing finished in 9 secs, took 0.46 GiB" ({{cite vllm/v1/worker/gpu/model_runner.py:1146-1152}}). The comment there says it "usually takes 5~20 seconds".

Then the worker logs "CUDA graph pool memory: ..." and a long line "Free memory on device ... Replace gpu_memory_utilization config with --kv-cache-memory=..." ({{cite vllm/v1/worker/gpu_worker.py:994-1057}}). The real flag name is --kv-cache-memory-bytes ({{cite vllm/engine/arg_utils.py:1385}}). The short form also works, because argparse accepts a unique prefix of a flag name by default (derived; no allow_abbrev=False in vllm/). Back in the engine core, one line sums up stops 14 to 16:

For example: "init engine (profile, create kv cache, warmup model) took 52.40 s (compilation: 29.70 s)". EngineCore.__init__ then builds the scheduler with the final block count, picks step_with_batch_queue, and turns on the {{term env-cache}} ({{cite vllm/v1/engine/core.py:177-185}}, {{cite vllm/v1/engine/core.py:227-229}}, {{cite vllm/v1/engine/core.py:241-243}}).

EngineCore.__init__ has returned. When the handshake context ends, the engine sends READY:

Before READY, still inside the with block, the engine core starts its input and output threads ({{cite vllm/v1/engine/core.py:1243-1265}}). The input thread connects to the front end and sends the ready response as its first message ({{cite vllm/v1/engine/core.py:1961-1968}}). The constructor waits for the input thread, then the block ends and READY goes out ({{cite vllm/v1/engine/core.py:1267-1272}}). After READY, the engine core calls vllm_config.__post_init__() again on its copy ({{cite vllm/v1/engine/core.py:1336-1337}}; see {{link concepts/config-system}}, Step 9).

In the API server, wait_for_engine_startup has polled the handshake socket every 10 seconds ({{cite vllm/v1/engine/utils.py:43}}):

A poll with no event logs at DEBUG level and continues, so this wait has no time limit. Only a dead process stops it, with "Engine core initialization failed. See root cause above." (lines 1448-1477). The READY message moves the engine to the state READY (lines 1547-1578). Then MPClient waits for the ready response on its ROUTER socket, now with the limit VLLM_ENGINE_READY_TIMEOUT_S, 600 s by default ({{cite vllm/v1/engine/core_client.py:753-771}}, {{cite vllm/envs.py:810-814}}). It copies max_model_len, num_gpu_blocks and block_size from the response into its own config ({{cite vllm/v1/engine/core_client.py:865-879}}).

The timeout error text says that a timeout "is often caused by slow weight loading" ({{cite vllm/v1/engine/core_client.py:760-768}}). With one API server, the weights load during the wait of wait_for_engine_startup, which has no limit. The 600 s limit starts only after READY. At that time the ready response is already on the socket, because the engine core sends it before READY. The limit matters when several API servers start before the engines (deep dive "DP = 2").

  1. Line 132. A utility call asks the engine core for its tasks. The log shows a tuple, for example "Supported tasks: ('generate',)" ({{cite vllm/v1/engine/async_llm.py:390}}).
  2. Line 136. build_app makes the FastAPI app with the routes, endpoint plugins, exception handlers and middleware ({{cite vllm/entrypoints/launchers/app.py:19-56}}). See {{link concepts/openai-server}}.
  3. Line 137. init_app_state makes the serving objects, for example the chat serving class ({{cite vllm/entrypoints/launchers/api_server/app_state.py:24-30}}).
  4. Line 139. "Starting vLLM server on http://0.0.0.0:8000".

serve_http logs "Available routes are:" and one line per route ({{cite vllm/entrypoints/launchers/launcher.py:188-208}}). Then it starts uvicorn on the socket from stop 4:

uvicorn runs the app's lifespan function. It starts the periodic stats log and freezes the start-up heap for the garbage collector ({{cite vllm/entrypoints/launchers/utils/server_utils.py:76-96}}). uvicorn then prints "Application startup complete." This text is in uvicorn, not in the vLLM repository. From now on, requests reach the server; the tour {{link tours/life-of-a-chat-request}} follows one.

vllm serve meta-llama/Llama-3.1-8B-Instruct -tp 2
  1. Stop 7. The world size is 2, so ParallelConfig picks "mp" when Ray is not active ({{cite vllm/config/parallel.py:1055-1061}}, {{cite vllm/config/parallel.py:1096}}). Stop 9 picks MultiprocExecutor ({{cite vllm/v1/executor/abstract.py:80-83}}).
  2. Stop 12. The executor makes a shared-memory broadcast queue and spawns one process per rank, named VllmWorker-0 and VllmWorker-1 ({{cite vllm/v1/executor/multiproc_executor.py:165-216}}, {{cite vllm/v1/executor/multiproc_executor.py:745-750}}). Each worker gets its own pickled vllm_config (lines 731-743).
  3. Stops 12-13 in parallel. Each worker runs init_device and load_model at the same time. The log prefixes become Worker_TP0 and Worker_TP1 after the process groups exist ({{cite vllm/v1/executor/multiproc_executor.py:1083-1116}}). Each worker sends READY over a pipe ({{cite vllm/v1/executor/multiproc_executor.py:930-937}}), and the executor waits for both ({{cite vllm/v1/executor/multiproc_executor.py:787-811}}).
  4. Stop 14. Each worker measures its own memory. The planner uses the smallest block count of all ranks ({{cite vllm/v1/core/kv_cache_planning.py:1619-1634}}).
  5. Stop 13. Each worker turns on its own environment cache at the end of WorkerProc.__init__, after load_model and before the profile run ({{cite vllm/v1/executor/multiproc_executor.py:680-688}}, {{cite vllm/v1/executor/multiproc_executor.py:708-710}}).

So the server has four vLLM processes: API server, engine core and two workers. The page {{link concepts/executors-and-workers}} lists every executor call. Tensor parallelism itself is explained in {{deepinfer learn/parallelism | Parallelism basics}}.

 
vllm serve meta-llama/Llama-3.1-8B-Instruct -dp 2
  1. Stop 3. --api-server-count defaults to the DP size, 2 ({{cite vllm/entrypoints/cli/serve.py:124-130}}). So run_multi_api_server runs, not run_server ({{cite vllm/entrypoints/cli/serve.py:151-152}}).
  2. Stops 4-8 in the CLI process. It binds the port with SO_REUSEPORT, builds its own VllmConfig and binds the ZMQ listeners for both API servers ({{cite vllm/entrypoints/cli/serve.py:298}}, {{cite vllm/entrypoints/cli/serve.py:307-334}}).
  3. Stop 10. launch_core_engines starts a DP coordinator process, because the internal load balancer needs its queue statistics ({{cite vllm/v1/engine/utils.py:1230-1274}}). It starts two engine core processes, EngineCore_DP0 and EngineCore_DP1 ({{cite vllm/v1/engine/utils.py:284}}).
  4. Inside the with block, before the engines are ready, the CLI process starts two API server processes, ApiServer_0 and ApiServer_1 ({{cite vllm/entrypoints/cli/serve.py:366-377}}, {{cite vllm/v1/utils.py:248-254}}). Each one runs stops 5-9 again: its own EngineArgs, create_engine_config and AsyncLLM, which connects to the existing engines ({{cite vllm/v1/utils.py:509-529}}, {{cite vllm/v1/engine/core_client.py:643-669}}).
  5. Engines. Llama is not a MoE model, so each engine core is an independent EngineCoreProc ({{cite vllm/v1/engine/core.py:1534-1543}}). The world size across DP is 2, so the backend is "mp" and each engine core has one worker process.
  6. Stop 17. The API server processes did not launch the engines, so they skip wait_for_engine_startup. They wait for the ready responses with the 600 s limit of VLLM_ENGINE_READY_TIMEOUT_S ({{cite vllm/v1/engine/core_client.py:753-768}}). If the engines load for longer than that, the API servers fail with the timeout error.

The count of vLLM processes is 8: the CLI supervisor, 2 API servers, the coordinator, 2 engine cores and 2 workers (derived). Helper processes of Python's multiprocessing are not counted. See {{link concepts/data-parallel-serving}}.
  1. Stop 8. __post_init__ sets the compilation mode and the CUDA graph mode to NONE and turns off the JIT kernel warm-up. It logs "Enforce eager set, disabling torch.compile, CUDAGraphs, and JIT kernel warmup ..." ({{cite vllm/config/vllm.py:1745-1763}}).   2. Stop 14. The profile run runs the model eagerly: no "torch.compile took" line.
  3. Stop 16. No capture ({{cite vllm/v1/worker/gpu_worker.py:983-985}}). The summary line has no "(compilation: ...)" part, because the compile time is 0 ({{cite vllm/v1/engine/core.py:401-405}}).

Start-up is faster, but each decode step pays the full Python and kernel launch cost. -O0 has the same effect on compilation and graphs ({{cite vllm/config/vllm.py:254-274}}, {{cite vllm/config/vllm.py:1806-1810}}). The CUDA graph idea is in {{deepinfer learn/gpus-kernels | GPUs and kernels}}.

Start the same command a second time, with the same config, code and environment. Stop 14 changes:

  • The AOT path finds its file under $VLLM_CACHE_ROOT/torch_compile_cache/torch_aot_compile/<sha256>/rank_0_0/model ({{cite vllm/compilation/decorators.py:570-596}}). It logs "Directly load AOT compilation from path ..." ({{cite vllm/compilation/decorators.py:326-330}}) and still logs the total time, now small ({{cite vllm/compilation/decorators.py:302-307}}).
  • The key of that folder is a hash of the env factors, VllmConfig.compute_hash() and, with the mega artifact, the Inductor factors ({{cite vllm/compilation/caching.py:572-588}}).
  • A changed source file or a load error falls back to a full compile, with "Compiling model again due to a load failure from ..." ({{cite vllm/compilation/decorators.py:332-348}}).

Stop 16 does not change: CUDA graphs are captured at every start ({{cite vllm/v1/worker/gpu_worker.py:983-985}}). Weight loading does not change either. The page {{link concepts/compile-and-cuda-graphs}} explains both cache folders.

-O0 and --enforce-eager remove compilation and CUDA graphs for the whole life of the server. Use them for a quick test, not for production. A warm compile cache gives most of the gain with no cost per step.

What can go wrong

  • The port is busy. sock.bind fails at stop 4, before any GPU work ({{cite vllm/entrypoints/launchers/launcher.py:349-353}}).
  • The engine core fails. It logs "EngineCore failed to start." with the stack trace ({{cite vllm/v1/engine/core.py:1570-1572}}). The API server then raises "Engine core initialization failed. See root cause above." ({{cite vllm/v1/engine/utils.py:1468-1477}}). Read the EngineCore lines above it for the real error, for example a CUDA out-of-memory error.
  • Not enough free memory. The worker checks at start that the free memory is at least gpu_memory_utilization × total, and raises ValueError if not ({{cite vllm/v1/worker/utils.py:761-770}}). Another process on the same GPU is the usual cause.
  • The KV cache is too small for max_model_len. The planner raises ValueError at stop 14: "To serve at least one request with the model's max seq len ...". The message gives an estimated maximum length ({{cite vllm/v1/core/kv_cache_planning.py:68-88}}).
  • The front end waits for a long time with no log. With one API server, the wait at stop 17 logs only at DEBUG level. Read the EngineCore lines to see the progress.
  • A timeout with several API servers. "Timed out waiting for engine core processes to start" after VLLM_ENGINE_READY_TIMEOUT_S ({{cite vllm/v1/engine/core_client.py:757-768}}).

Why it matters. A server that does not start, or starts slowly, costs capacity during each deploy and each restart. When you know the 18 stops, you can read the log, find the slow phase, and pick the setting that shortens it.

In which process does the model load when you run vllm serve on one GPU?

In the engine core process. The uni executor makes the worker object in that process and calls load_model on it ({{cite vllm/v1/executor/uniproc_executor.py:54-74}}).

 Why does a busy port fail in seconds and not after the model loads?

setup_server binds the socket before the engine starts, at stop 4 ({{cite vllm/entrypoints/launchers/launcher.py:372-379}}).

 Which stop runs torch.compile on a cold start, and why there?

Stop 14. The profile run in determine_available_memory is the first call of the compiled model, so the compilation happens inside it ({{cite vllm/v1/worker/gpu_worker.py:682-697}}). The memory profile then also measures the compiled model.

 You set VLLM_ENGINE_READY_TIMEOUT_S=60 and start a single-GPU server whose weights take 5 minutes to load. What happens?

The server starts normally. With one API server, the front end waits in wait_for_engine_startup, which has no time limit ({{cite vllm/v1/engine/utils.py:1434-1447}}). The 60 s limit applies only to the ready response after READY ({{cite vllm/v1/engine/core_client.py:753-768}}).

 How many times does pre_register_and_update run in the API server process for vllm serve <model>, and where?

Five times. Three parser builds at stop 2 (serve, launch render, run-batch) each call AsyncEngineArgs.add_cli_args ({{cite vllm/engine/arg_utils.py:3257}}). log_non_default_args at stop 4 builds a fourth parser ({{cite vllm/entrypoints/common/startup.py:70-71}}). create_engine_config calls the hook a fifth time, without a parser ({{cite vllm/engine/arg_utils.py:2246}}).
