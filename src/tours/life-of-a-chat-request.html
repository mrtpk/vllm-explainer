The idea

vllm serve starts an {{term openai-compatible-server | OpenAI-compatible server}}. A client sends a chat request as JSON and gets the answer back as a stream of small pieces. This tour follows one such request through the code, from the HTTP route to the last piece, data: [DONE].

The request crosses two processes. The {{term front-end | front end}} is the API server process: FastAPI, the chat template, the tokenizer and {{term async-llm | AsyncLLM}}. The {{term engine-core | engine core}} process holds the scheduler and, with one GPU, also the {{term worker}} and the {{term model-runner | model runner}}. The two processes talk through {{term zmq | ZMQ}} sockets. The messages are {{term msgpack}} bytes.

The engine core does not run one request from start to end. It runs steps. In each step it selects a batch of requests, runs the model once for all of them and adds one new token to each request. So our request goes through the engine step once for each output token. Each new token goes back to the front end and becomes one {{term sse | SSE}} chunk. The idea of steps and continuous batching is not new: see {{deepinfer learn/batching | Batching}}.

An everyday comparison. Think of a restaurant with a waiter and a kitchen. The waiter (the front end) writes the order on a ticket and passes it through a window (ZMQ). The kitchen (the engine core) cooks in rounds for all open orders. After each round, the waiter carries the new part of the dish to the table at once (streaming). The comparison stops being true in two places. A round adds only one token to each order, so an order needs hundreds of rounds. And the waiter must translate each part (token ids) into text before the guest can read it.

The example request

We start the server on one GPU with a chat model, and run the example client of the repository with --stream:

vllm serve Qwen/Qwen2.5-1.5B-Instruct          # any chat model; one GPU, default settings
python examples/basic/online_serving/openai_chat_completion_client.py --stream

The client sends four messages: a system message, a user question, an assistant answer and a second user question ({{cite examples/basic/online_serving/openai_chat_completion_client.py:16-24}}). It calls client.chat.completions.create(..., stream=args.stream) ({{cite examples/basic/online_serving/openai_chat_completion_client.py:46-50}}). On the wire this is one HTTP request:

POST /v1/chat/completions
{"model": "Qwen/Qwen2.5-1.5B-Instruct", "stream": true,
 "messages": [{"role": "system", "content": "You are a helpful assistant."},
              {"role": "user", "content": "Who won the world series in 2020?"},
              {"role": "assistant", "content": "The Los Angeles Dodgers won the World Series in 2020."},
              {"role": "user", "content": "Where was it played?"}]}

The model name and all numbers in this tour (61 prompt tokens, 48 cached tokens, the token ids) are illustrative. The tour assumes a ChatML-style chat template, like the one in {{cite examples/template_chatml.jinja}}. Other models have other templates, so their prompts have other lengths.

The example in the code block uses max_model_len = 32768. That value comes from the model config, not from vLLM, so it is illustrative.

The model reads one sequence of token ids, not a list of messages. The {{term chat-template | chat template}} (a Jinja template from the tokenizer files) writes the messages into one text, with special marker tokens. Then the tokenizer cuts the text into ids. Tokens and tokenizers are explained in {{deepinfer learn/tokens | Tokens and tokenizers}}.

The engine core needs a small, fixed object that it can send as bytes. This is the {{term engine-core-request | EngineCoreRequest}}. AsyncLLM.add_request gets a rendered engine input (a dict with a "type" key). So it calls the synchronous process_inputs of the {{term input-processor | input processor}}. No tokenization is left to do ({{cite vllm/v1/engine/async_llm.py:481-496}}).

process_inputs also does the last checks and fills in defaults:

  • It clones the sampling parameters, so a shared object of the caller does not change ({{cite vllm/v1/engine/input_processor.py:447-449}}).
  • It adds the generation config and the EOS token id of the model to the sampling parameters ({{cite vllm/v1/engine/input_processor.py:489-494}}).
  • It takes arrival_time from the engine input of stop 3 ({{cite vllm/v1/engine/input_processor.py:403-404}}).

  • The front end binds a ZMQ ROUTER socket for input and a PULL socket for output ({{cite vllm/v1/engine/core_client.py:670-682}}). With all engines on this machine, the addresses are ipc:// paths; else they are TCP ({{cite vllm/v1/engine/utils.py:1139-1151}}).
  • The engine identity is the DP rank as 2 little-endian bytes ({{cite vllm/v1/engine/core_client.py:749-751}}). The ROUTER socket uses the first frame to select the engine.
  • The request types are single bytes: ADD = b"\x00", ABORT = b"\x01", UTILITY = b"\x03" ({{cite vllm/v1/engine/__init__.py:300-313}}).
  • MsgpackEncoder.encode returns a list of buffers. The first is the msgpack message. Large tensors and arrays go as extra frames without a copy ({{cite vllm/v1/serial_utils.py:135-177}}). Our request has no tensors, so it is one frame.
  • The front end uses MsgpackEncoder for requests and MsgpackDecoder(EngineCoreOutputs) for outputs ({{cite vllm/v1/engine/core_client.py:731-732}}).
  • The output processor makes a RequestState with an incremental detokenizer and the collector queue ({{cite vllm/v1/engine/output_processor.py:663-693}}).

The main thread of the engine core process runs the {{term busy-loop | busy loop}} for its whole life:

_process_input_queue blocks on input_queue while there is no work, and then handles all queued messages ({{cite vllm/v1/engine/core.py:1635-1664}}). For ADD it calls EngineCore.add_request ({{cite vllm/v1/engine/core.py:1745-1749}}), which checks the request and calls self.scheduler.add_request(request) ({{cite vllm/v1/engine/core.py:548}}). The scheduler puts it into the waiting queue and into its requests dict ({{cite vllm/v1/core/sched/scheduler.py:2730-2734}}).

Now has_work() is true, so the loop calls _process_engine_step. That runs self.step_fn() and puts each output into output_queue ({{cite vllm/v1/engine/core.py:1666-1676}}).

step_fn is self.step without a batch queue, and self.step_with_batch_queue with one ({{cite vllm/v1/engine/core.py:227-229}}). The batch queue exists when max_concurrent_batches > 1 ({{cite vllm/v1/engine/core.py:205-211}}). With async scheduling and Model Runner V2, max_concurrent_batches is pp_size + 1, so 2 on one GPU ({{cite vllm/config/vllm.py:587-597}}).

Async scheduling is on by default: when the flag is not set and nothing is incompatible, the config sets it to True ({{cite vllm/config/vllm.py:1664-1698}}). The uniproc executor supports it ({{cite vllm/v1/executor/uniproc_executor.py:156-158}}). With async scheduling, the scheduler class is AsyncScheduler ({{cite vllm/config/scheduler.py:231-238}}). So the default path of our request is step_with_batch_queue and AsyncScheduler.

has_work() is also true while the batch queue is not empty ({{cite vllm/v1/engine/core.py:1596-1602}}). So the loop keeps stepping until the last in-flight step is processed.

An engine step has three parts: schedule, execute and update. With {{term async-scheduling | async scheduling}}, the engine uses the {{term batch-queue | batch queue}}. This version does not wait for a step right after it starts it. It starts the next step first:

  1. Line 725: the scheduler makes a {{term scheduler-output | SchedulerOutput}} (stop 10).
  2. Lines 727-729: the executor runs execute_model with non_block=True (stops 11 and 12). The uniproc executor runs the CPU part of the model runner at once, in this thread. The GPU work only goes into the CUDA queue. non_block only moves the wait for the GPU result into a future ({{cite vllm/v1/executor/uniproc_executor.py:108-117}}).
  3. Lines 743-745: the executor runs sample_tokens, also non-blocking (stop 13).
  4. Lines 753 and 759: the step goes into the queue. If the queue is not full, the function returns with no outputs.
  5. Lines 768-773: else it takes the oldest step and waits for its result.
  6. Line 783: update_from_output turns that result into outputs (stop 14).

For our request: the first call schedules and starts step 1 and returns. The second call schedules and starts step 2, then waits for step 1. So the first token is processed while step 2 is already on the GPU. The overlap works because the Model Runner V2 code of execute_model and sample_tokens does not wait for the GPU. The only wait is copy_event.synchronize() in get_output() (stop 13). A debug mode can report any other GPU-to-CPU wait in these two worker methods ({{cite vllm/utils/gpu_sync_debug.py:386-392}}, {{cite vllm/v1/worker/gpu_worker.py:1316-1327}}). The loop shows this in a diagram.

EngineCore.step does the same three parts in order and waits for each step: schedule, execute, future.result(), sample, update ({{cite vllm/v1/engine/core.py:657-687}}). The engine uses it with --no-async-scheduling.

We are in vllm/v1/core/sched/scheduler.py. The vLLM scheduler has no prefill phase and no decode phase. The comment at the top of schedule() explains the single rule:

So every request has two numbers: num_computed_tokens (tokens with KV in the cache) and the number of tokens it has. The scheduler gives each request tokens until the first number catches up with the second. The total per step is the token budget, max_num_scheduled_tokens (line 642). Prefill and decode are explained in {{deepinfer learn/prefill-decode | Prefill and decode}}.

  • Budget default. For vllm serve on a GPU with 70 GiB or more (not an A100 and not a GB10), the defaults are max_num_batched_tokens = 8192 and max_num_seqs = 1024. On a GPU with 160 GiB or more they are 16384 and 1024. On other GPUs they are 2048 and 256 ({{cite vllm/engine/arg_utils.py:2960-2993}}). --performance-mode throughput doubles the values that you did not set ({{cite vllm/engine/arg_utils.py:3171-3175}}).
  • Chunked prefill. It is on by default for a generative model that is not encoder-decoder: the engine arguments use model_config.is_chunked_prefill_supported ({{cite vllm/engine/arg_utils.py:3031-3035}}, {{cite vllm/config/model.py:2229-2236}}). A long prompt then gets only the rest of the budget in this step (line 1231), and the rest in the next steps. With chunked prefill off, a prompt that does not fit stops the waiting pass ({{cite vllm/v1/core/sched/scheduler.py:1220-1229}}).
  • Running requests. In later steps our request is in the running pass. There, num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens ({{cite vllm/v1/core/sched/scheduler.py:759-763}}).
  • Placeholders. AsyncScheduler adds one {{term output-placeholder | placeholder}} for each token in flight. It does this after it schedules a step that samples a token: a decode step, or the last chunk of a prefill ({{cite vllm/v1/core/sched/async_scheduler.py:32-47}}). It removes the placeholder when the token arrives ({{cite vllm/v1/core/sched/async_scheduler.py:71-73}}). So the next step can schedule one token before the CPU knows the token of this step.
  • Preemption. If a running request cannot get blocks, the scheduler preempts the last running request (FCFS) or the lowest-priority one ({{cite vllm/v1/core/sched/scheduler.py:850-858}}). See {{term preemption}} and {{link concepts/scheduler}}.

Now the model runs on the GPU. The runner chooses one of three ways, by the CUDA-graph mode of the batch:

  1. Line 2032: FULL mode replays a captured {{term cuda-graph | CUDA graph}} of the whole model. The comment says the inputs are already in the graph's input buffers.
  2. Line 2041: the other modes run inside set_forward_context(...). The {{term forward-context | forward context}} gives each attention layer its metadata and slot mapping.
  3. Line 2065: PIECEWISE runs a graph with the attention parts outside of it.
  4. Line 2070: NONE calls the model eagerly.

CUDA graphs remove the CPU cost of many kernel launches: see {{deepinfer concepts/cuda-graphs | CUDA graphs}}. In step 1 our batch has 13 query tokens of one prefill. In later steps it has 1 query token (a decode). The default optimization level is O2 ({{cite vllm/config/vllm.py:434}}), and O2 sets cudagraph_mode = FULL_AND_PIECEWISE ({{cite vllm/config/vllm.py:310}}). With this mode the runner picks the graph by the batch shape ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:523-553}}):

  • A uniform decode batch gets a FULL graph, if it has no more tokens than the largest captured size. In such a batch every request has exactly 1 query token (no spec decoding). Our decode steps are of this kind.
  • Another batch, for example our 13-token prefill, gets a PIECEWISE graph, padded to the next captured size ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:352-370}}).
  • A batch with more tokens than the largest captured size runs eagerly (NONE).

At start-up the attention backend can lower the mode, if it does not support FULL graphs ({{cite vllm/v1/worker/gpu/model_runner.py:754-763}}). See {{link concepts/compile-and-cuda-graphs}}.

The loop: one engine step per output token

Stops 9 to 16 repeat. Our request gets one step for the prompt (or more with chunked prefill) and then one step per new token. Each step gives one SSE chunk. The prefill step already samples the first token, so a request with 40 output tokens (EOS included) needs 40 engine steps. With async scheduling, one more step for the request is often already scheduled when it stops; the scheduler ignores its result.

The overlap. With async scheduling, the engine core does not wait between steps. It schedules and starts step k+1 first, and only then waits for the token of step k (stop 9). The scheduler can plan step k+1 because AsyncScheduler counts a placeholder for the token in flight (panel 3). The model runner then reads the real token from last_sampled_tokens on the GPU (stop 11). So the CPU work of scheduling and output handling hides behind the GPU work. DeepInfer uses the same idea: see {{deepinfer concepts/zero-overhead-scheduling | Zero-overhead scheduling}}. The page {{link concepts/async-scheduling}} explains the vLLM version in full.

The diagram shows one request. In a real server, every step holds many requests, and new requests join while ours runs. Durations are not to scale. With spec decoding a step can add more than one token; with stream_interval > 1 a chunk can carry more than one token.

The fields of SchedulerOutput are in {{cite vllm/v1/core/sched/output.py:232-313}}. A new request travels as NewRequestData with its prompt and block ids ({{cite vllm/v1/core/sched/output.py:41-56}}). The {{term ttft | time to first token}} and the {{term itl | inter-token latency}} metrics of vLLM are measured in the front end, in IterationStats.update_from_output:

  1. TTFT start: arrival_time = time.time() in render_chat_async (stop 3, {{cite vllm/renderers/base.py:1380}}). So it does not include the HTTP transfer, the JSON parse and the model check before rendering.
  2. TTFT end: iteration_timestamp, the wall-clock time when the output handler makes the IterationStats object for a batch of outputs ({{cite vllm/v1/metrics/stats.py:477-478}}, {{cite vllm/v1/engine/async_llm.py:883-885}}). That is after ZMQ, before detokenization and before the SSE write.
  3. ITL: the difference between the EngineCoreOutputs.timestamp values of two outputs. These are time.monotonic() values from the engine core process ({{cite vllm/v1/engine/__init__.py:295-297}}).

A client measures TTFT from its own send time to the first content chunk. Its value is larger: it adds the network, the HTTP parse, the work before arrival_time (model check, _preflight), the detokenization and the SSE write. Remember also that the first SSE chunk only has the role; the first text comes in the same RequestOutput (stop 16). The page {{link learn/serving-metrics}} defines the metrics, and {{link concepts/metrics-and-observability}} lists the Prometheus names.

The stats exist only when log_stats is true. disable_log_stats is False by default ({{cite vllm/engine/arg_utils.py:624}}).

With --tensor-parallel-size 2, the world size is 2, so the executor is "mp" on one node ({{cite vllm/config/parallel.py:1055-1096}}). Each GPU gets its own worker process. Stops 1 to 10 and 14 to 16 do not change. Stop 11 changes: the engine core does not call the worker directly. MultiprocExecutor.execute_model sends the call to all workers through a shared-memory message queue (rpc_broadcast_mq.enqueue, {{cite vllm/v1/executor/multiproc_executor.py:342-353}}, {{cite vllm/v1/executor/multiproc_executor.py:428}}). Only one worker replies, the first TP rank of the last PP stage ({{cite vllm/v1/executor/multiproc_executor.py:549-560}}). The workers exchange activations with all-reduce inside the forward pass ({{term tensor-parallel | tensor parallelism}}). The tour {{link tours/multi-gpu-step}} follows this path.

With --data-parallel-size 2, there are two engine core processes, one per DP rank. The front end then uses DPLBAsyncMPClient (internal load balancing) or DPAsyncMPClient (external load balancer) ({{cite vllm/v1/engine/core_client.py:158-169}}). For each new request, DPLBAsyncMPClient picks the engine with the lowest score. The score is the larger of two counts: waiting plus running requests, and the in-flight requests of this client. Waiting requests add a penalty when the KV cache usage is above 50% ({{cite vllm/v1/engine/core_client.py:1763-1789}}). An X-data-parallel-rank header can force a rank ({{cite vllm/entrypoints/generate/base/serving.py:215-227}}). For a dense model the DP ranks are independent. For an MoE model the engine core is a DPEngineCoreProc, which keeps the ranks in step ({{cite vllm/v1/engine/core.py:1537-1547}}). See {{link concepts/data-parallel-serving}} and {{link tours/multi-gpu-step}}.

By default api_server_count is the DP size with internal load balancing. It is the local DP size with hybrid load balancing, and 1 with an external load balancer ({{cite vllm/entrypoints/cli/serve.py:113-130}}). With more than one, run_multi_api_server starts several front-end processes that share one listen socket with reuse_port ({{cite vllm/entrypoints/cli/serve.py:269}}, {{cite vllm/entrypoints/cli/serve.py:298}}). So stops 1 to 6 and 15 to 16 run in one of N processes. The engine core opens one input socket and one output socket for each front end ({{cite vllm/v1/engine/core.py:1936-1943}}, {{cite vllm/v1/engine/core.py:2047-2052}}). It sends each output to the socket of the client that sent the request: client_index selects the socket ({{cite vllm/v1/engine/core.py:2089-2091}}). So each front end detokenizes only its own requests, and N processes share this work.

The client can close the connection at any time. Two mechanisms find out:

  1. Before the route returns, with_cancellation runs the handler and listen_for_disconnect as two tasks and cancels the other when one ends ({{cite vllm/entrypoints/serve/utils/api_utils.py:93-109}}).
  2. After the route returns a StreamingResponse, the response itself listens for the disconnect. The docstring of with_cancellation says this ({{cite vllm/entrypoints/serve/utils/api_utils.py:85-87}}). The stream generator is then stopped.

When the stream stops, AsyncLLM.generate() gets CancelledError or GeneratorExit and calls abort(q.request_id, internal=True) ({{cite vllm/v1/engine/async_llm.py:807-812}}). abort removes the request from the output processor and sends ABORT to the engine core ({{cite vllm/v1/engine/async_llm.py:948-956}}, {{cite vllm/v1/engine/core_client.py:1338-1340}}). In the engine core, abort_requests calls finish_requests(..., FINISHED_ABORTED), which frees the blocks ({{cite vllm/v1/engine/core.py:554-560}}). The engine core also checks aborts_queue before each update_from_output, so an abort that arrives during the forward pass acts at once ({{cite vllm/v1/engine/core.py:780-782}}).

The exact way Starlette stops the generator (a cancelled task, or a closed generator) is Starlette code and is not in this repository. Both cases reach the same except branch in generate().

What can go wrong

A streaming response starts before the engine sees the request (stop 2). Clients must read the error chunks in the stream, not only the status code ({{cite vllm/entrypoints/openai/chat_completion/serving.py:937-943}}, {{cite vllm/entrypoints/openai/chat_completion/serving.py:497-503}}).
  • Slow first token under load. The new request waits in the waiting queue until running requests leave room in the token budget and the KV cache (stop 10). Watch the waiting count and the cache usage; see {{link concepts/tuning}}.
  • A long prompt delays all streams. With chunked prefill, a long prompt takes a large part of the token budget for several steps. Every running request then gets its next token later. long_prefill_token_threshold limits the tokens of one prompt per step ({{cite vllm/v1/core/sched/scheduler.py:764-765}}).
  • Preemption. When blocks run out, the scheduler preempts a running request and computes it again later ({{cite vllm/v1/core/sched/scheduler.py:850-858}}). The stream of that request pauses.
  • Chat template timeout. A very slow template fails after VLLM_CHAT_TEMPLATE_RENDER_TIMEOUT seconds (default 30, {{cite vllm/renderers/hf.py:1044-1056}}).
  • Prompt too long. HTTP 400 "This model's maximum context length is ... tokens. However, your prompt contains ... input tokens" ({{cite vllm/renderers/params.py:524-538}}).
  • Busy front end. One front end does rendering, detokenization and JSON for all streams in one event loop. At high load it can be the bottleneck; more API servers share this work (Deep dive).

Why it matters. Most questions about a slow or broken stream start with "which stop is it?". A slow first token is often a scheduling question (stop 10). A slow stream with a fast GPU can be the front end (stops 15 and 16). A missing token can be a stop-string question (stop 15). With the map of this tour you can open the right file at once.

In which process does the chat template run, and in which thread?

In the API server process (the front end), in a thread pool. HfRenderer wraps safe_apply_chat_template with make_async(..., executor=self._executor) ({{cite vllm/renderers/hf.py:1011-1013}}). So the template does not block the asyncio event loop.

 Which two objects cross the ZMQ sockets, and how are they encoded?

EngineCoreRequest goes from the front end to the engine core, and EngineCoreOutputs comes back. Both are msgspec structs with array_like=True, encoded as msgpack ({{cite vllm/v1/engine/__init__.py:113-118}}, {{cite vllm/v1/engine/__init__.py:266-271}}, {{cite vllm/v1/engine/core_client.py:731-732}}).

 The client gets HTTP 200, but the stream holds only an error and data: [DONE]. How can this happen?

The route returns the StreamingResponse before AsyncLLM.generate() runs, because engine_client.generate(...) only makes an async generator (stop 2). The status line is already sent when the request reaches the engine. Later errors become data: chunks, followed by data: [DONE] ({{cite vllm/entrypoints/openai/chat_completion/serving.py:937-943}}, {{cite vllm/entrypoints/openai/chat_completion/serving.py:497-508}}).

 With async scheduling, how can the scheduler schedule the next decode step of our request before it knows the token of the current step? And where does the model runner get that token?

AsyncScheduler adds a placeholder per token in flight (num_output_placeholders, {{cite vllm/v1/core/sched/async_scheduler.py:45-47}}). The running pass computes num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens, which is 1 ({{cite vllm/v1/core/sched/scheduler.py:759-763}}). The model runner reads the real token from req_states.last_sampled_tokens on the GPU in combine_sampled_and_draft_tokens ({{cite vllm/v1/worker/gpu/model_runner.py:1493-1500}}). postprocess_sampled wrote it there in the step before ({{cite vllm/v1/worker/gpu/model_runner.py:1715-1726}}).

 A user measures TTFT in the client as 180 ms, but the vLLM TTFT metric says 120 ms. Name three parts of the 60 ms that the vLLM metric does not include.

The vLLM metric starts at arrival_time = time.time() in render_chat_async ({{cite vllm/renderers/base.py:1380}}) and ends when the output handler makes IterationStats for the batch with the first token ({{cite vllm/v1/metrics/stats.py:525}}, {{cite vllm/v1/engine/async_llm.py:883-885}}). It leaves out the network and the HTTP parse before the route, and the model check before rendering. It also leaves out the work after that moment: detokenization (stop 15), the JSON and the SSE write (stop 16), and the network.
