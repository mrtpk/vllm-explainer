Purpose

vllm/model_executor/models/registry.py maps an architecture name from config.json to a model class, and tells the rest of vLLM what that class supports, without an import of the model in the front end.

Filevllm/model_executor/models/registry.py, 1,623 lines of Python. About 820 lines are data tables (lines 73-887).
Main objectsModelRegistry, the one _ModelRegistry object ({{cite vllm/model_executor/models/registry.py:1565}}); classes _ModelInfo, _RegisteredModel, _LazyRegisteredModel, _ModelRegistry.
Runs inEvery process that imports it. In vllm serve: the {{term front-end}} inspects (in ModelConfig); each {{term worker}} resolves and imports the class; plugins call register_model everywhere. The file is also a script: python -m vllm.model_executor.models.registry is the inspection subprocess.
Called byModelConfig through its registry property ({{cite vllm/config/model.py:1165-1168}}), the model loader ({{cite vllm/model_executor/model_loader/utils.py:310}}), the speculative config for draft models ({{cite vllm/config/speculative.py:1779}}), some platform and KV-planning code, and general plugins through from vllm import ModelRegistry ({{cite vllm/__init__.py:26}}).
CallsThe detector functions of interfaces.py and interfaces_base.py ({{cite vllm/model_executor/models/registry.py:47-69}}), importlib, subprocess with cloudpickle, transformers (Transformers backend checks), safe_hash, current_platform.verify_model_arch.
Not in this fileThe model classes, the capability protocols (interfaces.py, page {{link concepts/model-interfaces}}), the conversion adapters for --convert (adapters.py), and the plugin loader.

The page {{link concepts/oot-models}} explains the registry from the user's side, with a plugin example. This page reads the file section by section.

Who calls it

  • Front end, config time. ModelConfig.__post_init__ asks is_text_generation_model and is_pooling_model, then calls inspect_model_cls and stores the record ({{cite vllm/config/model.py:703-744}}). PP and HC-SP checks call is_pp_supported_model and is_hc_sp_supported_model ({{cite vllm/config/model.py:1552}}, {{cite vllm/config/model.py:1570}}).
  • Worker, model build. _get_model_architecture calls resolve_model_cls ({{cite vllm/model_executor/model_loader/utils.py:305-313}}).
  • Other readers. The CPU platform ({{cite vllm/platforms/cpu.py:66}}), the Mamba page-size code of Platform ({{cite vllm/platforms/interface.py:1043}}) and model-owned KV cache grouping ({{cite vllm/v1/core/kv_cache_planning.py:1677}}).
  • Plugins. register_model and get_supported_archs ({{cite tests/plugins/vllm_add_dummy_model/vllm_add_dummy_model/__init__.py:11-12}}).

Walk through the main methods

_LazyRegisteredModel: the disk cache

  1. Line 997. The directory is $VLLM_CACHE_ROOT/modelinfos.
  2. Lines 1000-1001. The file name is module-Class.json with every dot replaced by "-".
  3. Lines 1005-1009. For a package __init__.py, all .py files below the package are hashed, sorted; else only the one file.
  4. Lines 1014-1020. The hash takes the relative path, a zero byte, the file bytes and a zero byte, for each file. safe_hash is md5, or sha256 where md5 is not allowed ({{cite vllm/utils/hashing.py:118-121}}).
  5. Lines 1036-1042. A different hash means "stale": DEBUG log, None.
  6. Line 1045. A hit rebuilds _ModelInfo from the JSON dict. Any other error also returns None with a DEBUG log (lines 1046-1052).

The save writes {"hash": ..., "modelinfo": asdict(mi)} through atomic_writer, and only logs an exception on failure ({{cite vllm/model_executor/models/registry.py:1054-1069}}). The method that uses both is inspect_model_cls ({{cite vllm/model_executor/models/registry.py:1071-1118}}), walked on {{link concepts/oot-models}}.

_try_inspect_model_cls: the error filter

  1. Lines 1125, 1140. lru_cache(maxsize=128) keyed by (name, entry). Entries are frozen dataclasses, so they are hashable and compare by value. A new registration with another target is a new key; the same module and class strings give an equal key.
  2. Line 1132. Before an import, the platform may reject the architecture.
  3. Lines 1135-1137, 1147-1149. Any exception is logged with its traceback ("Error in loading/inspecting model architecture"), and the result is None. The caller then tries the next step of the lookup.

resolve_model_cls: the worker's lookup

  1. Lines 1414-1425. transformers or terratorch implementation first.
  2. Lines 1427-1437. Transformers fallback when no name is registered and no conversion is set.
  3. Lines 1439-1443. Each name, normalized; the first class that imports wins. The returned name is the original one, not the normalized one.
  4. Lines 1445-1454. The fallback again, without the conversion condition.
  5. Line 1456. _raise_for_unsupported.

inspect_model_cls (lines 1351-1402) is the same with _try_inspect_model_cls, except one detail: for terratorch it asserts that inspection worked (line 1370).

_raise_for_unsupported: four messages

The order matters: a registered name that failed always gets "failed to be inspected" (lines 1208-1212), even when it is also in a removed-models table. The last message lists all supported names, so it can be long (lines 1233-1236).

How many names does the built-in registry hold at this commit, and what kind of entry is each?

406 names in _VLLM_MODELS (derived count). Each becomes a _LazyRegisteredModel ({{cite vllm/model_executor/models/registry.py:1565-1573}}).

 Why does _try_inspect_model_cls return None instead of raising?

So that the lookup can try the next step (another name, or the Transformers fallback). The exception is logged with its traceback ({{cite vllm/model_executor/models/registry.py:1141-1150}}); if all steps fail, _raise_for_unsupported raises "failed to be inspected" for a registered name.

 What is the cache file name for vllm.models.deepseek_v4:DeepseekV4ForCausalLM, and what does its hash cover?

vllm-models-deepseek_v4-DeepseekV4ForCausalLM.json ({{cite vllm/model_executor/models/registry.py:999-1001}}). The source is the package __init__.py, so the hash covers every .py file under vllm/models/deepseek_v4/ ({{cite vllm/model_executor/models/registry.py:1005-1009}}).

 Config says ["MyForSequenceClassification"], only MyForCausalLM is registered, and the user passes --convert classify. Which class do the workers build?

The Transformers fallback before the loop is skipped because a conversion is set ({{cite vllm/model_executor/models/registry.py:1427-1437}}). In the loop, _normalize_arch matches the suffix ForSequenceClassification and finds MyForCausalLM ({{cite vllm/model_executor/models/registry.py:1335-1347}}). The loader then wraps it with as_seq_cls_model ({{cite vllm/model_executor/model_loader/utils.py:331-333}}).
