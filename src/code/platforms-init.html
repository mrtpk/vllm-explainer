Purpose

vllm/platforms/__init__.py decides which Platform subclass a process uses, and gives the one object of that class to the rest of vLLM as current_platform.

Filevllm/platforms/__init__.py, 346 lines of Python. Ten functions (five of them detectors), the dict builtin_platform_plugins and two module globals.
Main functionsresolve_current_platform_cls_qualname ({{cite vllm/platforms/__init__.py:240}}), __getattr__ ({{cite vllm/platforms/__init__.py:303}}), and the detectors tpu_platform_plugin, cuda_platform_plugin, rocm_platform_plugin, xpu_platform_plugin, cpu_platform_plugin. There is no class: the classes are in interface.py, cuda.py, rocm.py and the other files of the folder.
Runs inEvery Python process of vLLM, on the CPU, in the thread of the first reader of current_platform. With vllm serve: the {{term front-end}}, the {{term engine-core}} process, each {{term worker}} process and the model registry subprocess.
Called byAny module that reads current_platform: 584 files in vllm/ use the name (from git grep at this commit). The first such read in a process runs the detection.
Callsload_plugins_by_group for vllm.platform_plugins ({{cite vllm/platforms/__init__.py:10}}), resolve_obj_by_qualname ({{cite vllm/platforms/__init__.py:11}}), hardware libraries inside the detectors (pynvml, amdsmi, libtpu, torch), and envs.VLLM_TARGET_DEVICE.
Not in this fileThe Platform base class and UnspecifiedPlatform (interface.py, page {{link code/platforms-interface}}), the vendor classes, and the plugin loader (vllm/plugins/__init__.py, page {{link code/plugins-init}}).

The page {{link concepts/platform-plugins}} explains the detection from the reader's side, with a worked example. This page reads the file from top to bottom.

Where it sits

The file has three layers. At the bottom are the five detectors (lines 33-228). In the middle, resolve_current_platform_cls_qualname runs them and the out-of-tree detectors, and picks one name (lines 240-293). At the top, __getattr__ turns the name into the one object, once per process (lines 303-326).

Who calls it

  • Every reader of current_platform. Most files import it at module level, for example vllm/engine/arg_utils.py ({{cite vllm/engine/arg_utils.py:122}}) and vllm/config/compilation.py ({{cite vllm/config/compilation.py:22}}). The first import in a process runs __getattr__ and the detection. The page {{link concepts/plugin-loading#deep-dive}} traces this first import in each process of vllm serve.
  • Platform classes. cuda.py and the other vendor files import Platform and PlatformEnum from .interface ({{cite vllm/platforms/cuda.py:33}}). This file re-exports them ({{cite vllm/platforms/__init__.py:13}}, {{cite vllm/platforms/__init__.py:339-346}}), so an out-of-tree platform can write from vllm.platforms import Platform without a detection.
  • Tests. A test reads _init_trace to report the first read ({{cite tests/plugins_tests/test_platform_plugins.py:28-34}}). Another test calls resolve_current_platform_cls_qualname and _is_amd_zen_cpu directly ({{cite tests/test_zen_cpu_platform_detection.py:12-14}}).

What it calls

  • load_plugins_by_group(PLATFORM_PLUGINS_GROUP): imports the out-of-tree detectors, filtered by VLLM_PLUGINS ({{cite vllm/platforms/__init__.py:250}}).
  • resolve_obj_by_qualname: imports the chosen class from its dotted name ({{cite vllm/platforms/__init__.py:319}}, {{cite vllm/utils/import_utils.py:119-123}}).
  • Hardware probes inside the detectors: pynvml through import_pynvml ({{cite vllm/platforms/__init__.py:61-64}}), amdsmi ({{cite vllm/platforms/__init__.py:112-116}}), libtpu ({{cite vllm/platforms/__init__.py:48}}), torch.xpu ({{cite vllm/platforms/__init__.py:156}}), /proc/cpuinfo and zentorch ({{cite vllm/platforms/__init__.py:165-171}}, {{cite vllm/platforms/__init__.py:205-212}}).
  • importlib.metadata.version("vllm"), to see if this is a CPU build ({{cite vllm/platforms/__init__.py:18-30}}).
  • The standard logging module through logging.getLogger(__name__) ({{cite vllm/platforms/__init__.py:15}}), not vLLM's init_logger.

Walk through the main methods

cuda_platform_plugin: a detector with error rules

  1. Lines 63-64. Import pynvml and start NVML. This does not start a CUDA context.
  2. Lines 71-74. CUDA is active when NVML counts at least one GPU and the vLLM version does not contain "cpu". The comment (lines 66-70) gives the reason: a CPU build of vLLM on a GPU host must not pick CUDA.
  3. Line 84. nvmlShutdown runs in a finally block.
  4. Lines 87-89. An exception whose class name does not contain "nvml" is raised again. The caller catches it and logs it at DEBUG level ({{cite vllm/platforms/__init__.py:260-265}}).
  5. Lines 94-101. An NVML error on a Jetson (one of two Tegra files exists) still gives CUDA.
  6. Line 105. The result is a dotted class name or None. vllm.platforms.cuda.CudaPlatform is itself an alias that cuda.py sets to the NVML or the non-NVML class ({{cite vllm/platforms/cuda.py:1040-1054}}).

cpu_platform_plugin: three ways to say CPU

  1. Line 176. VLLM_TARGET_DEVICE == "cpu" is enough.
  2. Line 184. Else a vLLM version string with "cpu" (a CPU build).
  3. Line 193. Else macOS (sys.platform starts with darwin).
  4. Lines 202-203. None of these: None.

The rest of the function (lines 205-228) returns ZenCpuPlatform on an AMD CPU with AVX-512 when zentorch imports. An ImportError falls back to CpuPlatform with a DEBUG log; an OSError (a build that does not match torch) falls back with a WARNING ({{cite vllm/platforms/__init__.py:205-228}}).

resolve_current_platform_cls_qualname: the decision

  1. Line 250. The out-of-tree detectors, as a dict from entry-point name to function. Lines 240-248 before it return early for VLLM_TARGET_DEVICE=cpu.
  2. Lines 254-259. chain runs the built-in dict first, then the plugin dict. A name is active when its function returns a value that is not None.
  3. Lines 267-270. Set intersections split the active names. A plugin with the same name as a built-in one (for example cuda) would count in both sets. (Derived from the set logic; no test covers it.)
  4. Lines 272-279. Out-of-tree first: two or more raise; one is called again and wins.
  5. Lines 280-289. Then built-in: two or more raise; one is called again and wins.
  6. Line 291. The fallback name of UnspecifiedPlatform.

__getattr__: the lazy object

  1. Line 304. Only the name current_platform gets the special path.
  2. Lines 317-321. First read: detect, import the class, call it with no arguments, keep the object, and keep the stack in _init_trace. Later reads return the same object.
  3. Lines 323-324. Other names that exist in the module globals are returned as they are.
  4. Line 326. Unknown names raise AttributeError, as a normal module does.

Note the name format: a detector returns module.Class with dots only, because resolve_obj_by_qualname splits at the last dot ({{cite vllm/utils/import_utils.py:121}}). The "module:Class" form of register_model does not work here.

The file has no lock. __getattr__ checks _current_platform is None and then assigns it (lines 317-319), so two threads that read the name for the first time at the same moment could both run the detection. In vllm serve the first read happens during imports, before vLLM starts its threads. (Derived; the code has no comment about threads.)

Each process has its own _current_platform. With the spawn start method ({{cite vllm/entrypoints/common/startup.py:147-149}}), each child starts with None and detects again. With fork, a child would get a copy of the parent's object, if the parent had made it. (Derived from the semantics of fork.)

The function named __setattr__. PEP 562 lets a module define __getattr__ and __dir__. It does not add __setattr__, so Python does not call the function at lines 329-336 when code assigns vllm.platforms.current_platform = x. The assignment makes a normal module attribute, and later reads find it without __getattr__. _current_platform keeps its old value. (Derived from Python semantics; no comment in the code says why the function exists.)

vLLM makes such an assignment once. For vllm bench, the CLI replaces an UnspecifiedPlatform with a CpuPlatform object ({{cite vllm/entrypoints/cli/main.py:72-86}}). The rule above applies to it: the function at lines 329-336 does not run.

A CI job installs a CPU wheel of vLLM, whose version is for example "0.x.y+cpu", on a host with 4 NVIDIA GPUs and pynvml installed. VLLM_TARGET_DEVICE is not set, so its value is "cuda" ({{cite vllm/envs.py:622}}). (The version string is an example.)

  1. No short-circuit: the value is not cpu (line 244).
  2. tpu: import libtpu fails → None, DEBUG log.
  3. cuda: NVML counts 4 GPUs, but the version contains "cpu", so is_cuda is False → None (lines 71-74, 77-80).
  4. rocm, xpu: None.
  5. cpu: the version contains "cpu" → "vllm.platforms.cpu.CpuPlatform" (lines 184-189).
  6. One built-in name is active → cpu_platform_plugin() runs again, DEBUG log "Automatically detected platform cpu." (lines 285-289).

The comment at lines 241-243 describes the case that the short-circuit is for: CPU-only jobs that reuse an accelerator wheel. There, VLLM_TARGET_DEVICE=cpu makes the CPU detector answer (line 176). The CUDA detector answers too, because the version has no "cpu". Without the short-circuit, lines 280-284 would raise RuntimeError. (Derived.)

Which function returns the dotted class name of the platform, and which code makes the object?

resolve_current_platform_cls_qualname() returns the name ({{cite vllm/platforms/__init__.py:240-293}}). The module __getattr__ imports the class and calls it once per process ({{cite vllm/platforms/__init__.py:318-319}}).

 A CPU build of vLLM runs on a GPU host. Why does the CUDA detector not answer?

It answers only when NVML counts GPUs and vllm_version_matches_substr("cpu") is false ({{cite vllm/platforms/__init__.py:71-74}}). A CPU build has "cpu" in its version, so the detector returns None, and the CPU detector answers ({{cite vllm/platforms/__init__.py:184}}).

 An out-of-tree plugin object in vllm.platform_plugins is a string, not a function. What happens?

assert callable(func) fails inside the try block, so the loop logs it at DEBUG level and treats it as not active ({{cite vllm/platforms/__init__.py:255-265}}). Detection goes on with the other detectors.

 A test runs vllm.platforms.current_platform = MyPlatform(). Does _current_platform change, and what do modules that imported current_platform earlier see?

No. Python does not call a module-level __setattr__ (PEP 562 covers only __getattr__ and __dir__), so the function at {{cite vllm/platforms/__init__.py:329-336}} does not run. The assignment makes a normal module attribute; new reads of vllm.platforms.current_platform get MyPlatform(). Modules that ran from vllm.platforms import current_platform before keep their own reference to the old object. (Derived from Python semantics; see the deep dive.)
