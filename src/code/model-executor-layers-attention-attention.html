Purpose

vllm/model_executor/layers/attention/attention.py is the bridge between a model file and an attention backend: the model calls Attention, and this file finds the per-step data and calls the backend's impl.

Where it sits

Who calls it

  • Model files build one Attention per decoder layer and call self.attn(q, k, v) ({{link concepts/model-definition}}).
  • The runner reads the layers from the static dict to build the KV cache spec and the attention groups ({{cite vllm/v1/worker/gpu/attn_utils.py:228-234}}).
  • The compiled graph calls torch.ops.vllm.unified_kv_cache_update and torch.ops.vllm.unified_attention_with_output as opaque nodes.

What it calls

  • get_attn_backend in its constructor ({{cite vllm/model_executor/layers/attention/attention.py:349-360}}); see {{link concepts/attention-backend-selection}}.
  • impl_cls(...) of the backend ({{cite vllm/model_executor/layers/attention/attention.py:419-432}}).
  • resolve_quant_method for KV cache scales ({{cite vllm/model_executor/layers/attention/attention.py:194-198}}).
  • get_forward_context() inside get_attention_context ({{cite vllm/model_executor/layers/attention/attention.py:705}}).

Walk through the main methods

Attention.__init__: data type and backend

  1. Lines 276-279. The KV cache dtype comes from --kv-cache-dtype, else "auto".
  2. Lines 287-291. A checkpoint with an FP8 kv_cache_scheme turns "auto" into "fp8". The comment says this case "is normally resolved upstream".
  3. Lines 294-297. A scheme with strategy == "attn_head" needs per-head scales; the selector checks backend support for it.

Then the constructor stores the head counts and asserts that num_heads divides by num_kv_heads ({{cite vllm/model_executor/layers/attention/attention.py:327-338}}). It selects the backend unless the caller passed one (lines 349-362). It rejects options the backend cannot do, for example use_alibi_sqrt ({{cite vllm/model_executor/layers/attention/attention.py:363-370}}).

Attention.__init__: impl, registration, placeholder

  1. Lines 419-432. The impl gets ten positional arguments plus backend extras.
  2. Line 440. use_direct_call is false on CUDA, ROCm, CPU and XPU, which want the opaque op.
  3. Lines 443-445. Register in static_forward_context by prefix; a duplicate raises.
  4. Lines 448-453. Validate a KV sharing target.
  5. Line 464. An empty placeholder until the runner binds the real cache view. The comment says the attribute is not read with direct calls; in this file the direct path also reads it, through get_attention_context (lines 553, 716-717).
  6. Line 467. KV cache quantization scales.

Attention.forward

  1. Lines 525-530. Allocate the output: [num_tokens, num_heads × head_size_v] unless the model gives a shape.
  2. Lines 533-540. Reshape q, k and v to [tokens, heads, head_size] outside the op, "to minimize the CPU overheads from the non-CUDA-graph regions".
  3. Lines 542-552. The direct-call path; the cache write runs only if the backend does not write in its forward and the layer does not share another layer's cache.
  4. Lines 553-560. The attention call. The opaque path (lines 561-580) is the same with torch.ops.vllm.* and an encoded name.

get_kv_cache_spec

A normal decoder layer returns a FullAttentionSpec with the current block size, per-rank KV heads, head sizes and the KV dtype. Encoder and encoder-only layers return None: they keep no KV cache ({{cite vllm/model_executor/layers/attention/attention.py:616-617}}). A sliding-window layer returns a SlidingWindowSpec and may choose its own block size ({{cite vllm/model_executor/layers/attention/attention.py:620-670}}); see {{link concepts/hybrid-kv-cache}}.

get_attention_context and the two ops

  1. Lines 767-768. Two decorators: @eager_break_during_capture makes the op a break point of breakable CUDA graphs; @maybe_transfer_kv_layer adds the KV connector's per-layer load and save. The breakable decorator must be outermost ({{cite vllm/compilation/breakable_cudagraph.py:82-96}}).
  2. Line 782. The dummy dependency is dropped; it only ordered the ops.
  3. Line 784. One lookup gives metadata, layer, KV cache (the slot mapping is not needed here).
  4. Lines 786-796. The impl call; the result lands in output.
  5. Lines 799-803. Registration: mutates_args=["output", "output_block_scale"] tells the compiler which inputs change.

get_attention_context itself is explained line by line on {{link concepts/forward-context}} (Step 5).

What does Attention.forward return, and where is the attention result written first?

It returns output.view(-1, hidden_size) ({{cite vllm/model_executor/layers/attention/attention.py:581}}). The impl writes into the output tensor that forward allocated, because the op mutates output ({{cite vllm/model_executor/layers/attention/attention.py:799-803}}).

 When does Attention.forward skip the cache write op?

When the backend writes the cache inside its own forward (forward_includes_kv_cache_update), when the layer shares another layer's cache, or when key or value is None ({{cite vllm/model_executor/layers/attention/attention.py:564-572}}).

 Which decorator must be outermost on unified_attention_with_output, and why?

@eager_break_during_capture. The KV connector's wait and save calls in @maybe_transfer_kv_layer must run in the eager segment; inside a captured graph they would hang on replay ({{cite vllm/compilation/breakable_cudagraph.py:82-96}}).
