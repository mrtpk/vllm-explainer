Purpose

vllm/v1/core/kv_cache_utils.py is the toolbox under the {{term block-pool}} and the single-type managers. It holds data types, the hash chain, and small helpers for the start-up of the engine core.

Where it sits

Who calls it

  • EngineCore resolves the block sizes, makes the hasher, and logs the capacity ({{cite vllm/v1/engine/core.py:57-65}}, {{cite vllm/v1/engine/core.py:173-175}}, {{cite vllm/v1/engine/core.py:216-225}}, {{cite vllm/v1/engine/core.py:324-354}}).
  • Request calls the hasher in its constructor and after each new token ({{cite vllm/v1/request.py:225-230}}, {{cite vllm/v1/request.py:285-288}}).
  • BlockPool makes all KVCacheBlocks and the free queue, and uses the hash-key helpers ({{cite vllm/v1/core/block_pool.py:16-29}}, {{cite vllm/v1/core/block_pool.py:172-178}}).
  • The single-type managers use resolve_block_hashes, BlockHashListWithBlockSize and trim_null_head ({{cite vllm/v1/core/single_type_kv_cache_manager.py:13-20}}).
  • The workers use KVCacheBlockCopy for copy-on-write ({{cite vllm/v1/worker/utils.py:30}}). A P2P offload tier reads the NONE_HASH seed ({{cite vllm/v1/kv_offload/tiering/p2p/manager.py:714}}).

What it calls

  • xxhash and xxhash_cbor, only to know which hash functions are not cryptographic ({{cite vllm/v1/core/kv_cache_utils.py:110-111}}).
  • get_mm_features_in_window to find the first image that touches a block ({{cite vllm/v1/core/kv_cache_utils.py:976-983}}).
  • KVCacheSpecRegistry.get_manager_class to check if every group supports fine-grained hits ({{cite vllm/v1/core/kv_cache_utils.py:936-942}}).
  • envs.VLLM_KV_EVENTS_USE_INT_BLOCK_HASHES for the hash format of KV events ({{cite vllm/v1/core/kv_cache_utils.py:82-85}}).

Walk through the main methods

KVCacheBlock: one record per block

  1. Line 161. slots=True: no __dict__ per block. A large GPU has tens of thousands of these objects.
  2. Lines 166-168. The id indexes the KV tensors of every worker. ref_cnt counts the requests that hold the block.
  3. Lines 170-172. The pool of the block. A deferred free can hold blocks of two pools (the GPU pool and a HiSparse host pool).
  4. Lines 175-178. The hash key, set only when the block is cached. _block_hash_num_tokens is the prefix length that the key covers. It can end inside a block for fine-grained (partial) entries.
  5. Lines 182-183. The two links of the free queue. Only FreeKVCacheBlockQueue changes them.
  6. Line 186. is_null marks block 0, the {{term null-block}}.
  7. Lines 201-203. A second hash on the same block is a bug, so the method asserts. BlockPool calls reset_hash() first on eviction.

FreeKVCacheBlockQueue: O(1) remove from the middle

A Python deque cannot remove an element from the middle in O(1). A prefix-cache hit on a free block must do exactly that. So the queue links the blocks themselves, with two fake ends that are never popped:

  1. Lines 285-289. At start-up the queue links the blocks in id order: block 0, 1, 2, ...
  2. Lines 297-305. Fake head and tail blocks with id −1. Every real block in the queue then has a previous and a next block, so no method needs a special case for the ends.
  3. Lines 400-403. remove() on a block that is not in the queue raises RuntimeError: a caller bug.
  4. Lines 406-412. Two pointer changes and a counter: O(1). BlockPool.touch() uses it for hits ({{cite vllm/v1/core/block_pool.py:766-767}}).

popleft_n() takes n blocks from the front, prepend_n() puts blocks at the front, and append_n() at the back ({{cite vllm/v1/core/kv_cache_utils.py:347-389}}, {{cite vllm/v1/core/kv_cache_utils.py:438-484}}). None of them makes a Python object; they only change the links (docstring, {{cite vllm/v1/core/kv_cache_utils.py:258-279}}).

get_request_block_hasher: the chain for one request

The engine core makes the closure once ({{cite vllm/v1/engine/core.py:223-225}}). The basics page reads it line by line ({{link learn/prefix-caching}}, deep dive "The hash chain in the code"). The key points:

It starts after the last existing hash and stops before a block that is not full ({{cite vllm/v1/core/kv_cache_utils.py:988-993}}). It returns only the new hashes; Request.update_block_hashes() appends them ({{cite vllm/v1/request.py:285-288}}).

resolve_kv_cache_block_sizes: three sizes for several groups

  1. Lines 840-858. One group: both sizes are the block size (times the decode context parallel size when the cache is sharded). Another prefix_match_unit raises ValueError when hashing is active.
  2. Lines 860-863. Several groups: the scheduler works in units of the least common multiple of the group block sizes.
  3. Lines 871-873. No prefix caching and no connector: nobody reads the hashes, so the hash size equals the scheduler size.

Otherwise the hash size is prefix_match_unit, or the greatest common divisor of the prefix-cacheable group sizes. Every such group size must divide by it ({{cite vllm/v1/core/kv_cache_utils.py:885-898}}). The engine core passes both sizes to the scheduler ({{cite vllm/v1/engine/core.py:173-185}}).

A pool of 6 blocks (ids 0-5), prefix caching on. (Derived from the methods above and {{cite vllm/v1/core/block_pool.py:172-188}}.)

  1. FreeKVCacheBlockQueue([b0..b5]): head ⇄ 0 ⇄ 1 ⇄ 2 ⇄ 3 ⇄ 4 ⇄ 5 ⇄ tail, num_free_blocks = 6.
  2. The pool pops block 0 as the null block: head ⇄ 1 ⇄ 2 ⇄ 3 ⇄ 4 ⇄ 5 ⇄ tail, 5 free.
  3. A request of 40 tokens with block size 16 takes 3 blocks with popleft_n(3): blocks 1, 2, 3. Queue: 4 ⇄ 5. The links of 1, 2 and 3 are None.
  4. Blocks 1 and 2 are full and get hashes; block 3 has 8 tokens.
  5. The request ends. The pool frees [3, 2, 1]: prepend_n([3]), then append_n([2, 1]). Queue: 3 ⇄ 4 ⇄ 5 ⇄ 2 ⇄ 1.
  6. A new request hits h0: remove(block 1) links 2 to the tail. Queue: 3 ⇄ 4 ⇄ 5 ⇄ 2.

Assume a hybrid model with a full-attention group of block size 16 and a sliding-window group of block size 32. Prefix caching is on, there is no decode context parallelism, and --prefix-match-unit is unset. (Derived from {{cite vllm/v1/core/kv_cache_utils.py:860-918}}.)

  1. group_block_sizes = [16, 32], so scheduler_block_size = lcm(16, 32) = 32.
  2. Both groups are prefix-cacheable: hash_block_size = gcd(16, 32) = 16. 16 and 32 both divide by 16, so no error.
  3. The request hasher makes one hash per 16 tokens. The sliding-window group reads them through BlockHashListWithBlockSize(scale_factor=2): its hash i is fine hash 2i + 1.
  4. The log shows "kv cache group sizes (16, 32)" and "kv lcm block sizes 32" ({{cite vllm/v1/core/kv_cache_utils.py:865-866}}).

Why does vLLM implement its own linked list instead of using collections.deque for free blocks?

A prefix-cache hit must take a block out of the middle of the free queue. The linked list does this in O(1), a deque does not ({{cite vllm/v1/core/kv_cache_utils.py:258-266}}, {{cite vllm/v1/core/kv_cache_utils.py:391-412}}).

 How many bytes is one key of the prefix-cache map with the default hash algorithm, and what are its parts?

36 bytes: the 32-byte SHA-256 digest of the block plus the KV cache group id as 4 big-endian bytes ({{cite vllm/v1/core/kv_cache_utils.py:60-69}}, {{cite vllm/utils/hashing.py:40-41}}).

 A request has 47 tokens and 2 hashes (block size 16). It gets one more token. What does the hasher return?

One new hash. It starts at 2 × 16 = 32 tokens; 32 + 16 = 48 ≤ 48, so block 2 is full now ({{cite vllm/v1/core/kv_cache_utils.py:967-972}}, {{cite vllm/v1/core/kv_cache_utils.py:989-1008}}). The request appends it to block_hashes ({{cite vllm/v1/request.py:285-288}}).

 Look at the deep dive "Worked example: block sizes for two groups". Why is the hash of sliding-window block 1 the fine hash 3, not a new hash of tokens 32-63?

Each fine hash chains over its whole prefix, so fine hash 3 (tokens 48-63) already names tokens 0-63. That is exactly the prefix of sliding-window block 1. The view returns block_hashes[(idx + 1) × scale_factor − 1] = block_hashes[3] ({{cite vllm/v1/core/kv_cache_utils.py:1178-1181}}).
