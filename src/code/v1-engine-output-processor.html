It keeps one RequestState per request, detokenizes incrementally, checks stop strings, collects logprobs, merges n > 1 children and feeds the per-request collectors. ---

Purpose

vllm/v1/engine/output_processor.py turns the token ids that come back from the engine core into {{term request-output | RequestOutputs}} with text. It is the only place in the front end that loops over all outputs of a step.

The docstring of process_outputs states the design rule: "vLLM V1 minimizes the number of python loops over the full batch ... This is the only function that should loop over EngineCoreOutputs" ({{cite vllm/v1/engine/output_processor.py:746-753}}).

Where it sits

The engine core client gives the output handler one EngineCoreOutputs per step. The handler passes slices of its outputs list to process_outputs. For each entry, the output processor finds the {{term request-state}}, updates it, and puts a RequestOutput into the collector of the request. The generate() task of the request takes it from there. The diagram on {{link concepts/engine-client#the-picture}} shows this path.

Who calls it

  • AsyncLLM.__init__ makes one OutputProcessor with the tokenizer, log_stats and the server-wide stream_interval ({{cite vllm/v1/engine/async_llm.py:180-186}}).
  • AsyncLLM._add_request calls add_request before it sends the request ({{cite vllm/v1/engine/async_llm.py:581}}). add_request makes the collector first ({{cite vllm/v1/engine/async_llm.py:529}}).
  • The output handler calls process_outputs per slice and update_scheduler_stats per message; on an error it calls propagate_error ({{cite vllm/v1/engine/async_llm.py:905-910}}, {{cite vllm/v1/engine/async_llm.py:924}}, {{cite vllm/v1/engine/async_llm.py:944}}).
  • AsyncLLM.abort calls abort_requests ({{cite vllm/v1/engine/async_llm.py:955}}).
  • AsyncLLM.check_admission reads get_num_unfinished_requests and get_num_queued_tokens ({{cite vllm/v1/engine/async_llm.py:319-323}}).

What it calls

  • IncrementalDetokenizer.from_new_request: a fast detokenizer with a tokenizers DecodeStream, a slow Python one, or a no-op one when there is no tokenizer. detokenize=False removes the tokenizer for the request ({{cite vllm/v1/engine/detokenizer.py:49-66}}, {{cite vllm/v1/engine/output_processor.py:297-298}}).
  • LogprobsProcessor.from_new_request and update_from_output ({{cite vllm/v1/engine/logprobs.py:46-71}}, {{cite vllm/v1/engine/logprobs.py:360-366}}).
  • ParentRequest.get_outputs for n > 1 ({{cite vllm/v1/engine/parallel_sampling.py:102-128}}).
  • IterationStats.update_from_output and update_from_finished_request for metrics ({{cite vllm/v1/engine/output_processor.py:1003-1047}}).

Walk through the main methods

process_outputs, part 1: find the state, update stats

  1. Lines 759-762. No state means the request was aborted, or finished on a stop string, in the front end. The output is ignored.
  2. Lines 764-772. An output with error set means the engine rejected the request on arrival, for example a paused engine. The collector gets the exception.
  3. Lines 775-777. Timing stats, only when iteration_stats exists (stats on).
  4. Lines 790-800. The first output ends the prefill. Its prefill_stats give the number of prompt tokens that came from the prefix cache.

process_outputs, part 2: detokenize, logprobs, output

  1. Lines 824-827. The detokenizer appends the new ids and returns a matched stop string or None. The second argument is true when the engine stopped the request with STOP: EOS or a stop token id.
  2. Lines 828-833. A stop string sets the finish reason to STOP, with the string as stop_reason, and trims surplus tokens.
  3. Line 842. Sample and prompt logprobs, if the request asked for them.
  4. Lines 849-857. make_request_output can return None: in FINAL_ONLY mode before the end, or between two stream intervals.
  5. Lines 861-866. AsyncLLM: into the collector. LLMEngine: into the returned list.

process_outputs, part 3: free finished requests

  1. Line 877. _finish_request removes the state, the id mapping and, for the last child, the parent ({{cite vllm/v1/engine/output_processor.py:917-932}}).
  2. Lines 878-882. If the engine core did not finish the request itself (a stop string), its id goes to reqs_to_abort. The output handler sends these aborts after each slice ({{cite vllm/v1/engine/async_llm.py:918-922}}).
  3. Lines 885-889. Finished-request stats and an optional trace span.

make_request_output: is an output due?

  1. Lines 367-369. FINAL_ONLY (a request without stream) gets one output, at the end.
  2. Lines 379-392. With stream_interval > 1, an output goes out only at the end, for the first token, or after stream_interval new tokens.
  3. Lines 394-400. In that case the DELTA output carries all tokens since the last sent one.
  4. Line 402. The output uses the external id, the one the client knows.
  5. Lines 406-412. A child of an n > 1 request asks its parent which outputs to send, and uses the parent's external id.

Incremental detokenization and stop strings

  1. Lines 107-111. When the engine stopped the request on EOS or a stop token, the last token is not decoded, unless include_stop_str_in_output is set. So the final chunk of a chat stream has empty content.
  2. Lines 116-124. Each new id gives the next piece of text through decode_next. With stop strings, token_offsets records the text length after each token.
  3. Lines 126-128. The skipped stop token still counts as an output token.
  1. Line 134. Stop strings count only after min_tokens output tokens.
  2. Line 136. The new text starts at the first token after min_tokens.
  3. Lines 137-142. check_stop_strings searches the new text plus up to (stop string length − 1) characters before it. So it finds a stop string that two tokens complete. It picks the stop string that ends first ({{cite vllm/v1/engine/detokenizer.py:336-361}}).
  4. Lines 150-153. Tokens after the token that completed the stop string are dropped, and the text is cut.

The fast detokenizer primes a DecodeStream with the prompt ids, so the first output token decodes in context ({{cite vllm/v1/engine/detokenizer.py:191-198}}). The text that a stream may send is shorter than the decoded text by stop_buffer_length = the longest stop string minus 1. This holds back a stop string that is only partly generated ({{cite vllm/v1/engine/detokenizer.py:85-90}}, {{cite vllm/v1/engine/detokenizer.py:161-176}}).

n > 1: the parent request

  1. Lines 108-115. A finished child leaves child_requests. A second finished output of the same child is not sent again.
  2. Lines 117-121. Streaming: each child's output goes out as it comes, with its own index.
  3. Lines 122-125. FINAL_ONLY: the parent collects all n outputs and sends them together when the last child finishes.
  4. Line 127. The parent is finished when no child is left.

A request has stop=["END"], include_stop_str_in_output=False, min_tokens=0 and a stream (DELTA). So stop_buffer_length = 3 − 1 = 2. The tokens are illustrative.

The client receives "The answer " without "END". In step 4, engine_core_output.finished is false, because the engine core did not stop the request. So the request goes to reqs_to_abort, and the engine core gets an ABORT ({{cite vllm/v1/engine/output_processor.py:878-882}}). The arithmetic follows {{cite vllm/v1/engine/detokenizer.py:132-153}}, {{cite vllm/v1/engine/detokenizer.py:161-176}} and {{cite vllm/v1/engine/detokenizer.py:351-373}}.

Real tokenizers split text in other places. The fast detokenizer can also return an empty string for a token that is only part of a multi-byte character; the text then appears with the next token.
  • The engine core sends logprobs as arrays: for each new token, the token ids, the logprobs and the ranks of the top candidates ({{cite vllm/v1/outputs.py:34-45}}). The sampled token comes first ({{cite vllm/v1/engine/logprobs.py:110-111}}).
  • _update_sample_logprobs adds the sampled token's logprob to cumulative_logprob and decodes each candidate token on its own, not incrementally ({{cite vllm/v1/engine/logprobs.py:89-122}}).
  • A decoded candidate that ends with the replacement character "�" is corrected with the sampled context, because it can be part of a multi-byte character ({{cite vllm/v1/engine/logprobs.py:341-358}}).
  • In DELTA mode, each CompletionOutput carries only the logprobs of its new tokens ({{cite vllm/v1/engine/output_processor.py:492-498}}). Prompt logprobs are sent once and then forgotten ({{cite vllm/v1/engine/output_processor.py:449-454}}).

abort_requests accepts both kinds of id ({{cite vllm/v1/engine/output_processor.py:599-661}}):

  1. With internal=True, each id is an internal id, or the id of a parent request. The code removes it from the external-to-internal map.
  2. With internal=False, each id is an external id. All internal ids that share it are aborted. This is how one external id can stop several requests.
  3. For each internal id with a state, the code removes the state and puts a final output with finish_reason=ABORT into the collector. So a waiting generate() ends cleanly.
  4. For a parent id, it aborts all children first.
  5. It returns the internal ids, which the caller sends to the engine core.

A client-disconnect abort skips the finished-request stats: abort_requests does not call _update_stats_from_finished.

The output processor has no lock. All its methods run on the event loop of one API server process: add_request and abort_requests in request tasks, process_outputs in the output handler task. They do not run in parallel, because asyncio runs one task at a time, and these methods do not await. (Derived from the code: none of the methods is async.)

The CPU cost of this file grows with the number of output tokens per step: one detokenizer step per token, plus logprobs work. That cost is why the output handler cuts large steps into slices ({{cite vllm/v1/engine/async_llm.py:887-893}}).

Where are stop strings checked, and why not in the engine core?

In the front end, in the detokenizer that the output processor calls ({{cite vllm/v1/engine/output_processor.py:825-833}}). The engine core works with token ids only and has no text; EngineCoreOutput carries new_token_ids ({{cite vllm/v1/engine/__init__.py:209-210}}).

 A request has stream_interval 4 on a server with the default 1. Which tokens make a new RequestOutput?

The first token, then each time 4 new tokens are ready, and the last one. The request value is clamped up to at least the server value, so 4 applies ({{cite vllm/v1/engine/output_processor.py:300-302}}). The rule is at {{cite vllm/v1/engine/output_processor.py:379-392}}.

 A request with n = 2 and no stream finishes child 1 before child 0. When does the client get an output?

Only when child 0 finishes too. In FINAL_ONLY mode the parent stores each final output and returns all of them when no child is left ({{cite vllm/v1/engine/parallel_sampling.py:122-128}}).

 The stop strings are ["END", "STOP"], without include_stop_str_in_output. How many characters does the stream hold back, and why?

3: the longest stop string has 4 characters, minus 1 ({{cite vllm/v1/engine/detokenizer.py:87-88}}). The last 3 characters could be the start of "STOP", so the stream must not send them before the next token decides. When the request finishes, the buffer is 0 and the rest goes out ({{cite vllm/v1/engine/detokenizer.py:165}}).
