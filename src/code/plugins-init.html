Purpose

vllm/plugins/__init__.py finds the {{term plugin | plugins}} that other Python packages publish as {{term entry-point | entry points}}, filters them with VLLM_PLUGINS, and imports them for the code that asks.

Filevllm/plugins/__init__.py, 159 lines of Python. Five group-name constants, one flag and three functions.
Main functionsload_plugins_by_group ({{cite vllm/plugins/__init__.py:36}}), load_general_plugins ({{cite vllm/plugins/__init__.py:77}}), load_endpoint_plugins ({{cite vllm/plugins/__init__.py:93}}). There is no class.
Runs inEvery process of vllm serve: the API server (the {{term front-end}}), the {{term engine-core}} process, each {{term worker}} process, and the model registry subprocess (only when it starts). With one GPU, the worker runs inside the engine core process. The code runs on the CPU, in the thread of the caller.
Called byNine call sites in vllm/: the engine arguments, EngineCore, the worker wrapper, the model registry, the platform detection, the stat loggers, the IO processor loader and the endpoint plugin wiring (see below).
Callsimportlib.metadata.entry_points, envs.VLLM_PLUGINS, EntryPoint.load(), and the loaded plugin functions or factories.
Not in this fileThe platform detection rules (vllm/platforms/__init__.py), the stat logger type check (vllm/v1/metrics/loggers.py), the IO processor choice (vllm/plugins/io_processors/__init__.py), the route wiring of endpoint plugins (vllm/plugins/endpoint_plugins/interface.py), and the group vllm.logits_processors.

The file only finds, filters and imports. Each caller decides what to do with the loaded objects. The page {{link concepts/plugin-loading}} explains the same code from the view of the processes. This page reads the file line by line.

Who calls it

load_general_plugins() has five callers in vllm/:

  • AsyncEngineArgs.add_cli_args in the front end, before the CLI parser gets its flags. The comment says that a plugin can add a choice to --quantization or --device ({{cite vllm/engine/arg_utils.py:3240-3243}}).
  • EngineArgs.__post_init__, again in the front end, and also for the offline LLM class, which builds no CLI parser ({{cite vllm/engine/arg_utils.py:921-924}}). The same file also imports the function at module level ({{cite vllm/engine/arg_utils.py:123}}).
  • EngineCore.__init__ in the engine core process, before it makes the executor ({{cite vllm/v1/engine/core.py:129-132}}, {{cite vllm/v1/engine/core.py:147}}).
  • WorkerWrapperBase.init_worker in each worker, before it resolves worker_cls ({{cite vllm/v1/worker/worker_base.py:282-284}}, {{cite vllm/v1/worker/worker_base.py:292-296}}).
  • _run() of the model registry subprocess, before it runs the function that the parent process sent ({{cite vllm/model_executor/models/registry.py:1608-1616}}). vLLM starts this subprocess only when it cannot use the cached model information: the cache has no valid entry, or vLLM cannot find the source file of the model ({{cite vllm/model_executor/models/registry.py:1086-1109}}). This is true for built-in models too, because every built-in model is a lazy registry entry ({{cite vllm/model_executor/models/registry.py:1565-1573}}).

load_plugins_by_group() has three callers outside this file. Each one imports the group constant from this file:

  • Platform detection. resolve_current_platform_cls_qualname() loads vllm.platform_plugins ({{cite vllm/platforms/__init__.py:10}}, {{cite vllm/platforms/__init__.py:250}}). It runs on the first read of {{term platform | current_platform}} in a process ({{cite vllm/platforms/__init__.py:316-319}}). With VLLM_TARGET_DEVICE=cpu, the function returns the CPU platform before it loads any platform plugin ({{cite vllm/platforms/__init__.py:244-248}}).
  • Stat loggers. load_stat_logger_plugin_factories() loads vllm.stat_logger_plugins ({{cite vllm/v1/metrics/loggers.py:84-98}}). AsyncLLM.__init__ calls it ({{cite vllm/v1/engine/async_llm.py:155-156}}).
  • IO processors. get_io_processor() loads vllm.io_processor_plugins, but only when a plugin name comes from the model config (io_processor_plugin) or from the Hugging Face config of the model ({{cite vllm/plugins/io_processors/__init__.py:42-61}}). The pooling serving code calls it ({{cite vllm/entrypoints/pooling/pooling/io_processor.py:51-55}}).

load_endpoint_plugins() has one caller: attach_endpoint_plugins() ({{cite vllm/plugins/endpoint_plugins/interface.py:106-108}}). build_app calls that function after the core routes ({{cite vllm/entrypoints/launchers/app.py:45-51}}).

Tests also call the loaders. For example, a test resets the flag plugins_loaded by hand, so that load_general_plugins() runs again ({{cite tests/v1/kv_connector/unit/test_scheduler_kv_connector_override.py:113-119}}).

What it calls

  • importlib.metadata.entry_points(group=...), imported inside the functions ({{cite vllm/plugins/__init__.py:38}}, {{cite vllm/plugins/__init__.py:120}}).
  • vllm.envs for VLLM_PLUGINS ({{cite vllm/plugins/__init__.py:8}}, {{cite vllm/plugins/__init__.py:40}}, {{cite vllm/plugins/__init__.py:122}}).
  • EntryPoint.load(), which imports the module of the plugin ({{cite vllm/plugins/__init__.py:69}}).
  • The plugin objects: each general plugin function ({{cite vllm/plugins/__init__.py:89-90}}) and each endpoint plugin factory ({{cite vllm/plugins/__init__.py:138}}).
  • The standard logging module. The file uses logging.getLogger(__name__) ({{cite vllm/plugins/__init__.py:14}}), not vLLM's init_logger, which adds helper methods to the same kind of logger ({{cite vllm/logger.py:328-335}}).

The subfolders of vllm/plugins/

Three subfolders hold plugin code that vLLM itself ships. The page {{link concepts/frontend-plugins}} explains how to write such plugins.

  • lora_resolvers/: two {{term general-plugin | general plugins}} that vLLM publishes in its own pyproject.toml ({{cite pyproject.toml:45-47}}). Each one registers a {{term lora-resolver}}. register_filesystem_resolver registers a resolver only when VLLM_LORA_RESOLVER_CACHE_DIR is set ({{cite vllm/plugins/lora_resolvers/filesystem_resolver.py:49-61}}). The resolver accepts a folder when its adapter_config.json has peft_type LORA and the same base model ({{cite vllm/plugins/lora_resolvers/filesystem_resolver.py:30-45}}). register_hf_hub_resolver registers a resolver for Hugging Face repositories only when VLLM_LORA_RESOLVER_HF_REPO_LIST is set and VLLM_PLUGINS names lora_hf_hub_resolver ({{cite vllm/plugins/lora_resolvers/hf_hub_resolver.py:131-145}}). OpenAIServingModels in the API server gets the registered resolvers ({{cite vllm/entrypoints/openai/models/serving.py:113-117}}).
  • io_processors/: the abstract class IOProcessor ({{cite vllm/plugins/io_processors/interface.py:18-24}}), with the abstract methods pre_process and post_process ({{cite vllm/plugins/io_processors/interface.py:41-65}}), and the loader get_io_processor(). An {{term io-processor-plugin}} changes the input and the output of a pooling model. The model config can name the plugin in io_processor_plugin ({{cite vllm/config/model.py:410}}).
  • endpoint_plugins/: the protocol EndpointPlugin ({{cite vllm/plugins/endpoint_plugins/interface.py:49-94}}) and the two wiring phases. Phase A, attach_endpoint_plugins(), adds the routes of each {{term endpoint-plugin}} to the FastAPI app ({{cite vllm/plugins/endpoint_plugins/interface.py:97-146}}). Phase B, init_endpoint_plugins_state(), calls init_state of each plugin ({{cite vllm/plugins/endpoint_plugins/interface.py:149-164}}). init_app_state runs Phase B ({{cite vllm/entrypoints/launchers/api_server/app_state.py:173}}). The render server runs it too, with no engine client ({{cite vllm/entrypoints/launchers/render/app_state.py:124}}).

Walk through the main methods

load_plugins_by_group: find, filter, import

  1. Line 38. The import of entry_points is inside the function, so it runs only on a call.
  2. Line 40. envs.VLLM_PLUGINS is None when the variable is not set, else the value split at commas ({{cite vllm/envs.py:1163-1167}}).
  3. Lines 42-45. entry_points(group=group) returns the entry points of all installed packages in the group. No entry points: a DEBUG log and an empty dict.
  4. Lines 48-50. The log level is DEBUG for vllm.general_plugins and INFO for every other group. The comment on line 47 does not match the code: the check is only for the group name.
  5. Lines 52-60. The function logs each found plugin as name -> value. When the allowlist is not set, it also logs that it loads all plugins.
  6. Lines 63-66. A plugin passes when there is no allowlist, or when its entry-point name is in the list. The test is an exact string match. With an allowlist, line 66 logs "Loading plugin" for each name that passes. A name that does not pass gets no such line.
  7. Lines 68-72. plugin.load() imports the module and gets the attribute. An exception is logged with its traceback, and the loop continues.
  8. Line 74. The result maps the entry-point name to the loaded object. The function does not call the objects.

load_general_plugins: once per process

Line 85 sets plugins_loaded = True before line 90 calls the first plugin function. If a plugin function raises and some code catches the exception, the next call in the same process returns at once. The remaining plugin functions then never run in that process. (Derived from lines 83-90.)
  1. Lines 78-80. The docstring warns that plugins can load many times, in different processes. So a plugin function must be safe to run again.
  2. Lines 82-85. The guard. The first call sets the module global; each later call in the same process returns at once.
  3. Line 87. The shared loader gets the functions of vllm.general_plugins, filtered by VLLM_PLUGINS.
  4. Lines 89-90. Each function runs with no arguments and no try block. An exception goes up to the caller, for example EngineCore.__init__.

load_endpoint_plugins: opt-in only

The docstring gives the reason for a stricter rule: endpoint plugins add HTTP routes, so a plugin loads only when VLLM_PLUGINS names it ({{cite vllm/plugins/__init__.py:98-103}}).

  1. Lines 122-131. VLLM_PLUGINS not set: the function still lists the group. If it finds plugins, it logs a WARNING with their names. Then it returns an empty list. So an endpoint plugin never loads by accident.
  2. Line 133. VLLM_PLUGINS set: the shared loader imports the named entry points. An empty string gives [""], which matches no name ({{cite vllm/plugins/__init__.py:105-109}}).
  3. Lines 136-141. Each factory runs with no arguments. If it raises, the function logs the error and skips the plugin.
  4. Lines 143-154. The task gate. required_tasks = None means "always eligible". Otherwise, the plugin needs at least one task in common with supported_tasks. If the caller gives supported_tasks = None, every plugin with tasks is skipped. A skip writes an INFO log.
  5. Lines 156-159. The function logs each loaded plugin and returns them in the order of discovery.

The docstring of EndpointPlugin.name says that the name is used "for VLLM_PLUGINS allowlisting" ({{cite vllm/plugins/endpoint_plugins/interface.py:58-59}}). In the code, the allowlist checks the entry-point name (line 64), and the logs use the same entry-point name (lines 140, 148, 156). No code in vllm/ reads EndpointPlugin.name: the loader and the wiring in interface.py use only required_tasks, attach_router() and init_state(). Use the same string in both places to avoid confusion. (Derived from the lines above.)

The platform comes first. In the processes of vllm serve, the platform plugins load before the general plugins. A module-level from vllm.platforms import current_platform calls the module __getattr__ and resolves the platform at import time ({{cite vllm/platforms/__init__.py:303-319}}). The package vllm.config has such an import: it imports vllm.config.compilation ({{cite vllm/config/__init__.py:7}}), which has the import ({{cite vllm/config/compilation.py:22}}). Each process imports vllm.config or vllm.platforms before it calls load_general_plugins():

  • The front end: arg_utils.py imports current_platform at module level ({{cite vllm/engine/arg_utils.py:122}}).
  • The engine core process: the package vllm.v1.engine imports vllm.config.kv_events ({{cite vllm/v1/engine/__init__.py:14}}). Python runs this package file before core.py, which also imports vllm.config ({{cite vllm/v1/engine/core.py:24}}).
  • A worker process: the package vllm.v1.executor imports abstract.py, which imports vllm.config ({{cite vllm/v1/executor/__init__.py:3}}, {{cite vllm/v1/executor/abstract.py:11}}). multiproc_executor.py also imports current_platform ({{cite vllm/v1/executor/multiproc_executor.py:46}}).

So a general plugin cannot change which platform vLLM detects. (Derived from the imports above.)

envs.VLLM_PLUGINS is read again on each access until enable_envs_cache() runs. After that, the value is cached ({{cite vllm/envs.py:2291-2298}}, {{cite vllm/envs.py:2308-2326}}). Only the engine core and the multiproc workers call enable_envs_cache() ({{cite vllm/v1/engine/core.py:243}}, {{cite vllm/v1/executor/multiproc_executor.py:710}}). The front end never calls it. The docstring says that the cache starts "after service initialization" ({{cite vllm/envs.py:2313-2315}}). So change VLLM_PLUGINS only before you start vLLM.

Assume this machine has vLLM and two more packages. Package acme_hw publishes acme = acme_hw:detect in vllm.platform_plugins. Package acme_routes publishes acme_admin = acme_routes:make in vllm.endpoint_plugins, with required_tasks = None. vLLM publishes lora_filesystem_resolver and lora_hf_hub_resolver in vllm.general_plugins ({{cite pyproject.toml:45-47}}). The names acme... are examples, not real packages.

Case 1: VLLM_PLUGINS is not set.

  1. General plugins: both vLLM functions run (line 64 passes every name). The filesystem resolver registers only if VLLM_LORA_RESOLVER_CACHE_DIR is set ({{cite vllm/plugins/lora_resolvers/filesystem_resolver.py:51-59}}). The Hugging Face resolver checks the allowlist itself: VLLM_PLUGINS is None, so it does not register. If VLLM_LORA_RESOLVER_HF_REPO_LIST is set, it logs a warning ({{cite vllm/plugins/lora_resolvers/hf_hub_resolver.py:131-142}}).
  2. Platform plugins: acme loads, and the platform code calls detect() ({{cite vllm/platforms/__init__.py:254-259}}).
  3. Endpoint plugins: none load. The log shows a WARNING with ['acme_admin'] ({{cite vllm/plugins/__init__.py:122-131}}).

Case 2: VLLM_PLUGINS=acme,acme_admin. The parsed value is ["acme", "acme_admin"].

  1. General plugins: line 64 rejects both vLLM names, so load_plugins_by_group returns {}, and no LoRA resolver registers. No error and no warning appears. The only log lines for this group are at DEBUG level (lines 50-54), and the default log level is INFO ({{cite vllm/envs.py:860}}).
  2. Platform plugins: acme loads, as before.
  3. Endpoint plugins: acme_admin loads, make() runs, and with required_tasks = None the plugin is kept. The log shows "Loaded endpoint plugin acme_admin" ({{cite vllm/plugins/__init__.py:156}}).

To keep the filesystem LoRA resolver in case 2, add its name: VLLM_PLUGINS=acme,acme_admin,lora_filesystem_resolver. (Derived from lines 63-64 and {{cite vllm/envs.py:1166}}. The code does not strip spaces, so do not put a space after a comma.)

Which function in this file calls the plugin functions, and which function only imports them?

load_general_plugins() calls each function ({{cite vllm/plugins/__init__.py:89-90}}). load_plugins_by_group() only imports the objects and returns a dict ({{cite vllm/plugins/__init__.py:68-74}}). The caller decides what to do with them.

 You install an endpoint plugin and do not set VLLM_PLUGINS. Does the route appear?

No. load_endpoint_plugins() returns an empty list and logs a warning with the plugin names ({{cite vllm/plugins/__init__.py:122-131}}). Endpoint plugins load only when VLLM_PLUGINS names them.

 A general plugin function raises KeyError. A test catches the exception and calls load_general_plugins() again in the same process. Do the other general plugins run?

No. Line 85 sets plugins_loaded = True before the loop, so the second call returns at once ({{cite vllm/plugins/__init__.py:83-85}}). The functions after the failed one never run in that process. To load again, code must reset the flag by hand, as a test does ({{cite tests/v1/kv_connector/unit/test_scheduler_kv_connector_override.py:113-119}}).

 An endpoint plugin has required_tasks = ("embed",). The server supports only ("generate",). What happens, and at which log level?

The factory runs, but the sets {"embed"} and {"generate"} have nothing in common. So the function skips the plugin with an INFO log ({{cite vllm/plugins/__init__.py:143-154}}). A test checks the same rule with the two tasks swapped ({{cite tests/plugins_tests/test_endpoint_plugins.py:129-140}}).

 You set VLLM_PLUGINS=acme,acme_admin to enable your platform and endpoint plugins, and VLLM_LORA_RESOLVER_CACHE_DIR=/loras. Requests for an unknown adapter in /loras now fail. Why, and what is the fix?

VLLM_PLUGINS is one allowlist for every group that goes through load_plugins_by_group(), the general plugins too. The name lora_filesystem_resolver is not in it, so line 64 skips vLLM's own general plugin, and register_filesystem_resolver never runs ({{cite vllm/plugins/__init__.py:63-64}}, {{cite pyproject.toml:46}}). No resolver registers, and nothing logs an error. Add the name: VLLM_PLUGINS=acme,acme_admin,lora_filesystem_resolver. This is the worked example in the deep dive.
