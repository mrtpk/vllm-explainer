Purpose

vllm/v1/core/sched/scheduler.py decides, once per {{term engine-step}}, which requests run and how many tokens each gets, and it applies the results of each step to the requests.

schedule: an overview

The method is about 1,000 lines. The deep dive below reads it in parts. In short:

  1. Set the two budgets: token_budget and input_budget ({{cite vllm/v1/core/sched/scheduler.py:642-648}}).
  2. Running pass: tokens, blocks, preemption ({{cite vllm/v1/core/sched/scheduler.py:713-943}}).
  3. Waiting pass, only without preemption ({{cite vllm/v1/core/sched/scheduler.py:956-1479}}).
  4. Checks, the SchedulerOutput, connector metadata ({{cite vllm/v1/core/sched/scheduler.py:1481-1634}}).
  5. _update_after_schedule ({{cite vllm/v1/core/sched/scheduler.py:1641-1643}}).

_update_after_schedule: the counters move

  1. Lines 1704-1712. The comment gives the reason for the order: the output must carry the old counts, and the counters move now so that a prefill can continue in the next step at once.
  2. Lines 1716-1717. num_computed_tokens moves forward optimistically; num_in_flight_tokens remembers what is not confirmed.
  3. Lines 1721-1723. A prefill chunk is a request that still misses tokens after this step.
  4. Lines 1734-1735. New sets, not clear(): the output that just left still points to the old sets.

update_from_output: an overview

For each request in num_scheduled_tokens, the method:

  1. skips requests that finished during the step (for example, aborted) ({{cite vllm/v1/core/sched/scheduler.py:2184-2192}});
  2. rolls back rejected draft tokens ({{cite vllm/v1/core/sched/scheduler.py:2203-2221}});
  3. appends the new tokens and checks for a stop ({{cite vllm/v1/core/sched/scheduler.py:2258-2262}});
  4. lets the grammar accept the tokens ({{cite vllm/v1/core/sched/scheduler.py:2279-2290}});
  5. frees stopped requests and makes an EngineCoreOutput when there is something to send ({{cite vllm/v1/core/sched/scheduler.py:2293-2295}}, {{cite vllm/v1/core/sched/scheduler.py:2316-2341}}).

After the loop it removes stopped requests from the queues, fails requests with errors, updates the connectors, publishes KV events and attaches the stats ({{cite vllm/v1/core/sched/scheduler.py:2388-2523}}).

_update_request_with_output: append and stop

  1. Line 2599. Each token is appended alone; the request updates its block hashes ({{cite vllm/v1/request.py:272-283}}).
  2. Line 2603. check_stop runs after every token, so a stop in the middle of several accepted tokens is found ({{cite vllm/v1/core/sched/utils.py:98-140}}).
  3. Lines 2607-2609. Tokens after the stop are cut, and num_computed_tokens drops by their number.

AsyncScheduler overrides this method: it removes the placeholders of the new tokens and caches the full blocks ({{cite vllm/v1/core/sched/async_scheduler.py:59-80}}).

add_request and finish_requests

A new request goes into the waiting queue (or into kv_holding_waiting when it already holds blocks) and into the requests dict ({{cite vllm/v1/core/sched/scheduler.py:2556-2562}}). Its QUEUED event is recorded only when stats are on.

finish_requests handles aborts from outside. It removes the requests from all queues at once, sets the finished status, and frees them ({{cite vllm/v1/core/sched/scheduler.py:2776-2812}}). With None it finishes every request. A request that waits for a remote KV load may keep its blocks until the load ends (lines 2802-2807).

In which process and thread does Scheduler.schedule() run?

In the engine core process, in its main thread, called by the step function of the busy loop ({{cite vllm/v1/engine/core.py:725}}). There is one scheduler per engine core.

 Why does _update_after_schedule run after the SchedulerOutput is built, and not before?

The output must carry the counts from before the step, so that the worker knows which input ids and positions to use. The comment at {{cite vllm/v1/core/sched/scheduler.py:1704-1712}} gives this reason. The call is the last line of schedule() ({{cite vllm/v1/core/sched/scheduler.py:1641-1643}}).

 A request samples 3 tokens in one step (2 accepted drafts and a bonus token). The second token is EOS. What does update_from_output send?

Two tokens. _update_request_with_output runs check_stop after each token, finds EOS at the second, and cuts the list there ({{cite vllm/v1/core/sched/scheduler.py:2598-2610}}). The request is freed and the output carries finish_reason stop.

 With the priority policy, the victim of a preemption was already scheduled earlier in the same running pass. What does the scheduler undo?

It removes the victim from scheduled_running_reqs, gives its tokens back to token_budget and input_budget (with the draft slots), drops its new blocks and draft tokens from the plan, and restores the encoder budget. It also moves req_index back when the victim was before the current request ({{cite vllm/v1/core/sched/scheduler.py:864-888}}). With FCFS this cannot happen, because the victim is the last request.
