Local readers share a lock-free ring of chunks in /dev/shm with one flag byte per reader; large messages and remote readers use ZMQ XPUB sockets. The executor uses it to send every call to its workers, and each worker uses one to reply. ---

Purpose

vllm/distributed/device_communicators/shm_broadcast.py implements the {{term message-queue}}: one process writes a Python object once, and every reader gets a copy. On one node the bytes go through a ring buffer in shared memory, with no lock and no copy per reader; too-large messages and readers on other nodes go through ZMQ.

Where it sits

Who calls it

  • Executor broadcast. On the leader node of a DP rank, MultiprocExecutor makes MessageQueue(world_size, local_world_size, max_chunk_bytes=16 MiB, connect_ip=…) and passes its handle to each worker process ({{cite vllm/v1/executor/multiproc_executor.py:148-172}}). Each call is one enqueue ({{cite vllm/v1/executor/multiproc_executor.py:428}}).
  • Worker side. A worker attaches with create_from_handle(handle, rank) and makes its own reply queue MessageQueue(1, 1) ({{cite vllm/v1/executor/multiproc_executor.py:618-625}}). When a replica spans nodes, the workers use the inner-DP world group's broadcaster and single-reader queues instead ({{cite vllm/v1/executor/multiproc_executor.py:626-645}}).
  • Busy loops. Workers block in dequeue(indefinite=True) ({{cite vllm/v1/executor/multiproc_executor.py:1046}}); the executor reads replies with dequeue(timeout=…) ({{cite vllm/v1/executor/multiproc_executor.py:441}}); a worker replies with enqueue(result) ({{cite vllm/v1/executor/multiproc_executor.py:1011-1012}}).
  • Process groups. A GroupCoordinator that asks for a broadcaster (TP, DCP) makes one with 6 chunks of 4 MiB; broadcast_object then uses it ({{cite vllm/distributed/parallel_state.py:562-567}}, {{cite vllm/distributed/parallel_state.py:864-866}}).

What it calls

  • shared_memory.SharedMemory(create=True, size=…) after a free-space check ({{cite vllm/distributed/device_communicators/shm_broadcast.py:335-343}}).
  • ZMQ sockets: XPUB for overflow and remote readers, PUB/SUB for wake-ups, PAIR for cancellation ({{cite vllm/distributed/device_communicators/shm_broadcast.py:508-542}}, {{cite vllm/distributed/device_communicators/shm_broadcast.py:150-176}}).
  • in_the_same_node_as and broadcast_object_list to spread the handle in a process group ({{cite vllm/distributed/device_communicators/shm_broadcast.py:1068-1148}}).

Walk through the main methods

ShmRingBuffer: layout and the flag rules

The docstring is the specification. Data chunks come first, then max_chunks × (1 + n_reader) flag bytes. The first flag of a chunk is "written"; then one "read" flag per reader ({{cite vllm/distributed/device_communicators/shm_broadcast.py:281-302}}). The four states:

The writer creates the segment and zeroes the flags; a reader attaches by name and patches out Python's resource tracker, so a reader process does not unlink a segment it did not create ({{cite vllm/distributed/device_communicators/shm_broadcast.py:332-365}}).

acquire_write: the writer's side of one chunk

  1. Lines 724-728. A chunk is writable unless it is written and not yet read by all readers.
  2. Lines 733-754. Not writable: yield the CPU and retry. A timeout raises TimeoutError; every VLLM_RINGBUFFER_WARNING_INTERVAL seconds (60) the writer logs "No available shared memory broadcast block found in 60 seconds".
  3. Line 760. Clear "written" first, so no reader starts on a half-written chunk.
  4. Lines 770-784. After the caller wrote: reset all read flags, fence, set "written", fence. The comment explains why this order matters: the other order passes through the "read by some" state.
  5. Line 785. Advance current_idx around the ring.

acquire_read: one reader

  1. Lines 876-882. Wait until the current chunk is written and not yet read by this reader. The wait uses SpinCondition: spin with sched_yield for 1 s after the last read, then sleep on the ZMQ notify socket for at most 5 s at a time before it checks the flags again ({{cite vllm/distributed/device_communicators/shm_broadcast.py:205-219}}, {{cite vllm/distributed/device_communicators/shm_broadcast.py:71}}, {{cite vllm/distributed/device_communicators/shm_broadcast.py:802-817}}).
  2. Lines 888-894. After the caller read, set this reader's flag and fence, so the writer sees it.
  3. Lines 895-897. Advance and record the read time (it controls the spin window).

enqueue: serialize, then write or overflow

  1. Lines 906-914. Out-of-band buffers of 1 MiB or more stay outside the pickle stream; smaller ones go inline.
  2. Lines 922-923. CPU tensors are reduced by _reduce_tensor, so their bytes become such buffers instead of a copy inside the pickle ({{cite vllm/distributed/device_communicators/shm_broadcast.py:433-462}}).
  3. Lines 943-946. If the total does not fit in one chunk, the chunk carries only the overflow flag, and all buffers go over the local XPUB socket.
  4. Lines 952-961. Otherwise the chunk holds: byte 0 = 0, bytes 1-2 = buffer count (big-endian), then each buffer with a 4-byte length.
  5. Line 963. Wake sleeping readers.
  6. Lines 965-966. Remote readers always get the message over the TCP XPUB socket.

dequeue reverses the steps. It copies each out-of-band buffer into a new bytearray, because the ring slot is reused after the read; on overflow it receives from the SUB socket after it releases the chunk ({{cite vllm/distributed/device_communicators/shm_broadcast.py:968-998}}).

create_from_process_group: one queue for a torch group

The writer counts the ranks on its own node with in_the_same_node_as; those become local readers on the ring, and the others remote readers on TCP. It broadcasts the handle over the gloo group; each reader attaches with it, and wait_until_ready runs the start-up handshake.

Each segment size is (max_chunk_bytes + 1 + n_reader) × max_chunks ({{cite vllm/distributed/device_communicators/shm_broadcast.py:326-328}}), and check_shm_free_space raises before it creates one that does not fit ({{cite vllm/distributed/device_communicators/shm_broadcast.py:248-262}}). The comment on the 24 MiB default says it is "large enough to accommodate grammar bitmask tensors for large batches (1024 requests)" ({{cite vllm/distributed/device_communicators/shm_broadcast.py:489-490}}). So a TP = 2 engine asks for about 664 MiB of /dev/shm in total (derived). Docker's default /dev/shm is far smaller; the error text suggests --shm-size or --ipc=host.
  1. The executor calls enqueue(("execute_model", (scheduler_output,), {}, 0)). For a decode step of 64 requests the pickle is small (no tensor of 1 MiB or more), so it fits into one 16 MiB chunk (illustrative size).
  2. acquire_write finds chunk i in state 111 (read by both workers in an earlier step), clears the written flag, and the payload is copied in: [0][count=1][len][pickle bytes].
  3. Flags become 100; the writer sends one byte on the notify PUB socket and moves to chunk i + 1.
  4. Both workers spin in dequeue(indefinite=True). They read within the 1-second spin window, so they see the flag without the socket. Each unpickles its own copy and sets its read flag: 110, then 111.
  5. Worker 0 (the output rank) later replies on its own MessageQueue(1, 1) with (SUCCESS, None); worker 1 replies nothing ({{cite vllm/v1/executor/multiproc_executor.py:1070-1071}}).

A multimodal request with a 30 MiB image tensor would not fit: the chunk gets the overflow flag, and the pickle plus the image buffer travel over the XPUB socket as separate ZMQ frames, without a copy into the pickle stream (derived from {{cite vllm/distributed/device_communicators/shm_broadcast.py:906-946}}).

In which order does the writer update the flags after it writes a chunk, and why?

It resets every read flag first, then sets "written". The other order would pass through "written and read by some", and a reader could skip the new message ({{cite vllm/distributed/device_communicators/shm_broadcast.py:764-780}}).

 A message pickles to 3 MiB and has one 20 MiB tensor buffer. How does it travel through the executor's queue?

The 20 MiB buffer is out of band (≥ 1 MiB). The total, 23 MiB plus framing, does not fit in a 16 MiB chunk, so the chunk only carries the overflow flag and both buffers go over the local XPUB socket ({{cite vllm/distributed/device_communicators/shm_broadcast.py:906-946}}).

 Why does an idle worker not print the "No available shared memory broadcast block" message every 60 seconds?

Workers call dequeue(indefinite=True) ({{cite vllm/v1/executor/multiproc_executor.py:1046}}), and acquire_read turns warnings off when indefinite is true ({{cite vllm/distributed/device_communicators/shm_broadcast.py:876-878}}).

 How much /dev/shm do the queues of one TP = 4 engine core ask for?

Broadcast: 10 × (16 MiB + 5) ≈ 160 MiB. Four reply queues of 10 × (24 MiB + 2) ≈ 240 MiB each = 960 MiB. The TP group broadcaster: 6 × (4 MiB + 4) ≈ 24 MiB. Total about 1,144 MiB (derived from {{cite vllm/distributed/device_communicators/shm_broadcast.py:326-328}}, {{cite vllm/distributed/device_communicators/shm_broadcast.py:489-492}}, {{cite vllm/v1/executor/multiproc_executor.py:152}}, {{cite vllm/distributed/parallel_state.py:564-567}}).
