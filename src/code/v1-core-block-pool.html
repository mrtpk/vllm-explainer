It hands out blocks from the free queue, frees them in eviction order, keeps the hash-to-block map of the prefix cache, emits KV cache events and computes the KV cache usage. ---

Purpose

vllm/v1/core/block_pool.py owns all KVCacheBlock objects of one engine core: which are free, which are in use, and which full blocks can serve a prefix-cache hit.

Who calls it

  • The coordinator builds one pool with kv_cache_config.num_blocks blocks ({{cite vllm/v1/core/kv_cache_coordinator.py:119-125}}).
  • Single-type managers call get_new_blocks, touch, free_blocks, cache_full_blocks and get_cached_block ({{cite vllm/v1/core/single_type_kv_cache_manager.py:303-306}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:406}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:531-539}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:597-598}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:794}}).
  • KVCacheManager reads get_usage and take_events, and calls evict_blocks ({{cite vllm/v1/core/kv_cache_manager.py:234}}, {{cite vllm/v1/core/kv_cache_manager.py:672}}, {{cite vllm/v1/core/kv_cache_manager.py:703}}).
  • The scheduler frees deferred blocks directly ({{cite vllm/v1/core/sched/scheduler.py:2884}}, {{cite vllm/v1/core/sched/scheduler.py:2901}}).

What it calls

  • FreeKVCacheBlockQueue: popleft, popleft_n, remove, prepend_n, append_n ({{cite vllm/v1/core/kv_cache_utils.py:258-484}}).
  • Hash helpers: make_block_hash_with_group_id, resolve_block_hashes, generate_block_hash_extra_keys ({{cite vllm/v1/core/block_pool.py:16-29}}).
  • The event types BlockStored, BlockRemoved, AllBlocksCleared ({{cite vllm/v1/core/block_pool.py:6-12}}).

Walk through the main methods

__init__: all blocks at once, and the null block

  1. Lines 172-174. One KVCacheBlock per id, all made at start-up. A block remembers its pool, because a deferred free can hold blocks of two pools (the GPU pool and a HiSparse host pool) ({{cite vllm/v1/core/kv_cache_utils.py:169-172}}).
  2. Line 178. All blocks start in the free queue, in id order.
  3. Lines 181-182. The prefix-cache map, and a second map for blocks with more than one hash entry.
  4. Lines 187-188. The first block (id 0) leaves the queue and becomes the {{term null-block}}. Its ref_cnt is not kept, so free_blocks skips it ({{cite vllm/v1/core/block_pool.py:790-791}}).

get_new_blocks: take from the front

  1. Lines 678-679. A request for more blocks than are free raises ValueError. Callers count first, so this means a bug.
  2. Line 681. popleft_n: the front of the queue is the eviction end.
  3. Lines 687-691. With prefix caching, a popped block may still hold a hash; _maybe_evict_cached_block removes it from the map and emits BlockRemoved ({{cite vllm/v1/core/block_pool.py:729-750}}). This is the only eviction path in normal serving. Then ref_cnt goes from 0 to 1.

free_blocks: back in eviction order

  1. Lines 790-794. The null block is skipped; a block of another pool goes to its own pool.
  2. Lines 795-802. ref_cnt -= 1. At 0, a block without a hash (or any block with prefix caching off) goes to the "evict first" list; a hashed block to the "evict last" list.
  3. Line 805. prepend_n: unhashed blocks at the front, reused next. The comment names GPU locality as a reason.
  4. Line 807. append_n: cached blocks at the end, in the order given. Callers pass the blocks of a request in reverse, so the tail of a prefix is evicted before its head.

A block that another request still uses keeps ref_cnt > 0 and stays out of the queue.

touch and cache_full_blocks

touch is how a hit takes a block: it removes the block from the middle of the free queue when the block was free (O(1) in the linked list), and adds a reference. cache_full_blocks gives each newly full block its hash key (block hash + group id) and inserts it in the map ({{cite vllm/v1/core/block_pool.py:261-301}}). It skips null blocks and blocks that a mask leaves out, for example sliding-window blocks that can never serve a hit ({{cite vllm/v1/core/block_pool.py:273-278}}).

get_usage: the KV cache usage metric

The null block is left out of the total. Free blocks with a cached prefix count as free. This value becomes vllm:kv_cache_usage_perc ({{link concepts/kv-cache-manager}}, Step 8).

The class uses @dataclass(slots=True), so each block has no __dict__ ({{cite vllm/v1/core/kv_cache_utils.py:161}}). With 27,955 blocks (an 8B model on an 80 GiB GPU, {{link concepts/kv-cache-manager}}), the pool holds 27,955 such objects plus 2 fake queue ends.

Why can two blocks have the same hash? The map does not deduplicate: when a block becomes full, the pool does not look for an identical cached block, so that block ids in the block tables never change ({{cite vllm/v1/core/block_pool.py:48-52}}). Two requests that computed the same block at the same time both keep their own copy.

A pool of 9 blocks (block 0 is null), block size 4, prefix caching on. Free queue at start: 1 2 3 4 5 6 7 8. (Derived from the methods above.)

  1. R1 (10 tokens) gets 3 blocks: get_new_blocks(3) → 1, 2, 3. Queue: 4 5 6 7 8. Blocks 1 and 2 are full: cache_full_blocks sets their hashes.
  2. R2 has the same first 8 tokens and 12 tokens in total. Hit: blocks 1, 2 → touch: ref_cnt 2 each (they were not in the queue). New: 1 block → 4. Queue: 5 6 7 8.
  3. R1 ends after one output token: free_blocks([3, 2, 1]). Block 3 (no hash): ref_cnt 0, to the front. Blocks 2, 1: ref_cnt 1, stay out. Queue: 3 5 6 7 8.
  4. R2 ends after one output token: free_blocks([4, 2, 1]). Block 4 is full (tokens 8-11) and hashed. All three reach 0 and have a hash: append in order 4, 2, 1. Queue: 3 5 6 7 8 4 2 1.
  5. R3 needs 6 blocks: it pops 3, 5, 6, 7, 8, 4. Block 4 loses its hash (eviction). Blocks 2 and 1 survive at the end, so the first 8 tokens are still a possible hit.

With --kv-events-config and enable_kv_cache_events, the pool queues an event for each change of the prefix cache: BlockStored when blocks get hashes ({{cite vllm/v1/core/block_pool.py:303-344}}), BlockRemoved when a hash goes ({{cite vllm/v1/core/block_pool.py:611-624}}), and AllBlocksCleared on a reset ({{cite vllm/v1/core/block_pool.py:867-868}}). The scheduler drains them in update_from_output and publishes one batch per step ({{cite vllm/v1/core/sched/scheduler.py:2469-2484}}). External routers use these events to know which prefixes an engine has cached.

Where does get_new_blocks take blocks from, and what happens to an old hash?

From the front of the free queue with popleft_n ({{cite vllm/v1/core/block_pool.py:681}}). With prefix caching, it removes the old hash of each block from the map: this is the eviction ({{cite vllm/v1/core/block_pool.py:687-691}}, {{cite vllm/v1/core/block_pool.py:729-750}}).

 Why does a freed block without a hash go to the front of the queue, and a block with a hash to the end?

A block without a hash can never be a prefix-cache hit, so reusing it first costs nothing. A hashed block may serve a later hit, so it waits as long as possible (LRU) ({{cite vllm/v1/core/block_pool.py:797-807}}).

 In the worked example of the deep dive, why do blocks 2 and 1 survive R3 while block 4 does not, although all three were freed at the same time?

R2 freed its blocks in reverse order, [4, 2, 1] ({{cite vllm/v1/core/single_type_kv_cache_manager.py:597-598}}). All three had a hash, so append_n added them to the end in that order ({{cite vllm/v1/core/block_pool.py:807}}). Block 4 is nearer the front, so R3 popped it first. The tail of a prefix goes before its head, which keeps the more shareable head longer.
