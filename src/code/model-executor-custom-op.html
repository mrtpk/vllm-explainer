Purpose

vllm/model_executor/custom_op.py gives layers a way to pick a forward method per platform, and gives plugins a way to replace a layer class without a change to the model code.

The page {{link concepts/custom-ops}} explains the ideas, the default switches and the IR ops, with a worked example. This page reads the file from top to bottom.

Where it sits

The file has three layers. At the top are the two registries (lines 16-29). PluggableLayer (lines 32-99) has only the class swap. CustomOp (lines 102-356) has the class swap and the per-platform dispatch.

Who calls it

  • Layer definitions. For example @CustomOp.register("rms_norm") on RMSNorm ({{cite vllm/model_executor/layers/layernorm.py:38-39}}) and @PluggableLayer.register("column_parallel_linear") ({{cite vllm/model_executor/layers/linear.py:434-435}}).
  • Model constructors. They build the layers inside set_current_vllm_config ({{cite vllm/model_executor/model_loader/utils.py:100-101}}). Construction runs __new__ and __init__ of this file.
  • Plugins. @RotaryEmbedding.register_oot in the test platform ({{cite tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/dummy_custom_ops.py:10-11}}).
  • LoRA. maybe_get_oot_by_class(QKVParallelLinear) and similar calls ({{cite vllm/lora/layers/column_parallel_linear.py:448}}).
  • Config check. custom_op_log_check imports op_registry to tell a missing op from an op that is not in the model ({{cite vllm/config/compilation.py:1343-1352}}).

What it calls

  • get_cached_compilation_config(): the current CompilationConfig, cached until the config context changes ({{cite vllm/config/vllm.py:3570-3573}}).
  • current_platform.is_rocm(), is_cpu(), is_tpu(), is_xpu(), is_out_of_tree() ({{cite vllm/model_executor/custom_op.py:194-205}}), and simple_compile_backend ({{cite vllm/model_executor/custom_op.py:230-233}}).
  • maybe_disable_graph_partition: {"graph_partition": False} for Inductor on torch 2.9 or newer ({{cite vllm/model_executor/utils.py:190-194}}).

Walk through the main methods

CustomOp.__new__: the class swap

  1. Lines 108-115. The try block reads cls.__name__. Every Python class has __name__, so the AttributeError branch, with its text about the name attribute, cannot run for a class. (Derived from Python semantics.)
  2. Line 117. The key is the class name of the object that the code builds, for example "RotaryEmbedding". A subclass with another name, such as a scaling variant of rotary embedding, is not swapped (derived).
  3. Lines 120-125. The OOT class is used, with a DEBUG log.
  4. Line 126. The parent __new__ makes an object of the chosen class. Python calls __init__ next only if that object is an instance of the called class, so the OOT class must subclass the in-tree class (general Python rule).

dispatch_forward: the decision

  1. Line 175. The comment above says that vLLM is built for one backend and has no dynamic dispatch. The config comes from the current config context.
  2. Line 183. enforce_enable from __init__ overrides the list. The comment says it exists for the vision encoder of multimodal models and will be removed (lines 177-182).
  3. Lines 184-187. The counters enabled_custom_ops and disabled_custom_ops record self.__class__.name.
  4. Lines 189-192. Disabled: forward_native, compiled only with compile_native=True.
  5. Lines 194-205. Enabled: the first matching platform test wins; CUDA is the final else. An UnspecifiedPlatform therefore gets forward_cuda (derived).

enabled and default_on

  1. Line 273. A class with no name attribute was never registered: WARNING once, and the base mode decides.
  2. Lines 282-289. Both +name and -name: ValueError. CompilationConfig already rejects this earlier ({{cite vllm/config/compilation.py:1027-1034}}).
  3. Line 290. (default_on() or enabled) and not disabled.
  4. Lines 300-305. Exactly one base mode, else ValueError.
  5. Line 307. not count_none > 0 or count_all > 0: true for "all", false for "none".

register_oot: the two working forms

  1. Line 337. The key is name, or the name of the class on which the decorator is called. On CustomOp.register_oot() without name, the key would be "CustomOp" (derived).
  2. Line 338. A duplicate key fails the assert.
  3. Line 339. The OOT class's name becomes the key. The +name switch for it is then +RotaryEmbedding, not the in-tree op name (derived; see {{link concepts/custom-ops}}).
  4. Lines 343-356. None → return the decorator; a class → decorate it now; anything else (a string) → TypeError.

PluggableLayer.register_oot (lines 82-99) has the same structure, with the text "Duplicate layer name".

Both dicts are module globals, so each process has its own. A plugin must register in every process that builds a model: a general plugin does this ({{link concepts/plugin-loading}}). Because name is a class attribute, a subclass without its own register call uses the parent's name. RotaryEmbedding is such a subclass: the decorator is on RotaryEmbeddingBase ({{cite vllm/model_executor/layers/rotary_embedding/base.py:14-15}}, {{cite vllm/model_executor/layers/rotary_embedding/base.py:139}}).
  1. Lines 218-228. Return fn unchanged when compilation is off for this call, for the whole config (mode NONE), or with the "eager" backend.
  2. Lines 230-233. The backend is the platform's simple_compile_backend ("inductor" by default, {{cite vllm/platforms/interface.py:172}}), with graph partition off.
  3. Lines 235-258. With dynamic_arg_dims: dynamic=False, and each call marks the listed dimensions as dynamic. A negative index counts from the end (line 254). An argument that is not a tensor is skipped (line 251).
  4. Lines 261-266. Else dynamic=True.

Example: mla_decode_concat_quant_fp8 registers dynamic_arg_dims={"decode_ql_nope": 0, "decode_q_pe": 0} ({{cite vllm/model_executor/layers/attention/mla_attention.py:1561-1564}}): dimension 0 (tokens) of both tensors is dynamic.
  • Import time. register runs when Python imports a layer module. register_oot runs when the plugin module is imported.
  • Model build. __new__, __init__ and dispatch_forward run once per layer object, inside set_current_vllm_config. A CustomOp built when no config is set raises AssertionError ({{cite vllm/config/vllm.py:3576-3586}}).
  • Forward. forward only calls _forward_method. No config lookup happens per step.
  • Threads. The registries have no lock. Registration happens at import and plugin time, before the model build. (Derived; the file has no comment about threads.)

Which dict does __new__ read, and with which key?

op_registry_oot, with cls.__name__ ({{cite vllm/model_executor/custom_op.py:109}}, {{cite vllm/model_executor/custom_op.py:117-120}}).

 An enabled op runs on ROCm. The subclass defines only forward_native and forward_cuda. Which method runs?

dispatch_forward returns forward_hip ({{cite vllm/model_executor/custom_op.py:194-195}}). Its default body calls forward_cuda ({{cite vllm/model_executor/custom_op.py:147-149}}).

 What is the difference between PluggableLayer and CustomOp?

Both swap the class in __new__ through op_registry_oot. Only CustomOp has the forward_* methods and dispatch_forward ({{cite vllm/model_executor/custom_op.py:33-44}}).

 An op registered with dynamic_arg_dims={"x": -1} is disabled and built with compile_native=True under VLLM_COMPILE. What does a call with a 2-D tensor x do?

maybe_compile compiled forward_native with dynamic=False. The wrapper binds the arguments, turns -1 into x.ndim - 1 = 1, calls mark_dynamic(x, 1), then calls the compiled function ({{cite vllm/model_executor/custom_op.py:235-258}}).
