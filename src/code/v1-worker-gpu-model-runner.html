It loads the model, sets up the KV cache, attention backends and CUDA graphs, and per step turns a SchedulerOutput into GPU inputs, runs the forward pass and samples into an AsyncOutput. ---

Purpose

vllm/v1/worker/gpu/model_runner.py is the GPU half of an engine step: it keeps the request states on the GPU, builds each step's inputs, runs the model and samples the next tokens.

Where it sits

Who calls it

  • Start-up, through the worker. load_model ({{cite vllm/v1/worker/gpu_worker.py:591-598}}), profile_run during memory profiling ({{cite vllm/v1/worker/gpu_worker.py:697}}), initialize_kv_cache ({{cite vllm/v1/worker/gpu_worker.py:898}}), warm-up _dummy_run calls and capture_model ({{cite vllm/v1/worker/gpu_worker.py:961-985}}).
  • Every step. Worker.execute_model and Worker.sample_tokens forward the engine core's calls ({{cite vllm/v1/worker/gpu_worker.py:1318-1321}}, {{cite vllm/v1/worker/gpu_worker.py:1350-1353}}).
  • Subclasses. The CPU runner subclasses this class ({{cite vllm/v1/worker/cpu/model_runner.py:10}}). An out-of-tree runner can pick its own PCP manager through pcp_manager_cls ({{cite vllm/v1/worker/gpu/model_runner.py:2433-2437}}).

What it calls

  • RequestState for the {{term persistent-batch}} ({{cite vllm/v1/worker/gpu/model_runner.py:286-295}}), InputBuffers and InputBatch for the per-step tensors, BlockTables for block tables and slot mappings.
  • init_attn_backend, init_kv_cache and build_slot_mappings_by_layer from attn_utils.py.
  • ModelCudaGraphManager and dispatch_cg_and_sync_dp for CUDA graphs.
  • set_forward_context around the model call ({{link code/forward-context}}).
  • Sampler, RejectionSampler, StructuredOutputsWorker, the speculator, AsyncOutput.

Walk through the main methods

load_model

  1. Line 398. get_model_loader picks the loader for --load-format ({{link concepts/weight-loading}}).
  2. Lines 402-406. The loader builds the model and loads the weights. JIT warm-up providers chosen during the build are recorded.
  3. Lines 407-410. With LoRA, the model's layers are wrapped.

After loading, it builds the model state and decode_query_len ({{cite vllm/v1/worker/gpu/model_runner.py:438-445}}). On the last PP rank of a generative model it builds the Sampler, a RejectionSampler with speculative decoding, the prompt-logprobs worker and the structured-output worker ({{cite vllm/v1/worker/gpu/model_runner.py:464-532}}). A pooling model gets a PoolingRunner instead (lines 534-535). In STOCK_TORCH_COMPILE mode the whole model is compiled here (lines 554-555).

initialize_kv_cache

init_attn_backend returns the attention groups, the weakest CUDA graph support and the kernel block sizes. Then the method builds BlockTables (lines 716-728), resolves the CUDA graph mode with the backend support, and builds the CUDA graph manager:

Last, it allocates the KV cache and binds each view to its layer through static_forward_context ({{cite vllm/v1/worker/gpu/model_runner.py:792-808}}), and creates the KV connector unless this is a profiling call ({{cite vllm/v1/worker/gpu/model_runner.py:813-823}}).

execute_model

The state updates (lines 1753-1771) and the input steps are on {{link concepts/model-runner}}. The core of the method:

  1. Lines 1806-1821. Pick the CUDA graph descriptor; with DP > 1 the ranks agree on one padded size.
  2. Lines 1823-1826. If every DP rank has zero tokens, return an empty output.
  3. Lines 1835-1838. Build the step tensors, then the block tables and slot mappings.

Then the method builds the attention metadata (lines 1924-1951), the model inputs (lines 1984-2010), and runs the model in FULL, PIECEWISE or eager mode (lines 2024-2070). It stores an ExecuteModelState and returns None, or IntermediateTensors on a non-last PP rank ({{cite vllm/v1/worker/gpu/model_runner.py:2090-2110}}).

sample_tokens

  1. Lines 2117-2119. No stored state means execute_model failed; return None.
  2. Line 2131. The state is used once and cleared.
  3. Line 2133. A non-last PP rank only receives the sampled tokens from the last rank and updates its counters (lines 2134-2153).

On the last rank: sample() (line 2163), prompt logprobs (lines 2176-2192), the ModelRunnerOutput shell with sampled_token_ids=None (lines 2195-2204), the AsyncOutput that starts the copy (lines 2210-2218), postprocess_sampled (lines 2249-2255), and the speculator (lines 2257-2293). It returns the AsyncOutput (line 2311).

prepare_inputs

Two of the four GPU steps: positions and sequence lengths, then the input tokens from the last sampled tokens and the drafts. The returned logits_indices select the rows for the sampler. The method ends with an InputBatch of more than 30 fields ({{cite vllm/v1/worker/gpu/model_runner.py:1532-1574}}).

capture_model

  1. Line 1092. Garbage collection is frozen during capture.
  2. Lines 1097-1098. A multimodal model can capture its encoder too.
  3. Lines 1104-1118. The decoder graphs: PIECEWISE and FULL descriptors ({{link concepts/compile-and-cuda-graphs}}).
  4. Lines 1119-1127. Model-state graphs and the speculator's graphs.

The method returns the graph memory and logs "Graph capturing finished in ... secs, took ... GiB" ({{cite vllm/v1/worker/gpu/model_runner.py:1144-1153}}).

Which method returns the AsyncOutput, and what does execute_model return on the last PP rank?

sample_tokens returns it ({{cite vllm/v1/worker/gpu/model_runner.py:2311}}). execute_model returns None and keeps its results in execute_model_state ({{cite vllm/v1/worker/gpu/model_runner.py:2090-2110}}).

 Where is the CUDA graph mode of the run finally decided, and with which inputs?

In initialize_kv_cache, by resolve_cudagraph_mode_and_sizes with the weakest attention support, its backend name, decode_query_len, the KV cache config and piecewise_capture_available ({{cite vllm/v1/worker/gpu/model_runner.py:754-763}}).

 Why does sample_tokens create the AsyncOutput before postprocess_sampled?

So the copy event is recorded first and the copy to the CPU does not wait for the post-processing kernels ({{cite vllm/v1/worker/gpu/model_runner.py:2244-2248}}).

 A dummy run for the profile uses skip_attn=True. Why can a FULL capture not do the same?

A FULL graph records the attention kernels too, so it needs real attention metadata at capture; the code asserts this ({{cite vllm/v1/worker/gpu/model_runner.py:1877-1881}}). The profile run only measures memory and may skip attention ({{cite vllm/v1/worker/gpu/model_runner.py:1022-1027}}).
