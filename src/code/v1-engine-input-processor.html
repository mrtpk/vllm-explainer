Purpose

vllm/v1/engine/input_processor.py turns one rendered prompt and its parameters into one {{term engine-core-request}}. On the way, it rejects requests that the engine cannot run and fills in the defaults that the engine core needs.

The name says "processor", but for vllm serve the heavy work is already done: the renderer has applied the chat template and tokenized the prompt. The input processor checks and packs.

Where it sits

The input processor stands between the renderer and the engine core client: renderer → EngineInput dict → InputProcessor.process_inputs → EngineCoreRequest → assign_request_id → engine core client. The page {{link concepts/data-contracts}} shows the types on both sides.

Who calls it

  • AsyncLLM.__init__ makes one instance and gives it the shared renderer ({{cite vllm/v1/engine/async_llm.py:170}}). LLMEngine does the same ({{cite vllm/v1/engine/llm_engine.py:101}}).
  • AsyncLLM.add_request calls process_inputs for rendered inputs and process_inputs_async for raw prompts, then assign_request_id ({{cite vllm/v1/engine/async_llm.py:481-521}}).
  • The serving classes keep a reference to it as self.input_processor ({{cite vllm/entrypoints/generate/base/serving.py:151}}). Online beam search calls resolve_watermarking and reads generation_config_fields ({{cite vllm/entrypoints/generate/beam_search/online.py:49}}, {{cite vllm/entrypoints/generate/beam_search/online.py:78}}).

What it calls

  • SamplingParams.verify and PoolingParams.verify for the parameter rules ({{cite vllm/v1/engine/input_processor.py:157-162}}, {{cite vllm/v1/engine/input_processor.py:245}}).
  • The logits processor validator, built once in the constructor. With Model Runner V2 it loads the custom logits processor classes ({{cite vllm/v1/engine/input_processor.py:93-113}}).
  • current_platform.validate_request, a hook for platform plugins ({{cite vllm/v1/engine/input_processor.py:430}}).
  • renderer.validate_token_ids, which rejects token ids outside the vocabulary ({{cite vllm/v1/engine/input_processor.py:646-647}}, {{cite vllm/renderers/base.py:453-458}}).

Walk through the main methods

process_inputs, part 1: checks and the engine input

  1. Lines 389-390. Check the parameters and the LoRA request first. _validate_params returns the watermark decision; the code applies it later to its own copy.
  2. Lines 392-400. An explicit data_parallel_rank must be in range. The range is the local DP size with hybrid or external load balancing, else the full DP size.
  3. Lines 402-406. The vllm serve path: the prompt is already an engine input. Its arrival_time, set by the renderer, wins over a new time.time().
  4. Lines 407-428. The old path for raw prompts logs a deprecation warning once and renders the prompt here.
  5. Line 430. The platform can reject the request.
  6. Lines 432-433. Split encoder and decoder inputs, and check their lengths and token ids.

process_inputs, part 2: sampling parameters and defaults

  1. Line 449. clone(): the caller's SamplingParams object can be shared by many requests, so the code changes only a copy. The comment at lines 450-451 says so.
  2. Lines 457-475. Two range checks for rarely used fields: routed_experts_prompt_start and the rows of prompt_logprob_token_ids.
  3. Lines 476-487. No max_tokens: use all the room that is left, max_model_len − prompt_len. Only now can min_tokens be checked against it.
  4. Lines 489-492. update_from_generation_config sets the EOS token id and adds the eos_token_id values of the model's generation config to stop_token_ids. With ignore_eos, it changes neither ({{cite vllm/sampling_params.py:775-803}}).
  5. Lines 493-494. update_from_tokenizer turns bad_words into token ids ({{cite vllm/sampling_params.py:805-847}}).
  6. Line 498. Pooling parameters are cloned too, but get no defaults here.

This file does not apply the default temperature or top_p of the model's generation config. The chat serving layer does that when it builds SamplingParams: "Priority: user -> server default -> OpenAI default" ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:740-748}}). The input processor reads the generation config only for EOS ids (line 490 and {{cite vllm/v1/engine/input_processor.py:64}}).

process_inputs, part 3: the struct

Every field comes from the steps above. cache_salt comes from the decoder input (line 548): a client can set it to keep its prefix-cache entries apart from other clients. client_index, current_wave and external_req_id keep their defaults here. The client and assign_request_id set them later.

assign_request_id

  1. Lines 358-362. A caller must not set external_req_id itself.
  2. Line 363. The caller's id becomes the external id. The output processor returns it in RequestOutput.request_id.
  3. Lines 364-369. With VLLM_DISABLE_REQUEST_ID_RANDOMIZATION, the id stays unchanged, with a warning about duplicates.
  4. Line 371. Else the first 8 characters of a new UUID are appended after a dash.

_validate_params for sampling

  1. Lines 151-155. A SamplingParams request needs a model with a generation task.
  2. Lines 157-162. SamplingParams.verify checks the fields against the model, the spec decoding config, the structured output config and the tokenizer.
  3. Lines 163-175. prompt_logprob_token_ids needs Model Runner V2 and does not work with --kv-sharing-fast-prefill.
  4. Line 177. Custom logits processors can check their own request arguments.

Further checks follow for diffusion models, sampling-mask replay, thinking_token_budget (needs a reasoning config) and trace replay ({{cite vllm/v1/engine/input_processor.py:179-220}}). Watermarking is resolved last, so a missing feature is reported before an incompatibility with watermarking ({{cite vllm/v1/engine/input_processor.py:221-223}}).

_validate_prompt_len

  1. Lines 565-566. An empty decoder prompt is an error.
  2. Lines 569-573. The limit is max_model_len for the decoder and the encoder cache size for an encoder prompt.
  3. Lines 574-591. Longer than the limit: error, with a hint for multimodal models.
  4. Lines 593-602. Exactly the limit, for a generative model: error too, because no room is left for one output token.

The class lives in the API server process. It has no lock and no thread of its own. process_inputs_async is make_async(process_inputs) with the renderer's executor ({{cite vllm/v1/engine/input_processor.py:79-84}}). So raw-prompt requests run in the same thread pool as the tokenizer. The comment explains why: tokenization and multimodal processing block, and must not block the event loop.

The engine core repeats a few checks. For example, it checks the pooling task again in EngineCore.add_request ({{cite vllm/v1/engine/core.py:520-529}}). Structured-output grammars are compiled only in the engine core. The input thread starts the compilation in a thread pool of the structured output manager ({{cite vllm/v1/engine/core.py:1129-1135}}, {{cite vllm/v1/structured_output/__init__.py:196-197}}).

A chat request has no max_tokens. The prompt has 1,000 tokens, and max_model_len is 8192. Which max_tokens reaches the engine core?

7192, if the server and the platform set no smaller limit. The chat serving layer computes it with get_max_tokens, the smallest of max_model_len − prompt_len and the other limits ({{cite vllm/entrypoints/serve/utils/api_utils.py:253-270}}). process_inputs would fill the same value if it were still None ({{cite vllm/v1/engine/input_processor.py:476-480}}).

 Why does process_inputs clone the SamplingParams?

The caller's object can be shared across prompts, requests and engines. The code then changes the copy: watermarking, max_tokens, EOS and stop ids ({{cite vllm/v1/engine/input_processor.py:447-453}}, {{cite vllm/v1/engine/input_processor.py:476-494}}).

 The client sends the id abc. Which ids do the output processor and the engine core use?

The engine core uses abc- plus 8 random characters, for example abc-1f2e3d4c. The output processor keeps abc as external_req_id and puts it into RequestOutput.request_id ({{cite vllm/v1/engine/input_processor.py:363-371}}). (For chat, the serving layer has already added the prefix chatcmpl-.)

 A model has max_model_len = 4096. A prompt of exactly 4096 tokens reaches process_inputs. What happens, and would an embedding model behave the same?

The generative model rejects it: the prompt length equals the limit, and the runner type is "generate", so no room is left for one output token ({{cite vllm/v1/engine/input_processor.py:593-602}}). An embedding model has another runner type, so a prompt of exactly 4096 tokens passes; only a longer one fails ({{cite vllm/v1/engine/input_processor.py:574}}).
