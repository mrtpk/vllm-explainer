Purpose

vllm/v1/engine/core.py is the inner loop of vLLM. It owns the scheduler and the {{term executor}}, runs the engine steps, and, in vllm serve, wraps all of this in a process that talks {{term zmq | ZMQ}} with the front end.

Filevllm/v1/engine/core.py, 2,847 lines of Python. Seven classes: three engine classes, one enum, three Ray actor classes.
Main classesEngineCore ({{cite vllm/v1/engine/core.py:118}}), EngineCoreProc ({{cite vllm/v1/engine/core.py:1153}}), DPEngineCoreProc ({{cite vllm/v1/engine/core.py:2269}}).
Runs inThe {{term engine-core}} process, one per data parallel rank: the main thread (busy loop), the {{term input-thread}} and the {{term output-thread}}. With the {{term uni-executor}}, the worker and the model runner also run in the main thread.
Called byThe engine core client, which starts the process with run_engine_core; with multiprocessing off, InprocClient makes an EngineCore in the caller's process ({{cite vllm/v1/engine/core_client.py:384-389}}).
CallsThe scheduler (schedule, update_from_output, get_grammar_bitmask), the executor (execute_model, sample_tokens, start-up RPCs), the KV cache planner, StructuredOutputManager, msgpack and ZMQ.
Not in this fileThe scheduling algorithm (v1/core/sched/scheduler.py), the client side of the sockets (core_client.py), the process launcher and the handshake on the front-end side (v1/engine/utils.py), the workers (v1/executor/, v1/worker/).

The page {{link concepts/engine-core-loop}} explains the ideas. This page reads the file method by method.

Where it sits

Who calls it

  • Process launch. The engine core client starts one process per local DP rank with the target EngineCoreProc.run_engine_core ({{cite vllm/v1/engine/utils.py:279-288}}).
  • Ray data parallel backend. EngineCoreActor or DPMoEEngineCoreActor run the same classes inside Ray actors ({{cite vllm/v1/engine/utils.py:516-522}}).
  • In-process engine. InprocClient calls EngineCore.step_fn directly, with no threads and no sockets ({{cite vllm/v1/engine/core_client.py:396-399}}). vllm serve never uses it: AsyncLLM always makes a multiprocess client ({{cite vllm/v1/engine/async_llm.py:193}}).
  • The front end at run time. ADD, ABORT and UTILITY messages over ZMQ; the utility methods are the public methods of EngineCore and EngineCoreProc, looked up by name ({{cite vllm/v1/engine/core.py:1756-1761}}).

What it calls

  • load_general_plugins, then executor_class(vllm_config) ({{cite vllm/v1/engine/core.py:130-147}}).
  • Executor start-up RPCs and get_kv_cache_configs in _initialize_kv_caches ({{cite vllm/v1/engine/core.py:253-379}}).
  • get_scheduler_cls() and the scheduler constructor ({{cite vllm/v1/engine/core.py:164-185}}).
  • Per step: schedule, execute_model, get_grammar_bitmask, sample_tokens, update_from_output ({{cite vllm/v1/engine/core.py:724-785}}).
  • Request.from_engine_core_request in the input thread ({{cite vllm/v1/engine/core.py:1128}}).

Walk through the main methods

EngineCore.__init__: build the engine

  1. Line 147. The executor constructor starts the workers and loads the model. This is the slowest line of start-up.
  2. Line 150. The failure callback (from EngineCoreProc) lets a dead worker stop the busy loop.
  3. Line 160. The KV cache set-up needs the loaded model (next method).
  4. Line 164. get_scheduler_cls() returns the class in scheduler_cls when it is set. Otherwise it returns AsyncScheduler when async scheduling is on, or Scheduler ({{cite vllm/config/scheduler.py:231-239}}).
  5. Lines 166-171. A model with no KV cache groups (an encoder-only model) gets chunked prefill turned off.
  6. Lines 177-185. The scheduler gets the final KV cache config, so its block pool has the real number of blocks.
  1. Lines 205-211. The batch queue is a deque with maxlen = max_concurrent_batches, only when that value is more than 1.
  2. Lines 217-225. The block hasher exists when prefix caching is on or a KV connector is set. The input thread uses it.
  3. Lines 227-229. The step function: step without a batch queue, step_with_batch_queue with one.
  4. Line 232. The abort queue for early aborts.
  5. Line 238. freeze_gc_heap() marks all start-up objects as static, so the garbage collector does not scan them again (comment at lines 236-237).
  6. Line 243. From here on, environment variables are cached.

_initialize_kv_caches: memory and KV cache

  1. Line 300. When the model has a KV cache (line 289), each worker runs a {{term profile-run}} and returns the bytes left for the KV cache. The page {{link code/v1-worker-gpu-worker}} has the formula and a worked example.
  2. Lines 311-313. get_kv_cache_configs turns bytes into blocks, one config per worker. The page {{link concepts/kv-cache-manager}} explains it.
  3. Lines 321-322. If the planner changed max_model_len (for example, auto-fit lowered it to fit the memory), the workers learn the new value by RPC.
  4. Lines 324-325. The scheduler's view of the cache, and the final num_gpu_blocks. The ready message sends this number to the front end ({{cite vllm/v1/engine/core.py:1876}}).
  1. Line 362. The workers allocate the KV cache tensors.
  2. Line 379. Compile, warm up and capture CUDA graphs. Only after this line can the engine serve requests.

step: the synchronous step

  1. Lines 665-666. No requests: no step.
  2. Lines 668-669. The forward pass starts (non-blocking), and the grammar bitmask runs on the CPU meanwhile.
  3. Lines 674-676. Wait for execute_model. A None result means "now call sample_tokens", which here is blocking.
  4. Line 687. The second return value tells post_step whether the model ran.

step_with_batch_queue: the default step

The page {{link concepts/engine-core-loop}} reads this method line by line in a deep dive, and {{link concepts/async-scheduling}} explains the deferred-sampling branch (line 749). The short version: start step N+1 (lines 725-753); if the queue is full, wait for step N (lines 768-778) and update the scheduler (line 783).

run_busy_loop

  1. Line 1608. fault_tolerant_wrapper re-raises at once unless fault tolerance is on ({{cite vllm/v1/fault_tolerance/engine_core_sentinel.py:175-183}}).
  2. Line 1611. _handle_shutdown() is true while running, and also while a requested shutdown drains work.
  3. Line 1613. Blocks when there is no work ({{cite vllm/v1/engine/core.py:1638-1656}}).
  4. Line 1620. The loop ends only with SystemExit. run_engine_core catches it and cleans up ({{cite vllm/v1/engine/core.py:1560-1583}}).

process_input_sockets: the input thread

  1. Lines 1930-1933. One typed decoder for ADD messages, one generic decoder for the rest. Both can receive tensors through the tensor IPC queue of multimodal inputs.
  2. Lines 1936-1943. One DEALER socket per front end (per API server), with this engine's identity. The front end owns the ROUTER side.
  3. Lines 1961-1968. The first message on each socket is the ready response.
  4. Line 1972. With a DP coordinator, the thread first waits for its READY.
  5. Line 1975. Only now can EngineCoreProc.__init__ finish ({{cite vllm/v1/engine/core.py:1267-1273}}).

The receive loop that follows (lines 1977-2028) is read on {{link concepts/engine-core-loop}}, Step 3.

process_output_sockets: the output thread

  1. Line 2035. One encoder for the life of the thread.
  2. Lines 2037 and 2042. Send buffers are reused. A buffer that ZMQ still sends waits in pending with its tracker.
  3. Line 2049. One PUSH socket per front end. linger=4000 gives the ENGINE_CORE_DEAD message 4 seconds to leave (comment at lines 2044-2045).
  4. Line 2062. At most one spare buffer per socket, plus one, is kept.

The send loop (lines 2064-2096) is read on {{link concepts/engine-core-loop}}, Step 7.

The input thread calls preprocess_add_request, which touches mm_receiver_cache and structured_output_manager. Its comments explain why there is no race: only the input thread uses the cache after start-up, and grammar compilation is asynchronous and per request ({{cite vllm/v1/engine/core.py:1120-1135}}).

One request, async scheduling, queue size 2, a 3-token answer that ends with EOS. Each line is one call of _process_engine_step ({{cite vllm/v1/engine/core.py:1666-1684}}).

  1. Call 1: schedule step 1 (the prompt) and return None. Nothing goes into output_queue.
  2. Call 2: schedule step 2, wait for step 1, update. output_queue gets (0, EngineCoreOutputs(outputs=[token 1])).
  3. Call 3: schedule step 3, wait for step 2. Output: token 2.
  4. Call 4: schedule step 4, wait for step 3. Output: token 3 = EOS, finish_reason=STOP.
  5. Call 5: has_requests() is still true for one call, because the finished request id must reach the workers in the next SchedulerOutput ({{cite vllm/v1/core/sched/scheduler.py:2913-2914}}, {{cite vllm/v1/core/sched/scheduler.py:1597-1601}}). It schedules an empty step 5, then waits for step 4, whose result is skipped. schedule() clears the finished ids ({{cite vllm/v1/core/sched/scheduler.py:1731-1734}}), so a sixth call only pops the empty step 5.

So 4 GPU steps produce 3 tokens. (Derived from {{cite vllm/v1/engine/core.py:724-785}} and {{cite vllm/v1/core/sched/scheduler.py:2184-2192}}.)

Which method does the engine core use as step_fn with the default settings on one GPU?

step_with_batch_queue, because the batch queue exists when max_concurrent_batches is more than 1 ({{cite vllm/v1/engine/core.py:209-211}}, {{cite vllm/v1/engine/core.py:227-229}}). With async scheduling and Model Runner V2 it is pp_size + 1 = 2 ({{cite vllm/config/vllm.py:591-593}}).

 In which order does EngineCore.__init__ build the executor, the KV cache and the scheduler, and why this order?

Executor (line 147), KV caches (line 160), scheduler (lines 177-185) ({{cite vllm/v1/engine/core.py:146-185}}). The KV cache size depends on a profile run of the loaded model, and the scheduler needs the final KV cache config.

 Which thread runs preprocess_add_request, and what does that buy?

The input thread ({{cite vllm/v1/engine/core.py:1993}}). The Request object and its block hashes are built while the main thread runs the model, as the docstring says ({{cite vllm/v1/engine/core.py:1115-1119}}).

 The front end sends a utility call to sleep while requests still run, with the pause mode "wait". When does the reply go out?

sleep() pauses the scheduler and gets a Future back, because the engine is not idle yet. It returns a second Future that puts the executor to sleep when the pause completes ({{cite vllm/v1/engine/core.py:994-1017}}). _invoke_utility_method sees a Future and adds a callback, so the reply is sent only when that future is done ({{cite vllm/v1/engine/core.py:1828-1834}}). The busy loop meanwhile keeps stepping the in-flight requests.
