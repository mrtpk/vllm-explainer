Purpose

vllm/v1/engine/core_client.py holds the {{term engine-core-client | engine core clients}}: the objects in the front end that send requests to the engine core and get its outputs back.

The page {{link concepts/engine-client}} shows how AsyncLLM uses these clients. This page reads the clients themselves.

Where it sits

The class tree has two branches: one in-process client, and the multiprocess clients that use ZMQ. The asyncio branch is the one of vllm serve:

EngineCoreClient                  abstract; factories
├── InprocClient                  EngineCore in this process
└── MPClient                      ZMQ, launch, ready wait
    ├── SyncMPClient              blocking; offline LLM
    └── AsyncMPClient             asyncio; vllm serve, DP = 1
        └── DPAsyncMPClient       DP > 1, external LB
            └── DPLBAsyncMPClient DP > 1, internal LB

Who calls it

  • AsyncLLM.__init__ calls EngineCoreClient.make_async_mp_client ({{cite vllm/v1/engine/async_llm.py:193-201}}). For every request it calls add_request_async; the output handler calls get_output_async and abort_requests_async ({{cite vllm/v1/engine/async_llm.py:584}}, {{cite vllm/v1/engine/async_llm.py:880}}, {{cite vllm/v1/engine/async_llm.py:920}}).
  • LLMEngine (offline) calls make_client with asyncio_mode=False. That gives SyncMPClient or, without multiprocessing, InprocClient ({{cite vllm/v1/engine/core_client.py:128-136}}).

What it calls

  • make_zmq_socket for the ROUTER, PULL, XSUB and PAIR sockets ({{cite vllm/v1/engine/core_client.py:673-682}}, {{cite vllm/v1/engine/core_client.py:1524-1527}}).
  • launch_core_engines, which starts the engine core processes and, when needed, the DP coordinator ({{cite vllm/v1/engine/core_client.py:695-702}}).
  • MsgpackEncoder and MsgpackDecoder(EngineCoreOutputs) ({{cite vllm/v1/engine/core_client.py:731-732}}).
  • The engine manager's monitor_engine_liveness in a thread ({{cite vllm/v1/engine/core_client.py:829-845}}).

Walk through the main methods

make_async_mp_client: which class

  1. Lines 150-157. All three classes take the same six arguments: the config, the executor class, log_stats, and the client addresses, count and index of this API server.
  2. Lines 158-164. DP > 1 with an external load balancer: DPAsyncMPClient, which sends everything to one engine core.
  3. Lines 165-169. DP > 1 otherwise: DPLBAsyncMPClient, which balances over all engine cores.
  4. Line 170. DP = 1: AsyncMPClient.

There is no asyncio client without multiprocessing: make_client raises NotImplementedError for that case ({{cite vllm/v1/engine/core_client.py:114-118}}). So vllm serve always runs the engine core in its own process.

MPClient.__init__: sockets and launch

  1. Lines 621-622. One ZMQ context with 2 I/O threads. The asyncio clients wrap it in a zmq.asyncio.Context.
  2. Lines 627-628. BackgroundResources holds everything that must be closed. A weakref.finalize calls it when the client is collected, even if the constructor fails half-way (lines 624-626).

Then the client binds its two sockets. In the multi-API-server case, the parent process has bound them already, and the client gets the listeners through client_addresses ({{cite vllm/v1/engine/core_client.py:643-669}}). In the single-server case, the client binds them itself and launches the engines:

  1. Lines 673-679. A ROUTER socket for requests, bound by the client. A ROUTER sends each message to the peer whose identity is the first frame.
  2. Lines 680-682. A PULL socket for outputs. All engine cores push into it.
  3. Lines 686-693. The real bound addresses go to the engines.
  4. Lines 695-697. launch_core_engines starts the engine core processes (and the DP coordinator when needed).

Next the client computes which engines it talks to, and waits for each one:

  1. Lines 740-743. With internal load balancing, the client manages all DP ranks. With hybrid or external load balancing, only the local ones.
  2. Lines 749-751. The ZMQ identity of each engine is its DP rank as 2 little-endian bytes. The engine core uses the same bytes as the identity of its DEALER socket ({{cite vllm/v1/engine/core.py:1178-1179}}).
  3. Lines 756-768. A blocking poll with timeout VLLM_ENGINE_READY_TIMEOUT_S. The error message names the variable.
  4. Lines 769-771. Each ready message carries the identity and an EngineCoreReadyResponse, which _apply_ready_response applies.
  5. Line 773. core_engine is the first engine: the default target of a DP = 1 client.
  6. Line 777. The monitor thread starts.

AsyncMPClient: the output task

  1. Line 1211. Receive one multipart message without a copy.
  2. Line 1212. validate_alive raises EngineDeadError when the message is the single frame ENGINE_CORE_DEAD ({{cite vllm/v1/engine/core_client.py:581-584}}).
  3. Line 1213. Decode into EngineCoreOutputs.
  4. Lines 1214-1243 (first excerpt ends at 1214). A message with utility_output is a reply to a utility call, or one of two special notifications. It never goes into the queue.
  5. Lines 1245-1251. A subclass hook. DPLBAsyncMPClient uses it to count finished requests per engine ({{cite vllm/v1/engine/core_client.py:1810-1817}}).
  6. Lines 1253-1254. Only messages with outputs or stats go to outputs_queue.
  7. Lines 1255-1258. An exception goes into the queue. A cancel puts an EngineDeadError there. The next get_output_async() raises it ({{cite vllm/v1/engine/core_client.py:1264-1273}}).
  8. Lines 1260-1262. The task is named EngineCoreOutputQueueTask. The constructor starts it if a loop runs, so that early EXECUTOR_FAILED messages are not missed ({{cite vllm/v1/engine/core_client.py:1177-1185}}).

Sending a request

  1. Line 1284. The frames are the type byte (for example b"\x00" for ADD) and the encoded buffers.
  2. Line 1290. ensure_alive raises EngineDeadError when the dead flag is set ({{cite vllm/v1/engine/core_client.py:803-805}}).
  3. Line 1294. The engine identity goes first. The ROUTER uses it to route the message, and removes it before delivery. send_multipart of the asyncio socket returns an awaitable.
  4. Line 1334. client_index tells the engine core which output socket to use for this request.
  5. Line 1339. Aborts are skipped when the engine is dead.

Utility calls: a small RPC system

A {{term utility-call}} runs one method of EngineCore in the engine core process and returns its result. Control methods such as sleep, add_lora and collective_rpc use it.

  1. Line 1319. A 64-bit call id from a UUID.
  2. Lines 1320-1321. An asyncio future, stored under the call id.
  3. Lines 1322-1325. The message is UTILITY plus (client_index, call_id, method, args).
  4. Line 1328. The caller waits on the future. The output task completes it with _process_utility_output ({{cite vllm/v1/engine/core_client.py:929-948}}).

On the engine side, the busy loop looks up the method by name on the EngineCore object and calls it. The result goes back as EngineCoreOutputs(utility_output=...) to the client that asked ({{cite vllm/v1/engine/core.py:1752-1765}}). If the method returns a Future, the reply waits for it ({{cite vllm/v1/engine/core.py:1826-1834}}). Three variants exist in the client: one engine (call_utility_async), all engines (call_utility_all_async), and all engines with a check that the results agree (call_utility_consensus_async) ({{cite vllm/v1/engine/core_client.py:1296-1314}}). DPLBAsyncMPClient changes call_utility_async: it calls all engines and returns the first result ({{cite vllm/v1/engine/core_client.py:1806-1808}}).

DPLBAsyncMPClient.get_core_engine_for_request: load balancing

  1. Lines 1755-1759 (above the excerpt). A request with data_parallel_rank set, or a late-interaction pooling request, goes to a fixed engine. Streaming-input sessions stick to their engine ({{cite vllm/v1/engine/core_client.py:1750-1752}}).
  2. Line 1768. The scan starts at eng_start_index, which depends on the client index, and rotates after each pick (line 1798).
  3. Lines 1777-1778. The base score is the larger of the coordinator's waiting + running and this client's in-flight count times the number of clients.
  4. Lines 1779-1786. Waiting requests add a penalty that grows with the KV cache usage above 50%: from 0 at 50% to 3 × waiting at 100%.
  5. Line 1792. The local waiting count goes up at once, so that the next request sees the new load before the next coordinator update.

Which client class does vllm serve use with one engine core, and which socket types does it bind?

AsyncMPClient ({{cite vllm/v1/engine/core_client.py:170-173}}). It binds a ROUTER socket for requests and a PULL socket for outputs ({{cite vllm/v1/engine/core_client.py:673-682}}).

 How does the client know which engine core a message on the ROUTER socket goes to?

The first frame is the engine identity: the DP rank as 2 little-endian bytes ({{cite vllm/v1/engine/core_client.py:749-751}}, {{cite vllm/v1/engine/core_client.py:1294}}). Each engine core sets the same bytes as the identity of its DEALER socket ({{cite vllm/v1/engine/core.py:1178-1179}}).

 A utility reply and a step output both arrive on the PULL socket. How does the output task tell them apart?

A utility reply has utility_output set. The task completes the future of its call id and does not put the message into outputs_queue ({{cite vllm/v1/engine/core_client.py:1214-1243}}).

 Two engines: engine 0 has waiting 2, running 6, KV usage 0.9; engine 1 has waiting 0, running 9. One API server, and no request in flight. Which engine does DPLBAsyncMPClient pick?

Engine 0: base max(1 × 0, 8) = 8, penalty 2 × 6.0 × 0.4 = 4.8, score 12.8. Engine 1: base max(0, 9) = 9, no penalty, score 9. It picks engine 1 ({{cite vllm/v1/engine/core_client.py:1777-1789}}).
