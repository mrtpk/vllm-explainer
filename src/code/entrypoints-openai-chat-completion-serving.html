Purpose

vllm/entrypoints/openai/chat_completion/serving.py holds the {{term serving-class}} of POST /v1/chat/completions: it turns one chat request into one engine generator and turns the engine's outputs back into the OpenAI chat format.

Where it sits

Who calls it

  • Start-up. init_generate_state makes one OpenAIServingChat with the CLI flags, only for models with the generate task ({{cite vllm/entrypoints/generate/api_router.py:127-151}}).
  • The route. create_chat_completion awaits handler.create_chat_completion(request, raw_request). It sends an ErrorResponse or a ChatCompletionResponse as JSON, and wraps a generator in a StreamingResponse ({{cite vllm/entrypoints/openai/chat_completion/api_router.py:67-85}}).
  • Subclasses. The Anthropic /v1/messages and Cohere v2 handlers reuse its generators, and the hooks _create_chat_message and _finalize_response_message exist for them ({{cite vllm/entrypoints/openai/chat_completion/serving.py:445-471}}).

What it calls

  • ParserManager.get_parser once at start-up ({{cite vllm/entrypoints/openai/chat_completion/serving.py:167-175}}).
  • self.online_renderer.render_chat(request) for each request ({{cite vllm/entrypoints/openai/chat_completion/serving.py:285}}).
  • self.engine_client.generate(...), or self.beam_search(...) for beam search ({{cite vllm/entrypoints/openai/chat_completion/serving.py:385-408}}).
  • ChatStreamProcessor.step for each output of a stream ({{cite vllm/entrypoints/openai/chat_completion/serving.py:705-710}}).

Walk through the main methods

__init__: what is fixed at start-up

  1. Lines 166-175. The parser class combines the tool parser (only with --enable-auto-tool-choice) and the reasoning parser. gpt-oss models are flagged as Harmony ({{link concepts/tool-and-reasoning-parsers}}).
  2. Line 166. With a reasoning parser, usage reports reasoning_tokens.
  3. Line 181. The server's default sampling parameters come from the model's generation config, read once here ({{link learn/openai-api}}, defaults deep dive).
  4. Lines 183-187. The max_tokens override: from --override-generation-config for the modes auto and vllm, else from the generation config folder.

Lines 191-196 turn off browsing and the code interpreter for this route; the comments point to the Responses API for those.

render_chat_request: checks, then render

  1. Line 278. _check_model: a wrong model name returns HTTP 404 here.
  2. Line 283. _preflight(n) raises the engine's dead error, or a 503 from check_admission ({{cite vllm/entrypoints/generate/base/serving.py:169-181}}). These are exceptions, not error responses; the route's exception handlers turn them into HTTP errors.
  3. Line 285. The renderer returns the parsed conversation and a list with one EngineInput ({{link concepts/renderers-and-chat-templates}}).

_create_chat_completion: from request to generator

  1. Lines 310-313. The parser is made before rendering; it needs the effective template kwargs.
  2. Lines 314-316. An error response from the checks or the renderer returns at once.
  3. Lines 320-322. The request id: "chatcmpl-" plus the X-Request-Id header or the body's request_id.
  4. Line 328. The LoRA adapter: by model name, or a default multimodal adapter that matches the request's content types.
  1. Line 339. The loop handles one engine input; the chat renderer always returns one (line 412 asserts it).
  2. Lines 349-358. max_completion_tokens wins over the deprecated max_tokens; get_max_tokens takes the smallest limit.
  3. Lines 366-369. Sampling parameters: request value, else server default, else OpenAI default; DELTA for a stream, FINAL_ONLY otherwise.
  1. Lines 396-408. generate() makes an async generator; nothing reaches the engine yet. The priority comes from the X-Vllm-Priority header or the body. _engine_reasoning_kwargs adds the two reasoning fields.
  2. Lines 415-426. For a stream, the method returns the SSE generator. The route sends HTTP 200 when it starts iterating it.
  3. Line 428. Without a stream, the method awaits the full generator, so the route gets a finished response.

chat_completion_stream_generator: the SSE framing

  1. Lines 497-498. An error chunk is serialized in full.
  2. Lines 500-502. A normal chunk keeps only the fields that the code set; a chunk without choices (the usage chunk) also drops None fields.
  3. Lines 504-507. An exception during serialization still gives one error chunk.
  4. Line 508. data: [DONE] ends every stream, also after an error.

chat_completion_stream_generator_raw: chunks per output

Set-up: one ChatStreamProcessor per choice, each with its own parser; usage flags from stream_options ({{cite vllm/entrypoints/openai/chat_completion/serving.py:528-564}}). Then the loop over RequestOutputs:

  1. Lines 676-677. A choice that already sent its finish reason is skipped.
  2. Line 679. A finish reason "error" raises GenerationError.
  3. Lines 696-703. An output with no text and no tokens, before the first token, is a chunked-prefill step: no chunk.
  4. Lines 705-710. The processor runs the parser and maps the finish reason ("tool_calls" when tools were streamed).

The first output also makes one role chunk per choice, with delta = {"role": ..., "content": ""} ({{cite vllm/entrypoints/openai/chat_completion/serving.py:578-629}}). A None delta sends nothing, unless the output has a finish reason, logprobs, or token ids to return ({{cite vllm/entrypoints/openai/chat_completion/serving.py:731-741}}). The final chunk of a choice carries finish_reason and stop_reason, and the fingerprint when no usage chunk follows ({{cite vllm/entrypoints/openai/chat_completion/serving.py:787-824}}).

  1. Lines 854-856. The usage chunk sums the output tokens of all choices; the prompt counts once.
  2. Lines 866-871. prompt_tokens_details only with --enable-prompt-tokens-details.

The method ends with two handlers: a GenerationError becomes an error chunk with its own status code, and any other exception becomes an error chunk with the code from create_error_response ({{cite vllm/entrypoints/openai/chat_completion/serving.py:937-943}}).

chat_completion_full_generator: one response

  1. Lines 961-964. Only the last output is kept. With FINAL_ONLY there is normally just one. A client disconnect gives the error response "Client disconnected".
  2. Lines 966-971. No output at all gives HTTP 500.
  3. Lines 984-990. A new parser for each further choice; parsers keep state.
  4. Lines 1007-1019. One parse call splits reasoning, content and tool calls. With include_reasoning: false, the reasoning and the logprobs are dropped.

Lines 1026-1095 choose how the message is built, by tool_choice and auto tool choice; lines 1110-1128 build the choice with resolve_finish_reason and the parallel_tool_calls filter. Usage and the response object follow ({{cite vllm/entrypoints/openai/chat_completion/serving.py:1147-1206}}).

Request: the two ChatML messages (system and user) of the renderer worked example, "n": 2, "stream": true, "stream_options": {"include_usage": true}. The prompt has 26 tokens ({{link concepts/renderers-and-chat-templates}}). Choice 0 writes 2 text tokens and EOS (3 tokens). Choice 1 writes 3 text tokens and EOS (4 tokens).

  1. _preflight(2): check_admission(2) counts two slots ({{cite vllm/entrypoints/openai/chat_completion/serving.py:283}}).
  2. num_choices = 2, so two ChatStreamProcessors (no parser configured) ({{cite vllm/entrypoints/openai/chat_completion/serving.py:528}}, {{cite vllm/entrypoints/openai/chat_completion/serving.py:552-555}}).
  3. The first RequestOutput triggers two role chunks, index 0 and 1, before any text ({{cite vllm/entrypoints/openai/chat_completion/serving.py:590-629}}).
  4. Each later RequestOutput holds the new outputs of one or both children; the collector merges outputs of the same index and keeps indexes apart ({{cite vllm/outputs.py:217-255}}). The loop sends one chunk per output, with its index ({{cite vllm/entrypoints/openai/chat_completion/serving.py:672-674}}). So chunks of choice 0 and choice 1 can interleave.
  5. Choice 0 ends first. Its EOS output has empty text, so the chunk has delta: {"content": ""} and finish_reason: "stop", and finish_reason_sent[0] becomes true ({{cite vllm/entrypoints/openai/chat_completion/serving.py:787-806}}). Choice 1 goes on.
  6. After the last output, the usage chunk: prompt_tokens 26, completion_tokens = 3 + 4 = 7 (each processor counts the token ids it saw, EOS included), total_tokens 33 ({{cite vllm/entrypoints/openai/chat_completion/serving.py:854-859}}, {{cite vllm/entrypoints/openai/chat_completion/stream_processor.py:75}}).
  7. data: [DONE].

In total the client gets 2 role chunks, 2 + 3 text chunks (one per text token, with the default stream_interval 1), 2 final chunks, 1 usage chunk and [DONE]: 11 events. (Derived; a chunk can carry more than one token when the reader is slower than the engine.)

The texts and token counts are illustrative. The fingerprint is on the usage chunk, not on the final chunks, because usage is on ({{cite vllm/entrypoints/openai/chat_completion/serving.py:815-824}}).

Which method returns the async generator of SSE strings, and which line always ends the stream?

chat_completion_stream_generator; line 508 yields data: [DONE]\n\n, after the loop and after any error chunk ({{cite vllm/entrypoints/openai/chat_completion/serving.py:485-508}}).

 Why does _create_chat_completion build a parser before it renders the request?

The parser needs the effective chat_template_kwargs, and its reasoning half decides reasoning_ended for the engine from the prompt ids ({{cite vllm/entrypoints/openai/chat_completion/serving.py:310-313}}, {{cite vllm/entrypoints/openai/chat_completion/serving.py:242-262}}).

 An output arrives with empty text, no token ids and no finish reason, before the first token of a choice. What does the stream send?

Nothing: the code treats it as a chunked-prefill step and skips it ({{cite vllm/entrypoints/openai/chat_completion/serving.py:696-703}}).

 A non-streaming request with n = 2 sets --enable-per-request-metrics on the server. Does the response carry the timing metrics?

No. The code builds per-request metrics only when n is 1, because the stats belong to one of the sequences ({{cite vllm/entrypoints/openai/chat_completion/serving.py:1173-1181}}).
