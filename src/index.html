--- summary: A study guide to the latest vLLM for readers of DeepInfer Explained. It follows one HTTP request through vllm serve, explains the plugin system, and goes down to the exact code. ---

vLLM is "a fast and easy-to-use library for LLM inference and serving" ({{cite README.md:24}}). Its main use is online serving: the command vllm serve starts an {{term openai-compatible-server}} that answers HTTP requests ({{cite vllm/entrypoints/cli/serve.py:39-40}}). Behind the HTTP routes, a {{term scheduler}} runs one {{term engine-step}} after the other and batches the requests of many clients on the GPUs. Outside code can change much of this through {{term plugin | plugins}}.

Who this site is for. You know Python. You read {{deepinfer index | DeepInfer Explained}}, or you know the LLM basics that it teaches. Now you want to become proficient in online serving with the latest vLLM: what happens to a request inside vllm serve, how to configure, tune, monitor and scale a deployment, and how plugins extend vLLM. This site does not teach the basics again. When a page needs one, it gives a one-line recap and a link to DeepInfer Explained. The site explains the code at commit {{project short_sha}}. To get exactly this version of the code, read The code version this site explains.

What it runs"200+ model architectures on Hugging Face": decoder-only and Mixture-of-Experts LLMs, hybrid and state-space models, multimodal models, embedding and reward models ({{cite README.md:53-60}}). The default model of vllm serve is Qwen/Qwen3-0.6B ({{cite vllm/config/model.py:155}}, {{cite vllm/engine/arg_utils.py:486}}, {{cite vllm/entrypoints/cli/serve.py:39-40}}).
HardwareBuilt-in {{term platform | platform}} detectors: TPU, CUDA (NVIDIA), ROCm (AMD), XPU (Intel) and CPU ({{cite vllm/platforms/__init__.py:231-237}}). The TPU platform class comes from the separate package tpu_inference ({{cite vllm/platforms/tpu.py:9-19}}). Other hardware comes as platform plugins, for example Intel Gaudi, IBM Spyre and Huawei Ascend ({{cite README.md:51}}).
Code size8,357 files. Python: 5,471 files, about 2.0 million lines; the package vllm/ has 2,907 Python files and about 1.13 million lines; the Python files in tests/ have about 0.77 million lines. C++ and CUDA: 313 files, about 143,000 lines (kernels, not explained here). Rust: 375 files, about 152,000 lines (an experimental front end). Method: the files of git ls-files at the pinned commit, grouped by extension (.py; .cpp .cu .cuh .h .hpp; .rs); a line is a newline, plus a last line without one. See {{link code/index}}.
Run itvllm serve <model>, for example vllm serve Qwen/Qwen3-0.6B. The command vllm is a console script ({{cite pyproject.toml:42-43}}). The server listens on port 8000 by default ({{cite vllm/entrypoints/common/cli_args.py:286}}).

How to read the map. Follow the left column from 1 to 8. Boxes 1 to 3 and 8 run in the API server process, the {{term front-end}}. Box 5 runs in the {{term engine-core}} process. Boxes 6 and 7 run in a {{term worker}}, which owns one GPU. With one GPU, the worker runs inside the engine core process. With more GPUs, each worker is a separate process. Box 4 and the end of the arrow after box 7 cross a process boundary. The arrow after box 5 crosses one only when there are worker processes. The right column shows parts that every step uses. The page {{link tours/life-of-a-chat-request}} walks the same path in 16 stops.

The map shows the default layout of vllm serve with one API server and one data-parallel rank. The full truth has more parts:

  • In vllm serve, the engine core always runs in its own process: AsyncLLM always makes a multiprocess client ({{cite vllm/v1/engine/async_llm.py:193}}). The variable VLLM_ENABLE_V1_MULTIPROCESSING (default 1, {{cite vllm/envs.py:1442-1443}}) decides this only for the offline LLMEngine ({{cite vllm/v1/engine/llm_engine.py:170}}, {{cite vllm/v1/engine/llm_engine.py:186-188}}).
  • With one GPU, the executor is uni ({{cite vllm/config/parallel.py:1099-1100}}). It runs the worker inside the engine core process ({{cite vllm/v1/executor/uniproc_executor.py:68}}). With more GPUs on one node, the executor is mp. It sends each step to all worker processes through a shared-memory message queue ({{cite vllm/v1/executor/multiproc_executor.py:342-353}}, {{cite vllm/v1/executor/multiproc_executor.py:428}}).
  • Async scheduling is on by default. It is off for pooling models and with some incompatible options ({{cite vllm/config/vllm.py:1664-1698}}). With async scheduling and Model Runner V2, the batch queue holds 2 steps on one GPU ({{cite vllm/config/vllm.py:587-597}}). So the engine core runs step_with_batch_queue instead of step ({{cite vllm/v1/engine/core.py:205-211}}, {{cite vllm/v1/engine/core.py:227-229}}). This version does not wait for a step right after it starts it, so the CPU work of the next step overlaps the GPU work. {{link concepts/async-scheduling}} explains it.
  • Not shown: several API servers, one engine core per data-parallel rank, the data-parallel coordinator, Ray, and the KV transfer between instances. The pages {{link concepts/data-parallel-serving}} and {{link concepts/disaggregated-prefill}} explain them.

How to use this site

  • Levels. Each page has a badge: Beginner, Intermediate or Advanced. A "Before you read" box lists the pages to read first.
  • Two depths on each page. A page starts with one sentence, a plain explanation and a diagram. Then it shows the real code. Deep dive boxes give the full detail: types, shapes, edge cases and environment variables.
  • Check yourself. Most pages end with 3 to 5 questions. Answer each one, then click "Show answer".
  • Search. Press /, then type a word, a file name or an environment variable.
  • Glossary. Words with a dotted line, such as {{term engine-core}}, are glossary terms. Point to them, or tap them on a phone, to see a short definition. {{link reference/glossary}} lists all terms.
  • Code. The build copies every code excerpt from the repository. Every {{term citation}} opens the file on GitHub at commit {{project short_sha}}.
  • DeepInfer links. A link with a small "↗" opens DeepInfer Explained or GitHub in a new tab.
  • Grey entries in the menu are pages that are not written yet. Diagrams open at full size when you click them.

What this site does not explain

  • Kernel internals. The site shows how vLLM selects and calls a kernel (a device program), but not how the kernel works inside: not csrc/ ({{cite csrc/}}), and not the Triton, CUDA, CuTe or Helion kernel code.
  • Legacy code. V0 is gone; only aliases remain, for example AsyncLLMEngine = AsyncLLM ({{cite vllm/engine/async_llm_engine.py:6}}). Model Runner V2 is the default. Model Runner V1 ({{cite vllm/v1/worker/gpu_model_runner.py}}) gets one note on {{link concepts/model-runner}}.
  • Outside libraries such as PyTorch, FlashAttention, FlashInfer, NCCL, Ray, ZMQ and FastAPI.
  • One paragraph only (on {{link learn/what-is-vllm}}): the experimental Rust front end ({{cite rust/}}) and the per-family model packages in vllm/models/ ({{cite vllm/models/}}). The special code of single model families is also out of scope; llama.py is the one model example.
