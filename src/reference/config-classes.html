The @config decorator

All config classes use the decorator config from vllm/config/utils.py. It makes a {{term config-class}}: a pydantic dataclass whose settings forbid extra fields:

dataclass here is pydantic.dataclasses.dataclass ({{cite vllm/config/utils.py:20}}). This has three effects:

  • Unknown keys are an error. extra="forbid" rejects a key that is not a field. A JSON flag such as --compilation-config is parsed with pydantic, and a ValidationError becomes an argparse error ({{cite vllm/engine/arg_utils.py:369-374}}). So a misspelled key stops vllm serve at start-up.
  • Field limits are checked. Fields can use Field(default=..., ge=1), and pydantic checks the value. For example, gpu_memory_utilization must be above 0 and at most 1 ({{cite vllm/config/cache.py:212}}).
  • A class can pass its own pydantic settings. VllmConfig uses @config(config=ConfigDict(arbitrary_types_allowed=True)) ({{cite vllm/config/vllm.py:347}}).

The docstring of the decorator says that all config classes in vLLM should use it ({{cite vllm/config/utils.py:61}}).

What __post_init__ does

VllmConfig.__post_init__ runs after pydantic has made the object. It is about 830 lines long ({{cite vllm/config/vllm.py:1492-2318}}). Its docstring says: "Verify configs are valid & consistent with each other." ({{cite vllm/config/vllm.py:1493}}). These are the main steps, in code order:

  1. It sets instance_id from the clock ({{cite vllm/config/vllm.py:1495}}).
  2. It turns off prefix caching for an instance that runs only the multimodal encoder ({{cite vllm/config/vllm.py:1505-1516}}).
  3. It runs the per-architecture config hooks of the model in try_verify_and_update_config ({{cite vllm/config/vllm.py:1521}}, {{cite vllm/config/vllm.py:2714-2733}}).
  4. It decides async scheduling when the flag is not set ({{cite vllm/config/vllm.py:1664-1698}}).
  5. With enforce_eager, it turns off torch.compile and CUDA graphs ({{cite vllm/config/vllm.py:1745-1747}}).
  6. It applies the platform defaults, picks the compilation mode from the optimization level, and applies the defaults of that level ({{cite vllm/config/vllm.py:1804-1810}}, {{cite vllm/config/vllm.py:1833-1834}}).
  7. It calls the platform hook current_platform.check_and_update_config(self), which can change any part of the config ({{cite vllm/config/vllm.py:2046}}).
  8. It resolves the KV transfer settings, for example the connector name for KV offloading ({{cite vllm/config/vllm.py:2197-2199}}).

The list names only the main steps. __post_init__ also sets CUDA graph sizes, compile ranges, multimodal devices and many checks. Read {{link code/config-vllm}} for the full walk-through.

compute_hash: one key for compiled code

VllmConfig.compute_hash() collects the compute_hash() of each sub-config and adds the vLLM version. It returns the first 10 hex digits of a hash of this list ({{cite vllm/config/vllm.py:474-483}}, {{cite vllm/config/vllm.py:572-575}}). Its docstring says that the hash covers the configs that change the computation graph ({{cite vllm/config/vllm.py:460-468}}). Each sub-config decides which fields count. For example, SchedulerConfig adds max_num_batched_tokens, because LoRA buffer sizes in the compiled graph and the index width that Inductor selects depend on it ({{cite vllm/config/scheduler.py:271-280}}).

The torch.compile backend uses the hash. When compilation_config.cache_dir is not set ({{cite vllm/compilation/backends.py:1086}}), it hashes four values together: the environment hash, the config hash, the code hash and the compiler hash. The result is the name of the cache folder under VLLM_CACHE_ROOT/torch_compile_cache/ ({{cite vllm/compilation/backends.py:1059-1063}}, {{cite vllm/compilation/backends.py:1091-1097}}). So when you change --max-num-batched-tokens, the next start compiles again into a new folder.

How to read the tables

  • All config classes lists each class with its file and line, the number of fields, and the first paragraph of the class docstring.
  • What each VllmConfig attribute holds maps each attribute to its class. quant_config holds a QuantizationConfig, which is not a @config class.
  • One table per class lists each annotated line of the class body: name, type and default as source text. The last column quotes the first paragraph of the field docstring as it is. (InitVar) and (ClassVar) mark lines that are not dataclass fields.
  • Defaults are dataclass defaults. They are not always the values that vllm serve uses. EngineArgs and __post_init__ change many of them. The table {{link reference/serve-flags#tune-first | Flags you tune first}} gives the real defaults of the tuning fields.
  • Inherited fields are not copied into a subclass table. Only vllm/config/*.py is scanned, so FrontendArgs (in vllm/entrypoints/common/cli_args.py) is not here; its flags are in {{link reference/serve-flags}}.

You start vllm serve with --compilation-config '{"cudagraph_mod": "NONE"}' (one letter is missing). What happens?

Start-up stops with an argument error. CompilationConfig is a @config class with extra="forbid" ({{cite vllm/config/utils.py:71}}), so pydantic rejects the unknown key, and parse_dataclass turns the ValidationError into an argparse.ArgumentTypeError ({{cite vllm/engine/arg_utils.py:369-374}}).

 Why does SchedulerConfig say max_num_seqs = 128, while vllm serve on an 80 GB H100 uses 1024?

The dataclass default is "mainly for convenience when testing" ({{cite vllm/config/scheduler.py:62-66}}). The flag passes None ({{cite vllm/engine/arg_utils.py:1743-1749}}), and EngineArgs sets the value by GPU memory before it builds SchedulerConfig ({{cite vllm/engine/arg_utils.py:2970-2983}}, {{cite vllm/engine/arg_utils.py:2631-2635}}). This assumes that the driver reports at least 70 GiB for the card ({{cite vllm/engine/arg_utils.py:2946}}).

 You restart a server with --max-num-batched-tokens 16384 instead of 8192, and nothing else changes. Can it reuse the torch.compile cache of the first run?

No. SchedulerConfig.compute_hash includes max_num_batched_tokens ({{cite vllm/config/scheduler.py:280}}). VllmConfig.compute_hash includes the scheduler hash ({{cite vllm/config/vllm.py:500-501}}). The compile backend puts the config hash into the cache folder name ({{cite vllm/compilation/backends.py:1090-1097}}), so the new run uses a new folder and compiles again.
