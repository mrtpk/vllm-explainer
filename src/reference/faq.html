Getting started

Which model runner runs: V1 or V2?

Model Runner V2 (vllm/v1/worker/gpu/), in most cases. With VLLM_USE_V2_MODEL_RUNNER unset, use_v2_model_runner is true when Triton is installed and no unsupported feature is set ({{cite vllm/config/vllm.py:730-749}}). The worker then builds the V2 runner; else it builds the V1 runner, the fallback ({{cite vllm/v1/worker/gpu_worker.py:567-583}}). A fallback logs "Model Runner V2 does not yet support ..." ({{cite vllm/config/vllm.py:740-747}}). HiSparse and watermarking always use V2 ({{cite vllm/config/vllm.py:714-728}}). See {{link concepts/model-runner}}.

Where is V0?

Gone. Only two aliases remain: vllm.engine.llm_engine.LLMEngine is the V1 LLMEngine ({{cite vllm/engine/llm_engine.py:4-6}}), and AsyncLLMEngine is AsyncLLM ({{cite vllm/engine/async_llm_engine.py:4-6}}). The engine code is in vllm/v1/. See {{link learn/what-is-vllm}}.

How many processes does vllm serve start?

Two with the defaults: the API server and one engine core. With TP = PP = DP = 1, the executor is uni and the worker runs inside the engine core ({{cite vllm/config/parallel.py:1099-1100}}). When the world size across DP is more than 1, the executor is mp, with one worker process per GPU ({{cite vllm/config/parallel.py:1055}}). AsyncLLM always starts the engine core in its own process ({{cite vllm/v1/engine/async_llm.py:188-193}}), so VLLM_ENABLE_V1_MULTIPROCESSING=0 does not change this. See {{link concepts/architecture-overview}}.

What does vllm serve serve with no model argument?

Qwen/Qwen3-0.6B ({{cite vllm/config/model.py:155}}, {{cite vllm/entrypoints/cli/serve.py:39-40}}).

Serving

Why does my request get HTTP 200, and then the stream fails?

The route returns the streaming response before the engine has seen the request. generate() only builds an async generator; the request reaches AsyncLLM.add_request when the stream starts ({{cite vllm/entrypoints/openai/chat_completion/serving.py:396-426}}). An error after that point cannot change the status. It comes as a data: chunk with an error object, then data: [DONE] ({{cite vllm/entrypoints/openai/chat_completion/serving.py:937-943}}, {{cite vllm/entrypoints/openai/chat_completion/serving.py:504-508}}). Check every chunk for error. See {{link concepts/openai-server}}.

Why is my max_tokens lowered?

The server uses the smallest of four values: max_model_len minus the prompt length, your value (or the server default), the --override-generation-config value, and a platform limit ({{cite vllm/entrypoints/serve/utils/api_utils.py:253-270}}). It does not report the change. A prompt longer than max_model_len raises instead ({{cite vllm/entrypoints/serve/utils/api_utils.py:248-252}}).

Why is --tool-call-parser ignored?

The parser is used only together with --enable-auto-tool-choice. Without it, get_tool_parser returns None ({{cite vllm/parser/parser_manager.py:33-35}}). See {{link concepts/tool-and-reasoning-parsers}}.

Why are my guided_* fields ignored?

These fields were removed. The request models accept unknown fields, so a request with guided_json and the other guided_* fields gets HTTP 200 with unconstrained output. The server logs one WARNING ({{cite vllm/entrypoints/serve/engine/protocol.py:21-34}}, {{cite vllm/entrypoints/serve/engine/protocol.py:61-71}}). Use structured_outputs or response_format. See {{link concepts/structured-outputs}}.

Which routes does --api-key protect?

Only paths that start with /v1, /v2, /inference or /cohere ({{cite vllm/entrypoints/serve/middleware/authenticate.py:11}}, {{cite vllm/entrypoints/serve/middleware/authenticate.py:59-61}}). Other routes answer without a key. Some of them run the model:

  • /invocations on every server (next question);
  • POST /generative_scoring on every generative server ({{cite vllm/entrypoints/generate/api_router.py:52-54}}, {{cite vllm/entrypoints/generate/generative_scoring/api_router.py:28-29}});
  • /pooling, /classify, /score and /rerank on a pooling server ({{cite vllm/entrypoints/pooling/pooling/api_router.py:26-28}}, {{cite vllm/entrypoints/pooling/classify/api_router.py:26}}, {{cite vllm/entrypoints/pooling/scoring/api_router.py:37-38}}, {{cite vllm/entrypoints/pooling/scoring/api_router.py:69-70}}).

/health, /ping, /metrics, /tokenize and /scale_elastic_ep are also open. Put a proxy in front of the server and let it pass only the routes your clients need. See {{link concepts/deployment-recipes#security}}.

What is /invocations?

A SageMaker route. Every server registers /ping and /invocations ({{cite vllm/entrypoints/launchers/api_server/routers.py:40-44}}, {{cite vllm/entrypoints/serve/sagemaker/api_router.py:91-99}}). /invocations picks a handler by the shape of the body and runs the same serving objects as the /v1 routes ({{cite vllm/entrypoints/serve/sagemaker/api_router.py:98-132}}). The help text of --api-key warns about it ({{cite vllm/entrypoints/common/cli_args.py:330-336}}).

What does /scale_elastic_ep do when elastic EP is off?

The route exists on every generative server, also without --enable-elastic-ep ({{cite vllm/entrypoints/launchers/api_server/routers.py:62-66}}), and outside the --api-key prefixes. The traced results:

Why does the API server stop before any engine starts?

One cause is an environment variable with a value that does not parse. Some modules read a variable when Python imports them. For example, the engine core client imports VLLM_ENGINE_READY_TIMEOUT_S at module level ({{cite vllm/v1/engine/core_client.py:29}}), and the lambda calls int() on the text ({{cite vllm/envs.py:812-814}}). A bad value raises in the API server. Other bad values raise later, in the engine core, when it caches all variables ({{cite vllm/v1/engine/core.py:241-243}}). See {{link concepts/troubleshooting}}.

Why does VLLM_ENGINE_READY_TIMEOUT_S not stop a slow start?

With one API server, the start-up wait has no time limit. The loop only logs at DEBUG and continues until the engines are ready or a process dies ({{cite vllm/v1/engine/utils.py:1434-1446}}). The timeout is used afterwards, and while API servers wait for engines that start after them ({{cite vllm/v1/engine/core_client.py:757-768}}). See {{link tours/serve-startup}}.

Why does each stats line start with "Engine 000:"?

The periodic log line always has the engine index as a prefix, also with one engine ({{cite vllm/v1/metrics/loggers.py:176-178}}, {{cite vllm/v1/metrics/loggers.py:334-337}}). See {{link concepts/metrics-and-observability}}.

Performance

Why are custom ops off?

With the default torch.compile mode and the Inductor backend, vLLM adds "none" to the custom-op list. With compile mode NONE, for example with --enforce-eager, it adds "all" ({{cite vllm/config/vllm.py:1819-1826}}). A disabled op runs forward_native, which Inductor compiles ({{cite vllm/model_executor/custom_op.py:189-192}}). vLLM and the platform can still turn single ops on with +name. See {{link concepts/custom-ops}}.

Why is my first request slow?

Not because of model compilation: the engine core compiles, profiles and captures CUDA graphs before it reports ready ({{cite vllm/v1/engine/core.py:394-400}}, {{cite vllm/v1/worker/gpu_worker.py:983-985}}). Costs that the first requests can still pay:

  • A request with structured output waits until its grammar is compiled ({{cite vllm/v1/request.py:116-117}}). xgrammar caches compiled grammars ({{cite vllm/v1/structured_output/backend_xgrammar.py:220-223}}), so a repeated grammar is faster.
  • The prefix cache starts empty, so no request gets a hit until earlier requests fill it.
  • vllm bench serve sends no warm-up requests by default ({{cite vllm/benchmarks/serve.py:1780-1785}}).

Cold start-up is a separate question: a cold torch.compile cache makes start-up longer, not the first request. See {{link concepts/compile-and-cuda-graphs}} and {{link concepts/benchmarking}}.

What does --performance-mode do?

Two things at this commit. throughput doubles the default max_num_batched_tokens and max_num_seqs, but only when you did not set them ({{cite vllm/engine/arg_utils.py:3170-3175}}). interactivity captures CUDA graphs for every size from 1 to 32 ({{cite vllm/config/vllm.py:2552-2556}}). The docstring also names "latency-oriented kernels" and "throughput-oriented kernels" ({{cite vllm/config/vllm.py:441-445}}); no other code reads the field. See {{link concepts/tuning}}.

Why does LoRA double the CUDA graph captures?

With LoRA on, the runner captures each size for each LoRA case ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:305-306}}). With the defaults (cudagraph_specialize_lora true, specialize_active_lora false) the cases are 0 and max_loras + 1 ({{cite vllm/config/compilation.py:663}}, {{cite vllm/v1/worker/gpu/lora_utils.py:31-34}}, {{cite vllm/lora/utils.py:64-65}}). Two cases double the graphs. See {{link concepts/lora-serving}}.

Why does a new --max-num-batched-tokens compile again?

The value is part of the scheduler config hash, which is part of the compile cache key. The comment gives two reasons: LoRA buffer sizes and the Inductor index width ({{cite vllm/config/scheduler.py:271-284}}). max_num_seqs is in the hash too. See {{link concepts/compile-and-cuda-graphs}}.

Plugins

Why is my plugin not loaded?

Check these causes in order:

  1. VLLM_PLUGINS does not name it. The list filters five groups by entry-point name ({{cite vllm/plugins/__init__.py:64}}). It does not strip spaces.
  2. It is an endpoint plugin. Endpoint plugins load only when VLLM_PLUGINS names them ({{cite vllm/plugins/__init__.py:122-131}}).
  3. The import failed. The loader logs the exception and goes on ({{cite vllm/plugins/__init__.py:71-72}}).
  4. The log level hides it. The general group logs its list at DEBUG ({{cite vllm/plugins/__init__.py:48-54}}). Set VLLM_LOGGING_LEVEL=DEBUG.
  5. It is a platform plugin and VLLM_TARGET_DEVICE=cpu. The group is skipped ({{cite vllm/platforms/__init__.py:244-248}}).
  6. Your registration ran in the wrong process. A register call in a launch script reaches only that process. Put it in a general plugin.

See {{link concepts/plugin-loading}} and {{link reference/extension-points}}.

Why does +rms_norm not enable my out-of-tree op?

register_oot gives your class the in-tree class name, for example "RMSNorm" ({{cite vllm/model_executor/custom_op.py:337-339}}). enabled() builds the switch from that name ({{cite vllm/model_executor/custom_op.py:282-283}}). The in-tree class registered "rms_norm" ({{cite vllm/model_executor/layers/layernorm.py:38-39}}), so +rms_norm matches nothing and vLLM warns that it "has no effect" ({{cite vllm/config/compilation.py:1341-1361}}). Use +RMSNorm. See {{link tours/build-a-toy-plugin}}.

How many times does pre_register_and_update run?

5 times in the vllm serve front end. Four calls pass a parser: one for each serve-type parser that the CLI builds at start ({{cite vllm/entrypoints/cli/main.py:100-109}}), and one more when setup_server logs the non-default arguments ({{cite vllm/entrypoints/launchers/launcher.py:368}}, {{cite vllm/entrypoints/common/startup.py:70-71}}). Each goes through add_cli_args ({{cite vllm/engine/arg_utils.py:3257}}). The fifth call has no parser, in create_engine_config ({{cite vllm/engine/arg_utils.py:2246}}). Make the hook safe to run again. See {{link reference/extension-points#platform-hooks}}.

Why does @CustomOp.register_oot("MyOp") raise TypeError?

The first positional argument must be a class. A string reaches the last branch and raises "Decorator can only be applied to classes." ({{cite vllm/model_executor/custom_op.py:336-356}}). Write @InTreeOp.register_oot or @CustomOp.register_oot(name="InTreeOp"). The design doc shows the string form (table below).
