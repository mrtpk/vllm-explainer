Each vLLM cell cites vLLM code; each DeepInfer cell links the DeepInfer page that states it. --- DeepInfer is a small, offline, one-model engine with a C++ scheduler; vLLM is a general online serving engine with a Python scheduler and many extension points.

DeepInfer "was originally built primarily on vLLM" ({{deepinfer index | DeepInfer Explained}}). So most ideas have the same name on both sites. This page lists where the two engines differ. Use it when a DeepInfer page gives a number or a rule, and you want to know if it holds in vLLM.

  • Each vLLM cell cites the vLLM code at the pinned commit, or links the page of this site that explains it.
  • Each DeepInfer cell links the DeepInfer Explained page that states it. This site does not cite DeepInfer code.

Scheduler and KV cache

TopicDeepInfervLLM
LanguageC++ scheduler ({{deepinfer concepts/scheduler | The scheduler}}).Python (vllm/v1/core/sched/). See {{link concepts/scheduler}}.
Step kindsA step is a prefill step or a decode step, never both. A prefill starts only at attempt points: every 70 or 100 decode steps ({{deepinfer concepts/scheduler | The scheduler}}).No prefill phase and no decode phase. Each request catches up from num_computed_tokens to its token count, so one step can mix prompt chunks and decode tokens ({{cite vllm/v1/core/sched/scheduler.py:624-633}}).
Order and preemptionDecode serves the fewest output tokens first; it preempts the sequence with the most output tokens. A preempted sequence stops or is recomputed (stop_preempted_request) ({{deepinfer concepts/scheduler | The scheduler}}).Running requests first, then waiting ones ({{cite vllm/v1/core/sched/scheduler.py:713-715}}, {{cite vllm/v1/core/sched/scheduler.py:956}}). With the default FCFS policy the victim is the last running request ({{cite vllm/v1/core/sched/scheduler.py:852-858}}). Preemption always recomputes: blocks freed, computed tokens set to 0, request back at the front of the queue ({{cite vllm/v1/core/sched/scheduler.py:1676-1700}}).
Overlap of CPU and GPUZero-overhead scheduling: the CPU prepares step N+1 while the device runs step N, and step() returns tokens one step late ({{deepinfer concepts/zero-overhead-scheduling | Zero-overhead scheduling}}).Async scheduling is on by default when the configuration allows it ({{cite vllm/config/vllm.py:1664-1698}}). The engine core then runs step_with_batch_queue ({{cite vllm/v1/engine/core.py:227-229}}). See {{link concepts/async-scheduling}}.
Block size128 tokens ({{deepinfer concepts/paged-kv-cache | Paged KV cache}}).16 tokens by default ({{cite vllm/config/cache.py:182}}). When you do not set --block-size, the platform picks a size that all attention backends accept ({{cite vllm/platforms/interface.py:771-781}}).
Prefix cachingNone in the release ({{deepinfer concepts/paged-kv-cache | Paged KV cache}}).On by default when the model supports it ({{cite vllm/engine/arg_utils.py:3062-3063}}, {{cite vllm/config/model.py:2275-2291}}). See {{link concepts/prefix-caching}}.
Cache layout for mixed layer typesOne paged byte buffer for the compressed KV and the indexer keys; the sliding-window cache is a ring per sequence in a separate state buffer, with a second block manager for state slots ({{deepinfer concepts/paged-kv-cache | Paged KV cache}}, {{deepinfer concepts/sliding-window-attention | Sliding-window attention}}).KV cache groups, one per kind of layer, with one shared block pool. The coordinator is NoPrefixCache, Unitary (one group) or Hybrid ({{cite vllm/v1/core/kv_cache_coordinator.py:995-1024}}). See {{link concepts/hybrid-kv-cache}}.

Numbers that change between the sites

Examples on DeepInfer pages use DeepInfer's settings. Recompute them with the vLLM defaults:

  • Blocks per prompt. A 1,000-token prompt needs ⌈1,000 / 16⌉ = 63 blocks in vLLM and ⌈1,000 / 128⌉ = 8 blocks in DeepInfer.
  • Tokens per decode step. DeepInfer sends 1 + 5 rows per request in a decode step by default ({{deepinfer concepts/speculative-decoding | Speculative decoding}}). vLLM sends 1 row per request when speculative decoding is off.
  • Wait for the first prefill. A new DeepInfer request waits for the next attempt point ({{deepinfer concepts/scheduler | The scheduler}}). In vLLM, a waiting request can start in the next step when the token budget and the KV cache allow it ({{cite vllm/v1/core/sched/scheduler.py:956}}).
What is the default KV block size in each engine, and which one has prefix caching?

DeepInfer uses 128 tokens and has no prefix cache in its release ({{deepinfer concepts/paged-kv-cache | Paged KV cache}}). vLLM uses 16 tokens by default ({{cite vllm/config/cache.py:182}}) and turns prefix caching on for models that support it ({{cite vllm/engine/arg_utils.py:3062-3063}}).

 Both engines have something called DSpark. Is it on by default in vLLM?

No. dspark is one value of the speculative method ({{cite vllm/config/speculative.py:70}}), and speculative decoding needs --speculative-config. Adaptive verification, which sizes the verification budget from per-request confidence, is a separate opt-in field ({{cite vllm/config/speculative.py:559-561}}).

 A DeepInfer page says that a step is either a prefill step or a decode step. Why can a vLLM metrics dashboard not show separate prefill-step and decode-step times?

The vLLM scheduler has no phases. Each request only catches up from its computed tokens to its token count, so one step holds prompt chunks and decode tokens together ({{cite vllm/v1/core/sched/scheduler.py:624-633}}). The per-request metrics measure intervals of one request instead, for example the prefill interval from the first SCHEDULED event to the first token ({{cite vllm/v1/metrics/stats.py:599-601}}).
