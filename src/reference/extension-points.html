This page is the lookup table. The guided version, with diagrams and a start-up timeline, is {{link concepts/plugin-map}}. Read that page first if the three kinds of {{term extension-point | extension points}} are new to you. Every row here cites the code at the pinned commit; open the linked page for the explanation.

Words in the tables:

  • Front end: the {{term front-end}} process of vllm serve (API server, AsyncLLM). With more than one API server, each one is a front end.
  • Engine core: the {{term engine-core}} process, one per data-parallel rank.
  • Workers: the {{term worker}} processes. With TP = PP = DP = 1 there is no worker process: the worker runs inside the engine core process ({{cite vllm/config/parallel.py:1099-1100}}). Then "workers" means the engine core process.
  • Registry subprocess: a short-lived process that inspects a model class. It runs only on a cache miss of the model-info cache, and it loads the general plugins first ({{cite vllm/model_executor/models/registry.py:1608-1612}}).

The six entry-point groups

vLLM finds these with importlib.metadata. Your package publishes an {{term entry-point}} in a {{term plugin-group}}; no other step is necessary. Five group names are constants in one file ({{cite vllm/plugins/__init__.py:16-30}}). The sixth, vllm.logits_processors, is in the sampler code of Model Runner V2 ({{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:34}}).

Registries that a general plugin fills

A registry is a module-level table plus a register function. The table lives in one process, so the register call must run in each process that reads the table. A {{term general-plugin}} does this, because every process runs it. Code in your own launch script reaches only that process. The config hooks apply_config_platform_defaults and check_and_update_config do not run only in the front end. The engine core process calls vllm_config.__post_init__() again ({{cite vllm/v1/engine/core.py:1336-1337}}), so both hooks run there too. Your hooks must give the same result when they run again on a config that they have already changed. And pre_register_and_update runs 5 times in the front end, not once.

How many times a general plugin runs

A general plugin runs once in each process (the guard at {{cite vllm/plugins/__init__.py:82-85}}). So the count is the number of processes. Add 1 for each registry subprocess, which runs only on a cache miss of the model-info cache.

vllm serve withProcesses that run itRuns
TP = 1 (default)front end, engine core (the worker is inside it)2
TP = 2front end, engine core, 2 workers4
TP = 4front end, engine core, 4 workers6

The process layout comes from the executor choice: mp when the world size across DP is more than 1, else uni ({{cite vllm/config/parallel.py:1055}}, {{cite vllm/config/parallel.py:1099-1100}}). The page {{link concepts/executors-and-workers}} explains it.

Which of the six entry-point groups ignores VLLM_PLUGINS, and which one loads nothing when VLLM_PLUGINS is unset?

vllm.logits_processors ignores it, because its loader calls entry_points() directly ({{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:46}}). vllm.endpoint_plugins loads nothing when the variable is unset ({{cite vllm/plugins/__init__.py:122-131}}).

 Your platform's check_and_update_config appends "+my_op" to the custom-op list. You serve with TP = 2. How many times does the hook run at start-up, and what can go wrong?

At least twice: once in the front end ({{cite vllm/config/vllm.py:2046}}) and once in the engine core, which runs __post_init__ again ({{cite vllm/v1/engine/core.py:1336-1337}}). The engine core gets the config that the front end already changed, so a hook that appends without a check adds the entry a second time. Make the hook give the same result when it runs again.

 A general plugin calls register_quantization_config("fp8") and register_model_loader("auto"). Neither raises. What happens to the built-in entries, and what does the log show at INFO?

Both registries overwrite. The quantization registry logs at DEBUG only ({{cite vllm/model_executor/layers/quantization/__init__.py:89-95}}), so INFO shows nothing for it. The model loader registry logs a WARNING ({{cite vllm/model_executor/model_loader/__init__.py:101-107}}) and then an INFO line "Registered model loader" ({{cite vllm/model_executor/model_loader/__init__.py:113-117}}). The general group's own list of plugins is at DEBUG ({{cite vllm/plugins/__init__.py:48-54}}).
