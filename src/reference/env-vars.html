This page tells how and when vLLM reads them, lists the 15 that a serving operator meets first, names the known problems, and lists every variable with its default and the code that reads it. --- Each VLLM_* setting is a lambda in one dict in vllm/envs.py; a read of envs.X calls the lambda, until a process turns on the cache.

Use this page in two ways. To learn the mechanism, read the first three sections. To look up one variable, go to All environment variables, or search for its name. The script tools/gen_env_vars.py makes the big tables from vllm/envs.py. The text above the tables is written by hand from the code.

How vLLM declares an environment variable

An {{term environment-variable}} is a named text value that a process gets from its parent when it starts. vLLM declares each of its variables two times in vllm/envs.py.

  1. For type checkers. The if TYPE_CHECKING: block at the top of the file gives each variable a type and a default. Python does not run this block, so these defaults have no effect at run time:
  2. For the run time. The dict environment_variables maps each name to a function with no arguments, mostly a lambda ({{cite vllm/envs.py:618}}). The function reads os.environ, parses the text and returns the value. Its fallback value is the real default:

Other code imports the module (import vllm.envs as envs) and reads envs.VLLM_LOGGING_LEVEL. The module has no such attribute. So Python calls the module-level __getattr__, which calls the lambda:

Two more helpers use the dict. envs.is_set("NAME") tells if the variable is in os.environ at all ({{cite vllm/envs.py:2344-2348}}). __dir__ returns all the names ({{cite vllm/envs.py:2340-2341}}).

When vLLM reads a variable

A read through envs.X runs the lambda again each time. So a change to os.environ has an effect at the next read. This stays true until the process calls enable_envs_cache():

The function wraps __getattr__ in functools.cache and then reads every variable one time. After that, each read returns the cached value. Two places call it, at the end of their start-up:

  • the {{term engine-core}}, as the last statement of EngineCore.__init__, after the executor and the KV cache are ready ({{cite vllm/v1/engine/core.py:241-243}}, {{cite vllm/v1/engine/core.py:147}}, {{cite vllm/v1/engine/core.py:160}}). This also covers a worker that runs inside the engine core process;
  • each {{term worker}} process of the multiprocessing executor, at the end of WorkerProc.__init__ ({{cite vllm/v1/executor/multiproc_executor.py:708-710}}).

No code in vllm/entrypoints/ calls it. So the {{term front-end}} process of vllm serve reads the environment again at each access. A code comment in the metrics code says the same: "processes that never enable the envs cache (the API server)" ({{cite vllm/v1/metrics/stats.py:479-481}}). cleanup_dist_env_and_memory removes the cache again with disable_envs_cache() ({{cite vllm/distributed/parallel_state.py:2543-2544}}).

Some code copies a value one time, at import, and the lambda never runs again for that copy:

  • from vllm.envs import VLLM_ENGINE_READY_TIMEOUT_S in the engine core client ({{cite vllm/v1/engine/core_client.py:29}}). The start-up wait uses this copy ({{cite vllm/v1/engine/core_client.py:757-759}}).
  • The class body of the front-end arguments: log_error_stack: bool = envs.VLLM_SERVER_DEV_MODE ({{cite vllm/entrypoints/common/cli_args.py:201}}).
  • The default logging dict of vllm/logger.py, a module-level value ({{cite vllm/logger.py:75}}, {{cite vllm/logger.py:82}}).

Child processes get a copy of the parent environment when they start. The vllm CLI sets VLLM_WORKER_MULTIPROC_METHOD=spawn when the variable is not set ({{cite vllm/entrypoints/common/startup.py:147-149}}). The engine core processes and the worker processes get their start method from get_mp_context() ({{cite vllm/v1/engine/utils.py:256}}, {{cite vllm/v1/executor/multiproc_executor.py:723}}). With spawn, they start as new Python interpreters. They import vllm.envs again and read the environment that they got at start.

Set every VLLM_* variable in the shell or the container spec before vllm serve starts. A change after start-up does not reach the processes that already run. Also, the cached values in the engine core and the workers do not change.

How to read the tables

  • Groups. envs.py has only two section comments: "Installation Time Env Vars" and "Runtime Env Vars" ({{cite vllm/envs.py:619}}, {{cite vllm/envs.py:710}}). The group "Installation time" keeps the code's placement. The script splits the runtime variables into topics by name patterns. The topics are the tool's choice, not a structure in the code.
  • Type and default come from the TYPE_CHECKING block. When the lambda falls back to another value, the row says so (but the read falls back to). A few variables have no TYPE_CHECKING line; the row then shows the fallback of the lambda.
  • Description is the code comment above the dict key, quoted as it is. It is not in Simplified Technical English.
  • Used in vllm/ counts the lines that read envs.NAME, from vllm.envs import NAME or envs.is_set("NAME"), and links the first five. "No envs.* use" means that no Python file in vllm/ reads the variable through envs. The row then names other files that mention it, for example setup.py or C++ code.

Known issues

For these variables, the type hint says one default, but the lambda falls back to another. The lambda value is the real one.

A declared variable that no code reads

VLLM_XLA_CHECK_RECOMPILATION is in the dict ({{cite vllm/envs.py:1086-1088}}), but no file in the repository mentions the name outside envs.py. So the variable has no effect.

Variables read outside envs.py

Some names are in the dict, but code outside vllm/, or code that reads os.environ, uses them:

  • C++: VLLM_ROCM_SLEEP_MEM_CHUNK_SIZE is read with getenv in csrc/cumem_allocator.cpp ({{cite csrc/cumem_allocator.cpp:26}}). The lambda and the envs cache do not apply.
  • Rust: VLLM_CHAT_TEMPLATE_FUEL is read by the experimental Rust front end ({{cite rust/src/chat/src/renderer/hf/mod.rs:106}}). No Python file outside envs.py reads it, so the Python front end does not use it.
  • Python, with os.environ: VLLM_ENABLE_CUDA_COMPATIBILITY and VLLM_CUDA_COMPATIBILITY_PATH ({{cite vllm/env_override.py:62-69}}), and VLLM_TRITON_FORCE_FIRST_CONFIG ({{cite vllm/env_override.py:976}}). These reads skip the lambda and the envs cache.
  • Build time only: MAX_JOBS, NVCC_THREADS, VLLM_USE_PRECOMPILED and other variables of the "Installation time" group have no reader in vllm/. setup.py loads vllm/envs.py as a separate module and reads them through it ({{cite setup.py:56}}, {{cite setup.py:218}}), so for these variables the lambda still gives the value. The Docker files also set them. The generated table names those files.

You start vllm serve with VLLM_DEBUG_LOG_API_SERVER_RESPONSE=1. Does the API server log its responses?

No. The lambda compares the lower-case text with "true", so "1" gives False ({{cite vllm/envs.py:830-832}}). Use true for this variable. Other booleans need 1, so check the lambda of each variable.

 A test changes os.environ["VLLM_LOG_STATS_INTERVAL"] while the server runs. Which processes see the new value?

Only the front-end process, and only at the next read. The front end never calls enable_envs_cache(), so each envs.X read runs the lambda again ({{cite vllm/envs.py:2297-2298}}). The engine core and the workers are other processes with their own copy of the environment. They cache their values at the end of start-up ({{cite vllm/v1/engine/core.py:241-243}}, {{cite vllm/v1/executor/multiproc_executor.py:708-710}}).

 You set VLLM_ENABLE_V1_MULTIPROCESSING=0 to run the engine core inside the API server process of vllm serve. Does it work? And what does VLLM_ENABLE_V1_MULTIPROCESSING=true do?

It does not work. Only LLMEngine reads the variable ({{cite vllm/v1/engine/llm_engine.py:170}}, {{cite vllm/v1/engine/llm_engine.py:186}}). AsyncLLM always calls EngineCoreClient.make_async_mp_client, which starts the engine core in a background process ({{cite vllm/v1/engine/async_llm.py:188-193}}). The text true raises ValueError at the first read, because the lambda calls int() on it ({{cite vllm/envs.py:1442-1444}}).
