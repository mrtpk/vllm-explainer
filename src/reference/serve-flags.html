How a config field becomes a flag

vllm serve builds its parser in make_arg_parser. It adds five arguments by hand: the positional model_tag, --headless, --api-server-count, --config and --grpc. Then it adds the front-end flags and the engine flags ({{cite vllm/entrypoints/common/cli_args.py:429-466}}):

The engine flags come from EngineArgs.add_cli_args. For each config class, it calls get_kwargs(XConfig), makes one argument group with the class name as its title, and adds one flag per field. The flag name is written by hand. The type, default, choices and help come from the field. Sometimes the code replaces the field default. In this excerpt, three scheduler flags get the default None:

get_kwargs returns a copy of the cached result of _compute_kwargs ({{cite vllm/engine/arg_utils.py:324}}, {{cite vllm/engine/arg_utils.py:443-453}}). _compute_kwargs reads each dataclass field ({{cite vllm/engine/arg_utils.py:324-440}}):

  • Default: the field default, or the result of its default factory ({{cite vllm/engine/arg_utils.py:339-352}}).
  • Help: the string literal after the field, read by get_attr_docs ({{cite vllm/engine/arg_utils.py:355-356}}, {{cite vllm/config/utils.py:201-215}}). The parser reads these strings only when the command line contains --help (or when mkdocs is loaded), because that is slow ({{cite vllm/engine/arg_utils.py:285-288}}, {{cite vllm/engine/arg_utils.py:327}}).
  • Type: from the type hint. A dataclass type takes JSON. A bool gets BooleanOptionalAction (a bool | str | None field takes an optional text value instead). A Literal gives the choices. A list, tuple or set takes several values. Some int fields accept 1k, 2M or 1G ({{cite vllm/engine/arg_utils.py:367-425}}).

Flag pairs: --enable-x and --disable-x

FlexibleArgumentParser replaces BooleanOptionalAction with EnableDisableAction ({{cite vllm/utils/argparse_utils.py:179}}). For a flag that starts with --enable-, it adds the opposite --disable- flag, and the reverse. The form --no-enable-x still works, but --help does not show it ({{cite vllm/utils/argparse_utils.py:120-151}}). Other boolean flags get the normal pair, for example --enforce-eager and --no-enforce-eager.

Other parser rules

  • Dashes and underscores. --max_num_seqs and --max-num-seqs are the same flag. The parser changes _ to - in the flag name ({{cite vllm/utils/argparse_utils.py:374-394}}).
  • JSON flags. A flag that takes a dataclass also accepts its keys one by one, for example -cc.mode=3 ({{cite vllm/config/vllm.py:405-406}}, {{cite vllm/utils/argparse_utils.py:462-491}}).
  • Optimization level. -O3 is short for --optimization-level 3 ({{cite vllm/utils/argparse_utils.py:395-399}}).
  • Config file. --config file.yaml reads flags from a YAML file ({{cite vllm/utils/argparse_utils.py:371-372}}).
  • Help by group. --help=ModelConfig shows one group, and --help=all shows all flags ({{cite vllm/utils/argparse_utils.py:384-386}}, {{cite vllm/utils/argparse_utils.py:241-252}}).

The model: positional, not --model

Give the model as the first positional argument: vllm serve Qwen/Qwen3-0.6B. The positional value goes into args.model ({{cite vllm/entrypoints/cli/serve.py:55-57}}). If you write --model X, the parser logs a warning that the option will be removed, and moves X to the front ({{cite vllm/utils/argparse_utils.py:324-353}}). With no model, the default is Qwen/Qwen3-0.6B ({{cite vllm/config/model.py:155}}). vllm serve --help does not list --model, because add_cli_args skips it when the command line contains both serve and --help ({{cite vllm/engine/arg_utils.py:961-962}}).

How the flags reach VllmConfig

  1. AsyncEngineArgs.from_cli_args(args) copies each parsed value into the EngineArgs field of the same name ({{cite vllm/entrypoints/launchers/api_server/entry.py:52}}, {{cite vllm/engine/arg_utils.py:1962-1970}}).
  2. create_engine_config(usage_context=OPENAI_API_SERVER) builds the sub-configs ({{cite vllm/entrypoints/launchers/api_server/entry.py:82}}). On the way, it replaces the None defaults. Chunked prefill and prefix caching come from the model ({{cite vllm/engine/arg_utils.py:2275}}), and the scheduler limits come from the GPU memory ({{cite vllm/engine/arg_utils.py:2631-2635}}).
  3. It makes one {{term vllm-config}} ({{cite vllm/engine/arg_utils.py:2870}}). VllmConfig.__post_init__ checks the sub-configs together and sets more defaults, for example the compilation mode and async scheduling. See {{link reference/config-classes}} and {{link concepts/config-system}}.

All flags

The script rebuilds the parser from the source with Python's ast module. It does not import vLLM. This has four results:

  • Plugins and platforms can add or change flags at run time ({{cite vllm/engine/arg_utils.py:3243}}, {{cite vllm/engine/arg_utils.py:3257}}). The table does not show these changes.
  • Choices that the code computes at run time show as source text.
  • Defaults are source text, for example CompilationConfig(). An envs.X default depends on the environment.
  • The help column has only the first paragraph of the field docstring. It does not show the text that the code appends.

The docstring of the script lists all limits.

It works. EnableDisableAction keeps the --no- form for old scripts, but hides it from the help. The help shows --enable-prefix-caching and --disable-prefix-caching ({{cite vllm/utils/argparse_utils.py:120-145}}).

 You serve a decoder model on one GPU with 48 GiB of memory and set no scheduler flags. What are max_num_seqs and max_num_batched_tokens? And with --performance-mode throughput?

48 GiB is below 70 GiB, so the defaults are 256 requests and 2048 tokens ({{cite vllm/engine/arg_utils.py:2984-2992}}). Throughput mode doubles both values that you did not set: 512 and 4096 ({{cite vllm/engine/arg_utils.py:3171-3175}}). Chunked prefill is on for this model, so the max_model_len floor does not apply ({{cite vllm/engine/arg_utils.py:3181-3186}}).

 The generated table says that the default of --enable-chunked-prefill is None, and SchedulerConfig says True. For a Whisper-style encoder-decoder model, is chunked prefill on?

No. EngineArgs.add_cli_args passes None, and _set_default_chunked_prefill_and_prefix_caching_args replaces it with model_config.is_chunked_prefill_supported ({{cite vllm/engine/arg_utils.py:3031-3035}}). That property returns False for a generative encoder-decoder model ({{cite vllm/config/model.py:2229-2233}}). So vllm serve never uses the dataclass value True ({{cite vllm/config/scheduler.py:134}}).
