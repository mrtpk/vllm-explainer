The idea

BF16, FP8 and FP4 are number formats with fewer bits per value, and block scales map the small values back to real values ({{deepinfer learn/number-formats | Number formats}}). A quantized checkpoint is a model folder that stores some tensors in such a small format. This page explains which tensors, how the checkpoint says it, and what that does to memory in a server.

Three families

  • {{term weight-only-quantization | Weight-only}} (W4A16, W8A16). Only the weights are small, for example 4-bit integers. The kernel expands them to 16 bits and multiplies with 16-bit activations. AWQ and GPTQ are the common 4-bit methods. This saves memory and memory bandwidth, so it helps decode, which reads all weights for each step. It does not make the multiply itself cheaper.
  • Weight and activation ({{term w8a8}}). Weights and the activations that enter each linear layer are 8-bit, FP8 or INT8. The GPU then runs the multiply in 8 bits. On GPUs with FP8 tensor cores (for example NVIDIA Hopper), the FP8 peak is about twice the BF16 peak. This is general knowledge, not from the vLLM repository. This helps prefill and large batches.
  • FP4 (NVFP4, MXFP4). 4-bit floating point with a scale for each small block of values. On the newest GPUs, weights and activations can both be FP4 (W4A4). On other GPUs, vLLM can run some FP4 checkpoints weight-only.

Scales: per tensor, per channel, per group, per block

A small format has a small range. So each group of values gets a scale: real value ≈ stored value × scale. The checkpoint stores the scales next to the weights. The group size is a trade-off: more scales give better accuracy but use more memory.

GranularityOne scale forExample for a weight [4096, 4096]

Activations change with every request. So their scales come from calibration data (static, one fixed scale), or from the live values (dynamic). A dynamic scheme computes, for example, one scale per token in the kernel.

The KV cache is separate

{{term kv-cache-quantization}} stores the keys and values in a small format, normally FP8. It is a separate choice from the weight format. You can serve a BF16 model with an FP8 KV cache, or an AWQ model with a BF16 KV cache. FP8 KV halves the bytes per token, so the same memory holds twice the tokens.

How a checkpoint says that it is quantized

A Hugging Face model folder has a config.json ({{link learn/hf-checkpoints}}). A quantized checkpoint adds a quantization_config object to it. The key quant_method names the format. The other keys depend on the format:

"quantization_config": {
  "quant_method": "awq",
  "bits": 4,
  "group_size": 128,
  "zero_point": true
}

Common values of quant_method are awq, gptq, fp8, compressed-tensors (from llm-compressor) and modelopt (from NVIDIA ModelOpt). A compressed-tensors config has config_groups. Each group says, for a list of target layers, how the weights and the input_activations are quantized.

Memory math: an 8B model

Take a Llama-3.1-8B-shaped model: 8.03 billion weights. 6.98 billion are in the linear layers of the 32 decoder layers. 1.05 billion are in the embedding and the LM head, which many quantized checkpoints keep in BF16.

WeightsBytes per linear weightWeights in GBFree for KV on a 24 GB GPUKV tokens (BF16 KV)KV tokens (FP8 KV)

The assumptions: 1 GB = 109 bytes, and the GPU has 24 GB. The model is untied, with a vocabulary of 128,256 tokens. The computation: the budget is 24 GB × 0.92 (the default gpu_memory_utilization, {{cite vllm/config/cache.py:212}}) = 22.1 GB. The KV cache needs 32 layers × 8 KV heads × 128 × 2 (K and V) × 2 bytes = 128 KiB per token in BF16. For FP8 weights, 22.1 − 9.1 = 13.0 GB, and 13.0 GB / 131,072 bytes = 99,200 tokens. The INT4 row counts one 16-bit scale and one 4-bit zero point per group of 128 weights, as AWQ stores them.

The table ignores the activation memory, the CUDA graph memory and the other buffers that vLLM measures at start-up. A real server has less free memory. But a card that is sold as "24 GB" usually has 24 GiB (25.8 × 109 bytes). Its budget is then about 1.6 GB larger. The ratios stay about the same: FP8 weights double the KV room here, and INT4 weights almost triple it.

An everyday comparison

Think of a photo library. Weight-only quantization is like small JPEG files that you open to full size when you look at them. They use less disk space, but the viewing work is the same. W8A8 is like a viewer that can show the small files directly, without the expand step. The KV cache is the stack of photos on your desk: if each one is smaller, more of them fit.

The comparison stops here: a JPEG loses detail in a fixed way. Quantization methods such as AWQ and GPTQ choose the scales with calibration data, to keep the error small where the model is sensitive.

In vLLM

This is a basics page, so this part gives only pointers. The page {{link concepts/quantization-plugins}} explains how a quantization method plugs into the layers.

  1. The flag. --quantization / -q selects a method ({{cite vllm/engine/arg_utils.py:985}}). Its default is None. Then vLLM reads quantization_config from the model config; without one, the weights are not quantized ({{cite vllm/config/model.py:264-268}}).
  2. Detection. ModelConfig._verify_quantization() runs in __post_init__ ({{cite vllm/config/model.py:922}}). It reads quant_method and asks each method class whether it wants to take over the checkpoint ({{cite vllm/config/model.py:1388-1462}}).
  3. The list. QuantizationMethods has 30 names: 24 methods such as awq, gptq, fp8, compressed-tensors, modelopt_fp4 and mxfp4, and 6 short names for online quantization such as fp8_per_tensor ({{cite vllm/model_executor/layers/quantization/__init__.py:15-48}}).
  4. The KV cache. --kv-cache-dtype has the default "auto" ({{cite vllm/config/cache.py:232}}). A KV format in the checkpoint wins first; otherwise "auto" means the model dtype (next deep dives).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

  1. Read the file. get_config() takes quantization_config from config.json. Older ModelOpt checkpoints keep it in a separate hf_quant_config.json, and vLLM reads that file instead ({{cite vllm/transformers_utils/config.py:945-958}}).
  2. Normalize. _normalize_quantization_config() also accepts the key compression_config of compressed-tensors. It sets quant_method for ModelOpt checkpoints from their quant_algo (FP8 → modelopt, NVFP4 → modelopt_fp4). It lower-cases the name and writes compressed_tensors as compressed-tensors ({{cite vllm/transformers_utils/model_arch_config_convertor.py:241-281}}). For multimodal models it also looks in the text config ({{cite vllm/transformers_utils/model_arch_config_convertor.py:283-290}}).
  3. Overrides. _verify_quantization() tries all methods; the methods in the overrides list go last, in a fixed order ({{cite vllm/config/model.py:1396-1426}}). Each class can return a better name for the checkpoint ({{cite vllm/config/model.py:1429-1450}}). For example, on a GPU an AWQ checkpoint becomes auto_awq ({{cite vllm/model_executor/layers/quantization/auto_awq.py:262-286}}), and a GPTQ checkpoint becomes auto_gptq ({{cite vllm/model_executor/layers/quantization/auto_gptq.py:214-233}}).
  4. Compare with the flag. Without --quantization, vLLM uses the detected method. With a flag that does not match the checkpoint, it raises ValueError ({{cite vllm/config/model.py:1452-1462}}).
  5. Check the platform. An unknown name raises ValueError, and the platform can reject a method ({{cite vllm/config/model.py:1464-1470}}). Deprecated methods (fbgemm_fp8, fp_quant) need --allow-deprecated-quantization ({{cite vllm/config/model.py:1472-1485}}, {{cite vllm/model_executor/layers/quantization/__init__.py:52-55}}).
  6. Build the config object. VllmConfig._get_quantization_config() makes the QuantizationConfig from the checkpoint dict. It raises if the GPU compute capability is too low or the model dtype is not supported ({{cite vllm/config/vllm.py:898-931}}).

The name maps to a class in get_quantization_config(): for example awq, awq_marlin and auto_awq all map to AutoAWQConfig ({{cite vllm/model_executor/layers/quantization/__init__.py:156-185}}). A plugin can add a new name with register_quantization_config() ({{cite vllm/model_executor/layers/quantization/__init__.py:61}}).

compressed-tensors schemes. One checkpoint format covers many schemes. vLLM has one scheme class for each, for example W8A8Fp8, W8A8Int8, WNA16, W4A4Fp4 (NVFP4) and W4A4Mxfp4 ({{cite vllm/model_executor/layers/quantization/compressed_tensors/schemes/}}). The NVFP4 scheme uses a group size of 16 and packs two FP4 values in one byte ({{cite vllm/model_executor/layers/quantization/compressed_tensors/schemes/compressed_tensors_w4a4_nvfp4.py:32}}, {{cite vllm/model_executor/layers/quantization/compressed_tensors/schemes/compressed_tensors_w4a4_nvfp4.py:52-58}}). The MXFP4 class comment says: E8M0 scales for groups of 32, true W4A4 on SM100+ with FlashInfer, otherwise W4A16 with Marlin ({{cite vllm/model_executor/layers/quantization/compressed_tensors/schemes/compressed_tensors_w4a4_mxfp4.py:25-37}}).

You can also quantize a normal BF16 checkpoint while vLLM loads it. This is online quantization. The 6 short names in QuantizationMethods are for this: fp8_per_tensor, fp8_per_block, fp8_per_channel, int8_per_channel_weight_only, nvfp4_per_token and mxfp8 ({{cite vllm/model_executor/layers/quantization/__init__.py:43-48}}). mxfp4 and mxfp8 are also checkpoint formats. They mean online quantization only when the checkpoint has no quantization metadata ({{cite vllm/config/quantization.py:233-235}}).

The loader still accepts it, if the checkpoint has no quantization config. It logs a deprecation warning that names fp8_per_tensor as the new flag. Then it uses the fp8_per_tensor online config ({{cite vllm/model_executor/model_loader/weight_utils.py:354-363}}). Fp8Config itself accepts only FP8 checkpoint configs, and raises an error for others ({{cite vllm/model_executor/layers/quantization/fp8.py:105-112}}, {{cite vllm/model_executor/layers/quantization/fp8.py:158-160}}). Many older guides still show --quantization fp8 for a BF16 model. Use the new name.

 
vllm serve meta-llama/Llama-3.1-8B-Instruct --quantization fp8_per_tensor

Online quantization saves weight memory, but it uses no calibration data. A checkpoint that a tool such as llm-compressor or ModelOpt made with calibration is usually more accurate.

The flag is --kv-cache-dtype ({{cite vllm/engine/arg_utils.py:1387}}). The field default is "auto", and the allowed names include fp8, fp8_e4m3, fp8_e5m2, nvfp4 and several per-head INT and FP formats ({{cite vllm/config/cache.py:44-63}}, {{cite vllm/config/cache.py:232-244}}). "auto" goes through three places:

  1. ModelOpt checkpoints. EngineArgs resolves "auto" before it makes the CacheConfig ({{cite vllm/engine/arg_utils.py:2285-2288}}, {{cite vllm/engine/arg_utils.py:2300}}). resolve_kv_cache_dtype_string() reads the KV algorithm from quantization_config ({{cite vllm/utils/torch_utils.py:503-521}}). But get_kv_cache_quant_algo_string() reads it only when quant_method starts with modelopt; for other methods it returns None ({{cite vllm/utils/torch_utils.py:457-458}}, {{cite vllm/utils/torch_utils.py:500}}).
  2. llm-compressor checkpoints. The attention layer checks the kv_cache_scheme of the quantization config. If the dtype is still "auto", it sets "fp8" ({{cite vllm/model_executor/layers/attention/attention.py:281-291}}). An explicit --kv-cache-dtype wins.
  3. Everything else. "auto" means the model dtype, for example BF16 ({{cite vllm/utils/torch_utils.py:524-529}}).

The comment in the attention layer says that resolve_kv_cache_dtype_string normally resolves the kv_cache_scheme case ({{cite vllm/model_executor/layers/attention/attention.py:284-286}}). That function handles only ModelOpt configs. For llm-compressor checkpoints, the attention layer is the place that actually sets FP8.

Scales. An FP8 KV cache needs a scale for K and V. A checkpoint can bring them; the attention layer reads the scheme, for example attn_head strategy for one scale per head ({{cite vllm/model_executor/layers/attention/attention.py:293-297}}). The page {{link concepts/quantization-plugins}} explains how the scales load.

What can go wrong

  • The flag does not match the checkpoint. --quantization fp8 on an AWQ checkpoint raises "Quantization method specified in the model config (awq) does not match ..." ({{cite vllm/config/model.py:1456-1462}}). Leave the flag out for a quantized checkpoint; vLLM detects the method.
  • --quantization fp8 on a BF16 model. It still works, but it logs a deprecation warning and runs as fp8_per_tensor ({{cite vllm/model_executor/model_loader/weight_utils.py:356-363}}). Use fp8_per_tensor or another online short name.
  • The GPU is too old. Each method has a minimum compute capability; vLLM stops at start-up below it ({{cite vllm/config/vllm.py:910-918}}).
  • The dtype does not fit the method. Some methods support only FP16 or only BF16 activations. Start-up then fails with "is not supported for quantization method" ({{cite vllm/config/vllm.py:919-925}}). Set --dtype to a supported type.
  • An FP8 KV cache without good scales. FP8 KV halves KV memory, but without calibrated scales the accuracy can drop. Test the quality of your task before you use it in production.
  • Docs that show old flags. Guides from older versions use --quantization fp8 for online quantization. The code marks it as deprecated ({{cite vllm/model_executor/model_loader/weight_utils.py:357-360}}). Use the new short names.

Why it matters. The weight format decides how much GPU memory is left for the KV cache, and so how many requests the server can hold at once. The activation format decides how fast prefill and large batches run. Pick both on purpose, and keep the KV cache format as a separate decision.

What is the difference between W4A16 and W8A8?

W4A16 stores only the weights in 4 bits; the activations and the multiply stay in 16 bits. W8A8 stores weights and activations in 8 bits, so the multiply runs in 8 bits too.

 You start vllm serve with an AWQ checkpoint and no --quantization flag. How does vLLM know that the model is quantized?

It reads quantization_config.quant_method from config.json ({{cite vllm/config/model.py:1389-1392}}). On a GPU, the AWQ class takes over the name and the method becomes auto_awq ({{cite vllm/model_executor/layers/quantization/auto_awq.py:267-284}}).

 An 8B model has 6.98 billion linear weights and 1.05 billion embedding and LM-head weights in BF16. About how many GB do the weights need with FP8 linear layers?

The FP8 linear weights need 6.98 GB (1 byte each). The BF16 embedding and LM head need 1.05 × 2 = 2.1 GB. Together that is about 9.1 GB, plus a little for the scales.

 A compressed-tensors checkpoint has an FP8 kv_cache_scheme. You start vLLM without --kv-cache-dtype. What KV dtype do you get, and which code decides it?

FP8. resolve_kv_cache_dtype_string() returns "auto" for this checkpoint, because it reads only ModelOpt configs ({{cite vllm/utils/torch_utils.py:457-458}}). The attention layer then sees the kv_cache_scheme and the dtype "auto", and it sets "fp8" ({{cite vllm/model_executor/layers/attention/attention.py:287-291}}).

 Why does a BF16 KV cache hold only 45,900 tokens next to BF16 weights on a 24 GB GPU, in this page's example? Give the computation.

The budget is 24 GB × 0.92 = 22.1 GB. The BF16 weights take 16.1 GB, so 6.0 GB are left. One token needs 32 × 8 × 128 × 2 × 2 = 131,072 bytes, and 6.0 GB / 131,072 B ≈ 45,900 tokens. The default 0.92 comes from the config ({{cite vllm/config/cache.py:212}}). Activations and other buffers make the real number lower.
