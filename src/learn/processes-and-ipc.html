This page explains the basics of each channel. --- vllm serve runs as several processes that talk through ZMQ sockets and a shared-memory ring buffer, so CPU work does not slow the GPU loop.

The idea

Why one engine uses several processes

Python runs the bytecode of only one thread at a time in a process: the global interpreter lock (GIL) does this. A serving engine has a lot of CPU work. It parses HTTP and JSON, applies the chat template, tokenizes and detokenizes text, and schedules the next step. If all of this shared one process with the loop that feeds the GPU, the GPU would wait for Python.

vLLM therefore splits the work. The design document says that V1 "uses a multi-process architecture to separate concerns and maximize throughput" ({{cite docs/design/arch_overview.md:69}}):

  • The API server process (the {{term front-end}}) does the HTTP and text work.
  • The engine core process runs the scheduler loop. It does no HTTP or text work, so it can start the next step at once. With one GPU, it also holds the worker.
  • A worker process owns one GPU when there are two or more GPUs per engine.
  • For more front-end CPU, --api-server-count starts several API server processes that share the same engine cores ({{cite docs/design/arch_overview.md:75}}).

A crash or a slow request in one process also stays in that process. For example, a slow chat template does not stop the engine loop.

How processes talk

Processes do not share Python objects. To send an object, one process turns it into bytes, and the other process turns the bytes back into an object. vLLM uses three channels:

  1. Requests in: a {{term zmq}} socket pair ROUTER → DEALER, from the front end to the engine core.
  2. Outputs back: a ZMQ socket pair PUSH → PULL, from the engine core to the front end.
  3. Work for the GPUs: a shared-memory ring buffer, MessageQueue, from the engine core to all workers.

Channels 1 and 2 carry {{term msgpack}} bytes. Channel 3 carries Python pickle bytes. With one GPU there is no channel 3: the worker is an object inside the engine core process.

An everyday comparison

Think of a restaurant again. The waiter puts each order slip into a slot in the kitchen wall (channel 1). The kitchen puts ready dishes on a counter for the waiter (channel 2). The head chef writes the next round on one whiteboard that all cooks can read at the same time (channel 3).

The comparison stops here: a slip is the order itself. A ZMQ message is only a copy in bytes, and the receiver must decode it into a new object.

In vLLM

This is a basics page, so this part gives only pointers. The pages {{link concepts/architecture-overview}}, {{link concepts/engine-client}} and {{link concepts/executors-and-workers}} explain the code in full.

  1. Front-end sockets. MPClient binds a ROUTER socket for inputs and a PULL socket for outputs ({{cite vllm/v1/engine/core_client.py:672-682}}). It encodes requests with MsgpackEncoder and decodes outputs with MsgpackDecoder(EngineCoreOutputs) ({{cite vllm/v1/engine/core_client.py:731-732}}).
  2. Engine-core sockets. The engine core runs two IO threads next to its busy loop. The code comment gives the reason: socket IO releases the GIL, so the threads overlap with the GPU work ({{cite vllm/v1/engine/core.py:1238-1265}}).
  3. Worker queue. MultiprocExecutor makes one MessageQueue for all workers ({{cite vllm/v1/executor/multiproc_executor.py:165-172}}). Each worker reads it in worker_busy_loop() ({{cite vllm/v1/executor/multiproc_executor.py:1041-1048}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Python's multiprocessing has three {{term start-method | start methods}}. The vLLM design document compares them ({{cite docs/design/multiprocessing.md:22-46}}):

  • fork copies the parent process. It is fast, but it does not work well with libraries that already started threads or CUDA.
  • {{term spawn}} starts a new interpreter that imports its modules again. It works with CUDA. But code that uses vLLM as a library needs an if __name__ == "__main__": guard.
  • forkserver has the same guard problem as spawn.

vLLM reads the method from VLLM_WORKER_MULTIPROC_METHOD, with the default fork ({{cite vllm/envs.py:938-940}}). The real choice follows these steps:

  1. The CLI sets spawn. When you run the vllm command and the variable is not set, cli_env_setup() sets it to spawn ({{cite vllm/entrypoints/common/startup.py:147-149}}). The comment explains that vLLM sets it only here, because spawn can break library code without a __main__ guard ({{cite vllm/entrypoints/common/startup.py:137-140}}). vllm snapshot skips this setup ({{cite vllm/entrypoints/cli/main.py:67-68}}).
  2. vLLM forces spawn when fork is not safe. _maybe_force_spawn() switches to spawn inside a Ray actor, with --numa-bind, when CUDA or XPU is already initialized, or on WSL ({{cite vllm/utils/system_utils.py:123-162}}).
  3. Each process manager asks for the context. get_mp_context() runs the check above and returns multiprocessing.get_context(method) ({{cite vllm/utils/system_utils.py:185-200}}). The engine core processes ({{cite vllm/v1/engine/utils.py:256}}) and the worker processes ({{cite vllm/v1/executor/multiproc_executor.py:723}}) use it.
  4. Extra API server processes always use spawn. APIServerProcessManager takes multiprocessing.get_context("spawn") directly ({{cite vllm/v1/utils.py:204}}, {{cite vllm/v1/utils.py:248-252}}).

So with the default vllm serve, every child process starts with spawn. Each child imports vLLM again, so each child pays the import time of vLLM once more.

ZMQ is a message library. A socket sends and receives whole messages, and a message can have several frames. The {{term zmq-socket-type}} decides the pattern. vLLM uses these types:

The DEALER sets its identity.Request input: the front end binds ROUTER ({{cite vllm/v1/engine/core_client.py:672-678}}). PUSH (engine core) → PULL (front end)One-way. PUSH sends, PULL receives.Outputs: the front end binds PULL ({{cite vllm/v1/engine/core_client.py:680-682}}); the engine core connects PUSH ({{cite vllm/v1/engine/core.py:2047-2050}}).

Who binds. make_zmq_socket() binds by default for all types except PUSH, SUB and XSUB, which connect ({{cite vllm/utils/network_utils.py:366-367}}). It also sets the high-water marks of ROUTER, DEALER, PUSH and PULL to 0, which means no message limit ({{cite vllm/utils/network_utils.py:371-377}}).

Addresses. Sometimes all engine cores run on the same node as the front end. Then the addresses are ipc:// paths: Unix sockets in VLLM_RPC_BASE_PATH (default: the temp folder) with a random UUID ({{cite vllm/v1/engine/utils.py:1148-1151}}, {{cite vllm/utils/network_utils.py:175-177}}, {{cite vllm/envs.py:731-733}}). Otherwise they are tcp://host:0, and the system picks the port ({{cite vllm/utils/network_utils.py:168-172}}).

Identities. The identity of an engine core is its DP rank as 2 little-endian bytes ({{cite vllm/v1/engine/core_client.py:749-751}}). So rank 0 is b"\x00\x00" and rank 3 is b"\x03\x00". The front end puts the identity first in each message ({{cite vllm/v1/engine/core_client.py:1287-1294}}). ROUTER uses that frame to pick the peer and removes it, so the engine core receives (type, data...) ({{cite vllm/v1/engine/core.py:1979-1986}}).

Request types. The type frame is one byte: ADD = 0x00, ABORT = 0x01, START_DP_WAVE = 0x02, UTILITY = 0x03 ({{cite vllm/v1/engine/__init__.py:300-308}}).

The messages between the front end and the engine core are msgspec.Struct classes. EngineCoreRequest uses array_like=True: msgpack writes it as a list of values in field order, without field names. The class also sets omit_defaults=True ({{cite vllm/v1/engine/__init__.py:113-128}}). For an array-like struct, msgspec still writes every field; the decoder accepts a shorter list and fills missing trailing fields with their defaults (general msgspec behaviour). EngineCoreOutputs uses the same options ({{cite vllm/v1/engine/__init__.py:266-271}}).

MsgpackEncoder.encode() returns a list of buffers, not one bytes object ({{cite vllm/v1/serial_utils.py:165-177}}):

  1. Buffer 0 is the msgpack bytes of the object.
  2. A CPU tensor or a NumPy array smaller than VLLM_MSGPACK_ZERO_COPY_THRESHOLD (default 256 bytes) goes inline into buffer 0 ({{cite vllm/envs.py:1704-1706}}, {{cite vllm/v1/serial_utils.py:242-245}}, {{cite vllm/v1/serial_utils.py:261-263}}).
  3. A larger CPU tensor stays in its own memory. The encoder appends a view of it as an extra buffer, and writes only its index into buffer 0 ({{cite vllm/v1/serial_utils.py:266-270}}).
  4. ZMQ sends all buffers as frames with copy=False, so large tensors are not copied into the message ({{cite vllm/v1/engine/core_client.py:1291-1294}}).

Worked example (illustrative shape). A multimodal request carries one image tensor of shape [3, 336, 336] in float16: 3 × 336 × 336 × 2 = 677,376 bytes. This uses the default mm_tensor_ipc = "direct_rpc" ({{cite vllm/config/multimodal.py:440-444}}); with "torch_shm", the tensor goes through a separate shared-memory queue instead ({{cite vllm/v1/engine/core_client.py:725-728}}). This is more than 256 bytes, so the image goes as buffer 1, a separate frame after the msgpack frame. Buffer 0 holds only ("float16", (3, 336, 336), 1): the dtype, the shape and the buffer index ({{cite vllm/v1/serial_utils.py:271-272}}). A 32-token prompt is a list of 32 ints inside buffer 0.

An object that the encoder does not know raises TypeError. Only VLLM_ALLOW_INSECURE_SERIALIZATION=1 allows a pickle fallback ({{cite vllm/v1/serial_utils.py:220-234}}, {{cite vllm/envs.py:1710-1712}}). Pickle can run code when it decodes, so keep this off.

With TP = 2 or more on one node, the engine core uses MultiprocExecutor. Each step, it sends the same call to every worker. A ZMQ message per worker would copy the data once per worker. MessageQueue writes it once into shared memory, and all workers read it.

The ring buffer. ShmRingBuffer has one writer and n_reader readers ({{cite vllm/distributed/device_communicators/shm_broadcast.py:265-279}}). Its memory has two parts ({{cite vllm/distributed/device_communicators/shm_broadcast.py:281-290}}):

  • data: max_chunks × max_chunk_bytes;
  • metadata: max_chunks × (1 + n_reader) bytes. Byte 0 of a chunk is the "written" flag. Then there is one "read" flag per reader.

The writer may write a chunk when no one wrote it yet, or when all readers have read it. A reader may read a chunk that is written and that it did not read yet ({{cite vllm/distributed/device_communicators/shm_broadcast.py:292-310}}). So there is no lock.

Sizes. MessageQueue defaults to 10 chunks ({{cite vllm/distributed/device_communicators/shm_broadcast.py:492}}). MultiprocExecutor sets the chunk size from VLLM_MQ_MAX_CHUNK_BYTES_MB, default 16 ({{cite vllm/v1/executor/multiproc_executor.py:152}}, {{cite vllm/envs.py:1856-1858}}). With TP = 2, the buffer is 10 × 16 MiB = 160 MiB of data plus 10 × 3 = 30 flag bytes.

One write, step by step (enqueue(), {{cite vllm/distributed/device_communicators/shm_broadcast.py:900-966}}):

  1. Pickle the object. The bytes of CPU tensors become pickle buffers. A buffer of 1 MiB or more goes out of band, as a separate buffer (lines 906-914, 915-922).
  2. If all buffers fit into one chunk, write 0 (no overflow), the buffer count and each buffer with its length into the chunk (lines 947-961).
  3. Otherwise write only the overflow flag 1, and send the buffers through the XPUB socket (lines 943-946).
  4. Wake the readers (line 963).

The executor puts (method, args, kwargs, output_rank) into the queue ({{cite vllm/v1/executor/multiproc_executor.py:428}}). Each worker calls getattr(self.worker, method) with the arguments ({{cite vllm/v1/executor/multiproc_executor.py:1055-1064}}). Each worker has its own MessageQueue(1, 1) for its reply ({{cite vllm/v1/executor/multiproc_executor.py:625}}), and the executor reads only the replies that it needs ({{cite vllm/v1/executor/multiproc_executor.py:430-449}}).

The model tensors between GPUs (for example the all-reduce of TP) do not use this queue. They use NCCL or a custom all-reduce. The page {{link concepts/executors-and-workers}} explains the executor.

With one API server, the server runs in the CLI process ({{cite vllm/entrypoints/cli/serve.py:154-156}}). The API server count defaults to the DP size ({{cite vllm/entrypoints/cli/serve.py:124-130}}). With more than one API server, the CLI process does not serve HTTP. It starts the API server processes and waits for them, so it is one more process ({{cite vllm/entrypoints/cli/serve.py:366-390}}).

The design document says "1 worker process per GPU" ({{cite docs/design/arch_overview.md:89-91}}). With one GPU, the code makes no worker process. So the table of the document gives 3 processes, but the code starts 2. For -tp 2 -dp 4, the formula gives 17, but the code also keeps the CLI process, so there are 18.

On Linux, the spawn start method of Python also starts one small resource-tracker process (general Python behaviour). A ps listing can show it next to the vLLM processes.

What can go wrong

  • A script without a __main__ guard. With spawn, the child imports your main module again. Code at the top level runs again, and Python raises an error about the "bootstrapping phase" ({{cite docs/design/multiprocessing.md:126-146}}). Put your code under if __name__ == "__main__":.
  • CUDA before fork. When your process already initialized CUDA, vLLM switches to spawn with a warning ({{cite vllm/utils/system_utils.py:145-162}}).
  • A full or small /tmp or /dev/shm. The ipc sockets live in VLLM_RPC_BASE_PATH ({{cite vllm/envs.py:731-733}}). The ring buffer checks for free shared memory before it makes the buffer ({{cite vllm/distributed/device_communicators/shm_broadcast.py:332-335}}). Docker gives a small /dev/shm by default, so set a larger one.
  • The engine core does not start in time. The front end waits for a ready message from each engine core. It raises TimeoutError after VLLM_ENGINE_READY_TIMEOUT_S seconds ({{cite vllm/v1/engine/core_client.py:757-761}}).
  • A worker fails. When a worker replies with an error status, the executor raises RuntimeError("Worker failed with error ..."). When the call has a time limit and the reply does not come in time, it raises TimeoutError ({{cite vllm/v1/executor/multiproc_executor.py:440-448}}).
  • Insecure serialization. VLLM_ALLOW_INSECURE_SERIALIZATION=1 allows pickle in ZMQ messages ({{cite vllm/v1/serial_utils.py:220-234}}). Use it only on a trusted network.

Why it matters. CPU limits, shared memory, ports and start-up errors all depend on this process layout. When you know the channels, you can size the machine and read the logs of each process.

Which ZMQ socket types carry requests from the front end to the engine core, and outputs back?

Requests: ROUTER in the front end ({{cite vllm/v1/engine/core_client.py:672-678}}) to DEALER in the engine core ({{cite vllm/v1/engine/core.py:1936-1941}}). Outputs: PUSH in the engine core ({{cite vllm/v1/engine/core.py:2047-2050}}) to PULL in the front end ({{cite vllm/v1/engine/core_client.py:680-682}}).

 You start vllm serve from the command line and do not set VLLM_WORKER_MULTIPROC_METHOD. Which start method do the workers use?

spawn. The CLI sets the variable to spawn when it is not set ({{cite vllm/entrypoints/common/startup.py:147-149}}), and get_mp_context() reads it ({{cite vllm/utils/system_utils.py:185-200}}).

 A request carries a CPU tensor of 100 bytes and one of 10,000 bytes. How does the encoder send each?

The 100-byte tensor is below the 256-byte threshold, so it goes inline in the msgpack buffer. The 10,000-byte tensor goes as an extra frame without a copy, and the msgpack buffer holds only its dtype, shape and frame index ({{cite vllm/v1/serial_utils.py:261-272}}, {{cite vllm/envs.py:1704-1706}}).

 TP = 4 runs on one node. How large is the data part of the worker ring buffer? How many flag bytes does it have? What happens with a 20 MiB message?

Data: 10 chunks × 16 MiB = 160 MiB ({{cite vllm/distributed/device_communicators/shm_broadcast.py:492}}, {{cite vllm/v1/executor/multiproc_executor.py:152}}). Flags: 10 × (1 + 4) = 50 bytes ({{cite vllm/distributed/device_communicators/shm_broadcast.py:322-330}}). A 20 MiB message does not fit into one chunk. The writer sets the overflow flag in the chunk and sends the buffers through the XPUB socket ({{cite vllm/distributed/device_communicators/shm_broadcast.py:943-946}}).
