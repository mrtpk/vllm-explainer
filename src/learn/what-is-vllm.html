Both reach the same engine core. --- vLLM is an engine that runs LLMs and serves them over HTTP; one engine core, V1, sits behind both of its entry points.

The idea

What vLLM is

vLLM calls itself "a fast and easy-to-use library for LLM inference and serving" ({{cite README.md:24}}). The package description says "a high-throughput and memory-efficient inference and serving engine for LLMs" ({{cite pyproject.toml:22}}). An inference engine runs a trained model and makes its tokens. It adds batching, a KV cache and a scheduler around the model ({{deepinfer learn/what-an-llm-does | What an LLM does}}). A serving engine also accepts requests from many users over the network and streams the answers back.

This site explains vLLM as a serving engine. The main path is the command vllm serve. It starts an {{term openai-compatible-server}}: "Launch a local OpenAI-compatible API server to serve LLM completions via HTTP" ({{cite vllm/entrypoints/cli/serve.py:39-40}}). Any client that can talk to the OpenAI API can then talk to your model.

One engine: V1

vLLM has exactly one engine at this commit: the {{term v1-engine}} in vllm/v1/. The older V0 engine is gone. Only two old names remain, and both are aliases of V1 classes:

  • vllm.engine.async_llm_engine.AsyncLLMEngine = AsyncLLM ({{cite vllm/engine/async_llm_engine.py:4-6}}).
  • vllm.engine.llm_engine.LLMEngine = V1LLMEngine ({{cite vllm/engine/llm_engine.py:4-6}}).

So when you read "AsyncLLMEngine" in old examples, it is the V1 {{term async-llm}}. This site uses only the V1 names.

Two ways to use it

  1. Online serving with vllm serve (this site). An HTTP client sends a request, for example POST /v1/chat/completions. The API server turns it into an engine request and streams the tokens back. The page {{link learn/openai-api}} explains the API.
  2. Offline inference with the LLM class (a side note). Your Python script makes LLM(model=...) and calls generate() or chat(). There is no HTTP server. The class builds a V1 LLMEngine ({{cite vllm/entrypoints/llm.py:341-343}}). Its own docstring says that it "is intended to be used for offline inference" ({{cite vllm/entrypoints/llm.py:171-173}}).

What runs where

One vllm serve deployment is a group of processes. Each one has its own job:

  • The {{term front-end}} (the API server process) runs the HTTP routes, the chat template, the tokenizer and AsyncLLM.
  • The {{term engine-core}} process runs the {{term scheduler}} and the KV cache manager in a loop. It tells the workers what to compute in each {{term engine-step}}.
  • The {{term worker | workers}} own the GPUs and run the model. With one GPU, the worker is an object inside the engine core process.

The page {{link concepts/architecture-overview}} explains this split in full. The page {{link learn/processes-and-ipc}} explains how the processes talk to each other.

An everyday comparison

Think of a restaurant. The waiter (the front end) takes orders from many tables and brings the dishes back. The head chef (the engine core) decides which dishes to cook in the next round. The cooks at the stoves (the workers) do the cooking. A take-away counter (the LLM class) uses the same kitchen, but without waiters.

The comparison stops here: a real kitchen cooks each dish once. Without speculative decoding, vLLM makes at most one new token per request in each step, and repeats the step until each answer is complete.

In vLLM

This is a basics page, so this part gives only pointers. The tour {{link tours/life-of-a-chat-request}} follows one request through all of the code.

  1. The command. The package installs one {{term console-script}}, vllm, that calls vllm.entrypoints.cli.main:main ({{cite pyproject.toml:42-43}}). With one API server, vllm serve runs the server in the same process as the command ({{cite vllm/entrypoints/cli/serve.py:154-156}}).
  2. The front end. The API server makes an AsyncLLM ({{cite vllm/entrypoints/launchers/api_server/entry.py:94-99}}). AsyncLLM always starts the engine core in a separate process, through make_async_mp_client ({{cite vllm/v1/engine/async_llm.py:193-201}}). The page {{link concepts/engine-client}} explains it.
  3. The engine core. EngineCoreProc in vllm/v1/engine/core.py runs the busy loop. The page {{link concepts/engine-core-loop}} explains it.

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

The LLM class is a side path on this site. It differs from vllm serve in three ways:

  1. It uses the synchronous V1 LLMEngine, not AsyncLLM ({{cite vllm/entrypoints/llm.py:341-343}}).
  2. LLMEngine turns on multiprocess mode when VLLM_ENABLE_V1_MULTIPROCESSING is true ({{cite vllm/v1/engine/llm_engine.py:186-188}}). The default is "1" ({{cite vllm/envs.py:1442-1444}}). Then the client is a SyncMPClient with ZMQ and an engine core process. With VLLM_ENABLE_V1_MULTIPROCESSING=0, the client is an InprocClient, and the engine core runs in your process ({{cite vllm/v1/engine/core_client.py:128-136}}).
  3. It has statistics off by default ({{cite vllm/entrypoints/llm.py:225-226}}).

AsyncLLM does not read VLLM_ENABLE_V1_MULTIPROCESSING. It always calls make_async_mp_client ({{cite vllm/v1/engine/async_llm.py:193}}), and an asyncio client without multiprocessing raises NotImplementedError ({{cite vllm/v1/engine/core_client.py:114-118}}). So for vllm serve, the engine core is always a separate process.

vLLM supports NVIDIA GPUs, AMD GPUs, Intel GPUs and x86, ARM and PowerPC CPUs. It also lists hardware plugins, for example Google TPUs, Intel Gaudi, IBM Spyre and Huawei Ascend ({{cite README.md:51}}).

In the code, each process selects one {{term platform}} object, current_platform. The selection works like this ({{cite vllm/platforms/__init__.py:240-292}}):

  1. If VLLM_TARGET_DEVICE is cpu, the CPU platform wins at once ({{cite vllm/platforms/__init__.py:244-248}}).
  2. vLLM loads the {{term out-of-tree}} platform plugins of the entry-point group vllm.platform_plugins ({{cite vllm/platforms/__init__.py:250}}).
  3. It calls every built-in detector and every plugin detector. A detector returns a class name or None. The five built-in detectors are tpu, cuda, rocm, xpu and cpu ({{cite vllm/platforms/__init__.py:231-237}}).
  4. One active plugin wins over the built-in detectors. Two active plugins, or two active built-in detectors, raise RuntimeError. No active detector gives UnspecifiedPlatform ({{cite vllm/platforms/__init__.py:272-292}}).

The TPU platform class itself lives in a separate package, tpu_inference ({{cite vllm/platforms/tpu.py:9-19}}). The pages {{link concepts/platform-plugins}} and {{link concepts/plugin-loading}} explain the plugins.

The version is not written in a source file. The build reads it from git tags with setuptools-scm ({{cite pyproject.toml:8}}, {{cite pyproject.toml:49-50}}):

  1. get_vllm_version() calls setuptools_scm.get_version() with the command git describe --dirty --tags --long --abbrev=40 --match v[0-9]* ({{cite setup.py:26-35}}, {{cite setup.py:1360-1363}}). It writes the result to vllm/_version.py.
  2. It adds a local suffix for the build target ({{cite setup.py:1364-1400}}). VLLM_SKIP_VERSION_SUFFIX turns this off. The suffixes are +precompiled, +cu<ver> when the CUDA version is not the main one, +rocm<ver>, +tpu, +cpu, +xpu or +empty. The main CUDA version is 13.0 by default ({{cite vllm/envs.py:624-626}}).
  3. VLLM_VERSION_OVERRIDE replaces the whole version ({{cite setup.py:1352-1358}}).
  4. At run time, vllm/version.py imports __version__ from _version.py. When that fails, it warns and uses "dev" ({{cite vllm/version.py:4-12}}).

Worked example. At the pinned commit, the git describe command of setup.py gives v0.32.1rc0-307-g3e44c0db26.... That is the tag v0.32.1rc0, then 307 commits, then g and the commit hash. The hash has all 40 hex digits, because of --abbrev=40. So this code comes after the 0.32.1 release candidate 0. The exact string that setuptools-scm makes from this (a .dev307 version with the hash) depends on that library and is not in the vLLM repository.

You can read the version in three places. vllm --version reads the installed package metadata ({{cite vllm/entrypoints/cli/main.py:92-97}}). GET /version on a running server returns {"version": ...} ({{cite vllm/entrypoints/serve/instrumentator/basic.py:53-56}}). Python code reads vllm.__version__ ({{cite vllm/__init__.py:7}}).

The Rust front end. The folder rust/ holds "a Rust drop-in alternative frontend for vLLM". It talks to the Python engine core processes "via ZMQ over the existing engine boundary", and its README calls it "experimental" and "not feature-complete" ({{cite rust/README.md:3-5}}). VLLM_USE_RUST_FRONTEND=1 turns it on; the default is off ({{cite vllm/envs.py:1452-1456}}). Then vllm serve starts the Rust binary instead of the Python API server processes ({{cite vllm/entrypoints/cli/serve.py:346-361}}). This site does not explain it further.

The per-family model packages. Besides vllm/model_executor/models/, there is a second model tree, vllm/models/, with one package per model family, for example deepseek_v4 and qwen4_exp ({{cite vllm/models/}}). The model registry points some architecture names to these packages, for example "DeepseekV4ForCausalLM": ("vllm.models.deepseek_v4", ...) ({{cite vllm/model_executor/models/registry.py:99}}). This site uses llama.py as its one model example and does not explain these packages.

What can go wrong

  • Old tutorials. A tutorial that says "V0", --use-v2-block-manager or AsyncLLMEngine internals describes code that is gone. The two old class names still import, but they are V1 classes ({{cite vllm/engine/async_llm_engine.py:6}}, {{cite vllm/engine/llm_engine.py:6}}).
  • Offline and online defaults differ. The LLM class turns statistics off by default ({{cite vllm/entrypoints/llm.py:225-226}}). It also gets other scheduler defaults than vllm serve, because the usage context differs ({{cite vllm/entrypoints/llm.py:341-343}}, {{cite vllm/engine/arg_utils.py:2960-2993}}). A benchmark with LLM does not tell you how vllm serve behaves.
  • No platform found. When no detector is active, vLLM uses UnspecifiedPlatform ({{cite vllm/platforms/__init__.py:290-292}}), and later code fails. Check that the right GPU drivers or the platform plugin package are installed.
  • Two platform plugins. Two installed and active platform plugins stop start-up with RuntimeError ({{cite vllm/platforms/__init__.py:272-276}}).
  • A version string of dev. If vllm/_version.py is missing (for example, a source tree that was never built), the version is "dev" with a warning ({{cite vllm/version.py:6-12}}).

Why it matters. Know your entry point and its processes. Then you know which pages of this site apply to you, and which process owns each flag and each log line.

Which command starts the OpenAI-compatible server, and which Python function does it call first?

vllm serve. The console script vllm calls vllm.entrypoints.cli.main:main ({{cite pyproject.toml:42-43}}), which dispatches to the serve subcommand ({{cite vllm/entrypoints/cli/main.py:116-117}}).

 An old example imports AsyncLLMEngine. Which class does it get?

The V1 AsyncLLM. The module only contains the alias AsyncLLMEngine = AsyncLLM ({{cite vllm/engine/async_llm_engine.py:4-6}}).

 You set VLLM_ENABLE_V1_MULTIPROCESSING=0 and start vllm serve. Does the engine core now run inside the API server process?

No. AsyncLLM always calls make_async_mp_client ({{cite vllm/v1/engine/async_llm.py:193}}). The variable only changes the LLMEngine of the offline LLM class ({{cite vllm/v1/engine/llm_engine.py:186-188}}).

 A machine has an NVIDIA GPU and you install one out-of-tree platform plugin whose detector also returns a class name. Which platform does vLLM select, and what happens with two such plugins?

The plugin platform: when exactly one out-of-tree plugin is active, it wins over the built-in CUDA detector ({{cite vllm/platforms/__init__.py:277-279}}). With two active plugins, start-up stops with RuntimeError("Only one platform plugin can be activated ...") ({{cite vllm/platforms/__init__.py:272-276}}).

 You build vLLM from source with CUDA 12.9 at this commit. Which suffix does the version get, and why?

+cu129, unless VLLM_SKIP_VERSION_SUFFIX is set or the build uses precompiled extensions. The CUDA version 12.9 is not the main version 13.0 ({{cite vllm/envs.py:624-626}}). So the build adds cu and the first three digits of the version without dots ({{cite setup.py:1376-1382}}).
