The idea

Modules and forward

A PyTorch model is a tree of nn.Module objects. Each module holds its parameters (the weights, nn.Parameter tensors) and its child modules. Its forward() method computes the output from the input. When you call module(x), PyTorch calls forward(x). The parameters and some extra tensors (buffers) form the state of the module; a checkpoint is a saved copy of that state.

vLLM models are such trees. For example, LlamaMLP has two linear layers and an activation, and its forward() calls them in order ({{cite vllm/model_executor/models/llama.py:82-122}}). The basics of the transformer layers are on {{deepinfer learn/transformer | Inside a transformer}}.

Ops, kernels and streams

Each tensor operation (an op, for example a matrix multiply) runs as one or more kernels on the GPU. The CPU only starts (launches) the kernels; the GPU runs them in order on a stream. A program can use several streams and synchronize them with events ({{deepinfer learn/gpus-kernels | GPUs, kernels, and speed}}). vLLM does this, for example, to copy the sampled tokens to the CPU on a separate copy stream. It records an event after the copy and waits for that event only when it needs the tokens ({{cite vllm/v1/worker/gpu/async_utils.py:134-140}}, {{cite vllm/v1/worker/gpu/async_utils.py:171-174}}).

Custom ops: one opaque box

Code can register its own operator with torch.library. Then torch.ops.<namespace>.<name>(...) calls it, and PyTorch treats it like a built-in op. vLLM registers its ops in the namespace vllm ({{cite vllm/utils/torch_utils.py:1056}}). The most important one is attention: torch.ops.vllm.unified_attention_with_output ({{cite vllm/model_executor/layers/attention/attention.py:573-580}}). For the compiler, this {{term torch-library-op}} is one opaque node. The compiler does not look inside it. The page {{link concepts/forward-context}} explains how the op finds its KV cache and metadata without arguments for them.

Compile: capture, then generate code

{{term torch-compile}} has two halves:

  1. {{term dynamo}} watches the Python code of forward() when it runs, and records the tensor ops as an {{term fx-graph}}: a list of nodes, one per op.
  2. A backend turns the graph into code. The default backend, {{term inductor}}, fuses many small ops into fewer, larger kernels, for example Triton kernels on NVIDIA GPUs.

Some Python cannot be captured, for example a branch on a tensor value. That place is a {{term graph-break}}. Plain torch.compile then splits the function into several graphs and runs the rest in Python. vLLM does not allow this: it compiles with fullgraph=True ({{cite vllm/compilation/wrapper.py:168-175}}).

CUDA graphs on top

A {{term cuda-graph}} records a series of kernel launches once and replays them with one call. This removes most of the launch cost of small decode steps ({{deepinfer concepts/cuda-graphs | CUDA graphs}}). vLLM captures CUDA graphs for the compiled pieces and, for pure decode batches, for the whole forward pass. The page {{link concepts/compile-and-cuda-graphs}} explains the full design.

An everyday comparison

Think of a cook who follows a recipe. Eager mode reads the recipe line by line, every time. Compilation rewrites the recipe once: it joins steps that use the same pan. A CUDA graph is a video of the cook; next time, the kitchen plays the video. Attention is one step that the rewrite must not touch, so it stays a sealed box in the recipe.

The comparison stops here: a video plays the same moves with the same food. A CUDA graph also reads the same memory addresses every time, so vLLM must copy each new input into the same buffers before a replay.

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

  1. Lines 95-101. gate_up_proj is one linear layer for two matrices, the gate and the up projection. output_sizes=[intermediate_size] * 2 stacks them. With tensor parallelism, each rank holds a slice of the columns ({{deepinfer learn/parallelism | Parallelism basics}}).
  2. Lines 103-110. down_proj is a row-parallel linear layer. With reduce_results=True, it ends with an all-reduce over the TP ranks.
  3. Line 116. SiluAndMul is a {{term custom-op}}: a vLLM layer that selects a CUDA kernel or a PyTorch version ({{cite vllm/model_executor/layers/activation.py:116}}).
  4. Lines 118-122. forward() calls the three layers. The activation goes through maybe_fused_act_quant(): for a quantized down_proj, it can use one kernel for the activation and the input quantization; else it calls SiluAndMul ({{cite vllm/model_executor/layers/fusion/fused_act_quant.py:196-205}}). The linear layers return a pair; the second value (an optional bias) is not used here.

Shapes. vLLM flattens the batch: the first dimension is the number of tokens in the step, not the number of requests ({{deepinfer learn/batching | Batching}}).

Worked example (sizes from the config.json of Llama-3.1-8B: hidden size 4,096, intermediate size 14,336; inferred, not in the repo). A step has 256 tokens and TP = 1, in BF16:

  1. x: [256, 4096].
  2. gate_up_proj: weight [28672, 4096] (2 × 14,336 rows), output [256, 28672].
  3. SiluAndMul: silu(first half) × second half, output [256, 14336].
  4. down_proj: weight [4096, 14336], output [256, 4096].

The two weights hold 28,672 × 4,096 + 4,096 × 14,336 = 176,160,768 parameters, which is 352 MB in BF16. With TP = 2, each rank holds half of each weight and computes [256, 14336] after gate_up_proj.

The weights are not loaded in __init__. vLLM makes the modules first and fills the parameters later from the checkpoint; see {{link concepts/weight-loading}}.

PyTorch has the public decorator torch.library.custom_op. vLLM uses its own helper, because the docstring says that custom_op "can have significant overhead" ({{cite vllm/utils/torch_utils.py:1068-1071}}):

  1. Line 1056. One Library("vllm", "FRAGMENT") object holds all vLLM ops. "FRAGMENT" means that other code can add ops to the same namespace.
  2. Lines 1082-1083. mutates_args lists the arguments that the op writes into. The compiler must know them, so it does not reorder or remove the op.
  3. Lines 1085-1088. The dispatch key comes from the platform: "CUDA" on NVIDIA ({{cite vllm/platforms/cuda.py:230}}), "CPU" by default ({{cite vllm/platforms/interface.py:145}}).
  4. Line 1090. infer_schema reads the type hints of the Python function and writes the op schema, for example (Tensor query, Tensor key, ...) -> ().
  5. Lines 1093-1094. define adds the schema; impl binds the Python function for the dispatch key.
  6. Lines 1095-1096. A fake implementation only makes empty output tensors with the right shapes. Dynamo calls it during capture instead of the real kernel (general PyTorch behaviour). The helper registers it only when the caller gives one.

Attention as an opaque op. vLLM registers unified_attention_with_output with mutates_args=["output", "output_block_scale"] ({{cite vllm/model_executor/layers/attention/attention.py:799-803}}). It returns nothing; it writes the result into output. Inside, it gets the attention metadata, the layer and the KV cache from the forward context ({{cite vllm/model_executor/layers/attention/attention.py:705-723}}). A second op, unified_kv_cache_update, writes the new keys and values into the cache first. It runs only when the attention backend does not write the KV cache in its own forward ({{cite vllm/model_executor/layers/attention/attention.py:564-572}}). It returns an empty tensor only to make a data dependency: the attention op takes it as an argument, so the compiler keeps the order ({{cite vllm/model_executor/layers/attention/attention.py:726-732}}, {{cite vllm/model_executor/layers/attention/attention.py:777-782}}).

Which platforms use the opaque op. The layer calls torch.ops.vllm.* only when current_platform.opaque_attention_op() is true. Otherwise it calls the Python functions directly ({{cite vllm/model_executor/layers/attention/attention.py:436-440}}, {{cite vllm/model_executor/layers/attention/attention.py:542-580}}). The base class returns false ({{cite vllm/platforms/interface.py:1286-1290}}); CUDA, ROCm, CPU and XPU return true ({{cite vllm/platforms/cuda.py:595-596}}, {{cite vllm/platforms/rocm.py:1231-1232}}, {{cite vllm/platforms/cpu.py:640-641}}, {{cite vllm/platforms/xpu.py:609-610}}).

A torch.library op (this section) is a PyTorch operator. A vLLM CustomOp (for example SiluAndMul) is an nn.Module class that selects a kernel per platform. The page {{link concepts/custom-ops}} explains the second kind.

What Dynamo records. When the compiled function runs for the first time, Dynamo follows its Python bytecode. It records each tensor op as a node of a torch.fx.Graph. The graph has a placeholder node per input, a call_function node per op, and an output node. vLLM's split code walks these nodes ({{cite vllm/compilation/backends.py:576-600}}). Python that does not touch tensors (for example a loop over the layers) runs during capture and leaves only its tensor ops in the graph.

Guards and dynamic shapes. Plain torch.compile adds guards: checks that run before each call and compile again when, for example, a shape changes. vLLM drops the guards in its own modes ({{cite vllm/compilation/wrapper.py:126-146}}). It marks the token dimension as dynamic instead, from dynamic_arg_dims ({{cite vllm/model_executor/models/llama.py:337-346}}). So one graph serves every number of tokens.

A graph break, by example (plain PyTorch, not vLLM code):

import torch

def f(x):
    y = x.sin()
    if y.sum() > 0:        # Python branch on a tensor value
        return y.cos()
    return y

torch.compile(f)(torch.randn(8))                  # works: two graphs and a Python branch
torch.compile(f, fullgraph=True)(torch.randn(8))  # fails: fullgraph does not allow the break

Dynamo cannot know the value of y.sum() during capture. Without fullgraph, it ends the graph before the branch, runs the branch in Python, and starts a new graph. With fullgraph=True, it raises an error instead. vLLM uses fullgraph=True ({{cite vllm/compilation/wrapper.py:168-175}}). So model code that vLLM compiles must not branch on tensor values in forward().

Where the work goes. In the default mode, the backend is VllmBackend ({{cite vllm/config/compilation.py:1123-1134}}). It splits the FX graph at the splitting ops. By default these are the attention ops in _attention_ops ({{cite vllm/config/compilation.py:766-788}}, {{cite vllm/config/compilation.py:1184}}). When Inductor graph partition is off (the O2 default), they also include the two KV cache update ops ({{cite vllm/config/compilation.py:1191}}, {{cite vllm/config/compilation.py:1212-1213}}, {{cite vllm/config/vllm.py:311}}). Then Inductor compiles each piece. The design document says that all compilation finishes before the server takes requests, and that vLLM caches the results ({{cite docs/design/torch_compile.md:18-28}}).

VLLM_COMPILE (3)vLLM's Inductor-based backend with caching, piecewise compilation and custom passes.

Defaults. The default optimization level is O2 ({{cite vllm/config/vllm.py:434}}). Above O0, an unset mode becomes VLLM_COMPILE ({{cite vllm/config/vllm.py:1806-1810}}). O2 sets the CUDA graph mode FULL_AND_PIECEWISE ({{cite vllm/config/vllm.py:310}}). --enforce-eager sets both the compile mode and the CUDA graph mode to NONE ({{cite vllm/config/vllm.py:1745-1747}}).

CUDA graph modes. NONE, PIECEWISE and FULL are run-time modes. FULL_DECODE_ONLY and FULL_AND_PIECEWISE are pairs: one mode for pure decode batches, one for mixed batches ({{cite vllm/config/compilation.py:53-69}}). Each step, the model runner looks for a captured graph for the padded token count, and falls back to NONE when none fits ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:523-553}}). In the common case (no speculative decoding), a FULL decode graph is captured for batches where each request has 1 new token ({{cite vllm/v1/worker/gpu/model_runner.py:442-445}}, {{cite vllm/v1/worker/gpu/cudagraph_utils.py:333-339}}). A batch matches it only with that uniform length and at most the captured token count ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:125-138}}). Other batches use PIECEWISE graphs.

With speculative decoding the decode query length is larger, and a "varlen decode" variant accepts mixed lengths ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:302-317}}). The page {{link concepts/compile-and-cuda-graphs}} covers these cases.

Worked example (illustrative numbers). A decode step of a 32-layer model starts about 15 kernels per layer in eager mode: 480 launches. At about 5 µs of CPU time per launch, that is 2.4 ms per step. A step of a small model on a fast GPU can take less than that, so the GPU would wait for the CPU. With a FULL CUDA graph, the CPU starts one replay instead.

The kernel count and the launch time are round numbers for the example, not measured. Fusion in Inductor also lowers the kernel count. The page {{link concepts/compile-and-cuda-graphs}} explains the capture sizes, the padding and the attention backends that lower the graph mode.

What can go wrong

  • Slow first start. Compilation runs at start-up, before the server takes requests ({{cite docs/design/torch_compile.md:28}}). CUDA graph capture also runs at start-up. Later starts reuse the cache. VLLM_DISABLE_COMPILE_CACHE=1 turns the cache off ({{cite vllm/envs.py:375}}), so every start compiles again.
  • A graph break in your own model. This applies to a model class with @support_torch_compile. With fullgraph=True, a branch on a tensor value or an unsupported Python call stops compilation with an error ({{cite vllm/compilation/wrapper.py:168-175}}). Move such logic out of forward(), or run with --enforce-eager to find the problem.
  • A custom op without a fake implementation. In PyTorch, an op that returns new tensors needs a fake implementation, so that Dynamo knows the output shapes during capture (general PyTorch rule). With the vLLM helper, you give it as fake_impl ({{cite vllm/utils/torch_utils.py:1095-1096}}), as for unified_kv_cache_update ({{cite vllm/model_executor/layers/attention/attention.py:759-764}}). The attention op is registered without a fake implementation; it returns nothing and writes into output ({{cite vllm/model_executor/layers/attention/attention.py:799-803}}).
  • A missing mutates_args. An op that writes into an argument without saying so can be reordered or removed by the compiler. vLLM lists output for attention ({{cite vllm/model_executor/layers/attention/attention.py:802}}).
  • --enforce-eager in production. It turns off both compilation and CUDA graphs ({{cite vllm/config/vllm.py:1745-1747}}). Use it to debug, not to serve: small decode steps become much slower.

Why it matters. Every model file in vLLM is written for this pipeline. Know what the compiler sees. Then you can read the model code, write a model plugin that compiles, and explain the start-up time of vllm serve.

What are the two halves of torch.compile, and what does each do?

Dynamo captures the Python code as an FX graph. A backend, by default Inductor, turns the graph into fused kernels. In vLLM's default mode, the backend is VllmBackend, which splits the graph and then compiles the pieces ({{cite vllm/config/compilation.py:1123-1134}}).

 Which flag turns off both torch.compile and CUDA graphs?

--enforce-eager. It sets the compile mode and the CUDA graph mode to NONE ({{cite vllm/config/vllm.py:1745-1747}}).

 Why is attention registered as a torch.library op on CUDA, and not left as plain PyTorch code?

The compiler then sees attention as one opaque node. vLLM splits the graph at that node, so the pieces around it can be compiled and captured as PIECEWISE CUDA graphs ({{cite vllm/config/compilation.py:766-769}}). The op reads its KV cache and metadata from the forward context ({{cite vllm/model_executor/layers/attention/attention.py:705-722}}). CUDA returns true for opaque_attention_op() ({{cite vllm/platforms/cuda.py:595-596}}).

 Your model plugin has if positions.max() > 4096: in the forward() of a class with @support_torch_compile. What happens at start-up with default flags, and why?

Compilation fails with an error. The branch depends on a tensor value, so Dynamo cannot capture it: it is a graph break. vLLM compiles with fullgraph=True ({{cite vllm/compilation/wrapper.py:168-175}}), and VLLM_COMPILE is the default above O0 ({{cite vllm/config/vllm.py:1806-1810}}). Move the check out of forward(), or use a tensor operation such as torch.where.

 In the LlamaMLP worked example, how many parameters does one rank hold with TP = 4, and what is the shape after gate_up_proj for 256 tokens?

Each rank holds a quarter of each weight: 176,160,768 / 4 = 44,040,192 parameters (88 MB in BF16). After gate_up_proj the shape is [256, 7168]: 2 × 14,336 / 4 columns. The column split comes from MergedColumnParallelLinear ({{cite vllm/model_executor/models/llama.py:95-101}}), and down_proj then reduces the results over the ranks ({{cite vllm/model_executor/models/llama.py:103-110}}).
