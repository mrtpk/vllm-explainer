--- title: Serving metrics: TTFT, TPOT, ITL, throughput, goodput nav_title: Serving metrics level: Beginner prerequisites: learn/ml-basics-recap related: concepts/metrics-and-observability, concepts/benchmarking, concepts/tuning, concepts/scheduler, reference/metrics, tours/life-of-a-chat-request summary: Serving metrics tell how fast a server answers one user (TTFT, TPOT, ITL, E2E latency) and how much work it does for all users (throughput, goodput). vLLM measures them in the API server and the engine core, and vllm bench serve measures them at the client. --- Serving metrics measure how long one user waits for tokens, and how many tokens and good requests the server makes per second.

The idea

The timeline of one request

A chat request goes through the same events every time. A client sends it. The server turns the messages into tokens. The request waits in a queue. Then the engine runs the prefill of the prompt and makes the first output token ({{deepinfer learn/prefill-decode | Prefill and decode}}). After that, each step adds one more token. The request ends with the last token.

Each latency metric is the time between two of these events:

  • Time to first token ({{term ttft}}): from arrival to the first output token. The user sees nothing before it. Queue time and prefill time are both inside TTFT.
  • Time per output token ({{term tpot}}): the time from the first to the last token, divided by the number of tokens after the first. It is one number per request.
  • Inter-token latency ({{term itl}}): the time between two outputs that follow each other. A request with 101 output tokens gives 100 ITL samples.
  • End-to-end latency ({{term e2e-latency | E2E latency}}): from arrival to the last token. E2E = TTFT + TPOT × (output tokens − 1).

TPOT and ITL look the same, but they are not. TPOT is an average for one request. ITL keeps every gap, so one long gap stays visible. A long gap is a stall: for example, a step that also runs a long prefill of another request.

Many requests: throughput, concurrency, goodput

A server has many users at the same time. Three numbers describe all of them together:

  • {{term request-throughput | Request throughput}}: finished requests per second. {{term token-throughput | Token throughput}}: output tokens per second (or input plus output tokens per second).
  • {{term concurrency | Concurrency}}: the number of requests in the server at one time. More concurrency gives bigger batches.
  • {{term goodput | Goodput}}: requests per second that meet every {{term slo}} (service level objective). An SLO is a limit, for example "TTFT ≤ 500 ms and TPOT ≤ 50 ms".

Throughput alone can hide bad service. A server can finish many requests per second while half of them wait for 10 seconds. Goodput counts only the requests that the users find fast enough.

Percentiles: p50 and p99

A mean hides the slow requests. A {{term percentile}} does not. The p50 (median) is the value that half of the samples are below. The p99 is the value that 99 % of the samples are below. SLOs often use p99, because 1 in 100 samples is at or above the p99 value. With 1,000 requests, that is 10 slow requests.

A worked example. One request has 100 ITL gaps. 99 gaps are 18 ms and one gap is 218 ms (a stall). The mean ITL is (99 × 18 + 218) / 100 = 20 ms, and TPOT is also 20 ms. The p50 is 18 ms. The maximum is 218 ms. One stall changes the mean only by 2 ms, but the user sees a pause of 0.2 s.

The latency and throughput trade-off

Batching puts the tokens of many requests into one step. The model reads its weights once for the whole batch ({{deepinfer learn/batching | Batching}}). So a bigger batch gives many more tokens per second, but each step takes a little longer. Each step is one ITL gap for every request in the batch.

A worked example (illustrative numbers). Assume that a decode step takes 15 ms plus 0.1 ms per request in the batch.

From 1 to 256 requests, throughput grows by about 95 times. ITL grows only by about 2.7 times. With the SLO "TPOT ≤ 50 ms", all four batch sizes are good, so the largest batch gives the most goodput. With "TPOT ≤ 20 ms", only batches of up to 50 requests meet the SLO.

A real step time also depends on attention, which reads the KV cache of each request, and on prefill chunks in the same step. The linear formula is only an example. Measure your own server with vllm bench serve.

New requests also move the trade-off. A prefill chunk in a step makes that step longer for every running request. A bigger token budget gives a shorter TTFT for long prompts, but longer ITL stalls for the others.

An everyday comparison

Think of a restaurant. TTFT is the time until the first dish comes to the table. ITL is the time between two dishes. Throughput is the number of guests that the kitchen serves in one hour. Goodput counts only the guests who got every dish in time. A cook can make 20 plates of the same dish at once. This serves more guests per hour, but each guest waits a little longer for each dish.

The comparison stops here: a kitchen cooks each dish only once. An LLM server must read all model weights again for each step. That is why a bigger batch costs so little extra time.

In vLLM

This is a basics page, so this part gives only pointers. The pages {{link concepts/metrics-and-observability}} and {{link concepts/benchmarking}} explain the full code.

  1. The engine core marks the events. When statistics are on, the scheduler records a QUEUED event when a request enters it ({{cite vllm/v1/core/sched/scheduler.py:2746-2747}}). It records SCHEDULED with one timestamp per schedule() call ({{cite vllm/v1/core/sched/scheduler.py:664}}, {{cite vllm/v1/core/sched/scheduler.py:1420-1422}}). Every EngineCoreOutputs carries one time.monotonic() timestamp for its new tokens ({{cite vllm/v1/engine/__init__.py:296-297}}).
  2. The front end turns the events into metrics. IterationStats in the {{term front-end}} computes TTFT at the first output of a request and one ITL sample at each later output. It computes E2E, queue, prefill, decode and TPOT when a request finishes. The PrometheusStatLogger puts them into histograms, for example vllm:time_to_first_token_seconds ({{cite vllm/v1/metrics/loggers.py:930-935}}).
  3. The benchmark measures at the client. vllm bench serve sends streamed requests and times the {{term sse}} chunks ({{cite vllm/benchmarks/lib/endpoint_request_func.py:466-486}}). Then calculate_metrics() reports throughput, goodput, mean, median and percentiles ({{cite vllm/benchmarks/serve.py:602-812}}).

So TTFT and E2E latency are front-end intervals: iteration_timestamp − arrival_time ({{cite vllm/v1/metrics/stats.py:505-507}}). They include the chat template, tokenization, the trip to the engine core and back, and the wait. They do not include HTTP parsing before rendering, detokenization after the output arrives, or the network to the client. Queue, prefill, decode, ITL and TPOT are engine-core intervals.

The design document says: "Currently arrival_time starts when tokenization begins." ({{cite docs/design/metrics.md:262-263}}). In the code, it starts a little earlier: before the chat template (render_messages_async, {{cite vllm/renderers/base.py:1385-1388}}).

Chunked prefill. The scheduler sends an output for a request only when it has new tokens, a pooling output or a stop ({{cite vllm/v1/core/sched/scheduler.py:2293-2295}}). A prompt chunk that makes no token sends nothing. So the first output, and the end of TTFT, comes after the last chunk of the prompt.

When a request finishes, the output processor calls update_from_finished_request() ({{cite vllm/v1/engine/output_processor.py:885-887}}):

  1. Line 594. E2E latency = front-end time now − arrival_time.
  2. Line 597. Queue time = first SCHEDULED − QUEUED.
  3. Line 601. Prefill time = first token − first SCHEDULED. A preemption during prefill stays inside this interval (comment on line 600).
  4. Line 605. Decode time = last token − first token.
  5. Line 609. Inference time = last token − first SCHEDULED.
  6. Lines 612-616. TPOT = decode time / (generated tokens − 1). The first token comes from prefill, so it is not counted. A request with 0 or 1 output token gets TPOT 0.

Docs and code differ on TPOT and ITL. The design document gives TPOT as (E2E latency − TTFT) / (output tokens − 1) ({{cite docs/design/metrics.md:55}}). The code divides the decode interval instead (lines 605 and 612-616). The document also calls each ITL sample a "wall-clock gap" between streamed outputs ({{cite docs/design/metrics.md:69-70}}). The code uses the monotonic timestamps of two engine outputs ({{cite vllm/v1/metrics/stats.py:554-556}}).

Why "first" SCHEDULED. A preempted request is scheduled again later. The code keeps only the first value: if req_stats.scheduled_ts == 0.0: # ignore preemptions ({{cite vllm/v1/metrics/stats.py:576-578}}). The design document instead says "between QUEUED and most recent SCHEDULED" ({{cite docs/design/metrics.md:212}}). The code wins: queue time does not grow after a preemption, but prefill or decode time does.

A {{term preemption}} frees all blocks of the request and sets num_computed_tokens to 0. The request goes back to the front of the waiting queue ({{cite vllm/v1/core/sched/scheduler.py:1676-1700}}). It records a PREEMPTED event, which counts in vllm:num_preemptions ({{cite vllm/v1/metrics/stats.py:580-583}}).

Worked example (the request of the diagram). arrival_time = 0, queued_ts = 5 ms, scheduled_ts = 55 ms, first token = 200 ms, last token = 2,200 ms, 101 output tokens. Then queue = 50 ms, prefill = 145 ms and TTFT = 200 ms. Decode = 2,000 ms, inference = 2,145 ms, TPOT = 2,000 / 100 = 20 ms and E2E = 2,200 ms.

The diagram puts all timestamps on one axis. In the code, arrival_time uses the wall clock of the API server, and the other four use the monotonic clock of the engine core. vLLM never subtracts one from the other.

Why buckets matter. Prometheus estimates a percentile from the bucket counts. With the default ITL buckets, all gaps between 10 ms and 25 ms fall into one bucket. So a p99 ITL from Prometheus is only as exact as the bucket edges.

Throughput counters and the log line. The counters vllm:prompt_tokens and vllm:generation_tokens grow by the tokens of each output ({{cite vllm/v1/metrics/loggers.py:1262-1272}}). The LoggingStatLogger also writes a log line with "Avg prompt throughput" and "Avg generation throughput" ({{cite vllm/v1/metrics/loggers.py:283-284}}). It divides the tokens by the time since the last log ({{cite vllm/v1/metrics/loggers.py:169-174}}). The API server writes this line every VLLM_LOG_STATS_INTERVAL seconds, default 10 ({{cite vllm/envs.py:874-878}}, {{cite vllm/entrypoints/launchers/utils/server_utils.py:79-84}}).

Turn off. The API server gives --disable-log-stats to AsyncLLM ({{cite vllm/entrypoints/launchers/api_server/entry.py:99}}). Then AsyncLLM makes no default stat loggers. A stat-logger plugin still turns statistics on, but only for the plugin loggers ({{cite vllm/v1/engine/async_llm.py:158-159}}, {{cite vllm/v1/engine/async_llm.py:204-210}}).

vllm bench serve is a subcommand that calls vllm/benchmarks/serve.py ({{cite vllm/entrypoints/cli/benchmark/serve.py:10-21}}). It sends requests to a running server and times them at the client.

One request. For the chat API, the client sends "stream": true with usage in the last chunk ({{cite vllm/benchmarks/lib/endpoint_request_func.py:423-432}}). It starts a time.perf_counter() clock before the POST ({{cite vllm/benchmarks/lib/endpoint_request_func.py:443-445}}). Then:

  1. TTFT = the time of the first SSE chunk with output − start (line 477).
  2. Each later chunk with output adds one ITL sample: the gap to the previous chunk with output (lines 481, 486).
  3. The usage chunk gives the output token count, but it does not move the end time (lines 484-490).
  4. Latency (E2EL) = the time of the last output chunk − start ({{cite vllm/benchmarks/lib/endpoint_request_func.py:501}}).

All requests. calculate_metrics() computes ({{cite vllm/benchmarks/serve.py:654-660}}, {{cite vllm/benchmarks/serve.py:778-781}}):

  • TPOT per request = (latency − TTFT) / (output tokens − 1). Requests with 1 output token are not in the TPOT statistics.
  • Request throughput = completed / duration. Output token throughput = output tokens / duration. Total token throughput = (input + output tokens) / duration.
  • The duration is the wall time of the whole run, from the start of the benchmark to the last result ({{cite vllm/benchmarks/serve.py:1048}}, {{cite vllm/benchmarks/serve.py:1123}}).
  • Mean, median, standard deviation and the selected percentiles, with np.percentile ({{cite vllm/benchmarks/serve.py:782-806}}).

Goodput. A request is good when every given SLO value is greater than or equal to its measured value ({{cite vllm/benchmarks/serve.py:669-692}}). Request goodput = good requests / duration. A request with 1 output token has TPOT 0 for this check.

  • Request throughput = 5 / 8.0 = 0.625 req/s.
  • Output token throughput = 455 / 8.0 = 56.9 tok/s. Total token throughput = (4,600 + 455) / 8.0 = 631.9 tok/s.
  • Request goodput = 3 / 8.0 = 0.375 req/s. Throughput says 0.625, but only 60 % of the requests met the SLO.
  • TTFT: sorted 120, 150, 200, 300, 650. Mean 284 ms, median 200 ms. np.percentile interpolates in a straight line by default. The p99 is at index 0.99 × 4 = 3.96, so p99 = 300 + 0.96 × (650 − 300) = 636 ms.
  • TPOT: E has 1 output token, so only A to D count: 20, 22, 25, 55. Mean 30.5 ms, median 23.5 ms. The p99 is at index 0.99 × 3 = 2.97, so p99 = 25 + 0.97 × (55 − 25) = 54.1 ms.
  • Average concurrency = the sum of all E2E times / duration = 14.57 s / 8.0 s = 1.8 requests in flight.

The mean TTFT (284 ms) is below the SLO, but one request in five missed it. This is why SLOs use percentiles or goodput, not means.

The vLLM scheduler has no prefill phase and no decode phase. Each step gives tokens to requests until their computed tokens catch up with their known tokens ({{cite vllm/v1/core/sched/scheduler.py:624-633}}). So one step can hold decode tokens and prefill chunks together.

  1. The step starts with the {{term token-budget}} max_num_scheduled_tokens ({{cite vllm/v1/core/sched/scheduler.py:642}}). This is normally max_num_batched_tokens ({{cite vllm/v1/core/sched/scheduler.py:138-142}}).
  2. It first serves the running requests ({{cite vllm/v1/core/sched/scheduler.py:713-715}}).
  3. It then takes waiting requests with the rest of the budget ({{cite vllm/v1/core/sched/scheduler.py:956}}). {{term chunked-prefill | Chunked prefill}} is on by default for generative models that are not encoder-decoder models ({{cite vllm/engine/arg_utils.py:3031-3035}}). So a long prompt takes only the rest of the budget.

Defaults for vllm serve (usage context OPENAI_API_SERVER) on a GPU depend on the GPU memory ({{cite vllm/engine/arg_utils.py:2960-2993}}). They apply only when you do not set the flag. --performance-mode throughput doubles both values ({{cite vllm/engine/arg_utils.py:3171-3175}}). TPU and CPU platforms have other values ({{cite vllm/engine/arg_utils.py:2995-3024}}).

With --enable-per-request-metrics (default off, {{cite vllm/entrypoints/common/cli_args.py:150-151}}), the response has a metrics object. In streaming, it comes in the final usage chunk. The server sends that chunk only when usage is on: stream_options.include_usage or --enable-force-include-usage. The server leaves the object out when n is more than 1 ({{cite vllm/entrypoints/openai/chat_completion/serving.py:873-885}}). The flag needs engine statistics: with --disable-log-stats, start-up fails ({{cite vllm/entrypoints/common/cli_args.py:536-542}}).

The field time_to_first_token_ms is first token − scheduled_ts ({{cite vllm/entrypoints/generate/base/serving.py:73-74}}). That is the prefill interval. It does not include the queue time or the chat template and tokenization. The histogram vllm:time_to_first_token_seconds starts at arrival_time.

The other fields: queue_time_ms = scheduled_ts − queued_ts; generation_time_ms = decode interval; mean_itl_ms = decode interval / (tokens − 1); tokens_per_second = all output tokens / inference interval ({{cite vllm/entrypoints/generate/base/serving.py:76-89}}). vllm bench serve reads queue_time_ms and time_to_first_token_ms from this object when the server sends it ({{cite vllm/benchmarks/lib/endpoint_request_func.py:110-125}}).

What can go wrong

  • Client and server numbers do not match. The client TTFT includes the network, HTTP parsing and the SSE send ({{cite vllm/benchmarks/lib/endpoint_request_func.py:443-477}}). The server TTFT starts at rendering ({{cite vllm/renderers/base.py:1380}}). Compare each metric only with the same metric from the same place.
  • ITL and TPOT differ with bundled tokens. With speculative decoding, one output can hold several tokens. ITL then has fewer, longer gaps, and TPOT spreads the time over all tokens ({{cite docs/benchmarking/cli.md:145-159}}). A --stream-interval above 1 also bundles tokens in the stream ({{cite vllm/config/scheduler.py:216-220}}). This changes the client ITL. The Prometheus ITL does not change, because the front end records it for each engine output before it applies the interval ({{cite vllm/v1/engine/output_processor.py:775}}).
  • TPOT of short requests. Prometheus records TPOT 0 for a request with 1 output token ({{cite vllm/v1/metrics/stats.py:612-616}}), but vllm bench serve leaves such requests out of its TPOT statistics ({{cite vllm/benchmarks/serve.py:655-659}}). The design document notes the same difference ({{cite docs/design/metrics.md:76-79}}).
  • A benchmark with --request-rate inf sends all requests at time 0 ({{cite vllm/benchmarks/serve.py:1749-1750}}). It measures the highest throughput, but TTFT then includes a long queue. Use a finite rate, or --max-concurrency, to measure the latency that users see.
  • Requests that the client stops are missing. When a client disconnects, AsyncLLM calls abort() ({{cite vllm/v1/engine/async_llm.py:807-809}}). The output processor then removes the request state and does not record a finished request ({{cite vllm/v1/engine/async_llm.py:955}}, {{cite vllm/v1/engine/output_processor.py:631-636}}). So such a request is not in the E2E, queue, prefill, decode or TPOT histograms.
  • Means hide stalls. One 218 ms stall in 100 gaps moves the mean ITL by only 2 ms. Watch p99 ITL and the vllm:num_preemptions counter ({{cite vllm/v1/metrics/loggers.py:1259-1261}}).

Why it matters. Every tuning choice in vLLM moves TTFT, ITL and throughput against each other. You can only tune well when you know what each number measures, where it is measured, and which SLO your users need.

A request has TTFT 300 ms, 51 output tokens and E2E latency 1,300 ms. What is its TPOT?

TPOT = (E2E − TTFT) / (output tokens − 1) = (1,300 − 300) / 50 = 20 ms. This is the formula of vllm bench serve ({{cite vllm/benchmarks/serve.py:655-657}}). The Prometheus TPOT uses the engine-core decode interval instead of E2E − TTFT. It also does not count the first token, because the first token comes from prefill ({{cite vllm/v1/metrics/stats.py:611-616}}).

 A run finishes 100 requests in 20 s. 80 of them meet every SLO. What are the request throughput and the request goodput?

Throughput = 100 / 20 = 5 req/s. Goodput = 80 / 20 = 4 req/s ({{cite vllm/benchmarks/serve.py:778-779}}).

 Why does vLLM take the queue time from engine-core timestamps, and not from API server timestamps?

Only the engine core sees the QUEUED and SCHEDULED events. An interval must use two timestamps of the same process, because monotonic clocks of two processes have different start points ({{cite docs/design/metrics.md:177-182}}). So the engine core records both events with time.monotonic() ({{cite vllm/v1/engine/__init__.py:196-200}}), and the front end subtracts them ({{cite vllm/v1/metrics/stats.py:597}}).

 A request waits 2 s, runs its prefill, is preempted during decode, waits 1 s more, and finishes. Which Prometheus interval gets the extra 1 s: queue time, prefill time or decode time?

Decode time (and inference time). The code keeps only the first SCHEDULED timestamp ({{cite vllm/v1/metrics/stats.py:577-578}}). So queue time stays 2 s. Decode time = last token − first token ({{cite vllm/v1/metrics/stats.py:605}}), and the extra wait is between these two tokens. The ITL histogram also gets one long gap.

 You enable --enable-per-request-metrics. A response says time_to_first_token_ms = 120, but your Prometheus TTFT for the same request is about 900 ms. Give a reason from the code.

The response field is first token − scheduled_ts ({{cite vllm/entrypoints/generate/base/serving.py:73-74}}): the prefill interval only. The histogram TTFT is front-end time − arrival_time ({{cite vllm/v1/metrics/stats.py:525}}), and arrival_time is set before the chat template ({{cite vllm/renderers/base.py:1380}}). So the difference of about 780 ms is the time before scheduled_ts (rendering, the trip to the engine core, the queue). It also has the trip of the first output back to the front end. Compare it with queue_time_ms in the same response to see the queue part.
