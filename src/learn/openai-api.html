This page shows the routes that vLLM registers, the request fields that matter for serving, vLLM's extra fields, the SSE stream format, tool calls, reasoning output and errors. --- vllm serve accepts OpenAI-style JSON requests on HTTP routes such as /v1/chat/completions and answers with JSON or a stream of SSE events.

The idea

A shared request format

Many client tools speak the HTTP API of OpenAI: the openai Python SDK, agent frameworks, benchmark tools and routers. vLLM accepts the same JSON. So you change only the base URL of the client, for example to http://localhost:8000/v1, and the client talks to your own model. The server listens on port 8000 by default ({{cite vllm/entrypoints/common/cli_args.py:286-287}}).

Each {{term route}} is one HTTP method and one path. Two routes do most of the work:

  • POST /v1/chat/completions takes a list of chat messages. The server turns them into one prompt with the {{term chat-template}} of the model. This is the main route for chat models and the route of all examples on this site.
  • POST /v1/completions takes a raw prompt: a string, a list of strings, or token ids ({{cite vllm/entrypoints/openai/completion/protocol.py:53-59}}). There is no chat template.

Other routes list the models (GET /v1/models), check health (GET /health), give Prometheus metrics (/metrics) and turn text into tokens (POST /tokenize). The first deep dive lists them all.

Chat roles and the chat template

A chat request is a list of messages. Each message has a role and content. The usual roles are system, user, assistant and tool. The model does not see JSON. The chat template, a Jinja template from the tokenizer files, writes the messages into one text with special tokens. Then the tokenizer turns that text into token ids ({{deepinfer learn/tokens | Tokens and tokenizers}}). The page {{link concepts/renderers-and-chat-templates}} explains how vLLM does this.

Streaming with server-sent events

With "stream": true, the server keeps the HTTP response open. It sends one {{term sse}} event for each new piece of text. Each event is one line data: {...} and a blank line. The last event is data: [DONE]. So the user sees the first words after the time to first token, not after the whole answer ({{link learn/serving-metrics}}).

An everyday comparison

Think of a standard order form in a chain of restaurants. Every kitchen accepts the same form, so a customer can order in any of them. vLLM is a new kitchen that accepts the standard form. It also reads some extra boxes on the form that only vLLM knows, for example top_k.

The comparison stops here: a kitchen sends the whole meal at once. With streaming, vLLM sends the answer in many small parts while it still makes the rest.

In vLLM

This is a basics page, so this part gives only pointers. The page {{link concepts/openai-server}} explains the server code, and stops 1, 2 and 16 of {{link tours/life-of-a-chat-request}} follow one request through it.

  1. The route. create_chat_completion() in vllm/entrypoints/openai/chat_completion/api_router.py handles POST /v1/chat/completions. It returns a JSONResponse, or a StreamingResponse with the media type text/event-stream ({{cite vllm/entrypoints/openai/chat_completion/api_router.py:43-84}}).
  2. The request class. ChatCompletionRequest is a pydantic model. Its fields follow the order of the OpenAI documentation, and vLLM's extra fields come after them ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:225-228}}).

The health check. GET /health asks the engine client. It returns 200 when the engine is alive and 503 after an EngineDeadError ({{cite vllm/entrypoints/serve/instrumentator/health.py:22-33}}).

API keys. With --api-key (or VLLM_API_KEY when the flag is not set), a middleware checks the Authorization: Bearer header ({{cite vllm/entrypoints/serve/middleware/register.py:32-36}}). It guards only paths that start with /v1, /v2, /inference or /cohere, and answers 401 otherwise ({{cite vllm/entrypoints/serve/middleware/authenticate.py:11}}, {{cite vllm/entrypoints/serve/middleware/authenticate.py:59-60}}). So /health and /metrics stay open.

vLLM's extra fields. These are not in the OpenAI specification. The OpenAI SDK sends them in its extra_body argument.

  • Sampling: top_k, min_p, repetition_penalty, min_tokens, stop_token_ids, ignore_eos, use_beam_search and others ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:278-288}}). The basics of these are on {{deepinfer learn/sampling | Sampling}}.
  • Chat template: chat_template, chat_template_kwargs, add_generation_prompt, continue_final_message ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:324-377}}). For example, "chat_template_kwargs": {"enable_thinking": false} reaches a Qwen3 template.
  • Scheduling: priority (lower is earlier, default 0) ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:393-402}}). The field description says that a value other than 0 raises an error without priority scheduling. At this commit, no code raises that error: the default first-come-first-served queue does not use the value ({{cite vllm/v1/core/sched/request_queue.py:200-205}}).
  • Structured output: structured_outputs ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:389-392}}).
  • Bookkeeping: request_id (default: a random id), cache_salt, vllm_xargs for custom extensions ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:403-410}}, {{cite vllm/entrypoints/openai/chat_completion/protocol.py:525-531}}).

A field that the client does not send does not always get the OpenAI default. The default --generation-config auto reads the model's generation_config.json first. Use --generation-config vllm for vLLM's neutral defaults.

Sampling defaults. to_sampling_params() uses this order for each of seven fields: the request value, else the server default, else the OpenAI default ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:735-747}}). The OpenAI defaults are temperature 1.0, top_p 1.0, top_k 0, min_p 0.0 and penalties that do nothing ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:692-700}}). The server default comes from ModelConfig.get_diff_sampling_param() ({{cite vllm/entrypoints/openai/chat_completion/serving.py:181}}):

  1. With generation_config = "vllm", it reads no file. Otherwise it reads the model's generation config ({{cite vllm/config/model.py:1875-1877}}). The default is "auto" ({{cite vllm/config/model.py:358}}).
  2. --override-generation-config replaces single values ({{cite vllm/config/model.py:1879-1880}}).
  3. It keeps only nine known keys, and it renames max_new_tokens to max_tokens ({{cite vllm/config/model.py:1882-1903}}).
  4. It logs a warning when a generation config file changes the defaults ({{cite vllm/config/model.py:1906-1915}}).

max_tokens. get_max_tokens() returns the smallest of these values that is set ({{cite vllm/entrypoints/serve/utils/api_utils.py:234-270}}):

  • max_model_len − prompt length;
  • the request value, or max_tokens from the server default when the request has none;
  • an override: max_new_tokens from --override-generation-config when --generation-config is auto or vllm, else max_new_tokens from the generation config folder that you give ({{cite vllm/entrypoints/openai/chat_completion/serving.py:183-187}});
  • a platform limit.

Worked example. max_model_len is 4,096 and the rendered prompt has 13 tokens. A request without max_completion_tokens can make up to 4,096 − 13 = 4,083 tokens. With "max_completion_tokens": 32, it makes at most 32. A prompt of 4,100 tokens raises ValueError("Input length (4100) exceeds model's maximum context length (4096).") ({{cite vllm/entrypoints/serve/utils/api_utils.py:248-252}}). The renderer normally rejects such a prompt before this, with HTTP 400.

Start a server with vllm serve Qwen/Qwen3-0.6B. Then send this request (example commands, not in the repo). The option -N turns off the output buffer of curl, so you see each event when it comes.

curl -N http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen3-0.6B",
       "messages": [{"role": "user", "content": "Hi"}],
       "max_completion_tokens": 32,
       "stream": true,
       "stream_options": {"include_usage": true},
       "chat_template_kwargs": {"enable_thinking": false}}'

The reply has this form. The ids, times, text and token counts are illustrative; "..." stands for the object, created and model fields.

data: {"id":"chatcmpl-3f9c...","object":"chat.completion.chunk","created":1761140000,"model":"Qwen/Qwen3-0.6B","choices":[{"index":0,"delta":{"role":"assistant","content":""},"logprobs":null,"finish_reason":null}],"prompt_token_ids":null,"prompt_text":null}

data: {"id":"chatcmpl-3f9c...",...,"choices":[{"index":0,"delta":{"content":"Hello"},"logprobs":null,"finish_reason":null,"token_ids":null}]}

data: {"id":"chatcmpl-3f9c...",...,"choices":[{"index":0,"delta":{"content":"!"},"logprobs":null,"finish_reason":null,"token_ids":null}]}

...

data: {"id":"chatcmpl-3f9c...",...,"choices":[{"index":0,"delta":{"content":""},"logprobs":null,"finish_reason":"stop","stop_reason":null,"token_ids":null,"weight_versions":null}]}

data: {"id":"chatcmpl-3f9c...",...,"choices":[],"usage":{"prompt_tokens":13,"total_tokens":23,"completion_tokens":10},"system_fingerprint":"vllm-<version>-<hash8>"}

data: [DONE]
  1. The first chunk carries only the role and empty content ({{cite vllm/entrypoints/openai/chat_completion/serving.py:590-598}}).
  2. Each later chunk carries the new text of one engine output, in delta.content. Each chunk is serialized with exclude_unset=True, so only the fields that the code sets appear ({{cite vllm/entrypoints/openai/chat_completion/serving.py:497-503}}).
  3. The last content chunk has finish_reason. Its content is empty because the detokenizer does not decode the end token ({{cite vllm/v1/engine/detokenizer.py:107-111}}).
  4. The usage chunk has choices: [] and usage ({{cite vllm/entrypoints/openai/chat_completion/serving.py:854-903}}). With empty choices, the serializer also drops all None fields (exclude_none=not chunk.choices). The server sends it only with include_usage or --enable-force-include-usage ({{cite vllm/entrypoints/serve/utils/api_utils.py:276-285}}). When usage is on, the fingerprint moves from the last content chunk to this chunk ({{cite vllm/entrypoints/openai/chat_completion/serving.py:815-824}}).
  5. data: [DONE] always ends the stream, also after an error chunk ({{cite vllm/entrypoints/openai/chat_completion/serving.py:504-508}}).

Check the numbers. total_tokens = 13 + 10 = 23. The 10 output tokens are nine text tokens and the end token. The 13 prompt tokens come from the Qwen3 chat template around the word "Hi" (inferred, not in the repo).

Keep-alive comments. A proxy can close an idle stream. With --sse-keep-alive-interval N (default 0, off), the server sends the comment line : keep-alive after N idle seconds ({{cite vllm/entrypoints/common/cli_args.py:156-160}}, {{cite vllm/entrypoints/serve/utils/sse_keep_alive.py:18-33}}). SSE clients ignore comment lines.

The type of one message is a union of three types ({{cite vllm/renderers/chat_utils/types.py:316-320}}). They are the OpenAI message types, a custom message type and the Harmony message type of gpt-oss models. The custom type has role: Required[str], so vLLM accepts any role name that the chat template knows ({{cite vllm/renderers/chat_utils/types.py:284-288}}). It also has the extra keys reasoning (earlier thinking text) and tools ({{cite vllm/renderers/chat_utils/types.py:306-310}}).

  • add_generation_prompt (default true) adds the start of an assistant turn to the prompt. continue_final_message instead continues the last assistant message. A request that sends both as true gets an error ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:1045-1055}}).
  • With add_generation_prompt, the role of the answer is --response-role, default assistant. Without it, the answer takes the role of the last message ({{cite vllm/entrypoints/common/cli_args.py:109-110}}, {{cite vllm/entrypoints/openai/chat_completion/serving.py:440-443}}).

The page {{link concepts/renderers-and-chat-templates}} explains how the renderer finds and applies the template.

Tool calls. The client sends tools (function definitions). The model writes a tool call as text in its own format. A tool parser turns that text into the OpenAI form message.tool_calls[i] = {id, type: "function", function: {name, arguments}} ({{cite vllm/entrypoints/generate/base/protocol.py:316-328}}).

  1. For tool_choice: "auto", start the server with --enable-auto-tool-choice and --tool-call-parser <name>. Without them, an "auto" request gets the error "auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set ({{cite vllm/renderers/online_renderer.py:260-271}}). The flag without a parser stops start-up ({{cite vllm/entrypoints/common/cli_args.py:524-525}}).
  2. "required" or a named function also needs both flags. The error text names only --tool-call-parser ({{cite vllm/renderers/online_renderer.py:272-281}}). But without --enable-auto-tool-choice, the server loads no tool parser, even when --tool-call-parser is set ({{cite vllm/parser/parser_manager.py:34-35}}).
  3. In a stream, a tool call comes in pieces as delta.tool_calls. Each piece has an index, and the name and the arguments can come in separate chunks ({{cite vllm/entrypoints/generate/base/protocol.py:331-342}}).

Reasoning content. Reasoning models write their thinking before the answer, for example between <think> tags. With --reasoning-parser <name> ({{cite vllm/engine/arg_utils.py:1136-1139}}), vLLM moves that text out of content into the vLLM-specific field reasoning of the message or the delta ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:79-80}}, {{cite vllm/entrypoints/generate/base/protocol.py:356-360}}). Without a parser, the thinking text stays in content. The request field include_reasoning (default true) controls whether the server returns it ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:271}}).

The page {{link concepts/tool-and-reasoning-parsers}} explains the parsers and how to add your own.

Every error body has the same shape: {"error": {"message", "type", "param", "code"}} ({{cite vllm/entrypoints/serve/engine/protocol.py:79-87}}). The app registers its handlers in four layers ({{cite vllm/entrypoints/serve/exception_handling/register.py:26-42}}):

  1. FastAPI errors. A body that does not match the pydantic model gives RequestValidationError. The handler answers 400 with at most 10 error entries ({{cite vllm/entrypoints/serve/exception_handling/handlers/validation.py:149-195}}).
  2. vLLM errors. All vLLM error classes derive from VLLMError ({{cite vllm/exceptions.py:10-28}}). One handler, vllm_error_handler(), gets them all ({{cite vllm/entrypoints/serve/exception_handling/register.py:32}}, {{cite vllm/entrypoints/serve/exception_handling/handlers/vllm_error.py:18-25}}). create_error_response() then selects the status from the class. VLLMValidationError becomes 400 BadRequestError with param set ({{cite vllm/entrypoints/serve/exception_handling/error_response.py:43-46}}). VLLMUnprocessableEntityError becomes 422, and a not-found error becomes 404 ({{cite vllm/entrypoints/serve/exception_handling/error_response.py:47-54}}). A GenerationError keeps its own status: 500, or 503 for a retryable error ({{cite vllm/entrypoints/serve/exception_handling/error_response.py:60-67}}, {{cite vllm/exceptions.py:131-144}}). Other server errors become 500 ({{cite vllm/entrypoints/serve/exception_handling/error_response.py:68-77}}).
  3. Raw Python errors. ValueError, TypeError and OverflowError still become 400; NotImplementedError becomes 501 ({{cite vllm/entrypoints/serve/exception_handling/error_response.py:80-87}}).
  4. Anything else becomes 500. The one exception is a Jinja TemplateError from the chat template, which becomes 400 ({{cite vllm/entrypoints/serve/exception_handling/error_response.py:88-96}}).

Which handler answers a validator error. Many request checks are pydantic validators with mode="before" that raise VLLMValidationError. Examples are "Stream options can only be defined when stream=True" ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:845-856}}) and the tool_choice checks ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:959-1043}}). The path of such an error is not the path of a type error:

  1. VLLMValidationError is not a ValueError ({{cite vllm/exceptions.py:20}}, {{cite vllm/exceptions.py:28}}). Pydantic turns only a ValueError or an AssertionError of a validator into a ValidationError, and lets other exceptions pass unchanged (general pydantic rule). The tests of vLLM show this: building the request raises VLLMValidationError itself ({{cite tests/tool_use/test_chat_completion_request_validations.py:30-38}}).
  2. So FastAPI does not make a RequestValidationError, and the validation handler of layer 1 does not run. The exception goes to vllm_error_handler() of layer 2, which calls exception_handler() and then create_error_response() ({{cite vllm/entrypoints/serve/exception_handling/handlers/vllm_error.py:24-25}}, {{cite vllm/entrypoints/serve/exception_handling/handlers/exception.py:14-24}}).
  3. The message is str(exc), and the class adds the parameter name to it ({{cite vllm/entrypoints/serve/exception_handling/error_response.py:22-24}}, {{cite vllm/exceptions.py:49-56}}). The server test expects a BadRequestError (HTTP 400) for this request ({{cite tests/entrypoints/openai/chat_completion/test_chat.py:406-415}}).

The body for "stream": false with stream_options is then (the field order follows ErrorInfo):

HTTP/1.1 400 Bad Request

{"error": {"message": "Stream options can only be defined when `stream=True`. (parameter=stream_options)",
           "type": "BadRequestError", "param": "stream_options", "code": 400}}

A field with a wrong type, for example "n": "x", takes the other path. Pydantic raises a ValidationError, and FastAPI makes a RequestValidationError. The validation handler answers 400 with the message "1 validation error: ..." and a param such as body.n ({{cite vllm/entrypoints/serve/exception_handling/handlers/validation.py:167-195}}). That handler still looks for a VLLMValidationError inside the pydantic errors ({{cite vllm/entrypoints/serve/exception_handling/handlers/validation.py:158-165}}). Because the class is no longer a ValueError, this branch cannot match a validator error any more (derived from the class tree).

A stream starts with HTTP 200. When an error happens later, the server cannot change the status. It sends the error as one more data: chunk and then data: [DONE] ({{cite vllm/entrypoints/openai/chat_completion/serving.py:504-508}}). The docstring of the engine error handler says the same ({{cite vllm/entrypoints/serve/exception_handling/handlers/vllm_error.py:46-48}}). A client must check each chunk for an error object.

What can go wrong

  • Unexpected sampling. The default --generation-config auto takes temperature, top-p and top-k from the model ({{cite vllm/config/model.py:1875-1903}}). Two servers with different models answer the same request with different defaults. Send the values that you need, or use --generation-config vllm.
  • Very long answers. Without max_completion_tokens, a request can run to the end of the context ({{cite vllm/entrypoints/serve/utils/api_utils.py:253-270}}). One such request keeps a slot in the batch and much of the KV cache for a long time.
  • stream_options without stream gives HTTP 400 ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:845-856}}).
  • Tool calls in content. Without --enable-auto-tool-choice and a parser, the model's tool-call text is not parsed ({{cite vllm/entrypoints/openai/chat_completion/serving.py:1036-1040}}), and an "auto" request fails ({{cite vllm/renderers/online_renderer.py:265-271}}).
  • Thinking text in the answer. A reasoning model without --reasoning-parser puts its thinking into content.
  • Lost connection behind a proxy. A long queue or prefill sends no bytes. Set --sse-keep-alive-interval ({{cite vllm/entrypoints/common/cli_args.py:156-160}}).
  • 401 on /v1 routes only. With an API key, /health and /metrics stay open ({{cite vllm/entrypoints/serve/middleware/authenticate.py:11}}).

Why it matters. The API is the contract with your users. Its defaults decide how long and how random the answers are, and its stream format decides what the client sees and when.

Which route takes a list of chat messages, and which takes a raw prompt?

POST /v1/chat/completions takes messages and applies the chat template ({{cite vllm/entrypoints/openai/chat_completion/api_router.py:43-44}}). POST /v1/completions takes prompt ({{cite vllm/entrypoints/openai/completion/protocol.py:53-59}}).

 How does a streamed response end?

With the line data: [DONE] and a blank line ({{cite vllm/entrypoints/openai/chat_completion/serving.py:508}}). With include_usage, a usage chunk with empty choices comes just before it.

 A request sets no temperature. The model's generation_config.json has "temperature": 0.6. Which temperature does vLLM use with the default flags, and with --generation-config vllm?

0.6 with the default auto, because the server default comes before the OpenAI default ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:741-747}}, {{cite vllm/config/model.py:1875-1877}}). With vllm, no file is read, so the OpenAI default 1.0 applies ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:692-700}}).

 max_model_len is 8,192, the prompt has 8,000 tokens, the request asks for max_completion_tokens: 500, and the generation config has no max_new_tokens. How many tokens can the answer have?

192. get_max_tokens() takes the minimum of 8,192 − 8,000 = 192 and 500 (and a platform limit, if any) ({{cite vllm/entrypoints/serve/utils/api_utils.py:253-270}}). The request does not fail; the answer ends with finish_reason: "length" after 192 tokens.

 A client gets HTTP 200, then a stream that stops with an error. Why is the status not 500, and where is the error?

The server sends the status with the first byte of the stream. A later error cannot change it. The stream generator catches the exception, sends it as one more data: chunk with an error object, and then sends data: [DONE] ({{cite vllm/entrypoints/openai/chat_completion/serving.py:504-508}}).
