The idea

DeepInfer Explained is a sister site. Its part "Learn the basics" teaches the general ideas of LLM inference: tokens, attention, the KV cache, batching and more. These ideas are the same in every engine. This site does not explain them again.

Use this page in two ways:

  • As a check. Read the recap lines. If a line is not clear to you, read the DeepInfer page first. Each link opens the DeepInfer site in a new tab.
  • As a map. The last column says where vLLM is different from DeepInfer. Each line cites the vLLM code and names the page of this site that explains it.

An everyday comparison. Think of a second car from a new maker. You already know how to drive. You only need to learn where this car puts the controls, and what it does in a different way. The comparison stops here: vLLM also adds parts that DeepInfer does not have at all, for example prefix caching and an OpenAI-compatible server.

Two facts touch every row of the table. First, vllm serve runs an API server process and a separate engine core process ({{cite vllm/v1/engine/async_llm.py:188-193}}). With one GPU, the worker runs inside the engine core process ({{cite vllm/config/parallel.py:1099-1100}}). Second, Model Runner V2 runs the model by default ({{cite vllm/config/vllm.py:730-748}}).

The 12 basics, and what vLLM changes

#DeepInfer pageRecap (one line)What is different in vLLM
1{{deepinfer learn/what-an-llm-does | What an LLM does}} An LLM gives a probability to every possible next token; an engine runs it in a loop: pick a token, add it, run again. One EngineCore.step() schedules, runs the model and updates all requests of the batch ({{cite vllm/v1/engine/core.py:657-686}}). Async scheduling is on by default when the configuration allows it ({{cite vllm/config/vllm.py:1664-1698}}). Then the engine core uses step_with_batch_queue(), which schedules the next batch before the current batch ends ({{cite vllm/v1/engine/core.py:227-229}}, {{cite vllm/config/vllm.py:591-593}}). See {{link concepts/engine-core-loop}}.
2{{deepinfer learn/tokens | Tokens and tokenizers}} A tokenizer cuts text into tokens from a fixed vocabulary and gives each token an integer id. The API server applies the chat template and tokenizes before the engine core gets the request ({{cite vllm/renderers/base.py:1385-1396}}). Detokenization is incremental, in the output processor of the front end ({{cite vllm/v1/engine/output_processor.py:307-310}}, {{cite vllm/v1/engine/async_llm.py:180}}). See {{link learn/openai-api}}.
3{{deepinfer learn/transformer | Inside a transformer}} Embedding, then a stack of layers (attention + MLP, with norms and residuals), then one score per vocabulary token. Most model families have one Python file in vllm/model_executor/models/. A registry maps the architectures name of config.json to a file and a class. Several names can share one class: InternLM3ForCausalLM also uses llama.py ({{cite vllm/model_executor/models/registry.py:140}}, {{cite vllm/model_executor/models/registry.py:152}}). The layer stack is in classes such as LlamaDecoderLayer ({{cite vllm/model_executor/models/llama.py:251}}). See {{link concepts/model-definition}}.
4{{deepinfer learn/attention | Attention, step by step}} Each token scores its query against earlier keys, applies softmax, and mixes the values; GQA and MLA make the KV cache smaller. Most models use the Attention layer class ({{cite vllm/model_executor/layers/attention/attention.py:229}}); MLA models use MLAAttention ({{cite vllm/model_executor/layers/attention/mla_attention.py:426}}). vLLM selects an attention backend (FlashAttention, FlashInfer, ...) from the head size, the dtype, the KV cache dtype, MLA and other layer properties ({{cite vllm/v1/attention/selector.py:109-122}}). See {{link concepts/attention-backends}}.
5{{deepinfer learn/prefill-decode | Prefill and decode}} Prefill reads the whole prompt in one pass (compute-bound); decode adds one token per step (memory-bound). The scheduler has no prefill phase and no decode phase. One step can mix prompt chunks and decode tokens ({{cite vllm/v1/core/sched/scheduler.py:624-633}}). See {{link concepts/scheduler}}.
6{{deepinfer learn/kv-cache | The KV cache}} The engine keeps the keys and values of earlier tokens in fixed-size blocks, with a block table per request. Blocks have 16 tokens by default; the attention backend can select another size ({{cite vllm/config/cache.py:182}}, {{cite vllm/platforms/interface.py:771-781}}). Prefix caching is on by default for most generative models ({{cite vllm/config/cache.py:254}}, {{cite vllm/engine/arg_utils.py:3062-3063}}, {{cite vllm/config/model.py:2275-2291}}). See {{link learn/prefix-caching}}.
7{{deepinfer learn/sampling | Sampling: temperature, top-k, top-p}} Sampling turns logits into probabilities, removes unlikely tokens (top-k, top-p) and draws one token with a seeded random number. Model Runner V2 samples on the GPU. In the general path, it applies top-k/top-p, then draws with a Gumbel sample from the request seed and the token position ({{cite vllm/v1/worker/gpu/sample/sampler.py:347-358}}). A request without a seed gets a random seed ({{cite vllm/v1/worker/gpu/sample/states.py:54-58}}). On supported hardware, a fused FlashInfer (or XPU) sampler can replace this path ({{cite vllm/v1/worker/gpu/sample/sampler.py:339-345}}). It does so only when requests use top-k or top-p, no request is greedy or has a seed, and no request needs processed logprobs ({{cite vllm/v1/worker/gpu/sample/sampler.py:304-315}}). See {{link concepts/sampling-and-logits-processors}}.
8{{deepinfer learn/batching | Batching}} Continuous batching makes a new packed batch in each step; chunked prefill splits a long prompt over steps. The scheduler serves running requests first, then waiting ones, in one token budget ({{cite vllm/v1/core/sched/scheduler.py:713-715}}, {{cite vllm/v1/core/sched/scheduler.py:956}}). Chunked prefill is on by default for generative models that are not encoder-decoder models ({{cite vllm/engine/arg_utils.py:3031-3035}}, {{cite vllm/config/model.py:2229-2236}}). See {{link learn/serving-metrics}}.
9{{deepinfer learn/gpus-kernels | GPUs, kernels, and speed}} A GPU runs kernels on many cores; speed depends on memory traffic, math and launch cost; CUDA graphs remove launch cost. vLLM compiles the model with torch.compile at every optimization level above O0 ({{cite vllm/config/vllm.py:1806-1810}}). The default level O2 sets cudagraph_mode to FULL_AND_PIECEWISE ({{cite vllm/config/vllm.py:434}}, {{cite vllm/config/vllm.py:310}}). See {{link concepts/compile-and-cuda-graphs}}.
10{{deepinfer learn/parallelism | Parallelism basics}} Work splits by requests (DP), matrices (TP), layers (PP), tokens (CP) or experts (EP); collectives move the data. vLLM has TP and PP groups; DeepInfer has neither. The rank grid is (-1, DP, PP, PCP, TP) ({{cite vllm/distributed/parallel_state.py:2157-2163}}). See {{link learn/tp-pp-in-practice}}.
11{{deepinfer learn/moe | Mixture of Experts (MoE)}} A router sends each token to a few of many expert MLPs, so each token uses only a small part of the weights. MoE layers come from the function FusedMoEFactory ({{cite vllm/model_executor/layers/fused_moe/layer.py:92}}). Expert parallelism is off by default; then MoE layers use tensor parallelism ({{cite vllm/config/parallel.py:190-191}}). See {{link concepts/expert-parallel-moe}}.
12{{deepinfer learn/number-formats | Number formats: BF16, FP8, FP4}} A format sets the bits for sign, exponent and mantissa; FP8 and FP4 use block scales to keep accuracy. vLLM loads many quantized checkpoint formats: FP8, AWQ, GPTQ, compressed-tensors, MXFP4 and more ({{cite vllm/model_executor/layers/quantization/__init__.py:15-49}}). The KV cache dtype auto uses the model dtype for most models ({{cite vllm/config/cache.py:232-240}}). See {{link learn/quantized-checkpoints}}.

DeepInfer has no prefix cache, no TP or PP group, no OpenAI server and no LoRA adapters. So this site explains them in full: {{link learn/prefix-caching}}, {{link learn/tp-pp-in-practice}}, {{link learn/openai-api}}, {{link learn/lora-adapters}}. Serving metrics are also new: {{link learn/serving-metrics}}.

Worked example. A request with a prompt of 1,000 tokens needs ⌈1,000 / 16⌉ = 63 blocks in vLLM with the default size. With DeepInfer's 128-token blocks, it needs ⌈1,000 / 128⌉ = 8 blocks. The memory is almost the same; only the number and size of the blocks change.

What can go wrong

  • The DeepInfer code is not the vLLM code. The "In DeepInfer" parts of the DeepInfer pages cite DeepInfer files. Use them only for the idea. For vLLM behaviour, use the citations on this site.
  • DeepInfer's step kinds do not apply. A DeepInfer step is a prefill step or a decode step. A vLLM step can be both ({{cite vllm/v1/core/sched/scheduler.py:624-633}}). Do not expect separate prefill and decode step times in vLLM metrics.

Why it matters. The rest of this site uses the basics without a new explanation. A gap in the basics makes the concept pages hard to follow.

Which DeepInfer page explains block tables and preemption, and what is the default block size in vLLM?

{{deepinfer learn/kv-cache | The KV cache}}. vLLM uses 16 tokens per block by default ({{cite vllm/config/cache.py:182}}). The attention backend can select another size when you do not set one ({{cite vllm/platforms/interface.py:771-781}}).

 A DeepInfer step is a prefill step or a decode step. Can one vLLM step hold decode tokens of 50 requests and a chunk of a new prompt?

Yes. The vLLM scheduler has no prefill or decode phase. It gives tokens to each request until its computed tokens catch up ({{cite vllm/v1/core/sched/scheduler.py:624-633}}). It serves the running requests first, then the waiting ones with the rest of the token budget ({{cite vllm/v1/core/sched/scheduler.py:713-715}}, {{cite vllm/v1/core/sched/scheduler.py:956}}).

 You start vllm serve on one H100 with 80 GB and set no scheduler flags. What are the token budget and max_num_seqs?

8,192 tokens and 1,024 requests. vllm serve uses the usage context OPENAI_API_SERVER ({{cite vllm/entrypoints/launchers/api_server/entry.py:72}}, {{cite vllm/entrypoints/launchers/api_server/entry.py:82}}). An H100 with 80 GB reports about 79 GiB (inferred, not in the repo). That is 70 GiB or more and less than 160 GiB, and the GPU is not an A100 or a GB10. So the "H100 and H200" defaults apply ({{cite vllm/engine/arg_utils.py:2970-2983}}). This is true with the default --performance-mode; the mode throughput doubles both values ({{cite vllm/engine/arg_utils.py:3171-3175}}).
