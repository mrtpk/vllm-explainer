It sends requests at a chosen rate, times the stream chunks, and reports latency percentiles and goodput.

The idea

To tune a server, you need numbers that you can repeat. vllm bench has several subcommands. Only one of them talks to a running server:

  • vllm bench serve sends HTTP requests to a server that you started with vllm serve. It measures what a client sees. The metrics are time to first token (TTFT), time per output token (TPOT), inter-token latency (ITL), end-to-end latency (E2EL), throughput and goodput ({{link learn/serving-metrics}}).
  • vllm bench throughput, latency and startup start their own engine in the same command, with the offline LLM class. They measure the engine without HTTP.

The client controls the load: how many requests, how long each prompt is, how fast they arrive, and how many run at once. The server's own metrics measure the same requests from the inside ({{link concepts/metrics-and-observability}}). The two views differ by design, and this page shows where.

An everyday comparison. Think of a test shopper. The shopper starts a stopwatch at the shop door and stops it when the bag is in the hand. The shop's own records start when the order reaches the counter. Both are correct; they time different things. The comparison stops at the crowd. The test shopper of vLLM can be a thousand shoppers at once, with a random rhythm of arrivals that you choose.

In the code

Step 1: the command and the request function

vllm bench serve is a thin subcommand: it adds the arguments of vllm/benchmarks/serve.py and calls its main ({{cite vllm/entrypoints/cli/benchmark/serve.py:10-21}}). The default backend is openai and the default endpoint is /v1/completions ({{cite vllm/benchmarks/serve.py:1647-1668}}). The backend picks a request function; openai-chat sends chat requests, and there are functions for embeddings and rerank servers ({{cite vllm/benchmarks/lib/endpoint_request_func.py:1155-1172}}). Without --model, the client asks the server's /v1/models for the first model ({{cite vllm/benchmarks/serve.py:2126-2131}}, {{cite vllm/benchmarks/serve.py:170-176}}).

Each request is a stream with usage in the last chunk, so the client gets the server's token count ({{cite vllm/benchmarks/lib/endpoint_request_func.py:226-238}}). The client takes its time points here:

  1. The clock starts with time.perf_counter() just before the POST ({{cite vllm/benchmarks/lib/endpoint_request_func.py:248-252}}).
  2. Line 286: TTFT is the time of the first SSE chunk that has choices, even when its text is empty.
  3. Line 290: each later chunk with choices adds one ITL value. One chunk can carry several tokens (for example with --stream-interval), so the client ITL is per chunk, not per token.
  4. Line 295: the usage chunk gives completion_tokens; it does not move the end time.
  5. E2EL (latency) is the time of the last chunk with choices ({{cite vllm/benchmarks/lib/endpoint_request_func.py:307}}). A request with no such chunk is a failure ({{cite vllm/benchmarks/lib/endpoint_request_func.py:298-305}}).

Step 2: datasets

--dataset-name picks where the prompts come from; the default is random ({{cite vllm/benchmarks/datasets/datasets.py:1593-1612}}):

The random dataset makes token ids from a seeded generator, decodes them and encodes them again, so the prompt has the asked length ({{cite vllm/benchmarks/datasets/datasets.py:556-579}}). --seed (default 0) seeds it and the arrival times ({{cite vllm/benchmarks/datasets/datasets.py:1585}}, {{cite vllm/benchmarks/serve.py:2060-2061}}). --num-prompts defaults to 1,000 ({{cite vllm/benchmarks/datasets/datasets.py:70}}).

The client sends the output length as max_tokens ({{cite vllm/benchmarks/lib/endpoint_request_func.py:232}}). The model can stop earlier at an end token. Add --ignore-eos when every request must produce exactly that many tokens ({{cite vllm/benchmarks/serve.py:1831-1836}}). Also note: the client sends no temperature unless you pass --temperature, so the server's default sampling applies ({{cite vllm/benchmarks/serve.py:2246-2252}}).

Step 3: request rate, burstiness and max concurrency

{{term request-rate | --request-rate}} is in requests per second; the default inf sends all requests at time 0 ({{cite vllm/benchmarks/serve.py:1745-1753}}). For a finite rate, the client draws the gap before each request from a gamma distribution:

  • {{term burstiness | --burstiness}} is the shape of the gamma distribution, default 1.0 ({{cite vllm/benchmarks/serve.py:1754-1765}}). The scale is 1 / (rate × burstiness), so the mean gap is always 1 / rate. Burstiness 1 gives exponential gaps (a Poisson process). Below 1, gaps vary more (bursts); above 1, they are more even.
  • Lines 513-526: without a ramp-up, the client then scales all gaps so that the last request starts exactly at num_prompts / rate. The comment says that this keeps the throughput stable across seeds.
  • --max-concurrency N wraps each request in an asyncio.Semaphore(N) ({{cite vllm/benchmarks/serve.py:1001-1013}}). Requests that wait for the semaphore start their TTFT clock only when they get it; the wait is kept as client_queue_time ({{cite vllm/benchmarks/serve.py:1014-1016}}). With a rate and a concurrency limit, the real rate can be lower than the asked rate ({{cite vllm/benchmarks/serve.py:1679-1690}}).
  • --ramp-up-strategy linear|exponential with start and end rates changes the rate during the run ({{cite vllm/benchmarks/serve.py:1965-1987}}).

Step 4: warm-up and the ready check

Two start steps are off by default. --ready-check-timeout-sec defaults to 0, so the client skips the initial test request and prints "Skipping endpoint ready check." ({{cite vllm/benchmarks/serve.py:1989-1994}}, {{cite vllm/benchmarks/serve.py:908-925}}). --num-warmups defaults to 0 ({{cite vllm/benchmarks/serve.py:1780-1785}}). A first request after a server start can pay one-time costs, so a run without warm-up includes them in its first results.

Step 5: how the metrics are computed

After all requests finish, calculate_metrics builds the result. TPOT is computed per request:

  • TPOT = (E2EL − TTFT) / (output tokens − 1), and only requests with more than one output token enter the TPOT statistics (lines 655-658). For goodput, a one-token request has TPOT 0 (line 660).
  • The output token count comes from the server's usage; without it, the client tokenizes the text ({{cite vllm/benchmarks/serve.py:635-650}}).
  • Throughputs divide by the benchmark duration, from the start of the send loop to the end of the last request ({{cite vllm/benchmarks/serve.py:773-781}}, {{cite vllm/benchmarks/serve.py:1048}}, {{cite vllm/benchmarks/serve.py:1123}}).
  • Mean, median, standard deviation and percentiles use NumPy over all requests (TTFT, TPOT, E2EL) or over all chunk gaps (ITL) ({{cite vllm/benchmarks/serve.py:782-806}}). --metric-percentiles defaults to 99 ({{cite vllm/benchmarks/serve.py:1858-1866}}); --percentile-metrics defaults to ttft,tpot,itl for generative models ({{cite vllm/benchmarks/serve.py:2255}}).
  • {{term goodput-slo | --goodput}} ttft:500 tpot:50 sets SLOs in milliseconds ({{cite vllm/benchmarks/serve.py:1867-1878}}). A request is good when each given SLO is at least its measured value. Request goodput = good requests / duration ({{cite vllm/benchmarks/serve.py:669-692}}, {{cite vllm/benchmarks/serve.py:779}}).

With --enable-per-request-metrics on the server, the client also stores the server's queue_time_ms and time_to_first_token_ms per request in its result data ({{cite vllm/benchmarks/lib/endpoint_request_func.py:110-125}}, {{cite vllm/benchmarks/serve.py:391-403}}). Step 7: vllm bench throughput

vllm bench throughput measures offline throughput: it builds an LLM from the engine flags and sends all prompts in one generate() call ({{cite vllm/benchmarks/throughput.py:37-48}}, {{cite vllm/benchmarks/throughput.py:129-151}}). It prints requests/s, total tokens/s and output tokens/s ({{cite vllm/benchmarks/throughput.py:1108-1114}}). Without --dataset-path, it uses the random dataset and needs --input-len or --random-input-len ({{cite vllm/benchmarks/throughput.py:642-650}}). --async-engine uses an in-process AsyncLLM instead ({{cite vllm/benchmarks/throughput.py:863-867}}, {{cite vllm/benchmarks/throughput.py:308-314}}). There is no HTTP, no SLO and no arrival process: all requests wait at time 0.

Step 8: vllm bench latency

vllm bench latency measures the time of one batch. The batch has --batch-size (default 8) random prompts of --input-len (32) tokens. Each prompt gets exactly --output-len (128) tokens, because the command sets ignore_eos ({{cite vllm/benchmarks/latency.py:35-37}}, {{cite vllm/benchmarks/latency.py:96-103}}). It runs 10 warm-up iterations and 30 measured ones, and prints the mean and the 10th to 99th percentiles of the batch time ({{cite vllm/benchmarks/latency.py:45-53}}, {{cite vllm/benchmarks/latency.py:158-168}}).

Step 9: vllm bench startup

vllm bench startup measures how long LLM(...) takes to start, cold and warm ({{cite vllm/benchmarks/startup.py:3-9}}). A cold run uses a new temporary VLLM_CACHE_ROOT and a fresh Inductor cache; a warm run reuses the caches ({{cite vllm/benchmarks/startup.py:109-128}}). Each run is a new subprocess ({{cite vllm/benchmarks/startup.py:133-147}}). The defaults are 3 cold runs, 1 warm-up and 3 warm runs ({{cite vllm/benchmarks/startup.py:193-210}}). It reports the start-up time and the compilation time of each run.

throughput, latency and startup start the engine with the usage context LLM_CLASS ({{cite vllm/entrypoints/llm.py:341-343}}). The exception is throughput --async-engine: it uses the vllm serve context OPENAI_API_SERVER ({{cite vllm/entrypoints/launchers/api_server/entry.py:69-82}}). On an 80 GiB H100, that gives a token budget of 16,384, but vllm serve uses 8,192 ({{cite vllm/engine/arg_utils.py:2970-2981}}). Set --max-num-batched-tokens explicitly when you compare with a server. vllm bench sweep runs vllm bench serve over a grid of server and client settings ({{cite vllm/benchmarks/sweep/cli.py:19-25}}, {{cite vllm/benchmarks/sweep/serve.py:465-520}}).

Command (an example, not from the repository):

vllm bench serve --model meta-llama/Llama-3.1-8B-Instruct --dataset-name random \
  --random-input-len 1024 --random-output-len 128 --ignore-eos --num-prompts 1000 \
  --request-rate 20 --num-warmups 20 --metric-percentiles 50,99 --goodput ttft:500 tpot:50

  1. Duration and throughput. 1,000 requests at 20 RPS start over 50 s (Step 3); the last ones finish at 52.1 s. Request throughput = 1000 / 52.10 = 19.19. It is below 20 because the duration includes the tail after the last send.
  2. Total token throughput = (1,024,000 + 128,000) / 52.10 = 22,111 ({{cite vllm/benchmarks/serve.py:781}}). Prompt tokens dominate it, so it says little about decode speed.
  3. Goodput 17.60 req/s = 917 good requests / 52.10 s. So 8.3 % of the requests missed at least one SLO. The mean TTFT (182 ms) and the mean TPOT (24 ms) are still far below the SLOs. The P99 TTFT (690 ms) shows the misses.
  4. ITL vs TPOT. The ITL median (19.8 ms) is below the TPOT median (23.9 ms), and the ITL P99 is high (95.7 ms). Some gaps contain a step with a large prefill chunk; TPOT spreads such spikes over the whole request.
  5. Peak values come from one-second buckets of the client's token times ({{cite vllm/benchmarks/serve.py:715-760}}). "Peak concurrent requests: 61" is the largest number of requests that were active in one second, as the client saw them. It is an upper bound for the requests in flight at one moment.

This method is advice; each step names the code that makes it work.

  1. Fix the inputs. Use one --seed, one dataset and fixed lengths, with --ignore-eos for synthetic data (Step 2).
  2. Warm up. Set --num-warmups (default 0) and --ready-check-timeout-sec (default 0) (Step 4). Better: run one short benchmark after each server start and throw it away.
  3. Sweep the request rate, not only inf. With inf, all requests arrive at once, and TTFT mostly measures the queue. Sweep for example 2, 4, 8, 16 RPS until goodput stops rising. vllm bench sweep automates grids.
  4. Compare at equal goodput. For two configurations, compare the highest request rate at which goodput stays at, say, 95 % of throughput, with the same SLOs.
  5. Watch the server at the same time. vllm:num_requests_waiting, vllm:kv_cache_usage_perc and preemptions explain why a rate fails ({{link concepts/metrics-and-observability}}).
  6. Run the client on another machine or on free CPU cores. The client is one Python process; a busy client delays its own timestamps.

For --request-rate 10, the mean gap is 0.1 s at every burstiness b. The gamma mean is shape × scale = b × 1/(10 b) = 0.1 s ({{cite vllm/benchmarks/serve.py:504-508}}). The spread changes: the coefficient of variation of a gamma distribution is 1/√b (general statistics). So b = 1 gives a standard deviation of 0.1 s, and b = 4 gives 0.05 s. b = 0.25 gives 0.2 s: arrivals come in clusters with long pauses. --burstiness inf gives a constant gap of 0.1 s ({{cite vllm/benchmarks/serve.py:499-502}}). A lower burstiness at the same rate gives higher TTFT percentiles, because requests come in groups.

What can go wrong

  • Huge TTFT at --request-rate inf. All requests arrive at time 0, so most of them wait in the queue (Step 3). Use a finite rate or --max-concurrency.
  • Output tokens below the asked length. The model stopped at an end token; use --ignore-eos (Step 2).
  • The first run is slower than the next ones. No warm-up by default (Step 4).
  • Client ITL is much larger than Prometheus ITL. The server sends several tokens per chunk (--stream-interval), or the client process is busy (Step 1, Step 6).
  • All requests fail with "Never received a valid chunk". The endpoint does not stream choices, for example the wrong --backend for --endpoint ({{cite vllm/benchmarks/lib/endpoint_request_func.py:298-305}}).
  • vllm bench throughput is faster than the server. It has no HTTP, no arrival process, and a larger default token budget (note in Step 9).

Why it matters. A benchmark number is only useful when you know its start point, its clock and its load. With that, you can compare two configurations fairly and explain the gap between the client view and the server view.

Which vllm bench subcommand needs a running vllm serve?

Only serve: it sends HTTP requests to --host/--port or --base-url ({{cite vllm/benchmarks/serve.py:1654-1662}}). throughput, latency and startup build an LLM themselves ({{cite vllm/benchmarks/throughput.py:48}}, {{cite vllm/benchmarks/latency.py:88}}).

 A request produced exactly 1 output token. How does it count in the TPOT statistics of vllm bench serve, and in the goodput check?

It is not in the TPOT statistics, because TPOT needs more than one token ({{cite vllm/benchmarks/serve.py:655-658}}). In the goodput check, its TPOT is 0 ({{cite vllm/benchmarks/serve.py:660}}), so it can only miss the TTFT or E2EL SLO.

 With --request-rate 10 --burstiness 0.5, what is the mean gap between requests, and how does the arrival pattern differ from the default?

The mean gap is still 0.1 s: shape 0.5 × scale 1/(10 × 0.5) ({{cite vllm/benchmarks/serve.py:504-508}}). The gaps vary more than with the default 1.0, so requests come in bursts. The client also scales the gaps so that the last request starts at 100 s for 1,000 prompts ({{cite vllm/benchmarks/serve.py:513-526}}).

 With --max-concurrency 8, a request waits 2 s for the semaphore. Is the wait in its TTFT?

No. The request function starts the clock only when it runs, after the semaphore ({{cite vllm/benchmarks/serve.py:1010-1013}}, {{cite vllm/benchmarks/lib/endpoint_request_func.py:248}}). The wait is kept as client_queue_time ({{cite vllm/benchmarks/serve.py:1016}}), which is reported only if you select it in --percentile-metrics.

 The client reports a P50 TTFT of 140 ms, the server's Prometheus P50 TTFT is 110 ms, and the per-request time_to_first_token_ms median is 60 ms. Explain all three.

The client clock runs from the POST to the first chunk, with the network, HTTP parsing and SSE output ({{cite vllm/benchmarks/lib/endpoint_request_func.py:248}}, {{cite vllm/benchmarks/lib/endpoint_request_func.py:286}}). Prometheus runs from arrival_time at render start to the handled first output ({{cite vllm/renderers/base.py:1380}}, {{cite vllm/v1/metrics/stats.py:525}}): rendering, tokenization, the queue and prefill. The per-request value is only SCHEDULED to first token, the prefill on the engine clock ({{cite vllm/entrypoints/generate/base/serving.py:73-74}}). So 140 − 110 ms is outside the server, and 110 − 60 ms is front-end work plus the queue.
