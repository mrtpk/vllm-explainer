A plugin adds or replaces an entry with register_model; a "module:Class" string keeps the import lazy, and a cached subprocess inspects the class. --- vLLM looks up the architecture name from config.json in ModelRegistry; a plugin adds its own class there with register_model.

The idea

A Hugging Face checkpoint names its model class in config.json, for example "architectures": ["LlamaForCausalLM"] ({{link learn/hf-checkpoints}}). vLLM does not use the Transformers class. It looks up the name in the {{term model-registry}}, a table from architecture name to a vLLM model class. At this commit the built-in table has 406 names.

An {{term out-of-tree}} package adds a name to the table, or replaces one, with ModelRegistry.register_model(). It calls this function from a {{term general-plugin}}, so the call runs in every process ({{link concepts/plugin-loading}}). The package can give the class itself, or a string "module:Class". The string makes a {{term lazy-registration | lazy entry}}: vLLM imports the module only in a process that needs the class.

The front end must know what the model can do before any worker exists: is it generative, does it support pipeline parallelism or LoRA? So the registry inspects the class and keeps the answers in a {{term model-info}} record. For a lazy entry, the inspection runs in a separate Python process, and the result goes into a JSON cache on disk. The page {{link concepts/model-interfaces}} explains the answers.

An everyday comparison. Think of a library catalogue. Each card has a title and a shelf position, not the book itself. You fetch the book only when you want to read it. A catalogue clerk writes a summary of each book on the card once, and reuses it until the book changes. The comparison stops here. A vLLM "card" can also hold the book itself (the eager form). And a new card with the same title replaces the old one.

Step 2: register_model(), eager or lazy

  1. Lines 1175-1177. The architecture name must be a str, else TypeError.
  2. Lines 1179-1185. A name that is already in the table is overwritten. vLLM logs this only at DEBUG level. So a plugin can also replace a built-in model, for example LlamaForCausalLM.
  3. Lines 1187-1193. A string must contain exactly one colon. "pkg.mod:Cls" becomes _LazyRegisteredModel("pkg.mod", "Cls"). Nothing is imported now. "pkg.mod.Cls" (dots only) raises ValueError.
  4. Lines 1194-1195. A subclass of nn.Module becomes a _RegisteredModel. Its constructor computes the model info at once, in this process ({{cite vllm/model_executor/models/registry.py:974-979}}).
  5. Lines 1196-1201. Anything else (an object, a function) raises TypeError.

Why lazy. The docstring gives the reason: a string avoids an import that starts CUDA, and so the error "Cannot re-initialize CUDA in forked subprocess" (lines 1170-1173). In vllm serve the CLI already uses spawn ({{cite vllm/entrypoints/common/startup.py:147-149}}), and get_mp_context switches to spawn when CUDA is already started ({{cite vllm/utils/system_utils.py:145-162}}). The lazy form still has a clear gain: a process that does not build the model does not import its module. A test checks that the inspection of a lazy entry does not start CUDA ({{cite tests/models/test_registry.py:150-158}}).

Step 4: from config.json to a class

The front end inspects the architecture while it makes ModelConfig ({{cite vllm/config/model.py:703-706}}, {{cite vllm/config/model.py:741-744}}). The log line "Resolved architecture: ..." shows the result at INFO level. inspect_model_cls tries these steps in order:

  1. Lines 1362-1367. With --model-impl transformers, the Transformers backend class comes first. See {{term model-impl}}.
  2. Lines 1368-1371. With --model-impl terratorch, the answer is always "Terratorch".
  3. Lines 1374-1383. If no name of the list is registered, model_impl is auto and no conversion is set, try the Transformers backend.
  4. Lines 1385-1389. Try each name of architectures in order. _normalize_arch keeps a registered name. Otherwise it maps a name with a known suffix to a registered base name, for example MyForSequenceClassification to MyForCausalLM ({{cite vllm/model_executor/models/registry.py:1325-1349}}). The first name that inspects wins.
  5. Lines 1391-1400. The Transformers fallback again, now without the conversion condition.
  6. Line 1402. No answer: _raise_for_unsupported raises ValueError.

resolve_model_cls has the same order, but it imports the class ({{cite vllm/model_executor/models/registry.py:1404-1456}}). The worker calls it when it builds the model ({{cite vllm/model_executor/model_loader/utils.py:305-313}}). If the result is a Transformers backend class and model_impl is auto, vLLM warns "has no vLLM implementation, falling back to Transformers implementation" ({{cite vllm/model_executor/model_loader/utils.py:315-322}}).

The four messages of _raise_for_unsupported tell you the cause ({{cite vllm/model_executor/models/registry.py:1205-1236}}):

  • "failed to be inspected": the name is registered, but the import or inspection failed. The traceback is in the log above it.
  • "was supported in vLLM until v...": the architecture was removed.
  • "is not supported in-tree anymore. Please install the plugin at ...": the architecture moved to a plugin.
  • "are not supported for now": the name is unknown. Your plugin did not load, or did not register this name.

Step 5: the inspection subprocess and its cache

A lazy entry inspects its class without an import in the calling process:

  1. Lines 1078-1085. Find the source file: directly for vllm.model_executor.models.*, else with importlib.util.find_spec. find_spec imports the parent package, not the module itself (Python rule).
  2. Lines 1088-1091. Hash the source and read the cache file. The hash is md5 (sha256 where md5 is not available) of the relative path and the bytes of the file ({{cite vllm/model_executor/models/registry.py:1004-1020}}, {{cite vllm/utils/hashing.py:118-121}}). For a package __init__.py, it covers every .py file of the package (lines 1005-1009).
  3. Lines 1106-1109. On a miss, run _ModelInfo.from_model_cls(self.load_model_cls()) in a subprocess. The comment says why: "to avoid initializing CUDA".
  4. Lines 1114-1116. Save the result, only if a source file was found.

The cache directory is $VLLM_CACHE_ROOT/modelinfos ({{cite vllm/model_executor/models/registry.py:996-997}}). VLLM_CACHE_ROOT defaults to ~/.cache/vllm, or $XDG_CACHE_HOME/vllm ({{cite vllm/envs.py:713-718}}). The subprocess is python -m vllm.model_executor.models.registry ({{cite vllm/model_executor/models/registry.py:823}}). It loads the general plugins first, so your plugin's packages are ready:

This runs only on a cache miss, and also for built-in models, because they are lazy too. The page {{link concepts/plugin-loading}} counts the extra plugin run that a miss causes.

Step 6: what the class must look like

The worker builds the model with initialize_model. It checks the constructor signature by name:

A class without both vllm_config and prefix gets a DeprecationWarning, and vLLM guesses the old arguments (lines 114-136 of the same file). The registry also checks the structure when it inspects the class ({{link concepts/model-interfaces}}):

  • __init__ accepts the keyword vllm_config, the class has embed_input_ids, and forward accepts input_ids and positions ({{cite vllm/model_executor/models/interfaces_base.py:108-115}}).
  • A generative model also has compute_logits ({{cite vllm/model_executor/models/interfaces_base.py:140-147}}).
  • The default loader calls model.load_weights(weights) with an iterator of (name, tensor) pairs ({{cite vllm/model_executor/model_loader/default_loader.py:503}}). The registry does not check this method.

The page {{link concepts/model-definition}} explains how to write these methods, with llama.py as the example.

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

A fresh host runs vllm serve meta-llama/Llama-3.1-8B-Instruct. config.json says "architectures": ["LlamaForCausalLM"]. (The model is an example.)

  1. The front end builds ModelConfig. registry.is_text_generation_model calls inspect_model_cls(["LlamaForCausalLM"], ...) ({{cite vllm/config/model.py:705}}).
  2. model_impl is auto and the name is registered, so the first fallback is skipped. Step 4 of the lookup finds the lazy entry ("vllm.model_executor.models.llama", "LlamaForCausalLM").
  3. The source path is vllm/model_executor/models/llama.py (line 1079). The cache file is ~/.cache/vllm/modelinfos/vllm-model_executor-models-llama-LlamaForCausalLM.json: module and class joined by "-", dots replaced by "-" ({{cite vllm/model_executor/models/registry.py:999-1001}}).
  4. The file does not exist: DEBUG log "not found", then a subprocess. It loads the general plugins, imports llama.py, computes the 24 fields and returns them. The parent writes {"hash": "...", "modelinfo": {...}} ({{cite vllm/model_executor/models/registry.py:1054-1070}}).
  5. The next start of the server finds the file with the same hash: no subprocess.

Now the user installs a plugin that calls register_model("LlamaForCausalLM", "acme.llama:FastLlama") (a made-up package). The front end loads general plugins while it builds the CLI parser, before ModelConfig exists ({{cite vllm/engine/arg_utils.py:3243}}). So the lookup finds the new lazy entry. Its cache file is acme-llama-FastLlama.json, with the hash of acme/llama.py. Each worker loads the same plugin in init_worker and imports acme.llama in resolve_model_cls.
  • Per process, per entry. _try_inspect_model_cls and _try_load_model_cls are module functions with lru_cache(maxsize=128), keyed by (name, entry) ({{cite vllm/model_executor/models/registry.py:1125-1150}}). ModelConfig asks the registry several times, but the subprocess runs at most once per entry and process.
  • Per model in the worker. get_model_architecture keeps a dict keyed by a hash of the model name, convert type, runner type, trust_remote_code, model_impl and architectures ({{cite vllm/model_executor/model_loader/utils.py:340-356}}).
  • On disk. One JSON file per (module, class). The key is the source hash only. A change in a file that the model module imports does not change the hash (derived from lines 1004-1020). Delete $VLLM_CACHE_ROOT/modelinfos after you edit an imported mixin.
  • Eager entries. No disk cache and no subprocess. The process computes the info at registration (line 1195). The front end, the engine core and every worker import the module, because each one runs the general plugin.

The method inspect_model_cls of a lazy entry has the @logtime decorator: "Registry inspect model class: Elapsed time ..." at DEBUG level ({{cite vllm/model_executor/models/registry.py:1071}}, {{cite vllm/logging_utils/log_time.py:17-26}}).

_try_resolve_transformers decides if the Transformers backend can run a name ({{cite vllm/model_executor/models/registry.py:1250-1323}}):

  1. A name from _TRANSFORMERS_BACKEND_MODELS, such as TransformersForCausalLM, is returned as it is (lines 1255-1256).
  2. Else it loads the auto_map classes of a custom checkpoint, config class first (lines 1270-1280).
  3. It looks for the name in the transformers package, then in auto_map["AutoModel*"] (lines 1282-1307). With nothing found: None for auto, ValueError for transformers.
  4. The class must be backend-compatible, or able to set its attention implementation (lines 1309-1321).
  5. It returns the name of the backend class from ModelConfig._get_transformers_backend_cls(): Transformers + MultiModal (nested config) + MoE + a suffix by task ({{cite vllm/config/model.py:1129-1157}}).

The names in _TRANSFORMERS_SUPPORTED_MODELS, such as OlmoForCausalLM, are normal registry names. They map to a backend class directly, so the fallback is not needed for them ({{cite vllm/model_executor/models/registry.py:734-752}}).

What can go wrong

register_model("MyArch", "my_pkg.model.MyModel") raises ValueError: the string must be "my_pkg.model:MyModel" ({{cite vllm/model_executor/models/registry.py:1187-1191}}). Other vLLM settings, such as scheduler_cls, use dots only ({{link concepts/plugin-map}}).
  • "failed to be inspected". The subprocess failed, for example because the module raises on import. vLLM wraps the child's stderr in a RuntimeError ({{cite vllm/model_executor/models/registry.py:1596-1602}}), logs it, and then raises the ValueError ({{cite vllm/model_executor/models/registry.py:1141-1150}}, {{cite vllm/model_executor/models/registry.py:1208-1212}}). Read the log above the error.
  • Two plugins register the same name. The last call wins, with only a DEBUG log ({{cite vllm/model_executor/models/registry.py:1179-1185}}). The order of the plugin calls is the order of entry_points().
  • A stale cache after an edit of an imported file. See the deep dive on caches. The flags can be wrong until the model file changes or you delete the cache.
  • An old-style constructor. A class with __init__(self, config, ...) works only through argument guessing, with a DeprecationWarning ({{cite vllm/model_executor/model_loader/utils.py:105-117}}).
  • The class is not generative. If the class has no embed_input_ids or no compute_logits, ModelConfig raises "This model does not support --runner generate" ({{cite vllm/config/model.py:727-728}}).

Why it matters. A model plugin is the usual way to serve a new architecture without a fork of vLLM. The registry decides the class in each process, and the cached model info decides which features start-up allows. Most model-plugin failures show up as one of the four registry messages.

What is the difference between register_model("A", MyModel) and register_model("A", "pkg.mod:MyModel")?

The class form makes a _RegisteredModel and computes the model info at once, in the calling process. The string form makes a _LazyRegisteredModel; vLLM imports the module only when a process needs the class ({{cite vllm/model_executor/models/registry.py:1187-1195}}).

 Your plugin registers "LlamaForCausalLM". What happens to the built-in Llama class?

The plugin's entry replaces it. register_model overwrites an existing name and logs only at DEBUG level ({{cite vllm/model_executor/models/registry.py:1179-1185}}). The general plugins load before ModelConfig inspects the model, so the lookup finds the new entry.

 The server starts with the message "Model architectures ['MyArch'] are not supported for now". Name a likely cause.

The name is not in the registry. The plugin did not load (for example, VLLM_PLUGINS does not name it), or it does not register this name. A registered name whose inspection fails gives "failed to be inspected" instead ({{cite vllm/model_executor/models/registry.py:1205-1236}}).

 MyModel in my_pkg/model.py inherits MyBase from my_pkg/mixins.py. You add SupportsPP to MyBase and change only mixins.py. The registration is "my_pkg.model:MyModel". Why can --pipeline-parallel-size 2 still fail?

The cache key is the hash of my_pkg/model.py only ({{cite vllm/model_executor/models/registry.py:1004-1020}}). The hash did not change, so the front end reads the old supports_pp=false from modelinfos ({{cite vllm/model_executor/models/registry.py:1088-1098}}). ModelConfig then raises NotImplementedError ({{cite vllm/config/model.py:1569-1576}}). Delete the cache file, or change model.py too. (Derived from the hash code.)
