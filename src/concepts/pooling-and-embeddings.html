Its task decides the HTTP routes.

The idea

A generative model ends with an LM head and a sampler, and it runs many steps per request. A {{term pooling-model}} ends with a {{term pooler}}. The pooler turns the hidden states of the prompt into one vector (an embedding), a few class scores, or one vector per token. The request then finishes after its prompt is processed: there is no decode phase.

vLLM runs one runner type per instance. With --runner pooling, the same engine core, scheduler and KV cache serve the request, but the worker calls the pooler instead of the sampler. vLLM can also convert a generative architecture: --convert embed or --convert classify wraps the model class. So, for example, a *ForCausalLM checkpoint can serve embeddings from its last hidden state.

An everyday comparison. A generative model is a writer who adds one word at a time. A pooling model is a reader who reads the whole text once and then writes one summary number or one index card. The comparison stops being true in one place. vLLM's reader may read a long text in several chunks, but only for some pooling types (Step 4).

In the code

Step 1: the pooling tasks

The task names are a Literal type. The old names score and encode are removed and raise a validation error with a hint:

TaskOutputTypical model
embedone vector per requestsentence embedding models
classifyclass scores per request; also cross-encoder scoring*ForSequenceClassification, rerankers
token_embedone vector per token; late-interaction scoringColBERT-style models
token_classifyscores per token*ForTokenClassification, process reward models
pluginwhatever an IO processor plugin returnssee {{link concepts/frontend-plugins}}

When a model supports several tasks, get_pooling_task picks one. The order is: --pooler-config '{"task": ...}' if set, else token_classify for *ForTokenClassification. Otherwise it takes the first of embed&token_classify, embed, classify, token_embed, token_classify, plugin ({{cite vllm/config/model.py:1918-1951}}). Reward models have no own task name; their default convert is embed ({{cite vllm/config/model.py:2353-2354}}).

Step 2: --runner and --convert

Both options default to auto ({{cite vllm/config/model.py:163-169}}). The runner types are generate, pooling and draft; a pooling runner allows the converts embed and classify ({{cite vllm/config/scheduler.py:20}}, {{cite vllm/config/model.py:124-128}}).

  • Runner. A set --convert forces pooling. Else a sentence-transformers config means pooling; else the registry decides; else the architecture suffix decides ({{cite vllm/config/model.py:1283-1329}}).
  • Convert. A native pooling model needs none. Else the suffix decides, and a generative architecture run as pooling becomes embed ({{cite vllm/config/model.py:1331-1360}}).

The convert is applied when vLLM resolves the model class ({{cite vllm/model_executor/model_loader/utils.py:325-333}}). as_embedding_model subclasses the model and gives it an embedding pooler. By default, it takes the normalized hidden state of the last token ({{cite vllm/model_executor/models/adapters.py:250-281}}). as_seq_cls_model adds a score linear layer with num_labels outputs and a classification pooler ({{cite vllm/model_executor/models/adapters.py:307-378}}). Both return a class unchanged if it already pools.

vllm serve Qwen/Qwen3-Embedding-0.6B --runner pooling
# LAST-token embeddings from a chat model:
vllm serve meta-llama/Llama-3.1-8B-Instruct --convert embed

Step 3: Pooler and PoolerConfig

Every pooler implements one small interface:

DispatchPooler holds one sub-pooler per task and calls the one for the request's task ({{cite vllm/model_executor/layers/pooler/special.py:25-57}}). --pooler-config sets PoolerConfig:

  • Pooling types. Sequence pooling CLS, LAST, MEAN; token pooling ALL, STEP ({{cite vllm/config/pooler.py:16-20}}). pooling_type fills one of the two by its value ({{cite vllm/config/pooler.py:143-168}}).
  • Defaults. The user's value wins. Next comes the sentence-transformers config of the checkpoint, then the model class default ({{cite vllm/config/model.py:775-803}}). The class defaults are LAST and ALL ({{cite vllm/model_executor/models/interfaces_base.py:163}}, {{cite vllm/model_executor/models/interfaces_base.py:173}}).
  • Normalization. normalize was removed; use_activation replaces it ({{cite vllm/config/pooler.py:125-137}}). For embed, an unset use_activation means true: the embedding is L2-normalized ({{cite vllm/pooling_params.py:215-217}}).
  • Dimensions. A request can ask for fewer dimensions only if the model is matryoshka; the head then cuts the vector before it normalizes ({{cite vllm/pooling_params.py:219-242}}, {{cite vllm/model_executor/layers/pooler/seqwise/heads.py:84-115}}).
  • Long inputs. enable_chunked_processing and max_embed_len let an embedding model accept inputs above its position limit, by weighted averaging of chunks; not for multimodal inputs ({{cite vllm/config/pooler.py:80-96}}).

Step 4: what is turned off for pooling models

  • Async scheduling is off by default for pooling models. The code says it "negatively impacts performance of pooling models" ({{cite vllm/config/vllm.py:1664-1675}}). An explicit --async-scheduling is not rejected.
  • Chunked prefill and prefix caching. Encoder-only (bidirectional) pooling models support neither. Decoder pooling models support both only with LAST or ALL pooling; MEAN, CLS and STEP turn them off ({{cite vllm/config/model.py:2193-2228}}, {{cite vllm/config/model.py:2239-2270}}). These properties set only the defaults. An explicit --enable-chunked-prefill or --enable-prefix-caching only logs a warning that the model does not officially support it ({{cite vllm/engine/arg_utils.py:3031-3035}}, {{cite vllm/engine/arg_utils.py:3051-3060}}, {{cite vllm/engine/arg_utils.py:3069-3078}}).
  • Logits processors. --logits-processors on a pooling model raises ValueError; entry-point processors are skipped ({{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:172-179}}).
  • The sampler. The model runner builds a PoolingRunner instead of a sampler ({{cite vllm/v1/worker/gpu/model_runner.py:467}}, {{cite vllm/v1/worker/gpu/model_runner.py:534-535}}).

The serving classes send the prompt with PoolingParams through AsyncLLM.encode ({{cite vllm/v1/engine/async_llm.py:1034-1037}}). An IO processor plugin turns custom input into pooling input, and the result into a custom response. Only the pooling entry points use it ({{link concepts/frontend-plugins}}, Step 2).

Step 6: the pooling runner in Model Runner V2

In a pooling model, the worker calls model_runner.pool() right after execute_model, not sample_tokens ({{cite vllm/v1/worker/gpu_worker.py:1355-1359}}). pool() calls the PoolingRunner and returns an AsyncPoolingOutput, which copies the result to the CPU on a side stream ({{cite vllm/v1/worker/gpu/model_runner.py:2318-2358}}):

The pooling cursor knows, per request, which rows of this step belong to it and whether the prompt is complete (finished_mask). The scheduler then finishes a request as soon as its pooler output arrives:

Model Runner V2 supports the tasks embed, classify, token_embed, token_classify and embed&token_classify. A model whose selected task is not in this list fails at start-up with a hint to use VLLM_USE_V2_MODEL_RUNNER=0 ({{cite vllm/v1/worker/gpu/pool/pooling_runner.py:20-50}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Server (example): vllm serve meta-llama/Llama-3.1-8B-Instruct --convert embed on one GPU. Hidden size 4,096.

  1. Start-up. --convert embed forces --runner pooling. The class becomes LlamaForCausalLM wrapped by as_embedding_model, named with the suffix ForEmbedding ({{cite vllm/model_executor/models/adapters.py:279}}). There is no sentence-transformers config, so seq_pooling_type is the class default LAST. Pooling task: embed. Async scheduling: off. Chunked prefill and prefix caching: allowed, because LAST pooling on a decoder model supports them.
  2. Routes. /pooling, /v1/embeddings, /v2/embed, and the score and rerank routes (embed enables scoring). No /v1/chat/completions.
  3. Request. {"model": "...", "input": "vLLM is fast", "dimensions": 256} → a validation error, because Llama-3.1 is not a matryoshka model (is_matryoshka reads the HF config, {{cite vllm/config/model.py:2083-2091}}). Without dimensions, the request goes through.
  4. Step. Say the prompt has 6 tokens. The scheduler schedules all 6; the forward pass gives hidden_states [6, 4096] for this request.
  5. Pool. LAST takes row 5: [4096]. The head casts it to the head dtype, applies no projector, keeps all 4,096 dimensions, and L2-normalizes it (use_activation true by default for embed).
  6. Finish. The output reaches the scheduler, the request becomes FINISHED_STOPPED in this same update, and the API server returns one vector of 4,096 floats.

PoolerConfig.compute_hash has no factors: the pooler settings do not change the compiled graph ({{cite vllm/config/pooler.py:186-201}}).

The code does not state the reasons for the rule in ModelConfig (Step 4, {{cite vllm/config/model.py:2193-2228}}). The pooling methods show them:

  • LAST takes the row of the last token in the step ({{cite vllm/model_executor/layers/pooler/seqwise/methods.py:50-57}}). Earlier chunks and cached prefix blocks only have to provide KV, which they do.
  • MEAN and CLS raise RuntimeError for a partial prefill. MEAN divides the sum of the step's rows by the full prompt length ({{cite vllm/model_executor/layers/pooler/seqwise/methods.py:37-47}}, {{cite vllm/model_executor/layers/pooler/seqwise/methods.py:60-106}}). Only token pooling (ALL) keeps the rows of earlier chunks ({{cite vllm/v1/pool/metadata.py:48-54}}). A cached prefix block has KV but no hidden states, so a prefix-cache hit would also lose rows (derived).
  • Bidirectional (encoder-only) models: every token attends to every other token, so a chunk cannot be computed before the rest of the prompt exists (derived).

So a BERT-style embedding model processes each prompt in one step. Without chunked prefill, vLLM raises an unset max_num_batched_tokens to at least max_model_len ({{cite vllm/engine/arg_utils.py:3177-3186}}).

What can go wrong

  • 404 on /v1/chat/completions. The model runs as a pooling model, so the generate routes do not exist ({{cite vllm/entrypoints/launchers/api_server/routers.py:55-60}}).
  • No /score or /rerank for a classifier. Scoring needs num_labels == 1 for classify ({{cite vllm/entrypoints/pooling/utils.py:231-236}}).
  • "score task was removed". Use classify; encode became token_embed or token_classify ({{cite vllm/tasks.py:20-30}}).
  • "Parameter normalize was removed". Use use_activation ({{cite vllm/config/pooler.py:125-135}}).
  • "does not support Matryoshka embeddings". The request sent dimensions to a model without matryoshka support ({{cite vllm/pooling_params.py:225-230}}).
  • Start-up error with a hint to VLLM_USE_V2_MODEL_RUNNER=0. The selected task is not one that Model Runner V2 supports (Step 6).

Why it matters. Embedding and reranking servers depend on settings that differ from chat serving. The pooling type decides whether chunked prefill and prefix caching work. The task decides which routes a client can call.

Which option turns a *ForCausalLM checkpoint into an embedding model, and what does it do to the class?

--convert embed. vLLM wraps the class with as_embedding_model, which adds an embedding pooler ({{cite vllm/model_executor/model_loader/utils.py:328-330}}, {{cite vllm/model_executor/models/adapters.py:250-281}}).

 A model is served with task classify and 3 labels. Which routes exist?

/pooling and /classify. No scoring routes, because classify enables them only with num_labels == 1 ({{cite vllm/entrypoints/pooling/factories.py:120-130}}, {{cite vllm/entrypoints/pooling/utils.py:231-236}}).

 Why does a decoder embedding model with MEAN pooling not use prefix caching?

is_prefix_caching_supported returns false for MEAN, CLS and STEP pooling on decoder models ({{cite vllm/config/model.py:2239-2270}}). MEAN needs the hidden states of all prompt tokens in one step, and it raises RuntimeError for a partial prefill ({{cite vllm/model_executor/layers/pooler/seqwise/methods.py:66-68}}). Cached KV blocks give no hidden states (derived).

 In Model Runner V2, which call produces the pooler output, and when does the scheduler finish the request?

The worker calls model_runner.pool() right after execute_model ({{cite vllm/v1/worker/gpu_worker.py:1355-1359}}); it runs the PoolingRunner and returns an AsyncPoolingOutput ({{cite vllm/v1/worker/gpu/model_runner.py:2338-2357}}). The scheduler sets FINISHED_STOPPED in the update that receives the pooler output ({{cite vllm/v1/core/sched/scheduler.py:2263-2266}}).
