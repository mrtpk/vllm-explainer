Identity attributes describe the device; config hooks change VllmConfig in the front end and again in each engine core; component pickers name the classes to use; kernel hooks load kernels. CudaPlatform is the reference implementation. --- The Platform class is the contract for a hardware vendor: vLLM reads its attributes and calls its hooks at fixed points of the start-up.

The idea

The page {{link concepts/platform-plugins}} explains how a process chooses its {{term platform}}. This page explains what the chosen object must do. Platform in vllm/platforms/interface.py is a class with 90 methods (84 without a leading underscore) and 12 class attributes. Most have a default. A vendor subclass overrides the ones that differ on its hardware.

The members fall into four groups:

  1. Identity attributes. Values that describe the device: its name, its PyTorch device type, its {{term dispatch-key}}, its distributed backend, and more.
  2. Config hooks. A {{term platform-hook}} that vLLM calls while it builds VllmConfig. The platform can check the config, change defaults, or reject a setting. check_and_update_config is the most important one: it sets the worker class.
  3. Component pickers. A {{term component-picker}} returns the dotted name of a class: the {{term attention-backend}}, the device communicator, the LoRA kernel wrapper, the graph wrapper. vLLM calls it where it builds that component.
  4. Kernel hooks. Methods that import kernel libraries or replace Triton kernels.

Anything that the class does not define goes to a fallback: Platform.__getattr__ looks for the name in torch.<device_type>, for example torch.cuda.

An everyday comparison. Think of a franchise manual. Head office writes the chapters and a default answer for each one. A local shop rewrites only the chapters that differ in its country. Head office reads each chapter at a fixed moment: the opening checklist before the shop opens, the staff chapter when it hires. The comparison stops here. In vLLM each process reads its own copy of the manual. The front end reads the config chapters; a worker reads the chapters about the model and the GPU.

The picture

Read the numbers in order. Steps 1-6 run in the front end and shape the VllmConfig. The engine core and the workers get that config through pickling, and they detect the platform again for themselves. After its handshake, each engine core calls vllm_config.__post_init__() again, so steps 5 and 6 run a second time there (step 17, {{cite vllm/v1/engine/core.py:1336-1337}}). The pickers in the worker column run in each worker.

Step 2: config hooks, and when each one runs

Four hooks change the config. Three of them run in the front end, while vllm serve parses the flags and builds VllmConfig. The two hooks in __post_init__ also run again in each engine core process ({{cite vllm/v1/engine/core.py:1336-1337}}):

  1. pre_register_and_update(parser) runs in AsyncEngineArgs.add_cli_args, after the general plugins and after the parser has its flags ({{cite vllm/engine/arg_utils.py:3243-3257}}). The docstring names the use: register an out-of-tree quantization config ({{cite vllm/platforms/interface.py:638-651}}). The CLI builds four parsers in the front end: serve, launch render and run-batch at start-up ({{cite vllm/entrypoints/cli/main.py:100-110}}), and one more in setup_server, which builds the parser again to find the non-default flags ({{cite vllm/entrypoints/launchers/launcher.py:368}}, {{cite vllm/entrypoints/common/startup.py:70-71}}). So this call runs four times. The hook runs a fifth time, with no parser, at the start of create_engine_config ({{cite vllm/engine/arg_utils.py:2246}}).
  2. apply_config_platform_defaults(vllm_config) runs in VllmConfig.__post_init__ ({{cite vllm/config/vllm.py:1804}}). It changes defaults, for example the list of custom ops. ROCm uses it to turn on custom ops for its AITER kernels ({{cite vllm/platforms/rocm.py:1074-1084}}).
  3. check_and_update_config(vllm_config) runs late in VllmConfig.__post_init__ ({{cite vllm/config/vllm.py:2046}}). The method goes on after it, to line 2318 ({{cite vllm/config/vllm.py:2318}}). It can raise for a setting that the hardware does not support, or change the config. Its most important job is worker_cls. CUDA shows the pattern:

The fourth config hook, update_block_size_for_backend, runs later, after the model is loaded, because it needs the attention backends of the layers ({{cite vllm/platforms/interface.py:749-794}}). With worker processes, each worker calls it ({{cite vllm/v1/executor/multiproc_executor.py:701-702}}). With the uni executor, the engine core process calls it ({{cite vllm/v1/executor/uniproc_executor.py:74-75}}). When the user did not set --block-size, it picks a block size that all attention backends accept. That is the preferred size of a single backend, else the default 16 if all accept it, else the smallest common size ({{cite vllm/platforms/interface.py:771-781}}, {{cite vllm/platforms/interface.py:721-739}}).

The front end also calls validate_environ, which warns about unknown VLLM_* variables ({{cite vllm/engine/arg_utils.py:2250}}, {{cite vllm/platforms/interface.py:1454-1468}}).

Step 4: kernel hooks

  • import_kernels imports the compiled kernel libraries. The default imports vllm._C and, if present, vllm._moe_C_stable_libtorch ({{cite vllm/platforms/interface.py:365-373}}). It runs when Python imports vllm._custom_ops, at module level ({{cite vllm/_custom_ops.py:21}}). CUDA imports its own set ({{cite vllm/platforms/cuda.py:238-250}}).
  • register_triton_kernel_overrides lets a platform replace core Triton kernels. The worker calls it right after the general plugins, before it makes the worker class ({{cite vllm/v1/worker/worker_base.py:286-290}}). The default does nothing ({{cite vllm/platforms/interface.py:375-386}}). The CPU platform registers C++ versions, but only when Triton is missing ({{cite vllm/platforms/cpu.py:690-705}}).
  • import_ir_kernels imports vllm.kernels, the IR op implementations. The docstring says that an out-of-tree platform should override it ({{cite vllm/platforms/interface.py:258-264}}). The kernel config calls it ({{cite vllm/config/kernel.py:54}}).

Step 5: the fallback to torch.<device_type>

  1. Lines 1303-1304. Dunder names raise AttributeError at once. The comment says why: pickle looks for names such as __getstate__.
  2. Lines 1306-1312. The method looks up torch.cuda (for CUDA) and returns the attribute, if it is not None.
  3. Lines 1314-1319. Otherwise it logs a warning once and returns None. It does not raise.

So current_platform.synchronize is torch.cuda.synchronize on CUDA, and the forward context checks for None before the call ({{cite vllm/forward_context.py:368-370}}). CudaPlatform does not define synchronize itself; the fallback finds it. (Derived from the method list of cuda.py.)

Not every hook runs once. pre_register_and_update runs five times in the front end of vllm serve (the two lines above). check_and_update_config and apply_config_platform_defaults run again in each engine core process, which calls vllm_config.__post_init__() again after its handshake ({{cite vllm/v1/engine/core.py:1336-1337}}). They also run again whenever code makes a new VllmConfig. vLLM's replace() helper does that: it calls the class again with the old fields ({{cite vllm/config/utils.py:121-129}}). For example, the EAGLE drafter loader in a worker calls it when the draft load config differs ({{cite vllm/v1/worker/gpu/spec_decode/eagle/utils.py:90-91}}). So these hooks must give the same result when they run again on a config that they have already changed.

cuda.py has two classes and picks one when the module loads. If pynvml.nvmlInit() works, CudaPlatform is NvmlCudaPlatform; otherwise (for example on Jetson) it is NonNvmlCudaPlatform ({{cite vllm/platforms/cuda.py:1040-1054}}). Both subclass CudaPlatformBase ({{cite vllm/platforms/cuda.py:226}}). The module docstring says that the code may use pynvml but must not start a CUDA context ({{cite vllm/platforms/cuda.py:3-5}}).

get_attn_backend_cls, step by step ({{cite vllm/platforms/cuda.py:419-518}}):

  1. Read the device capability, for example (9, 0) on H100.
  2. If the user selected a backend (--attention-backend), validate only that one. An import error or an invalid configuration raises ValueError; there is no fallback (lines 430-449).
  3. Else get the priority list for the case (MLA or not, capability, head count, KV cache dtype) and validate each backend in order (get_valid_backends, {{cite vllm/platforms/cuda.py:377-417}}).
  4. No valid backend: ValueError with every reason (lines 471-475).
  5. Pick the valid backend with the smallest priority number (lines 479-485).
  6. If the user set --block-size and that excluded a better backend, warn (lines 489-506).
  7. Log the choice once and return the dotted class path (lines 508-518).

CUDA does not override apply_config_platform_defaults or pre_register_and_update; ROCm overrides both ({{cite vllm/platforms/rocm.py:1064-1084}}). ROCm's pre_register_and_update sets an environment variable with os.environ.setdefault, so a second call does nothing new ({{cite vllm/platforms/rocm.py:1072}}).

The design doc lists the members that a platform must implement at least: _enum, device_type, device_name, check_and_update_config (which must set worker_cls), get_attn_backend_cls and get_device_communicator_cls ({{cite docs/design/plugin_system.md:100-108}}). The code shows why each one matters:

  • _enum = PlatformEnum.OOT makes an enabled CustomOp call forward_oot ({{cite vllm/model_executor/custom_op.py:183}}, {{cite vllm/model_executor/custom_op.py:202-203}}).
  • If worker_cls stays "auto", the worker passes "auto" to resolve_obj_by_qualname, which cannot split it at a dot ({{cite vllm/v1/worker/worker_base.py:293-296}}, {{cite vllm/utils/import_utils.py:121}}). Start-up fails in the worker. (Derived.)
  • The base get_attn_backend_cls returns "", and the selector raises "Invalid attention backend" ({{cite vllm/v1/attention/selector.py:223-226}}).
  • The base communicator class is generic. It is used only for groups with more than one rank ({{cite vllm/distributed/parallel_state.py:549}}).

The test platform overrides only check_and_update_config (it sets custom_ops = ["all"]) and get_attn_backend_cls ({{cite tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/dummy_platform.py:15-32}}). It leaves worker_cls as it is, because the tests do not start real workers on it. (Derived.)
  • The docstring of pre_register_and_update says that it is called "before global VllmConfig is initialized or cli arguments are parsed" ({{cite vllm/platforms/interface.py:644-645}}). This is true for the calls in add_cli_args while the CLI builds its parsers. The parser that setup_server builds and the call in create_engine_config come after the flags are parsed ({{cite vllm/engine/arg_utils.py:2246}}).
  • The design doc says that "triton ops" cannot use the custom way "now" ({{cite docs/design/plugin_system.md:143-144}}). The code now has register_triton_kernel_overrides for platforms that replace core Triton kernels ({{cite vllm/platforms/interface.py:375-386}}).
  • The design doc calls check_and_update_config "very early" in the start-up ({{cite docs/design/plugin_system.md:105}}). In the code it runs late in VllmConfig.__post_init__, after the platform detection, the general plugins and all five pre_register_and_update calls (Step 2).

What can go wrong

check_and_update_config runs in the process that builds VllmConfig (for vllm serve, the front end). It runs again in each engine core, but only after the engine core has started its workers ({{cite vllm/v1/engine/core.py:1190-1224}}, {{cite vllm/v1/engine/core.py:1336-1337}}). A change to a Python object outside the config (a module global, a registry) does not reach the workers. Change only fields of vllm_config: those reach the other processes inside the pickled config ({{cite vllm/v1/engine/utils.py:256-287}}).
  • A missing method returns None. Platform.__getattr__ logs "does not have ... attribute" once and returns None ({{cite vllm/platforms/interface.py:1314-1319}}). The caller then fails later with a TypeError if it calls the value. (Derived.)
  • LoRA on a new platform. The base get_punica_wrapper raises NotImplementedError ({{cite vllm/platforms/interface.py:1203-1206}}). Implement it, or do not use --enable-lora.
  • A selected backend is invalid. On CUDA, --attention-backend with an invalid backend raises ValueError; vLLM does not fall back ({{cite vllm/platforms/cuda.py:430-446}}).
  • The block sizes do not fit together. When the attention backends share no block size, update_block_size_for_backend raises ValueError ({{cite vllm/platforms/interface.py:740-747}}).
  • A quantization method is not supported. If the platform sets supported_quantization and the method is not in it, verify_quantization raises ValueError ({{cite vllm/platforms/interface.py:1153-1158}}).

Why it matters. A vendor port of vLLM is mostly a Platform subclass plus a worker class. Knowing which hook runs in which process, and when, tells you where to put each change and where to look when start-up fails.

Which Platform hook sets the worker class, and in which process does it run?

check_and_update_config. CUDA sets worker_cls to vllm.v1.worker.gpu_worker.Worker when it is "auto" ({{cite vllm/platforms/cuda.py:330-331}}). It runs in VllmConfig.__post_init__ ({{cite vllm/config/vllm.py:2046}}), in the front end for vllm serve, and again in each engine core process ({{cite vllm/v1/engine/core.py:1336-1337}}).

 Your platform class has no synchronize method, and its device_type is "cuda". What does current_platform.synchronize return?

torch.cuda.synchronize. Platform.__getattr__ looks up the name in torch.<device_type> ({{cite vllm/platforms/interface.py:1306-1312}}).

 With one GPU (TP = PP = DP = 1), which process calls get_attn_backend_cls, and is get_device_communicator_cls called?

The engine core process: the uni executor runs the worker there and loads the model ({{cite vllm/v1/executor/uniproc_executor.py:68-75}}). get_device_communicator_cls is not called, because the code asks for it only when the group has more than one rank ({{cite vllm/distributed/parallel_state.py:549-552}}).

 Your check_and_update_config appends "+my_op" to compilation_config.custom_ops each time it runs. Why can the list get the entry twice, and what is the fix?

check_and_update_config runs in every VllmConfig.__post_init__ ({{cite vllm/config/vllm.py:2046}}). Each engine core calls vllm_config.__post_init__() again on the config that the front end has already changed ({{cite vllm/v1/engine/core.py:1336-1337}}). vLLM's replace() also makes a new VllmConfig from the old fields, so __post_init__ runs again on a list that already has the entry ({{cite vllm/config/utils.py:121-129}}). An example is the EAGLE drafter loader ({{cite vllm/v1/worker/gpu/spec_decode/eagle/utils.py:90-91}}). Append only when the entry is missing, as the CPU platform does for +gelu ({{cite vllm/platforms/cpu.py:394-399}}). (Derived: the new config shares the old compilation_config object, because replace() passes the same field values.)
