The idea

Data parallelism runs several copies of the model, and each copy serves other requests ({{deepinfer learn/parallelism | Parallelism basics}}). In vllm serve, one copy is one engine core process with its own workers, scheduler and KV cache. Each copy is one {{term data-parallel-rank}}. With -dp 4 there are four engine cores, but the clients still see one HTTP endpoint.

Three questions follow. Which process decides where a request goes? How does it know the load of each engine? And do the engines need to wait for each other? vLLM answers them like this:

  • The API servers decide. Each one scores every engine and sends the request to the lowest score. This is the default {{term load-balancing-mode}}, internal load balancing.
  • The engines report their queue lengths and KV cache usage to a {{term dp-coordinator}}. The coordinator publishes them to all API servers, by default every 100 ms when they change.
  • The engines of a dense model are independent. The engines of an MoE model must run every forward pass together, because the expert layers exchange tokens across ranks. They step in {{term dp-wave | waves}} and run dummy batches when they have no work.

An everyday comparison. Think of a supermarket with four checkouts and four entrance doors. A guide at each door sends each customer to the checkout with the shortest line. A screen above the doors shows the line lengths and refreshes every few seconds. Each guide also remembers whom she sent recently, because the screen is a little late. The comparison stops here. For MoE models, the checkouts scan in lockstep, and an idle cashier must "scan" an empty basket while others work.

In the code

Step 1: one flag, N engine cores and N API servers

--data-parallel-size (-dp) sets the number of engine cores; the default is 1 ({{cite vllm/engine/arg_utils.py:1230-1232}}, {{cite vllm/config/parallel.py:147-149}}). The engine launcher starts one process per local DP rank, named EngineCore_DP<rank>:

Each rank gets its own GPUs: local rank r takes devices r × world_size and up. The docstring example is "[2, 3] for local_dp_rank=1" with world_size=2 ({{cite vllm/v1/engine/utils.py:441-445}}). The number of API server processes has its own default, set in the CLI by the load-balancing mode:

So internal load balancing gets one API server per DP rank. With more than one API server, the CLI process stays alive as a supervisor and serves no HTTP ({{cite vllm/entrypoints/cli/serve.py:149-156}}). The API servers share one listen socket with SO_REUSEPORT, so the kernel spreads the TCP connections over them ({{cite vllm/entrypoints/cli/serve.py:298}}). The page {{link concepts/architecture-overview}} counts all processes.

Step 2: dense model or MoE model

The engine core process chooses its class at start-up:

  • Dense model. reconfigure_for_independent_dp_rank() sets the DP size to 1 and the DP rank to 0 ({{cite vllm/config/parallel.py:1192-1201}}). The engine is a plain EngineCoreProc. It has its own NCCL world and never waits for the other ranks. It sleeps when it has no work.
  • MoE model. The engine is a DPEngineCoreProc. Its workers form one NCCL world with all DP ranks, so the expert layers can exchange tokens ({{link concepts/distributed-groups}}). Step 5 explains the lockstep.

Step 3: the DP coordinator

The coordinator is a separate process. It exists only when it has a job:

Only DP rank 0 starts it, and only in online serving. Wave coordination is turned on only for MoE models ({{cite vllm/v1/engine/utils.py:1227-1232}}, {{cite vllm/v1/engine/utils.py:1260-1265}}). The engines publish their counts only in internal and hybrid mode ({{cite vllm/v1/engine/core.py:1207-1213}}). When the counts change, an engine sends SchedulerStats with waiting count, running count and KV cache usage to client index −1, the coordinator ({{cite vllm/v1/engine/core.py:1622-1633}}).

  1. Line 267. Publish at most every stats_update_interval_ms (100 by default, {{cite vllm/v1/engine/coordinator.py:152}}) when something changed, otherwise every 5 s.
  2. Lines 269-275. For lockstep MoE engines, wait at least 50 ms so that the counts of one step arrive from all ranks.
  3. Lines 287-288. The message is (counts, current_wave, engines_running), sent on an XPUB socket to every API server.

The class docstring says the engines send "just waiting and running queue lengths" ({{cite vllm/v1/engine/coordinator.py:29-31}}). The code also stores kv_cache_usage ({{cite vllm/v1/engine/coordinator.py:404-406}}).

Step 4: the API server picks an engine

With DP > 1 and internal load balancing, AsyncLLM uses a DPLBAsyncMPClient ({{cite vllm/v1/engine/core_client.py:158-173}}). A background task keeps the newest published counts in lb_engines ({{cite vllm/v1/engine/core_client.py:1578-1590}}). Each new request runs this choice:

  1. Lines 1755-1759. A request may name its rank. The serving layer takes it from the X-data-parallel-rank header ({{cite vllm/entrypoints/generate/base/serving.py:216-228}}). Then no score is computed.
  2. Lines 1765-1768. The scan starts at eng_start_index, which differs per API server: (engines × client_index) // client_count ({{cite vllm/v1/engine/core_client.py:1739-1741}}).
  3. Lines 1777-1778. The base score is the larger of two loads. One is this API server's in-flight requests times the number of API servers; the other is waiting + running.
  4. Lines 1779-1786. Waiting requests cost extra when the KV cache is more than half full: up to 3 × waiting at 100 % usage.
  5. Line 1792. The chosen engine's waiting count grows by client_count at once, so the next request sees it before the next publication.
  6. Line 1798. The start index rotates by one, so equal scores do not always pick the same engine.

The in-flight count drops when the engine reports the request as finished ({{cite vllm/v1/engine/core_client.py:1810-1817}}). add_request_async also stamps the request with the current wave and this API server's client_index. So the engine can send the outputs back to the right API server ({{cite vllm/v1/engine/core_client.py:1599-1609}}).

The deployment doc says the internal load balancing is "based on the running and waiting queues" and could later add "KV cache aware logic" ({{cite docs/serving/data_parallel_deployment.md:77}}). The code already uses the KV cache usage in the waiting penalty (lines 1779-1786 above).

Step 5: MoE engines step together in waves

The expert layers of all ranks must meet in every forward pass ({{cite docs/serving/data_parallel_deployment.md:9}}, {{deepinfer concepts/expert-parallelism | Expert parallelism}}). So DPEngineCoreProc changes the busy loop:

  1. Lines 2486-2495. The engine ran no real step. If no rank is running, it waits. Otherwise it runs execute_dummy_batch(), so the other ranks' collectives do not hang.
  2. Lines 2502-2505. All ranks agree whether any rank still has unfinished requests.
  3. Lines 2507-2525. When none has, the wave ends. Rank 0 tells the coordinator, and every rank increments its wave number and resets its step counter.

The agreement is a CPU all-reduce over a gloo group that the engine core process makes for itself ({{cite vllm/config/parallel.py:735-743}}). It does not run every step: only at the first step of a wave and then every dp_sync_interval steps, 16 by default ({{cite vllm/v1/engine/core.py:2542-2559}}, {{cite vllm/config/parallel.py:163-164}}). A new request on an idle engine starts the next wave: the engine tells the coordinator, and the coordinator sends START_DP_WAVE to the others ({{cite vllm/v1/engine/core.py:2360-2373}}, {{cite vllm/v1/engine/coordinator.py:426-440}}).

Step 6: metrics per engine

Every Prometheus metric of the engines has an engine label with the DP rank as a string, next to model_name ({{cite vllm/v1/metrics/loggers.py:499-504}}). An engine core sends its scheduler stats of a step to only one front end ({{cite vllm/v1/core/sched/scheduler.py:2516-2521}}). With more than one API server, vLLM turns off the periodic log line, because each API server sees only part of the stats ({{cite vllm/v1/metrics/loggers.py:1384-1389}}). Prometheus then runs in multiprocess mode with a shared directory for all API server processes ({{cite vllm/entrypoints/cli/serve.py:282-283}}).

vllm serve meta-llama/Llama-3.1-8B-Instruct -dp 4      # one node, 4 GPUs, dense model

Processes. --api-server-count is unset, so it becomes 4. The coordinator runs, because the mode is internal. Each engine core has one worker process: world_size_across_dp is 4, so the executor backend is "mp" ({{cite vllm/config/parallel.py:1055-1061}}). Total (derived): 1 CLI supervisor + 4 API servers + 1 coordinator + 4 engine cores + 4 workers = 14.

The three decisions (score = max(C × in-flight, w + r) + 6 × w × max(0, kv − 0.5)):

  1. Request 1, scan 0, 1, 2, 3. e0 = max(8, 12) + 6 × 2 × 0.4 = 16.8. e1 = max(4, 8) = 8. e2 = max(4, 8) + 6 × 1 × 0.1 = 8.6. e3 = max(8, 9) = 9. Engine 1 wins. Its waiting count becomes 0 + 4 = 4, its in-flight count 2, and the start index 1.
  2. Request 2, scan 1, 2, 3, 0. e1 = max(8, 12) = 12, with no KV penalty because 0.40 < 0.5. e2 = 8.6, e3 = 9, e0 = 16.8. Engine 2 wins. Its waiting count becomes 5, its in-flight count 2, and the start index 2.
  3. Request 3, scan 2, 3, 0, 1. e2 = max(8, 12) + 6 × 5 × 0.1 = 15; e3 = 9; e0 = 16.8; e1 = 12. Engine 3 wins.

Engine 0 gets nothing: it has a queue and a nearly full KV cache. Engine 2 was a good choice once, but the local +4 on its waiting count and the KV penalty pushed request 3 elsewhere. The next publication from the coordinator, within about 100 ms, replaces these local guesses with real counts. (Derived from {{cite vllm/v1/engine/core_client.py:1754-1798}}.)

  1. Both engines are idle: engines_running is false, so has_work() is false, and each busy loop blocks on its input queue ({{cite vllm/v1/engine/core.py:1596-1602}}).
  2. The request reaches engine 0. add_request sees an idle, unpaused engine, sets engines_running and sends start_wave to the coordinator ({{cite vllm/v1/engine/core.py:2360-2373}}).
  3. The coordinator moves to "running" and sends START_DP_WAVE (wave, exclude=0) to the engines; engine 0 is excluded because it started the wave ({{cite vllm/v1/engine/coordinator.py:426-440}}, {{cite vllm/v1/engine/coordinator.py:447-456}}).
  4. Engine 1 starts its loop for the wave ({{cite vllm/v1/engine/core.py:2406-2424}}). With no requests, each of its steps is a dummy batch: one uniform-decode token through the model ({{cite vllm/v1/worker/gpu_worker.py:1454-1460}}).
  5. In every forward, the workers of both ranks first agree on a padded token count and a CUDA graph mode. They use a CPU all-reduce of a [6, dp_size] int32 tensor ({{cite vllm/v1/worker/gpu/dp_utils.py:65-74}}). Model Runner V2 calls this before it prepares the inputs ({{cite vllm/v1/worker/gpu/model_runner.py:1806-1821}}).
  6. At step 1 and every 16th step, the engines run the "unfinished?" all-reduce. Assume the request is done on engine 0 and nothing waits anywhere. Then the result is false: the wave ends, rank 0 sends wave_complete, and both engines block again ({{cite vllm/v1/engine/core.py:2502-2525}}).

So an idle MoE rank can run up to 15 dummy steps after the last request ends somewhere (derived from the sync interval). Larger --dp-sync-interval means fewer CPU all-reduces but more dummy steps at the end of a wave.

What can go wrong

  • The API servers time out at start-up. With more than one API server, they wait for the engines with VLLM_ENGINE_READY_TIMEOUT_S, 600 s by default; a slow model load can exceed it ({{cite vllm/v1/engine/core_client.py:753-768}}).
  • Runtime LoRA updates are refused. VLLM_ALLOW_RUNTIME_LORA_UPDATING with more than one API server raises ValueError ({{cite vllm/entrypoints/cli/serve.py:316-319}}).
  • Prefix-cache hits get lost. The score looks at load, not at prefixes, so a repeated prompt can land on another rank. Use X-data-parallel-rank or an external router if you need affinity.
  • Idle MoE ranks still use the GPU. During a wave, an idle rank runs dummy batches ({{cite vllm/v1/engine/core.py:2486-2495}}).
  • Missing log line. With several API servers, the periodic "Avg prompt throughput" line is gone by design; use /metrics ({{cite vllm/v1/metrics/loggers.py:1384-1389}}).

Why it matters. DP is the main way to add throughput when one copy of the model fits. With the routing score and the MoE lockstep, you can predict where a request goes and why an idle GPU is busy.

With -dp 4 and no other DP flag, how many API server processes run, and why?

Four. In internal mode, an unset --api-server-count becomes the DP size ({{cite vllm/entrypoints/cli/serve.py:124-125}}).

 Which engine core class does a dense model get with DP > 1, and which does an MoE model get?

Dense: EngineCoreProc, after the DP size is reset to 1. MoE: DPEngineCoreProc ({{cite vllm/v1/engine/core.py:1534-1543}}).

 When does the DP coordinator process not exist, even with DP > 1?

Only DP rank 0 (the head node) starts it, and never in offline mode ({{cite vllm/v1/engine/utils.py:1230-1232}}). needs_dp_coordinator is also false for a dense model in external load-balancing mode ({{cite vllm/config/vllm.py:870-874}}), but vllm serve refuses that combination at start-up ({{cite vllm/engine/arg_utils.py:2445-2454}}).

 An engine has waiting = 4, running = 6, KV usage 0.75. An API server with client_count 2 has 3 requests in flight on it. What is the score?

max(2 × 3, 4 + 6) = 10, plus 4 × 6 × max(0, 0.75 − 0.5) = 6. Score 16 ({{cite vllm/v1/engine/core_client.py:1777-1786}}).

 Why can an MoE rank with no requests keep its GPU busy for a while, and what controls how long?

During a wave every rank must join each forward pass, so an idle rank runs dummy batches ({{cite vllm/v1/engine/core.py:2486-2495}}). The wave ends only after an all-reduce shows no unfinished requests. That all-reduce runs at the first step and then every dp_sync_interval steps, 16 by default ({{cite vllm/v1/engine/core.py:2542-2559}}).
