The first traceback in that process's log names the cause; this page maps it to a fix.

The idea

A vllm serve problem shows up in one of three phases:

  1. Start-up: the log never reaches "Application startup complete.". The cause is almost always in the configuration, the memory or the environment.
  2. Serving: the server runs, but requests fail (HTTP errors) or are slow. The cause is in the request, the load or a dead engine.
  3. Output: HTTP 200, but the content is wrong: tool calls as plain text, rejected JSON schemas, changed quality, a plugin without effect.

The second rule: several processes write to one log ({{link concepts/architecture-overview}}). Each line has a prefix, for example (APIServer pid=...) or (EngineCore pid=...). When the engine core fails, the API server only reports that it failed. The real cause is the first traceback in the engine core or worker lines above it.

An everyday comparison. Think of the triage desk of a hospital. The nurse first asks when the problem started and where it hurts, and only then calls the right specialist. The comparison stops at the patient. In vLLM, the "patient" writes its own detailed notes (the tracebacks and log lines). This page tells you which note to read first.

The picture

Read the lane that matches the phase, from top to bottom. The cards are ordered by how often each problem shows up at start-up or in serving (a judgement, not a measurement). Each card has a step below with the code lines.

In the code

Step 1: read the right log line

When the engine core process fails during start-up, it logs the traceback with "EngineCore failed to start." and re-raises ({{cite vllm/v1/engine/core.py:1570-1572}}). A worker process logs "WorkerProc failed to start." ({{cite vllm/v1/executor/multiproc_executor.py:957}}). The API server then raises its own error, which points back to them:

So scroll up from "Engine core initialization failed. See root cause above." to the first traceback of an EngineCore or Worker line. For more detail, set VLLM_LOGGING_LEVEL=DEBUG (default INFO, {{cite vllm/envs.py:860}}). The vLLM docs also suggest CUDA_LAUNCH_BLOCKING=1 for a failing kernel and NCCL_DEBUG=TRACE for NCCL ({{cite docs/usage/troubleshooting.md:33-41}}).

Step 2: start-up runs out of memory

Four errors look alike, but they happen at four different points ({{link concepts/kv-cache-manager}} and {{link concepts/tuning}} explain the memory profile):

Message (start)CauseFix
"Free memory on device ... is less than desired GPU memory utilization"another process uses the GPU; total × gpu_memory_utilization is not free ({{cite vllm/v1/worker/utils.py:761-770}})lower --gpu-memory-utilization, or stop the other process
torch.OutOfMemoryError during the profile runthe dummy forward pass with max_num_batched_tokens tokens does not fit ({{cite vllm/v1/worker/gpu/model_runner.py:1022-1027}})lower --max-num-batched-tokens; TP or quantization for big weights
"No available memory for the cache blocks."weights, activations and the graph estimate use all the requested memory ({{cite vllm/v1/core/kv_cache_planning.py:56-64}})raise --gpu-memory-utilization; lower --max-num-batched-tokens; --enforce-eager
torch.OutOfMemoryError during graph capturethe real graph memory is larger than the estimatelower --gpu-memory-utilization a little, or --enforce-eager

--enforce-eager saves the graph memory: the estimate is 0 and no graph is captured ({{cite vllm/v1/worker/gpu_worker.py:704-708}}, {{cite vllm/v1/worker/gpu_worker.py:983-985}}). It costs speed in every step ({{link concepts/compile-and-cuda-graphs}}).

After a successful start, the worker logs the measured parts and a suggested fixed KV size. The text names the flag --kv-cache-memory=N, but the flag is {{term kv-cache-memory-bytes | --kv-cache-memory-bytes}} ({{cite vllm/v1/worker/gpu_worker.py:1046-1053}}, {{cite vllm/engine/arg_utils.py:1384-1386}}). The vLLM docs use the short name too ({{cite docs/configuration/optimization.md:24}}). The short name also works on the command line (derived, not run with vLLM). Python's argparse accepts an unambiguous prefix of a long option, and no vLLM parser sets allow_abbrev=False. FlexibleArgumentParser does not change the prefix matching ({{cite vllm/utils/argparse_utils.py:313-502}}). --kv-cache-memory-bytes is the only flag that starts with --kv-cache-memory.

Step 3: max_model_len is too large

Two different errors stop the start-up:

  1. Larger than the model allows. "User-specified max_model_len (N) is greater than the derived max_model_len (...)" when --max-model-len exceeds the model config. VLLM_ALLOW_LONG_MAX_MODEL_LEN=1 turns this into a warning, with a caution about NaN outputs for RoPE models ({{cite vllm/config/model.py:2656-2683}}).
  2. Larger than the KV cache can hold. The message starts "To serve at least one request with the model's max seq len (N), (X GiB KV cache is needed ...". It ends with "... the estimated maximum model length is M." ({{cite vllm/v1/core/kv_cache_planning.py:68-87}}).

For the second error: set --max-model-len M, or --max-model-len auto, which fits the length to the memory and logs "Auto-fit max_model_len: reduced from ..." ({{cite vllm/v1/core/kv_cache_planning.py:1584-1587}}, {{cite vllm/v1/core/kv_cache_planning.py:1401-1410}}). The other fixes are more KV memory (Step 2) or --kv-cache-dtype fp8 ({{link concepts/tuning}}). The playground on {{link concepts/tuning}} computes the same estimate.

Step 4: start-up is slow

After the model loads, the engine core profiles, compiles and captures graphs. Then it logs "init engine (profile, create kv cache, warmup model) took X s (compilation: Y s)" ({{cite vllm/v1/engine/core.py:394-400}}). A cold start compiles with torch.compile; a warm start loads the saved result and logs "Directly load AOT compilation from path ..." ({{cite vllm/compilation/decorators.py:326-330}}). The cache lives under VLLM_CACHE_ROOT ({{cite vllm/envs.py:713-718}}; {{link tours/serve-startup}}).

  • Keep the cache on a persistent disk (in a container, a volume). The docs have a section on this for Docker ({{cite docs/deployment/docker.md:32}}).
  • A change of max_num_batched_tokens, max_num_seqs or most environment variables gives a new cache key, so the next start compiles again ({{cite vllm/config/scheduler.py:271-284}}).
  • For fast restarts during development, use -O0 or --enforce-eager (no compile, no graphs) ({{cite vllm/config/vllm.py:1745-1747}}).

Step 5: "EngineCore failed to start." and the start-up timeouts

Besides memory and length errors, three causes are common:

  • A general plugin raises. The engine core runs every general plugin function, and their errors are not caught ({{cite vllm/plugins/__init__.py:87-90}}). A plugin that fails to import is only logged ("Failed to load plugin", {{cite vllm/plugins/__init__.py:68-72}}). See {{link concepts/plugin-loading}}.
  • A bad environment value. At the end of its __init__, the engine core reads every VLLM_* variable once to cache them ({{cite vllm/v1/engine/core.py:241-243}}, {{cite vllm/envs.py:2324-2326}}). A value that does not parse, for example VLLM_XLA_CHECK_RECOMPILATION=yes ({{cite vllm/envs.py:1086-1088}}), raises there, even when no code uses that variable. With TP > 1, each worker process does the same earlier and logs "WorkerProc failed to start." ({{cite vllm/v1/executor/multiproc_executor.py:708-710}}). A variable that the API server reads when it imports a module fails earlier, in the API server: for example VLLM_ENGINE_READY_TIMEOUT_S ({{cite vllm/v1/engine/core_client.py:29}}).
  • A wrong flag combination that only the engine core checks, for example an attention backend that the GPU does not support ({{link concepts/attention-backend-selection}}).

Timeouts at start-up depend on the shape:

  • With one API server, the front end waits for the engine with no time limit ({{link concepts/engine-client}}).
  • With more than one API server, the API servers start before the engines and wait VLLM_ENGINE_READY_TIMEOUT_S (default 600 s) ({{cite vllm/envs.py:812-814}}, {{cite vllm/v1/engine/core_client.py:755-768}}). The message says that slow weight loading is a common cause; raise the value for large models.
  • The engine core waits at most 5 minutes for the init message of the front end ({{cite vllm/v1/engine/core.py:113}}, {{cite vllm/v1/engine/core.py:1408-1413}}).

Step 6: the engine dies while serving

An error in the loop of the engine core makes it log "EngineCore encountered a fatal error.". Then it sends a dead message to the front end and exits ({{cite vllm/v1/engine/core.py:1573-1576}}). The front end then raises EngineDeadError ({{cite vllm/v1/engine/core_client.py:581-584}}). The result is {{term engine-death}}:

  • Requests get HTTP 500 with the message "The server had an error while processing your request." ({{cite vllm/v1/engine/exceptions.py:12-22}}, {{cite vllm/entrypoints/serve/exception_handling/error_response.py:68-72}}).
  • GET /health answers 503 ({{cite vllm/entrypoints/serve/instrumentator/health.py:29-33}}).
  • A watchdog checks every 5 s and stops the API server, unless VLLM_KEEP_ALIVE_ON_ENGINE_DEATH=1 (default 0) ({{cite vllm/entrypoints/launchers/launcher.py:314-337}}, {{cite vllm/envs.py:1107-1109}}). Let your orchestrator restart the container.

With worker processes, each execute_model call waits at most VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS (default 300) for the workers ({{cite vllm/envs.py:1859-1863}}, {{cite vllm/v1/executor/multiproc_executor.py:350}}). Then it raises TimeoutError("RPC call to execute_model timed out.") ({{cite vllm/v1/executor/multiproc_executor.py:443}}). This is an error in the engine core loop, so the engine dies as above (derived; with fault tolerance off, the default). The comment in envs.py says "only applies when TP > 1"; the code applies it to every multiprocessing executor, also with PP or DP. A hang inside a collective (NCCL) usually shows up as this timeout (Step 10).

Step 7: HTTP 400 and 404

The error body names the cause and often the field ({{link learn/openai-api}}). It has the form {"error": {"message": "...", "type": "BadRequestError", "param": "...", "code": 400}}. The common ones:

Status and messageCauseWhere
400 "This model's maximum context length is N tokens. However, your prompt contains M input tokens ..."the prompt is longer than max_model_len{{cite vllm/renderers/params.py:518-538}}
400 "Stream options can only be defined when `stream=True`."stream_options without stream{{cite vllm/entrypoints/openai/chat_completion/protocol.py:847-855}}
400 "tool_choice=... requires --tool-call-parser to be set"tools without the parser flags (Step 9){{link concepts/tool-and-reasoning-parsers}}
400 "Structured output processing only supports one backend per engine."Step 9{{cite vllm/v1/structured_output/__init__.py:143-150}}

A max_tokens larger than the rest of the context is not an error: the server lowers it to max_model_len − prompt length ({{cite vllm/entrypoints/serve/utils/api_utils.py:253-270}}). For a 404, check GET /v1/models: the served name is --served-model-name, else the model path ({{cite vllm/config/model.py:2330-2334}}).

Step 8: slow serving: preemption and prefix-cache misses

Preemption. When running requests need more blocks than are free, the scheduler preempts one and recomputes it later ({{link concepts/scheduler}}). The scheduler writes no log line per preemption. The signs are the counter vllm:num_preemptions_total and "Preemptions: N" in the periodic log line ({{cite vllm/v1/metrics/loggers.py:738-745}}, {{cite vllm/v1/metrics/loggers.py:310-312}}). Watch the {{term preemption-rate}}: rate(vllm:num_preemptions_total[5m]). The vLLM docs still show a V0-style warning line for preemption ({{cite docs/configuration/optimization.md:33-35}}); the current code does not print it. Fix: more KV memory, or fewer running requests ({{link concepts/tuning}}).

A low prefix-cache hit rate. The cache hits only when the hash chain of full blocks matches ({{link concepts/prefix-caching}}). Hits break when:

  • the shared prefix is shorter than one block, or the difference starts inside the first block: only full blocks hit ({{cite vllm/v1/core/kv_cache_manager.py:264-266}});
  • requests use different LoRA adapters, multimodal inputs or cache_salt values, which are part of the block hash ({{cite vllm/v1/core/kv_cache_utils.py:655-665}});
  • a request asks for prompt_logprobs: it skips reading the cache ({{cite vllm/sampling_params.py:625-632}});
  • the chat template puts a changing value (a date, an id) near the start of the prompt (general knowledge about templates);
  • you use a non-cryptographic hash (xxhash) without PYTHONHASHSEED. Then the hash seed is random per process, and tools that compare hashes across instances find no match ({{cite vllm/v1/core/kv_cache_utils.py:117-130}}).

Also note that requests that come back after a preemption are not in the exported prefix counters ({{link concepts/metrics-and-observability}}).

Step 9: wrong output with HTTP 200

  • Tool calls arrive as plain text in content. The server needs both --enable-auto-tool-choice and --tool-call-parser NAME. The first alone stops the start-up with TypeError ({{cite vllm/entrypoints/common/cli_args.py:523-525}}); the second alone gives no parser ({{cite vllm/parser/parser_manager.py:34-35}}). The parser must match the model's output format ({{link concepts/tool-and-reasoning-parsers}}).
  • Structured output requests fail after other ones worked. The API server picks a backend per request, but the engine core keeps the first backend it built and rejects others ({{cite vllm/v1/structured_output/__init__.py:143-150}}). Set one backend with --structured-outputs-config.backend ({{link concepts/structured-outputs}}).
  • The output quality changed. By default, the server takes default sampling parameters from the model's generation_config.json; --generation-config vllm uses vLLM's own defaults ({{cite vllm/config/model.py:358-364}}). The vLLM docs describe this change ({{cite docs/usage/troubleshooting.md:25-31}}).
  • A plugin does not load. When VLLM_PLUGINS is set, only the named plugins load; an empty value loads none ({{cite vllm/envs.py:1161-1167}}, {{cite vllm/plugins/__init__.py:63-66}}). General plugins log at DEBUG level only, so set VLLM_LOGGING_LEVEL=DEBUG to see "Available plugins for group ..." ({{cite vllm/plugins/__init__.py:48-54}}). Logits-processor plugins ignore VLLM_PLUGINS ({{link concepts/plugin-loading}}).
  • A custom op switch has no effect. custom_ops entries use the registered op name, for example +rms_norm. A name that matches no op of the model only logs a WARNING "... has no effect" ({{cite vllm/config/compilation.py:1343-1361}}). Also, at the default -O2 with Inductor, vLLM disables most custom ops on purpose ({{link concepts/custom-ops}}).

Step 10: multi-node and NCCL hangs

The vLLM docs have the details; this page points to them:

  • Check GPU-to-GPU communication across the nodes first, and set network variables such as NCCL_SOCKET_IFNAME on all nodes ({{cite docs/serving/distributed_troubleshooting.md:5-7}}).
  • With several IP addresses per node, set VLLM_HOST_IP per node ({{cite docs/serving/distributed_troubleshooting.md:9-11}}).
  • A test script with NCCL_DEBUG=TRACE shows whether the hardware and drivers work ({{cite docs/usage/troubleshooting.md:83-175}}).
  • vLLM sets a few variables itself when it is imported: PYTORCH_NVML_BASED_CUDA_CHECK=1 and TORCHINDUCTOR_COMPILE_THREADS=1 ({{cite vllm/env_override.py:164-168}}). It sets NCCL_GRAPH_REGISTER=0 only when sleep mode offloads CUDA graphs ({{cite vllm/config/vllm.py:2309-2316}}). Older versions set NCCL_CUMEM_ENABLE=0; the current code does not ({{cite docs/usage/troubleshooting.md:375}}).
  • Traffic between nodes is not encrypted; keep the nodes on an isolated network ({{cite docs/usage/security.md:3-10}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

The per-token values are the same as in the Llama-3.1-8B example on {{link concepts/tuning}}; the memory values are made up (illustrative). Assume a 24 GiB GPU with gpu_memory_utilization 0.92. The profile finds 15 GiB weights, 1 GiB other memory, a 2.5 GiB activation peak and a 0.5 GiB graph estimate. The KV cache needs 128 KiB per token, and max_model_len is 131,072 from the model config.

  1. Requested: ceil(24 × 0.92) = 22.08 GiB. Available: 22.08 − 16.0 − 2.5 − 0.5 = 3.08 GiB ({{cite vllm/v1/worker/gpu_worker.py:744-748}}).
  2. One block (16 tokens) is 2 MiB, so there are 1,576 blocks ({{cite vllm/v1/core/kv_cache_planning.py:1610-1611}}).
  3. The check keeps one block back: 3.08 GiB − 2 MiB. One request of 131,072 tokens needs 8,192 blocks = 16 GiB, which does not fit ({{cite vllm/v1/core/kv_cache_planning.py:1572-1582}}).
  4. The error estimates the largest length that fits: 1,575 blocks × 16 = 25,200 tokens ({{cite vllm/v1/core/kv_cache_planning.py:1288-1334}}).
  5. Fixes, each with its effect:
    • --max-model-len 25200 or auto: the server starts with a maximum concurrency of 1.0x.
    • --max-model-len 8192: 1,576 / 512 = 3.08x.
    • --kv-cache-dtype fp8: a block is 1 MiB, so 3,153 blocks fit and the estimate becomes 50,432 tokens.
    • A quantized checkpoint frees weight memory.

What can go wrong

Troubleshooting itself has traps:

  • Reading the last error instead of the first. The API server's "Engine core initialization failed" is a consequence; the cause is above it (Step 1).
  • Copying the suggested --kv-cache-memory=N to another machine. The value is valid only for the same GPU with the same free memory (Step 2).
  • Trusting old docs for preemption. The V0 warning line in the docs does not exist in the current code (Step 8).
  • Raising VLLM_ENGINE_READY_TIMEOUT_S with one API server. It has no effect there (Step 5).
  • Setting VLLM_KEEP_ALIVE_ON_ENGINE_DEATH=1 in production. The server stays up but answers 500 to every request; the orchestrator does not restart it unless it checks /health (Step 6).

Why it matters. Most vLLM problems leave a precise message in the right process log. Know the phase, the process and the line of code that wrote the message. Then a fix usually takes minutes instead of hours.

The log ends with "Engine core initialization failed. See root cause above." Where is the cause?

In the first traceback of an EngineCore or worker line above it. The engine core logs "EngineCore failed to start." with the traceback and re-raises ({{cite vllm/v1/engine/core.py:1570-1572}}); the API server only reports that the process exited ({{cite vllm/v1/engine/utils.py:1468-1477}}).

 A client gets HTTP 404 "The model ... does not exist". What do you check?

Compare the model field of the request with GET /v1/models. It must be a served name (--served-model-name, else the model path) or a loaded LoRA name ({{cite vllm/entrypoints/serve/engine/serving.py:75-84}}, {{cite vllm/config/model.py:2330-2334}}).

 After an hour of traffic, every request gets HTTP 500 and the server exits a few seconds later. What happened, and what keeps it from exiting?

The engine core died ({{term engine-death}}): the front end raises EngineDeadError, requests get 500, and the watchdog stops the server within about 5 s ({{cite vllm/entrypoints/serve/exception_handling/error_response.py:68-72}}, {{cite vllm/entrypoints/launchers/launcher.py:314-337}}). VLLM_KEEP_ALIVE_ON_ENGINE_DEATH=1 keeps it up, but the engine stays dead; read the engine core traceback instead.

 Prefix caching is on, every request has the same 10-token system prompt, and the hit rate is 0 %. Why?

Only full blocks can hit, and a block has 16 tokens by default ({{cite vllm/v1/core/kv_cache_manager.py:264-266}}, {{cite vllm/config/cache.py:182}}). A shared prefix of 10 tokens never fills a block, so no block hash matches.

 On a 24 GiB GPU, start-up says "the estimated maximum model length is 25200". You set --max-model-len 25200. How many full-length requests fit at once, and how could you get about twice as many?

One: the usable blocks (1,575) cover exactly 25,200 tokens, and the log shows a maximum concurrency of about 1.0x ({{cite vllm/v1/core/kv_cache_utils.py:1031-1047}}; deep dive). --kv-cache-dtype fp8 halves the bytes per token ({{cite vllm/v1/kv_cache_interface.py:571-575}}), so about twice as many tokens fit; check the output quality after the change.
