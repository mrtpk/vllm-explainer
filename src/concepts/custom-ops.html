It picks one method when it is built - forward_native when disabled, the platform's method when enabled. Plugins replace whole classes with register_oot, and vllm.ir adds a second, per-op provider choice. --- A CustomOp picks one forward method when vLLM builds it: forward_native when the op is disabled, else the method of the current platform.

The idea

Some layers, such as RMSNorm, rotary embedding or the SiLU-and-multiply activation, have a fast kernel on each kind of hardware and a plain PyTorch version. vLLM writes such a layer as a {{term custom-op}}: an nn.Module subclass with methods forward_cuda, forward_hip, forward_cpu, forward_xpu, forward_tpu, forward_oot and {{term forward-native}}. When the model builds the layer, the layer picks one method and keeps it.

The choice has two inputs. The first is a switch: is the op enabled? The list compilation_config.custom_ops decides. With torch.compile and Inductor, which is the default of vllm serve, ops are disabled by default. Then forward_native runs. For most ops this is plain PyTorch code, and Inductor generates fused kernels for it. The second input is the {{term platform}}: an enabled op calls the method for current_platform.

An {{term out-of-tree}} package can replace an op class with its own subclass through {{term register-oot}}. vLLM then builds the replacement wherever model code builds the in-tree class. A {{term pluggable-layer}} works the same way for a whole layer, such as a linear layer, but has no per-platform methods.

An everyday comparison. Think of a power tool with exchangeable heads. At assembly, the factory fits the head for the local power grid, or a manual hand crank when the "motor" switch is off. A vendor can ship a whole replacement tool with the same model name. The comparison stops here: the head is fixed at assembly. Changing the switch later does not change a tool that is already built.

The picture

Read the panels as one call of the constructor. The decision happens once, in __init__. Each call of forward() then calls the bound method directly.

Step 3: the dispatch decision

  1. Line 183. The op is enabled when enforce_enable=True was passed, or when enabled() says so.
  2. Lines 184-187. The op name goes into a counter of enabled or disabled ops. vLLM logs these counters at DEBUG level after it builds the model ({{cite vllm/config/compilation.py:1325-1330}}).
  3. Lines 189-192. Disabled: forward_native. maybe_compile wraps it in torch.compile only when the layer asked for compile_native=True (line 218).
  4. Lines 194-205. Enabled: one method per platform. The order matters: ROCm, CPU, TPU, XPU, then any out-of-tree platform, else CUDA.

The design doc gives forward_native as the "final fallback for all platforms" ({{cite docs/design/custom_op.md:21}}). In the code, the final else is forward_cuda (lines 204-205). forward_native is only the default body of four platform methods (Step 2).

So an out-of-tree platform reaches forward_oot only for an enabled op. is_out_of_tree() is true for a platform with _enum = PlatformEnum.OOT ({{cite vllm/platforms/interface.py:218-219}}, {{link concepts/platform-interface}}).

Step 4: enabled() and the custom_ops list

  1. Lines 273-280. A class without a name (not registered) logs a WARNING once and follows the base mode.
  2. Lines 282-283. The switches are the strings "+" + name and "-" + name.
  3. Line 290. The result is (base mode on, or +name) and not -name.
  4. Lines 300-307. The list must hold exactly one of "all" and "none", else ValueError.

The user does not normally write the base mode. VllmConfig.__post_init__ adds it:

For vllm serve at the default level O2, the compilation mode is VLLM_COMPILE ({{cite vllm/config/vllm.py:1806-1810}}). The backend is the platform's simple_compile_backend, "inductor" by default ({{cite vllm/config/compilation.py:1080-1081}}, {{cite vllm/platforms/interface.py:172}}). So the base mode is "none". An op is then disabled unless one of three things turns it on:

  • a +name entry in the list (line 290);
  • enforce_enable=True from the layer's constructor (line 183). The vision encoders of some multimodal models build ApplyRotaryEmb this way ({{cite vllm/model_executor/models/qwen2_5_vl.py:404}});
  • a class that overrides enabled(). MMEncoderAttention.enabled() always returns true ({{cite vllm/model_executor/layers/attention/mm_encoder_attention.py:507-509}}).

With --enforce-eager, the mode is NONE ({{cite vllm/config/vllm.py:1745-1746}}), so the base mode is "all". Two more cases set the mode to NONE before line 1819: TORCH_COMPILE_DISABLE=1 ({{cite vllm/config/vllm.py:1765-1770}}) and breakable CUDA graphs ({{cite vllm/config/vllm.py:849-851}}). vLLM turns on breakable CUDA graphs by default for a list of architectures, for example DeepseekV4ForCausalLM ({{cite vllm/config/vllm.py:75-108}}, {{cite vllm/config/vllm.py:825-833}}). So these models get the base mode "all" by default. LlamaForCausalLM is not in the list.

Some code adds switches for you. A model with block-quantized weights gets +quant_fp8 ({{cite vllm/config/vllm.py:1799-1802}}). If you turn on one of three RoPE fusion passes in the compilation config, vLLM adds +rotary_embedding ({{cite vllm/config/compilation.py:964-984}}). A platform can change the list in its config hooks. ROCm adds some switches, for example +sparse_attn_indexer ({{cite vllm/platforms/rocm.py:1111-1112}}); the CUDA platform adds none (from git grep). The test platform replaces the list with ["all"] ({{cite tests/plugins/vllm_add_dummy_platform/vllm_add_dummy_platform/dummy_platform.py:21-23}}).

To change the list yourself, use the compilation config flag ({{cite vllm/engine/arg_utils.py:1881}}):

vllm serve Qwen/Qwen3-0.6B --compilation-config '{"custom_ops": ["none", "+rms_norm"]}'

The design doc shows one string with commas, '["all,-op1"]' ({{cite docs/design/custom_op.md:46-47}}). The parser keeps the JSON list as it is ({{cite vllm/utils/argparse_utils.py:476-478}}). So the list has one entry, "all,-op1", and CompilationConfig stops start-up with "Invalid syntax" ({{cite vllm/config/compilation.py:1013-1019}}). Write '["all", "-op1"]'.

Step 6: PluggableLayer, and the second CustomOp registry

PluggableLayer uses the same op_registry and op_registry_oot, and the same __new__ swap ({{cite vllm/model_executor/custom_op.py:46-65}}). Its docstring says that it has no per-platform forward_* methods; it allows the replacement of the whole layer, with its own sub-modules ({{cite vllm/model_executor/custom_op.py:33-44}}). The linear layers use it, for example column_parallel_linear ({{cite vllm/model_executor/layers/linear.py:434-435}}). LoRA code finds the replacement class with maybe_get_oot_by_class, so that it still wraps a swapped layer ({{cite vllm/model_executor/custom_op.py:25-29}}, {{cite vllm/lora/layers/column_parallel_linear.py:169}}).

vllm/model_executor/hw_agnostic/custom_op.py is a second copy of the module with its own op_registry and op_registry_oot ({{cite vllm/model_executor/hw_agnostic/custom_op.py:16-22}}). Its dispatch has only two methods: an enabled op uses forward_oot on an out-of-tree platform; all other cases use forward_native ({{cite vllm/model_executor/hw_agnostic/custom_op.py:163-170}}). Only two layers use it: RMSNorm and SiluAndMul in hw_agnostic/layers/. Only the Transformers modeling backend picks them, and only with VLLM_USE_HW_AGNOSTIC set to 1 or true ({{cite vllm/model_executor/models/transformers/layers.py:23-38}}, {{cite vllm/model_executor/models/transformers/layers.py:46-56}}, {{cite vllm/envs.py:1218-1220}}). An OOT class registered with the main CustomOp.register_oot does not replace these classes, because the registries are separate (derived).

Step 7: vllm.ir, a second level of selection

The package vllm/ir defines {{term ir-op | IR ops}}: a function with a native PyTorch body, registered with @register_op. At this commit there are three: rms_norm, fused_add_rms_norm and gelu_and_mul_sparse ({{cite vllm/ir/ops/__init__.py:2-6}}). Each {{term kernel-provider}} adds an implementation with register_impl, for example vllm_c:

A priority list per op selects the provider at call time:

  1. Lines 327-335. No priority set: WARNING once, and the native body runs.
  2. Lines 337-344. Walk the list. The first provider whose supports_args accepts the arguments wins. The ValueError for an unsupported provider is only a guard: when vLLM installs a list, it removes the providers that the platform does not support ({{cite vllm/ir/op.py:387-391}}).
  3. Lines 356-359. No provider accepts: RuntimeError. When vLLM installs a list, it adds native at the end if no provider supports all arguments ({{cite vllm/ir/op.py:395-406}}).

The lists live in IrOpPriorityConfig, one field per op ({{cite vllm/config/kernel.py:20-38}}); the flag is --ir-op-priority ({{cite vllm/engine/arg_utils.py:1827}}). The platform adds its defaults after any user list ({{cite vllm/config/kernel.py:458-475}}). On CUDA the default for rms_norm and fused_add_rms_norm is ["native"] with Inductor compilation, else ["vllm_c", "native"] ({{cite vllm/platforms/cuda.py:716-732}}). gelu_and_mul_sparse always gets ["triton", "native"] (line 733). Each worker installs the lists once at start-up ({{cite vllm/v1/worker/worker_base.py:96-101}}).

The two systems stack. RMSNorm is a CustomOp, and its forward_native calls the IR op ({{cite vllm/model_executor/layers/layernorm.py:79-99}}). Its forward_cuda calls forward_native unless batch invariance is on ({{cite vllm/model_executor/layers/layernorm.py:101-120}}). So for RMSNorm on CUDA, the IR priority, not the CustomOp switch, picks the kernel.

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Default vllm serve of a Llama model on an NVIDIA GPU (O2).

  1. Mode VLLM_COMPILE, backend inductor: custom_ops = ["none"] (vllm.py lines 1819-1824).
  2. The model builds RMSNorm in the worker. enabled() finds no +rms_norm and returns false. The op is disabled: _forward_method = forward_native, not compiled alone (compile_native is false).
  3. forward_native calls ir.ops.rms_norm, or ir.ops.fused_add_rms_norm when the layer gets a residual. The CUDA priority is ["native"] (cuda.py line 720). With ir_enable_torch_wrap on ({{cite vllm/config/vllm.py:1813-1817}}), the call goes through the torch op vllm_ir.rms_norm, and the model-level torch.compile sees it.
  4. The field docstring says what follows: "Inductor generates (fused) Triton kernels for disabled custom ops" ({{cite vllm/config/compilation.py:489-492}}).

The same server with --enforce-eager.

  1. Mode NONE: custom_ops = ["all"]. RMSNorm is enabled: _forward_method = forward_cuda.
  2. forward_cuda calls forward_native (no batch invariance), which calls ir.ops.rms_norm (or fused_add_rms_norm).
  3. The priority is ["vllm_c", "native"]. For a BF16 input with BF16 weight and no variance size, vllm_c accepts the arguments, and the C++ kernel runs ({{cite vllm/kernels/vllm_c.py:17-25}}).

(Derived by reading the lines cited on this page in order.)
  • A current config. dispatch_forward and enabled() read get_cached_compilation_config(), which needs a config set with set_current_vllm_config ({{cite vllm/config/vllm.py:3570-3586}}). initialize_model sets it around the model constructor ({{cite vllm/model_executor/model_loader/utils.py:100-101}}). A CustomOp built when no config is set, for example at module import time, raises AssertionError "Current vLLM config is not set".
  • The process. The model is built in each worker (with TP = 1, in the engine core process). So register_oot must run in the worker before the model is built. A general plugin does this; the worker loads them in init_worker ({{link concepts/plugin-loading}}).
  • After the build. When the context ends, custom_op_log_check logs the enabled and disabled ops and warns about a +name or -name that matched no op of the model ({{cite vllm/config/vllm.py:3544-3545}}, {{cite vllm/config/compilation.py:1333-1361}}).

register_oot sets op_cls.name to the key (line 339), and the key is the in-tree class name by default. enabled() builds the switch from cls.name (line 282). So for the test class DummyRotaryEmbedding, the switch is +RotaryEmbedding, not +rotary_embedding, the name that the in-tree base class registered ({{cite vllm/model_executor/layers/rotary_embedding/base.py:14-15}}). (Derived from lines 282 and 337-339; no test covers it.)

The test platform turns on all ops with custom_ops = ["all"]. Then the name does not matter. Your platform can keep the default "none" base mode. Then your forward_oot does not run for a disabled op, because a disabled op uses forward_native (line 189).

Some layers call an op inside an opaque torch custom op (for example fused MoE), where the model-level torch.compile cannot see it. For them, compile_native=True compiles forward_native alone ({{cite vllm/model_executor/custom_op.py:207-266}}):

  1. No compile when enable is false, the mode is NONE, or the backend is "eager" (lines 218-228).
  2. The backend is current_platform.simple_compile_backend (line 233).
  3. With dynamic_arg_dims from register, vLLM compiles with dynamic=False and marks the listed dimensions as dynamic at each call (lines 235-258). A negative index counts from the end (line 254).
  4. Else it compiles with dynamic=True "to avoid recompilations" (lines 260-266).

What can go wrong

Under the default base mode "none" of compiled serving, an op without a +name uses forward_native, unless its layer uses enforce_enable=True or overrides enabled() ({{cite vllm/model_executor/custom_op.py:183}}, {{cite vllm/model_executor/custom_op.py:189-192}}). An out-of-tree platform must turn its ops on, for example in check_and_update_config.
  • The docs form of register_oot. register_oot("Name") raises TypeError (Step 5).
  • The registration runs too late. __new__ reads op_registry_oot when the layer is built. A class registered after the model build has no effect on existing layers (derived from lines 117-126).
  • Two plugins replace the same op. The second register_oot fails the assert at line 338 and stops the plugin function.
  • A switch with the wrong name. +RMSNorm instead of +rms_norm matches nothing; the only sign is the WARNING of custom_op_log_check.

Why it matters. CustomOp and IR ops decide which kernel runs for the small layers of every model. A hardware plugin uses them to bring its own kernels without a change to the model files.

When does a CustomOp choose its forward method?

Once, in __init__, through dispatch_forward; forward() then calls the stored method ({{cite vllm/model_executor/custom_op.py:128-134}}).

 With default vllm serve on CUDA, is RMSNorm enabled? Why?

No. The mode is VLLM_COMPILE and the backend is Inductor, so vLLM adds the base mode "none" ({{cite vllm/config/vllm.py:1819-1826}}). The CUDA platform adds no +rms_norm, and RMSNorm does not use enforce_enable. So enabled() returns false ({{cite vllm/model_executor/custom_op.py:290}}), and the op uses forward_native.

 Why does @CustomOp.register_oot("MMEncoderAttention") fail, and what works instead?

The string lands in the positional parameter _decorated_op_cls. It is neither None nor a class, so the method raises TypeError ({{cite vllm/model_executor/custom_op.py:343-356}}). Use @MMEncoderAttention.register_oot or @CustomOp.register_oot(name="MMEncoderAttention").

 With --enforce-eager on CUDA, which code computes RMSNorm for a BF16 input, and which two settings decide it?

The vllm_c provider of the IR op rms_norm (or fused_add_rms_norm with a residual). First, the base mode is "all", so the CustomOp is enabled and uses forward_cuda, which calls forward_native and the IR op ({{cite vllm/model_executor/layers/layernorm.py:101-120}}). Second, the CUDA IR priority without Inductor is ["vllm_c", "native"] ({{cite vllm/platforms/cuda.py:716-720}}), and vllm_c accepts these arguments ({{cite vllm/kernels/vllm_c.py:17-25}}).
