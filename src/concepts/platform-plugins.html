Five built-in detectors and the out-of-tree detectors from vllm.platform_plugins decide its class; one out-of-tree platform wins over the built-in ones. --- Each vLLM process makes one Platform object on first use. Built-in and out-of-tree detectors decide its class, and an out-of-tree platform wins.

The idea

vLLM runs on NVIDIA and AMD GPUs, on CPUs, on Intel XPUs and on other hardware. Much of its code must ask: which device do I run on, which attention backend can I use, which communicator do I use for collectives? vLLM puts all these answers into one object, the {{term platform}}. Code reads it as current_platform. Its class is a subclass of Platform, for example CudaPlatform.

vLLM must choose the class before it can use it. A {{term platform-detector}} is a small function that checks for one kind of hardware. It returns the dotted name of a Platform subclass when the hardware is there, and None when it is not. vLLM has five built-in detectors. A hardware vendor adds a sixth one as a {{term plugin}} in the group vllm.platform_plugins. When exactly one {{term out-of-tree}} detector answers, it wins over the built-in ones.

The choice happens late, on the first read of current_platform, not when Python imports vllm.platforms. The reason: an out-of-tree platform must import the Platform base class from vLLM before vLLM chooses a platform. Each process of vllm serve makes this choice again, because each process has its own Python objects.

An everyday comparison. Think of a universal remote control. The first time that you press a button, it tests which television is in the room. Then it uses the codes for that television for as long as it runs. A vendor can add a code card for a new television, and a code card always wins over the built-in codes. The comparison stops here. If two code cards answer, vLLM stops with an error. And each process of vLLM is a separate remote control that tests the room again.

In the code

Step 1: current_platform is made on first use

vllm/platforms/__init__.py has no variable named current_platform. It has a module-level __getattr__ function. Since Python 3.7 (PEP 562), Python calls such a function when code reads a name that the module does not have:

  1. Line 296. _current_platform starts as None in each process.
  2. Lines 299-300. The name exists only for type checkers. At run time it is not a module attribute, so the import from vllm.platforms import current_platform calls __getattr__.
  3. Line 318. The detection returns a dotted class name, for example "vllm.platforms.cuda.CudaPlatform".
  4. Line 319. resolve_obj_by_qualname imports the module and gets the class ({{cite vllm/utils/import_utils.py:119-123}}). The () makes the one object.
  5. Lines 320-321. _init_trace keeps the stack of the first read. A test prints it when a platform resolves too early ({{cite tests/plugins_tests/test_platform_plugins.py:28-34}}).

The comment gives the reason for the late choice. An out-of-tree platform needs from vllm.platforms import Platform to define its subclass. If the import of vllm.platforms chose the platform, the plugin could not load first. A test checks that import vllm alone does not resolve the platform ({{cite tests/plugins_tests/test_platform_plugins.py:37-48}}).

Step 2: resolve_current_platform_cls_qualname, part 1

The first part handles the CPU target and runs every detector:

  1. Lines 244-248. If VLLM_TARGET_DEVICE is cpu, the function returns the CPU class at once. It does not load the plugin group and does not run any other detector. The comment says why: CPU-only test jobs run on hosts with accelerators. The default value is cuda ({{cite vllm/envs.py:622}}).
  2. Line 250. load_plugins_by_group imports the detectors of vllm.platform_plugins. VLLM_PLUGINS filters them, as for the other groups ({{cite vllm/plugins/__init__.py:63-64}}).
  3. Line 254. The loop runs the five built-in detectors first, then the out-of-tree ones.
  4. Lines 257-259. A detector is active when it returns a name, not None.
  5. Lines 260-265. An exception in a detector is logged at DEBUG level, and the detector counts as not active.

Step 3: resolve_current_platform_cls_qualname, part 2

  1. Lines 267-270. The active names are split into built-in and out-of-tree. The split uses sets, so the order of the names in the error text can vary.
  2. Lines 272-276. Two or more active out-of-tree detectors: RuntimeError.
  3. Lines 277-279. Exactly one: vLLM calls the detector again to get the name, and logs "Platform plugin ... is activated" at INFO level. The built-in detectors do not matter here.
  4. Lines 280-284. No out-of-tree detector and two or more built-in ones: RuntimeError.
  5. Lines 285-289. Exactly one built-in detector: it is called again, with a DEBUG log.
  6. Lines 290-292. No active detector: UnspecifiedPlatform, with a DEBUG log only.

{{term unspecified-platform}} has device_type = "" ({{cite vllm/platforms/interface.py:1493-1495}}). Most methods of the base class raise NotImplementedError or return a default, so start-up fails later with a less clear error.

Step 5: the platform comes before the general plugins

In every process of vllm serve, the platform resolves before the first general plugin runs. A module-level from vllm.platforms import current_platform in the import chain triggers __getattr__ early, for example in vllm/engine/arg_utils.py ({{cite vllm/engine/arg_utils.py:122}}) and in vllm/config/compilation.py ({{cite vllm/config/compilation.py:22}}). The page {{link concepts/plugin-loading#deep-dive}} traces the chain for the front end, the engine core and the workers. So a general plugin cannot change which platform vLLM detects. A platform package that needs general setup publishes a second entry point (Step 6).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

For one process, the first read of current_platform does this ({{cite vllm/platforms/__init__.py:240-322}}):

  1. If _current_platform is not None, return it. Stop.
  2. If envs.VLLM_TARGET_DEVICE == "cpu" (the value is lower-cased, {{cite vllm/envs.py:622}}), run cpu_platform_plugin(). It must return a name (an assert). Go to step 8.
  3. Load vllm.platform_plugins through load_plugins_by_group: filter by VLLM_PLUGINS, import each object, log and skip an import error ({{cite vllm/plugins/__init__.py:36-74}}).
  4. For each built-in name, then each plugin name: assert that the object is callable, and call it. Mark it active if the result is not None. Catch any exception, log it at DEBUG level and go on.
  5. Count the active out-of-tree names. Two or more: raise RuntimeError. One: call it again and use the result.
  6. Else count the active built-in names. Two or more: raise RuntimeError. One: call it again and use the result.
  7. Else use "vllm.platforms.interface.UnspecifiedPlatform".
  8. Import the class from the dotted name, call it with no arguments, keep the object in _current_platform, and save the stack in _init_trace.

Worked example. A host has 8 NVIDIA GPUs and the packages acme_hw (a made-up platform plugin) and vLLM. VLLM_PLUGINS is not set. Step 4 calls six detectors: tpu (None, no libtpu), cuda (active, NVML counts 8), rocm (None), xpu (None), cpu (None), acme_hw (active). Step 5 finds one out-of-tree name, calls acme_hw a second time and logs "Platform plugin acme_hw is activated". The CUDA answer is ignored. With VLLM_PLUGINS=acme_admin, step 3 filters out acme_hw, and the process uses CudaPlatform with no warning.
  • Every detector runs, even when an out-of-tree platform wins. The loop calls all of them before the decision (line 254). So the CUDA detector calls NVML on a host where your plugin wins. A detector must be cheap and must not start a device context.
  • The winner runs twice. Line 278 (out-of-tree) or line 286 (built-in) calls the winning detector again, outside the try block. A detector must return the same answer each time, and an exception in the second call is not caught.
  • Detectors can have side effects. The XPU detector sets XPUPlatform.dist_backend = "xccl" when XCCL is available, even when XPU is not the result ({{cite vllm/platforms/__init__.py:149-154}}).
  • The CUDA detector raises some errors. It raises again any exception whose class name does not contain "nvml" ({{cite vllm/platforms/__init__.py:85-89}}). The loop catches it (line 260), so CUDA is then "not active" with only a DEBUG log. One such error: the vLLM package metadata is missing, so vllm_version_matches_substr raises PackageNotFoundError after a warning ({{cite vllm/platforms/__init__.py:18-30}}).
  • Jetson. When NVML fails with an NVML error, the CUDA detector checks two Tegra files and still answers CUDA on a Jetson ({{cite vllm/platforms/__init__.py:91-101}}).
  • Only cpu is a short-circuit. VLLM_TARGET_DEVICE=rocm does not skip detection: the function checks only for "cpu" (line 244).

_current_platform is a module global, so each Python process has its own ({{cite vllm/platforms/__init__.py:296}}). With the spawn start method that vllm serve uses, each child runs the detection again ({{cite vllm/entrypoints/common/startup.py:147-149}}). A child inherits the environment variables of its parent, so it normally gets the same answer. (Derived.)

The module also defines a function named __setattr__ ({{cite vllm/platforms/__init__.py:329-336}}). Python does not call a module-level __setattr__: PEP 562 adds only __getattr__ and __dir__ for modules. So vllm.platforms.current_platform = x makes a normal module attribute. Later reads find that attribute and do not call __getattr__. _current_platform keeps the old object, and modules that imported the old object keep it. vLLM does such an assignment once: for vllm bench, when the platform is UnspecifiedPlatform ({{cite vllm/entrypoints/cli/main.py:80-83}}). (Derived from Python semantics; the code has no comment about it.)

The methods of Platform are mostly class methods. An attribute that the class does not have goes to Platform.__getattr__, which forwards to torch.<device_type> ({{cite vllm/platforms/interface.py:1300-1319}}). The page {{link concepts/platform-interface}} explains this fallback.

What can go wrong

If you set VLLM_PLUGINS and do not list your platform plugin, vLLM does not load it. It then uses a built-in platform or UnspecifiedPlatform, and it gives no warning ({{cite vllm/plugins/__init__.py:63-64}}, {{cite vllm/platforms/__init__.py:285-292}}).
  • Two platform plugins are installed. If both detectors answer, start-up stops with "Only one platform plugin can be activated" ({{cite vllm/platforms/__init__.py:272-276}}). Uninstall one, or make its detector return None.
  • Your detector raises. vLLM logs it only at DEBUG level and uses another platform ({{cite vllm/platforms/__init__.py:260-265}}). Run with VLLM_LOGGING_LEVEL=DEBUG to see the traceback.
  • The platform resolves too early. If code reads current_platform during import vllm, the detection runs the platform plugins against a half-imported vLLM. A test checks this ({{cite tests/plugins_tests/test_platform_plugins.py:37-48}}). Another test prints _init_trace to find the first read ({{cite tests/plugins_tests/test_platform_plugins.py:28-34}}).
  • No platform is found. UnspecifiedPlatform has an empty device_type ({{cite vllm/platforms/interface.py:1493-1495}}). The first device call then fails far from the cause.
  • libtpu without tpu_inference. The TPU detector answers vllm.platforms.tpu.TpuPlatform, but that module defines the name only when tpu_inference imports ({{cite vllm/platforms/tpu.py:9-20}}). The import of the class then fails. (Derived.)

Why it matters. The platform decides the attention backend, the communicator, the worker class and many defaults. A wrong platform gives errors that look like model or kernel bugs. Check the platform first: look for the "activated" line, or log at DEBUG level.

When does vLLM choose the platform of a process?

On the first read of vllm.platforms.current_platform in that process. The module __getattr__ runs the detection when _current_platform is still None ({{cite vllm/platforms/__init__.py:303-319}}).

 Why is the choice lazy, and not made at import vllm.platforms?

An out-of-tree platform plugin needs from vllm.platforms import Platform to define its class. The platform can only be chosen after the plugins load. The comment at {{cite vllm/platforms/__init__.py:306-315}} gives this reason.

 A host has an NVIDIA GPU and two platform plugin packages. Both detectors return a class name. What happens?

Start-up stops with RuntimeError: two or more active out-of-tree detectors are not allowed ({{cite vllm/platforms/__init__.py:272-276}}). The active CUDA detector does not change this, because the out-of-tree count is checked first.

 You set VLLM_TARGET_DEVICE=cpu on a GPU host that has your platform plugin. Is your detector called?

No. The function returns the CPU class before it loads vllm.platform_plugins ({{cite vllm/platforms/__init__.py:244-250}}).

 Your detector opens a device handle each time that it runs, and it is the only active out-of-tree detector. With vllm serve and TP = 2, how many times does it run? Ignore the model registry subprocess.

Eight times. In each process it runs twice: once in the loop (line 257) and once more to get the name (line 278) ({{cite vllm/platforms/__init__.py:254-279}}). Four processes detect: the front end, the engine core and the 2 workers. Each is a spawned process with its own _current_platform ({{cite vllm/entrypoints/common/startup.py:147-149}}). So 2 × 4 = 8 calls. (Derived from the lines above.)
