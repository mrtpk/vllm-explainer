Every step then masks the logits, so only allowed tokens can be sampled.

The idea

Structured outputs force the answer into a format. Examples are valid JSON for a schema, a string that matches a regex, one of a list of choices, or text of a grammar. The method is a token mask. At each step, a grammar state machine says which tokens may come next, and the sampler sees -inf for all others ({{deepinfer concepts/structured-outputs | Structured outputs: token masks}}). This page shows how vLLM splits that work between its processes.

The API server turns the request fields into one constraint and picks a {{term structured-output-backend}} for it. The engine core compiles the constraint into a grammar matcher, in a thread pool, while the request waits. In every step, the engine core fills a {{term grammar-bitmask}} row for each constrained request; the worker applies it to the logits on the GPU. After the step, the engine core feeds the sampled token to the matcher.

An everyday comparison. Think of a form with boxes that accept only digits. Before the clerk starts, someone prints the form (compile). For every character, the form shows which keys still work (the bitmask), and the clerk can press only those. The comparison stops being true in one place: vLLM's clerk may write freely for a while first. While a reasoning model thinks, the mask allows every token; the form starts only after the thinking ends.

In the code

Step 1: the request fields

Three fields lead to a constraint. All end in one StructuredOutputsParams inside SamplingParams:

  • response_format (OpenAI). json_object becomes json_object=True; {{term json-schema-response-format | json_schema}} becomes json=<schema>; structural_tag stays a structural tag. text means no constraint ({{cite vllm/entrypoints/generate/base/protocol.py:181-211}}). A json_schema without the schema gives HTTP 400 ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:827-838}}).
  • structured_outputs (vLLM extra field) with exactly one of json, regex, choice, grammar, json_object, structural_tag ({{cite vllm/sampling_params.py:102-141}}). response_format overrides the matching fields when both are set ({{cite vllm/entrypoints/generate/base/protocol.py:208-211}}).
  • tool_choice "required" or a named function: the tool parser writes a constraint into structured_outputs during rendering ({{link concepts/tool-and-reasoning-parsers}}).

guided_json, guided_regex, guided_choice, guided_grammar and guided_decoding_backend are no longer request fields. A request that still sends them gets HTTP 200 and unconstrained output; the server only logs a warning once ({{cite vllm/entrypoints/serve/engine/protocol.py:21-34}}, {{cite vllm/entrypoints/serve/engine/protocol.py:62-71}}). Use structured_outputs or response_format.

The sampling parameters are made with structured_outputs=self.extract_structured_outputs() for chat and for completions ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:801}}, {{cite vllm/entrypoints/openai/completion/protocol.py:427}}).

Step 2: StructuredOutputsConfig and the backend choice

The backend is set with --structured-outputs-config.backend; the default is auto. A search of vllm/ finds no other assignment to this field; EngineArgs merges only the reasoning parser into this config ({{cite vllm/engine/arg_utils.py:2187-2204}}). The choice happens per request, when InputProcessor validates the sampling parameters inside AsyncLLM.add_request ({{cite vllm/v1/engine/input_processor.py:157-162}}):

  1. Lines 1397-1399: auto tries xgrammar first. If xgrammar accepts the constraint, the request uses xgrammar.
  2. Lines 1405-1425: else outlines, for a non-Tekken Mistral tokenizer or a JSON schema with features that guidance does not support.
  3. Lines 1427-1439: else guidance, if the tokenizer is a fast Hugging Face tokenizer; else HTTP 400.
  4. Line 1441: _backend_was_auto remembers that the choice was automatic.

A Tekken Mistral tokenizer with a Lark grammar goes to guidance directly ({{cite vllm/sampling_params.py:1374-1389}}). A fixed backend (not auto) validates with that backend only and has no fallback ({{cite vllm/sampling_params.py:1336-1373}}).

This check runs in add_request, so it runs when the generator starts. For a non-streaming request that is still before any HTTP byte, so the client gets a plain HTTP 400. For a stream, the HTTP 200 is already out, so the client gets an error chunk ({{link concepts/openai-server}}, Step 6).

Step 3: compile in the engine core, wait in the scheduler

The engine core's input thread turns the EngineCoreRequest into a Request and starts the grammar at once ({{cite vllm/v1/engine/core.py:1128-1135}}). A request with a constraint starts in the status WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR, not WAITING ({{cite vllm/v1/request.py:112-117}}).

  1. Lines 143-150: the engine has one backend. A request with another backend than the one already built gets VLLMValidationError. The input thread finishes the request with a validation error, which the client sees as HTTP 400, or as an error chunk in a stream ({{cite vllm/v1/engine/core.py:1999-2005}}, {{cite vllm/v1/engine/core.py:2158-2167}}).
  2. Lines 157-193: the first constrained request builds the backend.
  3. Lines 196-197: the compile runs in a ThreadPoolExecutor with (CPU count + 1) // 2 workers ({{cite vllm/v1/structured_output/__init__.py:95-96}}); the request keeps a Future. With the external_launcher executor the compile runs at once instead, so that every rank switches state at the same time ({{cite vllm/v1/structured_output/__init__.py:65-74}}).

The scheduler's waiting pass skips the request until the Future is done ({{cite vllm/v1/core/sched/scheduler.py:3291-3303}}). Then the status becomes WAITING, and the request is scheduled like any other. A compile error finishes the request with FINISHED_ERROR and a validation_error, which the front end turns into VLLMValidationError ({{cite vllm/v1/core/sched/scheduler.py:2399-2425}}, {{cite vllm/outputs.py:30-35}}).

The xgrammar backend keeps two compilers with a cache. One is for JSON, regex, choice and EBNF grammars; it never allows special tokens. The other is for structural tags and Lark grammars, which may need special tokens ({{cite vllm/v1/structured_output/backend_xgrammar.py:84-112}}). The cache is limited by VLLM_XGRAMMAR_CACHE_MB, 512 MB by default ({{cite vllm/v1/structured_output/backend_xgrammar.py:215-224}}, {{cite vllm/envs.py:1689}}). So the same schema compiles fast the second time (cache inside xgrammar; library behaviour).

Step 4: the bitmask of each step

In the default engine loop, the engine core schedules a step, starts the forward pass, and then asks for the bitmask while the GPU runs ({{cite vllm/v1/engine/core.py:724-745}}):

Only requests that sample in this step get a row. A chunk of a long prefill that is not the last one gets none (line 2098). grammar_bitmask fills the rows ({{cite vllm/v1/structured_output/__init__.py:382-531}}):

  • The bitmask has max_num_seqs × (1 + num_speculative_tokens) rows, allocated once (lines 397-406). Each structured request owns mask_stride rows: one per draft position plus one for the bonus token (line 395).
  • A request that is still thinking gets a full row of ones: no constraint (lines 241-247 and 466-469).
  • A request in its format gets the matcher's mask for the next token (line 242).
  • Above 128 structured requests and without speculative decoding, up to 8 threads fill the rows in batches of 16 (lines 79-87 and 416-448).

The result goes to the worker as a GrammarOutput with a numpy array ({{cite vllm/v1/structured_output/__init__.py:523-531}}).

Step 5: masking on the worker

Model Runner V2 applies the mask after compute_logits and before the sampler ({{link concepts/model-runner}}):

StructuredOutputsWorker keeps an int32 [max_num_logits, cdiv(vocab_size, 32)] buffer on the GPU ({{cite vllm/v1/worker/gpu/structured_outputs.py:60-68}}). It copies the rows on a side CUDA stream, then a Triton kernel writes -inf into each logit whose bit is 0 ({{cite vllm/v1/worker/gpu/structured_outputs.py:80-124}}, {{cite vllm/v1/worker/gpu/structured_outputs.py:162-171}}). The sampler then sees only allowed tokens.

Step 6: after the step

update_from_output feeds the new tokens to the matcher ({{cite vllm/v1/core/sched/scheduler.py:2279-2290}}):

Tokens before the end of the thinking are not fed. When the end token is among the new tokens, reasoning_ended is latched, and the grammar starts after it (lines 545-552). If the matcher rejects a token, the request finishes with an error; the log says "Unexpected", because the mask should make this impossible ({{cite vllm/v1/core/sched/scheduler.py:2282-2290}}). The matcher is built with the request's stop tokens ({{cite vllm/v1/structured_output/__init__.py:216-223}}, {{cite vllm/v1/structured_output/backend_xgrammar.py:198-203}}). Two parts are library behaviour of xgrammar. At the end of the format, the mask allows a stop token. After the matcher accepts a stop token, it reports is_terminated(). vLLM then stops feeding the matcher, and any later row would be a full row ({{cite vllm/v1/structured_output/backend_xgrammar.py:271-286}}, {{cite vllm/v1/structured_output/__init__.py:241-247}}).

Step 7: async scheduling, speculative decoding and reasoning

  • Async scheduling. The bitmask for step k+1 needs the token of step k, but with async scheduling that token may still be on the GPU. The scheduler sets pending_structured_output_tokens for such a step ({{cite vllm/v1/core/sched/async_scheduler.py:37-39}}). The engine core still starts the forward pass of step k+1. But it calls sample_tokens only after it has processed the output of step k ({{cite vllm/v1/engine/core.py:737-749}}, {{cite vllm/v1/engine/core.py:789-810}}). The flag is for the whole batch. So one structured request in decode delays the sampling of every request in that step (derived from line 37). See {{link concepts/async-scheduling}}.
  • Speculative decoding. Draft tokens are checked against the grammar before they are scheduled; the longest valid prefix stays, and the rest becomes -1 padding ({{cite vllm/v1/core/sched/scheduler.py:2663-2666}}, {{cite vllm/v1/core/sched/scheduler.py:2691-2699}}). The bitmask has one row per draft position; the manager advances the matcher through the drafts to fill the rows and rolls it back afterwards ({{cite vllm/v1/structured_output/__init__.py:476-521}}). The matcher allows a rollback of num_speculative_tokens tokens ({{cite vllm/v1/structured_output/backend_xgrammar.py:198-203}}).
  • Reasoning. With a reasoning parser, the grammar starts only after the thinking ends, unless enable_in_reasoning is set ({{cite vllm/v1/structured_output/__init__.py:300-319}}). The front end tells the engine core whether the prompt already ended the thinking. With reasoning_ended unset, the engine core checks the prompt with its own parser (lines 312-319). Some engine-based parsers end the thinking with a content token, for example a tool-call start. Such a token stays masked during the thinking if the grammar cannot start with it ({{cite vllm/v1/structured_output/__init__.py:258-281}}).

Server: vllm serve Qwen/Qwen2.5-0.5B-Instruct on one GPU, default flags (max_num_seqs from the GPU size, async scheduling on, no reasoning parser). Request (example):

{"messages": [{"role": "user", "content": "Give me a city as JSON."}],
 "response_format": {"type": "json_schema",
   "json_schema": {"name": "city", "schema": {"type": "object",
      "properties": {"name": {"type": "string"}}, "required": ["name"]}}}}
  1. API server. to_sampling_params makes StructuredOutputsParams(json={...schema...}) ({{cite vllm/entrypoints/generate/base/protocol.py:192-195}}). In add_request, the input processor validates with xgrammar; it accepts, so _backend = "xgrammar" and _backend_was_auto = True.
  2. Input thread. Request starts as WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR. This is the first constrained request, so the manager builds XgrammarBackend: two compilers, each with max_threads=8 ({{cite vllm/v1/structured_output/backend_xgrammar.py:215-224}}). The compile job goes to the pool.
  3. Scheduler. While the Future runs, each waiting pass skips the request. When it is done, the request becomes WAITING and is admitted.
  4. Prefill step. The whole prompt fits into one step, so the request is not a partial prefill chunk; it gets bitmask row 0. The matcher allows only tokens that can start a JSON object of the schema; every other token gets -inf.
  5. Size of the mask. The Qwen2.5 vocabulary has 151,936 entries (inferred from its config.json). One row is cdiv(151936, 32) = 4,748 int32 words = 18,992 bytes. With 3 structured requests in a step, the array is int32 [3, 4748], about 57 KB, copied to the GPU once per step.
  6. Decode steps. With async scheduling, the next step is scheduled while the token of this step is in flight, so pending_structured_output_tokens is true. The engine core starts the forward pass and processes the previous output, which feeds the token to the matcher. Only then does it fill the row and sample.
  7. End. After {"name": "Paris"}, the format is complete. The mask then allows a stop token of the request (here <|im_end|>), and the request finishes with finish_reason: "stop" when the model samples it.

The order of tokens and the exact allowed set come from xgrammar (library behaviour); the steps above follow vLLM's calls. Whitespace rules depend on disable_any_whitespace.

What can go wrong

The API server picks a backend per request, but the engine core keeps the first one it built ({{cite vllm/v1/structured_output/__init__.py:143-150}}). If the first constrained request used xgrammar, a later schema that only guidance supports is rejected with a validation error, and the other way around. Set --structured-outputs-config.backend to one backend if your clients send mixed schemas. (Derived from the two code paths.)
  • Unconstrained output with HTTP 200. The request uses guided_json or another removed field (Step 1).
  • JSON appears only after a long thinking text. With a reasoning parser, the grammar starts after the thinking (Step 7). Set enable_in_reasoning or turn the thinking off.
  • The JSON is cut off. max_tokens ended the request before the matcher reached a final state; check finish_reason: "length".
  • Slow first token for new schemas. The request waits for its compile (Step 3). Repeat schemas hit the cache.
  • Lower throughput with async scheduling. One constrained decode request defers the sampling of the whole step (Step 7).

Why it matters. Structured outputs make agent and tool pipelines reliable, but they add a compile wait, a per-step CPU job and, with async scheduling, less overlap. Knowing where each part runs tells you what to tune.

Which field of the OpenAI API asks for JSON that matches a schema, and what does vLLM turn it into?

response_format with type: "json_schema". vLLM turns it into StructuredOutputsParams(json=<schema>) ({{cite vllm/entrypoints/generate/base/protocol.py:192-195}}).

 In which process and on which thread does the grammar compile, and what does the request do meanwhile?

In the engine core process, in the ThreadPoolExecutor of the structured output manager; the input thread submits the job ({{cite vllm/v1/engine/core.py:1128-1135}}, {{cite vllm/v1/structured_output/__init__.py:196-197}}). The request waits in the status WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR, and the scheduler skips it until the Future is done ({{cite vllm/v1/core/sched/scheduler.py:3291-3303}}).

 How large is one bitmask row for a vocabulary of 151,936 tokens? How many rows does a structured request own with 3 speculative tokens?

cdiv(151936, 32) = 4,748 int32 words, 18,992 bytes ({{cite vllm/v1/worker/gpu/structured_outputs.py:63-65}}). With 3 speculative tokens, mask_stride = 3 + 1 = 4 rows per request ({{cite vllm/v1/structured_output/__init__.py:393-395}}).

 The server uses async scheduling. A batch has 200 normal requests and 1 JSON-schema request in decode. What happens to the sampling of that step, and why?

The step is scheduled while the previous token of the JSON request is still in flight, so the scheduler sets pending_structured_output_tokens for the step ({{cite vllm/v1/core/sched/async_scheduler.py:37-39}}). The engine core starts the forward pass but defers sample_tokens for the whole batch. It first processes the previous step's output, then fills the bitmask and samples ({{cite vllm/v1/engine/core.py:737-749}}, {{cite vllm/v1/engine/core.py:789-810}}). The flag is per batch, so all 201 requests wait (derived).

 A reasoning model with --reasoning-parser deepseek_r1 gets a JSON-schema request. Which tokens does the grammar see, and what is the bitmask while the model thinks?

While the thinking is not ended, the constraint bounds start after the thinking, so the rows are full rows: every token is allowed ({{cite vllm/v1/structured_output/__init__.py:300-319}}, {{cite vllm/v1/structured_output/__init__.py:241-247}}). accept_tokens ignores the tokens before the end; when </think> arrives, it latches reasoning_ended and feeds only the tokens after it to the matcher ({{cite vllm/v1/structured_output/__init__.py:545-553}}).
