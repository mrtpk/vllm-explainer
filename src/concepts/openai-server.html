The idea

The page {{link learn/openai-api}} shows the API from the outside: routes, fields and the stream format. This page shows the inside of the {{term api-server}}. The API server is one process (or several) with an asyncio event loop. uvicorn reads HTTP, FastAPI matches the {{term route}}, and a route function calls a {{term serving-class}}. The serving class checks the request, asks the renderer for token ids, makes the sampling parameters and calls {{term async-llm | AsyncLLM}}, the {{term engine-client}} ({{link concepts/engine-client}}).

The server makes one object per serving class at start-up and keeps it in the {{term app-state}}. So a route function is short: it takes the serving object from app.state, calls one method, and turns the result into an HTTP response. The result is an error, a full JSON body, or an async generator of SSE strings.

Some work is the same for every route. {{term middleware | Middleware}} checks CORS and the API key. Exception handlers turn Python exceptions into HTTP status codes. Decorators on the route functions watch for a client disconnect and count the load.

An everyday comparison. Think of the front desk of a large office. A guard at the door checks the visitor's badge (middleware). Signs send the visitor to the right counter (the router). The clerk at the counter checks the form and copies it onto the internal form (renderer and sampling parameters). Then the clerk puts it into the internal mail (AsyncLLM). The comparison stops being true for streams. The clerk promises the answer piece by piece before the mail has left the building. So a stream starts with HTTP 200 before the engine sees the request.

In the code

Step 1: the launch modes of vllm serve

ServeSubcommand.cmd picks one of five ways to start ({{cite vllm/entrypoints/cli/serve.py:54-156}}). The page {{link code/entrypoints-cli-serve}} reads it line by line; the short form is:

  • One API server (the default when the DP size is 1). The CLI process itself runs uvloop.run(run_server(args)) ({{cite vllm/entrypoints/cli/serve.py:153-156}}). run_server binds the socket first and then builds the engine client and the app ({{cite vllm/entrypoints/launchers/api_server/entry.py:164-201}}). The comment gives the reason for the early bind: it avoids a race with Ray ({{cite vllm/entrypoints/launchers/launcher.py:372-379}}).
  • Several API servers. --api-server-count defaults to the DP size with internal load balancing ({{cite vllm/entrypoints/cli/serve.py:113-130}}). Then the CLI process becomes a supervisor. It binds one socket with SO_REUSEPORT, starts the engine cores and spawns ApiServer_i processes ({{cite vllm/entrypoints/cli/serve.py:298}}, {{cite vllm/v1/utils.py:248-254}}). Each process runs the same app with its own AsyncLLM. A process that has more open connections than another one waits up to 5 ms before it accepts a new connection ({{cite vllm/entrypoints/launchers/launcher.py:103-125}}).
  • Headless. --headless sets the count to 0 and starts only engine cores, for multi-node data parallelism ({{cite vllm/entrypoints/cli/serve.py:69-77}}, {{cite vllm/entrypoints/cli/serve.py:181-266}}).
  • gRPC. --grpc starts a gRPC server on --port instead of HTTP. It wraps AsyncLLM with the VllmEngineServicer of the external smg-grpc-servicer package ({{cite vllm/entrypoints/cli/serve.py:59-63}}, {{cite vllm/entrypoints/launchers/grpc_server.py:56-85}}).

The Rust frontend (one paragraph). rust/ holds an experimental OpenAI-compatible frontend in Rust. It talks to the same engine core processes over the same ZMQ boundary ({{cite rust/README.md:1-5}}). With VLLM_USE_RUST_FRONTEND=1, vllm serve takes the multi-server path, forces the API server count to 1, and starts the Rust binary instead of Python API servers ({{cite vllm/entrypoints/cli/serve.py:131-136}}, {{cite vllm/entrypoints/cli/serve.py:346-365}}). The README calls it experimental and not feature-complete, and this site does not explain it further.

Step 2: build_app makes the FastAPI app

After AsyncLLM is ready, build_and_serve asks the engine for the supported tasks, builds the app, fills the app state and starts uvicorn ({{cite vllm/entrypoints/launchers/api_server/entry.py:115-161}}):

  1. Lines 34-41: --disable-fastapi-docs removes /docs, /redoc and the OpenAPI schema; --enable-offline-docs serves the bundled Swagger files.
  2. Line 45: register_api_routers adds the {{term router | routers}} by task and flag ({{cite vllm/entrypoints/launchers/api_server/routers.py:12-90}}). The route table is on {{link learn/openai-api}}.
  3. Line 51: endpoint plugins attach their routes after the core routes, so they can replace one ({{link concepts/frontend-plugins}}).
  4. Line 53: the exception handlers, in four layers ({{cite vllm/entrypoints/serve/exception_handling/register.py:26-42}}).
  5. Line 54: the middleware ({{cite vllm/entrypoints/serve/middleware/register.py:19-75}}):
    • CORSMiddleware, always. --allowed-origins is empty by default, so browsers on other origins are refused ({{cite vllm/entrypoints/common/cli_args.py:318-325}}).
    • AuthenticationMiddleware, only with --api-key or VLLM_API_KEY. It compares SHA-256 hashes in constant time and guards only /v1, /v2, /inference and /cohere paths ({{cite vllm/entrypoints/serve/middleware/authenticate.py:11}}, {{cite vllm/entrypoints/serve/middleware/authenticate.py:28-45}}). All other paths need no key, also /invocations (see "What can go wrong").
    • XRequestIdMiddleware, only with --enable-request-id-headers. It copies the request's X-Request-Id, or a new UUID, into the response header ({{cite vllm/entrypoints/serve/middleware/x_request_id.py:26-36}}).
    • ScalingMiddleware for the generate task (elastic EP), and the classes or functions named by --middleware.
  6. Line 55: the external package model_hosting_container_standards wraps the app for SageMaker hosting ({{cite vllm/entrypoints/serve/sagemaker/api_router.py:145-159}}). The SageMaker routes /ping and /invocations are already registered on every server ({{cite vllm/entrypoints/launchers/api_server/routers.py:40-44}}). /invocations picks a handler by the type of the body and runs the same serving objects as the /v1 routes ({{cite vllm/entrypoints/serve/sagemaker/api_router.py:98-132}}).

serve_http then prints every route and runs uvicorn with NoSignalServer, which leaves SIGINT and SIGTERM to vLLM's own shutdown handler ({{cite vllm/entrypoints/launchers/launcher.py:47-72}}, {{cite vllm/entrypoints/launchers/launcher.py:251-291}}). A watchdog task checks the engine every 5 seconds ({{cite vllm/entrypoints/launchers/launcher.py:314-337}}).

Step 4: the serving class hierarchy

The three layers split the work:

  1. BaseServing knows the model names. _check_model accepts the served name, a loaded LoRA name, or (with VLLM_ALLOW_RUNTIME_LORA_UPDATING) a name that a LoRA resolver can load. Any other name gives HTTP 404 NotFoundError ({{cite vllm/entrypoints/serve/engine/serving.py:49-84}}). create_error_response maps an exception class to a status code ({{cite vllm/entrypoints/serve/exception_handling/error_response.py:14-96}}).
  2. GenerateBaseServing knows the engine. It takes the renderer and the input processor from the engine client ({{cite vllm/entrypoints/generate/base/serving.py:148-151}}). Its _preflight runs the engine checks that must come before a stream starts:
  3. OpenAIServingChat (and its siblings) knows one API format: the fields, the chunks and the full response.

Step 5: the request flow inside one serving call

For /v1/chat/completions, _create_chat_completion runs these steps in order ({{cite vllm/entrypoints/openai/chat_completion/serving.py:302-438}}). /v1/completions has the same shape without the chat template ({{cite vllm/entrypoints/openai/completion/serving.py:131-296}}).

  1. Validate. Pydantic and the model validators of the request class have already run in FastAPI. Errors there give HTTP 400 ({{link learn/openai-api}}, errors deep dive).
  2. Check the model and the engine. _check_model, then _preflight(n) ({{cite vllm/entrypoints/openai/chat_completion/serving.py:278-283}}).
  3. Render. The online renderer applies the chat template and tokenizes; the prompt length check runs here ({{cite vllm/entrypoints/openai/chat_completion/serving.py:285}}). See {{link concepts/renderers-and-chat-templates}}.
  4. Request id. "chatcmpl-" + the X-Request-Id header, else the body field request_id (a random UUID by default) ({{cite vllm/entrypoints/openai/chat_completion/serving.py:320-322}}, {{cite vllm/entrypoints/serve/engine/serving.py:132-142}}).
  5. Sampling parameters. get_max_tokens, then to_sampling_params with output_kind DELTA for a stream and FINAL_ONLY otherwise ({{cite vllm/entrypoints/openai/chat_completion/serving.py:349-369}}).
  6. Make the generator. engine_client.generate(...) with the priority, the DP rank header and the reasoning flags ({{cite vllm/entrypoints/openai/chat_completion/serving.py:396-408}}). This only makes an async generator; the engine sees nothing yet.
  7. Answer. For a stream, return chat_completion_stream_generator; else await chat_completion_full_generator ({{cite vllm/entrypoints/openai/chat_completion/serving.py:415-438}}).

Step 2 and step 6 meet: check_admission runs in _preflight and again inside AsyncLLM.add_request, when the generator starts ({{cite vllm/v1/engine/async_llm.py:551}}, {{cite vllm/v1/engine/async_llm.py:575-578}}). The first check gives a clean HTTP 503 before a stream starts; the second one sees the requests that other tasks added in between.

Step 6: streaming

The route wraps the generator of SSE strings in a StreamingResponse ({{cite vllm/entrypoints/openai/chat_completion/api_router.py:80-85}}). Three details matter in production:

  • Status first. The HTTP status 200 goes out with the first bytes. Later errors become a data: error chunk, and data: [DONE] always ends the stream ({{cite vllm/entrypoints/openai/chat_completion/serving.py:485-508}}).
  • Keep-alive comments. With --sse-keep-alive-interval N (default 0, off), with_sse_keep_alive sends : keep-alive after N idle seconds. Then a proxy does not close the connection during a long queue or prefill ({{cite vllm/entrypoints/serve/utils/sse_keep_alive.py:18-33}}, {{cite vllm/entrypoints/common/cli_args.py:156-162}}).
  • Disconnect means abort. Before the route returns, with_cancellation runs the handler and a disconnect listener as two tasks; the first to finish cancels the other ({{cite vllm/entrypoints/serve/utils/api_utils.py:92-111}}). After the route returns a StreamingResponse, Starlette watches for the disconnect. Either way AsyncLLM.generate() gets the cancel and sends ABORT to the engine core ({{cite vllm/v1/engine/async_llm.py:807-812}}). Tour 1 follows this path in its cancellation deep dive ({{link tours/life-of-a-chat-request}}).

Step 7: non-streaming answers, n > 1, logprobs and usage

Without a stream, the output kind is FINAL_ONLY. The output processor makes no RequestOutput until the request is finished ({{cite vllm/v1/engine/output_processor.py:364-369}}). With n > 1, AsyncLLM sends n child requests, and the parent collects their final outputs. It returns one RequestOutput with all n outputs when the last child finishes ({{cite vllm/v1/engine/parallel_sampling.py:117-128}}). The full generator then reads one result:

It builds one choice per output, with a new parser per choice because parsers keep state ({{cite vllm/entrypoints/openai/chat_completion/serving.py:980-990}}). Logprobs are built only when logprobs is true ({{cite vllm/entrypoints/openai/chat_completion/serving.py:994-1005}}). The usage counts the prompt once and the tokens of all choices ({{cite vllm/entrypoints/openai/chat_completion/serving.py:1147-1163}}). With --enable-prompt-tokens-details, it adds the cached prompt tokens ({{cite vllm/entrypoints/openai/chat_completion/serving.py:1164-1169}}).

Step 8: request ids, priority and admission limits

  • Request id. The X-Request-Id header wins over the body field, with or without --enable-request-id-headers; that flag only echoes the id in the response header (Step 2). The engine adds 8 random characters to make the internal id ({{link concepts/data-contracts}}, deep dive "The three request ids").
  • Priority. The header X-Vllm-Priority overrides the body field priority, if it parses as an integer ({{cite vllm/entrypoints/generate/base/serving.py:42}}, {{cite vllm/entrypoints/generate/base/serving.py:253-265}}). Only the priority scheduling policy uses it ({{link concepts/scheduler}}).
  • Admission limits. --max-num-queued-reqs and --max-num-queued-tokens are off by default ({{cite vllm/config/scheduler.py:92}}, {{cite vllm/config/scheduler.py:105}}). When set, a full queue gives HTTP 503 with QueueOverflowError or MaxQueuedTokensError, so a load balancer can retry elsewhere ({{cite vllm/exceptions.py:162-189}}). The details are on {{link concepts/engine-client}}.
  • DP rank. A router can pin a request to one data-parallel engine with the header X-data-parallel-rank ({{cite vllm/entrypoints/generate/base/serving.py:215-228}}).

Step 9: the other routes

The full route table is on {{link learn/openai-api}}. Some routes have rules that the table does not show:

  • GET /health calls check_health() on the engine client: 200, or 503 after EngineDeadError ({{cite vllm/entrypoints/serve/instrumentator/health.py:22-33}}).
  • GET /load returns server_load_metrics ({{cite vllm/entrypoints/serve/instrumentator/basic.py:30-50}}). The counter changes only with --enable-server-load-tracking (default off), so without the flag it stays 0 ({{cite vllm/entrypoints/serve/utils/api_utils.py:196-197}}, {{cite vllm/entrypoints/launchers/api_server/app_state.py:175-176}}).
  • GET /v1/models lists the base model names and the loaded LoRA adapters ({{cite vllm/entrypoints/openai/models/serving.py:149-151}}).
  • POST /tokenize and /detokenize use the same renderer as the chat route ({{cite vllm/entrypoints/launchers/api_server/app_state.py:122-130}}). GET /tokenizer_info exists only with --enable-tokenizer-info-endpoint ({{cite vllm/entrypoints/serve/tokenize/api_router.py:86-90}}).
  • /start_profile and /stop_profile exist only when a profiler is configured ({{cite vllm/entrypoints/serve/profile/api_router.py:56-65}}).
  • Development routes such as /sleep, /reset_prefix_cache, /collective_rpc and /server_info exist only with VLLM_SERVER_DEV_MODE=1, and the server logs a security warning ({{cite vllm/entrypoints/launchers/api_server/routers.py:46-49}}, {{cite vllm/entrypoints/serve/__init__.py:43-65}}).
  • /metrics is the Prometheus endpoint ({{link concepts/metrics-and-observability}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Start vllm serve Qwen/Qwen2.5-0.5B (one GPU, default flags) and send this request (example, not in the repo):

curl http://localhost:8000/v1/completions -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen2.5-0.5B", "prompt": "The capital of France is",
       "n": 2, "max_tokens": 8, "temperature": 0.8}'
  1. HTTP layers. uvicorn parses the request; CORS passes (no Origin header); there is no API key. FastAPI builds a CompletionRequest and calls create_completion under with_cancellation ({{cite vllm/entrypoints/openai/completion/api_router.py:37-60}}).
  2. Model and engine checks. The name matches the served name. _preflight(2) checks that the engine is alive and calls check_admission(2), which does nothing because no queue limit is set ({{cite vllm/entrypoints/openai/completion/serving.py:107-113}}, {{cite vllm/v1/engine/async_llm.py:352-383}}).
  3. Render. render_cmpl_async sets arrival_time and tokenizes in the thread pool ({{cite vllm/renderers/base.py:1304-1329}}). The prompt has 5 tokens, [785, 6722, 315, 9625, 374], with the Qwen2.5 tokenizer (measured outside the repo; Qwen2.5 adds no BOS token).
  4. Ids and parameters. The request id is cmpl-<uuid>, and the one prompt gets the item id cmpl-<uuid>-0 ({{cite vllm/entrypoints/openai/completion/serving.py:147}}, {{cite vllm/entrypoints/openai/completion/serving.py:183}}). get_max_tokens gives min(max_model_len − 5, 8) = 8 ({{cite vllm/entrypoints/serve/utils/api_utils.py:253-270}}). The output kind is FINAL_ONLY ({{cite vllm/entrypoints/openai/completion/protocol.py:423-425}}).
  5. Generator. generate() makes a generator, and merge_async_iterators wraps it; with one prompt it takes the fast path ({{cite vllm/entrypoints/openai/completion/serving.py:210-223}}, {{cite vllm/utils/async_utils.py:91-103}}). The handler then iterates it at once, because there is no stream ({{cite vllm/entrypoints/openai/completion/serving.py:244-248}}).
  6. Fan-out in AsyncLLM. The internal id becomes cmpl-<uuid>-0-k3m9q2zv (8 random characters). Because n = 2, a ParentRequest makes the children 0_cmpl-…-k3m9q2zv and 1_cmpl-…-k3m9q2zv. With no seed, both share one copy of the parameters with n = 1. check_admission(2) runs again, and both children go to the engine core ({{cite vllm/v1/engine/async_llm.py:538-565}}, {{cite vllm/v1/engine/parallel_sampling.py:69-96}}).
  7. Engine core. The scheduler sees two independent requests with the same 5-token prompt. The prompt is shorter than one block of 16 tokens, and only full blocks can hit the prefix cache, so both compute the prefill ({{cite vllm/v1/core/kv_cache_manager.py:264-266}}). Each request runs 1 prefill step and then decode steps, until 8 tokens or an end token.
  8. Collect. Each child output is held back until it is finished ({{cite vllm/v1/engine/output_processor.py:364-369}}). When child 0 finishes first, the parent stores it and returns nothing. When child 1 finishes, the parent returns both outputs, and the output processor makes one RequestOutput with the external id cmpl-<uuid>-0 ({{cite vllm/v1/engine/parallel_sampling.py:117-128}}, {{cite vllm/v1/engine/output_processor.py:406-420}}).
  9. Build the body. request_output_to_completion_response makes choice 0 and choice 1 in output order. If both stop at max_tokens, the usage is prompt 5 (counted once per prompt), completion 8 + 8 = 16, total 21 ({{cite vllm/entrypoints/openai/completion/serving.py:581-661}}). The response id is cmpl-<uuid>, without -0 ({{cite vllm/entrypoints/openai/completion/serving.py:697-707}}).
  10. Answer. The route returns a JSONResponse with status 200 ({{cite vllm/entrypoints/openai/completion/api_router.py:66-70}}).
{"id": "cmpl-3f9c...", "object": "text_completion", "model": "Qwen/Qwen2.5-0.5B",
 "choices": [{"index": 0, "text": " Paris. It is the largest city", "finish_reason": "length", ...},
             {"index": 1, "text": " Paris, which is known for its", "finish_reason": "length", ...}],
 "usage": {"prompt_tokens": 5, "completion_tokens": 16, "total_tokens": 21, ...},
 "system_fingerprint": "vllm-<version>-<hash8>"}

The texts are illustrative, and "..." stands for fields such as logprobs and stop_reason. The timing of the two children depends on the batch. The 5-token count is measured with the Qwen2.5 tokenizer; it is not in the repo.

The client waits for the slower child: with FINAL_ONLY, no byte goes out before both children finish. If the client disconnects while it waits, with_cancellation cancels the handler task. generate() then aborts the parent and both children, and the route returns an empty response ({{cite vllm/entrypoints/serve/utils/api_utils.py:106-109}}, {{cite vllm/v1/engine/output_processor.py:599-661}}).

The uvicorn settings that build_and_serve passes contain one time limit only: timeout_keep_alive ({{cite vllm/entrypoints/launchers/api_server/entry.py:141-161}}). It closes an idle connection between two requests; it does not limit a running request. A long request is limited by max_tokens and by the client or proxy timeout.

With N API servers, all of the above runs in each ApiServer_i process. Each process has its own AsyncLLM, renderer and serving objects, and its own client index ({{cite vllm/v1/utils.py:230-252}}). Four points change:

  1. A connection lands on the process with the fewest open connections. A worker that is not the least loaded waits up to 5 × 1 ms before it accepts ({{cite vllm/entrypoints/launchers/launcher.py:39-44}}, {{cite vllm/entrypoints/launchers/launcher.py:103-125}}).
  2. Prometheus uses a multiprocess directory, so /metrics of any process shows all of them ({{cite vllm/entrypoints/cli/serve.py:282-283}}).
  3. The admission counters are shared through a RawArray, but only when --max-num-queued-reqs is set ({{cite vllm/v1/utils.py:207-214}}).
  4. Runtime LoRA loading is refused at start-up, because each process would load its own copy ({{cite vllm/entrypoints/cli/serve.py:315-318}}).

The engine core sends each output only to the API server that sent the request ({{link concepts/data-parallel-serving}}).

What can go wrong

The API key guards only paths that start with /v1, /v2, /inference or /cohere ({{cite vllm/entrypoints/serve/middleware/authenticate.py:11}}, {{cite vllm/entrypoints/serve/middleware/authenticate.py:59-61}}). Every other path answers without a key.

Examples are /health, /metrics, /tokenize, the development routes, and the SageMaker routes /ping and /invocations. Every server registers the SageMaker routes ({{cite vllm/entrypoints/launchers/api_server/routers.py:40-44}}). /invocations runs the same serving objects as the /v1 routes, so a client without the key can still generate text ({{cite vllm/entrypoints/serve/sagemaker/api_router.py:98-132}}). Other open routes also run the model: POST /generative_scoring on every generative server ({{cite vllm/entrypoints/generate/api_router.py:52-54}}, {{cite vllm/entrypoints/generate/generative_scoring/api_router.py:30-31}}), and /pooling, /classify, /score and /rerank on a pooling server ({{cite vllm/entrypoints/pooling/pooling/api_router.py:27-28}}, {{cite vllm/entrypoints/pooling/classify/api_router.py:26}}, {{cite vllm/entrypoints/pooling/scoring/api_router.py:37-38}}, {{cite vllm/entrypoints/pooling/scoring/api_router.py:69-70}}). A generative server also registers POST /scale_elastic_ep outside the guarded prefixes ({{cite vllm/entrypoints/launchers/api_server/routers.py:55-66}}); {{link concepts/deployment-recipes}} describes it.

This is a documented limitation: the help text of --api-key says so, and it names /invocations ({{cite vllm/entrypoints/common/cli_args.py:326-336}}). Do not use --api-key as the only protection. Put a proxy or a network rule in front of the server that allows only the routes you need.

Errors after the first byte are data: chunks with an error object, followed by data: [DONE] ({{cite vllm/entrypoints/openai/chat_completion/serving.py:937-943}}). Check every chunk for error.
  • 404 "The model ... does not exist". The model field must be a served name (--served-model-name, else the model path) or a LoRA name ({{cite vllm/entrypoints/serve/engine/serving.py:75-84}}).
  • 401 on /v1 only. This is the expected behaviour of --api-key; the paths outside the guarded prefixes are open (warning above). OPTIONS requests are never checked ({{cite vllm/entrypoints/serve/middleware/authenticate.py:48-54}}).
  • A browser client fails with a CORS error. No origin is allowed by default; set --allowed-origins ({{cite vllm/entrypoints/common/cli_args.py:320-321}}).
  • A proxy closes slow streams. Nothing is sent during a long queue or prefill. Set --sse-keep-alive-interval.
  • 503 under load with queue limits set. This is the intended behaviour of --max-num-queued-reqs; the token limit counts whole prompts and can reject early ({{cite vllm/v1/engine/async_llm.py:337-341}}).
  • The event loop is the bottleneck. Rendering, detokenization and JSON for all requests share one event loop per API server. More API servers split this work (Step 1).
  • /load always shows 0. Turn on --enable-server-load-tracking.

Why it matters. Every request of vllm serve crosses these layers twice. Most serving problems (wrong status codes, early 503s, lost streams behind proxies, an overloaded front end) are visible here before they reach the engine.

Which object does the route function of /v1/chat/completions call, and where does it come from?

app.state.openai_serving_chat, an OpenAIServingChat object ({{cite vllm/entrypoints/openai/chat_completion/api_router.py:35-36}}). init_generate_state makes it at start-up, only when the model supports the generate task ({{cite vllm/entrypoints/generate/api_router.py:149-151}}).

 A client sends "model": "gpt-4" to a server that serves Qwen. Which status does it get, and from which class?

HTTP 404 with NotFoundError, from BaseServing._check_model ({{cite vllm/entrypoints/serve/engine/serving.py:75-84}}), unless VLLM_SKIP_MODEL_NAME_VALIDATION is set or a LoRA resolver loads an adapter with that name.

 A client sends the header X-Request-Id: abc to a server without --enable-request-id-headers. Which id does the chat response carry, and does the response have an X-Request-Id header?

The response id is chatcmpl-abc, because _base_request_id reads the header in every case ({{cite vllm/entrypoints/serve/engine/serving.py:132-142}}, {{cite vllm/entrypoints/openai/chat_completion/serving.py:320-322}}). The response has no X-Request-Id header, because only XRequestIdMiddleware adds it, and only with the flag ({{cite vllm/entrypoints/serve/middleware/register.py:38-41}}).

 A non-streaming completion asks for n = 2. The first child finishes after 3 tokens with EOS; the second after 8 tokens. When does the client get bytes, and what is completion_tokens?

Only after the second child finishes. With FINAL_ONLY each child gives no output before it finishes, and the parent returns nothing until all children are done ({{cite vllm/v1/engine/output_processor.py:364-369}}, {{cite vllm/v1/engine/parallel_sampling.py:117-128}}). completion_tokens is the sum of the token ids of both outputs: 3 + 8 = 11 (the EOS token counts as an output token) ({{cite vllm/entrypoints/openai/completion/serving.py:653}}).

 You start vllm serve M -dp 2 on one node. How many API server processes run, where does vllm serve itself go, and how does a new connection pick a process?

Two API servers, because the count defaults to the DP size with internal load balancing ({{cite vllm/entrypoints/cli/serve.py:124-130}}). The CLI process runs run_multi_api_server and only supervises ({{cite vllm/entrypoints/cli/serve.py:151-152}}, {{cite vllm/entrypoints/cli/serve.py:384-390}}). Both processes share one socket, and each publishes its number of open connections in a shared array. A process accepts when its count is the smallest, or after 5 checks of 1 ms ({{cite vllm/entrypoints/launchers/launcher.py:103-125}}).
