One connector class runs as two objects - a scheduler-side object in the engine core that plans loads and saves, and a worker-side object in each worker that moves the bytes. KVConnectorFactory finds the class by name. --- A KV connector moves KV blocks in and out of vLLM; its scheduler half plans each step and its worker half moves the bytes.

The idea

The KV cache keeps the keys and values of earlier tokens, so decode does not compute them again ({{deepinfer learn/kv-cache | The KV cache}}). Prefix caching reuses these blocks inside one vLLM instance ({{link concepts/prefix-caching}}). A {{term kv-connector}} goes further: it moves blocks to or from something outside the instance. Examples are a second vLLM instance (disaggregated prefill), CPU memory, a local disk or a distributed store.

The work has two parts that run in different processes. The scheduler must know, before it allocates blocks, how many prompt tokens it can load instead of compute. The workers must copy the bytes into or out of the GPU. So one connector class is made twice, with a different {{term connector-role}}. The SCHEDULER object lives in the {{term engine-core}} process. The WORKER object lives in each {{term worker}}. Each step, the scheduler side writes a metadata object; the worker side reads it.

You turn a connector on with --kv-transfer-config, a {{term kv-transfer-config}}. Its field kv_connector names the class. KVConnectorFactory maps names to classes. vLLM registers 17 built-in connectors, and a plugin can register more, or name a module path.

An everyday comparison. Think of a restaurant kitchen with an external store room. Before each round of orders, the head chef checks the store list for the sauces of each order. If they are in the store, she reserves a shelf and writes a pick list. The kitchen porters read the list, bring the items to the shelf, and take finished items back to the store. The comparison stops here. In vLLM the porters (workers) can also carry items layer by layer during cooking, and the chef can postpone an order until its items arrive.

The picture

Follow the numbers. Steps 1-3 run on the CPU in the engine core, before the step goes to the workers. Steps 4-6 run in every worker around the forward pass. Steps 7-9 run in the engine core when the outputs come back, and in the next schedule.

In the code

Step 1: the configuration

  • kv_connector is the registered name or the class name. kv_role is kv_producer, kv_consumer or kv_both; a connector without a role raises ({{cite vllm/config/kv_transfer.py:120-124}}).
  • kv_connector_extra_config is a free dict for the connector, for example cpu_bytes_to_use.
  • kv_load_failure_policy defaults to "fail": a failed load fails the request.
  • engine_id becomes a random UUID when unset ({{cite vllm/config/kv_transfer.py:111-112}}).

The producer and consumer properties decide some scheduler behaviour ({{cite vllm/config/kv_transfer.py:126-136}}). A typical disaggregated setup runs one instance with kv_producer and one with kv_consumer; the page {{link concepts/disaggregated-prefill}} explains it. This command is adapted from the docs ({{cite docs/features/disagg_prefill.md:41}}):

vllm serve Qwen/Qwen3-8B --kv-transfer-config \
  '{"kv_connector":"OffloadingConnector","kv_role":"kv_both","kv_connector_extra_config":{"cpu_bytes_to_use":1000000000}}'

Step 2: the factory finds the class

  1. Lines 106-124. When kv_connector_module_path is set, it wins over the registry. vLLM imports the module and takes the class named kv_connector. A class without the kv_cache_config constructor argument raises.
  2. Lines 125-126. Else the registry: it calls the stored loader, which imports the module only now.
  3. Lines 127-128. An unknown name raises "Unsupported connector type".

A plugin registers a name with register_connector(name, module_path, class_name). A name that exists raises ValueError ({{cite vllm/distributed/kv_transfer/kv_connector/factory.py:30-40}}). The built-in names are registered when the factory module is imported (lines 149-249). The page {{link code/distributed-kv-transfer-kv-connector-factory}} reads the file line by line.

Step 6: async loads, delayed caching and deferred frees

The scheduler integrates the connector in four places:

  1. External prefix hits. The connector sees a block-aligned local hit and returns more tokens. The scheduler counts them as computed ({{cite vllm/v1/core/sched/scheduler.py:1027-1039}}).
  2. Async loads. For an async load, allocate_slots gets delay_cache_blocks=True ({{cite vllm/v1/core/sched/scheduler.py:1327}}). The block hashes are not committed yet, because the bytes are not there ({{cite vllm/v1/core/kv_cache_manager.py:602-605}}). The request goes to WAITING_FOR_REMOTE_KVS and is skipped for this step ({{cite vllm/v1/core/sched/scheduler.py:1384-1411}}).
  3. Completion. When a worker reports finished_recving, the request is marked ready ({{cite vllm/v1/core/sched/scheduler.py:3325-3334}}). The next schedule caches the loaded blocks and moves it back to WAITING ({{cite vllm/v1/core/sched/scheduler.py:3275-3289}}, {{cite vllm/v1/core/sched/scheduler.py:3254-3257}}).
  4. Frees. request_finished can return True (a connector with SupportsHMA gets request_finished_all_groups, {{cite vllm/v1/core/sched/scheduler.py:3145-3157}}): the blocks stay until the worker reports finished_sending ({{cite vllm/v1/core/sched/scheduler.py:2840-2842}}, {{cite vllm/v1/core/sched/scheduler.py:3335-3338}}). Separately, defer_block_free holds freed blocks while an in-flight step may still write them. It is on only with more than one batch in flight and a consumer role ({{cite vllm/v1/core/sched/scheduler.py:187-193}}).

The registry is a class attribute in each process. Three processes read it, for different reasons:

So a connector registered by a plugin must be registered in all three processes. A {{term general-plugin}} does that. kv_connector_module_path needs no registration, because each process imports the module itself.

There is no P2pNcclConnector at this commit (git grep finds no such name in vllm/). The docs say "Now supports 9 types of connectors" and name nine in eight bullets ({{cite docs/features/disagg_prefill.md:20-49}}). LMCacheMPConnector is inside the LMCache bullet. The registry has 17 names.
  • Scheduler → worker. KVConnectorMetadata is an empty abstract class; each connector defines its own ({{cite vllm/distributed/kv_transfer/kv_connector/v1/base.py:155-160}}). It travels inside SchedulerOutput to every worker. The worker binds it before the forward and clears it after ({{cite vllm/distributed/kv_transfer/kv_connector/v1/base.py:249-268}}).
  • Worker → scheduler. Each worker returns a KVConnectorOutput with finished_sending, finished_recving, failed loads, invalid block ids, stats, events and optional worker metadata ({{cite vllm/v1/worker/gpu/kv_connector.py:145-157}}). Worker metadata objects must implement aggregate, because vLLM merges the objects of all workers ({{cite vllm/distributed/kv_transfer/kv_connector/v1/base.py:163-178}}).
  • All workers answer. With a KV connector, the engine core sets up an output aggregator ({{cite vllm/v1/engine/core.py:191-192}}). The multiprocess executor then collects the outputs of all workers, not only of the output rank, and merges them ({{cite vllm/v1/executor/multiproc_executor.py:405-419}}).
  • Request outputs. request_finished may return kv_transfer_params; vLLM puts them into the request output, so a router can pass them to the next instance ({{cite vllm/distributed/kv_transfer/kv_connector/v1/base.py:631-650}}).

A consumer instance with block_size 16 gets a request with a 3,000-token prompt. The local prefix cache has the first 62 full blocks, 992 tokens; only full blocks can hit ({{cite vllm/v1/core/kv_cache_manager.py:264-266}}). The connector can load 1,984 more tokens asynchronously. (The numbers are an example; the steps follow the cited lines.)

  1. The local hit is 992 tokens. 992 mod 16 = 0, so the connector sees all 992 tokens ({{cite vllm/v1/core/sched/scheduler.py:1031-1034}}).
  2. get_num_new_matched_tokens(request, 992) returns (1984, True). There is no partial tail, so all 1,984 tokens are external ({{cite vllm/v1/core/sched/scheduler.py:1083-1084}}). (A local hit that ends inside a block loses its partial block when the remote hit is longer, lines 1064-1075.)
  3. allocate_slots gets 992 local and 1,984 external computed tokens, and delay_cache_blocks=True ({{cite vllm/v1/core/sched/scheduler.py:1320-1337}}). 2,976 tokens fill 186 blocks of 16. update_state_after_alloc tells the connector the block ids.
  4. The request goes to WAITING_FOR_REMOTE_KVS, with num_computed_tokens set already ({{cite vllm/v1/core/sched/scheduler.py:1393-1407}}). It runs no prefill this step.
  5. The workers start the load after their forward. Some steps later a worker reports finished_recving.
  6. The next schedule() caches the loaded blocks and puts the request back to WAITING. The remaining 24 prompt tokens are prefilled as usual.

If the whole prompt was loaded, vLLM sets num_computed_tokens to the prompt length minus one. So one token runs, and the model samples the first output token ({{cite vllm/v1/core/sched/scheduler.py:3271-3272}}).

A multimodal model runs an encoder (for example a vision tower) before the language model. An {{term ec-connector}} moves the encoder outputs between instances, so one instance can run only the encoder. It has its own config, --ec-transfer-config, with ec_connector, ec_role (ec_producer, ec_consumer or ec_both) and ec_connector_module_path ({{cite vllm/config/ec_transfer.py:10-54}}).

The factory is a copy of the KV factory, with one difference: the registry wins, and the module path is only the fallback ({{cite vllm/distributed/ec_transfer/ec_connector/factory.py:58-74}}). Three connectors are built in: ECExampleConnector, ECCPUConnector and ECMooncakeConnector ({{cite vllm/distributed/ec_transfer/ec_connector/factory.py:81-97}}). The scheduler makes the scheduler-side object ({{cite vllm/v1/core/sched/scheduler.py:201-205}}); each worker makes the worker-side object ({{cite vllm/distributed/ec_transfer/ec_transfer_state.py:26-39}}). The base class has start_load_caches, save_caches, has_cache_item, update_state_after_alloc and build_connector_meta as abstract methods ({{cite vllm/distributed/ec_transfer/ec_connector/base.py:164-312}}). The scheduler calls request_finished on it next to the KV connector ({{cite vllm/v1/core/sched/scheduler.py:2829-2832}}).

{{term kv-offloading | KV offloading}} copies blocks to CPU memory or another tier, so a later request with the same prefix can load them. The easy switch is --kv-offloading-size in GiB. VllmConfig then makes or changes the KV transfer config:

The default backend native selects OffloadingConnector, or SimpleCPUOffloadConnector with VLLM_USE_SIMPLE_KV_OFFLOAD=1 (default 0, {{cite vllm/envs.py:2239-2241}}). The size becomes cpu_bytes_to_use. The docstring says that with TP > 1 the size is "the total buffer size summed across all TP ranks" ({{cite vllm/config/cache.py:380-389}}). The native code has its own small plugin point. OffloadingConnector builds an OffloadingSpec through OffloadingSpecFactory ({{cite vllm/distributed/kv_transfer/kv_connector/v1/offloading_connector.py:87-89}}). The spec gives a scheduler-side OffloadingManager and a worker-side OffloadingWorker ({{cite vllm/v1/kv_offload/base.py:724-743}}). Two specs are built in, CPUOffloadingSpec (the default) and TieringOffloadingSpec. An out-of-tree spec is named with spec_name and spec_module_path in kv_connector_extra_config, with an "experimental" warning ({{cite vllm/v1/kv_offload/factory.py:30-69}}).

What can go wrong

register_connector raises ValueError for a name that exists, and the built-in names exist from the import of the factory ({{cite vllm/distributed/kv_transfer/kv_connector/factory.py:33-34}}). A general plugin that raises stops the start-up of that process. Pick a name that vLLM does not use.
  • The front end does not know your connector. The front end reads the class for config checks ({{cite vllm/config/vllm.py:2243}}). If only the engine core and the workers register it, VllmConfig or the metrics loggers fail with "Unsupported connector type". Use a general plugin or kv_connector_module_path.
  • Old constructor. A module-path connector must accept kv_cache_config as the third argument, else ValueError ({{cite vllm/distributed/kv_transfer/kv_connector/factory.py:116-124}}).
  • Hybrid models. A connector without SupportsHMA turns the hybrid KV cache manager off, and the warning says that hybrid SSM models "will fail at startup without it" ({{cite vllm/config/vllm.py:2245-2256}}).
  • Encoder-decoder models. The scheduler asserts "Encoder-decoder models are not currently supported with KV connectors" ({{cite vllm/v1/core/sched/scheduler.py:174-176}}).
  • Backends that refuse a connector. An attention backend can reject a KV connector in its validation; ROCM_ATTN does ({{cite vllm/v1/attention/backends/rocm_attn.py:184-188}}). See {{link concepts/attention-backend-selection}}.
  • Load failures. With the default policy "fail", a failed load fails the request; "recompute" computes the missing blocks instead ({{cite vllm/config/kv_transfer.py:88-91}}, {{cite vllm/v1/core/sched/scheduler.py:184-185}}).

Why it matters. KV connectors are the base of disaggregated prefill and of KV offloading, two of the main ways to scale online serving. Most connector problems are process problems: which process registered the class, and which role runs where.

Which object of a KV connector runs in the engine core, and which runs in the workers?

The SCHEDULER-role object runs in the engine core, made by the scheduler ({{cite vllm/v1/core/sched/scheduler.py:177-181}}). Each worker makes a WORKER-role object ({{cite vllm/distributed/kv_transfer/kv_transfer_state.py:88-92}}).

 What does get_num_new_matched_tokens return, and what does None mean?

A pair: the number of extra tokens that can be loaded, and whether the load is asynchronous. None as the count means that the connector needs more time; the scheduler skips the request this step and asks again ({{cite vllm/distributed/kv_transfer/kv_connector/v1/base.py:529-538}}, {{cite vllm/v1/core/sched/scheduler.py:1043-1048}}).

 You set both kv_connector_module_path and a registry entry for the same name. Which class runs? And for an EC connector?

For KV connectors the module path wins ({{cite vllm/distributed/kv_transfer/kv_connector/factory.py:106-108}}). For EC connectors the registry wins and the module path is the fallback ({{cite vllm/distributed/ec_transfer/ec_connector/factory.py:66-73}}).

 Why does the scheduler pass delay_cache_blocks=True for an async load?

The blocks are allocated, but the bytes arrive later. Committing their hashes now would let another request hit blocks that hold no data. allocate_slots returns before cache_blocks in that case ({{cite vllm/v1/core/kv_cache_manager.py:602-605}}), and the blocks are cached when the load finishes ({{cite vllm/v1/core/sched/scheduler.py:3254-3257}}).

 You start with --kv-offloading-size 8 --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_producer"}'. Which connector and role run?

OffloadingConnector with kv_both. When kv_offloading_size is set and the backend is native, _post_init_kv_transfer_config overwrites kv_connector and sets kv_role = "kv_both" on the existing config ({{cite vllm/config/vllm.py:1149-1167}}). To combine both, use MultiConnector. (Derived from these lines.)
