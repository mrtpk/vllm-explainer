--- title: torch.compile and CUDA graphs in vLLM nav_title: Compile and CUDA graphs level: Advanced prerequisites: learn/pytorch-for-serving, concepts/forward-context, concepts/model-runner related: concepts/model-runner, concepts/forward-context, concepts/attention-backends, concepts/custom-ops, learn/pytorch-for-serving, concepts/tuning, concepts/troubleshooting, tours/serve-startup summary: vLLM compiles the inner model once with torch.compile and its own Inductor backend, splits the graph at the attention ops, caches the result on disk, and captures CUDA graphs at start-up. Each step, Model Runner V2 replays a FULL graph for uniform decode batches, PIECEWISE graphs for other batches up to the largest capture size, and runs eagerly above it. --- vLLM compiles the model once, cuts it at attention, records CUDA graphs at start-up, and picks FULL, PIECEWISE or eager per step.

The idea

A decoder step launches hundreds of small kernels. Two tools cut this cost ({{link learn/pytorch-for-serving}} has the PyTorch basics):

  • {{term torch-compile}} captures the model's Python code as one graph and lets {{term inductor}} fuse the small ops into fewer kernels. vLLM does it once per process, with no guards, and keeps the token count as a dynamic dimension.
  • {{term cuda-graph | CUDA graphs}} record the kernel launches of one batch shape at start-up and replay them later with one call ({{deepinfer concepts/cuda-graphs | CUDA graph capture and replay}}).

Attention is the hard part. Its kernels depend on the batch layout, and some backends cannot run inside a graph for every layout. So vLLM cuts the compiled graph at the attention ops, the {{term splitting-op | splitting ops}}. Each piece between two attention ops gets its own {{term piecewise-cuda-graph}}, and attention runs eagerly between them. For pure decode batches, it also captures a {{term full-cuda-graph}} of the whole forward pass, attention included.

The {{term optimization-level}} sets the defaults. At the default -O2, the {{term compilation-mode}} is VLLM_COMPILE and the CUDA graph mode is FULL_AND_PIECEWISE. Each step, Model Runner V2 looks at the batch and picks FULL, PIECEWISE or NONE (eager).

An everyday comparison. Think of a factory line with fixed robot programs. The engineers write one program per standard product size. They leave a manual station in the middle, for the step that changes with every order. Small standard orders run one complete program with no stop (FULL). Other orders run the programs with a stop at the manual station (PIECEWISE). A giant order runs fully by hand (eager). The comparison stops here: the programs are recorded once at start-up, for a fixed list of sizes. An order is padded up to the next size.

In the code

Step 1: optimization levels and their defaults

The OptimizationLevel enum has four values; O2 is the default ({{cite vllm/config/vllm.py:131-143}}, {{cite vllm/config/vllm.py:434}}). The CLI accepts -O2, -O 2, -O=2 and --optimization-level 2 ({{cite vllm/utils/argparse_utils.py:395-406}}).

LevelCompile mode (if unset)CUDA graph mode (if unset)Fusion passes
-O0NONENONE ({{cite vllm/config/vllm.py:268}})all off
-O1VLLM_COMPILEPIECEWISE ({{cite vllm/config/vllm.py:289}})norm+quant and act+quant when their conditions hold; no all-reduce fusion
-O2 (default)VLLM_COMPILEFULL_AND_PIECEWISE ({{cite vllm/config/vllm.py:310}})as O1, plus all-reduce+RMSNorm and some RoPE/KV-cache fusions when their conditions hold
-O3VLLM_COMPILEFULL_AND_PIECEWISE ({{cite vllm/config/vllm.py:331}})same as O2: "Currently the same as -O2"

The compile mode is not in the level tables. VllmConfig.__post_init__ sets it: above O0, an unset mode becomes VLLM_COMPILE ({{cite vllm/config/vllm.py:1806-1810}}). Then the level's table fills only the fields that are still None, so your own settings win ({{cite vllm/config/vllm.py:1005-1019}}, {{cite vllm/config/vllm.py:1833-1834}}).

  • --enforce-eager sets the compile mode and the CUDA graph mode to NONE ({{cite vllm/config/vllm.py:1745-1747}}).
  • TORCH_COMPILE_DISABLE=1 sets the compile mode to NONE ({{cite vllm/config/vllm.py:1765-1770}}). The CUDA graph mode then loses its piecewise part: FULL_AND_PIECEWISE becomes FULL_DECODE_ONLY ({{cite vllm/config/vllm.py:1111-1129}}).
  • Breakable CUDA graphs set the compile mode to NONE too ({{cite vllm/config/vllm.py:849-852}}). vLLM turns them on by default for 30 architectures, for example DeepseekV4ForCausalLM, unless VLLM_USE_BREAKABLE_CUDAGRAPH is set ({{cite vllm/config/vllm.py:75-107}}, {{cite vllm/config/vllm.py:824-836}}). With VLLM_BATCH_INVARIANT=1, some BF16 models on CUDA also get them ({{cite vllm/config/vllm.py:834-843}}). On ROCm the list is only DeepseekV41ForCausalLM ({{cite vllm/config/vllm.py:111-128}}).

Later checks can lower the CUDA graph mode again. A pooling model gets PIECEWISE instead of FULL graphs; an encoder-decoder model gets FULL_DECODE_ONLY ({{cite vllm/config/vllm.py:1932-1954}}). A KV connector can ask for PIECEWISE ({{cite vllm/config/vllm.py:1957-1980}}). At KV cache init, the attention backends can lower it once more ({{link concepts/attention-backends}}).

Step 2: @support_torch_compile marks what to compile

A model class opts in with the decorator; in Llama it sits on LlamaModel ({{link concepts/model-definition}}). Without explicit dynamic_arg_dims, dimension 0 of every argument annotated as a tensor or IntermediateTensors is dynamic: the token count ({{cite vllm/compilation/decorators.py:214-232}}). The decorator adds TorchCompileWithNoGuardsWrapper as a base class ({{cite vllm/compilation/decorators.py:360-367}}). It skips compilation when the mode is NONE or STOCK_TORCH_COMPILE, when the class is marked with ignore_torch_compile, or when enable_if says no ({{cite vllm/compilation/decorators.py:409-418}}).

The wrapper builds the compiled callable once:

fullgraph=True forbids graph breaks; dynamic=False plus the marked dimensions give one graph with a symbolic token count. Outside STOCK_TORCH_COMPILE all guards are dropped, so Dynamo never traces again after the first call ({{cite vllm/compilation/wrapper.py:65-70}}, {{cite vllm/compilation/wrapper.py:126-146}}). The backend comes from init_backend: a VllmBackend in VLLM_COMPILE mode ({{cite vllm/config/compilation.py:1083-1134}}).

The first call happens in the first forward pass of the worker, the {{term profile-run}} with max_num_batched_tokens dummy tokens ({{cite vllm/v1/worker/gpu/model_runner.py:1022-1027}}). The worker runs it inside its memory profiling, and a comment says that this run "compiles the model" ({{cite vllm/v1/worker/gpu_worker.py:654-655}}, {{cite vllm/v1/worker/gpu_worker.py:681-697}}). So on a start without a cache, the compile time is part of the memory profiling time.

Step 3: VllmBackend hashes and caches

Dynamo calls VllmBackend with the traced graph. First it decides the {{term compile-cache}} folder:

  1. Env factors. Every known vLLM environment variable, minus a list of ignored ones such as VLLM_PORT and VLLM_CACHE_ROOT ({{cite vllm/envs.py:2351-2381}}).
  2. Config hash. VllmConfig.compute_hash(): the vLLM version and the hashes of the model, cache, parallel, scheduler, compilation and other configs, cut to 10 hex digits ({{cite vllm/config/vllm.py:459-501}}, {{cite vllm/config/vllm.py:571-574}}). The scheduler part holds max_num_batched_tokens, because LoRA buffers and Inductor's index width depend on it, and max_num_seqs, because some static per-request buffers depend on it ({{cite vllm/config/scheduler.py:271-284}}).
  3. Code hash. The source of every file that Dynamo traced (lines 1064-1083).
  4. Compiler hash. From the Inductor adaptor ({{cite vllm/compilation/backends.py:159-160}}).

The folder is $VLLM_CACHE_ROOT/torch_compile_cache/<10 hex digits>/rank_<rank>_<dp>/<prefix>, where the prefix is backbone for the main model ({{cite vllm/compilation/backends.py:1103-1107}}, {{cite vllm/compilation/backends.py:804}}). VLLM_CACHE_ROOT defaults to ~/.cache/vllm when XDG_CACHE_HOME is not set ({{cite vllm/envs.py:710-718}}). vLLM computes the hash folder only when compilation_config.cache_dir is empty ({{cite vllm/compilation/backends.py:1086-1098}}). VLLM_DISABLE_COMPILE_CACHE=1 turns the cache off ({{cite vllm/compilation/compiler_interface.py:204-219}}).

On PyTorch 2.10 or newer, vLLM also uses ahead-of-time (AOT) compilation by default: VLLM_USE_AOT_COMPILE is 1 unless the compile cache is off ({{cite vllm/envs.py:378-387}}). The decorator then first tries to load a saved compiled function from torch_compile_cache/torch_aot_compile/<hash>/rank_<rank>_<dp>/model. After a fresh compile it saves one there ({{cite vllm/compilation/decorators.py:556-605}}, {{cite vllm/compilation/decorators.py:731-756}}).

So both folders can exist side by side. On a start without a cache, Dynamo traces the model, and VllmBackend compiles the pieces into its hash folder. Then the decorator saves the AOT file. On the next start, a loaded AOT file skips the Dynamo trace ({{cite vllm/compilation/decorators.py:595-605}}). From the saved graph, VllmBackend runs again and finds its compiled pieces in its own folder ({{cite vllm/compilation/caching.py:351-380}}). With VLLM_USE_MEGA_AOT_ARTIFACT (default on with AOT on PyTorch 2.12 or newer), the AOT file holds the Inductor code too ({{cite vllm/envs.py:390-397}}, {{cite vllm/compilation/caching.py:326-349}}).

Step 4: split_graph cuts at the splitting ops

Without Inductor graph partition (the default at every level, {{cite vllm/config/vllm.py:311}}), the backend splits the FX graph itself:

The default list is the attention ops plus the two KV cache update ops ({{cite vllm/config/compilation.py:1175-1213}}):

  • vllm::unified_attention_with_output, vllm::unified_mla_attention_with_output, the Mamba and linear-attention ops and some model-specific ops: 17 names in _attention_ops ({{cite vllm/config/compilation.py:768-788}});
  • vllm::unified_kv_cache_update and vllm::unified_mla_kv_cache_update, because the string argument "prevents Inductor from reusing piecewise graphs" ({{cite vllm/config/compilation.py:1186-1187}}).

split_graph walks the nodes in order. A splitting op starts a new subgraph, and consecutive splitting ops stay in one subgraph ({{cite vllm/compilation/backends.py:589-617}}). Only the pieces that are not splitting graphs are compiled ({{cite vllm/compilation/backends.py:1235-1239}}). The attention subgraphs stay plain FX code that calls the custom ops, so they run eagerly.

If attention-quant fusion is on (Inductor graph partition off), vLLM must keep attention inside the graph. If you did not set splitting_ops, it sets [], and a mode with piecewise graphs becomes FULL ({{cite vllm/config/compilation.py:1260-1278}}).

Step 5: PiecewiseBackend and CUDAGraphWrapper

PiecewiseCompileInterpreter runs the split graph with fake tensors. For each piece to compile it makes a PiecewiseBackend, wraps it, and puts the wrapper in place of the piece ({{cite vllm/compilation/backends.py:765-795}}). The backend compiles the piece with Inductor once per compile range. The default range list has one range, from 1 to max_num_batched_tokens; all-reduce and RoPE/KV-cache fusions can add an extra endpoint ({{cite vllm/config/vllm.py:2637-2645}}, {{cite vllm/compilation/piecewise_backend.py:244-276}}). At run time it picks the compiled code of the range that holds the token count ({{cite vllm/compilation/piecewise_backend.py:357-379}}).

The wrapper is added only when the CUDA graph mode has a piecewise part and Inductor graph partition is off ({{cite vllm/compilation/backends.py:656-707}}):

The wrapper reads the forward context. It replays only when the run-time mode equals its own mode, PIECEWISE. Then it looks up a graph by the BatchDescriptor: the padded token count and the LoRA flags ({{cite vllm/forward_context.py:29-57}}). A missing entry is captured on the spot, which is allowed only during the capture phase ({{cite vllm/compilation/cuda_graph.py:258-279}}).

Take a BF16 Llama with TP = 1 on CUDA, at O2. The CustomOps are off by default ({{link concepts/custom-ops}}), and the CUDA IR priority of rms_norm starts with native when Inductor compiles ({{cite vllm/platforms/cuda.py:716-731}}). So of these flags only eliminate_noops is on (derived from the table). The pass manager always adds its IR lowering and clean-up passes ({{cite vllm/compilation/passes/pass_manager.py:119-134}}). With TP = 2 on an H100 and FlashInfer installed, fuse_allreduce_rms joins it. vLLM logs the list as "Enabled custom fusions: ..." ({{cite vllm/config/compilation.py:301-320}}).

Step 7: CUDA graph modes and capture sizes

CUDAGraphMode has three run-time modes and two pairs ({{cite vllm/config/compilation.py:53-63}}). A pair has one mode for uniform decode batches and one for mixed batches ({{cite vllm/config/compilation.py:65-69}}):

NONEeagereager
PIECEWISEPIECEWISEPIECEWISE
FULLFULLFULL
FULL_DECODE_ONLYFULLeager
FULL_AND_PIECEWISE (O2)FULLPIECEWISE

The {{term capture-size | capture sizes}} are padded token counts. When you do not set max_cudagraph_capture_size, the maximum is min(max_num_seqs × decode_query_len × 2, 512), or 1024 on data-center Blackwell (compute capability 10.x) ({{cite vllm/config/vllm.py:2440-2449}}). It is also capped at max_num_batched_tokens ({{cite vllm/config/vllm.py:2530-2531}}). The list is 1, 2, 4, then steps of 8 below 256, then steps of 16 ({{cite vllm/config/vllm.py:2557-2570}}). max_num_batched_tokens joins the list if it is below the maximum (lines 2571-2576).

With LoRA on, the runner captures graphs for more than one count of active adapters. By default the counts are 0 and max_loras + 1, so each capture size gets two graphs ({{cite vllm/v1/worker/gpu/lora_utils.py:20-35}}). See {{link concepts/lora-serving}}.

Step 8: Model Runner V2 captures the graphs

The runner makes a ModelCudaGraphManager at KV cache init ({{cite vllm/v1/worker/gpu/model_runner.py:764-772}}). Its _init_candidates turns the mode and the sizes into a list of BatchExecutionDescriptors to capture ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:256-394}}). After warm-up, the worker calls capture_model(), unless --enforce-eager is set ({{cite vllm/v1/worker/gpu_worker.py:983-985}}). The manager captures all PIECEWISE descriptors first, then all FULL ones, the largest size first in each mode ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:447-449}}, {{cite vllm/v1/worker/gpu/cudagraph_utils.py:376-378}}):

  • PIECEWISE. A warm-up run, then a run in the forward context with mode PIECEWISE. Each piece's wrapper records its graph ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:464-479}}).
  • FULL. A warm-up run, fresh inputs, then torch.cuda.graph(...) around the whole forward with the mode NONE inside. The piece wrappers pass through, so the outer graph records everything ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:480-512}}).

The comment gives the order's reason: "PIECEWISE has larger activations so FULL activations should fit in already allocated buffers in the graph pool" ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:444-446}}).

Step 9: the dispatch rule for each step

execute_model calls dispatch_cg_and_sync_dp before it prepares the inputs ({{cite vllm/v1/worker/gpu/model_runner.py:1806-1819}}). It passes the uniform decode token count. This count is set only when every request has the same query length and the batch has no real prefill ({{cite vllm/v1/worker/utils.py:958-976}}, {{cite vllm/v1/worker/gpu/model_runner.py:1335-1372}}). The manager then takes the candidates for this token count and returns the first compatible one, else NONE:

The compatibility test:

  1. FULL decode graph. Its uniform_token_count is decode_query_len: 1 without speculative decoding, 1 + k with k drafts ({{cite vllm/v1/worker/gpu/model_runner.py:442-445}}). The batch must have the same count, and the graph enough request slots.
  2. Varlen decode FULL variant. Only with adaptive verification: a FULL graph for decode batches whose requests have 1 to decode_query_len tokens ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:302-318}}). A batch with a prefill passes max_query_len=None and cannot use it ({{cite vllm/v1/worker/gpu/model_runner.py:1780-1785}}).
  3. PIECEWISE. No request count and no uniform count, so any batch up to its token count fits ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:352-370}}).
  4. Above the largest size. The token count has no candidates, so the result is NONE (line 553).

With DP > 1, the ranks agree on one padded size with a collective ({{cite vllm/v1/worker/gpu/dp_utils.py:278-312}}).

Step 10: breakable CUDA graphs

A {{term breakable-cuda-graph}} gives piecewise graphs without torch.compile. Instead of cutting an FX graph, one capture context runs the whole forward. Each attention op ends the current graph segment, runs eagerly, and a new segment starts ({{cite vllm/compilation/breakable_cudagraph.py:3-20}}). The ops that break are marked with @eager_break_during_capture, for example unified_attention_with_output ({{cite vllm/model_executor/layers/attention/attention.py:767-769}}). The decorator does nothing outside a capture, and nothing during a FULL capture ({{cite vllm/compilation/breakable_cudagraph.py:99-118}}). In MRV2, run_pw_graph uses the BreakableCUDAGraphWrapper instead of the compiled model when this mode is on ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:578-583}}). The environment variable is described as experimental ({{cite vllm/envs.py:776-779}}).

Step 11: the start-up cost, and how to reduce it

Compilation and capture are the slow part of vllm serve start-up. The logs show each part: "Dynamo bytecode transform time" ({{cite vllm/compilation/backends.py:1186-1190}}), "Compiling a graph for compile range ... takes ... s", once per compile range after its last piece ({{cite vllm/compilation/backends.py:415-422}}), and "Graph capturing finished in ... secs, took ... GiB" ({{cite vllm/v1/worker/gpu/model_runner.py:1146-1152}}). The comment there says capture "usually takes 5~20 seconds".

  • Keep the compile cache. The second start with the same config, code and env loads the compiled pieces. Mount ~/.cache/vllm (or VLLM_CACHE_ROOT) as a volume in containers. Changing --max-num-batched-tokens or --max-num-seqs changes the hash.
  • -O0: no compile, no CUDA graphs, fastest start, slowest steps. --enforce-eager has the same effect on compile and graphs.
  • -O1: compile with PIECEWISE graphs only, so no FULL capture.
  • Fewer sizes. Set -cc.max_cudagraph_capture_size or -cc.cudagraph_capture_sizes. Fewer sizes mean shorter capture and less memory, but more padding or eager steps.
  • -cc.cudagraph_mode=FULL_DECODE_ONLY: no piecewise graphs; the docstring suggests it for decode instances in prefill/decode disaggregation ({{cite vllm/config/compilation.py:628-631}}).

The default splitting ops cut Llama at the KV cache write and the attention of each layer. The order inside Attention.forward is: reshape q/k/v, the cache update op, then the attention op ({{cite vllm/model_executor/layers/attention/attention.py:535-540}}, {{cite vllm/model_executor/layers/attention/attention.py:561-580}}). No other op sits between the two op calls, so Dynamo records them as neighbours in the FX graph. split_graph keeps consecutive splitting ops in one subgraph ({{cite vllm/compilation/backends.py:605-613}}). So each layer gives one eager attention subgraph, and N layers give N + 1 compiled pieces: 33 for the 32 layers of Llama-3-8B (derived). To see the real split, open computation_graph.py in the cache folder ({{cite vllm/compilation/backends.py:1292-1306}}).

Each compiled piece covers the end of one layer and the start of the next. It holds o_proj, the MLP, the norms, the next QKV projection and RoPE. Inductor can fuse inside a piece, but never across an attention op.

What can go wrong

  • Slow first start, fast second start. This is the compile cache at work. If every start is slow, something in the hash changes: a different --max-num-batched-tokens, another environment variable, or a lost cache volume.
  • Large steps run eagerly. Batches above the largest capture size get no CUDA graph (Step 9). This is normal for long prefill chunks, where launch overhead is small.
  • A mode quietly lowered. A backend, a pooling model, an encoder-decoder model or a KV connector can change FULL_AND_PIECEWISE with only a log line (Step 1, {{link concepts/attention-backends}}).
  • A model without a compiled part. If the model has no compiled submodule and breakable graphs are off, piecewise capture is not possible. At KV cache init the runner then lowers the mode to its non-piecewise form, with a warning ({{cite vllm/config/compilation.py:1467-1480}}). The capture code checks the same condition and raises "piecewise CUDA graphs ... unavailable" ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:633-641}}).
  • FULL with a weak backend. -cc.cudagraph_mode=FULL with a NEVER backend stops start-up with ValueError ({{cite vllm/config/compilation.py:1394-1410}}).
  • Docs that do not match. docs/design/torch_compile.md shows a cache folder torch_compile_cache/1517964802/rank_0_0 ({{cite docs/design/torch_compile.md:15}}); the code uses 10 hex digits and adds the prefix folder. docs/design/cuda_graphs.md describes the dispatcher of Model Runner V1 ({{cite docs/design/cuda_graphs.md:98-118}}); Model Runner V2 uses CudaGraphManager.dispatch.

Why it matters. These settings decide both the start-up time and the speed of every decode step. For a latency-sensitive deployment, keep O2, keep the compile cache on disk, and check in the log that FULL decode graphs survived start-up. For fast restarts during development, use -O0 or --enforce-eager.

What are the default compile mode and CUDA graph mode of vllm serve?

VLLM_COMPILE and FULL_AND_PIECEWISE: the default level is O2 ({{cite vllm/config/vllm.py:434}}), an unset mode above O0 becomes VLLM_COMPILE ({{cite vllm/config/vllm.py:1806-1808}}), and O2 sets FULL_AND_PIECEWISE ({{cite vllm/config/vllm.py:310}}). Exceptions: --enforce-eager, TORCH_COMPILE_DISABLE=1 and breakable-graph architectures.

 Which ops are splitting ops by default, and why is the KV cache write one of them?

The 17 attention-like ops in _attention_ops, plus unified_kv_cache_update and unified_mla_kv_cache_update when Inductor graph partition is off ({{cite vllm/config/compilation.py:1184-1213}}). The update op takes a string argument that "prevents Inductor from reusing piecewise graphs" ({{cite vllm/config/compilation.py:1186-1187}}).

 On one H100 with max_num_seqs = 1024, what is the largest capture size, and what happens to a 600-token batch?

512: min(1024 × 1 × 2, 512) ({{cite vllm/config/vllm.py:2440-2449}}). A 600-token batch has no candidate descriptor, so dispatch returns NONE and the model runs eagerly ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:547-553}}).

 During a FULL capture, why do the PIECEWISE CUDAGraphWrappers inside the compiled model not record their own graphs?

The capture runs the forward with run-time mode NONE inside torch.cuda.graph ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:496-502}}). A wrapper replays or captures only when the forward context mode equals its own mode, PIECEWISE; otherwise it just calls the piece ({{cite vllm/compilation/cuda_graph.py:245-256}}). So the outer graph records all kernels.

 You change --max-num-batched-tokens from 8192 to 16384. Why does the next start compile again?

The cache folder name hashes the config. The scheduler config hash contains max_num_batched_tokens, because LoRA buffers and Inductor's 32/64-bit index choice depend on it ({{cite vllm/config/scheduler.py:271-280}}, {{cite vllm/compilation/backends.py:1086-1098}}). A new hash gives a new, empty folder.
