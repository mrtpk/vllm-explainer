The uni executor calls one worker in the engine core process; the multiproc executor sends calls to one worker process per GPU through a shared-memory queue. --- The executor starts the workers and runs every engine call on all of them. Each worker owns one GPU and holds the model runner.

The idea

The {{term engine-core}} does not touch a GPU itself. It talks to an {{term executor}}, and the executor talks to the {{term worker | workers}}. A worker owns one GPU: it sets up the device and the process groups, loads its part of the model, and holds the {{term model-runner}}. With tensor parallelism, one model runs on several GPUs, so there are several workers ({{deepinfer learn/parallelism | Parallelism basics}}).

The engine core asks the executor for things like "run this step" or "how much memory is free?". The executor turns each request into a {{term collective-rpc}}: it calls the same worker method on every worker, and collects the results. How it reaches the workers depends on the backend:

  • The {{term uni-executor}} keeps the one worker as an object in the engine core process. A call is a plain Python call. By default, vLLM uses it only when TP = PP = DP = 1.
  • The {{term multiproc-executor}} starts one worker process per GPU on the node. It writes each call once into a shared-memory {{term message-queue}}, and all workers read it.
  • The Ray executor uses the same message queues, but its workers are Ray actors ({{cite vllm/v1/executor/ray_executor_v2.py:239-247}}).

An everyday comparison. Think of a conductor and an orchestra. The conductor (the engine core) gives one sign, and every musician (worker) plays the same bar on their own instrument (GPU). One musician, the first violin, reports when the bar is done. The comparison stops here: the musicians in vLLM also talk to each other during the bar (NCCL collectives), and the conductor never hears that.

Step 1: which backend

distributed_executor_backend has the default None ({{cite vllm/config/parallel.py:290-292}}). ParallelConfig.__post_init__ fills it in:

world_size_across_dp is world_size × data_parallel_size ({{cite vllm/config/parallel.py:626-629}}), and world_size is PP × TP × PCP ({{cite vllm/config/parallel.py:965-969}}). So, when you do not set a backend, "uni" applies only when TP, PP, DP (and the prefill context parallel size) are all 1. With DP = 2 and TP = 1, each engine core gets one worker process (see {{link concepts/architecture-overview}}). Ray replaces "mp" only after three earlier tests ({{cite vllm/config/parallel.py:1063-1078}}). TPU with SPMD picks "uni". CUDA with more than one node (--nnodes) keeps "mp". Too few GPUs on the node raise ValueError. Then Ray is used when the data parallel backend is Ray, or when Ray is installed and a Ray placement group is set or active ({{cite vllm/config/parallel.py:1079-1095}}). Step 2: the executor interface

Every executor implements collective_rpc. The docstring defines it: run a method "on all workers", by name or as a callable that gets the worker as self ({{cite vllm/v1/executor/abstract.py:209-242}}). The base class builds the step calls on top of it:

With non_block=True, the call returns a Future instead of the result. The default loop, step_with_batch_queue, uses this for both calls of a step ({{cite vllm/v1/engine/core.py:727-729}}, {{cite vllm/v1/engine/core.py:743-745}}). In step(), only execute_model uses it ({{cite vllm/v1/engine/core.py:668}}, {{cite vllm/v1/engine/core.py:676}}). Start-up and control calls go the same way. For example, determine_available_memory is collective_rpc("determine_available_memory") ({{cite vllm/v1/executor/abstract.py:156-157}}), and sleep is collective_rpc("sleep", ...) ({{cite vllm/v1/executor/abstract.py:393-403}}).

Step 3: UniProcExecutor, one worker in the same process

The executor wraps the worker in a WorkerWrapperBase, then runs the three start-up steps directly: init_worker, init_device and load_model. A call is run_method on the wrapper, which calls getattr(wrapper, method) ({{cite vllm/v1/serial_utils.py:485-508}}). The wrapper's own methods, such as execute_model, run first; other names go to the worker through __getattr__ ({{cite vllm/v1/worker/worker_base.py:365-366}}):

With non_block=True, the method still runs at once, in the engine core's main thread. Only an AsyncModelRunnerOutput result becomes a future that waits later, in get_output() ({{cite vllm/v1/executor/uniproc_executor.py:32-48}}). So non_block does not make the call faster. It moves the wait for the GPU result to the moment when the engine core pops the step from its batch queue.

Step 4: MultiprocExecutor starts the worker processes

_init_executor does four things in order ({{cite vllm/v1/executor/multiproc_executor.py:119-268}}):

  1. It makes the broadcast queue, with one reader per worker and a chunk size from VLLM_MQ_MAX_CHUNK_BYTES_MB (16 MiB by default):
  2. It starts one process per local rank with WorkerProc.make_worker_process ({{cite vllm/v1/executor/multiproc_executor.py:191-207}}). The process name is VllmWorker-<rank>, and it uses the context of get_mp_context(), normally spawn ({{cite vllm/v1/executor/multiproc_executor.py:723-750}}).
  3. It waits until every worker sends READY through a pipe, with the handle of its reply queue ({{cite vllm/v1/executor/multiproc_executor.py:786-822}}).
  4. It starts the worker monitor (Step 6), connects the reply queues, and computes output_rank ({{cite vllm/v1/executor/multiproc_executor.py:224-268}}).

Step 5: collective_rpc over shared memory

  1. Line 428: the call goes into the broadcast queue once, as (method, args, kwargs, output_rank). The queue pickles it ({{cite vllm/distributed/device_communicators/shm_broadcast.py:925-941}}).
  2. Lines 430-432: with an output_rank, the executor reads only that worker's reply queue.
  3. Lines 444-448: when the worker that replies failed, it sends a FAILURE status, and the executor raises RuntimeError with the error text.
  4. Lines 452-456: the reply is read later, in FutureWrapper.result().

For execute_model and sample_tokens, the output_rank is the first TP worker of the last PP stage ({{cite vllm/v1/executor/multiproc_executor.py:342-366}}, {{cite vllm/v1/executor/multiproc_executor.py:549-563}}). The other workers run the same method but send nothing back. With a KV or EC connector, all workers reply, and an aggregator merges their outputs ({{cite vllm/v1/executor/multiproc_executor.py:405-419}}, {{cite vllm/v1/engine/core.py:191-194}}).

The replies come back in call order, and FutureWrapper uses that. Each future joins a shared deque. When you ask a future for its result, it first reads the replies of all older futures ({{cite vllm/v1/executor/multiproc_executor.py:79-110}}). So the engine core can wait for the sample_tokens future of step N, and the execute_model reply of step N is read on the way.

Step 6: detecting a dead worker

Two threads watch the processes. In the engine core, MultiprocWorkerMonitor waits on the sentinels of all worker processes:

The callback puts EXECUTOR_FAILED into the engine core's input queue, and the busy loop raises ({{link concepts/engine-core-loop}}, Step 10). In each worker, DeathPipeMonitor blocks on a pipe from the parent. When the parent process ends, the pipe returns EOFError, and the worker shuts down its queues ({{cite vllm/v1/executor/multiproc_executor.py:835-859}}). The wait for a call that hangs also ends: execute_model and sample_tokens use the timeout VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS, 300 s by default ({{cite vllm/v1/executor/multiproc_executor.py:350}}, {{cite vllm/envs.py:1861-1863}}). The engine core then gets TimeoutError ({{cite vllm/v1/executor/multiproc_executor.py:440-443}}); the hung worker keeps running.

On CUDA that is vllm.v1.worker.gpu_worker.Worker, when worker_cls is "auto" ({{cite vllm/platforms/cuda.py:330-331}}). The busy loop reads calls forever:

Line 1070: only the output rank (or every worker when output_rank is None) sends a reply. With async scheduling, handle_output passes the result to the WorkerAsyncOutputCopy thread, which waits for the GPU copy and then writes the reply ({{cite vllm/v1/executor/multiproc_executor.py:1000-1002}}, {{cite vllm/v1/executor/multiproc_executor.py:1019-1039}}).

use_v2_model_runner is true by default when Triton is present and no unsupported feature is set ({{cite vllm/config/vllm.py:713-748}}). A multimodal encoder-only instance gets MMEncoderModelRunner (lines 570-573). Step 10: Ray in one paragraph

RayExecutorV2 subclasses MultiprocExecutor. Its docstring says it reuses "the MQ-based control plane and NCCL data plane", with Ray actors as workers ({{cite vllm/v1/executor/ray_executor_v2.py:239-247}}). Each actor runs a RayWorkerProc, a WorkerProc that learns its GPU after Ray places it ({{cite vllm/v1/executor/ray_executor_v2.py:79-100}}). So steps 5, 8 and 9 of this page also hold for Ray, and so does the worker busy loop. Process creation, placement and the monitoring differ: Ray has its own RayWorkerMonitor thread ({{cite vllm/v1/executor/ray_executor_v2.py:487-537}}), and RayWorkerProc.run() calls worker_busy_loop without worker_main ({{cite vllm/v1/executor/ray_executor_v2.py:223-231}}). The inherited supports_async_scheduling() is true, so async scheduling stays on.

What can go wrong

  • "World size (...) is larger than the number of available GPUs". With the mp backend, all workers of one engine must fit on the node ({{cite vllm/config/parallel.py:1067-1078}}).
  • "RPC call to execute_model timed out." A step took more than 300 s, or a worker hangs in a collective. Check the logs of every worker; the hung rank is often not the one that reports ({{cite vllm/v1/executor/multiproc_executor.py:440-443}}).
  • "Worker proc VllmWorker-1 died unexpectedly". Often the kernel OOM killer or a CUDA crash. The engine then fails all requests ({{link concepts/engine-core-loop}}, Step 10).
  • The error message has no stack trace. The reply carries only str(exception) ({{cite vllm/v1/executor/multiproc_executor.py:1007-1008}}). The traceback is in the worker's own log line "WorkerProc hit an exception.".
  • An out-of-tree executor turns off async scheduling. See {{link concepts/async-scheduling}}.

Why it matters. The executor is the boundary between "what to run" and "where it runs". To debug a multi-GPU server, you must know that every worker runs every call, that only one replies, and which thread waits where. To size a server, you must know that TP = 1 and DP = 1 give no worker process at all.

Which executor backend does vllm serve use with one GPU and default flags, and why is there no worker process?

"uni", because world_size is 1 and DP is 1 ({{cite vllm/config/parallel.py:1099-1100}}). UniProcExecutor makes the worker as an object in the engine core process and calls it directly ({{cite vllm/v1/executor/uniproc_executor.py:51-75}}).

 With TP = 4, how many times does the executor write one execute_model call into shared memory, and how many replies does it read?

Once, into rpc_broadcast_mq, which all four workers read ({{cite vllm/v1/executor/multiproc_executor.py:428}}). It reads one reply, from output_rank = world_size - TP × PCP = 0 ({{cite vllm/v1/executor/multiproc_executor.py:549-563}}). With a KV connector, it reads all four and aggregates them ({{cite vllm/v1/executor/multiproc_executor.py:405-419}}).

 The engine core waits only for the sample_tokens future of a step. How does the execute_model reply of the same step get read from the reply queue?

FutureWrapper.result() first drains all older futures in the shared futures_queue, in order ({{cite vllm/v1/executor/multiproc_executor.py:92-100}}). The execute_model future is older, so its reply is read first.

 Async scheduling is on and the executor is mp. Which thread of the worker process waits for the copy of the sampled tokens to the CPU? Why not the main thread?

The WorkerAsyncOutputCopy thread. handle_output puts the result into async_output_queue ({{cite vllm/v1/executor/multiproc_executor.py:1014-1022}}), and that thread calls enqueue_output, which calls get_output() ({{cite vllm/v1/executor/multiproc_executor.py:995-1002}}, {{cite vllm/v1/executor/multiproc_executor.py:1037-1039}}). So the main thread can dequeue and start the next call at once, which keeps the GPU stream full.
