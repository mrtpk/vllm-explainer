--- title: Hooks in the engine core and the workers nav_title: Engine hooks level: Advanced prerequisites: concepts/plugin-map, concepts/executors-and-workers related: concepts/plugin-map, concepts/executors-and-workers, concepts/scheduler, concepts/sampling-and-logits-processors, concepts/weight-loading, concepts/platform-interface, concepts/quantization-plugins summary: Several extension points of the engine core and the workers are config fields or registries, not entry-point groups - scheduler_cls, worker_cls and worker_extension_cls, logits processors, model loaders, sleep-mode backends and KV cache dtypes. This page shows where each one is read and what your class must do. --- The engine core and the workers read class names from config fields and registries. That is how you replace the scheduler, the worker or the loader.

The idea

The {{term engine-core}} process runs the scheduler. Each {{term worker}} owns one GPU, builds the model and runs it ({{link concepts/executors-and-workers}}). These parts have extension points of two kinds:

  • Config hooks. A field of VllmConfig holds a class name, for example --scheduler-cls my_pkg.sched.MyScheduler. The front end parses it, the other processes get it inside the pickled config, and each process imports the class itself. No registration is needed.
  • Registries. A module-level table maps a name to a class, for example --load-format values to model loaders. A {{term general-plugin}} fills it in every process.

One more extension point is an entry-point group: vllm.logits_processors. vLLM loads it in the workers, and in the front end for a request check.

An everyday comparison. Think of a theatre production. The director's script names the actors for the main roles: the scheduler, the worker, an extra helper. Every theatre that plays the script hires these actors itself. The prop room has labelled shelves (registries) that a stage manager fills before the show. The comparison stops here: in vLLM each process is its own theatre, and a shelf filled in one process is empty in the next.

In the code

Step 1: scheduler_cls

The field takes a class or a dotted name ({{cite vllm/config/scheduler.py:175-180}}). The engine core resolves it after the KV cache plan ({{cite vllm/v1/engine/core.py:160-164}}):

  1. Lines 232-239. Not set: AsyncScheduler when async scheduling is on, else Scheduler. VllmConfig turns async scheduling on when no option conflicts with it ({{cite vllm/config/vllm.py:1664-1698}}).
  2. Lines 243-253. A class object, or a string that does not start with vllm., logs a WARNING once. It says that the interface "is not public", and that a subclass of Scheduler instead of AsyncScheduler turns async scheduling off.
  3. Lines 254-256. A class object is used as it is; a string is split at the last dot ({{cite vllm/utils/import_utils.py:119-123}}). From the CLI the value is always a string, so write pkg.module.Class, not pkg.module:Class.

The test passes a class object, because it builds the engine in the same process:

With vllm serve, the engine core is a separate process, so pass a dotted name that the engine core can import.

Step 2: worker_cls and worker_extension_cls

Both are strings in ParallelConfig; worker_cls defaults to "auto", which the platform replaces ({{cite vllm/config/parallel.py:306-312}}, {{cite vllm/platforms/cuda.py:330-331}}). The worker wrapper resolves both in init_worker:

  1. Lines 293-302. worker_cls must be a string. A class object raises ValueError "passing worker_cls is no longer supported".
  2. Lines 310-321. Each attribute of the extension must be new, except names that start with __. An assert stops start-up when the worker class has it already. Callable attributes are listed as "extended collective_rpc calls".
  3. Lines 323-325. The extension becomes an extra base class of the worker class. The worker object made at line 347 has its methods.

The wrapper also calls an optional hook init_worker_extension(worker) after init_device ({{cite vllm/v1/worker/worker_base.py:356-363}}).

The extension's methods are reached with {{term collective-rpc}} by name. In each worker, run_method looks the name up on the wrapper, which forwards unknown names to the worker ({{cite vllm/v1/serial_utils.py:485-508}}, {{cite vllm/v1/worker/worker_base.py:365-366}}). AsyncLLM has collective_rpc ({{cite vllm/v1/engine/async_llm.py:1247}}). Over HTTP, the route POST /collective_rpc exists only with VLLM_SERVER_DEV_MODE, and its comment says that it passes only serialized string arguments ({{cite vllm/entrypoints/launchers/api_server/routers.py:46-49}}, {{cite vllm/entrypoints/serve/dev/rpc/api_router.py:43-50}}). An endpoint plugin is the normal way to expose such a method ({{link concepts/frontend-plugins}}).

vllm serve Qwen/Qwen3-0.6B --worker-extension-cls my_pkg.ext.WeightSync
# an endpoint plugin, or code with the engine client, then calls:
#   await engine_client.collective_rpc("update_weights_from", args=("s3://...",))

Step 3: logits processors

A logits processor changes the logits of the batch before sampling. Two sources feed Model Runner V2, and the loader combines them:

  • The group vllm.logits_processors. The loader calls entry_points() directly, so VLLM_PLUGINS does not filter it. A failed import raises RuntimeError; a class that is not a V2 LogitsProcessor raises ValueError ({{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:37-74}}).
  • The field logits_processors (--logits-processors): classes or "module:Class" strings, with exactly one colon ({{cite vllm/config/model.py:407-409}}, {{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:99-104}}).

The model runner builds them in load_model ({{cite vllm/v1/worker/gpu/model_runner.py:463-466}}). A pooling model with custom processors raises ({{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:172-179}}). The front end loads the same classes once, to call validate_params for each request ({{cite vllm/v1/engine/input_processor.py:93-107}}, {{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:186-211}}).

The V2 interface has five methods:

BatchUpdate is part of the older interface in vllm/v1/sample/logits_processor/ ({{cite vllm/v1/sample/logits_processor/interface.py:37}}). Model Runner V2 does not use it. A processor sees each new request in add_request, keyed by a recycled slot index. It sees the batch layout in apply ({{cite vllm/v1/worker/gpu/sample/logits_processor/interface.py:92-107}}). Step 5: sleep-mode backends

{{term sleep-mode | Sleep mode}} frees GPU memory of an idle engine. --enable-sleep-mode turns it on ({{cite vllm/config/model.py:370-372}}). The field docstring says "only cuda and hip", but the platform check also accepts XPU ({{cite vllm/config/model.py:666-668}}, {{cite vllm/platforms/interface.py:231-236}}). The mechanism is a backend class with suspend(level) and resume(tags) ({{cite vllm/device_allocator/sleep_mode_backend.py:37-69}}). The factory mirrors the KV connector factory:

The worker makes the backend on first use, from model_config.sleep_mode_backend ({{cite vllm/v1/worker/gpu_worker.py:249-259}}), and calls suspend and resume ({{cite vllm/v1/worker/gpu_worker.py:317}}, {{cite vllm/v1/worker/gpu_worker.py:339}}). The field defaults to "cumem" ({{cite vllm/config/model.py:379-383}}).

EngineArgs passes enable_sleep_mode and the other sleep fields to ModelConfig, but not sleep_mode_backend ({{cite vllm/engine/arg_utils.py:2039-2043}}). At this commit no other line in vllm/ sets the field. So vllm serve always uses cumem, unless your code changes model_config.sleep_mode_backend, for example a platform in check_and_update_config. A plugin also cannot replace "cumem": the factory raises ValueError for a taken name ({{cite vllm/device_allocator/sleep_mode_backend.py:173-174}}). (Derived from a search of the repository.)

The table on {{link concepts/plugin-map}} puts these hooks next to the other extension points.

You start vllm serve ... --tensor-parallel-size 2 --worker-extension-cls my_pkg.ext.WeightSync. WeightSync defines update_weights_from(path) and init_worker_extension(worker).

  1. The front end stores the string in parallel_config.worker_extension_cls. The workers get it in the pickled VllmConfig.
  2. Each of the 2 worker processes runs init_worker: it imports my_pkg.ext, checks that Worker has no attribute update_weights_from, and adds WeightSync to Worker.__bases__ ({{cite vllm/v1/worker/worker_base.py:304-331}}). It logs "Injected ... for extended collective_rpc calls ['init_worker_extension', 'update_weights_from']". (The list holds every callable name that does not start with __.)
  3. After init_device, the wrapper calls WeightSync.init_worker_extension(worker) ({{cite vllm/v1/worker/worker_base.py:361-363}}).
  4. Later, collective_rpc("update_weights_from", args=(path,)) runs the method in both workers and returns a list of 2 results. With TP = 1 the uni executor calls run_method on its one in-process worker ({{cite vllm/v1/executor/uniproc_executor.py:103}}).

Note that line 323 changes the class Worker itself, not one object. Every worker object of that process gets the methods. (Derived.)
  • Extension already a base. If the extension class is already in worker_class.__bases__, the injection and the clash check are skipped (line 310).
  • Unknown RPC method. run_method raises NotImplementedError("Method ... is not implemented.") ({{cite vllm/v1/serial_utils.py:499-505}}).
  • Mixed-case load format. load_format is lower-cased ({{cite vllm/config/load.py:136-138}}), but register_model_loader stores the name as given. A loader registered as "My_Format" is never found. (Derived.)
  • Logits processors and VLLM_PLUGINS. An allowlist does not stop a logits processor plugin. To keep one out, uninstall its package.
  • Unsupported sleep backend. A backend whose is_supported() is false raises "Sleep-mode backend ... is not supported on this platform." on first use ({{cite vllm/device_allocator/sleep_mode_backend.py:198-201}}).

What can go wrong

vLLM's default is AsyncScheduler. For a class that subclasses Scheduler, vLLM only warns of "degraded performance due to async scheduling being disabled" ({{cite vllm/config/scheduler.py:247-253}}). Subclass AsyncScheduler unless you need the synchronous behaviour.
  • The class does not import in the child process. Config hooks are imported in the engine core or the workers. A class that exists only in your launch script fails there. Put it in an installed package.
  • Colon instead of dot. scheduler_cls, worker_cls and worker_extension_cls need pkg.module.Class; logits_processors strings need pkg.module:Class ({{cite vllm/utils/import_utils.py:119-123}}, {{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:99-104}}).
  • A name clash in the extension. An attribute that the worker class has already stops start-up with an AssertionError ({{cite vllm/v1/worker/worker_base.py:315-319}}).
  • A V1 logits processor. Model Runner V2 rejects it with ValueError at model load ({{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:67-72}}).

Why it matters. These hooks change the engine itself: the scheduling policy, the worker code, the sampler input and the weight source. They are powerful, and most of them are not public, stable interfaces. Read the code of the version that you run before you rely on one.

Which class does the engine core use when --scheduler-cls is not set and async scheduling is on?

AsyncScheduler ({{cite vllm/config/scheduler.py:232-236}}).

 How do the methods of a worker extension class become callable with collective_rpc?

init_worker adds the extension class to the bases of the worker class ({{cite vllm/v1/worker/worker_base.py:323-325}}). run_method then finds the method by name with getattr ({{cite vllm/v1/serial_utils.py:499-501}}).

 You set VLLM_PLUGINS=acme_admin. Does an installed vllm.logits_processors plugin still load in the workers?

Yes. The Model Runner V2 loader calls entry_points(group=...) directly and does not read VLLM_PLUGINS ({{cite vllm/v1/worker/gpu/sample/logits_processor/loader.py:46}}).

 A general plugin calls SleepModeBackendFactory.register_backend("cumem", ...) to replace the built-in backend. What happens?

The factory raises ValueError "Sleep-mode backend 'cumem' is already registered." because vLLM registered cumem at import ({{cite vllm/device_allocator/sleep_mode_backend.py:173-174}}, {{cite vllm/device_allocator/sleep_mode_backend.py:210-214}}). The general plugin does not catch it, so start-up stops ({{cite vllm/plugins/__init__.py:89-90}}).

 You register a model loader with @register_model_loader("Fast_Load") and start with --load-format Fast_Load. What happens, and why?

Start-up fails with "Load format `fast_load` is not supported". The config lower-cases load_format ({{cite vllm/config/load.py:136-138}}), but the table stores "Fast_Load" as given ({{cite vllm/model_executor/model_loader/__init__.py:112}}), so get_model_loader does not find it ({{cite vllm/model_executor/model_loader/__init__.py:126-127}}). Register lower-case names. (Derived from these lines.)
