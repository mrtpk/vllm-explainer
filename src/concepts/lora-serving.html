The worker puts each adapter into a GPU slot, and wrapped layers add its update.

The idea

{{link learn/lora-adapters}} explains what a {{term lora-adapter}} is, why vLLM keeps adapters unmerged, and the flags with their real defaults (--enable-lora off, --max-loras 1, --max-lora-rank 16). This page follows one adapter through the processes of vllm serve.

Four parts work together. The API server turns the model field into a {{term lora-request}}. The scheduler admits a request only if the step does not exceed max_loras adapters. The worker keeps adapters in two LRU caches: one in CPU memory, and a fixed number of {{term lora-slot | GPU slots}}. At model load, vLLM replaces each supported layer with a LoRA wrapper. The wrapper runs the base layer once for the batch and then calls the {{term punica}} kernels, which add each token's own adapter update.

An everyday comparison. Think of a print shop with one press and a rack of three stencil holders. The front desk writes the customer's stencil name on each order. The planner never puts more than three stencils into one run. The stock room keeps stencils on shelves and moves one into a holder when a run needs it. The comparison stops being true in one place: the shop moves a stencil into a holder only when a run needs it. vLLM also activates an adapter at once when you load it through the API.

The picture

Read the panels from top to bottom. Panel 1 runs in three processes: the API server, the engine core and the worker. Panels 2 and 3 run in the worker in every step. The slot layout [1, 3, 2] is one possible order, for example after an LRU eviction; it depends on when each adapter was activated. The worked example in the deep dive gets [1, 2, 3] from its start-up order.

In the code

Step 1: the request gets a LoRARequest

The model field of a request selects the base model or an adapter; _maybe_get_adapters looks the name up ({{cite vllm/entrypoints/serve/engine/serving.py:194-200}}). The result is a small msgspec struct:

lora_int_id must be above 0 ({{cite vllm/lora/request.py:37-39}}). Two LoRA requests are equal when their names are equal; the hash also uses only the name ({{cite vllm/lora/request.py:56-69}}). An unknown name gives HTTP 404. Only with VLLM_ALLOW_RUNTIME_LORA_UPDATING does the server first ask the {{term lora-resolver | LoRA resolvers}} ({{cite vllm/entrypoints/serve/engine/serving.py:62-66}}; {{link concepts/frontend-plugins}}, Step 4).

Step 2: the scheduler limits adapters per step

At the start of the waiting pass, the scheduler collects the adapter ids of all running requests. This includes requests that are not scheduled in this step ({{cite vllm/v1/core/sched/scheduler.py:945-954}}). A waiting request with a new adapter is skipped when that set already has max_loras entries:

The skipped request goes back to the front of the queue and tries again in the next step. The gauge vllm:lora_requests_info shows max_lora and the waiting and running adapters as labels ({{cite vllm/v1/metrics/loggers.py:1099-1112}}).

Step 3: the worker loads and activates adapters

The LoRA manager exists only with --enable-lora. load_lora_model checks that the model supports LoRA, builds an LRUCacheWorkerLoRAManager, and wraps the model ({{cite vllm/v1/worker/lora_model_runner_mixin.py:43-66}}). In each step with LoRA requests, the model runner passes the active LoRARequests to the manager ({{cite vllm/v1/worker/lora_model_runner_mixin.py:68-87}}):

  1. Lines 279-284: more adapters than GPU slots in one batch raises RuntimeError. The scheduler check of Step 2 prevents this.
  2. Lines 295-303: an adapter that is not in the CPU cache is loaded from disk first.
  3. Lines 309-313: when the CPU cache is full (max_cpu_loras), the oldest adapter is removed.
  4. Line 323: activate_adapter puts the adapter into a GPU slot.

Loading. _load_adapter resolves the path. An absolute path is used as is. A path that does not exist locally is a Hugging Face Hub repository, and vLLM downloads it. With VLLM_USE_MODELSCOPE, it is a ModelScope repository ({{cite vllm/lora/utils.py:358-385}}). Then it checks the rank against max_lora_rank and loads the weights to CPU memory in the LoRA dtype ({{cite vllm/lora/worker_manager.py:119-150}}). When the adapter enters the cache, alpha / r is merged into B, so the kernels use scale 1.0 ({{cite vllm/lora/model_manager.py:907-908}}, {{cite vllm/lora/lora_weights.py:37-42}}).

In vllm serve, the front end loads a new adapter with add_lora before a request uses it: for --lora-modules, the load route and the resolvers ({{cite vllm/entrypoints/openai/models/serving.py:194-197}}, {{cite vllm/entrypoints/openai/models/serving.py:333-334}}). The engine core runs this call in its loop, between two steps ({{cite vllm/v1/engine/core.py:1661-1664}}, {{cite vllm/v1/engine/core.py:1752-1765}}). An adapter that the CPU cache evicted loads again inside the step, in add_adapter, with a GPU sync allowed ({{cite vllm/lora/worker_manager.py:294-303}}). In both cases, a download from the Hub or a slow disk delays every running request (derived). Preload the adapters, and set --max-cpu-loras high enough for all the adapters that you serve.

Activation. activate_adapter takes the first free slot and copies each module's A and B into the stacked buffers at that index ({{cite vllm/lora/model_manager.py:355-412}}). The LRU manager first deactivates the oldest active adapter when all slots are used ({{cite vllm/lora/model_manager.py:1440-1452}}). A module without weights in the adapter gets its slot zeroed (reset_lora).

Step 4: the wrapped layers

At model load, the LoRA model manager walks over all modules. Without --lora-target-modules, it wraps every supported module ({{cite vllm/lora/model_manager.py:476-500}}). from_layer picks the first LoRA class whose can_replace_layer accepts the layer, and allocates its buffers for max_loras slots ({{cite vllm/lora/utils.py:113-131}}). A BaseLayerWithLoRA keeps the original layer as base_layer and forwards unknown attributes to it ({{cite vllm/lora/layers/base.py:17-34}}). The linear wrappers run the base layer, then add the LoRA output:

The {{term punica}} wrapper class comes from the platform: PunicaWrapperGPU on CUDA ({{cite vllm/platforms/cuda.py:577-578}}, {{cite vllm/lora/punica_wrapper/punica_selector.py:13-21}}). add_lora_linear first runs a "shrink" (x @ A, into an FP32 buffer of rank width) and then an "expand" (buffer @ B, added to the output) ({{cite vllm/lora/punica_wrapper/punica_gpu.py:218-262}}). The kernels themselves are Triton code and out of scope.

Step 5: token_lora_mapping in Model Runner V2

LoraState keeps one LoRA id per request slot; 0 means no adapter ({{cite vllm/v1/worker/gpu/lora_utils.py:75-89}}). In execute_model, it builds the per-token map and activates the adapters:

Punica turns LoRA ids into slot indices; a token without an adapter gets -1 ({{cite vllm/lora/punica_wrapper/utils.py:87-111}}). set_adapter_mapping rebuilds the metadata only when the mapping or the slot layout changed since the last step ({{cite vllm/lora/model_manager.py:1401-1409}}).

Step 6: CUDA graphs with LoRA

A CUDA graph fixes the number of active adapters it was captured with. So Model Runner V2 captures every capture size once per "LoRA case" ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:305-307}}), and a graph matches a batch only with the same case ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:136}}):

  • Default: cudagraph_specialize_lora is on, specialize_active_lora is off ({{cite vllm/config/compilation.py:663-669}}, {{cite vllm/config/lora.py:66-72}}). So the cases are [0, max_loras + 1]: one graph set for batches without adapters, one for batches with any adapters. LoRA start-up captures twice as many graphs.
  • With --specialize-active-lora: the cases are 0, the powers of 2 up to max_loras, and max_loras + 1 ({{cite vllm/lora/utils.py:55-69}}). A batch with 3 adapters and max_loras 4 uses the case 4 ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:203-227}}).

The number of active adapters for the dispatch is the set of LoRARequests in the batch ({{cite vllm/v1/worker/gpu/lora_utils.py:38-49}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Server (example): vllm serve meta-llama/Llama-3.1-8B-Instruct --enable-lora --max-loras 3 --lora-modules sql=/adapters/sql chat-de=/adapters/de legal=/adapters/legal. The front end gives the adapters the ids 1, 2 and 3 when it registers them (lora_id_counter, {{cite vllm/entrypoints/openai/models/serving.py:167-184}}).

  1. Requests. R1 model: "sql" with a 3-token prefill chunk, R2 "chat-de" in decode, R3 the base model in decode, R4 "legal" with 2 tokens. Each request carries its LoRARequest to the engine core.
  2. Scheduler. The running set is {1, 2, 3}, equal to max_loras. A new waiting request for a fourth adapter is skipped. A new request for sql is admitted, because id 1 is already in the set.
  3. Worker, at start-up. The front end loaded the three adapters in the order of --lora-modules, and each add_adapter activated its adapter at once (Step 3, line 323). So slot 0 holds sql, slot 1 chat-de, slot 2 legal: lora_index_to_id = [1, 2, 3].
  4. Worker, in this step. _apply_adapters gets {1, 2, 3}. All are in the CPU cache and active, so each add_adapter only touches the LRU, and activate_adapter changes nothing ({{cite vllm/lora/model_manager.py:360-361}}).
  5. Mapping. Per-request ids [1, 2, 0, 3], tokens per request [3, 1, 1, 2] → token_lora_mapping = (1, 1, 1, 2, 0, 3, 3). Punica slot indices: (0, 0, 0, 1, -1, 2, 2).
  6. One q_proj. Base GEMM [7, 4096] × [4096, 4096]. Shrink buffer FP32 [1, 7, 16] (one slice for q_proj). Expand adds [7, 4096]. Token 4 (R3) has no adapter.
  7. CUDA graph. 3 adapters are active. With the default cases [0, 4], the batch uses the LoRA graphs (case 4). A batch with only base-model requests uses case 0.

Each wrapped linear layer allocates lora_a_stacked [max_loras, 1, max_lora_rank, input_size] and lora_b_stacked [max_loras, 1, output_size, max_lora_rank] per slice ({{cite vllm/lora/layers/base_linear.py:133-154}}). The size follows the configured maximum rank, not the rank of the loaded adapters.

{{link learn/lora-adapters}} computes the numbers for Llama-3.1-8B at rank 16 and TP = 1. The 7 linear layers of all 32 blocks take 83.9 MB, and embed_tokens and lm_head add 8.5 MB. So one slot holds 92.4 MB. With --max-loras 3 that is 277 MB; with --max-loras 4 --max-lora-rank 64 it is 1.48 GB. This memory is reserved before the KV cache is sized. The CPU cache holds the loaded adapters at their own rank, in the LoRA dtype.

The routes /v1/load_lora_adapter and /v1/unload_lora_adapter exist only with VLLM_ALLOW_RUNTIME_LORA_UPDATING, and vLLM logs that this "should ONLY be used for local development" ({{cite vllm/entrypoints/serve/lora/api_router.py:30-36}}).

  1. Load. The API server builds a LoRARequest and calls engine_client.add_lora() ({{cite vllm/entrypoints/openai/models/serving.py:179-197}}). The call goes AsyncLLM.add_lora → EngineCore.add_lora → collective_rpc("add_lora") on every worker → add_adapter ({{cite vllm/v1/engine/async_llm.py:1231-1233}}, {{cite vllm/v1/engine/core.py:1076-1077}}, {{cite vllm/v1/executor/abstract.py:363-365}}, {{cite vllm/v1/worker/lora_model_runner_mixin.py:296-298}}). add_adapter also activates the adapter into a GPU slot (line 323 in Step 3), which can evict another one.
  2. Unload. The API server only deletes the name from its dict ({{cite vllm/entrypoints/openai/models/serving.py:234-247}}). No code in vllm/entrypoints/ calls the engine's remove_lora ({{cite vllm/v1/engine/core.py:1079-1080}}). The worker keeps the adapter in its CPU and GPU caches until LRU eviction needs the room.
  3. Reload in place from the same path keeps the old prefix-cache blocks valid, and vLLM warns about it ({{cite vllm/entrypoints/openai/models/serving.py:215-224}}).
  4. One API server. With api_server_count above 1, start-up fails ({{cite vllm/entrypoints/cli/serve.py:315-318}}).

An adapter changes the KV values, so the block hash of a LoRA request includes ("lora", lora_name, lora_path) ({{cite vllm/v1/core/kv_cache_utils.py:590-607}}). The same prompt with two adapters never shares blocks. See {{link learn/prefix-caching}}.

LoRA also touches the compile hash: max_num_batched_tokens is part of the scheduler hash, and the LoRA buffers are one of the two reasons ({{cite vllm/config/scheduler.py:271-280}}). With speculative decoding, LoRA requires max_num_batched_tokens ≥ max_num_seqs × (k + 1) ({{cite vllm/engine/arg_utils.py:2700-2713}}).

What can go wrong

  • Requests wait with many adapters. More distinct adapters than --max-loras among running requests make new requests wait (Step 2).
  • Latency spikes on new adapters. Loading stops the engine loop while it runs (Step 3). Preload the adapters.
  • "LoRA rank ... is greater than max_lora_rank". Raise --max-lora-rank to the largest rank you serve ({{link learn/lora-adapters}}).
  • "... does not support LoRA yet." The model class does not implement SupportsLoRA ({{cite vllm/v1/worker/lora_model_runner_mixin.py:49-50}}).
  • Unloaded adapters still use memory. Unload only removes the name in the API server (deep dive).
  • Longer start-up. LoRA doubles the CUDA graph captures by default, and --specialize-active-lora adds more (Step 6).

Why it matters. Multi-LoRA serving puts many fine-tuned variants on one GPU. Its limits come from three fixed sizes: max_loras per step, max_cpu_loras in memory, and slot buffers sized for max_lora_rank.

Which request field selects the adapter, and what does the API server make from it?

The model field. The server returns the stored LoRARequest for that name ({{cite vllm/entrypoints/serve/engine/serving.py:194-200}}).

 Where are the adapter weights after _load_adapter, and when do they reach the GPU?

In CPU memory: the loader uses device="cpu" ({{cite vllm/lora/worker_manager.py:145}}). activate_adapter copies them into a GPU slot of the stacked buffers ({{cite vllm/lora/model_manager.py:355-412}}).

 With default settings and --max-loras 4, which LoRA cases does Model Runner V2 capture CUDA graphs for?

[0, 5]: cudagraph_specialize_lora is on and specialize_active_lora is off, so the cases are 0 and max_loras + 1 ({{cite vllm/v1/worker/gpu/lora_utils.py:29-35}}, {{cite vllm/lora/utils.py:64-65}}).

 A batch has 7 tokens: 3 for adapter id 1, 1 for id 2, 1 base, 2 for id 3. The slots hold ids [1, 3, 2]. What are token_lora_mapping and the Punica slot indices?

(1, 1, 1, 2, 0, 3, 3) from lora_ids.repeat(num_scheduled_tokens) ({{cite vllm/v1/worker/gpu/lora_utils.py:100-102}}). Slot indices (0, 0, 0, 2, -1, 1, 1): id → index in lora_index_to_id, and 0 → -1 ({{cite vllm/lora/punica_wrapper/utils.py:94-111}}).

 You call /v1/unload_lora_adapter for "legal". Is GPU memory freed, and can a new request still use "legal"?

No memory is freed: slot buffers are fixed at start-up, and the worker keeps the adapter until LRU eviction ({{cite vllm/lora/worker_manager.py:309-313}}). New requests get 404, because the API server deleted the name ({{cite vllm/entrypoints/openai/models/serving.py:244-246}}). Requests that already carry the LoRARequest continue (derived).
