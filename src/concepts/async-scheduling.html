Placeholders in the scheduler and a GPU-side token buffer in Model Runner V2 make this possible. --- With async scheduling, the engine core plans and starts step N+1 while the GPU still runs step N. So the GPU does not wait for the CPU.

The idea

Each {{term engine-step}} has CPU work and GPU work. The CPU schedules the batch, prepares the inputs, launches the kernels, and later turns the sampled tokens into outputs. The GPU runs the forward pass and the sampler. If the CPU waits for each step before it plans the next one, the GPU is idle during the CPU work. For small decode batches, that CPU work can take a large part of the step time.

The fix is to plan one step ahead. DeepInfer uses the same idea: the CPU prepares batch N+1 while the GPU runs batch N ({{deepinfer concepts/zero-overhead-scheduling | Zero-overhead scheduling}}). vLLM does it with three parts:

  1. The engine core keeps a {{term batch-queue}} of started steps, and it waits only for the oldest one ({{link concepts/engine-core-loop}}).
  2. AsyncScheduler counts an {{term output-placeholder}} for each token that a started step will sample. So it can schedule the next decode step before it knows the token.
  3. Model Runner V2 keeps the last sampled token of each request in a GPU tensor. The next step reads its input token from there, without a copy to the CPU and back.

An everyday comparison. Think of a relay race where the next runner starts to run before the baton arrives, and takes it at full speed. The next step starts before the token arrives. The comparison stops in one place: in a relay race the baton must arrive. Here the token never has to reach the CPU before the next step: the GPU passes it to itself.

The picture

Compare the GPU lanes of panels 1 and 2. Without async scheduling, the GPU has a gap in every step. With it, the GPU lane is full, and the CPU waits instead (dashed blocks). Panel 3 shows why the GPU can start step N+1 at once: it takes its input token from its own memory.

In the code

Step 1: when async scheduling is on

The flag async_scheduling has the default None ({{cite vllm/config/scheduler.py:211-214}}). VllmConfig.__post_init__ turns None into True unless an incompatible option is set:

So async scheduling is off in these cases:

  • You pass --no-async-scheduling (the flag is --async-scheduling, {{cite vllm/engine/arg_utils.py:1800-1802}}).
  • The model is a pooling model, for example an embedding model ({{cite vllm/config/vllm.py:1666-1675}}).
  • The executor class does not support it ({{cite vllm/config/vllm.py:1676-1682}}). The base class says no ({{cite vllm/v1/executor/abstract.py:452-455}}). The uni and mp executors say yes ({{cite vllm/v1/executor/uniproc_executor.py:156-158}}, {{cite vllm/v1/executor/multiproc_executor.py:565-567}}). The Ray executor inherits the mp answer ({{cite vllm/v1/executor/ray_executor_v2.py:239-247}}). An out-of-tree executor class gets False unless it overrides the method.
  • ROCm with dual-batch overlap and the deepep_high_throughput all-to-all backend ({{cite vllm/config/vllm.py:1624-1628}}, {{cite vllm/config/vllm.py:1683-1689}}).
  • The fallback Model Runner V1 is in use, with one of three options: pipeline parallelism, disable_padded_drafter_batch, or an unsupported speculative method ({{cite vllm/config/vllm.py:1630-1645}}, {{cite vllm/config/vllm.py:1690-1696}}). The supported methods are the EAGLE types, GPU n-gram, draft_model, dspark and dflash. With the default Model Runner V2, none of these options turn it off.
  • The CPU platform. Its platform hook always sets async_scheduling = False ({{cite vllm/platforms/cpu.py:342-343}}). The hook runs later in __post_init__, so it wins over your flag and raises no error ({{cite vllm/config/vllm.py:2046-2048}}).

If you set --async-scheduling yourself and the executor, ROCm or Model Runner V1 case applies, the config raises ValueError instead ({{cite vllm/config/vllm.py:1647-1663}}). A pooling model does not raise: async scheduling stays on. With async scheduling on and no scheduler class set, the scheduler class is AsyncScheduler ({{cite vllm/config/scheduler.py:231-236}}). Step 2: AsyncScheduler and the placeholders

AsyncScheduler is a small subclass of Scheduler. It changes two hooks. After each schedule(), it adds placeholders:

  1. Lines 34-35: a request in the middle of a chunked prefill samples no token, so it gets no placeholder.
  2. Lines 37-39: a structured output request with a token still in flight sets pending_structured_output_tokens (Step 5).
  3. Lines 45-47: each sampling step adds one placeholder per sampled token, plus one per draft token with speculative decoding.
  4. Line 50: the draft tokens of the next step are not known yet either. The scheduler uses a list of -1 values as their placeholders ({{cite vllm/v1/core/sched/async_scheduler.py:17-18}}, {{cite vllm/v1/core/sched/async_scheduler.py:28-31}}). The worker fills in the real draft tokens on the GPU.

The running pass of schedule() counts the placeholders as tokens that the request already has:

Take a decode with one token in flight and no speculative decoding. The request has T known tokens, one placeholder, and num_computed_tokens = T. The result is T + 1 - T = 1: the scheduler plans exactly one more token. When the real token arrives, the second hook removes the placeholder:

Step 3: the batch queue gives the overlap

The engine core uses step_with_batch_queue when max_concurrent_batches > 1 ({{cite vllm/v1/engine/core.py:205-211}}, {{cite vllm/v1/engine/core.py:227-229}}). On each call it schedules and starts step N+1, and only then waits for step N:

Timeline of one call, for steps N and N+1:

  1. The GPU runs step N (it was queued in the previous call).
  2. The CPU schedules step N+1. The decode requests of step N+1 count their step-N token as a placeholder.
  3. The CPU runs the CPU part of the model runner for step N+1. The kernels of step N+1 go into the same CUDA stream, behind step N.
  4. The CPU waits for the result of step N. Often the GPU is already done, so the wait is short.
  5. The CPU runs update_from_output for step N and sends its tokens. The GPU already runs step N+1.

The page {{link concepts/engine-core-loop}} reads the whole function line by line.

Step 4: the next input token comes from the GPU

The CPU does not know the token of step N when it prepares step N+1. Model Runner V2 does not need it. The sampler output stays on the GPU, and postprocess_sampled writes it into req_states.last_sampled_tokens with the post_update kernel:

In the next step, prepare_inputs copies that token into the input ids on the GPU:

The copy to the CPU runs at the same time on a separate CUDA stream. AsyncOutput starts it in sample_tokens and records an event ({{cite vllm/v1/worker/gpu/async_utils.py:171}}); nobody waits for it there:

The only wait is copy_event.synchronize() in get_output() (line 174). With the uni executor, the engine core calls it when it pops step N from the batch queue ({{cite vllm/v1/executor/uniproc_executor.py:38-48}}). With the mp executor, a worker thread calls it (Step 6). The design doc of Model Runner V2 states the rule: the core execution loop is "a CUDA stream with no CPU synchronization points" ({{cite docs/design/model_runner_v2.md:47}}). get_output also trims each row to the number of sampled tokens (line 183). So a prefill chunk that sampled nothing gets an empty list.

Step 5: execute_model and sample_tokens are two calls

The engine core calls the workers twice per step: execute_model runs the forward pass, and sample_tokens computes logits and samples. The worker interface links this design to structured outputs:

Between the two calls the engine core computes the grammar bitmask for structured output on the CPU, while the GPU runs the forward pass:

The bitmask of step N+1 needs the token of step N, because the grammar must first advance by that token. When a structured output request still has a token in flight, the token is not on the CPU yet. Then the engine defers sampling: it processes step N first, computes the bitmask, and only then queues sample_tokens for step N+1 ({{cite vllm/v1/engine/core.py:789-810}}). In this case the GPU can wait for the CPU for a short time. Structured outputs as token masks are explained in {{deepinfer concepts/structured-outputs | Structured outputs}}.

Step 6: the same overlap with worker processes

With the uni executor, execute_model and sample_tokens run in the engine core's main thread. They return without a GPU wait; non_block only moves the wait into a future ({{cite vllm/v1/executor/uniproc_executor.py:108-117}}). With the mp executor, each worker process has an extra thread, WorkerAsyncOutputCopy, only when async scheduling is on ({{cite vllm/v1/executor/multiproc_executor.py:690-699}}). On the output rank, the worker's main thread hands each output to it and reads the next call at once ({{cite vllm/v1/executor/multiproc_executor.py:1019-1020}}, {{cite vllm/v1/executor/multiproc_executor.py:1070-1071}}). The extra thread calls get_output() and writes the result into the reply queue ({{cite vllm/v1/executor/multiproc_executor.py:1000-1002}}, {{cite vllm/v1/executor/multiproc_executor.py:1037-1039}}). See {{link concepts/executors-and-workers}}.

Step 7: what it costs

  • One step of extra work after a stop. When step N samples EOS or a stop token id, step N+1 for that request is already on the GPU. update_from_output skips results of finished requests ({{cite vllm/v1/core/sched/scheduler.py:2184-2192}}). The GPU time of that row is lost, but the client never sees the token.
  • No extra step for max_tokens. The running pass skips a request when the step in flight surely reaches max_tokens ({{cite vllm/v1/core/sched/scheduler.py:720-734}}).
  • Stop strings cost more. The engine core has no text. The front end finds a stop string after detokenization and sends an ABORT ({{cite vllm/v1/engine/output_processor.py:825-830}}, {{cite vllm/v1/engine/output_processor.py:878-882}}, {{cite vllm/v1/engine/async_llm.py:918-921}}). By then the engine may have started more than one further step for the request.
  • Prefix caching lags by one step. After an update, the scheduler caches only blocks up to num_computed_tokens - num_output_placeholders, the tokens whose values are known ({{cite vllm/v1/core/sched/async_scheduler.py:75-79}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

A request has a 10-token prompt and max_tokens = 3. It runs alone. "S k" = schedule step k; "U k" = update with the result of step k. In each call of step_with_batch_queue, S k+1 comes before U k. The skip test is placeholders > 0 and computed + 2 - placeholders >= prompt + max_tokens ({{cite vllm/v1/core/sched/scheduler.py:720-729}}).

Eventcomputedplaceholdersnum_tokensNote
S 1 (prefill)0 → 100 → 110last prefill chunk samples a token
S 210 → 111 → 210test: 10 + 2 − 1 = 11 < 13, schedule 1 token
U 1 (token 1)112 → 111
S 311 → 121 → 211test: 11 + 2 − 1 = 12 < 13, schedule
U 2 (token 2)122 → 112
S 412112test: 12 + 2 − 1 = 13 ≥ 13, skip
U 3 (token 3)121 → 013check_stop: length reached

No wasted step. Now let token 2 be EOS. At U 2 the request finishes, but S 3 has already started step 3 for it. At U 3 the request is finished, so the result is skipped. One GPU row is wasted. (Derived from the code above and {{cite vllm/v1/core/sched/async_scheduler.py:45-47}}, {{cite vllm/v1/core/sched/async_scheduler.py:71-73}}.)

With k speculative tokens, each scheduled decode adds 1 + k placeholders (lines 45-47 above). The scheduled draft tokens are the list [-1] * k from the previous schedule call (line 29-31). The real drafts exist only on the GPU. sample_tokens writes them into req_states.draft_tokens after the speculator runs ({{cite vllm/v1/worker/gpu/model_runner.py:2257-2289}}). The next prepare_inputs reads them in combine_sampled_and_draft_tokens (the draft_tokens argument at line 1500).

When the result arrives, rejected drafts roll back both counters: num_computed_tokens and num_output_placeholders go down by the number of rejected drafts ({{cite vllm/v1/core/sched/scheduler.py:2213-2221}}). Then _update_request_with_output removes one placeholder per accepted token. For this reason EngineCore.post_step does not take draft tokens from the workers when async scheduling is on ({{cite vllm/v1/engine/core.py:689-696}}). The page {{link concepts/speculative-decoding}} explains the methods.

The worker methods execute_model and sample_tokens have the decorator with_gpu_sync_check ({{cite vllm/v1/worker/gpu_worker.py:1316-1327}}). It reports any GPU-to-CPU synchronization inside these calls ({{cite vllm/utils/gpu_sync_debug.py:386-392}}). The check is off unless VLLM_GPU_SYNC_CHECK is warn or error ({{cite vllm/envs.py:657-658}}). It starts only after warm-up, when the worker calls enable_gpu_sync_check() ({{cite vllm/v1/worker/gpu_worker.py:1108-1110}}). This is the tool to use when you add code to the model runner and want to keep the overlap.

With Model Runner V2 and PP = 2, the batch queue has 3 slots ({{cite vllm/config/vllm.py:591-593}}). The comment gives the reason: PP needs pp_size batches in flight "to fill the pipeline", and async scheduling one more to overlap ({{cite vllm/config/vllm.py:588-589}}). The scheduler then enforces pp_size steps between two decodes of the same request, through next_decode_eligible_step ({{cite vllm/v1/core/sched/async_scheduler.py:52-57}}, {{cite vllm/v1/core/sched/scheduler.py:736-740}}). On XPU with VLLM_XPU_PP_MICROBATCH off, the gap is 1 step ({{cite vllm/v1/core/sched/async_scheduler.py:20-23}}). The page {{link concepts/distributed-groups}} explains PP in vLLM.

What can go wrong

  • Async scheduling is off and you do not know it. For a pooling model it is off by default and the log says so only at DEBUG level ({{cite vllm/config/vllm.py:1672-1675}}). For an unsupported executor it logs a warning ({{cite vllm/config/vllm.py:1677-1681}}).
  • A custom executor loses the overlap. An out-of-tree executor class gets supports_async_scheduling() = False from the base class ({{cite vllm/v1/executor/abstract.py:452-455}}). Override it if your executor returns futures correctly.
  • Structured output slows decode. Each step with a pending structured output token defers sampling until the previous step is processed ({{cite vllm/v1/engine/core.py:746-749}}). The GPU can then wait for the CPU grammar work.
  • New code adds a GPU sync. A .item() or a .cpu() in the model runner path breaks the overlap without an error. Run with VLLM_GPU_SYNC_CHECK=warn to find it.
  • Wasted tokens after a stop. With many short answers that end on EOS, about one row per finished request is wasted. This is normally much smaller than the gain.

Why it matters. At small batch sizes, the CPU work per step is a large part of the step time. Async scheduling hides it, and that improves both the inter-token latency and the throughput. When you change scheduling or model runner code, keep the two rules of this page. Plan with placeholders. Do not wait for the GPU before the next step is queued.

What is the default of async_scheduling for a chat model on one GPU, and which scheduler class does the engine core use?

The flag is None, and VllmConfig.__post_init__ sets it to True because nothing is incompatible ({{cite vllm/config/vllm.py:1664-1698}}). The scheduler class is then AsyncScheduler ({{cite vllm/config/scheduler.py:231-236}}).

 How does the scheduler compute the number of new tokens for a decoding request whose last token is still in flight?

num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens ({{cite vllm/v1/core/sched/scheduler.py:759-763}}). The placeholder stands for the token in flight, so the result is 1, and the scheduler can plan the step before the token is known.

 Where does Model Runner V2 get the input token of a decode step when the CPU has not received the previous token yet?

From req_states.last_sampled_tokens, a GPU tensor. post_update writes the sampled token there in sample_tokens ({{cite vllm/v1/worker/gpu/model_runner.py:1715-1726}}), and combine_sampled_and_draft_tokens reads it in the next prepare_inputs ({{cite vllm/v1/worker/gpu/model_runner.py:1493-1500}}).

 A request with max_tokens = 3 finishes by length. Another request ends with EOS at its second token. Which of the two wastes a GPU step, and which line prevents the waste for the other?

The EOS request wastes one step. Step 3 was scheduled before the EOS token reached the scheduler. Its result is skipped because the request is finished ({{cite vllm/v1/core/sched/scheduler.py:2184-2192}}). The length case wastes nothing: the running pass skips the request when computed + 2 - placeholders >= prompt + max_tokens ({{cite vllm/v1/core/sched/scheduler.py:720-734}}). See the worked example in the deep dive.

 Why are execute_model and sample_tokens two separate worker calls?

So the engine core can compute the grammar bitmask on the CPU between them, while the GPU runs the forward pass. sample_tokens takes the bitmask as its argument ({{cite vllm/v1/engine/core.py:740-745}}). The worker interface ties this design to structured outputs ({{cite vllm/v1/worker/worker_base.py:177-182}}).
