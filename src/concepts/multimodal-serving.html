The idea

A vision-language model has a vision encoder next to the language model. The encoder turns an image into a sequence of vectors in the model's embedding space. The language model then reads them like token embeddings ({{deepinfer concepts/vision-encoder | The vision encoder}}). vLLM must fit this into its token-based scheduler and its KV cache.

The trick is the {{term placeholder-token}}. The {{term mm-processor | multimodal processor}} of the model replaces the image marker in the prompt with N placeholder tokens, one per encoder output vector. From then on, the scheduler treats the request as a normal prompt of text plus N tokens. When a step reaches the placeholders, the worker runs the encoder and splices the N vectors into the input embeddings. The {{term encoder-cache}} keeps the output, keyed by a hash of the image. So a long prompt split over several steps needs no second encoder run, and nor does a second request with the same image.

An everyday comparison. Think of a book with a figure. The typesetter leaves a blank area of the right size on the page (the placeholders). A separate studio draws the figure (the encoder), and the printer pastes it into the blank area. The comparison stops being true in one place. vLLM keeps the drawn figure in a cache, and can paste it into other books with the same figure.

In the code

Step 1: content parts and media loading

A chat message can hold a list of content parts. The renderer has one parser per part type:

image_url, audio_url, input_audio and video_url load media. The image_embeds, audio_embeds and video_embeds parts take precomputed embeddings and need --enable-mm-embeds, which the config marks as "only for trusted users" ({{cite vllm/config/multimodal.py:326-338}}; the checks at {{cite vllm/renderers/chat_utils/content_parser.py:186-190}}, {{cite vllm/renderers/chat_utils/content_parser.py:214-218}}, {{cite vllm/renderers/chat_utils/content_parser.py:296-300}}). prompt_embeds needs --enable-prompt-embeds instead ({{cite vllm/renderers/chat_utils/content_parser.py:165-168}}). The renderer gets its media loader, the media connector, from a registry; VLLM_MEDIA_CONNECTOR picks it, default http ({{cite vllm/renderers/chat_utils/content_parser.py:140-151}}, {{cite vllm/envs.py:1072-1076}}).

  • data: URLs must be base64 ({{cite vllm/multimodal/media/connector.py:328-346}}).
  • HTTP(S): with --allowed-media-domains set, other hosts raise ValueError ({{cite vllm/multimodal/media/connector.py:370-379}}). Timeouts are VLLM_IMAGE_FETCH_TIMEOUT 5 s, VLLM_VIDEO_FETCH_TIMEOUT 30 s and VLLM_AUDIO_FETCH_TIMEOUT 10 s; one download is at most VLLM_MAX_MEDIA_DOWNLOAD_SIZE_MB 256 MB; redirects are allowed by default ({{cite vllm/envs.py:955-994}}). The timeouts are for the first attempt. By default vLLM makes up to 3 attempts, and each new attempt has a 4 times longer timeout ({{cite vllm/connections.py:292-306}}, {{cite vllm/connections.py:30}}).
  • file: works only with --allowed-local-media-path, and only for files under it ({{cite vllm/multimodal/media/connector.py:348-368}}). The config calls this "a security risk" ({{cite vllm/config/model.py:231-237}}).

Step 2: the multimodal processor and its placeholders

Each multimodal model class registers its processor on the global MULTIMODAL_REGISTRY with a decorator ({{cite vllm/multimodal/__init__.py:7}}, {{cite vllm/multimodal/registry.py:82-113}}); Llava is one example ({{cite vllm/model_executor/models/llava.py:487-491}}). The registry builds the processor for the served model ({{cite vllm/multimodal/registry.py:150-166}}). Its apply method does the work:

The result holds the new prompt token ids, the processed tensors (mm_kwargs), one hash per item, and the placeholder ranges. A range is an offset and a length in the prompt. The count limit is --limit-mm-per-prompt: 999 per modality when unset, capped by what the model supports. A prompt above it gets a validation error, "At most ... may be provided in one prompt." ({{cite vllm/config/multimodal.py:695-707}}, {{cite vllm/multimodal/processing/context.py:608-626}}).

--mm-processor-kwargs passes options to the HF processor, for example {"num_crops": 4} for Phi-3-Vision ({{cite vllm/config/multimodal.py:343-351}}). A request can also send mm_processor_kwargs or media_io_kwargs, but the server rejects non-empty values unless it runs with --trust-request-mm-kwargs ({{cite vllm/entrypoints/generate/base/protocol.py:70-95}}).

Step 3: the processor cache between the API server and the engine core

Processing an image can cost more than the HTTP request itself. The processor cache keeps processed items by hash. Its type depends on the deployment:

  • lru (default, one API server): the API server keeps a "sender" cache and the engine core a mirrored "receiver" cache. On a hit, the API server sends the hash without the data, and the engine core fills it in ({{cite vllm/multimodal/cache/factories.py:49-87}}).
  • processor_only: with more than one API server, or with data parallelism without an external load balancer, only the API server caches its own processing results.
  • shm: a shared-memory FIFO that the workers read; objects up to 128 MiB each ({{cite vllm/config/multimodal.py:369-378}}).

The size is --mm-processor-cache-gb, 4 GiB by default, once per API server process and once per engine core ({{cite vllm/config/multimodal.py:357-368}}). The two mirrored caches can drift. The engine core then raises MultiModalCacheMissError, and the API server drops the stale entries so a retry sends the data again ({{cite vllm/multimodal/cache/base.py:33-52}}).

Step 4: the encoder cache and its budget in the scheduler

The scheduler owns an EncoderCacheManager. It counts in encoder embeddings, not in bytes, and shares entries between requests with the same hash ({{cite vllm/v1/core/encoder_cache_manager.py:19-46}}). Its size and the per-step encoder budget come from compute_mm_encoder_budget:

Both base values are max_num_batched_tokens; they are not configurable ({{cite vllm/config/scheduler.py:145-157}}, {{cite vllm/config/scheduler.py:306-307}}). So by default the cache holds as many embeddings as one step holds tokens, or one largest item if that is bigger.

When the scheduler gives a request new tokens, it checks the multimodal items in that token window. It schedules an encoder input only if its output is not cached, there is budget, and the cache has room. Otherwise it stops the request's chunk just before the item ({{cite vllm/v1/core/sched/scheduler.py:2007-2032}}). The SchedulerOutput lists the scheduled inputs per request and the hashes that workers may drop ({{cite vllm/v1/core/sched/output.py:255}}, {{cite vllm/v1/core/sched/output.py:263}}).

Step 5: the encoder run in Model Runner V2

The worker keeps the encoder outputs in a dict from hash to tensor ({{cite vllm/v1/worker/gpu/mm/encoder_cache.py:8-13}}). Before the forward pass, the model state runs the encoder and builds the input embeddings:

  1. prepare_mm_inputs skips items that are already in the cache ({{cite vllm/v1/worker/gpu/mm/encoder_runner.py:81-108}}).
  2. execute_mm_encoder groups the items by modality and calls the model's embed_multimodal, or a captured encoder CUDA graph ({{cite vllm/v1/worker/gpu/mm/encoder_runner.py:150-176}}).
  3. gather_mm_embeddings takes, for each request, the part of each item that falls into this step's tokens, and a boolean mask is_mm_embed. A step with only decodes gathers nothing (except for realtime models). A missing cache entry raises RuntimeError ({{cite vllm/v1/worker/gpu/mm/encoder_runner.py:207-294}}).
  4. get_inputs_embeds calls the model's embed_input_ids with the embeddings and the mask, and copies the result into the fixed buffer for CUDA graphs ({{cite vllm/v1/worker/gpu/mm/encoder_runner.py:296-308}}).

The worker drops entries when the scheduler lists them in free_encoder_mm_hashes ({{cite vllm/v1/worker/gpu/model_runner.py:1187-1190}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Example values: a server with max_num_batched_tokens = 2048, a prompt of 100 text tokens, then an image, then 50 text tokens. Assume the processor gives N = 1,500 placeholder tokens for this image (the real N depends on the model and the image size).

  1. API server. The prompt has 100 + 1,500 + 50 = 1,650 tokens. The placeholder range is offset 100, length 1,500. The item hash is computed from the image data (default hasher blake3, {{cite vllm/config/multimodal.py:372-374}}).
  2. Encoder budget. max(2048, largest item). With 1,500 as the largest item for this model, the cache and the per-step budget are both 2,048 embeddings.
  3. Step 1. Suppose other requests leave 600 tokens of budget. The window is tokens 0 to 599, which reaches the image at 100. The image is not cached, budget and space are free, so the encoder runs for all 1,500 embeddings. The decoder uses positions 100 to 599 of it (500 rows).
  4. Step 2. The next chunk covers tokens 600 to 1,649. The scheduler finds the item in the cache, so the encoder does not run again. The worker gathers rows 500 to 1,499 of the cached output.
  5. Prefix cache. The KV blocks that contain image positions get the extra key ("mm", hash, offset), with the item offset relative to the block start. So a later request with the same image and the same text can hit these blocks; a different image cannot ({{cite vllm/v1/core/kv_cache_utils.py:559-574}}).
  6. End. When no running request needs the item, its cache entry becomes freeable. It is evicted only when space is needed. Then the hash goes to the workers in free_encoder_mm_hashes.

With --disable-chunked-mm-input, step 1 would stop the chunk before position 100, because a chunk may not cover only part of an item ({{cite vllm/v1/core/sched/scheduler.py:1953-1970}}). Encoder-decoder models turn this option on by themselves ({{cite vllm/config/scheduler.py:295-298}}).

vLLM can run the vision encoder in a separate instance and send the embeddings to the language-model instance. The docs list the gains: independent scaling, lower TTFT and shared reuse of encoder outputs ({{cite docs/features/disagg_encoder.md:1-8}}). An {{term ec-connector}} moves the encoder cache entries, as a KV connector moves KV blocks ({{link concepts/kv-connectors}}). --ec-transfer-config sets the connector and the role (ec_producer, ec_consumer, ec_both) ({{cite vllm/config/ec_transfer.py:16-45}}). A producer-only instance sets mm_encoder_only ({{cite vllm/config/vllm.py:2863-2875}}), turns off prefix caching ({{cite vllm/config/vllm.py:1505-1516}}), and its workers build an MMEncoderModelRunner instead of the normal Model Runner V2 ({{cite vllm/v1/worker/gpu_worker.py:567-576}}).

What can go wrong

--allowed-local-media-path lets any client read files under that folder. Without --allowed-media-domains, the API server fetches any HTTP URL that a client sends. Set both on a public server ({{cite vllm/multimodal/media/connector.py:348-379}}).
  • "At most N image(s) may be provided in one prompt." The request is above --limit-mm-per-prompt or the model's own limit (Step 2).
  • "Cannot load local files without --allowed-local-media-path." A file: URL without the flag ({{cite vllm/multimodal/media/connector.py:353-357}}).
  • Slow TTFT for large images. The encoder runs inside the step that first reaches the image. The scheduler may also cut the chunk before an item that does not fit the encoder budget (Step 4).
  • Per-request mm_processor_kwargs rejected. Start the server with --trust-request-mm-kwargs only for trusted clients (Step 2).
  • Host memory. The processor cache exists once per API server and once per engine core (Step 3).

Why it matters. A multimodal request costs more than its token count shows: media download, processing, an encoder run and cache space. Knowing which cache sits where helps you to size the server and to keep repeated images cheap.

What does a placeholder token stand for, and who inserts it?

One encoder output vector of a multimodal item. The model's multimodal processor inserts them in apply() ({{cite vllm/multimodal/processing/processor.py:1816-1826}}).

 How large is the encoder cache with max_num_batched_tokens = 8192 and a largest item of 1,200 embeddings, and in which unit?

8,192 encoder embeddings: max(8192, 1200). The unit is embeddings, not bytes or tokens of text ({{cite vllm/v1/core/encoder_cache_manager.py:355-362}}, {{cite vllm/v1/core/encoder_cache_manager.py:19-46}}).

 You start 4 API servers. Which processor cache type does vLLM use, and what changes?

processor_only: IPC caching needs exactly one API process ({{cite vllm/multimodal/cache/factories.py:36-43}}). Each API server caches only its own processing results, and the engine core gets the full data every time.

 A prompt with one image is split over two steps. Why does the encoder run only once, and how does the worker get the second half?

In the second step the scheduler finds the item's hash in the encoder cache and does not schedule it again ({{cite vllm/v1/core/sched/scheduler.py:2007-2010}}). The worker's gather_mm_embeddings slices the cached output by the step's token window ({{cite vllm/v1/worker/gpu/mm/encoder_runner.py:240-290}}).
