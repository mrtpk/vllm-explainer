They resolve a quantization method per layer, allocate only their slice, cut checkpoint tensors when they load, and call the all-reduce or all-gather in forward. QKVParallelLinear splits by heads and copies KV heads when TP is larger than their count. --- Each TP layer allocates only its slice, cuts its slice from the checkpoint when it loads, and calls the collective that its split needs.

The idea

With {{term tensor-parallel}} (TP) each GPU holds a slice of every weight. A {{term column-parallel}} layer splits the output features; a {{term row-parallel}} layer splits the input features and adds the partial sums with an {{term all-reduce}}. The page {{link learn/tp-pp-in-practice}} shows this with one Llama MLP. This page explains the classes that do it.

A model file never calls a collective and never computes a slice. It builds layers such as QKVParallelLinear(hidden_size, head_size, total_num_heads, total_num_kv_heads) with full sizes ({{link concepts/model-definition}}). Each layer class then does five jobs itself:

  1. It asks the quantization config for a {{term quantize-method}} for its {{term model-prefix}}.
  2. It computes its per-rank sizes and lets the quantize method make parameters of that size.
  3. It gives each parameter a {{term weight-loader}} that cuts this rank's slice from a full checkpoint tensor ({{link concepts/weight-loading}}).
  4. In forward, it runs the GEMM through the quantize method.
  5. It calls the collective that the split needs: an all-gather when {{term gather-output}} is set, an all-reduce when {{term reduce-results}} is set.

An everyday comparison. Think of a choir that sings one long chord. In a column split, each singer sings different notes of the chord; together they give the full chord. In a row split, every singer sings the same note at part of the volume. The hall adds the voices into one loud note. The comparison stops here. A hall adds the voices for free. On GPUs, the sum is an all-reduce over the links between the GPUs, and it costs time in every layer.

The picture

Colour marks the KV head. A query head always lands on a rank that also holds the KV head it reads. So attention needs no data from other ranks; only o_proj adds the results.

In the code

Step 1: LinearBase resolves the quantize method

  1. Lines 290-296. Without a quantization config the method is UnquantizedLinearMethod. Else resolve_quant_method(quant_config, self, prefix=prefix) asks the config; it must return a method, or the constructor raises ValueError. The page {{link concepts/quantization-plugins}} explains the methods.
  2. Lines 299-309. disable_tp=True makes the layer act as if TP were 1 (rank 0 of size 1). Else the rank and size come from the TP group, or from explicit arguments.

LinearBase is a PluggableLayer, so a plugin can replace a whole layer class by its registered name, for example column_parallel_linear ({{cite vllm/model_executor/layers/linear.py:434-436}}; {{link concepts/custom-ops}}). The bare LinearBase creates no weights; each subclass calls quant_method.create_weights() with its own sizes.

Step 2: ReplicatedLinear: no split

A {{term replicated-linear}} layer makes the full weight on every rank: create_weights(self, input_size, [output_size], input_size, output_size, ...) ({{cite vllm/model_executor/layers/linear.py:379-387}}). Its loader copies the whole tensor after a size check ({{cite vllm/model_executor/layers/linear.py:404-412}}), and its forward needs no communication ({{cite vllm/model_executor/layers/linear.py:414-425}}). 62 model files use it (git grep at this commit). An example is the score head that as_seq_cls_model adds, with one output per class label ({{cite vllm/model_executor/models/adapters.py:365-372}}).

Step 3: ColumnParallelLinear: split the outputs

  1. Line 623. The quantize method multiplies the full input [T, in] with the local weight. The result is [T, out / tp_size].
  2. Lines 625-629. Only with gather_output=True and TP > 1 does the layer call tensor_model_parallel_all_gather. The default is False ({{cite vllm/model_executor/layers/linear.py:473}}), because a row-parallel layer usually comes next.

divide() asserts that the size divides by TP; a wrong size stops the build with an AssertionError ({{cite vllm/distributed/utils.py:51-55}}, {{cite vllm/distributed/utils.py:122-126}}).

Step 4: MergedColumnParallelLinear: several outputs in one GEMM

MergedColumnParallelLinear(input_size, output_sizes) stacks several column-parallel matrices, for example gate and up with output_sizes=[14336, 14336] ({{cite vllm/model_executor/models/llama.py:95-102}}). Each part must divide by TP, and each part is split on its own ({{cite vllm/model_executor/layers/linear.py:727-731}}). So a rank holds [gate slice; up slice], not a slice of [gate; up]. This is what lets SiluAndMul work locally.

The shard id is an integer (0 for gate, 1 for up) or a tuple of consecutive ids. None means that the checkpoint already stores the tensor merged ({{cite vllm/model_executor/layers/linear.py:745-770}}).

Step 5: QKVParallelLinear: split by heads

  1. Line 1065. The query heads must divide by TP.
  2. Lines 1066-1068. When TP is at least the number of KV heads, each rank gets one KV head, and num_kv_head_replicas = tp_size / total_num_kv_heads ranks share it. divide() asserts that TP is a multiple of the KV head count.
  3. Lines 1069-1071. Else the KV heads are split, with no copies.
  4. Lines 1073-1077. output_sizes are the sizes across all ranks, including copies: num_kv_heads × head_size × tp_size. With TP = 16 and 8 KV heads, the "total" K size is 16 × 128, twice the 8 × 128 of the checkpoint.

The parameter of a rank is [q | k | v] along dimension 0. The offsets are 0, num_heads × head_size and (num_heads + num_kv_heads) × head_size ({{cite vllm/model_executor/layers/linear.py:1101-1117}}). When it loads, the q part takes slice number tp_rank of the checkpoint tensor; k and v take slice number tp_rank // num_kv_head_replicas ({{cite vllm/model_executor/parameter.py:191-195}}). The page {{link concepts/weight-loading}} follows one tensor through this code.

The model splits the GEMM output with the same per-rank sizes: qkv.split([q_size, kv_size, kv_size], dim=-1) ({{cite vllm/model_executor/models/llama.py:229-230}}). QKVParallelLinear always uses gather_output=False ({{cite vllm/model_executor/layers/linear.py:1084}}).

Step 6: RowParallelLinear: split the inputs, add the outputs

  1. Lines 1789-1795. With input_is_parallel=True (the default) the input is already this rank's slice, [T, in / tp_size]. Else the layer splits the last dimension and keeps its part.
  2. Line 1800. Only rank 0 adds the bias; with TP ranks adding it, the all-reduce would add it TP times.
  3. Lines 1803-1806. With reduce_results=True (the default) and TP > 1, the layer all-reduces the partial sums [T, out]. With False, the caller must reduce later, so a bias is then not allowed unless skip_bias_add is set ({{cite vllm/model_executor/layers/linear.py:1736-1740}}).

The per-rank sizes are the reverse of the column case: input_size / tp_size and the full output ({{cite vllm/model_executor/layers/linear.py:1692-1696}}). The bias is not split ({{cite vllm/model_executor/layers/linear.py:1742-1745}}).

Step 7: VocabParallelEmbedding and ParallelLMHead

The embedding splits the vocabulary rows across the ranks. First it applies {{term vocab-padding}}: the vocabulary is rounded up to a multiple of padding_size, 64 by default ({{cite vllm/model_executor/layers/vocab_parallel_embedding.py:36}}, {{cite vllm/model_executor/layers/vocab_parallel_embedding.py:95-97}}, {{cite vllm/model_executor/layers/vocab_parallel_embedding.py:286-291}}). Each rank holds padded_vocab / tp_size rows ({{cite vllm/model_executor/layers/vocab_parallel_embedding.py:304-306}}).

  1. Lines 542-550. get_masked_input_and_mask shifts each token id into the local row range and marks ids that other ranks own. On CUDA with an unquantized weight, a fused kernel does this instead (lines 527-536).
  2. Line 557. Rows for ids of other ranks become zero.
  3. Lines 558-563. The all-reduce adds the ranks: exactly one rank gives a non-zero row for each token, so the sum is the embedding.

ParallelLMHead has the same weight layout, but its forward raises: the weight is used by LogitsProcessor ({{cite vllm/model_executor/layers/vocab_parallel_embedding.py:640-642}}). LogitsProcessor multiplies the hidden states with the local rows, gathers the vocabulary slices across the TP group, and cuts off the padding ({{cite vllm/model_executor/layers/logits_processor.py:180-199}}). It uses an all-gather: Platform.use_all_gather() returns True, and no built-in platform overrides it ({{cite vllm/platforms/interface.py:1275-1278}}). tie_weights makes the head use the embedding's weight object ({{cite vllm/model_executor/layers/vocab_parallel_embedding.py:88-92}}).

Step 8: the collectives and the communicator

The layers call two small functions. Both use the TP group of this process:

GroupCoordinator.all_reduce returns the input unchanged when the group has one rank. On CUDA, ROCm, XPU and TPU it calls the registered op torch.ops.vllm.all_reduce, so torch.compile sees one opaque op. Other platforms call the device communicator directly ({{cite vllm/distributed/parallel_state.py:740-746}}, {{cite vllm/distributed/parallel_state.py:571-573}}, for example {{cite vllm/platforms/cuda.py:708-709}}). The CUDA communicator then picks one of several all-reduce implementations, such as custom all-reduce, symmetric-memory NCCL or plain NCCL ({{cite vllm/distributed/device_communicators/cuda_communicator.py:362-446}}). The page {{link concepts/distributed-groups}} explains the groups and the communicators.

vLLM has no sequence-parallel or async-TP pass in vllm/compilation/ at this commit. The one TP fusion pass is fuse_allreduce_rms: it fuses the all-reduce with the next RMSNorm through FlashInfer ({{cite vllm/config/compilation.py:136-137}}). At optimization level O2 it is on only with TP > 1, CUDA, FlashInfer and a Hopper or Blackwell GPU, or AITER on ROCm ({{cite vllm/config/vllm.py:178-202}}, {{cite vllm/config/vllm.py:296-301}}). The page {{link concepts/compile-and-cuda-graphs}} explains the passes.

Read the qkv_proj column: (num_heads + 2 × num_kv_heads) × 128. At TP = 8 that is (4 + 2) × 128 = 768. At TP = 16 it is (2 + 2) × 128 = 512: the query part halves again, but the KV part cannot get smaller than one head. The MLP column for TP = 2 is the table of {{link learn/tp-pp-in-practice}}.

The class docstring gives an example with an original vocabulary of 1,010, 16 LoRA tokens and padding 64 ({{cite vllm/model_executor/layers/vocab_parallel_embedding.py:216-233}}). Without LoRA tokens it goes like this:

  1. pad_vocab_size(1010, 64) = 1,024. With TP = 2, each rank holds 512 rows.
  2. Rank 0 owns ids 0-511. Rank 1 owns ids 512-1009 in its rows 0-497; rows 498-511 are padding.
  3. The loader copies 498 rows into rank 1 and fills the rest with zeros ({{cite vllm/model_executor/layers/vocab_parallel_embedding.py:518-520}}).
  4. Token id 700 in a batch: rank 0 masks it (out of range) and returns a zero row. Rank 1 looks up row 700 − 512 = 188. The all-reduce gives the row of id 700 on both ranks.

For Llama-3 the vocabulary is 128,256, which is 2,004 × 64, so there is no padding. With TP = 2 each rank holds 64,128 rows: [64128, 4096], about 501 MiB in BF16 (derived). The LM head after the gather gives [R, 128256] logits; the slice [..., :org_vocab_size] removes padding columns when there are any ({{cite vllm/model_executor/layers/logits_processor.py:196-198}}).

What can go wrong

  • A TP size that does not fit the model. Start-up checks the query heads first ({{cite vllm/config/model.py:1559-1564}}). Other sizes fail later, while the layers are built, in divide() or an assertion. Examples are the MLP intermediate size, or a KV head count that does not fit TP ({{cite vllm/model_executor/layers/linear.py:731}}, {{cite vllm/model_executor/layers/linear.py:1066-1071}}).
  • KV replication eats KV cache. With TP larger than the KV head count, each rank stores one full KV head, so the cluster stores copies ({{cite vllm/model_executor/layers/linear.py:1066-1068}}). TP = 16 for an 8-KV-head model gives twice the KV bytes of TP = 8 in total.
  • A custom layer without a reduce. A model that sets reduce_results=False must call the all-reduce itself. Without it, each rank keeps a partial sum, and the output is wrong with no error (derived) ({{cite vllm/model_executor/layers/linear.py:1803-1806}}).
  • TP across nodes. Every decoder layer has two all-reduces on the critical path ({{link learn/tp-pp-in-practice}}). Over a slow network, prefer PP or DP across nodes.

Why it matters. These layer classes decide the memory per GPU, the number of collectives per step and the rules for valid TP sizes. When you know them, you can predict the per-GPU shapes of any model and read the errors of a wrong TP size.

Which flag makes a RowParallelLinear add the partial sums of the ranks, and what is its default?

reduce_results, default True ({{cite vllm/model_executor/layers/linear.py:1684}}). The all-reduce runs only when TP > 1 ({{cite vllm/model_executor/layers/linear.py:1803-1806}}).

 Why does MergedColumnParallelLinear split gate and up separately instead of splitting the stacked matrix once?

So each rank holds matching slices of gate and up, and SiluAndMul can combine them without data from other ranks. The loader puts part i at offset sum(output_sizes[:i]) / tp_size ({{cite vllm/model_executor/layers/linear.py:965-983}}).

 Why does only rank 0 add the bias in RowParallelLinear.forward?

The all-reduce sums the outputs of all ranks. If every rank added the bias, the sum would contain it TP times ({{cite vllm/model_executor/layers/linear.py:1798-1801}}).

 A model has 32 query heads and 8 KV heads. What is the shape of qkv_proj.weight on each rank with TP = 16, and which checkpoint rows of v_proj does rank 9 load?

num_heads = 2, num_kv_heads = 1, replicas = 2 ({{cite vllm/model_executor/layers/linear.py:1065-1068}}), so the weight is [(2 + 1 + 1) × 128, 4096] = [512, 4096]. For v the slice index is 9 // 2 = 4 ({{cite vllm/model_executor/parameter.py:191}}), so rank 9 loads rows 512-639 (KV head 4).

 With TP = 2, token id 70,000 enters the embedding of a Llama-3 model (vocabulary 128,256). What does each rank compute?

Each rank holds 64,128 rows. Rank 0 owns ids 0-64,127, so it masks the id and returns a zero row. Rank 1 looks up local row 70,000 − 64,128 = 5,872. The all-reduce sums both rows, so both ranks get the embedding of id 70,000 ({{cite vllm/model_executor/layers/vocab_parallel_embedding.py:541-563}}).
