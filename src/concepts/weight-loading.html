The idea

A checkpoint is a set of named tensors in safetensors files, and loading copies each tensor into the matching model parameter ({{deepinfer concepts/weight-loading | Weight loading}}). The page {{link learn/hf-checkpoints}} shows which files vLLM downloads and keeps. This page follows the tensors from the files into the parameters of each GPU.

vLLM loads the weights in six steps, in every {{term worker}}:

  1. Pick a loader. The {{term load-format}} (--load-format, default auto) selects a {{term model-loader}} class. For auto it is DefaultModelLoader.
  2. Build an empty model. The loader builds the model class on the GPU. Each tensor-parallel layer makes parameters of its per-rank shape, with no values yet.
  3. Stream the tensors. An iterator opens the files one by one and gives (name, tensor) pairs. In the default path, the tensors stay on the CPU.
  4. Map the names. The model's load_weights() uses an {{term auto-weights-loader}}. A {{term weights-mapper}} renames checkpoint names to vLLM names, for example q_proj to qkv_proj with the shard id "q".
  5. Copy the slice. The target parameter has a {{term weight-loader}}. It cuts the part of the tensor that this rank owns and copies it into the right rows of the parameter.
  6. Post-process. Each layer's quantization method can repack or quantize its weights once, in process_weights_after_loading.

An everyday comparison. Think of the branches of a library that all get the same delivery list. Each branch reads every line of the list. For each book, the list gives the shelf name in the publisher's words, and a branch translates it into its own shelf names. Some books go into a shared box with three marked parts, such as Q, K and V. Each branch keeps only the pages for its own readers. The comparison stops here. In vLLM, nobody sends a branch its part: every GPU walks the full list itself, and the parameter cuts its slice.

In the code

Step 1: the load format picks the loader

get_model_loader() looks up load_config.load_format in this table and raises ValueError for an unknown name ({{cite vllm/model_executor/model_loader/__init__.py:123-128}}). The field default is "auto", and a validator lower-cases the value ({{cite vllm/config/load.py:30}}, {{cite vllm/config/load.py:136-138}}). EngineArgs copies this default without a change ({{cite vllm/engine/arg_utils.py:509}}). One later override exists: for a model in object storage (S3, GCS, Azure), auto becomes runai_streamer ({{cite vllm/config/vllm.py:2754-2762}}). A plugin can add a format with register_model_loader ({{link concepts/engine-hooks}}).

Model Runner V2 calls the loader in load_model() ({{cite vllm/v1/worker/gpu/model_runner.py:398-406}}). It runs in every worker: with TP = 2, two processes do all the steps below at the same time.

Step 2: build the model with empty parameters

  1. Lines 73-74. The default dtype is the model dtype, and the default device is the GPU of this worker. So every torch.empty in a layer constructor makes a GPU tensor of the right dtype.
  2. Lines 76-80. create_model() calls initialize_model(), which builds the class with vllm_config and prefix ({{link concepts/model-definition}}). The log line "Initializing model took ... seconds" measures this part.
  3. Line 88. self.load_weights() is the loader's method; for the default loader it streams the files (Step 3).
  4. Lines 106-109. Online quantization finishes first; then process_weights_after_loading() runs for every layer (Step 6).

The layer constructors do the per-rank sizing. UnquantizedLinearMethod.create_weights() makes torch.empty(sum(output_partition_sizes), input_size_per_partition) ({{cite vllm/model_executor/layers/linear.py:178-205}}). The page {{link concepts/tp-layers}} gives these sizes for each layer class.

Step 3: choose the files and stream the tensors

DefaultModelLoader._prepare_weights() finds, downloads and filters the files ({{cite vllm/model_executor/model_loader/default_loader.py:147-263}}); {{link learn/hf-checkpoints}} explains that part. Then _get_weights_iterator() picks an iterator by format ({{cite vllm/model_executor/model_loader/default_loader.py:301-365}}). The usual case is safetensors_weights_iterator():

  • Order. The files are sorted by a natural sort key, so ...-00002-of-... comes before ...-00010-of-... ({{cite vllm/model_executor/model_loader/weight_utils.py:1134}}).
  • Strategies. --safetensors-load-strategy is None by default. eager reads the whole file into CPU memory first; torchao rebuilds torchao tensors ({{cite vllm/model_executor/model_loader/weight_utils.py:1207-1242}}).
  • Prefetch. With the default None, vLLM prefetches the files into the page cache only on NFS or Lustre. They must also fit in 90% of the free RAM ({{cite vllm/model_executor/model_loader/weight_utils.py:1136-1155}}). prefetch forces it. Each process prefetches a different part of the files, sorted_files[rank::world_size]. Rank and world size are the global values of torch.distributed, not the TP values ({{cite vllm/model_executor/model_loader/weight_utils.py:1051-1057}}).
  • PyTorch files. For .bin and .pt files, pt_weights_iterator() calls torch.load(..., weights_only=True) on each file and yields its items ({{cite vllm/model_executor/model_loader/weight_utils.py:1479-1495}}).
  • Many threads. --model-loader-extra-config '{"enable_multithread_load": true}' selects the multi-thread iterators, with 8 threads by default ({{cite vllm/model_executor/model_loader/default_loader.py:58-59}}, {{cite vllm/model_executor/model_loader/default_loader.py:329-336}}).

The loader then calls model.load_weights() with the iterator, and logs "Loading weights took ... seconds" ({{cite vllm/model_executor/model_loader/default_loader.py:503-509}}).

Step 4: map the names (WeightsMapper and AutoWeightsLoader)

Llama has two load_weights methods. The outer class makes an AutoWeightsLoader without a mapper ({{cite vllm/model_executor/models/llama.py:559-561}}). The loader groups the names by their first part and finds the child model. That child has its own load_weights, so the loader gives it the names without model. ({{cite vllm/model_executor/models/utils.py:387-400}}). LlamaModel.load_weights uses the mapper:

The mapper has six kinds of rule: orig_to_new_renaming, _regex, _substr, _stacked, _prefix and _suffix, applied in this order. A regex, substring, prefix or suffix rule that maps to None drops the tensor ({{cite vllm/model_executor/models/utils.py:48-61}}, {{cite vllm/model_executor/models/utils.py:108-145}}). AutoWeightsLoader.load_weights() adds more mappers. With a quantization config, it adds the config's mappers for KV cache scale names and checkpoint names. It always adds a rule that drops old rotary tables ({{cite vllm/model_executor/models/utils.py:460-473}}).

Then the loader walks the module tree:

  1. Line 409. _groupby_prefix() splits each name at the first dot: layers.0.self_attn.qkv_proj.weight becomes layers and 0.self_attn.qkv_proj.weight.
  2. Lines 412-415. A child module: recurse. For QKVParallelLinear the recursion ends early, because that layer has its own load_weights (line 388).
  3. Lines 416-424. A parameter: _load_param() calls param.weight_loader, or default_weight_loader when the parameter has none ({{cite vllm/model_executor/models/utils.py:340-341}}).

QKVParallelLinear.load_weights reads the shard id from the tensor and calls param.weight_loader(param, loaded_weight, shard_id) ({{cite vllm/model_executor/layers/linear.py:1339-1354}}). MergedColumnParallelLinear has the same method for the integer shard ids of gate_up_proj ({{cite vllm/model_executor/layers/linear.py:985-1000}}).

Step 5: the weight loader of each parameter

A linear layer chooses one of two loader families when it is built. If the class name of its quantization method is in WEIGHT_LOADER_V2_SUPPORTED, it uses weight_loader_v2; else weight_loader ({{cite vllm/model_executor/layers/linear.py:530-534}}). UnquantizedLinearMethod is in the list, so a BF16 model uses v2 ({{cite vllm/model_executor/layers/linear.py:50-64}}). The v2 loaders give the work to the parameter class:

The shard size is the size of the parameter on this rank, so the loader needs no TP arithmetic of its own. ModelWeightParameter inherits both methods, and the layer calls the one that fits ({{cite vllm/model_executor/parameter.py:229-234}}). The v1 loaders do the same cut with getattr(param, "output_dim") and "input_dim" ({{cite vllm/model_executor/layers/linear.py:589-606}}, {{cite vllm/model_executor/layers/linear.py:1758-1774}}).

For a stacked parameter, the loader first selects the part of the parameter, then the part of the tensor:

  1. Line 191. For q, the slice index is the TP rank. For k and v it is tp_rank // num_kv_head_replicas; num_heads here carries the replica count ({{cite vllm/model_executor/layers/linear.py:1203-1209}}).
  2. Line 192. The part of the parameter: offset and size from the head counts of this rank ({{cite vllm/model_executor/layers/linear.py:1101-1117}}).
  3. Lines 193-195. The part of the checkpoint tensor. Then an assertion and one copy.

Other parameters:

  • Embedding and LM head. VocabParallelEmbedding.weight_loader cuts rows org_vocab_start_index to org_vocab_end_index, and fills the padding rows with zeros ({{cite vllm/model_executor/layers/vocab_parallel_embedding.py:497-520}}).
  • Norm weights. RMSNorm.weight is a plain nn.Parameter without a loader ({{cite vllm/model_executor/layers/layernorm.py:65-67}}). default_weight_loader checks the shape and copies the full tensor on every rank ({{cite vllm/model_executor/model_loader/weight_utils.py:1529-1547}}).

Step 7: quantized weights

For a quantized checkpoint, the layer's quantization method makes the parameters in create_weights() ({{link concepts/quantization-plugins}}). FP8, for example, registers an FP8 weight and a weight_scale (or weight_scale_inv for block scales), each with the layer's weight loader ({{cite vllm/model_executor/layers/quantization/fp8.py:312-339}}). The checkpoint has tensors with the same names, so the mapping and slicing above work for them too. A per-tensor scale of a stacked layer has one slot per part (q, k, v). PerTensorScaleParameter copies each checkpoint scale into the slot of its shard id ({{cite vllm/model_executor/parameter.py:253-301}}); the v1 loaders use adjust_scalar_to_fused_array for the same job ({{cite vllm/model_executor/layers/linear.py:97-121}}).

After all tensors are copied, process_weights_after_loading() visits every module with a quantization method and calls its post-processing ({{cite vllm/model_executor/model_loader/utils.py:157-196}}). FP8 with per-tensor scales, for example, re-quantizes the parts of a stacked layer to one scale, the maximum of their scales, and transposes the weight. This happens only without block scales and without the Marlin kernel ({{cite vllm/model_executor/layers/quantization/fp8.py:372-409}}, {{cite vllm/model_executor/layers/quantization/utils/fp8_utils.py:1454-1479}}). The page {{link learn/quantized-checkpoints}} explains the formats.

What can go wrong

The tree walk raises "There is no module or parameter named ..." for every name it cannot place ({{cite vllm/model_executor/models/utils.py:442-448}}). By default the loader ignores only .bias tensors and the suffixes of the quantization config, and the mapper drops old rotary tables. A fine-tuned checkpoint with extra tensors needs a mapper rule that maps them to None.
  • A shape mismatch. The weight loaders assert that the slice and the parameter have the same shape ({{cite vllm/model_executor/parameter.py:197}}, {{cite vllm/model_executor/model_loader/weight_utils.py:1538-1541}}). A checkpoint for another config, or a wrong --hf-overrides, fails here.
  • Missing weights. An unquantized model raises "Following weights were not initialized from checkpoint" for an empty norm weight, or another parameter outside quantize-method modules ({{cite vllm/model_executor/model_loader/default_loader.py:533-572}}). A missing linear weight gives no error here (derived).
  • A dtype mismatch. A tensor with another dtype is converted by copy_, and the loader logs a warning ({{cite vllm/model_executor/models/utils.py:324-339}}).
  • An unknown format. --load-format gguf raises "Load format `gguf` is not supported" ({{cite vllm/model_executor/model_loader/__init__.py:126-127}}).
  • Slow loads from network storage. On NFS, a large model that does not fit in 90% of the free RAM is not prefetched, and vLLM logs a warning ({{cite vllm/model_executor/model_loader/weight_utils.py:1156-1165}}). Try --safetensors-load-strategy eager or prefetch, or a pre-sharded checkpoint.

Why it matters. Weight loading is often the longest part of start-up, and its errors are the first errors of a new model or a new checkpoint. When you know the path from file to parameter, you can read the log timers, fix name and shape errors, and choose a faster format.

Which loader class serves the default --load-format auto, and which iterator does it use for a safetensors checkpoint?

DefaultModelLoader ({{cite vllm/model_executor/model_loader/__init__.py:51}}). Without the multi-thread option it uses safetensors_weights_iterator ({{cite vllm/model_executor/model_loader/default_loader.py:337-349}}).

 How does QKVParallelLinear know that a tensor is the K part?

Llama's mapper renames .k_proj to .qkv_proj with the shard id "k" ({{cite vllm/model_executor/models/llama.py:351-353}}). WeightsMapper.apply() stores it as tensor.shard_id ({{cite vllm/model_executor/models/utils.py:158-164}}), and QKVParallelLinear.load_weights reads it back ({{cite vllm/model_executor/layers/linear.py:1342-1354}}).

 For a BF16 model with TP = 4, which dimension of o_proj.weight does each rank cut, and at which offset?

o_proj is row-parallel, so the loader cuts input_dim = 1 at tp_rank × shard_size ({{cite vllm/model_executor/parameter.py:216-220}}). For Llama-3-8B, the parameter is [4096, 1024], so rank 2 takes columns 2048-3071.

 A model has 8 KV heads and runs with TP = 16. Which rows of k_proj.weight does rank 5 load? Why does rank 4 load the same rows?

num_kv_heads is 1 and num_kv_head_replicas is 2 ({{cite vllm/model_executor/layers/linear.py:1066-1068}}). The slice index for k is tp_rank // num_heads, where num_heads carries the replica count: 5 // 2 = 2 ({{cite vllm/model_executor/parameter.py:191}}, {{cite vllm/model_executor/layers/linear.py:1203-1205}}). With a slice size of 128 rows, rank 5 loads rows 256-383 (KV head 2). Rank 4 gives 4 // 2 = 2 too, so both ranks hold a copy of KV head 2.

 A model runs with PP = 2. What happens to the checkpoint tensors of layers 16-31 on stage 0?

The iterator still reads every tensor of every file, because it calls get_tensor for each name ({{cite vllm/model_executor/model_loader/weight_utils.py:1243-1249}}). The tree walk reaches PPMissingLayer objects for those layers and returns without a copy ({{cite vllm/model_executor/models/utils.py:382-383}}). Hand-written loaders use is_pp_missing_parameter() for the same skip ({{cite vllm/model_executor/models/minicpm.py:524-525}}).
