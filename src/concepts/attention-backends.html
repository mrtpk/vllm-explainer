--- title: Attention backends: backend, metadata builder and implementation nav_title: Attention backends level: Advanced prerequisites: concepts/attention-backend-selection, concepts/forward-context, concepts/hybrid-kv-cache related: code/v1-attention-backend, concepts/attention-backend-selection, concepts/forward-context, concepts/compile-and-cuda-graphs, concepts/model-runner, concepts/hybrid-kv-cache, code/model-executor-layers-attention-attention, tours/forward-pass summary: An attention backend is three classes. The backend class describes what it supports, the metadata builder turns the common batch description of a KV cache group into backend metadata once per step, and the implementation writes the KV cache and runs the kernel for one layer. The builders also report how much CUDA graph capture they allow. --- An attention backend is three classes: a description, a metadata builder that runs once per step and group, and an implementation that runs per layer.

The idea

Attention computes softmax(QKT)V over the cached keys and values of each request ({{deepinfer learn/attention | Attention basics}}). vLLM has many {{term attention-backend | attention backends}}: FlashAttention, FlashInfer, Triton, FlashMLA and more. Which one a layer gets is decided when the model is built ({{link concepts/attention-backend-selection}}). This page explains what a backend is made of, and how vLLM calls it each step. Kernel code is out of scope.

Each backend has three classes, with three lifetimes:

  • AttentionBackend, a class with only static and class methods. It names the other two classes and answers questions: which head sizes, data types, block sizes and features it supports.
  • AttentionMetadataBuilder, the {{term metadata-builder}}. The runner makes one per group of layers at start-up. Each step it turns the {{term common-attention-metadata}} into the backend's own {{term attention-metadata}}.
  • AttentionImpl, one object per attention layer, made in the layer's constructor. Each step it writes the new keys and values into the KV cache and runs the kernel.

The split saves work. Metadata depends on the batch, not on the layer. So a 32-layer model builds it once per group and step, and all 32 layers use the same object.

An everyday comparison. Think of a train line. The timetable office (the builder) prints one timetable for all trains each day. Each driver (the impl) reads the same timetable and drives one train. The rule book (the backend class) says which trains and tracks the line can use. The comparison stops here: a builder can also say that a CUDA graph cannot replay some batches. Then vLLM changes the whole run plan at start-up.

Step 2: one impl per layer

The Attention constructor makes the impl right after the backend is selected ({{cite vllm/model_executor/layers/attention/attention.py:419-432}}). The impl gets the per-rank head counts, the head size, the scale, the sliding window and the KV cache data type. The abstract forward has this signature:

query is [num_tokens, num_heads, head_size]; the layer reshapes q, k and v before the op ({{cite vllm/model_executor/layers/attention/attention.py:533-540}}). The impl writes into output; it does not return a new tensor. Some backends set forward_includes_kv_cache_update = False. They also implement do_kv_cache_update(layer, key, value, kv_cache, slot_mapping), which writes the keys and values of the new tokens into their slots. For FlashAttention it is a scatter by slot ({{cite vllm/v1/attention/backends/flash_attn.py:1430-1464}}).

In the profile run there is no metadata. FlashAttention then only fills the output with zeros ({{cite vllm/v1/attention/backends/flash_attn.py:1224-1226}}).

Step 3: attention groups and builders, at start-up

When the KV cache is initialized, init_attn_backend groups the layers. Inside each {{term kv-cache-group}}, layers with the same backend class, the same KV cache spec and the same number of query heads form one AttentionGroup:

Then each group makes its builders. It passes the KV cache spec (with the kernel block size), the layer names, the config and the device ({{cite vllm/v1/worker/gpu/attn_utils.py:291-300}}, {{cite vllm/v1/worker/utils.py:330-339}}). Normally there is one builder per group; with dual-batch overlap there is one per micro-batch, because "some builders keep the prepared metadata on themselves" ({{cite vllm/v1/worker/gpu/attn_utils.py:296-299}}).

Step 5: builder.build, and one metadata object for many layers

For each attention group of the KV cache group, the runner calls the builder and stores the result under every layer name of the group:

  1. Lines 553-560. Mamba groups with the same spec and builder reuse the first metadata and only swap the block table, through update_block_table.
  2. Lines 561-564. During CUDA graph capture, build_for_cudagraph_capture is called instead. Its default just calls build ({{cite vllm/v1/attention/backend.py:720-729}}).
  3. Lines 574-576. The normal path: AttentionGroup.build_metadata calls build(common_prefix_len=0, common_attn_metadata) ({{cite vllm/v1/worker/utils.py:341-352}}). The common_prefix_len argument is "Deprecated and always 0" ({{cite vllm/v1/attention/backend.py:686-704}}).
  4. Lines 579-580. The same object goes under every layer name of the group.

If the backend's kernel uses smaller blocks than the KV cache manager, the attention group first rewrites the block table into kernel blocks ({{cite vllm/v1/worker/utils.py:368-378}}).

Step 6: CUDA graph support, and how it lowers the mode

A builder reports how much {{term cuda-graph}} capture it allows, with {{term cudagraph-support | AttentionCGSupport}}:

The default is NEVER ({{cite vllm/v1/attention/backend.py:593-595}}). The runner asks every group and keeps the weakest answer ({{cite vllm/v1/worker/gpu/attn_utils.py:314-341}}). Then resolve_cudagraph_mode_and_sizes may lower the configured mode ({{cite vllm/v1/worker/gpu/model_runner.py:754-763}}):

  1. FULL for mixed batches, but support below ALWAYS. NEVER raises ValueError. Otherwise the mode becomes FULL_AND_PIECEWISE if attention is a splitting op, else FULL_DECODE_ONLY ({{cite vllm/config/compilation.py:1394-1418}}).
  2. FULL decode graphs, but support NEVER. The mode becomes PIECEWISE if attention is compiled piecewise, else NONE ({{cite vllm/config/compilation.py:1421-1445}}).
  3. FULL decode graphs with speculative decoding (decode query length above 1), but support below UNIFORM_BATCH. The mode becomes PIECEWISE or NONE in the same way ({{cite vllm/config/compilation.py:1448-1465}}).
  4. Last check: a mode with FULL graphs and support NEVER raises ({{cite vllm/config/compilation.py:1482-1493}}).

Each change logs a warning that names the backend. {{link concepts/compile-and-cuda-graphs}} explains the modes.

Step 7: the MLA variant

Models with multi-head latent attention, such as DeepSeek-V3, use the layer MLAAttention and an impl based on MLAAttentionImpl. Its constructor gets the MLA dimensions and the kv_b_proj layer ({{cite vllm/v1/attention/backend.py:1034-1064}}). The impl has two paths instead of one forward:

  • forward_mqa for decode tokens, over the compressed latent cache ({{cite vllm/v1/attention/backend.py:1080-1089}});
  • forward_mha for prefill tokens, "MHA-style" ({{cite vllm/v1/attention/backend.py:1066-1079}}).

The layer sends the first num_decode_tokens rows to forward_mqa and the rest to forward_mha ({{cite vllm/model_executor/layers/attention/mla_attention.py:984-985}}, {{cite vllm/model_executor/layers/attention/mla_attention.py:1017-1020}}). The MLA builder finds the split with split_decodes_and_prefills ({{cite vllm/model_executor/layers/attention/mla_attention.py:2605-2612}}). This is why Model Runner V2 puts the decodes first in the batch ({{cite vllm/v1/worker/gpu/model_runner.py:2476-2483}}). The cache write is one shared method, do_kv_cache_update, which calls the concat_and_cache_mla op ({{cite vllm/v1/attention/backend.py:1108-1128}}). The custom ops are unified_mla_kv_cache_update and unified_mla_attention_with_output ({{cite vllm/model_executor/layers/attention/mla_attention.py:1475-1479}}, {{cite vllm/model_executor/layers/attention/mla_attention.py:1524-1530}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Older code and many guides use AttentionBackend.get_kv_cache_shape(). At this commit the base class has no such method; only one MLA backend still defines it (git grep, {{cite vllm/v1/attention/backends/mla/flashinfer_mla_sparse_sm90.py:227}}). The shape now comes from the KV cache spec and a layout descriptor:

  1. Logical shape per layer. [B, H, N, C]: blocks, head slots, states (tokens) per block, and C bytes of content ({{cite vllm/v1/kv_cache_interface.py:345-361}}). For normal attention, C is (head_size + head_size_v) × dtype bytes: key and value of one token and head ({{cite vllm/v1/kv_cache_interface.py:570-575}}).
  2. Physical order. A KVCacheLayout member is a permutation of [L, B, H, N, C], where L is the layer inside a shared allocation ({{cite vllm/v1/kv_cache_layout.py:11-28}}).
  3. Choice. The engine core resolves one layout for the whole model. A backend lists the layouts it can read with supported_kv_cache_layouts(); with no list from any backend, the default preference starts with LBNHC ({{cite vllm/v1/attention/backends/utils.py:228-235}}, {{cite vllm/v1/attention/backends/utils.py:240-276}}). VLLM_KV_CACHE_LAYOUT can force a layout that every backend supports ({{cite vllm/v1/attention/backends/utils.py:361-367}}).
  4. Views. allocate_kv_cache allocates one int8 buffer and makes a strided view per layer, then casts it to the KV dtype ({{cite vllm/v1/worker/utils.py:564-625}}, {{cite vllm/v1/kv_cache_interface.py:461-466}}).

FlashAttention, traced. FlashAttention declares no layout list (it does not override the method), so a model with only FlashAttention layers gets LBNHC. Its forward docstring gives the view: [num_blocks, num_kv_heads, block_size, 2 * head_size] ({{cite vllm/v1/attention/backends/flash_attn.py:1199-1200}}). The cache write transposes it to (B, N, H, 2D) and splits the last dimension into a key half and a value half ({{cite vllm/v1/attention/backends/flash_attn.py:1445-1446}}). With LBNHC, the N axis is outside the H axis in memory (derived). FlashInfer on compute capability 10 lists LBHNC first, because "the trtllm-gen kernels consume head-major block interiors" ({{cite vllm/v1/attention/backends/flashinfer.py:700-706}}).

Worked example: Llama-3-8B with TP = 1, BF16 and block size 16. The view of one layer is [num_blocks, 8, 16, 256] bfloat16. So one block of one layer is 8 × 16 × 256 × 2 = 65,536 bytes (derived from the formula above). {{link concepts/hybrid-kv-cache}} explains page sizes across groups.

The builder copies most fields straight from the common metadata ({{cite vllm/v1/attention/backends/flash_attn.py:821-829}}). It adds backend-only fields, for example scheduler_metadata for ahead-of-time scheduling and the DCP context lengths. The fast_build flag "disables AOT scheduling, used when there will be few iterations i.e. spec-decode" ({{cite vllm/v1/attention/backends/flash_attn.py:818-820}}). Its CUDA graph support is ALWAYS with FlashAttention 3 or 4 (or on XPU), else UNIFORM_BATCH ({{cite vllm/v1/attention/backends/flash_attn.py:612-621}}).

Example: Llama-3-8B on an H100 with FlashAttention 3 reports ALWAYS, so the default FULL_AND_PIECEWISE stays. With FlashInfer at UNIFORM_SINGLE_TOKEN_DECODE and EAGLE drafts (decode query length 1 + k), rule 3 of Step 6 lowers the mode to PIECEWISE (derived). The design document has a similar table ({{cite docs/design/cuda_graphs.md:173-187}}).
  • reorder_batch_threshold: the query length up to which the builder treats a request as a decode. _init_reorder_batch_threshold raises it to 1 + num_speculative_tokens for backends that run speculative verification as decodes ({{cite vllm/v1/attention/backend.py:658-684}}, {{cite vllm/v1/attention/backend.py:572-589}}).
  • update_block_table: reuse metadata with another block table; only when supports_update_block_table is true ({{cite vllm/v1/attention/backend.py:706-718}}).
  • build_for_drafting: metadata for a draft model, with fast_build=True ({{cite vllm/v1/attention/backend.py:731-751}}).
  • update_draft_decode_metadata: capture-safe update between draft steps, for the fused multi-step draft graph ({{cite vllm/v1/attention/backend.py:753-761}}, {{cite docs/design/model_runner_v2.md:194-200}}).
  • get_varlen_cudagraph_max_query_len: the largest per-request query length that a FULL graph of this builder can replay in a variable-length decode batch ({{cite vllm/v1/attention/backend.py:635-656}}).

What can go wrong

  • A backend with no CUDA graph support and -cc.cudagraph_mode=FULL. Start-up stops with "CUDAGraphMode.FULL is not supported with ... backend (support: NEVER); please try cudagraph_mode=PIECEWISE" ({{cite vllm/config/compilation.py:1400-1410}}).
  • Silent mode changes. A weaker backend lowers FULL_AND_PIECEWISE to PIECEWISE or NONE with only a warning. Decode then loses its full graph and gets slower. Look for "is not supported with" in the log.
  • Batch invariance. With VLLM_BATCH_INVARIANT=1, a backend without supports_batch_invariance() raises RuntimeError in init_attn_backend ({{cite vllm/v1/worker/gpu/attn_utils.py:235-242}}).
  • A layout that some backend cannot read. VLLM_KV_CACHE_LAYOUT outside the supported set raises ValueError; backends with no common layout raise too ({{cite vllm/v1/attention/backends/utils.py:361-367}}, {{cite vllm/v1/attention/backends/utils.py:271-276}}).
  • Fused output quantization on FlashAttention. Its forward raises NotImplementedError when it gets an output scale ({{cite vllm/v1/attention/backends/flash_attn.py:1219-1222}}).

Why it matters. A backend plugin implements these three classes. The builder decides the CPU cost of each step and whether decode can use a FULL CUDA graph; the impl decides the GPU cost. When a deployment is slower than expected, check which backend each layer got and which CUDA graph mode survived start-up.

How many FlashAttention metadata objects does Llama-3-8B build per step, and how many impl objects exist?

One metadata object per step: one KV cache group, one attention group, stored under all 32 layer names ({{cite vllm/v1/worker/gpu/attn_utils.py:579-580}}). There are 32 impl objects, one per Attention layer ({{cite vllm/model_executor/layers/attention/attention.py:419-432}}).

 Which class decides which CUDA graph modes are possible, and through which method?

The metadata builder, through get_cudagraph_support(), which returns an AttentionCGSupport ({{cite vllm/v1/attention/backend.py:626-633}}). The runner takes the minimum over all groups and passes it to resolve_cudagraph_mode_and_sizes ({{cite vllm/v1/worker/gpu/model_runner.py:754-763}}).

 What is in seq_lens of CommonAttentionMetadata for a decode request with 40 computed tokens?

41: computed tokens plus the 1 new query token. Model Runner V2 writes num_computed_tokens + query_len ({{cite vllm/v1/worker/gpu/input_batch.py:375-376}}), although the docstring says "computed tokens" ({{cite vllm/v1/attention/backend.py:401-402}}).

 A model runs FlashInfer with support UNIFORM_SINGLE_TOKEN_DECODE, with EAGLE and 3 speculative tokens, at the default O2. Which CUDA graph mode does it get, and why?

PIECEWISE. O2 sets FULL_AND_PIECEWISE, whose decode mode is FULL. The decode query length is 1 + 3 = 4 > 1, and the support is below UNIFORM_BATCH. Attention is a splitting op by default, so the mode becomes PIECEWISE ({{cite vllm/config/compilation.py:1448-1465}}).

 Where does FlashAttention write the new keys, and what memory layout does it see?

In do_kv_cache_update, called by the separate update op because forward_includes_kv_cache_update = False. It views the cache [B, H, N, 2D] as (B, N, H, 2D) and splits it into a key half and a value half. Then it scatters the new rows by slot mapping ({{cite vllm/v1/attention/backends/flash_attn.py:1430-1464}}).
