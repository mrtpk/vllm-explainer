The idea

The {{term scheduler}} lives in the {{term engine-core}} process. Once per {{term engine-step}}, it decides which requests run and how many of their tokens. DeepInfer Explained teaches the basics: continuous batching and chunked prefill ({{deepinfer learn/batching | Batching}}), and KV blocks and preemption ({{deepinfer learn/kv-cache | The KV cache}}). It also shows a scheduler with both ({{deepinfer concepts/scheduler | The scheduler}}). This page explains what vLLM does differently.

The vLLM scheduler has no prefill phase and no decode phase. Each request has two numbers: {{term num-computed-tokens}} (tokens whose KV values are in the cache) and its number of tokens (prompt plus output). The scheduler gives each request the difference, as far as the {{term token-budget}} allows. A new prompt asks for many tokens, so it gets a prefill. A request in the middle of its answer asks for one token, so it gets a decode. A long prompt that does not fit gets a part of it: that is {{term chunked-prefill}}. One rule covers all three cases.

Each call of schedule() has two passes. The first pass serves the {{term running-queue}}, from the front. The second pass starts requests from the {{term waiting-queue}}, but only if the first pass did not preempt anything. Each scheduled request also needs KV blocks. When the blocks run out, the scheduler takes away all the blocks of the last running request. That request must compute its tokens again later: this is {{term recompute-preemption}}. After the GPU step, update_from_output() appends the sampled tokens and finishes the requests that must stop.

An everyday comparison. Think of a print shop that can print 16 pages per hour. Each job asks for the pages that it still needs. The shop serves the jobs that it already started first, then new jobs. A job also needs paper trays (the KV blocks). When the trays run out, the shop takes all the trays of the newest job, and that job must start again later. The comparison stops here. In vLLM, a restarted request can often get some of its old work back from the prefix cache. Also, a print job does not make its own next input.

Try it yourself

The simulator follows these rules of the real code. It leaves out everything in the box above.

  1. The running pass goes first, from the front of self.running, while budget is left ({{cite vllm/v1/core/sched/scheduler.py:713-715}}).
  2. A request gets num_tokens - num_computed_tokens tokens, at most the rest of the budget ({{cite vllm/v1/core/sched/scheduler.py:759-768}}).
  3. A request needs ceil((num_computed_tokens + new) / block_size) blocks in total ({{cite vllm/v1/core/single_type_kv_cache_manager.py:214}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:401-402}}).
  4. If blocks are short, the scheduler preempts the last running request, and stops the pass if that was the request itself ({{cite vllm/v1/core/sched/scheduler.py:857-858}}, {{cite vllm/v1/core/sched/scheduler.py:889-904}}).
  5. The waiting pass runs only if nothing was preempted ({{cite vllm/v1/core/sched/scheduler.py:957}}), and only while fewer than max_num_seqs requests run ({{cite vllm/v1/core/sched/scheduler.py:979-981}}).
  6. A waiting request starts only if all its tokens fit in free blocks ({{cite vllm/v1/core/kv_cache_manager.py:522-539}}). If not, or if chunked prefill is off and the prompt does not fit the budget, the pass stops ({{cite vllm/v1/core/sched/scheduler.py:1222-1229}}, {{cite vllm/v1/core/sched/scheduler.py:1339-1346}}).
  7. Freed blocks go to the front of the free queue in reverse order ({{cite vllm/v1/core/single_type_kv_cache_manager.py:597-598}}, {{cite vllm/v1/core/block_pool.py:797-807}}).
  8. A request that reaches the end of its known tokens samples one token. It stops at max_tokens ({{cite vllm/v1/core/sched/utils.py:114-119}}).

In the code

Step 1: the request state that the scheduler reads

The scheduler works on Request objects (vllm/v1/request.py). Three counters drive every decision:

num_tokens is the prompt plus the output tokens so far. num_tokens_with_spec adds the draft tokens of speculative decoding. num_computed_tokens starts at 0 ({{cite vllm/v1/request.py:184}}). The comment at the top of schedule() states the rule with these names:

The status of a request is an IntEnum. Every value after PREEMPTED means "finished":

A request with structured output starts in WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR, not WAITING ({{cite vllm/v1/request.py:116-117}}). Its grammar compiles in a thread pool, and the waiting pass skips the request until the grammar is ready (Step 5).

Step 2: the token budget and max_num_seqs

The budget of one step is max_num_scheduled_tokens. When you do not set it, the scheduler uses max_num_batched_tokens:

The dataclass defaults (2048 tokens, 128 sequences) are only test values ({{cite vllm/config/scheduler.py:41-43}}, {{cite vllm/config/scheduler.py:48-53}}). For vllm serve, the engine arguments pick the real defaults from the GPU memory ({{cite vllm/engine/arg_utils.py:2960-2993}}):

GPU memorymax_num_batched_tokensmax_num_seqs
160 GiB or more (for example B200)163841024
70 GiB or more, not A100, not GB10 (for example H100)81921024
other GPUs (for example A100)2048256

--performance-mode throughput doubles both values when you did not set them ({{cite vllm/engine/arg_utils.py:3171-3175}}). Some later rules can change an unset value again, for example when chunked prefill is off, the token default is at least max_model_len ({{cite vllm/engine/arg_utils.py:3177-3221}}). TPU and CPU have their own defaults ({{cite vllm/engine/arg_utils.py:2995-3024}}). max_num_seqs limits the length of the running queue: the scheduler asserts it after each call ({{cite vllm/v1/core/sched/scheduler.py:1496}}). The waiting pass uses max_num_active_seqs, which is max_num_seqs unless you set a smaller value ({{cite vllm/v1/core/sched/scheduler.py:133-137}}). The page {{link concepts/tuning}} explains how to choose these values.

Step 3: the running pass

The running pass walks self.running from the front while budget is left ({{cite vllm/v1/core/sched/scheduler.py:713-715}}). For each request it computes the missing tokens and caps them:

  1. Lines 759-763. The missing tokens. num_output_placeholders counts tokens that a started step will sample; it is 0 without {{term async-scheduling}}.
  2. Lines 764-765. The {{term long-prefill-threshold}}. Its default is 0, which means no cap ({{cite vllm/config/scheduler.py:79-84}}). The scheduler also ignores it when only one request is running or waiting ({{cite vllm/v1/core/sched/scheduler.py:677-683}}).
  3. Lines 766-768. The rest of the budget. input_budget is max_num_batched_tokens. draft_slots is 0 without speculative decoding and for most drafting methods. It is 1 for a separate draft model, and more for parallel drafting ({{cite vllm/v1/core/sched/scheduler.py:644-645}}, {{cite vllm/config/speculative.py:1977-1995}}).
  4. Lines 772-777. The position must stay below max_model_len; one slot stays free for the sampled token.

When the result is 0, the scheduler skips the request and goes on to the next one. The comment explains the choice:

With async scheduling, a request can skip a step for one more reason. When its in-flight tokens surely reach max_tokens, the scheduler plans no extra step ({{cite vllm/v1/core/sched/scheduler.py:720-734}}).

Step 4: KV blocks, and preemption when they run out

Each request then asks the KV cache manager for blocks with {{term allocate-slots}} ({{cite vllm/v1/core/sched/scheduler.py:833-842}}). The page {{link concepts/kv-cache-manager}} explains that call. If it returns None, the scheduler picks a victim:

With the default policy (fcfs), the victim is the last request in the running queue. That is usually the request that started last. With the priority policy, it is the request with the largest (priority, arrival_time): the lowest priority, and among equals the latest arrival. The victim leaves the running queue, and _preempt_request resets it:

  1. Line 1676. All KV blocks of the request go back to the block pool. Only with a consumer KV connector and overlapping steps does the scheduler hold them until the running step ends ({{cite vllm/v1/core/sched/scheduler.py:187-193}}, {{cite vllm/v1/core/sched/scheduler.py:2866-2875}}).
  2. Lines 1679-1680. The status becomes PREEMPTED, and num_computed_tokens becomes 0. The output tokens stay in the request. So when it runs again, it computes the prompt and its output tokens again: this is recompute.
  3. Lines 1683-1694. With async scheduling, tokens of a started step can still arrive. They are marked stale, so they do not change the reset counters.
  4. Lines 1700-1701. The request goes to the front of the waiting queue, and its id goes into preempted_req_ids of the next SchedulerOutput.

Then the scheduler tries allocate_slots again. If the victim was the request itself, the running pass stops ({{cite vllm/v1/core/sched/scheduler.py:898-904}}). The blocks keep their hashes when prefix caching is on. So the preempted request can find its own full blocks again in the prefix cache, if no other request has reused them ({{link concepts/prefix-caching}}).

Step 5: the waiting pass

  1. Line 957. The waiting pass runs only if the running pass preempted nothing. It makes no sense to start a new request when a running one just lost its blocks.
  2. Lines 972-974. Waiting requests that still hold KV blocks (for example after a remote KV load) go first, from kv_holding_waiting.
  3. Lines 979-981. The max_num_seqs limit (through max_num_active_seqs).
  4. Lines 986-989. A request whose grammar is not compiled yet, or whose remote KV has not arrived, is skipped for this step. The pass continues with the next request ({{cite vllm/v1/core/sched/scheduler.py:3275-3310}}).

A LoRA request is also skipped when max_loras different adapters already run and its adapter is not one of them ({{cite vllm/v1/core/sched/scheduler.py:998-1009}}). A request with num_computed_tokens == 0 then looks up the prefix cache ({{cite vllm/v1/core/sched/scheduler.py:1016-1024}}). A KV connector can add tokens from an external cache. An asynchronous load parks the request in WAITING_FOR_REMOTE_KVS until the data arrives ({{cite vllm/v1/core/sched/scheduler.py:1384-1411}}, {{link concepts/kv-connectors}}). Next, the number of tokens, and the rule for chunked prefill:

With chunked prefill on, the request takes the rest of the budget and continues in the next step. With chunked prefill off, a prompt that does not fit stops the pass. Chunked prefill is on by default for generative models that are not encoder-decoder models ({{cite vllm/engine/arg_utils.py:3031-3035}}, {{cite vllm/config/model.py:2229-2236}}).

The request then calls allocate_slots with full_sequence_must_fit=True by default, so all its tokens must fit in free blocks, not only the first chunk ({{cite vllm/config/scheduler.py:190-194}}, {{cite vllm/v1/core/sched/scheduler.py:1320-1337}}). If the call fails, the pass stops ({{cite vllm/v1/core/sched/scheduler.py:1339-1346}}). If it succeeds, the request moves to the running queue:

Step 6: speculative tokens use the same budget

Draft tokens are part of num_tokens_with_spec (Step 1), so the running pass counts them in the same budget. After the request is scheduled, the scheduler keeps only the draft tokens that fit and moves them into scheduled_spec_decode_tokens:

Rejected drafts roll back num_computed_tokens later, in update_from_output ({{cite vllm/v1/core/sched/scheduler.py:2206-2221}}). The page {{link concepts/speculative-decoding}} explains the methods.

Step 7: the SchedulerOutput, then the counters move

At the end, schedule() builds the {{term scheduler-output}}:

With Model Runner V2, a resumed request travels as a new request, with all its block ids ({{cite vllm/v1/core/sched/scheduler.py:1505-1516}}). Only after the output exists does _update_after_schedule advance the counters:

A request is a prefill chunk when it still has tokens to compute after this step (line 1721). With the default AsyncScheduler, every request that is not a prefill chunk also gets an {{term output-placeholder}} for the token that the step will sample ({{cite vllm/v1/core/sched/async_scheduler.py:32-47}}). That is why the running pass adds num_output_placeholders (Step 3). The page {{link concepts/async-scheduling}} explains the overlap. All fields of the output are on {{link concepts/data-contracts}}.

Step 8: update_from_output appends tokens and finishes requests

When the step's result arrives, the engine core calls update_from_output. For each scheduled request, it takes the sampled tokens and checks for a stop:

check_stop tests in this order: EOS, a stop token id, the length limits (max_model_len or max_tokens), then min_tokens and repetition detection ({{cite vllm/v1/core/sched/utils.py:98-140}}). A finished request frees its blocks ({{cite vllm/v1/core/sched/scheduler.py:2316-2323}}), and leaves the running queue ({{cite vllm/v1/core/sched/scheduler.py:2390-2391}}). The scheduler makes an EngineCoreOutput only for requests with new tokens, a pooler output or a stop ({{cite vllm/v1/core/sched/scheduler.py:2293-2295}}). So a prefill chunk sends nothing to the front end. Tour {{link tours/engine-step}} follows this method with real numbers.

Step 9: the scheduling policy

The {{term scheduling-policy}} is --scheduling-policy, with fcfs as the default ({{cite vllm/config/scheduler.py:159-165}}). It selects the class of the waiting queue:

The FCFS queue is a deque: new requests go to the end, preempted requests to the front ({{cite vllm/v1/core/sched/request_queue.py:78-94}}). The priority queue is a heap ordered by Request.__lt__: smaller priority first, then earlier arrival_time, then the request id ({{cite vllm/v1/core/sched/request_queue.py:131-157}}, {{cite vllm/v1/request.py:357-367}}).

A client sets the priority with the priority field of the request body. The header X-Vllm-Priority overrides the field when it holds an integer ({{cite vllm/entrypoints/generate/base/serving.py:254-265}}).

The field description says that a priority other than 0 raises an error when the server does not use priority scheduling ({{cite vllm/entrypoints/openai/chat_completion/protocol.py:393-402}}). No code raises this error. With fcfs, the queue simply appends the request ({{cite vllm/v1/core/sched/request_queue.py:78-80}}), and the priority has no effect.

Step 10: replace the scheduler with scheduler_cls

--scheduler-cls takes a class or a "module.Class" path. Without it, vLLM picks AsyncScheduler when async scheduling is on, else Scheduler:

The engine core builds the class in EngineCore.__init__ ({{cite vllm/v1/engine/core.py:164}}, {{cite vllm/v1/engine/core.py:177-185}}). The warning on lines 247-253 is a real trap: a custom class that subclasses Scheduler instead of AsyncScheduler loses the placeholders of async scheduling. The page {{link concepts/engine-hooks}} lists this hook with the other engine hooks.

Lines of vllm/v1/core/sched/scheduler.py, in the order that they run for one running request:

  1. 642-648. token_budget = max_num_scheduled_tokens; input_budget = max_num_batched_tokens. A full pause (PAUSED_ALL) sets the budget to 0.
  2. 666. kv_cache_manager.new_step_starts() tells the managers that a step begins.
  3. 670-711. Prefill throttling for data parallel MoE and the local prefill_schedule_interval (default 1, so off) ({{cite vllm/config/scheduler.py:203-209}}). When it is active, running prefill chunks wait for a later step, and decodes still run (lines 742-746).
  4. 713-718. The loop. It breaks when input_budget cannot hold one more token plus the draft slots.
  5. 720-734. Async scheduling: skip a request whose in-flight tokens already reach max_tokens.
  6. 736-740. Model Runner V2 with PP and async scheduling: a request decodes at most every pp_size steps.
  7. 748-757. An encoder-cache connector can hold a multimodal request back.
  8. 759-777. The token count and its four caps (Step 3).
  9. 780-809. Mamba block alignment, encoder inputs and the MTP lookahead can lower the count further.
  10. 811-829. A count of 0: continue.
  11. 831-904. allocate_slots and the preemption loop. With a KV connector that has pending block frees, the loop stops without a preemption (lines 844-848).
  12. 906-914. The request is scheduled: num_scheduled_tokens[req_id] = num_new_tokens; both budgets go down.
  13. 916-943. Draft tokens (Step 6) and encoder inputs.
  14. 945-954. The LoRA ids of all running requests, for the max_loras check of the waiting pass.

With the priority policy, the victim can be a request that this pass already scheduled. Then the scheduler gives its tokens back to both budgets and removes its blocks and draft tokens from the plan (lines 864-888). With FCFS this cannot happen: the victim is the last request, and the pass has not reached it yet.
  1. 958-967. skip_request moves a request out of the queue for this step only. Skipped requests go back to the front of their queue at the end (lines 1469-1473), so they keep their place.
  2. 969-981. Loop while budget is left; queue choice; max_num_active_seqs.
  3. 986-996. Blocked statuses, and stale output of a preempted request that is still in flight.
  4. 998-1009. LoRA: skip.
  5. 1016-1146. First admission (num_computed_tokens == 0): local prefix-cache hit, then the KV connector hit, then bookkeeping for statistics.
  6. 1147-1158. A request that already has computed tokens (after a remote KV load, or a streaming-input session) uses them.
  7. 1171-1283. The token count. An async KV load schedules 0 tokens. With speculative decoding, a waiting request with only 1 token to compute can be padded to 1 + num_spec_tokens. This happens only when no prefill chunk runs in the step, and keeps a uniform batch for CUDA graphs (lines 1196-1215). Then the long-prefill cap, the chunked-prefill rule and the budget.
  8. 1320-1346. allocate_slots, with the prefix-cache hit and full_sequence_must_fit. None: break.
  9. 1378-1382. Prefix-cache statistics are recorded only for admitted requests.
  10. 1413-1467. The request moves to running. Its status before the move decides the list: WAITING goes to scheduled_new_reqs, PREEMPTED to scheduled_resumed_reqs.

Note the asymmetry. In the waiting pass, a request that does not fit stops the pass. A smaller request behind it does not get a chance in this step. Only skipped requests (blocked, LoRA, 0 tokens) let the pass continue.

What the victim loses. All its KV blocks and its num_computed_tokens. It keeps its prompt and output tokens. Take a victim with a 1000-token prompt and 200 output tokens. Without a prefix-cache hit, it must compute 1200 tokens again when it resumes (derived from lines 1680 and 1191). The waiting pass treats it like a new request. It looks up the prefix cache, because num_computed_tokens is 0, and all its tokens must fit.

What comes back. _free_request_blocks frees the blocks in reverse order ({{cite vllm/v1/core/sched/scheduler.py:2866-2875}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:597-598}}). Blocks with a hash go to the end of the free queue. Blocks without a hash, for example the partial last block, go to the front ({{cite vllm/v1/core/block_pool.py:776-807}}). So the full blocks stay in the prefix cache as long as nobody needs their memory. If they survive, the resumed request hits them and computes only the rest.

How you see it. The scheduler records a PREEMPTED event when stats are on ({{cite vllm/v1/core/sched/scheduler.py:1696-1697}}). The front end counts these events in vllm:num_preemptions ({{cite vllm/v1/metrics/loggers.py:738-745}}). The periodic log line adds "Preemptions: N" when N is above 0 ({{cite vllm/v1/metrics/loggers.py:310-312}}).

Docs and code. docs/configuration/optimization.md shows a WARNING line "Sequence group 0 is preempted by PreemptionMode.RECOMPUTE mode ..." ({{cite docs/configuration/optimization.md:33-35}}). The V1 scheduler does not log a line per preemption: _preempt_request has no log call ({{cite vllm/v1/core/sched/scheduler.py:1658-1701}}). Watch the metric or the "Preemptions" field instead. The same page says that recompute is the default mode in V1 ({{cite docs/configuration/optimization.md:47}}). In the V1 code it is the only mode: _preempt_request always frees the blocks and resets num_computed_tokens ({{cite vllm/v1/core/sched/scheduler.py:1676-1680}}).

Other preemptions. reset_prefix_cache(reset_running_requests=True) preempts every running request, from the end, with their stale output dropped ({{cite vllm/v1/core/sched/scheduler.py:2950-2960}}).

The scheduler checks some combinations at start-up: max_num_batched_tokens must be at least max_model_len when chunked prefill is off, and at least max_num_seqs ({{cite vllm/config/scheduler.py:317-336}}).
  • Encoder inputs (images, audio): a separate encoder compute budget and encoder cache; a chunk can stop before an image that does not fit ({{cite vllm/v1/core/sched/scheduler.py:1876-1903}}).
  • Mamba "align" mode: chunks end on block boundaries so that states can be cached ({{cite vllm/v1/core/sched/scheduler.py:474-488}}). See {{link concepts/hybrid-kv-cache}}.
  • Pause states: PAUSED_ALL schedules nothing; PAUSED_NEW admits only requests that hold blocks ({{cite vllm/v1/core/sched/scheduler.py:646-648}}, {{cite vllm/v1/core/sched/scheduler.py:970-974}}).
  • Streaming-input sessions (resumable requests): a stopped turn waits in WAITING_FOR_STREAMING_REQ for the next input ({{cite vllm/v1/core/sched/scheduler.py:2564-2589}}).
  • KV load failures of a connector: the scheduler recomputes the bad blocks or fails the request, by kv_load_failure_policy ({{cite vllm/v1/core/sched/scheduler.py:184-185}}, {{cite vllm/v1/core/sched/scheduler.py:3444-3457}}).

What can go wrong

  • Many preemptions. The KV cache is too small for the running requests. Each preemption throws away computed work. Watch vllm:num_preemptions. Raise --gpu-memory-utilization, or lower --max-num-seqs ({{link concepts/kv-cache-manager}}).
  • Decodes slow down during a long prompt. A prompt chunk can take the whole rest of the budget, so the step gets long for every request in it. --long-prefill-token-threshold caps one request's share ({{cite vllm/v1/core/sched/scheduler.py:764-765}}).
  • Head-of-line blocking. The first waiting request that does not fit stops the waiting pass ({{cite vllm/v1/core/sched/scheduler.py:1339-1346}}). With chunked prefill off, a long prompt at the front stops it too ({{cite vllm/v1/core/sched/scheduler.py:1222-1229}}).
  • Requests wait with free memory. max_num_seqs requests already run ({{cite vllm/v1/core/sched/scheduler.py:979-981}}), or the LoRA requests wait for an adapter slot ({{cite vllm/v1/core/sched/scheduler.py:998-1009}}).
  • The priority field does nothing. The server runs fcfs. Start it with --scheduling-policy priority.
  • A custom scheduler is slower. It subclasses Scheduler, so async scheduling is lost ({{cite vllm/config/scheduler.py:247-253}}).

Why it matters. The scheduler sets the shape of every step: how many tokens, which requests, how much of a prompt. TTFT, inter-token latency and throughput all follow from these choices. When you tune max_num_batched_tokens or max_num_seqs, or read the preemption metric, you change or watch this one function.

Does the vLLM scheduler have a prefill phase and a decode phase?

No. Each request asks for num_tokens_with_spec - num_computed_tokens tokens, and the scheduler gives them from one budget. A new prompt asks for many tokens, a decoding request for one ({{cite vllm/v1/core/sched/scheduler.py:624-633}}, {{cite vllm/v1/core/sched/scheduler.py:759-768}}).

 With the default policy, which request does the scheduler preempt when a running request cannot get blocks?

The last request in the running queue: self.running.pop() ({{cite vllm/v1/core/sched/scheduler.py:889-890}}). With the priority policy, it is the request with the largest (priority, arrival_time) ({{cite vllm/v1/core/sched/scheduler.py:852-856}}).

 In a step, the running pass preempts one request. A short new request waits, and 2000 tokens of budget are left. Does the short request start in this step?

No. The waiting pass runs only when nothing was preempted in this step ({{cite vllm/v1/core/sched/scheduler.py:957}}). The budget stays unused.

 Why does the running pass use continue for a request with 0 tokens, while the waiting pass uses break when allocate_slots fails?

A running request with 0 tokens (for example, all its tokens are in flight) must not block the requests behind it. The comment says that the scheduler gives up strict FCFS for this ({{cite vllm/v1/core/sched/scheduler.py:825-829}}). In the waiting pass, a failed allocation means the free blocks are short, so the scheduler stops admitting new requests ({{cite vllm/v1/core/sched/scheduler.py:1339-1346}}).

 A request has a 1000-token prompt and 200 output tokens when it is preempted. Prefix caching is on, block size 16, and no other request reused its blocks. How many tokens does it compute when it resumes, at the minimum?

_preempt_request sets num_computed_tokens to 0 ({{cite vllm/v1/core/sched/scheduler.py:1680}}), so the waiting pass looks up the prefix cache again ({{cite vllm/v1/core/sched/scheduler.py:1017-1024}}). The request has 1200 tokens. Its full blocks were cached and stay cached until reused. The lookup returns full blocks only, up to num_tokens - 1 = 1199 tokens ({{cite vllm/v1/core/kv_cache_manager.py:289-300}}): 74 blocks = 1184 tokens. So it computes at least 1200 − 1184 = 16 tokens. This assumes that every full block was cached; with async scheduling, the blocks of the last in-flight tokens may not be cached yet (derived).
