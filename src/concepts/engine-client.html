It turns requests into EngineCoreRequests, sends them to the engine core, and streams RequestOutputs back through one background task and one collector per request. --- AsyncLLM is the engine client of the API server. It sends each request to the engine core and streams the outputs back through a per-request collector.

The idea

The OpenAI-compatible routes do not talk to the engine core process directly. They call one object, the {{term engine-client}}, through a fixed set of methods: generate(), abort(), check_health() and some more. In vllm serve this object is {{term async-llm}}. It lives in the API server process, the {{term front-end}}.

AsyncLLM does three jobs. On the way in, it checks the rendered prompt and makes an {{term engine-core-request}}. In the middle, its {{term engine-core-client}} sends the request over {{term zmq | ZMQ}} and receives {{term engine-core-outputs}}. On the way out, its {{term output-processor}} detokenizes the token ids and makes a {{term request-output}} for each request.

Many requests run at the same time, but the engine core sends one message per step for all of them. So AsyncLLM has one background task, the {{term output-handler}}, that reads all outputs. It puts each request's output into a small queue for that request, the {{term request-output-collector}}. The task that serves the HTTP request waits only on its own collector.

An everyday comparison. Think of a post office with mailboxes. A truck (the engine core) brings one bag of letters after each step. One clerk (the output handler) sorts the bag into the mailboxes. Each customer (a generate() task) waits at its own mailbox. The comparison stops in one place: a mailbox holds only one item. When a new letter arrives before the customer takes the old one, the clerk staples the two letters together.

In the code

Step 1: the EngineClient interface

EngineClient is an abstract class in vllm/engine/protocol.py. It declares four attributes and the state properties that the server checks:

The main abstract methods are generate ({{cite vllm/engine/protocol.py:93-115}}), encode for pooling models, abort ({{cite vllm/engine/protocol.py:132-141}}) and check_health ({{cite vllm/engine/protocol.py:163-166}}). Sleep, wake-up, LoRA, cache resets and pause are abstract too ({{cite vllm/engine/protocol.py:184-256}}). collective_rpc and the weight-transfer methods have a default that raises NotImplementedError ({{cite vllm/engine/protocol.py:275-283}}, {{cite vllm/engine/protocol.py:303-335}}). In the vllm/ package, AsyncLLM is the one class that implements it ({{cite vllm/v1/engine/async_llm.py:93}}).

The serving classes use the attributes too. They take the renderer and the input processor from the engine client ({{cite vllm/entrypoints/generate/base/serving.py:150-151}}). Before they start a response, they check errored and call check_admission ({{cite vllm/entrypoints/generate/base/serving.py:169-181}}).

Step 2: construction

The API server calls AsyncLLM.from_vllm_config ({{cite vllm/entrypoints/launchers/api_server/entry.py:93-103}}). This class method picks the executor class from the config and turns disable_log_stats into log_stats:

The constructor then builds the parts in this order: the renderer, the {{term input-processor}}, the output processor and the engine core client ({{cite vllm/v1/engine/async_llm.py:167-201}}). With one API server, the engine core client also starts the engine core processes. In every case it waits until each engine core is ready (page {{link concepts/architecture-overview}}, Step 2). Then the constructor makes the stat loggers when log_stats is on ({{cite vllm/v1/engine/async_llm.py:203-214}}). Stat logger plugins can turn on log_stats even when you disable the default loggers ({{cite vllm/v1/engine/async_llm.py:155-165}}).

At the end, the constructor starts the output handler, but only if an event loop already runs. Otherwise the first add_request starts it ({{cite vllm/v1/engine/async_llm.py:218-224}}, {{cite vllm/v1/engine/async_llm.py:523-526}}).

Step 3: generate() and add_request()

The chat handler calls self.engine_client.generate(...) with the rendered engine input and the sampling parameters ({{cite vllm/entrypoints/openai/chat_completion/serving.py:396-408}}). generate() is an async generator, so this call only makes the generator object. The code runs when the HTTP stream asks for the first chunk (see {{link tours/life-of-a-chat-request#stop-4 | Tour 1, stop 4}}):

add_request does the work before the loop. For a request with n = 1, the important lines are:

  1. Line 521: assign_request_id keeps the caller's id as external_req_id and adds 8 random characters to request_id ({{cite vllm/v1/engine/input_processor.py:353-371}}).
  2. Line 529: one collector per request. Its mode depends on output_kind: DELTA for a stream.
  3. Line 535: _add_request registers the request in the output processor first, and then sends it ({{cite vllm/v1/engine/async_llm.py:580-584}}). So an output can never arrive for a request that the output processor does not know.

Step 4: the output handler and its chunks

One task serves all requests. It loops for the whole life of the server:

  • Line 880 waits for the next EngineCoreOutputs from the engine core client.
  • Lines 891-893 cut the list into slices of VLLM_V1_OUTPUT_PROC_CHUNK_SIZE outputs, 128 by default ({{cite vllm/envs.py:1474-1476}}).
  • Lines 915-916 give the event loop to other tasks between two slices. The comment at lines 887-889 gives the reason: one large step must not block the event loop for too long.
  • Lines 919-922 abort the requests that the detokenizer stopped with a stop string. The engine core cannot know about stop strings, because it has no text.

process_outputs makes a new reqs_to_abort list for each call ({{cite vllm/v1/engine/output_processor.py:756}}). The abort call is inside the slice loop, so the handler sends the aborts of each slice before it processes the next slice ({{cite vllm/v1/engine/async_llm.py:891-922}}). A stop string in any slice stops the request in the engine core.

After all slices, the handler updates the LoRA state and records the scheduler and iteration stats ({{cite vllm/v1/engine/async_llm.py:924-935}}).

Step 5: the collector hands the output over

The collector has one slot (self.output) and an asyncio.Event. When the slot is full and a new RequestOutput comes, put() merges it into the old one (line 79). With DELTA, the merge appends the new text and token ids ({{cite vllm/outputs.py:220-225}}). So a slow HTTP writer gets one larger chunk, and no token is lost. An exception in the slot replaces any output, and get() raises it (lines 71 and 91-92).

Step 6: abort when the client goes away

When the HTTP client disconnects, Starlette cancels the response task. The cancel reaches generate() as CancelledError or GeneratorExit:

abort() first removes the request from the output processor. It returns the internal ids, which include the children of an n > 1 request ({{cite vllm/v1/engine/output_processor.py:599-661}}). Then it sends one ABORT message with these ids to the engine core. Before a streaming response starts, the route decorator with_cancellation watches for the disconnect itself ({{cite vllm/entrypoints/serve/utils/api_utils.py:85-109}}).

Step 7: errors and engine death

vLLM has two engine exceptions. EngineGenerateError is for one request and "Recoverable". {{term engine-dead-error}} means that the engine core died, and it is "Unrecoverable" ({{cite vllm/v1/engine/exceptions.py:6-22}}). The death becomes visible in four places:

  1. The engine core sends ENGINE_CORE_DEAD. The client sets engine_dead and raises EngineDeadError ({{cite vllm/v1/engine/core_client.py:581-584}}). The monitor thread sets the same flag when an engine core process exits ({{cite vllm/v1/engine/core_client.py:829-838}}).
  2. The exception reaches the output handler, which puts it into every collector ({{cite vllm/v1/engine/async_llm.py:936-944}}, {{cite vllm/v1/engine/output_processor.py:593-597}}). Each waiting generate() raises it again, without an abort ({{cite vllm/v1/engine/async_llm.py:814-818}}).
  3. errored becomes true when the flag is set or the output handler task has ended ({{cite vllm/v1/engine/async_llm.py:1373-1384}}). New requests then fail at once ({{cite vllm/v1/engine/async_llm.py:418-419}}), and /health returns 503 ({{cite vllm/entrypoints/serve/instrumentator/health.py:29-33}}).
  4. A watchdog task checks every 5 seconds and stops uvicorn, unless VLLM_KEEP_ALIVE_ON_ENGINE_DEATH is set ({{cite vllm/entrypoints/launchers/launcher.py:314-337}}).

Step 8: which engine core client

AsyncLLM always uses a multiprocess client: make_async_mp_client chooses the class by the data parallel settings:

  • AsyncMPClient (DP = 1): one engine core, one ZMQ identity.
  • DPLBAsyncMPClient (DP > 1, internal load balancing): picks an engine core for each request by load ({{cite vllm/v1/engine/core_client.py:1743-1804}}).
  • DPAsyncMPClient (DP > 1, external load balancer): sends everything to its own engine core ({{cite vllm/v1/engine/core_client.py:1611-1612}}).

The page {{link code/v1-engine-core-client}} reads these classes line by line. The page {{link concepts/data-parallel-serving}} explains the load balancing modes.

Step 9: sleep, wake-up and collective RPCs at a glance

Control methods do not go through generate(). AsyncLLM forwards them as {{term utility-call | utility calls}}. For example, sleep() clears the multimodal cache and calls engine_core.sleep_async ({{cite vllm/v1/engine/async_llm.py:1196-1202}}). collective_rpc forwards any worker method name ({{cite vllm/v1/engine/async_llm.py:1247-1257}}). In the engine core, the utility method collective_rpc calls the executor, which runs the method on every worker ({{cite vllm/v1/engine/core.py:1098-1105}}).

The HTTP routes /sleep, /wake_up and /collective_rpc exist only when VLLM_SERVER_DEV_MODE is set ({{cite vllm/entrypoints/launchers/api_server/routers.py:46-49}}, {{cite vllm/entrypoints/serve/__init__.py:43-65}}).

The offline LLM class uses LLMEngine, not AsyncLLM. It has the same input and output processors ({{cite vllm/v1/engine/llm_engine.py:101-104}}). With VLLM_ENABLE_V1_MULTIPROCESSING on (the default), it uses SyncMPClient: a blocking client with a background output thread ({{cite vllm/v1/engine/llm_engine.py:186-188}}, {{cite vllm/v1/engine/core_client.py:1015-1021}}). There is no collector: process_outputs returns the outputs as a list ({{cite vllm/v1/engine/output_processor.py:864-866}}).

  1. Lines 418-419. A dead engine fails the request at once with EngineDeadError.
  2. Lines 421-423. Trace headers without an OTLP endpoint only log a warning, and the headers are dropped.
  3. Lines 427-436. --kv-sharing-fast-prefill with prompt logprobs raises VLLMValidationError, which becomes HTTP 400.
  1. Line 481. A dict with a "type" key is a rendered engine input. This is the normal path of vllm serve: the renderer has already tokenized. So process_inputs runs in the event loop, with no thread hop (line 483).
  2. Lines 497-513. A raw prompt still needs tokenization. process_inputs_async runs the same function in the renderer's thread pool ({{cite vllm/v1/engine/input_processor.py:82-84}}).
  3. Line 487. get_supported_tasks() is a utility call to the engine core, but only the first time. AsyncLLM caches the result ({{cite vllm/v1/engine/async_llm.py:390-395}}).
  4. Line 514. The prompt text is kept for the output, for example for RequestOutput.prompt.
  1. Line 542. With n > 1, a ParentRequest makes n child requests. Child i gets the id f"{i}_{request_id}" and a copy of the parameters with n = 1 ({{cite vllm/v1/engine/parallel_sampling.py:84-96}}). With a seed, child i gets the seed seed + i ({{cite vllm/v1/engine/parallel_sampling.py:76-81}}).
  2. Line 551. Admission control counts the request as n slots.
  3. Lines 553-559. All children are registered with the same collector, then sent one by one. The engine core sees n independent requests.
  4. Lines 562-564. If a send fails, the parent and all its children are aborted.

Assume 300 requests are running, and one engine step produces one token for each. The engine core sends one EngineCoreOutputs with 300 entries in outputs.

  1. EngineCoreOutputQueueTask receives the frames, decodes them and puts the object into outputs_queue ({{cite vllm/v1/engine/core_client.py:1211-1254}}).
  2. The output handler gets it. num_outputs = 300, and with stats on it makes one IterationStats ({{cite vllm/v1/engine/async_llm.py:880-885}}).
  3. With the default chunk size 128, the loop runs for start = 0, 128 and 256. The slices have 128, 128 and 44 outputs.
  4. After the first and the second slice, end (128, then 256) is smaller than 300, so the handler calls asyncio.sleep(0). After the third slice, end = 384 is not smaller than 300, so there is no sleep. (Derived from lines 891-916.)
  5. Between the slices, other tasks can run: for example, 128 generate() tasks wake up and write their SSE chunks before the next slice is detokenized.

A smaller chunk size gives more fairness on the event loop and more task switches. The code gives no measured numbers for this trade-off.

check_admission rejects a request with HTTP 503 before any response starts. It applies two optional limits from the scheduler config ({{cite vllm/v1/engine/async_llm.py:325-383}}):

  • max_num_queued_reqs: the number of unfinished requests, waiting plus running. A request with n = 4 needs 4 slots.
  • max_num_queued_tokens: the sum of the prompt lengths of the requests that are still in prefill.

The docstring warns that the token count overestimates the work. The API server does not see chunked prefill progress or prefix-cache hits until the prefill is complete ({{cite vllm/v1/engine/async_llm.py:337-341}}). The count comes from the output processor: prompt_len of every request whose is_prefilling is still true ({{cite vllm/v1/engine/output_processor.py:579-588}}).

What can go wrong

  • The server exits after an engine error. This is the default for EngineDeadError: the watchdog stops uvicorn ({{cite vllm/entrypoints/launchers/launcher.py:325-337}}). Read the log of the engine core process for the root cause. The message of the exception says "See stack trace (above) for the root cause" ({{cite vllm/v1/engine/exceptions.py:19-21}}).
  • A stop string ends the text, but the engine still runs a step. The engine core does not see stop strings. The output handler sends an ABORT after the detokenizer finds one ({{cite vllm/v1/engine/async_llm.py:918-922}}). The default loop schedules the next step before it processes the output of the current one ({{cite vllm/v1/engine/core.py:724-759}}, {{cite vllm/v1/engine/core.py:767-785}}). So the next step for that request is usually already on the GPU, and more steps can start before the ABORT arrives. (Derived.) The front end ignores these outputs, because the request state is gone ({{cite vllm/v1/engine/output_processor.py:759-762}}).
  • The event loop is busy. All requests share one event loop and one output handler. A very large batch, long stop strings or many logprobs make process_outputs slow, and all streams wait. More API servers (--api-server-count) split this CPU work ({{link concepts/architecture-overview}}).
  • The 503 errors come early. With max_num_queued_tokens set, the admission check counts full prompt lengths, so it can reject requests while the GPU still has room ({{cite vllm/v1/engine/async_llm.py:337-341}}).

Why it matters. Every request of vllm serve goes through AsyncLLM twice: once on the way in and once on the way out. Its single event loop and its error handling decide how the server behaves under load and after a crash.

Which class implements EngineClient for vllm serve, and which method does the chat route call to start a request?

AsyncLLM ({{cite vllm/v1/engine/async_llm.py:93}}). The chat handler calls self.engine_client.generate(...) ({{cite vllm/entrypoints/openai/chat_completion/serving.py:396}}).

 Why does _add_request call output_processor.add_request before engine_core.add_request_async?

So the output processor knows the request before its first output can arrive, and before any other task runs. The comment says "Register locally before the first await so concurrent tasks see this request" ({{cite vllm/v1/engine/async_llm.py:580-584}}). The output processor ignores outputs of unknown requests ({{cite vllm/v1/engine/output_processor.py:759-762}}).

 The engine core produces two tokens for a stream before the HTTP writer reads the first one. What does the writer get?

One RequestOutput with both tokens. The collector has one slot. With DELTA output, put() merges the second output into the first ({{cite vllm/v1/engine/output_processor.py:74-79}}), and the merge appends the text and the token ids ({{cite vllm/outputs.py:220-225}}).

 A step returns 200 outputs. With the default settings, how many slices does the output handler process, and how often does it call asyncio.sleep(0)?

Two slices: 128 and 72 outputs, because VLLM_V1_OUTPUT_PROC_CHUNK_SIZE is 128 ({{cite vllm/envs.py:1474-1476}}). It sleeps once, after the first slice, because end = 128 < 200. After the second slice end = 256, so there is no sleep ({{cite vllm/v1/engine/async_llm.py:891-916}}).

 The engine core process crashes while 10 streams run. Trace what each stream sees and what the server does.

The engine core sends ENGINE_CORE_DEAD, and the client raises EngineDeadError ({{cite vllm/v1/engine/core_client.py:581-584}}). The output handler puts it into all 10 collectors ({{cite vllm/v1/engine/async_llm.py:936-944}}). Each generate() raises it without an abort ({{cite vllm/v1/engine/async_llm.py:814-818}}). Each stream generator writes an error chunk, because the 200 status is already sent ({{cite vllm/entrypoints/openai/chat_completion/serving.py:941-943}}). Within 5 seconds the watchdog stops the server, unless VLLM_KEEP_ALIVE_ON_ENGINE_DEATH is set ({{cite vllm/entrypoints/launchers/launcher.py:314-337}}).
