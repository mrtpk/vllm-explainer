The idea

A vLLM server has a few dozen flags that change speed. They act in three places, at three times. This page sorts them by place, gives each real default with the line that sets it, and says what the knob trades. It does not give performance numbers: measure your own workload with {{link concepts/benchmarking}}.

  1. Memory, once at start-up. --gpu-memory-utilization, --kv-cache-memory-bytes, --kv-cache-dtype, --max-model-len and the size of the weights decide how many KV blocks exist. The block count does not change while the server runs. The engine core logs it as the {{term max-concurrency | maximum concurrency}}.
  2. The scheduler, every step. --max-num-seqs, --max-num-batched-tokens (the {{term token-budget}}), chunked prefill and the scheduling policy decide which requests share a step. They trade time to first token (TTFT) against inter-token latency (ITL) and throughput ({{link learn/serving-metrics}}).
  3. Execution and the front end. CUDA graphs, torch.compile, speculative decoding and async scheduling change how long a step takes. --api-server-count, the renderer threads and --stream-interval change the CPU work in the API server.

Most knobs have a default that the code computes. The dataclass default is often not the real default: for example, SchedulerConfig says 128 sequences, but vllm serve on an 80 GiB H100 uses 1024. The full flag list with real defaults is on {{link reference/serve-flags#tune-first | the serve-flags reference}}; this page explains the mechanisms behind the most important ones.

An everyday comparison. Think of a restaurant. The size of the dining room is fixed when it opens (memory knobs). The head waiter decides each minute which guests to seat and how many dishes the kitchen starts (scheduler knobs). The kitchen equipment and the number of waiters at the door decide how fast one round goes (execution and front-end knobs). The comparison stops at the tables. In vLLM, one long conversation can take the space of many short ones. A guest can also lose the table (preemption) when the room is full.

The picture

Read the panels from top to bottom. Panel 1 runs once, so its knobs need a restart. Panel 2 runs in the {{term engine-core}} process at every {{term engine-step | step}}. Panel 3 mixes the GPU workers (compile, graphs, drafts) and the API server process (amber).

In the code

Step 1: the memory budget and the KV cache size

At start-up, each worker measures how much memory is left for the KV cache. The page {{link concepts/kv-cache-manager}} explains the block pool; {{link concepts/executors-and-workers}} explains the {{term profile-run}}. The worker first computes the requested memory, a share of the whole GPU, and refuses to start when less is free ({{cite vllm/v1/worker/utils.py:724-726}}, {{cite vllm/v1/worker/utils.py:761-770}}). After a dummy forward pass with max_num_batched_tokens tokens, it computes the rest:

non_kv_cache_memory is the memory consumed since the start snapshot (weights, buffers, non-torch memory) plus the transient peak of the activations ({{cite vllm/utils/mem_utils.py:312-321}}). The CUDA graph estimate is on by default (VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=1, {{cite vllm/envs.py:2217-2219}}). So the KV cache gets:

available_kv = ceil(total × gpu_memory_utilization) − (consumed + peak_activation_headroom) − cudagraph_estimate

Four knobs change this result:

  • --gpu-memory-utilization, default 0.92, is the share of the whole GPU for this instance ({{cite vllm/config/cache.py:212-221}}). Each 0.01 adds 1 % of the GPU to the KV cache.
  • --max-num-batched-tokens sets the size of the profile run, so a larger budget measures a larger activation peak and leaves less KV memory ({{cite vllm/v1/worker/gpu/model_runner.py:231}}, {{cite vllm/v1/worker/gpu/model_runner.py:1022-1027}}).
  • --enforce-eager turns off CUDA graphs, so the graph estimate is 0 and no graph is captured ({{cite vllm/v1/worker/gpu_worker.py:704-708}}, {{cite vllm/v1/worker/gpu_worker.py:983-985}}).
  • {{term kv-cache-memory-bytes}} replaces the whole formula. The worker still runs the profile run (it compiles the model), but then returns the given size and logs that it does not respect gpu_memory_utilization ({{cite vllm/v1/worker/gpu_worker.py:653-679}}).

After graph capture, the worker logs the measured parts and suggests a value: "Replace gpu_memory_utilization config with `--kv-cache-memory=N`" ({{cite vllm/v1/worker/gpu_worker.py:1035-1055}}). The flag is --kv-cache-memory-bytes ({{cite vllm/engine/arg_utils.py:1384-1386}}). The value takes plain bytes or a suffix: 40G is 40 GiB, 40g is 40 × 109 bytes ({{cite vllm/engine/arg_utils.py:396-409}}, {{cite vllm/utils/argparse_utils.py:30-74}}). The suggestion keeps a 150 MiB buffer ({{cite vllm/v1/worker/gpu_worker.py:1017}}). It is valid only for the same GPU with the same free memory at start-up.

Step 2: max_model_len and the maximum-concurrency line

After the KV cache is sized, the engine core stores the capacity and logs one line ({{cite vllm/v1/engine/core.py:342}}):

The concurrency is the number of blocks divided by the blocks that one request of max_model_len needs. For a model with one KV cache group, that is num_blocks / cdiv(max_model_len, block_size). With several groups, vLLM adds the blocks per request of all groups ({{cite vllm/v1/core/kv_cache_utils.py:1031-1041}}). The token count in the log is int(concurrency × max_model_len) ({{cite vllm/v1/core/kv_cache_utils.py:1074-1082}}). So "Maximum concurrency 3.41x" means: 3.41 requests of the full length fit at once. Shorter requests fit many more times.

--max-model-len does not change the block count. It changes the check at start-up: one request of that length must fit in the KV cache, minus one block for the null block ({{cite vllm/v1/core/kv_cache_planning.py:1572-1582}}, {{cite vllm/v1/core/kv_cache_planning.py:1590-1598}}). If it does not fit, start-up stops with an estimate of the largest length that fits ({{cite vllm/v1/core/kv_cache_planning.py:68-87}}). With --max-model-len auto (or -1), vLLM lowers the length to that estimate and logs "Auto-fit max_model_len: reduced from ..." ({{cite vllm/v1/core/kv_cache_planning.py:1584-1587}}, {{cite vllm/v1/core/kv_cache_planning.py:1393-1410}}). The default is the length from the model's config ({{cite vllm/config/model.py:2639-2653}}).

The playground uses only these formulas from the code:

  1. requested = ceil(total × gpu_memory_utilization) ({{cite vllm/v1/worker/utils.py:724-726}}).
  2. available = requested − (consumed + peak_headroom) − cudagraph_estimate ({{cite vllm/v1/worker/gpu_worker.py:744-748}}, {{cite vllm/utils/mem_utils.py:312-321}}). With --kv-cache-memory-bytes: available = that value ({{cite vllm/v1/worker/gpu_worker.py:653-679}}).
  3. bytes_per_block = bytes_per_token × block_size, where bytes per token is the sum over the layers of num_kv_heads × (head_size + head_size_v) × dtype_bytes ({{cite vllm/v1/kv_cache_interface.py:571-579}}, {{cite vllm/v1/core/kv_cache_planning.py:587-593}}).
  4. num_blocks = available // bytes_per_block ({{cite vllm/v1/core/kv_cache_planning.py:1610-1611}}).
  5. Fit check: cdiv(max_model_len, block_size) × bytes_per_block ≤ available − bytes_per_block ({{cite vllm/v1/core/kv_cache_planning.py:1572-1582}}, {{cite vllm/v1/core/kv_cache_planning.py:68-87}}). When available − bytes_per_block ≤ 0, start-up stops earlier with "No available memory for the cache blocks." ({{cite vllm/v1/core/kv_cache_planning.py:56-64}}).
  6. max_concurrency = num_blocks / cdiv(max_model_len, block_size); logged tokens = int(max_concurrency × max_model_len) ({{cite vllm/v1/core/kv_cache_utils.py:1031-1047}}, {{cite vllm/v1/core/kv_cache_utils.py:1074-1082}}).
  7. "Use vllm serve defaults" applies the memory tiers, the throughput doubling and the two caps of Step 3 ({{cite vllm/engine/arg_utils.py:2958-2993}}, {{cite vllm/engine/arg_utils.py:3171-3175}}, {{cite vllm/engine/arg_utils.py:3206-3221}}).

The playground assumes one KV cache group (a plain decoder such as Llama) and per-GPU values (with TP, enter the share of one GPU). "Requests that fit" divides the usable blocks by the blocks of one average request. The real scheduler admits a request only when all its current tokens fit ({{cite vllm/v1/core/kv_cache_manager.py:522-539}}). The request then grows during decode, and the scheduler preempts when blocks run out ({{link concepts/scheduler}}). Prefix-cache hits share blocks and let more requests fit. Hybrid models have several groups ({{link concepts/hybrid-kv-cache}}). The real profile also checks that the requested memory is free at start-up. Multimodal models also reserve some GPU memory for the front end, which the playground leaves out ({{cite vllm/v1/worker/gpu_worker.py:807-811}}).

Step 3: max_num_seqs and max_num_batched_tokens

Both flags are None by default. create_engine_config fills them by the usage context and the memory of one GPU ({{term usage-context}}). For vllm serve (OPENAI_API_SERVER):

Then these rules apply, only to values that you did not set yourself:

  • {{term performance-mode | --performance-mode throughput}} doubles both defaults (above). The other modes are balanced (default) and interactivity ({{cite vllm/config/vllm.py:146}}).
  • Without chunked prefill, the token budget is at least max_model_len ({{cite vllm/engine/arg_utils.py:3177-3186}}).
  • The token budget is at most max_num_seqs × max_model_len ({{cite vllm/engine/arg_utils.py:3206-3211}}).
  • max_num_seqs is at most the token budget ({{cite vllm/engine/arg_utils.py:3219-3221}}).
  • For a multimodal prefix-LM model, the budget grows until the largest multimodal item fits ({{cite vllm/engine/arg_utils.py:3188-3203}}).

Values that you set are checked, not changed. max_num_seqs larger than the token budget raises ValueError at start-up ({{cite vllm/config/scheduler.py:331-336}}). When chunked prefill is on, SchedulerConfig logs the budget once: "Chunked prefill is enabled with max_num_batched_tokens=N." ({{cite vllm/config/scheduler.py:309-313}}).

What the two knobs change:

  • max_num_seqs caps the running requests per step ({{cite vllm/v1/core/sched/scheduler.py:979-981}}). It also sizes the per-request buffers of the model runner and the default CUDA graph capture sizes (Step 6). A larger value gives more throughput only when the KV cache can hold that many requests. --max-num-active-seqs lowers only the admission limit and keeps the buffers ({{cite vllm/config/scheduler.py:69-76}}).
  • max_num_batched_tokens caps the tokens per step. The scheduler gives running requests their tokens first, then admits waiting requests with the rest ({{cite vllm/v1/core/sched/scheduler.py:713-715}}, {{cite vllm/v1/core/sched/scheduler.py:956-957}}). A larger budget moves prompts through faster (lower TTFT under load) but makes the steps longer, so running requests see a higher ITL. It also sets the profile-run size (Step 1) and is part of the compile cache key, so a change compiles again ({{cite vllm/config/scheduler.py:271-284}}).

Start from the defaults. Change max_num_batched_tokens first, and judge it by TTFT and ITL percentiles at your target request rate. The vLLM docs say: "For optimal throughput, we recommend setting max_num_batched_tokens > 8192 especially for smaller models on large GPUs" ({{cite docs/configuration/optimization.md:66}}). Raise max_num_seqs only when vllm:num_requests_running stays at the limit while the KV cache usage is low.

Step 4: chunked prefill and the long-prefill cap

Chunked prefill is on for generative decoder models: the default comes from is_chunked_prefill_supported of the model, not from the dataclass ({{cite vllm/engine/arg_utils.py:3031-3040}}). A prompt that does not fit the rest of the budget gets a chunk, and the next steps continue it ({{deepinfer learn/batching | Batching}}). Without chunked prefill, the budget must be at least max_model_len ({{cite vllm/config/scheduler.py:318-329}}).

A long prompt can still take the whole rest of a step. --long-prefill-token-threshold N caps the tokens that one prefill takes per step. The default 0 turns the cap off ({{cite vllm/config/scheduler.py:79-84}}):

The cap applies only when more than one request runs or waits (lines 679-683). With --long-prefill-token-threshold-adaptive, the cap is never below a fair share of the budget (lines 684-689). A smaller cap spreads a long prompt over more steps: its own TTFT grows, and the other requests get more room in each step.

Step 5: bytes per token: block size, prefix caching, KV dtype, quantization

  • --block-size: 16 tokens unless an attention backend needs another size ({{cite vllm/config/cache.py:182}}; {{link concepts/attention-backends}}). The block size does not change the bytes per token. It changes the rounding: a request uses cdiv(tokens, block_size) blocks, and only full blocks are cached for prefix hits.
  • --enable-prefix-caching: on by default for generative decoder and hybrid models ({{cite vllm/engine/arg_utils.py:3062-3063}}). Requests with a shared prefix share blocks and skip that part of the prefill ({{link concepts/prefix-caching}}). It changes no block count, but more requests fit when they share blocks.
  • --kv-cache-dtype fp8: 1 byte per value instead of 2, so the page size and the bytes per token halve (derived from {{cite vllm/v1/kv_cache_interface.py:571-575}}). The default auto uses the model data type ({{cite vllm/config/cache.py:232-233}}), unless the checkpoint declares a KV cache scheme, for example an FP8 one ({{cite vllm/utils/torch_utils.py:503-521}}, {{cite vllm/model_executor/layers/attention/attention.py:287-291}}). Without scales in the checkpoint, the layer uses the scale 1.0 ({{cite vllm/model_executor/layers/attention/attention.py:133-154}}). Check the output quality of your model after the change ({{deepinfer learn/number-formats | Number formats}}).
  • --quantization: smaller weights leave more memory for the KV cache. The default is the quantization_config of the checkpoint ({{cite vllm/config/model.py:264-268}}); see {{link learn/quantized-checkpoints}} and {{link concepts/quantization-plugins}}.

Step 6: compile, CUDA graphs and -O levels: start-up time against step time

The default optimization level is O2 ({{cite vllm/config/vllm.py:434}}). O2 compiles the model with torch.compile and captures FULL and PIECEWISE CUDA graphs ({{cite vllm/config/vllm.py:131-143}}, {{cite vllm/config/vllm.py:310}}). {{link concepts/compile-and-cuda-graphs}} explains both. For tuning, the trade is simple: compile and capture cost start-up time and some memory, and save launch overhead in every step ({{deepinfer concepts/cuda-graphs | CUDA graphs}}).

  • -O0 or --enforce-eager: no compile, no graphs. --enforce-eager sets the compile mode and the graph mode to NONE ({{cite vllm/config/vllm.py:1745-1747}}). Start-up is fastest, and the graph memory goes to the KV cache (Step 1). Every step pays the full kernel launch cost.
  • -O1: compile with PIECEWISE graphs only.
  • Capture sizes. When you set no sizes, the largest captured batch is min(max_num_seqs × decode_query_len × 2, 512) (1024 on data-center Blackwell), then at most the token budget ({{cite vllm/config/vllm.py:2439-2449}}, {{cite vllm/config/vllm.py:2530-2531}}). The sizes are 1, 2, 4, then steps of 8 up to 248, then steps of 16 ({{cite vllm/config/vllm.py:2557-2570}}). A decode batch larger than the largest size runs without a graph.
  • --performance-mode interactivity captures every size from 1 to 32 instead of 1, 2, 4, 8, 16, 24, 32 ({{cite vllm/config/vllm.py:2552-2556}}). Small batches then need less padding, and start-up captures more graphs.

The warm start matters as much as the level: the compile cache under VLLM_CACHE_ROOT makes the second start-up much shorter ({{link tours/serve-startup}}, {{link concepts/troubleshooting}}).

Step 7: async scheduling and speculative decoding: fewer idle gaps, fewer steps

Async scheduling is on by default for generative models when the executor supports it ({{cite vllm/config/vllm.py:1664-1698}}). The engine core schedules step N+1 while the GPU runs step N ({{link concepts/async-scheduling}}). Turn it off (--no-async-scheduling) only to compare.

Speculative decoding (--speculative-config, off by default, {{cite vllm/config/vllm.py:383}}) proposes k draft tokens and checks them in one target step ({{deepinfer concepts/speculative-decoding | Speculative decoding}}; {{link concepts/speculative-decoding}}). It saves steps only when drafts are accepted. The vLLM docs say that it reduces "inter-token latency under medium-to-low QPS (queries per second), memory-bound workloads" ({{cite docs/features/speculative_decoding/README.md:3}}). Their table rates the gain per method for low and high QPS ({{cite docs/features/speculative_decoding/README.md:30-39}}). Watch the acceptance with these PromQL formulas from the code ({{cite vllm/v1/spec_decode/metrics.py:178-196}}):

acceptance rate      = rate(vllm:spec_decode_num_accepted_tokens_total[5m]) / rate(vllm:spec_decode_num_draft_tokens_total[5m])
mean acceptance len  = 1 + rate(vllm:spec_decode_num_accepted_tokens_total[5m]) / rate(vllm:spec_decode_num_drafts_total[5m])

The log line "SpecDecoding metrics: Mean acceptance length: ..." shows the same values every log interval ({{cite vllm/v1/spec_decode/metrics.py:107-136}}). A mean acceptance length near 1 means that the drafts cost work and save no step.

Step 8: parallelism, API servers, streaming and priorities

  • TP or DP. {{term tensor-parallel | Tensor parallelism}} splits one model copy over several GPUs: it fits larger models and makes each step faster, with an all-reduce per layer ({{link learn/tp-pp-in-practice}}). {{term data-parallel | Data parallelism}} (-dp N) runs N engine copies; each has its own scheduler and KV cache ({{link concepts/data-parallel-serving}}). A practical rule, not a measured number: when one copy fits on one GPU, more copies give more throughput. TP gives a lower latency per request.
  • --api-server-count runs N API server processes on one port. The default is the DP size with internal load balancing, the local DP size with hybrid load balancing, else 1 ({{cite vllm/entrypoints/cli/serve.py:113-130}}). Rendering, tokenization, detokenization and JSON run in the API server ({{link concepts/openai-server}}). When the API server process is at 100 % CPU, more API servers help; the vLLM docs show --api-server-count 4 with one engine ({{cite docs/configuration/optimization.md:316-327}}). With more than one API server, the periodic log line is off and Prometheus uses a multiprocess directory ({{cite vllm/v1/metrics/loggers.py:1385-1389}}, {{cite vllm/entrypoints/cli/serve.py:282-283}}).
  • --renderer-num-workers, default 1, is the number of threads that tokenize and render chat templates in each API server ({{cite vllm/config/model.py:412-420}}, {{cite vllm/renderers/base.py:143-144}}).
  • --stream-interval N, default 1, makes the front end send a stream chunk only every N tokens, plus the first and the last ({{cite vllm/config/scheduler.py:216-220}}, {{cite vllm/v1/engine/output_processor.py:379-391}}). Fewer chunks mean less CPU work per token. A request can raise it with its own stream_interval field, never lower it ({{cite vllm/v1/engine/output_processor.py:300-302}}).
  • --scheduling-policy priority admits requests by the priority field (lower value first) and preempts the request with the largest priority value first ({{cite vllm/config/scheduler.py:159-165}}; {{link concepts/scheduler}}). The header X-Vllm-Priority overrides the body field ({{cite vllm/entrypoints/generate/base/serving.py:253-265}}). With the default fcfs, the field has no effect.

Deep dive

Start: an 80 GiB GPU and gpu_memory_utilization 0.92. The profile finds 15 GiB weights, 1 GiB other consumed memory, a 2.5 GiB activation peak and a 0.5 GiB graph estimate. These four memory values are assumptions (the same as in the figure of {{link concepts/kv-cache-manager}}); vLLM measures them on your GPU. The KV values are from the model's Hugging Face config (inferred, not in the repository). One token needs 32 layers × 8 KV heads × (128 + 128) × 2 bytes = 128 KiB. With block_size 16, one block is 2 MiB.

  1. Requested: ceil(80 GiB × 0.92) = 73.6 GiB. Available: 73.6 − (16.0 + 2.5) − 0.5 = 54.6 GiB ({{cite vllm/v1/worker/gpu_worker.py:744-748}}).
  2. Blocks: 54.6 GiB / 2 MiB = 27,955 ({{cite vllm/v1/core/kv_cache_planning.py:1610-1611}}).
  3. Concurrency: 131,072 / 16 = 8,192 blocks per full request; 27,955 / 8,192 = 3.41 ({{cite vllm/v1/core/kv_cache_utils.py:1031-1047}}).
  4. Requests that fit: one 2,500-token request uses cdiv(2500, 16) = 157 blocks; (27,955 − 1) / 157 = 178 (the null block is not usable).

Three lessons follow. First, --max-model-len changes the concurrency in the log, but not the memory: the same 178 average requests fit. Second, max_num_seqs 1024 does not bind here: the KV cache stops this workload at about 178 running requests, so a larger max_num_seqs changes nothing. Third, the KV dtype doubles the capacity; the other knobs give a few percent.

In one step at that load, 178 decode tokens use 178 of the 8,192 budget tokens. About 8,014 tokens are left for prefill chunks, so a new 2,500-token prompt fits into one step (derived from the order in {{cite vllm/v1/core/sched/scheduler.py:713-715}}).

On one 80 GiB H100 with the defaults (max_num_seqs 1024, budget 8,192, no speculative decoding):

  1. Largest size: min(1024 × 1 × 2, 512) = 512, then min(8192, 512) = 512 ({{cite vllm/config/vllm.py:2442-2450}}, {{cite vllm/config/vllm.py:2530-2531}}).
  2. Sizes: 1, 2, 4 (3 sizes); 8, 16, ..., 248 (31 sizes); 256, 272, ..., 512 (17 sizes) = 51 sizes ({{cite vllm/config/vllm.py:2557-2570}}).
  3. With --performance-mode interactivity: 1 to 32 (32 sizes) plus 40, ..., 248 (27 sizes) plus the 17 large sizes = 76 sizes (derived from {{cite vllm/config/vllm.py:2552-2570}}).
  4. On an A100 with 2,048 tokens and 256 sequences: min(256 × 2, 512) = 512, so again 51 sizes.

Each size is captured for each graph mode that applies, so more sizes mean a longer capture at start-up and more graph memory. A decode batch of 600 requests is above 512 and runs without a CUDA graph ({{link concepts/compile-and-cuda-graphs}}).

The docstring of the field says that interactivity uses "fine-grained CUDA graphs, latency-oriented kernels" and throughput uses "larger CUDA graphs, more aggressive batching, throughput-oriented kernels" ({{cite vllm/config/vllm.py:440-445}}). At this commit, the code reads the field in two places only: the doubling of the batch defaults ({{cite vllm/engine/arg_utils.py:3171-3175}}) and the interactivity capture sizes ({{cite vllm/config/vllm.py:2552-2556}}). A search of vllm/ finds no other reader of performance_mode (a git grep at the pinned commit; open question for later commits). The doubling applies only to values that you did not set. A mode other than balanced is logged: "Performance mode set to ..." ({{cite vllm/config/vllm.py:1518-1519}}).

This method is advice, not code. Each step names the signal that the code gives.

  1. Read the start-up log: "Available KV cache memory", "GPU KV cache size: N tokens, Maximum concurrency ..." ({{cite vllm/v1/worker/gpu_worker.py:763-766}}, {{cite vllm/v1/core/kv_cache_utils.py:1101-1108}}). If the concurrency for your real request length is low, fix memory first (Step 1, Step 5).
  2. Run vllm bench serve with your request lengths at several request rates ({{link concepts/benchmarking}}).
  3. Watch vllm:num_requests_waiting, vllm:kv_cache_usage_perc and rate(vllm:num_preemptions_total[1m]) during the run ({{link concepts/metrics-and-observability}}). Waiting requests with low KV usage point to the token budget or max_num_seqs; high KV usage with preemptions points to memory.
  4. Change one knob at a time, and compare the goodput at the same SLO.

Why it matters. Most slow servers have one binding limit: KV memory, the token budget, the batch width or the CPU of the front end. Know the code path of each knob. Then the start-up log and four metrics show the limit, and you change the right knob.

Which two values set max_num_seqs and max_num_batched_tokens when you start vllm serve without these flags?

The usage context (OPENAI_API_SERVER for vllm serve) and the memory of one GPU, plus a name check for A100 and GB10 ({{cite vllm/engine/arg_utils.py:2958-2993}}). --performance-mode throughput then doubles both ({{cite vllm/engine/arg_utils.py:3171-3175}}).

 The log says "Maximum concurrency for 131,072 tokens per request: 3.41x". Can the server run only 3 requests at once?

No. The value is blocks divided by the blocks of one request of max_model_len ({{cite vllm/v1/core/kv_cache_utils.py:1031-1047}}). Shorter requests use fewer blocks, so many more fit; the running count is limited by max_num_seqs and the real request lengths.

 You set --max-num-seqs 2048 --max-num-batched-tokens 1024. What happens?

Start-up stops with ValueError: the token budget must be at least max_num_seqs ({{cite vllm/config/scheduler.py:331-335}}). vLLM caps max_num_seqs only when it fills the default itself ({{cite vllm/engine/arg_utils.py:3219-3221}}).

 Why can a larger --max-num-batched-tokens lower the KV cache size?

The profile run uses max_num_batched_tokens tokens ({{cite vllm/v1/worker/gpu/model_runner.py:231}}, {{cite vllm/v1/worker/gpu/model_runner.py:1022-1027}}). A larger run has a larger activation peak, and the peak is subtracted from the requested memory ({{cite vllm/utils/mem_utils.py:318-321}}, {{cite vllm/v1/worker/gpu_worker.py:744-748}}).

 In the worked example, 178 requests of 2,500 tokens fit, and max_num_seqs is 1024. You raise max_num_seqs to 2048. What changes, and what does not?

The KV cache still holds only about 178 such requests: the block count comes from memory, not from max_num_seqs (deep dive "Worked example"). The scheduler admits a request only when its tokens fit in free blocks ({{cite vllm/v1/core/kv_cache_manager.py:522-539}}), so the running count stays near 178. Three things do change. The per-request buffers of the runner grow. The default capture size stays at 512, because min(2048 × 2, 512) = 512 ({{cite vllm/config/vllm.py:2442-2450}}). The compile hash changes, so start-up compiles again ({{cite vllm/config/scheduler.py:271-284}}).
