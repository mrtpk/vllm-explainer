The GPU tensors live in the workers.

The idea

The KV cache is split into fixed blocks, and each request has a table of its blocks ({{deepinfer learn/kv-cache | The KV cache}}, {{deepinfer concepts/paged-kv-cache | Paged KV cache}}). In vLLM the blocks are 16 tokens by default. This page explains who manages them in vLLM, and how.

The manager runs in the {{term engine-core}} process, next to the {{term scheduler}}. It never touches GPU memory. It keeps one small Python object per block, a {{term kv-cache-block}}, with an id, a reference count and an optional hash. The real KV tensors live in the workers, one copy per GPU. The scheduler decides; the workers only receive block ids in the {{term scheduler-output}} and write into those blocks.

The manager has four layers. KVCacheManager is the API that the scheduler calls. A KVCacheCoordinator spreads each call over the {{term kv-cache-group | KV cache groups}}. A SingleTypeKVCacheManager per group knows the rules of one attention type, for example full attention or a sliding window. One {{term block-pool}} owns all blocks and the {{term free-block-queue}}. A plain decoder model such as Llama has one group, so the coordinator is a thin wrapper.

The pool shares blocks through reference counts. Two requests with the same prefix can point to the same full block. The block returns to the free queue only when its count reaches 0. A free block keeps its hash, so it can still serve a prefix-cache hit until the pool reuses it ({{link learn/prefix-caching}}). How many blocks exist is decided once, at start-up, from a memory profile of the GPU.

An everyday comparison. Think of a warehouse office. The office keeps a ledger of shelf numbers: who rents which shelf, which shelves hold a well-known kit, and which are empty. The workers in the warehouse only get shelf numbers and do the lifting. The comparison stops at the empty shelves. An empty shelf in vLLM still holds its old contents. A new tenant who needs the same kit can take it as it is.

The scheduler builds the manager in its __init__, with the KV cache configuration from start-up and the prefix caching flag:

The manager builds the coordinator ({{cite vllm/v1/core/kv_cache_manager.py:167-180}}). The factory picks one of three classes: no prefix caching, exactly one KV cache group, or several groups:

Every coordinator makes one BlockPool with kv_cache_config.num_blocks blocks, and one single-type manager per KV cache group, all on the same pool. The only exception is the host group of HiSparse, which replaces the pool of its manager with a private host pool ({{cite vllm/v1/core/single_type_kv_cache_manager.py:2231-2247}}). For this reason a block remembers its pool, and free_blocks sends a block of another pool back to that pool ({{cite vllm/v1/core/block_pool.py:792-794}}, {{cite vllm/v1/core/block_pool.py:808-809}}).

A registry maps each spec class to a manager class: FullAttentionSpec and MLAAttentionSpec to FullAttentionManager, SlidingWindowSpec to SlidingWindowManager, MambaSpec to MambaManager, and more ({{cite vllm/v1/core/single_type_kv_cache_manager.py:2645-2715}}). A platform can register its own specs ({{cite vllm/v1/core/single_type_kv_cache_manager.py:2717-2719}}). Models with several groups (for example sliding window plus full attention) are the topic of {{link concepts/hybrid-kv-cache}}.

Step 2: KVCacheBlock and the BlockPool

A block has an id from 0 to num_gpu_blocks - 1 and a reference count. It has a hash only when it is full and cached, and two links for the free queue. The pool makes all blocks at once, puts them all in the free queue, and takes out block 0:

Block 0 becomes the {{term null-block}}. No request gets it as a real block. Managers put it in block tables at places that hold no data, for example blocks that a sliding window has left ({{cite vllm/v1/core/single_type_kv_cache_manager.py:311-312}}). So a pool of N blocks has N − 1 usable blocks.

The free queue is a doubly linked list through the blocks themselves, so it can remove a block from the middle in O(1) ({{cite vllm/v1/core/kv_cache_utils.py:258-279}}). Its order is the LRU order of prefix caching, which {{link learn/prefix-caching}} explains in its deep dive "Free blocks, LRU order and eviction".

Step 3: allocate_slots, the count

The scheduler calls {{term allocate-slots}} for every scheduled request. A running request passes only num_new_tokens. A new request also passes its prefix-cache hit. The method first counts, and changes nothing until it knows that the blocks fit:

  1. Lines 501-507. The tokens that already have KV values: the computed tokens, plus the new prefix-cache hit, plus tokens from a KV connector.
  2. Lines 512-516. A watermark (default 0) applies only to waiting and preempted requests, and only when other requests run.
  3. Lines 522-539. The admission gate for new requests: all their tokens (at most max_model_len) must fit, not only the first chunk (scheduler_reserve_full_isl, default True). Sliding-window and chunked-local groups cap this count, because they free blocks as the request moves on ({{cite vllm/v1/core/single_type_kv_cache_manager.py:215-227}}). The scheduler passes the flag only in the waiting pass.
  4. Lines 541-544. The slots needed: computed plus new tokens, plus num_lookahead_tokens for speculative decoding, at most max_model_len.

The single-type manager turns slots into blocks. For a running request, it is the difference between the blocks needed and the blocks held:

For a new request, it also counts the prefix-cache hits that are free right now (ref_cnt == 0). The request will take them out of the free queue, so they use up free capacity too ({{cite vllm/v1/core/single_type_kv_cache_manager.py:256-266}}).

Step 4: allocate_slots, the changes

  1. Lines 555-559. Blocks that the attention no longer reads (outside a sliding window) go back first, so the pool has more free blocks. For full attention this does nothing.
  2. Lines 561-579. The count, then the check: not enough free blocks means return None. Nothing has changed yet. The scheduler then preempts a request or stops its waiting pass.
  3. Lines 581-593. A new request adopts its prefix-cache hit. The manager touches the hit blocks (ref_cnt += 1, out of the free queue). Then it puts them at the start of the request's {{term block-table}} ({{cite vllm/v1/core/single_type_kv_cache_manager.py:303-318}}).
  4. Lines 595-600. New blocks for the rest. The single-type manager takes them from the front of the free queue ({{cite vllm/v1/core/single_type_kv_cache_manager.py:400-410}}). The pool removes an old hash from a reused block (this is the eviction) and sets ref_cnt to 1 ({{cite vllm/v1/core/block_pool.py:681-700}}).
  5. Lines 604-605. With an asynchronous KV load, the blocks are not cached yet: the data is not there.
  6. Lines 612-616. The blocks that are now full get a hash, so later requests can hit them. Draft tokens are left out: the count stops at request.num_tokens.

The return value holds only the new blocks of this call. For a new request, the scheduler reads all its blocks with get_blocks() instead ({{cite vllm/v1/core/sched/scheduler.py:1432-1434}}).

Step 5: free, in reverse order

When a request finishes or is preempted, the scheduler calls free() ({{cite vllm/v1/core/sched/scheduler.py:2866-2872}}). Each single-type manager gives its blocks back, last block first:

BlockPool.free_blocks lowers each ref_cnt. A block that reaches 0 goes back into the free queue: at the front without a hash, at the end with a hash ({{cite vllm/v1/core/block_pool.py:776-807}}). A block that another request still uses stays out of the queue. Because the last block comes first, the tail of a cached prefix is evicted before its head. Prefix caching itself (hashes, lookup, eviction) is the topic of {{link concepts/prefix-caching}}.

Step 6: how the block ids reach the worker

The manager returns KVCacheBlocks, a tuple with one list per KV cache group. The scheduler turns it into ids:

A new request carries all its ids in NewRequestData.block_ids. A running request carries only the ids of new blocks in CachedRequestData.new_block_ids, or None when it got no new block ({{cite vllm/v1/core/sched/output.py:47}}, {{cite vllm/v1/core/sched/output.py:140-150}}, {{cite vllm/v1/core/sched/scheduler.py:1821-1823}}). Model Runner V2 writes them into its block tables on the GPU. It overwrites the row of a new request and appends to the row of a running one:

The block table is an int32 tensor [max_num_reqs, max_num_blocks] per KV cache group ({{cite vllm/v1/worker/gpu/block_table.py:65-71}}). The slot of a token is block_id × block_size + offset ({{cite vllm/v1/worker/gpu/block_table.py:409}}). A preempted request leaves the runner like a finished one ({{cite vllm/v1/worker/gpu/model_runner.py:1178-1185}}). When it resumes, it comes back as a new request with a fresh list of block ids ({{cite vllm/v1/core/sched/scheduler.py:1505-1507}}). The page {{link concepts/model-runner}} explains the runner side.

Step 7: how many blocks, from the memory profile

The number of blocks is fixed once, in EngineCore._initialize_kv_caches. Each worker measures the memory that is left for the KV cache ({{cite vllm/v1/engine/core.py:297-301}}). The executor and worker pages explain the {{term profile-run}} and the formula ({{link concepts/executors-and-workers}}):

Then the engine core divides the bytes by the bytes of one block, over all layers of the group:

The engine core gets bytes_per_block from a probe layout with one block. For a plain model, that is the sum of the page sizes of all layers. A helper computes the same divisor directly ({{cite vllm/v1/core/kv_cache_planning.py:251-262}}):

The page of one layer is num_kv_heads × block_size × (head_size + head_size_v) × dtype bytes ({{cite vllm/v1/kv_cache_interface.py:571-579}}, {{cite vllm/v1/kv_cache_interface.py:254-255}}). With several workers (TP), every worker gets the smallest block count of all workers ({{cite vllm/v1/core/kv_cache_planning.py:1622-1636}}). The result goes into cache_config.num_gpu_blocks, which the scheduler reads ({{cite vllm/v1/engine/core.py:324-325}}, {{cite vllm/v1/core/sched/scheduler.py:207-208}}).

Two settings change the input of this division:

  • --gpu-memory-utilization, default 0.92: the share of the whole GPU that this vLLM instance may use, for weights, activations and KV cache together ({{cite vllm/config/cache.py:212-221}}).
  • --kv-cache-memory-bytes: a fixed KV cache size per GPU. The worker then skips the memory measurement, and gpu_memory_utilization has no effect ({{cite vllm/config/cache.py:371-378}}, {{cite vllm/v1/worker/gpu_worker.py:653-679}}).

Step 8: what "KV cache usage" means

The usage that vLLM reports is the share of blocks that are not in the free queue:

When stats are on, the scheduler puts this value into its stats every step ({{cite vllm/v1/core/sched/scheduler.py:3023-3024}}, {{cite vllm/v1/core/sched/scheduler.py:3050}}). The front end shows it as the gauge vllm:kv_cache_usage_perc, with values from 0 to 1 in spite of its name ({{cite vllm/v1/metrics/loggers.py:619-623}}). The log line shows "GPU KV cache usage: x%" ({{cite vllm/v1/metrics/loggers.py:314-320}}).

A free block that still holds a cached prefix is in the free queue, so it counts as free. A server with a warm prefix cache can show a low {{term kv-cache-usage}} while most blocks still hold useful data. The usage tells you how close the running requests are to preemption, not how full the prefix cache is.

The docstring of allocate_slots draws the token ranges of one call ({{cite vllm/v1/core/kv_cache_manager.py:420-452}}):

| comp | new_comp | ext_comp | new | lookahead |
comp      = request.num_computed_tokens          (blocks already held)
new_comp  = num_new_computed_tokens              (local prefix-cache hit, this call)
ext_comp  = num_external_computed_tokens         (KV connector hit)
new       = num_new_tokens                       (to compute; may include draft tokens)
lookahead = num_lookahead_tokens                 (slots for the drafter)

Allocated: everything after comp. Computed in this step: new and lookahead. Cached: up to min(comp + new_comp + ext_comp + new, request.num_tokens) ({{cite vllm/v1/core/kv_cache_manager.py:612-615}}).

The method raises ValueError when a call asks for 0 new tokens and adopts no computed tokens ({{cite vllm/v1/core/kv_cache_manager.py:474-482}}). With prefix-cache retention of some groups (Mamba, sliding window), the hit is first cut to the reused prefix (lines 484-497).

Llama-3.1-8B has 32 layers, 8 KV heads and a head size of 128; the KV cache is BF16 (2 bytes). These model values are from its Hugging Face config (inferred, not in the vLLM repo).

  1. One layer, one block. 8 heads × 16 tokens × (128 + 128) × 2 bytes = 65,536 bytes = 64 KiB ({{cite vllm/v1/kv_cache_interface.py:571-579}}).
  2. One block, all layers. 32 × 64 KiB = 2 MiB ({{cite vllm/v1/core/kv_cache_planning.py:587-593}}).
  3. Blocks. With 54.6 GiB available (figure above): 55,910 MiB / 2 MiB = 27,955 blocks ({{cite vllm/v1/core/kv_cache_planning.py:1610-1612}}). Block 0 is the null block, so 27,954 blocks can hold tokens.
  4. Tokens. 27,955 × 16 = 447,280 token slots.
  5. Concurrency. With max_model_len 131,072, one full-length request needs 8192 blocks. 27,955 / 8192 = 3.41. The start-up log prints "GPU KV cache size: 447,280 tokens, Maximum concurrency for 131,072 tokens per request: 3.41x" ({{cite vllm/v1/core/kv_cache_utils.py:1090-1108}}, {{cite vllm/v1/core/kv_cache_utils.py:1015-1047}}).

The capacity log counts all num_blocks, including the null block (derived from the lines above). The difference of one block does not matter in practice.

At runtime, a chat request with 2000 prompt tokens and 500 output tokens holds cdiv(2500, 16) = 157 blocks at its end. That is 0.56 % of the pool. Its KVCacheBlock objects take some bytes of CPU memory each; the KV data (314 MiB) is on the GPU (derived).

What can go wrong

  • Start-up fails with "No available memory for the cache blocks". The weights and the profile run used all of gpu_memory_utilization. Raise the value, or lower max_num_batched_tokens (it sets the size of the profile run) ({{cite vllm/v1/core/kv_cache_planning.py:56-64}}).
  • Start-up fails because one request of max_model_len does not fit. Lower --max-model-len to the estimate in the error, or add memory ({{cite vllm/v1/core/kv_cache_planning.py:68-87}}).
  • Many preemptions. The pool is too small for the running requests. See {{link concepts/scheduler}}.
  • Another process on the same GPU. gpu_memory_utilization is a share of the whole GPU, and the worker checks at start-up that this much memory is free ({{link concepts/executors-and-workers}}). Two instances on one GPU need two shares that add up to less than 1.
  • The usage metric looks low, but prefix hits drop. Cached blocks count as free (Step 8); new requests evict them from the front of the free queue.

Why it matters. The number of blocks sets how many tokens can be in flight at the same time. Too few blocks give preemptions and short batches; prefix-cache hits save blocks and prefill time. To tune memory, you must know where the block count comes from and what the usage metric counts.

Which process holds the KVCacheBlock objects, and which holds the KV tensors?

The engine core process holds the KVCacheBlock objects in the BlockPool of the scheduler's manager ({{cite vllm/v1/core/sched/scheduler.py:329}}, {{cite vllm/v1/core/block_pool.py:171-174}}). The workers hold the KV tensors on their GPUs and only receive block ids ({{cite vllm/v1/worker/gpu/model_runner.py:1266-1269}}).

 Why does a pool of 1000 blocks give requests at most 999?

The pool takes block 0 out of the free queue at start-up and makes it the null block ({{cite vllm/v1/core/block_pool.py:184-188}}). The usage formula also leaves it out ({{cite vllm/v1/core/block_pool.py:888-892}}).

 A running request has 32 computed tokens and 3 blocks of 16. It gets 1 new token. How many new blocks does allocate_slots take, and why?

None. It needs cdiv(32 + 1, 16) = 3 blocks and holds 3, so the difference is 0 ({{cite vllm/v1/core/single_type_kv_cache_manager.py:214}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:230-236}}). It needs a 4th block only when it reaches 49 tokens.

 The usage gauge shows 0.10, but the prefix-cache hit rate falls. How can both be true?

Usage counts only blocks outside the free queue ({{cite vllm/v1/core/block_pool.py:881-892}}). Cached blocks with ref_cnt 0 are in the free queue, and get_new_blocks evicts them from the front when new requests need blocks ({{cite vllm/v1/core/block_pool.py:681-700}}). A low usage says nothing about how many cached prefixes survive.

 A new request has 3 prefix-cache hit blocks that are free (ref_cnt 0) and needs 1 more block. The pool has exactly 3 free blocks. Does allocate_slots succeed?

No. The count adds the free hit blocks to the new blocks: 1 + 3 = 4 ({{cite vllm/v1/core/single_type_kv_cache_manager.py:256-266}}). The 3 free blocks in the queue are exactly the hit blocks, so 4 > 3 and the method returns None. The admission gate finds this first; the second check would give the same result ({{cite vllm/v1/core/kv_cache_manager.py:537-539}}, {{cite vllm/v1/core/kv_cache_manager.py:575-579}}). Touching the hits would take them out of the free queue, and nothing would be left for the new block.
