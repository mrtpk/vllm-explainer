The input thread hashes each new request, the scheduler looks the hashes up in the block pool and touches the hits, allocate_slots hashes blocks that become full, and the free queue decides what to evict. KV events tell an external router what each engine holds. scripts: viz/prefix_cache_explorer.js --- The engine core names each full block by a chained hash, looks up the hashes of new requests, and evicts cached blocks only for space.

The idea

The page {{link learn/prefix-caching}} teaches the idea: why chat traffic repeats, the {{term hash-chain}}, the extra keys, two chat turns and the metrics. Read it first. This page shows who does each part in the engine core, when, and with which data. It also covers what the basics page leaves out. That is the hash types, the lookup code and the moment a block gets its hash. It is also the reset route, external hits from a KV connector, and KV events.

Four parts work together, all in the {{term engine-core}} process:

  1. The hasher. When a request arrives, the input thread computes one {{term block-hash}} per full block of its tokens. When the request gets new tokens, the hasher adds the hashes of new full blocks.
  2. The lookup. When the scheduler admits a request, the KV cache manager walks the hashes from block 0 and stops at the first miss. It never looks past num_tokens − 1 tokens ({{term cache-hit-cap}}).
  3. The cache. When allocate_slots() gives a request its blocks, the blocks that will be full after this step get their hash. From then on, other requests can hit them.
  4. The eviction. A freed block keeps its hash in the {{term free-block-queue}}. Normally its hash goes away only when the pool hands the block out again, or when somebody resets the cache. A failed load from a KV connector can also evict hashes ({{cite vllm/v1/core/sched/scheduler.py:3515-3516}}).

An everyday comparison. Think of a library that keeps photocopies of book chapters. Each copy has a label that names the book and all earlier chapters. A reader asks for chapters 1 to 5. The desk checks the labels in order and stops at the first chapter that has no copy. Old copies stay on a "free" shelf, and the library recycles the oldest copy only when it needs paper. The comparison stops at the label: vLLM does not compare text. Two blocks match when their hashes are equal, and the hash includes every earlier token.

The picture

Read the panels from top to bottom. Panel 2 is get_computed_blocks(): a miss ends the walk, because every later hash includes the missed one. Panel 3 is the first part of allocate_slots(). touch() runs before get_new_blocks(), so the request cannot pop and evict its own hit blocks.

The explorer follows these rules of the real code:

  1. Only full blocks get a hash. The hash of block i uses the hash of block i − 1, and block 0 uses NONE_HASH ({{cite vllm/v1/core/kv_cache_utils.py:988-1008}}, {{cite vllm/v1/core/kv_cache_utils.py:731-737}}).
  2. The lookup checks at most (num_tokens − 1) // block_size hashes and stops at the first miss ({{cite vllm/v1/core/kv_cache_manager.py:295-300}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:791-799}}).
  3. A request starts only if its new blocks plus its free hit blocks fit in the free queue ({{cite vllm/v1/core/single_type_kv_cache_manager.py:256-266}}, {{cite vllm/v1/core/kv_cache_manager.py:575-579}}).
  4. touch() adds 1 to ref_cnt and takes a free hit block out of the queue ({{cite vllm/v1/core/block_pool.py:761-768}}). Only then does get_new_blocks() pop new blocks from the front and evict their old hashes ({{cite vllm/v1/core/block_pool.py:681-691}}).
  5. The blocks that are full now get their hash; an equal hash on a second block is kept as a duplicate ({{cite vllm/v1/core/block_pool.py:273-299}}, {{cite vllm/v1/core/block_pool.py:48-52}}).
  6. A finished request frees its blocks in reverse order. At ref_cnt 0, a block without a hash goes to the front, a block with a hash to the back ({{cite vllm/v1/core/single_type_kv_cache_manager.py:597-598}}, {{cite vllm/v1/core/block_pool.py:795-807}}).
  7. Block 0 is the {{term null-block}}; the pool never hands it out ({{cite vllm/v1/core/block_pool.py:184-188}}).

The explorer has no steps, no token budget and no chunked prefill. Send admits the whole prompt at once, and +1 token adds one generated token. The real scheduler computes the KV of a new token in the step after the sampler gives it. When no block is free, it preempts a running request ({{link concepts/scheduler}}). The explorer has one KV cache group and no {{term extra-keys}}, and its hash is FNV-1a over a text string, not SHA-256 over pickled data.

In the code

Step 1: the hasher is made once, and runs when a request arrives

EngineCore.__init__ first resolves the hash granularity, hash_block_size. With one {{term kv-cache-group}}, it is the block size ({{cite vllm/v1/engine/core.py:173-175}}, {{cite vllm/v1/core/kv_cache_utils.py:840-858}}). Then it makes the request hasher, but only when prefix caching or a KV connector is on:

  1. Line 217. No prefix caching and no connector: request_block_hasher stays None, and requests get no hashes at all.
  2. Lines 218-221. The hash function comes from --prefix-caching-hash-algo. init_none_hash() sets the module-level {{term none-hash}} for this process.
  3. Lines 223-225. get_request_block_hasher() returns a closure over the block size and the hash function ({{cite vllm/v1/core/kv_cache_utils.py:953-1012}}).

Each new Request gets this function and calls it in its constructor ({{cite vllm/v1/engine/core.py:1128}}, {{cite vllm/v1/request.py:225-230}}). In vllm serve, the input thread of the engine core process builds the Request while the main thread runs the model ({{cite vllm/v1/engine/core.py:1114-1119}}, {{cite vllm/v1/engine/core.py:1990-1993}}). So the hashing of a long prompt does not delay the current step.

When the scheduler appends a sampled token, the request runs the hasher again ({{cite vllm/v1/core/sched/scheduler.py:2598-2599}}, {{cite vllm/v1/request.py:272-288}}). The hasher starts after the last hash and returns an empty list until a new block is full ({{cite vllm/v1/core/kv_cache_utils.py:967-972}}). So request.block_hashes always covers every full block of the known tokens.

Step 2: the hash types

  • BlockHash is the raw digest of one block: 32 bytes for sha256, 16 bytes for the xxHash 128-bit options ({{cite vllm/utils/hashing.py:41}}, {{cite vllm/utils/hashing.py:69}}).
  • BlockHashWithGroupId appends the KV cache group id as 4 big-endian bytes. The hash map uses this key, so the same tokens in two groups are two entries (line 69).
  • ExternalBlockHash is what KV events publish. By default VLLM_KV_EVENTS_USE_INT_BLOCK_HASHES=1 turns the digest into a 64-bit integer: the low 64 bits of the big-endian number (line 85, {{cite vllm/envs.py:2022-2024}}).

Step 3: the hash function and NONE_HASH

The four names of --prefix-caching-hash-algo and their serialization are in the basics page ({{link learn/prefix-caching}}, deep dive "The hash chain in the code"). In short: sha256 (the default) pickles the tuple (parent, tokens, extra_keys); the _cbor options use canonical CBOR, so other languages can compute the same hash ({{cite vllm/utils/hashing.py:26-81}}).

The comment above NONE_HASH gives the reason for the two seeds. A cryptographic hash can use a fixed, public seed, so independent processes compute equal hashes and can share a cache. A non-cryptographic hash keeps a secret random seed, because a known seed would let an attacker build colliding blocks ({{cite vllm/v1/core/kv_cache_utils.py:90-101}}). PYTHONHASHSEED overrides both ({{cite vllm/v1/core/kv_cache_utils.py:125-130}}).

Step 4: extra keys

generate_block_hash_extra_keys() joins four lists in a fixed order: LoRA, multimodal items, cache salt, prompt-embedding digests. Without any key it returns None, so a plain text block hashes (parent, tokens, None):

The basics page explains each key ({{link learn/prefix-caching}}, deep dive "Extra keys"). KV events publish the keys without their tags: a bare LoRA name, a bare salt, (identifier, offset) pairs for images ({{cite vllm/v1/core/kv_cache_utils.py:678-704}}).

Step 5: the lookup

The scheduler asks for the hit only in the waiting pass, and only for a request with num_computed_tokens == 0: a new or a preempted request ({{cite vllm/v1/core/sched/scheduler.py:1016-1024}}). KVCacheManager.get_computed_blocks() does the work:

  1. Lines 286-287. No lookup when prefix caching is off, or when the request sets skip_reading_prefix_cache ({{cite vllm/v1/core/kv_cache_manager.py:249-251}}). Sampling parameters set it for prompt logprobs; pooling parameters can set it too ({{cite vllm/sampling_params.py:625-632}}, {{cite vllm/v1/request.py:314-325}}).
  2. Line 295. The {{term cache-hit-cap}}: the last token must be computed, so it gives logits.
  3. Lines 296-300. The coordinator finds the hit. With one group, UnitaryKVCacheCoordinator calls the manager of that group directly ({{cite vllm/v1/core/kv_cache_coordinator.py:574-591}}).

For full attention, the walk is short:

Line 793 checks only max_length // block_size hashes. Line 794 asks the pool for a block per group. get_cached_block() builds the key from the hash and the group id. It returns the first block with that key, or None ({{cite vllm/v1/core/block_pool.py:198-224}}). A model with several groups needs one hit length that is valid for every group; {{link concepts/hybrid-kv-cache}} explains that search.

Step 6: adopting the hit

The scheduler passes the hit blocks to allocate_slots(). The count check includes free hit blocks, because touch() will take them out of the free queue ({{link concepts/kv-cache-manager}}, Step 3). If the blocks fit, allocate_slots() adds the hit blocks first and allocates the new blocks after that ({{cite vllm/v1/core/kv_cache_manager.py:581-600}}). The coordinator adds the hits in two phases. First it touches the hit blocks of every group, then it allocates blocks for external tokens of a KV connector. The comment names the bug that this order prevents:

Line 305 is the {{term touch}}. Line 318 records that the hit blocks are already cached, so the caching step does not hash them again. Line 312 puts null blocks where a sliding window has skipped blocks (see {{link concepts/hybrid-kv-cache}}).

Step 7: caching blocks that become full

At the end of allocate_slots(), the manager hashes every block that will be full after this step:

  1. Lines 604-605. With an asynchronous load from a KV connector, the data is not there yet, so caching waits. The scheduler caches these blocks when the transfer is done ({{cite vllm/v1/core/sched/scheduler.py:3254-3257}}).
  2. Lines 612-616. Otherwise it caches up to computed + new tokens, but not past request.num_tokens. So draft tokens never get a hash. The hash is set when the step is scheduled, before the GPU computes the KV values.

The default AsyncScheduler plans the next step before the sampled token is known. That token is a placeholder and not part of num_tokens yet, so a block that it fills is not hashed at that allocation. The block gets its hash in a later allocate_slots(), after the token arrives. When tokens arrive, the async scheduler also caches up to num_computed_tokens − num_output_placeholders tokens ({{cite vllm/v1/core/sched/async_scheduler.py:75-79}}).

The single-type manager skips the blocks that already have a hash. Then it calls the pool for the new full blocks only ({{cite vllm/v1/core/single_type_kv_cache_manager.py:531-541}}):

Lines 277-278 skip null blocks and blocks that a mask leaves out (sliding-window and Mamba groups). Lines 295-299 set the hash on the block and insert it into the map. The map does not remove duplicates: two blocks with the same hash both stay, so the block ids in running block tables never change ({{cite vllm/v1/core/block_pool.py:48-52}}).

Step 8: free, eviction and reset

{{link concepts/kv-cache-manager}} (Step 5) and the basics deep dive "Free blocks, LRU order and eviction" explain the free order and the eviction. In short, a request frees its blocks in reverse order. At ref_cnt 0, an unhashed block goes to the front and a hashed block to the back ({{cite vllm/v1/core/block_pool.py:795-807}}). get_new_blocks() pops the front and evicts the old hash ({{cite vllm/v1/core/block_pool.py:729-750}}).

A reset drops every hash at once. The API server has the route only in dev mode ({{cite vllm/entrypoints/launchers/api_server/routers.py:46-49}}):

Scheduler.reset_prefix_cache() can first preempt every running request (reset_running_requests=true), so that all blocks are free. Without it, the reset fails while any block is in use ({{cite vllm/v1/core/sched/scheduler.py:2950-2975}}, {{cite vllm/v1/core/block_pool.py:841-848}}). reset_external=true also resets the cache of the KV connector ({{cite vllm/v1/core/sched/scheduler.py:2977-2978}}). The docstring of the pool names two uses: RLHF after a weight update, and benchmarks ({{cite vllm/v1/core/block_pool.py:831-835}}).

Step 9: external hits from a KV connector

A {{link concepts/kv-connectors | KV connector}} can hold KV blocks outside this engine: in CPU memory, on disk, or in another vLLM instance. After the local lookup, the scheduler asks the connector how many tokens after the local hit it can load ({{cite vllm/v1/core/sched/scheduler.py:1026-1039}}). A request that skips the prefix cache gets 0 external tokens too ({{cite vllm/v1/core/sched/scheduler.py:1040-1041}}). The external tokens are added to the computed tokens, and an asynchronous load puts the request into WAITING_FOR_REMOTE_KVS ({{cite vllm/v1/core/sched/scheduler.py:1101-1104}}, {{cite vllm/v1/core/sched/scheduler.py:1384-1393}}). The connector uses the same block hashes, which is one reason why the hasher also runs when only a connector is on (Step 1).

Step 10: KV events

With {{term kv-events}} on, the pool queues an event for each change of the prefix cache. Turn them on with --kv-events-config ({{cite vllm/engine/arg_utils.py:1873}}):

vllm serve Qwen/Qwen3-0.6B \
  --kv-events-config '{"enable_kv_cache_events": true, "publisher": "zmq", "topic": "kv-events"}'

The KV cache manager adds the spec kind and the window size of the group to each BlockStored ({{cite vllm/v1/core/kv_cache_manager.py:703-720}}). At the end of update_from_output(), the scheduler takes the events of the pool and of the connector, and publishes one KVEventBatch per step ({{cite vllm/v1/core/sched/scheduler.py:2469-2484}}). The ZMQ publisher runs its own thread. It sends three frames per batch: the topic, an 8-byte sequence number and the msgpack payload ({{cite vllm/distributed/kv_events.py:472-507}}). With replay_endpoint, a subscriber that missed a sequence number can ask for the batches from that number on. The publisher keeps the last buffer_steps batches for this ({{cite vllm/distributed/kv_events.py:306-329}}). Each data-parallel rank adds its rank to the port ({{cite vllm/distributed/kv_events.py:530-563}}).

What an external router can do with them. A router in front of several vLLM instances can subscribe to every instance. From BlockStored and BlockRemoved it keeps, per instance, the set of block hashes that the instance holds. For a new request, the router tokenizes the prompt and computes the same hash chain. Then it sends the request to the instance with the longest run of known hashes.

This works only when the router computes the same digests: the same block size, algorithm, extra keys and NONE_HASH seed. By default, the events carry only the low 64 bits of each digest as an integer. The router must convert its digests the same way ({{cite vllm/v1/core/kv_cache_utils.py:82-85}}). The default sha256 with its fixed seed allows it; xxhash without PYTHONHASHSEED does not (Step 3). sha256 hashes a Python pickle, so a router in another language needs sha256_cbor. The repository has a small subscriber that prints the events ({{cite examples/features/kv_events/kv_events_subscriber.py:72-120}}).

By default, a prefix-cache hit emits no event, because the blocks are already known. A request can set kv_cache_report_mode to "full" in the extra arguments of its sampling parameters. Then a hit re-emits BlockStored for the reused blocks, so a gateway also learns about them ({{cite vllm/v1/request.py:126-130}}, {{cite vllm/v1/core/kv_cache_manager.py:302-310}}).

Step 11: the metrics

vllm:prefix_cache_queries and vllm:prefix_cache_hits count tokens; the basics page shows the PromQL ({{link learn/prefix-caching}}). Three details are new here:

  • The scheduler records a lookup only when the request is admitted ({{cite vllm/v1/core/sched/scheduler.py:1378-1382}}). A lookup for a request that waits is not counted.
  • A request that was preempted before is counted in separate preempted_* fields, not in queries and hits ({{cite vllm/v1/metrics/stats.py:138-155}}). No logger exports these fields, so the Prometheus counters show only first admissions.
  • The log line "Prefix cache hit rate" is a moving value over about the last 1,000 requests, not a total ({{cite vllm/v1/metrics/stats.py:39-57}}, {{cite vllm/v1/metrics/loggers.py:321-323}}).

With a KV connector, vllm:external_prefix_cache_queries and vllm:external_prefix_cache_hits count the external lookup ({{cite vllm/v1/metrics/loggers.py:685-707}}). Its queries are the tokens after the local hit ({{cite vllm/v1/core/sched/scheduler.py:1096-1099}}). vllm:prompt_tokens_cached_by_source splits the cached prompt tokens by tier: device, host, disk, p2p or external_unspecified ({{cite vllm/v1/metrics/loggers.py:781-796}}). Local hits count as device ({{cite vllm/v1/metrics/loggers.py:1174-1177}}).

Worked example. A prompt of 2,000 tokens with block size 16 has 2000 // 16 = 125 full blocks. The input thread computes 125 SHA-256 digests over pickled tuples of 16 integers: 125 × 32 = 4,000 bytes of hashes. The lookup checks at most 1999 // 16 = 124 of them, so even a complete hit computes the last 16 tokens: 2,000 − 124 × 16 = 16. If the request also generates 500 tokens, it reaches 2,500 tokens and 156 hashes. Block 156 (tokens 2,496-2,499) has no hash when the request ends. (Derived from the lines above.)

  2. Lines 776-786. Fine-grained mode only for hybrid models whose hits can end inside a block. Normal models skip it.
  3. Lines 791-799. Phase 1, the walk of the figure. hit_length is a whole number of blocks.
  4. Lines 803-822. Phase 2, only in fine-grained mode: try a partial hit inside the next block, longest first.
  5. Lines 828-829. With EAGLE or MTP drafting, drop the last matched block (or hash unit). The drafter needs the hidden states of those tokens, so they are computed again.
  6. Lines 833-837. Round down to the alignment and cut the block lists to the new length.

Assume block size 16, synchronous scheduling, and a prompt of 40 tokens that runs in one step.

  1. The request arrives. The input thread computes h0 and h1 (tokens 0-31). Tokens 32-39 fill no block.
  2. The scheduler admits it: allocate_slots(num_new_tokens=40) gets 3 blocks. It caches min(0 + 40, 40) = 40 tokens: 40 // 16 = 2 blocks get h0 and h1. The GPU has not run yet.
  3. The step runs, and the sampler gives token 40. append_output_token_ids() runs the hasher: 41 tokens, still 2 full blocks.
  4. Decode steps follow. When the request has 48 tokens, the hasher adds h2. The next allocate_slots() caches min(47 + 1, 48) = 48 tokens, so block 2 gets h2.

With the AsyncScheduler, step 4 differs. The step that computes the KV of token 47 is planned while token 47 is still a placeholder. Then request.num_tokens is 47, so that allocation caches only 47 // 16 = 2 blocks. When token 47 arrives, that step is already planned: num_computed_tokens is 48, and 1 placeholder is left. _update_request_with_output() caches 48 − 1 = 47 tokens, which adds no block ({{cite vllm/v1/core/sched/async_scheduler.py:75-79}}). The allocate_slots() of the step after that caches min(48 + 1, 48) = 48 tokens, and block 2 gets h2. (Derived from the cited lines and {{cite vllm/v1/core/sched/scheduler.py:759-763}}, with a batch queue of 2.)

What can go wrong

  • The router sends requests to the wrong instance. The router hashes with another algorithm, block size or seed than the engines. Its hashes never match the events. Use the default sha256, or set PYTHONHASHSEED on every instance, and convert digests the same way as VLLM_KV_EVENTS_USE_INT_BLOCK_HASHES ({{cite vllm/v1/core/kv_cache_utils.py:82-85}}).
  • Prompt logprobs give no cache benefit. The request skips the lookup and the external lookup ({{cite vllm/sampling_params.py:625-632}}, {{cite vllm/v1/core/sched/scheduler.py:1040-1041}}).
  • The reset route returns 404. The dev routes exist only with VLLM_SERVER_DEV_MODE ({{cite vllm/entrypoints/launchers/api_server/routers.py:46-49}}). A reset under load returns false unless you also pass reset_running_requests=true.
  • The hit rate in the log differs from Prometheus. The log uses a window of recent requests; the counters are totals since start-up ({{cite vllm/v1/metrics/stats.py:47-57}}).
  • An identical prompt still computes a whole block. The cap is num_tokens − 1, and hits are whole blocks. A prompt of 4,096 tokens hits at most 4,080 tokens with block size 16.

Why it matters. The prefix cache uses no extra memory: it has no size limit and no timer, only the order of the free queue. The metrics, a prefix-aware router and a reset after a weight update all depend on one fact. It is when a block gets its hash, and when it loses it.

Which thread computes the block hashes of a new request in vllm serve?

The input thread of the engine core process. It builds the Request in preprocess_add_request(), and the constructor runs the hasher ({{cite vllm/v1/engine/core.py:1990-1993}}, {{cite vllm/v1/request.py:225-230}}). The docstring says that this runs in parallel with the model forward ({{cite vllm/v1/engine/core.py:1114-1119}}).

 Prefix caching is off, but a KV connector is configured. Do requests get block hashes?

Yes. The engine core makes the hasher when prefix caching or a connector is on ({{cite vllm/v1/engine/core.py:217}}). The connector needs the hashes to find blocks outside the engine.

 A new request hits three blocks. Two of them have ref_cnt 0. Why does allocate_slots() touch them before it calls get_new_blocks()?

touch() removes free hit blocks from the free queue ({{cite vllm/v1/core/block_pool.py:766-768}}). If get_new_blocks() ran first, it could pop one of those blocks and evict its hash. Then the request would lose its own hit. allocate_slots() adds the hit blocks before it allocates new blocks ({{cite vllm/v1/core/kv_cache_manager.py:581-600}}). The coordinator comment gives the same rule across KV cache groups ({{cite vllm/v1/core/kv_cache_coordinator.py:291-301}}).

 With synchronous scheduling, a request has just sampled its 48th token (tokens 0-47 now exist). When does block 2 (tokens 32-47) get its hash, compared with the GPU step that computes the KV of token 47?

Before it. The hasher adds h2 as soon as the request has 48 tokens. The next allocate_slots() caches min(computed + new, num_tokens) = 48 tokens, so block 2 enters the map when that step is scheduled ({{cite vllm/v1/core/kv_cache_manager.py:612-616}}). The GPU computes the KV of the last token in that same step. See the deep dive "When exactly does a block get its hash?".

 An external router uses xxhash with a fixed seed, and the engines run with --prefix-caching-hash-algo xxhash and no PYTHONHASHSEED. Why does routing by prefix fail?

Without PYTHONHASHSEED, each engine process picks a random seed for NONE_HASH when the algorithm is xxhash ({{cite vllm/v1/core/kv_cache_utils.py:125-130}}). Every chain starts from NONE_HASH ({{cite vllm/v1/core/kv_cache_utils.py:731-732}}), so the router's hashes and the hashes in the events never match. Set the same PYTHONHASHSEED everywhere, or use sha256.
