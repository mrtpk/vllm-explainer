--- title: The hybrid KV cache: specs, groups and one manager per layer type nav_title: Hybrid KV cache level: Advanced prerequisites: concepts/kv-cache-manager, concepts/prefix-caching related: concepts/kv-cache-manager, concepts/prefix-caching, learn/prefix-caching, concepts/attention-backends, concepts/kv-connectors, code/v1-core-kv-cache-utils, code/v1-core-kv-cache-manager, code/v1-core-block-pool, concepts/tuning summary: Models that mix full attention with sliding-window, chunked-local or Mamba layers get one KV cache group per layer type. Each group has its own block table and single-type manager, all groups share one block pool, and so every group must use the same page size. Prefix caching finds one hit length that is valid for all groups. --- vLLM groups the layers with the same KV cache spec, gives each group its own block table, and shares one block pool between groups.

The idea

Many new models mix layer types. Some layers use full attention and read every earlier token. Other layers use a sliding window and read only the last few tokens, or chunked local attention, or a Mamba layer with a fixed-size state. The design document lists examples: gpt-oss, Gemma 2 and 3, Llama 4, Jamba and others ({{cite docs/design/hybrid_kv_cache_manager.md:6-21}}). If every layer kept the KV of every token, the sliding-window layers would hold blocks that they never read again.

The hybrid KV cache manager gives each layer type its own rules, on top of the {{link concepts/kv-cache-manager | KV cache manager}}:

  1. Each layer describes its cache with a {{term kv-cache-spec}}: full attention, sliding window, chunked local, MLA, Mamba and more.
  2. Layers with the same spec form a {{term kv-cache-group}}. A request has one {{term block-table}} per group.
  3. Each group gets a single-type manager that knows the rules of its spec. The {{term sliding-window-manager}} frees blocks behind the window.
  4. All groups take block ids from one {{term block-pool}}. A block id belongs to one group at a time, and it means the same bytes in every group. So every group must use the same page size in bytes ({{term page-size-unification}}).

Prefix caching still works: the coordinator finds the longest prefix that every group can reuse.

An everyday comparison. Think of a hotel with one stock of identical rooms and two kinds of guests. A long-stay guest keeps every room that he ever booked. A traveller keeps only the last two rooms and checks out of older rooms as he moves on. Both kinds of guests take rooms from the same stock, so all rooms must have the same size. The comparison stops at the room number. In vLLM, one block id stands for one page in each layer of its group, not for one place.

After loading the model, each worker asks every attention layer for its spec. A decoder layer with a sliding window returns a SlidingWindowSpec, any other decoder layer a FullAttentionSpec:

The page size of an attention spec is num_heads × num_states × (head_size + head_size_v) × dtype bytes, where num_states is the block size for normal layers ({{cite vllm/v1/kv_cache_interface.py:570-586}}, {{cite vllm/v1/kv_cache_interface.py:253-260}}). The page size of a Mamba spec comes from its state shapes, not from the block size ({{cite vllm/v1/kv_cache_interface.py:1094-1114}}).

Step 2: from specs to groups

The engine core turns the specs of all layers into groups in get_kv_cache_configs() ({{cite vllm/v1/engine/core.py:311}}). A model can bring its own grouping (SupportsKVCacheGrouping); otherwise the default builder calls get_kv_cache_groups() ({{cite vllm/v1/core/kv_cache_planning.py:1659-1670}}). It tries the simple cases first:

  1. Lines 1127-1128. With the hybrid manager off, sliding-window and chunked-local specs become full-attention specs first (Step 6).
  2. Lines 1138-1147. All layers have the same spec, or the same type: one group. A plain Llama ends here.
  3. Lines 1159-1165. Only with a block-outermost KV cache layout: a packed grouping that does not need equal page sizes ({{cite vllm/v1/core/kv_cache_planning.py:929-932}}).
  4. Lines 1170-1176. The normal hybrid path: make the page sizes equal (Step 3), then group the layers.

The grouping puts layers with the same spec into buckets. Then it cuts each bucket into groups of equal size, so every group has the same bytes per block:

The group size is the smallest bucket, or the largest bucket when the buckets are almost equal (lines 521-532). gpt-oss-20b has 12 sliding and 12 full layers, so it gets two groups of 12 (the comment at lines 526-531 names gpt-oss with EAGLE). A short group wastes memory, and the code logs a warning (lines 535-541). Line 555 takes every n-th layer, which keeps the groups equal with pipeline parallelism.

Each group becomes a KVCacheGroupSpec: the layer names and one merged spec ({{cite vllm/v1/kv_cache_interface.py:1484-1502}}, {{cite vllm/v1/core/kv_cache_planning.py:187-215}}).

Step 3: one page size for all groups

All groups use the same memory. The KV cache tensors of different groups start at byte 0 of the same allocation, and the comment explains why that is safe ({{cite vllm/v1/kv_cache_interface.py:1458-1467}}):

So one block id must cover the same bytes in every group. unify_kv_cache_spec_page_size() makes the page sizes equal:

  1. Line 375. The target is the largest page.
  2. Lines 380-389. A Mamba page does not grow with the block size, so it is padded.
  3. Lines 392-395. If the largest page is a multiple of this page, the block size of this layer grows by that factor. Its group then has a larger block size than the others.
  4. Lines 396-399. Otherwise a non-MLA attention page is padded.
  5. Lines 400-405. MLA cannot be padded: NotImplementedError, and get_kv_cache_groups() tries a full-allocation fallback.

For attention + Mamba models, the platform does most of this work before the model is built. _align_hybrid_block_size() raises the attention block size until one attention page is at least one Mamba state. Then it pads the Mamba page to the attention page:

When groups end up with different block sizes, the scheduler works in units of their least common multiple. Prefix hashes use their greatest common divisor, or --prefix-match-unit ({{cite vllm/v1/core/kv_cache_utils.py:860-891}}). BlockHashListWithBlockSize then reads the hashes of a larger block from the finer list ({{cite vllm/v1/core/kv_cache_utils.py:1111-1181}}).

Step 4: the coordinator and the single-type managers

With more than one group and prefix caching on, the manager uses the HybridKVCacheCoordinator ({{cite vllm/v1/core/kv_cache_coordinator.py:1009-1038}}). Every coordinator makes one block pool and one manager per group ({{cite vllm/v1/core/kv_cache_coordinator.py:119-125}}, {{cite vllm/v1/core/kv_cache_coordinator.py:157-172}}). Each allocation call loops over the managers ({{cite vllm/v1/core/kv_cache_coordinator.py:335-344}}). The managers differ in three methods: how many tokens the attention skips, how a prefix hit looks, and which blocks get a hash.

FullAttentionManager. It skips nothing and keeps every block until the request ends ({{cite vllm/v1/core/single_type_kv_cache_manager.py:721-732}}).

SlidingWindowManager. The next token reads only the last sliding_window tokens, so everything before them is skipped:

At the start of every allocate_slots(), the manager frees the skipped blocks and puts the null block in their place. It counts only processed tokens, because a step in flight can still read the old blocks ({{cite vllm/v1/core/kv_cache_manager.py:546-559}}):

The table keeps its length, so position i is still block i of the sequence. The worker sees the null block (id 0) at the freed places. Admission uses a cap per request, because the group frees blocks while the request runs ({{cite vllm/v1/kv_cache_interface.py:922-929}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:214-227}}).

ChunkedLocalAttentionManager. Chunked local attention reads only the tokens of the current chunk. All tokens before the start of the chunk are skipped ({{cite vllm/v1/core/single_type_kv_cache_manager.py:1418-1421}}). Its prefix hit counts all blocks before the current chunk as computed and fills them with the null block ({{cite vllm/v1/core/single_type_kv_cache_manager.py:1345-1375}}).

MambaManager. A Mamba layer keeps one {{term mamba-state}} per request, not one entry per token. The manager needs only the state after the last computed token, so it skips num_computed_tokens − 1 tokens ({{cite vllm/v1/core/single_type_kv_cache_manager.py:1966-1971}}). What it keeps depends on mamba_cache_mode:

  • "none" (prefix caching off): the Mamba block size becomes max_model_len, so one block holds the state of the whole request ({{cite vllm/model_executor/models/config.py:779-786}}). A request needs 1 + num_speculative_blocks pages ({{cite vllm/v1/kv_cache_interface.py:1120-1126}}).
  • "align" (prefix caching on): the state is stored at block boundaries, so a later request can resume from it. The Mamba block size equals the attention block size, and chunked prefill must be on ({{cite vllm/model_executor/models/config.py:762-778}}). A request holds 2 + num_speculative_blocks + num_prefill_checkpoint_blocks pages at a time; older states are freed ({{cite vllm/v1/kv_cache_interface.py:1121-1124}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:1636-1653}}).

The manager refuses prefix caching in any other mode ({{cite vllm/v1/core/single_type_kv_cache_manager.py:1437-1440}}).

Step 5: prefix caching across groups

The block pool keys every cached block by (block hash, group id), so each group caches and evicts its own blocks ({{cite vllm/v1/core/kv_cache_utils.py:60-69}}). A hit is useful only if every group has the blocks for it. The coordinator finds the longest such length with a fixed-point loop:

  1. The attention groups are sorted so that full attention comes first ({{cite vllm/v1/core/kv_cache_coordinator.py:746-750}}). Its left-to-right walk gives the first upper bound.
  2. Lines 848-855. Full attention is "downward-closed": a hit of length L is also a hit of every shorter length. So the code looks it up once and later only cuts it.
  3. Lines 876-890, 896. Each other group searches a hit of at most the current length, and may return a shorter one.
  4. Lines 903-907. If no group made the length shorter, the loop ends. A model with one full group plus one other group needs only one pass.

After the loop, the code cuts the full-attention block lists to the final length ({{cite vllm/v1/core/kv_cache_coordinator.py:909-922}}). Some group can have a longer hit than the final one. The difference is an "uncached common prefix", and the scheduler stores its end as shared_prefix_boundary ({{cite vllm/v1/core/kv_cache_coordinator.py:924-931}}, {{cite vllm/v1/core/kv_cache_manager.py:312-321}}, {{cite vllm/v1/core/sched/scheduler.py:1019-1024}}). Later, cache_blocks() keeps a hash at that boundary, so the next request can hit it in every group ({{cite vllm/v1/core/single_type_kv_cache_manager.py:510-512}}).

The sliding-window search is different from the full-attention walk. A hit at length L needs only the blocks of the last sliding_window − 1 tokens before L. So the manager searches from right to left for enough contiguous cached blocks, and fills the rest with the null block:

Not every sliding-window or Mamba block gets a hash. With the default --prefix-cache-retention-interval 0, these groups keep hashes only at "semantic checkpoints": the end of the prompt (num_prompt_tokens − 1) and shared-prefix junctions ({{cite vllm/config/cache.py:272-278}}, {{cite vllm/v1/core/kv_cache_coordinator.py:65-86}}). A mask in cache_blocks() leaves out the other blocks ({{cite vllm/v1/core/single_type_kv_cache_manager.py:1131-1142}}, {{cite vllm/v1/core/block_pool.py:277-278}}).

Step 6: when the hybrid manager or prefix caching is off

Prefix caching. The default comes from is_prefix_caching_supported. Generative decoder models, including sliding-window ones, and generative attention + Mamba hybrids get it. Hybrid pooling models, attention-free models and encoder-decoder models do not ({{cite vllm/config/model.py:2272-2291}}). With prefix caching off, the manager uses KVCacheCoordinatorNoPrefixCache for any number of groups ({{cite vllm/v1/core/kv_cache_coordinator.py:476-481}}).

The hybrid manager. --disable-hybrid-kv-cache-manager has the default None, and VllmConfig decides ({{cite vllm/config/vllm.py:2202-2273}}):

  • off on a platform without hybrid support; the base Platform says no, CUDA says yes ({{cite vllm/platforms/interface.py:1351-1353}}, {{cite vllm/platforms/cuda.py:683-684}});
  • off for chunked local attention with EAGLE, or when VLLM_ALLOW_CHUNKED_LOCAL_ATTN_WITH_HYBRID_KV_CACHE=0 (default 1, {{cite vllm/envs.py:1929-1931}});
  • off when the KV connector does not support it, with a WARNING. vLLM checks the connector only when neither flag is given;
  • an explicit --enable-hybrid-kv-cache-manager in one of the first two cases raises ValueError.

When it is off, sliding-window and chunked-local specs become full-attention specs, so every layer keeps every block. The attention still computes only the window ({{cite vllm/v1/core/kv_cache_planning.py:853-876}}). Mamba layers cannot be converted, so attention + Mamba models need the hybrid manager ({{cite vllm/config/vllm.py:2245-2256}}).

The design document says that the hybrid prefix-cache search supports exactly two attention types, full attention plus one other ({{cite docs/design/hybrid_kv_cache_manager.md:201}}). It also says that HybridKVCacheCoordinator handles exactly two KV cache groups ({{cite docs/design/hybrid_kv_cache_manager.md:221}}). A code comment says the same ({{cite vllm/v1/core/kv_cache_planning.py:464-469}}). The coordinator code has a fixed-point loop over any number of attention types (Step 5), and models without full attention get full_attention_group_id = None ({{cite vllm/v1/core/kv_cache_coordinator.py:756-759}}). The document also assumes one block size for all groups; the code allows different sizes (Step 3).

The model numbers are from the public Hugging Face config of gpt-oss-20b, not from the vLLM repo. They are 24 layers, sliding window 128, 8 KV heads, head size 64, BF16 KV cache, and max_position_embeddings 131,072. vLLM puts the window on every even layer, so 12 layers are sliding and 12 are full ({{cite vllm/model_executor/models/gpt_oss.py:174-175}}). The memory size, the batched tokens and block size 16 are assumptions. The attention backend can choose another block size ({{cite vllm/model_executor/layers/attention/attention.py:621-660}}).

  1. Specs. 12 SlidingWindowSpec(sliding_window=128) and 12 FullAttentionSpec, block size 16.
  2. Page. 8 × 16 × (64 + 64) × 2 bytes = 32 KiB for both types. The pages are equal, so no layer changes its block size.
  3. Groups. Buckets of 12 and 12: 12 < 1.5 × 12, so the group size is 12. Two groups, no padding.
  4. Bytes per block. 12 × 32 KiB = 384 KiB ({{cite vllm/v1/core/kv_cache_planning.py:578-586}}). Without the hybrid manager, one group of 24 layers: 768 KiB.
  5. Blocks. With 40 GiB for the KV cache: 41,943,040 KiB / 384 KiB = 109,226 blocks.
  6. One request of 1,200 tokens. Full group: cdiv(1200, 16) = 75 blocks. Sliding group: 1200 − 128 + 1 = 1073 skipped tokens, so 67 null places and 8 real blocks. Total 83 blocks = 31.1 MiB. Without the hybrid manager: 75 blocks of 768 KiB = 56.25 MiB.
  7. Capacity at max_model_len 131,072 (from the config). Assume 8,192 batched tokens and async scheduling, so 16,384 in-flight tokens ({{cite vllm/config/vllm.py:586-608}}). Full group: 8,192 blocks per request. Sliding group: cdiv(min(127 + 16384, 131072), 16) + 1 = 1,033 ({{cite vllm/v1/kv_cache_interface.py:922-929}}). Together 9,225 blocks, so the start-up log shows about 109,226 / 9,225 = 11.8x concurrency ({{cite vllm/v1/core/kv_cache_utils.py:1030-1047}}, {{cite vllm/v1/core/kv_cache_utils.py:1101-1107}}). Without the hybrid manager: 54,613 blocks / 8,192 = 6.7x.

All numbers after the config values are derived from the cited lines.

Gemma-3-27b has 52 sliding-window and 10 full-attention layers, according to the design document ({{cite docs/design/hybrid_kv_cache_manager.md:113}}). The code at {{cite vllm/v1/core/kv_cache_planning.py:521-556}} does this:

  1. Smallest bucket 10, largest 52. 52 is not below 1.5 × 10, so the group size is 10.
  2. Full attention: 10 layers, one group.
  3. Sliding window: cdiv(52, 10) = 6 groups. The code logs "Add 8 padding layers, may waste at most 15.38% KV cache memory".
  4. Line 555 takes layers[i::6]: groups of 9, 9, 9, 9, 8 and 8 layers. The bytes per block come from the largest group, the full group with 10 layers. So the smaller groups leave part of each block empty.

The design document draws the six sliding groups as consecutive runs: five groups of 10 and one group of 2 + 8 padding ({{cite docs/design/hybrid_kv_cache_manager.md:115-121}}). The code interleaves the layers instead (lines 543-555). The padding is the same: 7 groups × 10 layer slots for 62 layers, so 8 empty slots.

A Mamba state is the result of all earlier tokens, like a hash chain. To resume a new request at token t, the engine needs the state exactly after token t. In "align" mode, vLLM keeps the state of the last token of each step and of each block boundary ({{cite vllm/config/cache.py:301-308}}).

  • Lookup. The manager searches from right to left and takes the last cached state. It puts null blocks before it, so the hit length is (i + 1) × block_size ({{cite vllm/v1/core/single_type_kv_cache_manager.py:1518-1542}}).
  • Same-step rule. A request cannot use a state that another request cached in the current step. The manager then reports more needed blocks than the pool has, so the scheduler waits one step ({{cite vllm/v1/core/single_type_kv_cache_manager.py:1700-1708}}).
  • Free. Each step copies the state from the block of the previous step into a new block. The block of two steps ago is freed ({{cite vllm/v1/core/single_type_kv_cache_manager.py:1636-1653}}).
  • Page. The platform raised the attention block size so that one attention page holds one Mamba state, and padded the Mamba page (Step 3). For a large state, the attention block size can become several hundred tokens; the design document mentions more than 400 ({{cite docs/design/hybrid_kv_cache_manager.md:144}}).

With fine-grained hashing (--prefix-match-unit smaller than the Mamba block), hits can also end inside a block ({{cite vllm/v1/core/kv_cache_utils.py:762-801}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:1496-1516}}).

What can go wrong

  • Less KV capacity than expected with a KV connector. A connector without hybrid support turns the hybrid manager off. Sliding-window layers then keep every block ({{cite vllm/config/vllm.py:2236-2256}}). Check the start-up log for "Turning off hybrid kv cache manager".
  • An attention + Mamba model fails at start-up with a connector. The same warning; such models need the hybrid manager.
  • Prefix hits are shorter on a sliding-window model. With retention interval 0, sliding-window blocks keep hashes only at the end of a prompt and at shared-prefix junctions. A hit must end where all groups have blocks (Step 5). --prefix-cache-retention-interval keeps more checkpoints ({{cite vllm/config/cache.py:272-278}}).
  • A large attention block size on a Mamba hybrid. The platform logs "Setting attention block size to N tokens" ({{cite vllm/platforms/interface.py:1103-1109}}). Larger blocks make prefix hits coarser.

Why it matters. For models with sliding-window or Mamba layers, the hybrid manager decides how many requests fit in the KV cache. To size a deployment, you must know which layers keep every block, which free them, and when the manager is off.

Why do all KV cache groups need the same page size?

All groups take block ids from one block pool, and their KV cache tensors use the same bytes from offset 0 ({{cite vllm/v1/core/kv_cache_planning.py:685-694}}). A block id belongs to one group at a time, so it must mean the same number of bytes in every group ({{cite vllm/v1/kv_cache_interface.py:1465-1467}}).

 A sliding-window layer has a window of 128 and block size 16. A request has processed 300 tokens. How many leading places of its block table hold the null block?

The skipped tokens are 300 − 128 + 1 = 173 ({{cite vllm/v1/core/single_type_kv_cache_manager.py:1176-1179}}). That is 173 // 16 = 10 whole blocks, so 10 places hold the null block ({{cite vllm/v1/core/single_type_kv_cache_manager.py:713-719}}).

 What happens to a sliding-window model when you pass --disable-hybrid-kv-cache-manager?

The sliding-window specs become full-attention specs, so all layers form one group and keep every block. The attention still computes only the window ({{cite vllm/v1/core/kv_cache_planning.py:853-876}}, {{cite vllm/v1/core/kv_cache_planning.py:785-808}}).

 In the gpt-oss-20b deep dive, why does the sliding-window group need 1,033 blocks per request at start-up, and not cdiv(128, 16) = 8?

The group frees blocks only for processed tokens. Blocks for every in-flight token stay allocated: up to max_concurrent_batches × max_num_batched_tokens ({{cite vllm/config/vllm.py:600-608}}). The cap adds them to window − 1, plus one block because the window may start inside a block ({{cite vllm/v1/kv_cache_interface.py:922-929}}).

 A model has one full-attention group and one sliding-window group. The full-attention walk finds 96 cached tokens, but the sliding-window group has a valid hit only at 64 tokens. What is the hit, and what does the scheduler remember?

The hit is 64 tokens: the sliding-window group cuts the candidate length, and the full-attention blocks are cut to 64 ({{cite vllm/v1/core/kv_cache_coordinator.py:896}}, {{cite vllm/v1/core/kv_cache_coordinator.py:909-922}}). The longest group hit was 96, so 32 tokens are an uncached common prefix ({{cite vllm/v1/core/kv_cache_coordinator.py:927}}). The request stores shared_prefix_boundary = 64 + 32 = 96 ({{cite vllm/v1/core/kv_cache_manager.py:316-318}}). When its blocks get hashes, the sliding-window mask keeps the blocks that end at 96, so a later request can hit 96 tokens ({{cite vllm/v1/core/single_type_kv_cache_manager.py:510-512}}, {{cite vllm/v1/core/single_type_kv_cache_manager.py:1131-1140}}).
