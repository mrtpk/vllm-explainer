The idea

The {{term front-end}} of vllm serve is the API server process. It parses HTTP requests, renders prompts, talks to the engine core and turns the engine output into OpenAI responses ({{link concepts/openai-server}}). Several parts of this work are open to {{term plugin | plugins}}, because deployments differ in these places. Examples are extra routes, output formats, model-specific parsing, adapter storage and metrics systems.

Each front-end extension point reaches vLLM in its own way:

  • {{term endpoint-plugin | Endpoint plugins}} (group vllm.endpoint_plugins) add HTTP routes, and can replace an existing route. They load only when VLLM_PLUGINS names them.
  • {{term io-processor-plugin | IO processor plugins}} (group vllm.io_processor_plugins) change the input and output of a pooling model.
  • {{term tool-parser | Tool parsers}} and {{term reasoning-parser | reasoning parsers}} are registries. A flag imports your module: --tool-parser-plugin or --reasoning-parser-plugin.
  • {{term lora-resolver | LoRA resolvers}} are a registry that a {{term general-plugin}} fills.
  • {{term stat-logger | Stat loggers}} (group vllm.stat_logger_plugins) receive the statistics of each engine step.

An everyday comparison. Think of the reception of a hotel. A partner company can add a service desk (an endpoint) or bring a translator for some guests (a parser). It can give the porters a list of storage rooms for unknown luggage (a resolver), or put a counter on the door (a stat logger). The comparison stops here: in vLLM the receptionist does not ask the partner; each plugin must be installed and, for routes, named in an allowlist.

Step 3: tool parser and reasoning parser plugins

ToolParserManager keeps two dicts: classes and lazy entries (module path, class name) ({{cite vllm/tool_parsers/abstract_tool_parser.py:243-244}}). vLLM registers its own parsers lazily at import ({{cite vllm/tool_parsers/__init__.py:264-270}}). A lookup tries the classes first, then imports a lazy entry and caches it:

register_module has two forms ({{cite vllm/tool_parsers/abstract_tool_parser.py:327-370}}). With module=... it registers the class at once; force=False raises KeyError for a taken name. As a decorator it only stores a lazy entry with the class's module and name, and overwrites any entry with that name. ReasoningParserManager has the same shape ({{cite vllm/reasoning/abs_reasoning_parsers.py:225-373}}).

Your module reaches the manager through a flag:

  1. Lines 579-583. The value is imported only if it is longer than 3 characters. The code does not say why.
  2. import_plugin tries a module name first, then a file path. A file that fails to import is logged, not raised ({{cite vllm/utils/import_utils.py:81-98}}). The file is loaded under its file name as a module and put into sys.modules ({{cite vllm/utils/import_utils.py:101-116}}), so a decorator entry that points to it works.
  3. Lines 589-594. With --enable-auto-tool-choice, an unknown --tool-call-parser raises KeyError at start-up. So a plugin that failed to import shows up here.

The API server calls init_parser_plugin in setup_server and again in run_server_worker ({{cite vllm/entrypoints/launchers/launcher.py:369-370}}, {{cite vllm/entrypoints/launchers/api_server/entry.py:183}}). The reasoning parser is also needed in the engine core, for structured outputs. So the engine core imports the reasoning parser plugin itself, with the same length rule:

The page {{link concepts/tool-and-reasoning-parsers}} explains what the parsers do with the text.

The tool calling guide ends its plugin example with register_lazy_module(name="example", module_path="vllm.tool_parsers.example", ...) ({{cite docs/features/tool_calling.md:676-681}}). Step 4: LoRA resolvers

A resolver finds a LoRA adapter by name when a request asks for a model name that the server does not know. The registry holds instances by name; a second registration overwrites with a WARNING ({{cite vllm/lora/resolver.py:52-72}}). vLLM ships two resolvers, as general plugins:

  • Filesystem resolver. It registers only when VLLM_LORA_RESOLVER_CACHE_DIR is set, and raises ValueError if that is not a directory ({{cite vllm/plugins/lora_resolvers/filesystem_resolver.py:49-61}}).
  • HF Hub resolver. It needs VLLM_LORA_RESOLVER_HF_REPO_LIST and the name lora_hf_hub_resolver in VLLM_PLUGINS, "because it allows remote downloads" ({{cite vllm/plugins/lora_resolvers/hf_hub_resolver.py:129-147}}).

The serving layer copies all resolvers when it starts ({{cite vllm/entrypoints/openai/models/serving.py:113-117}}). It asks them only when VLLM_ALLOW_RUNTIME_LORA_UPDATING is on:

The resolvers run in registration order. The first one that finds the adapter and loads it wins. If a found adapter fails to load, vLLM logs a WARNING and asks the next resolver. When adapters were found but none loads, the answer is HTTP 400 ({{cite vllm/entrypoints/openai/models/serving.py:315-359}}). The page {{link concepts/lora-serving}} covers adapters in general.

attach_endpoint_plugins rebuilds the route list after the plugins have attached their routes ({{cite vllm/plugins/endpoint_plugins/interface.py:108-146}}):

  1. Remember the ids of all routes that exist before the plugins run (line 109).
  2. Call attach_router(app) for each plugin, in discovery order (lines 110-111).
  3. Walk all routes. A new APIRoute removes the methods it shares with an earlier route of the same path. An earlier route with no methods left is dropped; one with other methods stays, as a copy (lines 121-139).
  4. Insert the new route at the place of the first route it replaced, so it stays ahead of mounts (lines 133, 140).
  5. Reset the OpenAPI schema, and keep the plugin list in app.state.endpoint_plugins for phase B (lines 144-146).

So a later plugin also replaces an earlier plugin's route for the same method. A test checks this ({{cite tests/plugins_tests/test_endpoint_plugins.py:280}}).

What can go wrong

Without VLLM_PLUGINS, vLLM only warns "Found endpoint plugin(s) ... but VLLM_PLUGINS is not set" ({{cite vllm/plugins/__init__.py:125-130}}). Set VLLM_PLUGINS to the entry-point name. Remember that this list then also filters the general, platform and stat logger plugins.
  • A short parser plugin value is ignored. Three characters or fewer are not imported ({{cite vllm/entrypoints/common/cli_args.py:579}}).
  • A broken parser file only logs. The ERROR log "Failed to load module ..." is easy to miss. Start-up then fails later with "invalid tool call parser" only when auto tool choice is on ({{cite vllm/utils/import_utils.py:94-98}}, {{cite vllm/entrypoints/common/cli_args.py:589-594}}).
  • The resolver never runs. VLLM_ALLOW_RUNTIME_LORA_UPDATING is off, or VLLM_PLUGINS filtered out the general plugin that registers it.
  • A stat logger class is wrong. A non-StatLoggerBase entry raises TypeError in AsyncLLM.__init__ and stops start-up ({{cite vllm/v1/metrics/loggers.py:88-94}}).
  • An IO processor plugin is missing. A pooling model that names a plugin fails with "The model requires the ... IO Processor plugin but it is not installed" ({{cite vllm/plugins/io_processors/__init__.py:79-84}}).

Why it matters. These plugins change what clients see: routes, response formats, parsed tool calls and metrics. They all live in the API server, so they cost no GPU time, but a mistake in them shows up directly in the HTTP responses.

Which front-end plugin group loads only when VLLM_PLUGINS names it?

vllm.endpoint_plugins. With VLLM_PLUGINS unset, load_endpoint_plugins returns an empty list after a warning ({{cite vllm/plugins/__init__.py:122-131}}).

 What must the object behind a vllm.stat_logger_plugins entry point be?

A class that subclasses StatLoggerBase, else TypeError ({{cite vllm/v1/metrics/loggers.py:87-94}}).

 You pass --reasoning-parser-plugin my.py --reasoning-parser mine. In which processes does vLLM import my.py?

In two processes. "my.py" has 5 characters, so it passes the length rule. The API server imports it ({{cite vllm/entrypoints/common/cli_args.py:582-583}}), and the engine core imports it again for structured outputs ({{cite vllm/v1/structured_output/__init__.py:103-104}}).

 Your endpoint plugin registers POST /v1/completions. What happens to vLLM's own route, and to a GET on the same path?

The plugin route replaces the core POST route; other methods of the path stay ({{cite vllm/plugins/endpoint_plugins/interface.py:121-141}}, docstring {{cite vllm/plugins/endpoint_plugins/interface.py:72-74}}).

 A request asks for model "sql-lora", which the server does not know. You set VLLM_LORA_RESOLVER_CACHE_DIR=/loras and VLLM_PLUGINS=acme_admin. Is the adapter found?

No. The filesystem resolver registers from the general plugin lora_filesystem_resolver ({{cite pyproject.toml:45-46}}), and VLLM_PLUGINS=acme_admin filters it out ({{cite vllm/plugins/__init__.py:63-64}}). Also, resolvers run only with VLLM_ALLOW_RUNTIME_LORA_UPDATING=1 ({{cite vllm/entrypoints/serve/engine/serving.py:62-66}}). The request gets "The model `sql-lora` does not exist."
