--- title: The forward context: how layers find per-step data nav_title: Forward context level: Advanced prerequisites: concepts/model-definition, learn/pytorch-for-serving, concepts/model-runner related: code/forward-context, code/model-executor-layers-attention-attention, concepts/attention-backends, concepts/compile-and-cuda-graphs, concepts/model-runner, concepts/model-definition, tours/forward-pass summary: Attention layers register themselves by name when the model is built, get their KV cache tensor bound at start-up, and read the per-step metadata from a global forward context that the model runner sets around each forward pass. The attention custom ops take only the layer name, so torch.compile sees them as opaque. --- An attention layer gets no KV cache or metadata arguments. It looks them up by its own name in a context that the runner sets.

The idea

A model file calls self.attn(q, k, v) and nothing else ({{link concepts/model-definition}}). But attention needs more: the {{term kv-cache-block | KV cache}} tensor of this layer, where to write the new keys and values, and the shape of the batch. vLLM passes these through two dictionaries keyed by the layer name, the {{term model-prefix}} such as model.layers.0.self_attn.attn:

  • The {{term static-forward-context}} maps each name to its layer object. A layer adds itself when it is built. At start-up, the runner binds each layer's KV cache tensor to the object, as layer.kv_cache.
  • The {{term forward-context}} exists only during one forward pass. The model runner sets it with the {{term attention-metadata}} per layer name, the {{term slot-mapping}} per layer name, the CUDA graph mode and a {{term batch-descriptor}}.

The attention custom op gets the tensors q, k, v and output, plus the layer name. Inside, it looks up the layer, the KV cache, the metadata and the slot mapping. Why so indirect? For torch.compile, the op is one opaque node with plain inputs ({{link learn/pytorch-for-serving}}). The graph does not depend on Python objects that change every step, so vLLM can compile it once and split it at these ops.

An everyday comparison. Think of a theater with a prop table. Each actor has a spot on the table, labeled with the actor's name. Before each show, the stage manager puts that night's props on each labeled spot. During the show, an actor walks to the table and takes the props under the label. The script never lists the props. The comparison stops here: in vLLM, the label also leads to the actor's own permanent locker, the KV cache, which nobody refills between shows.

The picture

Follow the name model.layers.0.self_attn.attn through the three panels. It is a key in every dictionary. The violet parts happen once at start-up; the blue parts happen in every step.

In the code

Step 1: the layer registers itself by name

  1. Line 440. use_direct_call is false on platforms that want "one giant opaque custom op" for attention. CUDA, ROCm, CPU and XPU return true from opaque_attention_op() ({{cite vllm/platforms/cuda.py:595-596}}, {{cite vllm/platforms/rocm.py:1231-1232}}, {{cite vllm/platforms/cpu.py:640-641}}, {{cite vllm/platforms/xpu.py:609-610}}); the base Platform returns false ({{cite vllm/platforms/interface.py:1286-1290}}).
  2. Lines 443-445. The prefix is the key. A second layer with the same prefix raises ValueError: Duplicate layer name.

The dict is a field of the compilation config. Its docstring says: "Map from layer name to layer objects that need to be accessed outside model code" ({{cite vllm/config/compilation.py:757-760}}). Attention is not the only user. MLA attention ({{cite vllm/model_executor/layers/attention/mla_attention.py:620}}), the MoE runner ({{cite vllm/model_executor/layers/fused_moe/runner/moe_runner.py:68}}), Mamba layers ({{cite vllm/model_executor/layers/mamba/mamba_mixer2.py:528}}) and LoRA linear layers ({{cite vllm/lora/layers/base_linear.py:102}}) also register.

The runner reads this dict to find all attention layers. get_layers_from_vllm_config filters it by type ({{cite vllm/config/vllm.py:3596-3617}}), and the KV cache spec of the model comes from these layers ({{cite vllm/v1/worker/gpu/attn_utils.py:138-155}}).

Step 2: the runner binds the KV cache tensor

When the KV cache is allocated, init_kv_cache gets compilation_config.static_forward_context as its first argument ({{cite vllm/v1/worker/gpu/model_runner.py:794-797}}). It allocates one backing buffer and makes a view per layer, then binds each view to its layer:

The default bind_kv_cache just stores the view: self.kv_cache = kv_cache ({{cite vllm/model_executor/layers/attention_layer_base.py:27-33}}). Until then, the layer holds an empty placeholder tensor ({{cite vllm/model_executor/layers/attention/attention.py:461-464}}). The binding happens once; the tensor stays the same for the whole life of the server. How the views are laid out is on {{link concepts/attention-backends}}.

Step 3: the runner sets the forward context each step

For PIECEWISE and eager steps, Model Runner V2 wraps the model call:

set_forward_context builds a ForwardContext and installs it in a module-level variable for the duration of the with block:

  • no_compile_layers is the static dict itself, not a copy: create_forward_context passes the same object ({{cite vllm/forward_context.py:247-248}}).
  • attn_metadata and slot_mapping are dicts from layer name to value. They are built fresh each step ({{link concepts/model-runner}}, Step 6).
  • cudagraph_runtime_mode and batch_descriptor tell the CUDA graph wrappers inside the compiled model what to do ({{link concepts/compile-and-cuda-graphs}}).

The context manager restores the previous context on exit ({{cite vllm/forward_context.py:262-274}}). Any code inside the forward pass reads it with get_forward_context() ({{cite vllm/forward_context.py:208-214}}).

Step 4: the attention layer calls a custom op with its name

  1. Line 563. The name is wrapped by _encode_layer_name. On PyTorch 2.11 or newer with VLLM_USE_LAYERNAME=1 (the default), it becomes a LayerName object; else it stays a str ({{cite vllm/utils/torch_utils.py:990-995}}, {{cite vllm/utils/torch_utils.py:1045-1047}}).
  2. Lines 564-572. Only when the backend does not write the KV cache inside its own forward, a first op writes k and v into the cache. It returns an empty tensor, the "dummy dependency".
  3. Lines 573-580. The attention op takes the dummy as an argument, so the compiler cannot move it before the cache write ({{cite vllm/model_executor/layers/attention/attention.py:779-782}}). It returns nothing and writes into output.

At this commit, the FlashAttention, FlashInfer and Triton backends set forward_includes_kv_cache_update = False, so they use the separate update op ({{cite vllm/v1/attention/backends/flash_attn.py:367}}, {{cite vllm/v1/attention/backends/flashinfer.py:708}}, {{cite vllm/v1/attention/backends/triton_attn.py:347}}). The base class default is True ({{cite vllm/v1/attention/backend.py:69-70}}).

Step 5: get_attention_context resolves the name

  1. Line 709. The normal case: attn_metadata is a dict, and the layer's entry is taken.
  2. Line 713. A list of dicts: the comment says index 0 holds the base model's metadata in speculative decoding.
  3. Lines 716-717. The layer object comes from no_compile_layers, and the KV cache from the attribute bound in Step 2.
  4. Line 722. The slot mapping may be None; then unified_kv_cache_update writes nothing ({{cite vllm/model_executor/layers/attention/attention.py:736}}).

Then the two ops call the backend: impl.do_kv_cache_update(...) ({{cite vllm/model_executor/layers/attention/attention.py:740-746}}) and impl.forward(self, query, key, value, kv_cache, attn_metadata, output=...) ({{cite vllm/model_executor/layers/attention/attention.py:786-796}}). The backend classes are on {{link concepts/attention-backends}}.

Step 6: why a name and not the tensors

The two ops are registered once, at import, in the vllm library ({{cite vllm/model_executor/layers/attention/attention.py:759-764}}, {{cite vllm/model_executor/layers/attention/attention.py:799-803}}). For the compiler, three facts follow:

  • Opaque. Dynamo records one node per call and does not trace into the backend code. The node has only tensors and a name as inputs.
  • A splitting point. The op names are in the default {{term splitting-op | splitting ops}}, so vLLM cuts the graph here. Attention then runs eagerly between piecewise CUDA graphs and can use any batch shape ({{cite vllm/config/compilation.py:768-770}}, {{cite vllm/config/compilation.py:1184}}).
  • One graph for 32 layers. A str argument is a constant in the graph. The LayerName class is an opaque type. torch.compile "lifts [it] as a graph input instead of baking it as a constant", which avoids "per-layer recompilation" ({{cite vllm/utils/torch_utils.py:1003-1010}}).

The code also says that the string in unified_kv_cache_update "prevents Inductor from reusing piecewise graphs"; this is why that op is a splitting op too ({{cite vllm/config/compilation.py:1186-1213}}).

Step 7: FULL CUDA graph steps do not read the context

In FULL mode the runner replays one graph and does not call set_forward_context ({{cite vllm/v1/worker/gpu/model_runner.py:2024-2032}}). No Python code of the model runs, so no layer looks anything up. The comment says the inputs "are already copied to the CUDA graph input buffers" (lines 2026-2027). The context was used at capture time: the capture runs the model inside set_forward_context, with the dummy metadata of that batch shape ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:754-771}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Llama-3-8B has 32 decoder layers. So the static dict has 32 attention entries, from model.layers.0.self_attn.attn to model.layers.31.self_attn.attn (prefix rules on {{link concepts/model-definition}}). All 32 layers use full attention and one backend, so there is one {{term kv-cache-group}} and one attention group (derived).

  1. Metadata dict. build_attn_metadata builds one metadata object for the group and stores the same object under all 32 names ({{cite vllm/v1/worker/gpu/attn_utils.py:574-580}}).
  2. Slot mapping dict. build_slot_mappings_by_layer stores the same row tensor of group 0 under all 32 names ({{cite vllm/v1/worker/gpu/attn_utils.py:447-455}}).
  3. Lookups. Each layer does three dict lookups and one attribute read per op call. With two ops per layer, a step does 64 calls of get_attention_context (derived, eager or PIECEWISE mode).

A model with several KV cache groups, for example sliding-window and full layers, gets one metadata object per group. Each layer name points to the object of its group ({{link concepts/hybrid-kv-cache}}).

The comment on all_moe_layers explains a second way around strings in the graph. MoE custom ops pop the next layer name from this list instead of taking it as a constant ({{cite vllm/forward_context.py:170-195}}). On PyTorch 2.11 or newer, vLLM turns fast_moe_cold_start off, because the LayerName approach replaces it ({{cite vllm/config/vllm.py:1913-1918}}).
  1. If batch-size logging is on and attn_metadata is not None, take the start time ({{cite vllm/forward_context.py:295-297}}).
  2. For an MoE model with DP > 1 (or sequence-parallel MoE), make DPMetadata. If the caller gave no token counts across ranks, they are computed with a collective here, and padding across ranks is off ({{cite vllm/forward_context.py:308-322}}).
  3. If num_tokens is given and no descriptor, make BatchDescriptor(num_tokens=num_tokens) (lines 331-332).
  4. Ask the platform for extra fields (lines 334-343).
  5. Build the context and install it with override_forward_context (lines 345-360).
  6. On exit, in the same case, synchronize the device and record the forward time per batch size. Every VLLM_LOG_BATCHSIZE_INTERVAL seconds, log the median time per size ({{cite vllm/forward_context.py:362-392}}).

VLLM_LOG_BATCHSIZE_INTERVAL defaults to -1, which turns the logging off ({{cite vllm/envs.py:1445-1447}}). The module reads it once, at import ({{cite vllm/forward_context.py:22-25}}).

KV sharing. A layer built with kv_sharing_target_layer_name reuses the cache of an earlier layer. The constructor checks the target in the static dict: it must exist, come before this layer and have the same attention type ({{cite vllm/model_executor/layers/attention/attention.py:61-91}}). Such a layer skips the cache write (line 566), and its KV cache entry points to the target's tensor ({{cite vllm/v1/worker/gpu/attn_utils.py:427-428}}).

KV connector. unified_attention_with_output has the decorator @maybe_transfer_kv_layer. With a KV connector, it waits for the layer's KV to load before the attention and saves it after ({{cite vllm/model_executor/layers/attention/kv_transfer_utils.py:15-55}}). It finds the layer data through the same get_attention_context. See {{link concepts/kv-connectors}}.

What can go wrong

  • A model call outside a context. get_forward_context() asserts "Forward context is not set. Please use `set_forward_context` to set the forward context." ({{cite vllm/forward_context.py:210-213}}). This happens when you call the model directly in a test or a script.
  • Two layers with one prefix. ValueError: Duplicate layer name at model build time ({{cite vllm/model_executor/layers/attention/attention.py:443-444}}).
  • A wrong KV sharing target. ValueError "must come before the current layer", "is not a valid Attention layer in the model" or "must be the same type" ({{cite vllm/model_executor/layers/attention/attention.py:80-91}}).
  • Batch-size logging slows the server. With VLLM_LOG_BATCHSIZE_INTERVAL >= 0, every forward pass that runs inside set_forward_context with metadata ends with a device synchronize ({{cite vllm/forward_context.py:295}}, {{cite vllm/forward_context.py:363-370}}). In Model Runner V2 these are the eager and PIECEWISE steps; FULL replays have no context. That removes the CPU/GPU overlap of {{link concepts/async-scheduling}}. The comment above it still says "we use synchronous scheduling right now" (line 365); with the default async scheduling this is no longer true.
  • A backend without a separate cache write. If a backend says forward_includes_kv_cache_update = False but has no do_kv_cache_update, the update op fails its assertion ({{cite vllm/model_executor/layers/attention/attention.py:737-739}}).

Why it matters. The forward context is the contract between the model runner, the model code and the attention backends. A model file stays free of serving details, the compiler sees a clean graph, and a new backend only needs to read its metadata. When you write a model or a backend plugin, keep the layer name unique, and read per-step data from the context, never from arguments.

Which key does the first Llama attention layer use in static_forward_context?

Its prefix, model.layers.0.self_attn.attn. The constructor stores static_forward_context[prefix] = self ({{cite vllm/model_executor/layers/attention/attention.py:445}}).

 Where does unified_attention_with_output get the KV cache tensor from?

From get_attention_context: it takes the layer object from forward_context.no_compile_layers[layer_name] and reads layer.kv_cache ({{cite vllm/model_executor/layers/attention/attention.py:716-717}}). The runner set that attribute once, in bind_kv_cache_to_layers ({{cite vllm/v1/worker/utils.py:879-880}}).

 Why does unified_kv_cache_update return an empty tensor?

As a data dependency. The attention op takes it as kv_cache_dummy_dep, so torch.compile keeps the cache write before the attention ({{cite vllm/model_executor/layers/attention/attention.py:731-733}}, {{cite vllm/model_executor/layers/attention/attention.py:779-782}}).

 In a FULL CUDA graph step, how many times is get_attention_context called in Python, and why?

Zero. The runner replays the captured graph without set_forward_context and without Python model code ({{cite vllm/v1/worker/gpu/model_runner.py:2024-2032}}). The lookups ran once, at capture time, inside set_forward_context ({{cite vllm/v1/worker/gpu/cudagraph_utils.py:754-771}}).

 On PyTorch 2.14, how does the layer name reach the attention op, and what would go wrong with a plain string?

As a LayerName object, because PyTorch is 2.11 or newer and VLLM_USE_LAYERNAME defaults to 1 ({{cite vllm/utils/torch_utils.py:990-995}}, {{cite vllm/envs.py:1451}}). It is a hoisted opaque type that becomes a graph input. A plain string is baked in as a constant, which the code says causes per-layer recompilation ({{cite vllm/utils/torch_utils.py:1003-1010}}).
