The front end picks the name from the checkpoint or --quantization and makes one config object; each layer in the worker asks it for a quantize method that makes the weights and runs the forward. --- A quantization method is a named QuantizationConfig class; each layer asks the config object for a quantize method that owns its weights.

The idea

A quantized checkpoint stores weights in fewer bits, with scales ({{deepinfer learn/number-formats | Number formats}}). The page {{link learn/quantized-checkpoints}} explains the formats and the memory that they save. This page explains the code path: how vLLM knows the format, and how a layer gets the right weights and kernel.

Each format is a {{term quantization-method}}. In code it is a class pair. The {{term quantization-config}} holds the settings of one checkpoint, for example the group size of AWQ. The {{term quantize-method}} works on one layer: it makes the layer's weight tensors, and it runs the layer's matrix multiply. The config chooses a quantize method for each layer, so one model can mix methods, for example a quantized MLP and an unquantized lm_head.

vLLM keeps a table from a name, such as "fp8" or "awq", to a config class. A {{term plugin}} adds a name with the decorator @register_quantization_config. Then --quantization my_quant, or a checkpoint whose config says "quant_method": "my_quant", uses the new class. No file of vLLM changes.

An everyday comparison. Think of a print shop that receives files in many formats. At the front desk, a clerk reads the file header and picks the matching instruction sheet. The sheet says, for each page, which machine and which paper to use. The machine operators only follow the sheet. A new format needs a new sheet, not new machines. The comparison stops here: in vLLM, the front desk (the API server) passes a copy of the filled-in sheet to every worker.

  1. Lines 89-95. A name that exists already is not an error. vLLM logs at DEBUG level and overwrites it. A plugin can replace a built-in method this way.

Step 4: how vLLM picks the method name

ModelConfig._verify_quantization runs in ModelConfig.__post_init__ ({{cite vllm/config/model.py:922}}), in the front end. It reads the checkpoint's quant_method and asks every method whether it wants to take over:

  1. Line 1392. The checkpoint names a method in quant_method, for example "awq".
  2. Lines 1396-1416. Seventeen built-in names are "overrides": their class has its own override_quantization_method. The order matters, "particularly ... for GPTQ".
  3. Lines 1420-1426. All other names come first, then the overrides. Plugin names are in the first part, so "custom overrides have preference over the built-in ones".
  4. Lines 1429-1433. The first method whose override_quantization_method returns a name wins. For an AWQ checkpoint on a GPU, AutoAWQConfig answers "auto_awq" ({{cite vllm/model_executor/layers/quantization/auto_awq.py:263-286}}).
  5. Lines 1438-1447. A built-in method that overrides but is missing from the list raises ValueError. This guards vLLM's own code, not plugins.

The rest of the method checks the result ({{cite vllm/config/model.py:1452-1485}}). --quantization must match the checkpoint, unless an override changed it. An unknown name raises "Unknown quantization method". The platform can refuse the name in verify_quantization. A deprecated name raises unless --allow-deprecated-quantization is set.

Step 5: one config object, made in the front end

VllmConfig.__post_init__ makes the object once:

get_quant_config finds the settings. It reads quantization_config from the HF config, or from its text_config, or compression_config, and calls from_config with that dict ({{cite vllm/model_executor/model_loader/weight_utils.py:239-279}}). Without one, it looks for the files that get_config_filenames() names. If that list is empty, it calls the class with no arguments ({{cite vllm/model_executor/model_loader/weight_utils.py:352-368}}). So a plugin that quantizes a BF16 checkpoint at load time needs a constructor without required arguments.

--quantization fp8 on a BF16 checkpoint does not fail. Fp8Config names no config file, so get_quant_config logs "--quantization fp8 is deprecated for online quantization; use --quantization fp8_per_tensor instead." and returns an OnlineQuantizationConfig ({{cite vllm/model_executor/model_loader/weight_utils.py:354-363}}). With an FP8 checkpoint, the same flag uses Fp8Config.from_config.

Step 6: how the workers get the config

The worker does not look up the name again. quant_config is a field of VllmConfig, and the engine core and the workers get the whole VllmConfig pickled, as an argument of the new process ({{cite vllm/v1/engine/utils.py:256-287}}). Python imports the module of the config class while it unpickles the object. So a worker needs your module importable, but not your registration. (Derived from the pickling.)

Two worker paths do look up a name, so register in every process to be safe. A draft model for speculative decoding makes its own config ({{cite vllm/model_executor/models/utils.py:1003-1007}}). The torchao loader calls get_quant_config again ({{cite vllm/model_executor/model_loader/default_loader.py:491-492}}). A {{term general-plugin}} runs the decorator in every process.

Step 7: each layer asks for its quantize method

The model reads the object from the config, for example in Llama ({{cite vllm/model_executor/models/llama.py:370}}), and passes it to each layer with a prefix. A linear layer asks it in its constructor:

resolve_quant_method calls get_quant_method(layer, prefix), and adds online quantization on top when it is configured ({{cite vllm/model_executor/layers/quantization/base_config.py:295-356}}). The prefix is the module name, so the config can skip layers by name. A linear layer must get a method; None raises "All linear layers should support quant method." Other layer types, such as attention, accept None.

The quantize method has two required methods and one important optional one ({{cite vllm/model_executor/layers/quantization/base_config.py:43-85}}):

  • create_weights(layer, ...) makes the parameters and sets them on the layer. A replicated linear layer calls it with the sizes and its weight_loader ({{cite vllm/model_executor/layers/linear.py:379-387}}).
  • apply(layer, x, bias) runs in every forward ({{cite vllm/model_executor/layers/linear.py:420}}).
  • process_weights_after_loading(layer) runs once after the weights are loaded, for example to repack them for a kernel. The loader calls it for every module that has a quant_method ({{cite vllm/model_executor/model_loader/utils.py:157-186}}).

Step 8: a minimal out-of-tree method

The test suite has a complete plugin. It fakes 8-bit quantization of the activations and keeps BF16 weights:

Note the choices. FakeQuantLinearMethod subclasses UnquantizedLinearMethod, so it reuses its create_weights and only changes apply. get_config_filenames() returns [] and the constructor has a default, so --quantization custom_quant works on a normal BF16 checkpoint. The test loads Llama-3.2-1B with it and checks that qkv_proj uses the method ({{cite tests/quantization/test_register_quantization_config.py:130-140}}).

To use such a class with vllm serve, publish a general plugin that imports the module, so that the decorator runs:

# my_quant_pkg/__init__.py  (illustrative, not in the vLLM repository)
def register():
    from my_quant_pkg import config  # noqa: F401  (runs @register_quantization_config("custom_quant"))

# pyproject.toml
# [project.entry-points."vllm.general_plugins"]
# my_quant = "my_quant_pkg:register"
vllm serve meta-llama/Llama-3.2-1B-Instruct --quantization custom_quant

The guide in the docs shows the same pattern, and a MoE method too ({{cite docs/features/quantization/README.md:93-148}}).

A platform has its own hook for this: the docstring of pre_register_and_update says it can import and register "the out-of-tree quantization config" ({{cite vllm/platforms/interface.py:639-651}}). It runs in the front end five times: each time the front end builds a parser, four times in all ({{cite vllm/engine/arg_utils.py:3257}}), and again when create_engine_config starts ({{cite vllm/engine/arg_utils.py:2246}}).

The KV cache data type is a separate setting, --kv-cache-dtype. Its default auto is resolved in two places, and the result depends on the checkpoint format:

  1. ModelOpt checkpoints. EngineArgs resolves auto before it makes CacheConfig ({{cite vllm/engine/arg_utils.py:2285-2288}}). resolve_kv_cache_dtype_string reads the KV scheme only when quant_method starts with "modelopt" ({{cite vllm/utils/torch_utils.py:457-466}}, {{cite vllm/utils/torch_utils.py:509-521}}).
  2. compressed-tensors (llm-compressor) checkpoints. The Attention layer sees kv_cache_scheme on the quant config and turns auto into fp8 while the model is built ({{cite vllm/model_executor/layers/attention/attention.py:287-291}}).
  3. Other checkpoints. auto stays the model dtype ({{cite vllm/utils/torch_utils.py:527-529}}).

The scales come through the same quant config. Each attention layer asks resolve_quant_method for a KV cache method. A quantized one must be a BaseKVCacheMethod, and its create_weights makes k_scale and v_scale parameters that the checkpoint fills ({{cite vllm/model_executor/layers/attention/attention.py:194-226}}). The KV dtype also limits the attention backends ({{link concepts/attention-backend-selection}}).

A new --kv-cache-dtype value has its own registry, register_kv_cache_dtype ({{cite vllm/config/cache.py:111-155}}). No code in vllm/ calls it at this commit; the page {{link concepts/engine-hooks}} explains it.

What can go wrong

The front end checks the name and makes the config object while it builds VllmConfig. If the decorator has not run in the API server process by then, start-up stops with "Unknown quantization method" ({{cite vllm/config/model.py:1464-1469}}). A general plugin runs early enough: the CLI loads it while it builds the parser ({{link concepts/plugin-loading}}).
  • A plugin hides a built-in method. A name collision only logs at DEBUG level, and the plugin class wins ({{cite vllm/model_executor/layers/quantization/__init__.py:89-95}}, {{cite vllm/model_executor/layers/quantization/__init__.py:195}}).
  • The method is refused on ROCm. A platform with a list accepts only listed names. The decorator appends a new name to the list (lines 97-100). It does not append a name that exists already. So ROCm still refuses a plugin that replaces a built-in method missing from its list, such as experts_int8. (Derived from {{cite vllm/model_executor/layers/quantization/__init__.py:89-100}} and {{cite vllm/platforms/rocm.py:625-649}}.)
  • The config class needs arguments. On a checkpoint without quantization settings, vLLM calls your class with no arguments ({{cite vllm/model_executor/model_loader/weight_utils.py:368}}).
  • A deprecated method. fbgemm_fp8 and fp_quant need --allow-deprecated-quantization ({{cite vllm/config/model.py:1472-1485}}).

Why it matters. Most production models are quantized. When a checkpoint loads with the wrong method, or with no method, the model gives wrong answers or uses too much memory. The startup log and the error messages above show which method vLLM picked and why.

Which decorator adds a new quantization method, and what must the class subclass?

@register_quantization_config("name"); the class must subclass QuantizationConfig, else ValueError ({{cite vllm/model_executor/layers/quantization/__init__.py:61}}, {{cite vllm/model_executor/layers/quantization/__init__.py:102-105}}).

 Which method of the quantize method runs in every forward of a linear layer?

apply(layer, x, bias) ({{cite vllm/model_executor/layers/linear.py:420}}). create_weights runs once when the layer is built.

 A checkpoint says "quant_method": "awq" and you pass no flag. Which method name does vLLM use on a GPU, and which code decides?

auto_awq. _verify_quantization asks each method's override_quantization_method ({{cite vllm/config/model.py:1429-1450}}), and AutoAWQConfig answers for "awq" when the platform is not CPU ({{cite vllm/model_executor/layers/quantization/auto_awq.py:263-284}}).

 Your plugin registers "my_quant" only in a script that runs in the API server process. With TP = 2, do the workers fail?

Not for the main model: the workers get the config object inside the pickled VllmConfig ({{cite vllm/v1/engine/utils.py:256-287}}), and need only your module importable. But a draft model or the torchao loader looks the name up again in the worker ({{cite vllm/model_executor/models/utils.py:1003-1007}}, {{cite vllm/model_executor/model_loader/default_loader.py:491-492}}). A general plugin avoids the difference.

 You run --quantization custom_quant on a BF16 checkpoint, and get_config_filenames() returns []. How is the config object made, and what follows for the constructor?

config.json has no quantization config, so get_quant_config goes past line 279. The class names no files, and custom_quant is neither fp8 nor an online shorthand, so vLLM calls quant_cls() with no arguments ({{cite vllm/model_executor/model_loader/weight_utils.py:352-368}}). The constructor must work without arguments; the test class has num_bits: int = 8 ({{cite tests/quantization/test_register_quantization_config.py:71-74}}).
